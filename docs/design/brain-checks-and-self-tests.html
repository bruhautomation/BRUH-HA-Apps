Design proposal · brAIn add-on

What brAIn should check, how it should test itself, and how its bugs should reach you

A catalog of Home Assistant problems brAIn can find without spending a token, a self-test that walks every face of the add-on with a real round trip, and the instrumentation that turns a field report into a reproducible bug.

brAIn 1.28.10 · surveyed panel/, scripts/, ha-mcp-server/, custom_components/brain/, tests/ · 2026-09-02

Today every finding costs a Claude run, and the model is doing the discovery. The analyst sweeps a category on a schedule and is told that an empty findings list is the honest answer, so most runs spend 25–45k tokens to report nothing. Study sessions are the same shape with more turns. Meanwhile the deterministic checks that already exist (orphan references, orphaned devices, restored entities in the power tools) are services nobody schedules and whose output reaches no list.

The biggest lever is to invert that. A checker layer reads the registry, states, statistics, traces and the error log, files findings for zero tokens on an hourly cadence, and hands its ledger to the analyst so Claude spends its run on judgement (is this cupboard contact really stuck?) rather than on search. The second lever is already in the product: every ending on the Findings tab is a labelled outcome, and nothing aggregates them. The third is that field bugs currently arrive as prose, because the add-on has no diagnostics bundle and no run journal to attach.

1House checks: findings that cost nothing

A check is a pure function from a house snapshot to a list of findings in the shape the inbox already takes (text, detail, fix, severity, fixable, entity_id, source: "check:<id>"). It reads what the panel already fetches for the analyst (ha_data.get_registries, states, get_history, get_statistics) plus three sources the analyst does not yet see: automation traces, the WebSocket system_log/list, and dashboard configs. It never calls Claude.

The bar for a check is the same bar the card contract sets for the model: something is actually wrong, it is specific and checkable, and the fix is concrete. A check that fires on a healthy house is worse than no check, because it is the one the person learns to ignore first. Every rule below has a floor or a window for that reason, and the scorecard in section 4 is what proves each one earns its place.

How they plug in

  • One snapshot, many checks. checks.snapshot() fetches registries, states, statistics for the numeric sensors, traces and the system log once, and every check reads from it. It is the same fetch the analyst's snapshot path makes, so the cost is one set of HA calls an hour.
  • Hourly, cheap, and the analyst reads the result. The scheduler runs the checks before any insight run. prompt_block already renders open and dismissed findings into the analyst's prompt; the checker's rows ride the same block. The automations card's focus becomes “the ledger says these three things; what do they miss, and which of them matter here?”, which is the question a model is good at.
  • Every check is a fixture test. tests/fixtures/houses/ holds registry and state dumps with planted defects, and each check has a test that asserts it finds exactly the planted rows and nothing else on the clean house. The checks are pure functions, so this is the ordinary suite, not the manual one.
  • Surfaces. brain check [group] on the CLI (through the panel API, like brain findings, so there is one writer); brain.check as an HA service with response data; a button.brain_run_checks entity; POST /api/checks/run for the tab. All four end in the same inbox.
  • Optionally, HA Repairs. A findings_to_repairs option (default off) mirrors serious+ findings into create_repair_issue, and ending the finding removes the issue. It meets people where HA already tells them things, and it is off by default because a Repairs page with twelve brAIn issues on it is the tab moved somewhere with worse buttons.

2Questions people actually ask

Four services where the answer is a deterministic walk that Claude narrates, rather than a sweep Claude performs. Each is an HA service with response data, a brain CLI verb, and a chat command, because the same question is asked from an automation trace, a terminal and a phone.

Why did that happen?

“Why did the hallway light come on at 3am” is the most common question in any HA forum, and the answer is already in the recorder: a state change carries a context_id, and its context_parent_id points at the automation, script, service call or user that caused it. get_logbook does not surface context today. Add it, walk the chain server-side to a root cause, and hand Claude the chain to narrate: “Hallway light turned on at 03:12 because Night motion fired on binary_sensor.hallway_motion, which reported motion for 2s. That sensor has tripped at night 6 times this week.” brain.why takes an entity id and an optional time; the chat answers why did … the same way.

What changed since…

A diff of two check snapshots: entities that went unavailable, automations that errored for the first time, new entities, renamed entities, integrations that failed setup. The sys.after_update check is this service with the update as the “since”. brain.changes with since: 24h | last update | last backup.

Explain this error

sys.log_storm finds the noisiest logger; this takes one entry from the system log (or an error the person pastes) and answers in three parts: which integration and device it belongs to, what it usually means, and what to try. Claude is doing the reading here and that is the right use of it. The value over pasting into the chat is that the service pre-fetches the integration's config entry, the device and the last trace, so the answer is about this house.

Rehearse an automation

Given an automation id and an optional “as if” (a time, an entity state), evaluate its conditions against the live house and report which would pass and which would not, from the same condition code HA runs. No actions are executed; this is a read. It answers “will my morning routine fire tomorrow” before tomorrow. It needs one new read-only MCP tool (evaluate_condition, a WebSocket test_condition call) which must land on ANALYST_TOOLS and be asserted in test_security.py as a read.

3brAIn testing itself in situ

brain doctor answers “is the plumbing connected”. The gap is “does each face work end to end, right now, on this install”, which is what every field report is really about. BRight's director_check is the shape to copy: walk the chain, do a real trivial round trip, stop at the first break, and make the sentence at that break name the switch or the log to look at.

brain doctor --deep

Planted defects: a rehearsal on the real house

The checks in section 1 are testable in the suite on fixture houses. What the suite cannot see is this install's HA version, its integrations and its data shapes, which is where every late bug has lived. So brain doctor --rehearse (opt-in, with a consent prompt naming exactly what it creates) installs a small set of helpers and automations under a brain_test_ prefix: an automation referencing a non-existent entity, one disabled, one whose condition can never pass, an input_number it freezes. It runs the checks and asserts each planted defect is found and nothing else under the prefix is, then runs the analyst's automations card and reports whether the model found the same planted rows. Then it removes everything it created and verifies the removal.

That last step is the interesting number: it is a live precision/recall reading of the prompt and model on this house, per version, and it is what makes a prompt change measurable somewhere other than the developer's own home.

Health as an entity

  • --json on brain doctor, so the panel, the sensor and the diagnostics bundle read one structured verdict rather than scraping text.
  • sensor.brain_health that never goes unavailable, on the usage tracker sensor's pattern: its state is the worst stage (ok, degraded, failed) and its attributes carry the failing stage's sentence. HA hides attributes of an unavailable entity, which is why the tracker sensor exists, and the same rule applies here.
  • A canary automation (opt-in): once a day, brain.run_task with “reply OK” and a sensor recording the round-trip seconds. A missed canary is the earliest external signal that a listener died, and it costs one tiny turn.

4The feedback loop: catching bugs and measuring the model

Read the CLAUDE.md history and one pattern repeats: a silent fallback read as the real thing, a stale value reported as fresh, a swallowed stderr, a guard that refused without changing the next attempt. None were visible from the suite; all were visible from inside the add-on if anything had been counting. This section is about making the add-on count, and making what it counts leave the house in a form that can be attached to an issue.

Run journal

/data/journal.jsonl, capped and rotated, one line per Claude run of any kind: insight, ask, fix, study, consolidation, chat turn, voice turn, automation task, auth check, doctor stage. usage_store.record_run already records tokens per insight id; the journal is that ledger widened to every path and to the fields that explain a failure.

source
the same vocabulary run_sources.SOURCES uses, so a journal row and a Chats rail row agree on who ran what
model · duration · tokens
from the result envelope via split_from_meta, one derivation
outcome
ok, timeout (124 by name), max_turns, unparseable (with the capped raw tail, as the fixer already keeps), auth, denied, crash (exit code plus the stderr tail)
fallbacks
flags for every silent slide: search→snapshot, pool→one-shot, resume→fresh, --session-id rejected, account usage→local estimate
silent excepts
a counter keyed by site name for every except that deliberately does nothing, so a failure that is swallowed by design is at least counted by design

The panel gets a Diagnostics section under ⚙ (not a sixth tab) that reads the journal: runs in the last 24h by source and outcome, fallbacks taken, the last ten failures with their tails. The usage popover's breakdown is already one view of this ledger; this is the other.

Diagnostics bundle

brain report writes one redacted archive to /share/brain/reports/ and the docs' Troubleshooting page grows a “Copy a report” button that produces the same thing. The custom integration also implements diagnostics.py, so the standard Download diagnostics button on the integration page yields the same bundle, because that is the button HA users already know how to find and the one issue templates already ask for.

The GitHub issue template asks for the bundle by name. A report that arrives with one is a bug with a run id, a model, an exit code and a fallback flag; a report that arrives without one is the prose the project gets today.

Producer scorecard

Every ending on the Findings tab is a label: I did it and Fix it → Got it are true positives, Wrong is a false positive with a free-text reason, a snooze that expires unended is a shrug. The settled ledger records the kind and the note but not the producer, so the one field to add is source on _remember_settled. With it, the panel can compute precision per producer: per check id, per insight category, per study topic, per model.

Two readers. The person sees a line under the Findings filter: “Battery checks: 11 of 12 confirmed. Automations card: 6 of 9 wrong.” That is the number that makes the tab trusted or ignored, and it lets them switch off a check that is wrong in their house. The developer sees the same numbers in the bundle, aggregated, and that is the number that says which producer to fix next. A check under 70 % precision across reports is a check with a bad floor, and the Wrong notes say why in the person's own words.

Corpus and replay

The BRight detect_hits bug is the lesson: the suite's only fixture was a synthetic stab loud enough to clear a threshold no real mix reaches, and the feature returned zero results for its entire life while the suite stayed green. brAIn's analyst prompts have the same exposure, since no test runs them against a real house or a real model.

  • Capture (opt-in, off by default, one switch in ⚙): the bundle the analyst was sent, the card it produced, and later the ending the person gave each finding. Redacted the same way the diagnostics bundle is, and reviewable in the panel before it is exported.
  • Corpus: tests/corpus/ holds contributed bundles with their labelled outcomes. The maintainer's own house is the first entry; the rehearsal fixtures from section 3 are the second, because their ground truth is known by construction.
  • Replay: a nightly CI job, capped in spend, runs the current prompts against the corpus with the real model and scores against the labels. A prompt edit then has a number attached to it before it ships. The _CARD_CONTRACT is shared by both prompt builders precisely so that one copy drifts; replay is what tells you when it drifted somewhere that matters.
  • Shadow mode for a new producer: it runs, files to a shadow status the tab does not render, and for two weeks its rows are compared with what the analyst filed over the same window. It ships to the visible list when its precision on the corpus and in shadow both clear the bar. This is how a check can be added without a week of “Wrong” presses on every install.

5Build order

Ordered by what each unlocks, not by size. The first tier is the substrate the rest reads.

T1substrate
Journal, brain doctor --json, diagnostics.py, brain report, source on settled entries

Small, stdlib-only, no new Claude paths. From this point every field report can carry evidence and every ending is attributable. Nothing user-facing changes except a Diagnostics section under ⚙ and a working Download diagnostics button.

T2value
House checks, first eight

auto.dead_ref, auto.dead_service, auto.trace_error, auto.condition_never_passes, dev.unavailable, dev.frozen, dev.battery_low, org.dashboard_dead_ref. Each with a fixture-house test. Hourly schedule, results into the analyst's prompt block. This is the first release where the Findings tab fills for zero tokens.

T3trust
Scorecard on the tab, sys.after_update, brain.why

Precision per producer visible to the person and in the bundle. The after-update diff and the context-chain walk are the two questions with the highest ask-to-effort ratio.

T4in situ
brain doctor --deep, sensor.brain_health, rehearsal with planted defects

Real round trips per face, one never-unavailable health entity, and the live precision reading that makes a prompt change measurable on a stranger's house.

T5flywheel
Capture, corpus, nightly replay, shadow mode, remaining checks

The loop closes: contributed houses score the prompts, and new producers earn their place before anyone sees them.

6Not building

  • A health score. One number over a house is a number with one critical problem hidden in it. The Findings badge already answers “how much is waiting on me”, and the health sensor answers “is brAIn working”; nothing in between is actionable.
  • A second list. Check results are findings, in the findings store, on the Findings tab. A “Checks” tab beside it is the three-places problem the hypotheses fix already solved once.
  • Per-check notifications. findings_notify_service with its severity floor already covers it, and the dedupe on the created list is what keeps a hourly checker from ringing a phone hourly.
  • An unattended deep doctor. It spends real turns. Lazily on request, like the auth re-check, never on a timer.
  • Any capture that is on by default. A house's entity names are a floor plan. The corpus is opt-in, reviewed before export, and useful even if the only contributor is the maintainer.

7Open decisions

  1. Rehearsal fixtures on a real house. Creating brain_test_* automations in someone's config, even with consent and cleanup, is a step some people will not want. The alternative is rehearsal only in the demo house, which loses the per-install reading. Recommendation: ship it opt-in behind a named consent step, and make cleanup the first thing the doctor verifies on its next run.
  2. Repairs mirroring default. Off, per above, but worth a poll in the release notes: some people live in the Repairs page and never open an add-on panel.
  3. Check cadence. Hourly is cheap on HA but the traces and system-log reads are the heaviest; every 6 hours for those and hourly for state-based checks is the likely shape. Decide from the journal after a release, not before.
  4. Where the scorecard's precision floor sits. 70 % is a starting guess. Below it a check should default off for new installs; the first release of data decides the number.

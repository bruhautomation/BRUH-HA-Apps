# brAIn: house checks

The checks catalog and its floors, snapshot keys, clearing, corrections at the rule, automation/device/network/battery checks, shadow checks.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **`state_class: measurement` is not a claim that a number varies** (`checks/devices.FROZEN_SKIP_CLASSES`). `dev.frozen` says "a real sensor moves", which is true of a measurement of a physical quantity and false of a fixed tariff, a rated capacity, a configured current limit, a nameplate figure, a count of devices on a hub or a vendor index. Nothing declares what kind of quantity those are, while every case the check is *for* names its own class (a stuck thermometer carries `temperature`, a stuck plug `power`, a stuck barometer `pressure`), so a `device_class` is required. It is a guess in the direction where being wrong is cheap, `measures_something_hot`'s trade: a missed stuck sensor costs one finding nobody got, a false one costs the list. `monetary`, `aqi` and `enum` are named out beside `battery` and `signal_strength`, **and `duration` is the one the first cut missed**: a duration is a SPAN, and the spans a house publishes are almost all configured or last-measured (a button's hold time, a timer's length, how long the last run took), so each reads one value until somebody changes it or runs the thing again, which on anything used occasionally is weeks. A *configured* current limit carries no class and is skipped, while a real `current` sensor that has not moved in a week is what this check is for, so adding a class to the set must not take a neighbour with it. **And a class says what is measured, not that it is MEASURED** (`states_a_fixed_figure`): an estimate integration publishes one constant current or power under a real meter's class, so a sensor whose name calls it an estimate, a nominal, rated, assumed or configured figure (whole words) or that reports a `fixed` calculation mode is skipped (the same cheap-direction trade; a real stuck `current` sensor is still reported). Past `FROZEN_MAX_ROWS` it says nothing at all (`base.unusual`'s rule), because a dozen frozen at once is a recorder purge or an integration reload.
- **A stuck reading beside a flat battery is the battery's, however the battery is reported, and "unpowered unless we use it" is the `dev.unavailable` rule** (`checks/devices._flat_battery_beside` / `_own_battery_low` / `_frozen_fix`, `corrections.normally_unpowered`, `server._unwatchable_condition`). A low-battery FLAG on the device (a `binary_sensor` of class battery, on) owns a stuck reading the way a percentage at or under `BATTERY_LOW_PCT` does, because `dev.battery_low` files that flag; a sensor that carries its battery as its own attribute (`battery_level`/`battery`, which no battery check reads) still files, with a fix that names the battery first. A Wrong on `dev.unavailable` whose reason says the device is normally without power ("unpowered unless we're using it", "unplugged except when we need it", "off most of the year") is written as the rule rather than parked as a fact and a question, since the condition names the very state the check reports; the same words under any other check are still a question, and "for now" is the snooze (`corrections.temporary`). Left alone on purpose: "normal for this sensor", "this is intentional", "these were tests", "the drift is someone driving more often" and "it's been really dry" are about one entity or one pair and are answered by the per-entity rule a Wrong already writes; a phone's companion-app features on a phone that answers are skipped (`FEATURE_PLATFORMS`), and a phone gone quiet altogether is still reported as the device.
- **`device_class: temperature` does not mean room air, and the bound was an ambient one** (`checks/devices.measures_something_hot`). `_RANGES` says a temperature sensor cannot read outside -40–60°C, which is true of a thermometer on a wall and false of a 3D printer's bed and nozzle, an oven, a kettle, a sous-vide, a boiler flow pipe, a CPU, a water cylinder or a pizza stone. The ambient range is applied only where the sensor is plausibly measuring room air, and the gate is a **name** gate, a guess in the direction where being wrong is cheap (the same trade `chore.waiting` writes down): a missed implausible reading costs one finding nobody got, a false one costs the list, which a person learns to ignore first. `bed`, `chamber` and `plate` are hot only beside a printer word, because a bedroom sensor is a room. `base.unusual` reads the same function through the same `out_of_range`, so the two cannot disagree about which sensors those are. **`dev.implausible`: a reading the registry files as the device's own is not room air** (`checks/devices.reads_its_own_device`, read by `measures_something_hot`): a plug's relay, a hub's board or a light driver publishes a `diagnostic` temperature at 60–70 °C; the category is the integration's claim about the entity, not a name. The cold floor still holds.
- **A printer's heater is judged by the printer, and an answer about the band is not an answer about the idle case** (`checks/devices.printer_heater` / `computer_temperature`, `checks/chores.machine_status`, `checks/baseline.heater_idle`, `corrections.NEVER_CHECKS`). A printer heater is left out of the band (`not_a_house_reading`) and judged by `base.heater_idle` instead, off the device's own status entity in `chores`' job vocabulary plus `JOB_IDLE`: working (any word that is not idle or finished, `heatbed_preheating` included) says nothing, could-not-tell says nothing, and idle or finished for `HEATER_COOL_S` with the heater over `HEATER_IDLE_HOT` is a row, `now`. It is a check of its own so a Wrong given about the band, even one stored as a rule for the whole sensor, cannot silence it, and it is in `NEVER_CHECKS` so no wide rule (the sensor, its device, its room) stands it down: only an answer about the idle case does. A computer's chip or drive temperature (`COMPUTER_PLATFORMS`, `_COMPUTER_WORDS`) is left out of the band too, because it follows its load; the hot words that are not a computer's (a tank, a probe) still get a band. An `impossible` record is re-read against the bounds the pass knows NOW (`recently_impossible(…, bounds)`), so a record an older pass left about a chip's 90 °C files nothing. **The printer was one machine of a class**: any reading on a device whose own status speaks the job vocabulary (a dishwasher's water temperature mid-wash, a kettle's) moves with the job, so `base.unusual` asks `chores.machine_status` after the band has spoken and stands down, `explained` on the trail, while it says `working`; idle, finished and could-not-tell are compared as before. A stand-down rather than a band per state, because the baseline store keys only on the hour of the week and the status is already read live.
- **What a reading is part of is answered by the registries before any guess, and a target is not a reading** (`checks/devices.machine_of` / `is_setpoint`). `machine_of` is the one answer (`"printer"`/`"computer"`/""): the integration, then the integrations of the other entities on the same device, then the device's name, model and maker, and only then the entity's own words or a model's reading; `measures_something_hot`, `printer_heater` and `computer_temperature` all read it, so `dev.implausible` and `base.unusual` cannot disagree. A setpoint the printer reports ("nozzle target temperature") is not a reading: `is_setpoint` (whole words `target`/`setpoint`/`set point`, `SETPOINT_WORDS` living in `devices`) is shared by both checks.
- **An integration is read however it is spelled, and a sensor's own week is evidence of what it measures** (`checks/devices.platform_machine` / `history_says_hot`). `platform_machine` compares integrations with punctuation folded (`system_monitor` against `systemmonitor`) and reads an integration's own name for a chip or 3D-printer word (a narrow set: `google_drive` is not a disk and `bruh_print` is a label printer). The range also comes from what the sensor has READ: a temperature whose daily statistics (`snap["stats"]`, the week `dev.frozen` already reads) stayed at or above `WARM_FLOOR` (30 °C) on every one of at least `HOT_HISTORY_MIN_DAYS` days, passed the ambient ceiling on some, and moved by at least two degrees is something hot and gets the heater's range. A room thermometer that spiked today has cool days behind it, a probe stuck at its failure value (85 °C) has not moved, and the cold floor is never lifted, so all three still file. The nightly baseline pass reads the same rule over its hourly series (`HOT_HISTORY_MIN_DAYS * 24` rows), so such a sensor's hot hours are learned rather than dropped as impossible and `base.unusual` judges it against its own band.
- **A Wrong whose reason names a machine state holds only in that state** (`chores.report_while` / `condition_holds` / `House._applies_now`, `server._unwatchable_condition` / `_MACHINE_STATUS`, `corrections.condition_offer_row`). A rule's text IS the reason, so `House.withheld_by` reads it at check time: where `report_while` finds the state the person wants to hear about (an "only … if/when/while" or "unless" clause, else "normal while" read the other way round) and the device carries a job status (`chores.status_entity`), the rule stands down in the other state only, and a status that cannot be read stands nothing down; a reason naming no state is the plain rule. At the press a check's conditional reason brAIn cannot watch (no status on the device in `_MACHINE_STATUS`, or words naming no state) writes NO rule: it is kept as a fact and a correction question asks "Stop flagging … for X at all?", whose Yes writes the press's own rule (`accept_offer`'s `entity_check` scope). `base.heater_idle` stays in `NEVER_CHECKS`, so no rule about the band silences it. **`corrections.conditional` must know every shape `report_while` reads**: "normal while the dishwasher is running" (no "only") would otherwise be a plain rule at the press (widened by the `correct` job to `exception:*`, or a whole-entity mute on a device with no status) while the check read it as a state. It also knows "except when …" and "only the ecobee sensor counts" (which of several matters, kept as a fact on a Resident case, never `exception:resident` on every entity), and `conditional_confirmation(note=)` says that one was kept as a fact.
- **A broken probe is not the season, and the trail says which it was** (`baselines.fetch_hourly`'s `min`/`max`, `_without_impossible`, `decision_trail.KINDS`' `drift`/`claimed`/`explained`, `House.gave_up(kind=)`). The statistics call asks for the hour's min and max in the same request, and an hour whose min, max or mean is impossible is dropped and recorded, so the recent level is never built from a broken week and `dev.implausible` claims the sensor for two days; `base.unusual` stands down for a claimed sensor BEFORE the drift guard and writes `claimed` on the trail. `gave_up` kinds: `cap` is only a too-many-at-once limit that fired, `drift` is the season or the weather (the recent level, several of one kind moving together, in `forecast.decline` too), `explained` is something in the house accounting for it (the room's dehumidifier).
- **A machine's reading is learned and judged by what the machine was doing, and an on/off `running` sensor is a status** (`chores.machine_status` / `status_entity` / `phase_of` / `RUNNING_CLASSES`, `baselines.fetch_status_history` / `split_by_phase` / `by_state`, `base.unusual`'s `judged_in`). A `binary_sensor` of class `running` on the device is a status (on working, off idle, unavailable could-not-tell). The nightly pass asks Core for the month of each status on a measured sensor's device (`STATUS_FETCH_MAX`, one `/history/period` request, the checks pass's own `_job_history` shape), files each hourly row under what the status said at the middle of the hour and keeps a band per state (`by_state`, with `status`) when both states were seen. The check judges a reading against the band of the state the machine is in now (an idle hot bed against the idle hours, a runaway heater against the print hours) and only without one falls back to the band of every hour and the stand-down; the recent-level figure belongs to the mixed band and is not read for a state's. The row says which state it was judged in.
- **A reason typed on a reading's row explains that reading, not every reading** (`checks._util.explained_range` / `EXPLAINED_MARGIN`, `House._explains_now`, the row's `explained`, `findings_store.clean_explained`, `facts_store.add(explained=)`, `corrections.scope_map` / `apply_plan`). Each row carries `[low, high]`: the usual (or the edge of what the sensor's kind can read) to the reading shown, widened by a tenth of that distance and at least the check's smallest move. The press keeps it on the rule it writes and on the whole-entity rule the `correct` job may add, and `_applies_now` holds a rule whose reason names no machine state only while the reading stays inside it. A reason naming a state is read as the state (`report_while`); a rule reached through another entity of the device (`via`), and every rule written before ranges existed, carries no range and holds without one.
- **History that ends early is not evidence** (`ha_data.history_cutoffs` / `checks/_util.history_cut` / `sys.history_incomplete`). Core's history can stop at a restart while the entity kept changing (longer windows ending EARLIER is the tell), and every per-entity "silent since", "0 W all week" and "frozen" built on it is a fault of the recorder filed against a device. An entity whose last history row is more than `HISTORY_GAP_S` before its live `last_changed` (inside the window) is cut: the bundle drops the series and says so, the MCP `get_history` tool says so, closures skip it, and `dev.frozen` is `reads_history` so a probe that finds ≥2 cut entities skips it (clearing nothing) and files ONE recorder finding instead. Entities with no rows are not judged: "nothing recorded" and "recorded until Tuesday" are different claims. **A restart re-stamps a clock; it does not cut history** (`ha_data.SHARED_CHANGE_MIN` / `_shared_seconds`): a restart or an integration reload re-publishes every entity it owns with a fresh `last_changed` and the same state, so a live `last_changed` that six or more states share to the second is not judged (a real cut is one entity changing on its own after its history ends), nor is a live state that is no reading (`NO_READING`) carrying `restored: true`, or one whose history also ends on no reading (unavailable then and now is no change missing). **What the recorder leaves out on purpose, and a value a restart re-stamped, are not a cut** (`checks/_util.recorder_excludes`/`history_cut`, `snapshot.load_recorder_filter`): the probe reads the recorder's own `include`/`exclude` from configuration.yaml (one `!include` followed, inside /config) and neither probes nor counts an excluded entity, in Home Assistant's order (named include, named exclude, exclude glob/domain, include glob/domain, then anything an include did not name); and `history_cut` drops a row whose live VALUE is the value its history ends on, since a restart moves the stamp, not the value. A recorded entity whose value changed with no row still fires. `history_cutoffs` itself is unchanged (it also carries `history_state`/`live_state`), because a fetch standing a stale window down is a different question from the recorder being reported. **And an absence is a claim the card itself has to check** (`_CARD_CONTRACT`'s "nothing for N h" line): a series can be flat for reasons the cut-off cannot see and long-term statistics carry no such flag, so both card prompts say to check related sensors and `history_incomplete` before claiming nothing happened, and to report a disagreement rather than the silence. The MCP server's `get_statistics` carries no cut-off note and its copy of the restart rule is missing; that file is outside what the development loop may change.
- **The thing people check by hand every week was the thing no check read** (`checks/snapshot._supervisor`'s fifth path + `checks/system.update_pending`). Core, the OS, the Supervisor and every add-on publish what is waiting at `/available_updates`. It rides in the **same gather** as the other four, which makes it free, and it is its **own snapshot key** rather than a field on `supervisor`: a Supervisor that refused this one has answered every other system check, and folding it in would take `sys.backup_stale` and `sys.addon_down` down with it. An empty list is a real answer and a shape the unwrapper cannot read is not: `result.get("available_updates")` is required to be a **list**, or the key stays `None`, because `or []` there is "you are up to date" invented out of a 500. **One row however many updates**, `evening.left_open`'s rule: this is a single visit to one screen; the text is stable and the count that moves every week lives in `detail`, or every pass files a new finding. Its urgency is `whenever` against the `check:sys.` family's `today`: an update waiting at 23:00 is the same update at 08:00. **It ships in `SHADOW`**, and each entry carries the release its fortnight started in. **A new snapshot key is what proves a frozen corpus entry is frozen**: every committed house predates it, so the check is skipped on both (the honest answer), and the clean-house expectation asserts that each skip names a key that house *predates* rather than the entry being rebuilt to make the number go away. `score_checks` passes `run_all`'s per-**check** skip map under the same word `replay.render` uses for an **entry** it refused to grade, so `entry_skipped` is the line that tells the two apart.
- **An answer about a device holds for the stretch it was given in, on every entity of the device; and two rules contradict only in the same moment** (`House._answered_this_stretch` / `stretch_began`, `findings_store.answered_checks`' `wrong_at`, `checks/automations.FIGHT_S`, `checks/devices._stands_in_for`). A Wrong on any entity of the device under any `DEVICE_QUIET` check holds while the entity filed is still in the state it was answered in (the earlier of the recorder's stretch start and a `last_changed` that is not a restart's re-stamp); one that came back and went again is news, and "for now" is still the snooze. This covers a Wrong whose reason wrote no rule (a condition brAIn cannot watch, kept as a question), which the ledger read only under the entity the row led with. Reading "broken" out of a free answer is deliberately not done: every guard (repaired, for now, some of the time) still let a plan read as retirement ("broken sensor, replacement arrives friday"), and a True there silences the sensor for good. Missing a phrase costs one card; silencing a device for good on a sentence about its repair costs the device. `auto.conflict` counts an undo inside `RACE_S`, both undos of a loop (the pair undoing each other again on the entity within `FIGHT_S`), and a schedule that disagrees with itself: two rules that run only on a clock, the second undoing the first inside `SCHEDULE_S`, filed on one such undo because the miner's day of logbook holds one run of a daily schedule. `dev.restored` says, per entity, whether a live entity of the same kind on its device or of the same name still does its job, and asks for a reinstall only about the ones nothing stands in for.
- **A correction reaches the RULE, and the check reads it off the snapshot** (`facts_store.exceptions` / `exception_map` / `House.excepted` / `server._record_exception`). `_end_finding` with `kind == "ignored"` on a `check:` row writes a fact whose `predicate` is `exception:<check_id>` under that entity (`*` for the whole entity), and `checks/snapshot.collect` loads `exception_map` into `snap["facts"]`: a snapshot key like any other, `{}` on failure, so the checks stay pure over what they are handed and a store that could not be read excepts **nothing**, the direction in which being wrong shows a card. `dev.frozen`, `dev.implausible`, `chore.waiting` and `base.unusual` ask `house.excepted(eid, id)` and skip; the rest of the catalog can read it the day a house says it is wrong about them. A predicate written in one module and read in another is a wire format: only a round trip through the real `_end_finding` and the real check proves it.
- **Every per-entity check asks `House.should_report`, and the AST sweep holds it** (`tests/test_scoped_corrections.py::TestEveryCheckAsks` once enforced it). Any function in a check module building a row with `text` and a non-empty `entity_id` must call it. A snapshot with no `corrections` key falls back to `snap["facts"]` (the exception map), so nothing standing down starts filing because of how a pass was built. `excepted` is kept for its callers. **A device somebody said is finished with, on any card, closes the device checks for it** (`snap["faulty"]` = `corrections.known_faulty`, read by `House.answered_off` for `DEVICE_FINISHED`): "we no longer use the shed remote" said Wrong on a Resident or overnight card writes an exception no battery check reads, so the remote's low battery would be asked about again. `_never_covered` still wins.
- **House checks are findings that cost nothing, and they clear themselves** (`panel/checks/`). A check is a pure function from one snapshot of the house (`checks.snapshot.collect`: states, registries, services, the YAML config files with HA's own tags tolerated, `.storage/trace.saved_traces`, a week of daily statistics, sixty days of battery means, the storage-mode dashboards) to wire-shaped findings under `source: "check:<id>"`; `run_all` files them through `findings_store.add_many` like every other producer, so they dedupe against the settled ledger and ride into the analyst's prompt block. Three rules keep them honest. **Finding text is stable across runs**: the store dedupes by it, so the number that changes ("9 days left", "since 3 Sep") lives in `detail`, and `findings_store.refresh_details` updates it in place. **Only a check that RAN may clear**: `clear_resolved` removes open rows (never `fixing`/`fixed`: those are a person's or the fixer's) whose source is in the set of checks that ran and whose key was not re-reported; a check skipped because its snapshot key was unavailable, or one that raised, is not in that set, because "I could not look" and "it went away" are different claims and only the second may delete a row. Clearing writes no memory line and no ledger entry: a problem that went away on its own is not a fact about the house, and if it comes back the check files it again. **A check that fires on a healthy house is worse than no check**: every rule has a floor or a window, each is asserted silent on a clean fixture before it is asserted to find a planted row, and the scorecard is what proves it in the field. Two traps: a service name has the shape of an entity id (`light.turn_on`), so `House.entity_refs` skips the values of `service`/`action`/`trigger`/`platform` keys and anything in the registered services set; and `age_days` of a trace from this second is `0.0`, which `or 99` turns into 99 and drops the freshest evidence, so test `is not None`, never truthiness, on an age.
- **Inside a template a `domain.object` token is not always a reference** (`checks/_util._template_spans` / `_not_a_ref`, `automations._without_field_hints`). `"switch.pump_" ~ zone` builds an id, `zone.split('-')` is a method on a loop variable, and a `{% for zone in … %}` variable's attributes are not entities; `entity_refs` skips a token followed by `~` or `(`, or whose domain a `for` in that string binds, only inside `{{ }}`/`{% %}`. `auto.dead_ref` also ignores a script field's `example`/`default`/`selector`. `states('sensor.x')` is still a reference.
- **The second set of checks reads what Home Assistant is not.** The snapshot has three keys beyond Core. **`supervisor`** is `/backups`, `/addons`, `/host/info` and `/core/info`, gathered rather than awaited in turn, and each add-on row is folded together with its *own* `/addons/<slug>/info`, because the list endpoint does not carry `boot`, the entire difference between "somebody stopped this on purpose" and "this was meant to be running": `sys.addon_down` reports a `boot: auto` add-on that is stopped, and an add-on whose `/info` did not answer carries no `boot` and reads as **I could not look** and files nothing. **`recorder`** is one `stat` of `home-assistant_v2.db` plus `purge_keep_days` from `configuration.yaml`: an `!include`d recorder block reads as unset (`sys.recorder_size` then names HA's own default rather than a number this invented), and a database that is not a file under `/config` takes the whole key **unavailable** rather than reporting as small, because Postgres is not a smaller database, it is a question this cannot answer. **`zha_devices`** is `zha/devices`, which errors on a house with no ZHA and so goes unavailable: no Zigbee is not an unhealthy Zigbee. `dev.zha_unseen` keys on `last_seen` and *not* on `available`: a sleepy sensor is `available` between check-ins, so availability says nothing and silence says everything. `dev.zwave_dead` reads the node status sensor the controller publishes, and `dev.unavailable` **skips a device it claims**: the same box under two fixes ("restart it" and "re-interview it, or remove the failed node") is how a list stops being read, so the two checks share `_zwave_dead_devices`. `auto.trigger_unavailable` has no symptom at all (the automation is on, nothing errors, no trace is written, and it can never fire again), so it is deliberately separate from `dev.unavailable`, which reports the sensor; only the second answers "why did the hallway light stop coming on". It reads both spellings of the trigger key (`trigger:` and 2024.10's `triggers:`, `platform:` and `trigger:`), and stands down for a missing entity (`auto.dead_ref`'s) and for a switched-off automation (`auto.forgotten_off`'s). The `reg.*` checks are the most at risk of firing on a healthy house, and each carries a floor: `reg.no_area` says nothing below three areas; `reg.unused_helper` gives a helper 30 days to be wired up and checks the configs, the storage dashboards **and** other entities' attributes in one `entity_refs` pass (it rebuilds the services set per call, and this walks the whole house); `reg.orphan_device` spares a device another names as its `via_device`, because a hub with no entities of its own is still doing a job; and `reg.hardware_name` requires a hex run to carry both a digit and an `a-f` letter, or `Bedroom 123456789012` and `deadbeefface` both read as hardware and neither is.
- **The networks a device talks through are checks, and they ship live** (`checks/network.py`, `checks/integrations.py`; conservative floors rather than `SHADOW`). Three snapshot keys, each its own so an unreadable source skips only its own checks: **`wifi_history`** (a week of each UniFi wireless client's tracker plus one probe entity of the device its MAC joins it to through the device registry's `connections`, `network.wifi_history_candidates` shared by collector and check, at most `FLAP_FETCH_MAX`), **`zwave_nodes`** (`zwave_js/node_status` + `node_statistics` per node in one `_ws_calls` round trip: a status, and a `last_seen` a restart does not reset; `last_changed` is never read) and **`core_log`** (the Supervisor's `/core/logs`, folded by `integrations.summarise_log` by logger and message with addresses, ids and numbers folded, redacted through `reports.redact`). `net.wifi_hung` is a client UniFi holds while its own entities have been unavailable two hours, ONE row per access point; `net.wifi_flapping` counts separate spells into unavailable with the tracker never leaving, and **a minute many entities dropped together is a restart or an integration, never a device's drop** (`_mass_moments`, `after_restart`); every UniFi tracker dropping together repeatedly is `net.unifi_dropped`'s single row. `net.zwave_silent` is a battery node silent past three wake-up intervals (26 h when unknown), `net.zwave_link` RSSI ≤ −90 or a round trip ≥ 150 ms; `net.zigbee_weak` a router under LQI 40, `net.zigbee_silent` mains past 6 h or battery past 26 h, and a week is still `dev.zha_unseen`'s: one classifier (`zigbee_quiet`) so a device is never both. **One box, one check**: `dev.unavailable` stands down for a hung client and a quiet Zigbee device, `dev.battery_low` for a silent Z-Wave node, as it does for a dead one. A device disabled or labelled not in use (the label's name, or its slug id when the label list could not be read) is never raised. `integ.log_flood` is a logger repeating an error more than 100 times in a day, one row per logger naming the device or address the house knows, never brAIn's own. `sys.entry_failed` is titled Integrations and waits a day (`ENTRY_STUCK_S`) off a ledger the collector keeps (`system.stamp_failing`, `ENTRY_FAILING_FILE`), seeded on its first pass from when the entry was created so a row already on the list is not cleared and refiled; `dev.battery_low` reads a low-battery flag (a battery-class binary sensor) from any integration, once per device. A catalog entry's `source_title` names the producer on the card (`title_for`). **One device is one drop card, and one integration-wide outage is one card** (`network.device_keys`, `findings_store._fold_devices` / `DROP_CHECKS` / `is_drop_report`, the row's `integration`). The panel puts each entity's device into `_NAMES` (`device`, a UniFi client's tracker joined to the device it is a client of through the registry's MAC), and after every filing a row about a device dropping folds into a live row whose devices include it (the widest first, then a house check, then the oldest), taking its evidence less any count the card's own detail contradicts (`quotes_other_counts`); a row carrying `integration` (`net.unifi_dropped`, a log flood that names nothing of its own, an overnight cause about a line that names nothing of its integration's) folds with every other row about that integration as a whole. Such a row is filed on NO entity; a line naming the integration's own entity by its friendly name is filed on it, and several of one hub's things on the hub (`sre._subjects`). `_fold_shared`'s refusals apply.

- **An override is the only signal a house gives about an automation being wrong for it.** A person putting something back within `OVERRIDE_WINDOW_S` of an automation moving it: the automation ran, nothing errored, and the light is off, so no check that reads Core can see it. Three rules keep it honest: **the state has to actually differ** (a person pressing "on" after a rule turned it on is agreement), **one automation move is undone once** (somebody nudging a dimmer three times is one disagreement), and **an automation undoing an automation is not an override** (that is a conflict, and a different finding). `auto.overridden` reads `find_overrides` rather than recomputing any of it, and fires at three in a day: once is a one-off, twice is a coincidence. **A rule a person sets off by pressing is not a rule being undone, a lock is not a door, and a quieted rule says so at two Wrongs** (`checks/automations.overridden` via `_relays`, `checks/evening.left_open`, `reports.faults`): `auto.overridden` skips an automation every trigger of which is a press (`_is_press`), the same reading `auto.conflict` has. `evening.left_open` says "unlocked"/"locked" for a lock and names a car as a car (`_CAR_RE`); the row's text follows. Passes overlap (every 6h over a 26h window) so every override is offered four or five times: **the id is the event, not the offering**, or one disagreement is filed as five. A pattern is about **days** (four overrides in one evening is one evening), so `MIN_DAYS` gates it whatever the count. `_band` reports the hours that are **occupied, not the window that found them**: ties go to the tighter span and the band is shrunk to its first and last occupied hour, wrap included (22:00–01:00 is a real bedtime), because a condition somebody would write from a loose band stands the rule down for hours nothing happens in. **And a pattern has to still be happening**: the ledger keeps 60 days, but a rule somebody *fixed* keeps its shape in that history, so `RECENT_DAYS` gates on the last override, and `pattern` takes the pass's own `now` rather than the wall clock so it ages from the same instant every other check does.
- **`auto.conflict` is the finding the override rules named and deferred.** Two rules undoing each other: the entity ends in whichever state the later trigger left it, and *which one wins depends on the order two triggers happened to fire in*. Nothing else can see it. `find_conflicts` carries `find_overrides`' three rules and adds a fourth: **an automation cannot conflict with itself**, and a person's move *ends the pairing*, because what follows it answers the person. The pair is keyed **unordered**: A-undoes-B and B-undoes-A is one disagreement. `CONFLICT_MIN` is 2 rather than 3 because nobody is choosing to do this: two rules that have disagreed twice will disagree every time their triggers land in that order. **But a sequence is not a fight** (`checks/automations.RACE_S`): a motion-on rule and a no-motion-off rule put the light back every time, in a different state, from a different automation, which is two rules doing what they were written to do. A pair is reported only when it has undone each other in **both** directions, or when the second landed within `RACE_S` of the first (one trigger reaching two rules, where the winner is the order Core ran them in); a one-way pair slower than that says nothing whatever the count. `find_conflicts` still records every undo (the direction and the gap are the check's to read, so the miner stays one implementation of *what happened*). **And a rule a person sets off is the person** (`checks/automations._relays` / `_is_press`, `actions.find_conflicts(relayed=, triggers=)`, `RELAY_S`): an automation whose every trigger is a press (a scene controller's `event` entity, a Z-Wave value notification, a device trigger whose type is a press, a tag) is somebody's hand with a rule in between, and so is a rule answering within `RELAY_S` of a person changing what it watches (a room mode picked in the UI); its move ends the pairing as a press on the light does. The check re-runs the miner's own `find_conflicts` with what only the configs know, never a second copy of the pairing rules, and falls back to the miner's answer when the configs or the action list are not there. **A conflict row is about two rules, so a Wrong is written under both and asked of both** (`except_evidence` on the catalog entry, read by `server._exception_rule`; the row's `evidence` names the pair): the row is filed under whichever rule sorts first, so writing and asking only that one would let the rule a homeowner kept answering about come back under every new partner. **`auto.conflict` counts only explanations about the conflict** (`automations.CONFLICT_EXPLAINS`): it asks `owner_explained(e, CONFLICT_EXPLAINS)` (`auto.conflict`, `auto.overridden` and a `*` rule) of the entities AND the two rules, so a reason given on a battery row of the same device does not quieten a real fight, and a reason given on the conflict itself (written under the rules) is read.

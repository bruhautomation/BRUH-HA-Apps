# brAIn: house checks

The checks catalog and its floors, snapshot keys, clearing, corrections at the rule, automation/device/network/battery checks, shadow checks.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **`state_class: measurement` is not a claim that a number varies** (`checks/devices.FROZEN_SKIP_CLASSES`). `dev.frozen` says "a real sensor moves", which is true of a measurement of a physical quantity and false of a fixed tariff, a rated capacity, a configured current limit, a nameplate figure, a count of devices on a hub or a vendor index — each of which reads exactly one value for a week because that is what it *is*. The scorecard read **0 confirmed against 6 marked Wrong** with ten more filed in the same pass, which is the Findings tab saying this rule is wrong about this house: `dev.implausible`'s failure again, one check over. What those false rows have in common is that nothing declares what kind of quantity they are, while every case the check is *for* names its own class — a stuck thermometer carries `temperature`, a stuck plug `power`, a stuck barometer `pressure` — so a `device_class` is required, which keeps the whole point and drops the rest. It is a guess in the direction where being wrong is cheap, `measures_something_hot`'s trade: a missed stuck sensor costs one finding nobody got, a false one costs the list. `monetary`, `aqi` and `enum` are named out beside `battery` and `signal_strength`, **and `duration` is the one the first cut missed** — a duration is a SPAN, and the spans a house publishes are almost all configured or last-measured (a button's hold time, a timer's length, how long the last run took, a track's length), so each reads one value until somebody changes it or runs the thing again, which on anything used occasionally is weeks. It arrived the way the ambient-temperature gap did: a real house, a real row, and a sensor working exactly as intended. The test names it beside `current` on purpose — a *configured* current limit carries no class and is skipped, while a real `current` sensor that has not moved in a week is precisely what this check is for, so adding a class to the set cannot quietly take a neighbour with it. **And a class says what is measured, not that it is MEASURED** (`states_a_fixed_figure`): an estimate integration publishes one constant current or power under a real meter's class and rewrites the state daily with the same number, so a sensor whose name calls it an estimate, a nominal, rated, assumed or configured figure (whole words) or that reports a `fixed` calculation mode is skipped — the same cheap-direction trade, and a real stuck `current` sensor is still reported. Past `FROZEN_MAX_ROWS` it says nothing at all — `base.unusual`'s rule, because a dozen frozen at once is a recorder purge or an integration reload rather than a dozen broken sensors.
- **`device_class: temperature` does not mean room air, and the bound was an ambient one** (`checks/devices.measures_something_hot`). `_RANGES` says a temperature sensor cannot read outside -40–60°C, which is true of a thermometer on a wall and false of a great many sensors in a house — so a working 3D printer reporting its bed at 65°C and its nozzle at 220°C had brAIn file four rows saying those readings are impossible. They are ordinary; that sensor measures a heater, and so do an oven, a kettle, a sous-vide, a boiler flow pipe, a CPU, a water cylinder and a pizza stone. **The producer scorecard is what caught it** — 0 confirmed against 2 marked Wrong is the Findings tab saying this rule is wrong about this house, which is the whole reason that number is on the screen — and it is the exact failure the check catalog opens by naming: a check that fires on a healthy house is worse than no check, because it is the one a person learns to ignore first. The ambient range is applied only where the sensor is plausibly measuring room air, and the gate is a **name** gate, which is a guess made in the direction where being wrong is cheap — a missed implausible reading costs one finding nobody got, a false one costs the list — the same trade `chore.waiting` writes down for the same reason. `bed`, `chamber` and `plate` are hot only beside a printer word, because a bedroom sensor is a room; `base.unusual` reads the same function through the same `out_of_range`, so the two cannot disagree about which sensors those are and a nozzle cannot stop being impossible only to start being unusual.
- **A printer's heater is judged by the printer, and an answer about the band is not an answer about the idle case** (`checks/devices.printer_heater` / `computer_temperature`, `checks/chores.machine_status`, `checks/baseline.heater_idle`, `corrections.NEVER_CHECKS`). `base.unusual` compared a nozzle and a bed with an hour-of-the-week median whatever the printer was doing, and BRUH Bambu Studio's own `bruh_bambu` sensors were not on the printer list: 0 confirmed against 4 Wrong, two of them saying *only unusual if hot while the printer is idle*. A printer heater is left out of the band (`not_a_house_reading`) and judged by `base.heater_idle` instead, off the device's own status entity in `chores`' job vocabulary plus `JOB_IDLE`: working (any word that is not idle or finished, `heatbed_preheating` included) says nothing, could-not-tell says nothing, and idle or finished for `HEATER_COOL_S` with the heater over `HEATER_IDLE_HOT` is a row, `now`. It is a check of its own so a Wrong given about the band — even one stored as a rule for the whole sensor — cannot silence it, and it is in `NEVER_CHECKS` so no wide rule (the sensor, its device, its room) stands it down: only an answer about the idle case does. A computer's chip or drive temperature (`COMPUTER_PLATFORMS`, `_COMPUTER_WORDS`) is left out of the band too, because it follows its load; the hot words that are not a computer's (a tank, a probe) still get a band. And an `impossible` record is re-read against the bounds the pass knows NOW (`recently_impossible(…, bounds)`), so a record an older pass left about a chip's 90 °C files nothing. **The printer was one machine of a class**: any reading on a device whose own status speaks the job vocabulary (a dishwasher's water temperature mid-wash, a kettle's) moved with the job and was judged against one band over every hour, so `base.unusual` asks `chores.machine_status` after the band has spoken and stands down, `explained` on the trail, while it says `working`; idle, finished and could-not-tell are compared as before. A stand-down rather than a band per state, because the baseline store keys only on the hour of the week and the status is already read live (`tests/test_running_machine_readings.py`).
- **What a reading is part of is answered by the registries before any guess, and a target is not a reading** (`checks/devices.machine_of` / `is_setpoint`). 3.8.6 read the providing integration first and the impossible-readings check was still answered Wrong about a nozzle, a bed and a processor: the platform answered only when it was a printer's or a computer's own, and otherwise `world_model`'s reading of the ENTITY ran ahead of the device's evidence, so a bed published by a bridge on a printer maker's device was room air whenever the model said so — and a setpoint the printer reports ("nozzle target temperature") was judged as a reading by `dev.implausible` while `base.unusual` already stood it down. `machine_of` is the one answer (`"printer"`/`"computer"`/""): the integration, then the integrations of the other entities on the same device, then the device's name, model and maker, and only then the entity's own words or a model's reading; `measures_something_hot`, `printer_heater` and `computer_temperature` all read it, so `dev.implausible` and `base.unusual` cannot disagree. `is_setpoint` (whole words `target`/`setpoint`/`set point`) is shared by both checks, `SETPOINT_WORDS` living in `devices`.
- **An integration is read however it is spelled, and a sensor's own week is evidence of what it measures** (`checks/devices.platform_machine` / `history_says_hot`). A computer's processor temperature was filed as impossible again — the fourth time a name gate missed one — because nothing it carried was on a list: an integration spelled `system_monitor` against the table's `systemmonitor`, a model that read "temperature" as room air, a sensor named for the box rather than the chip. `platform_machine` compares integrations with punctuation folded and reads an integration's own name for a chip or 3D-printer word (a narrow set: `google_drive` is not a disk and `bruh_print` is a label printer). And the range now also comes from what the sensor has READ: a temperature whose daily statistics (`snap["stats"]`, the week `dev.frozen` already reads) stayed at or above `WARM_FLOOR` (30 °C) on every one of at least `HOT_HISTORY_MIN_DAYS` days, passed the ambient ceiling on some, and moved by at least two degrees is something hot and gets the heater's range. A room thermometer that spiked today has cool days behind it, a probe stuck at its failure value (85 °C) has not moved, and the cold floor is never lifted, so all three still file. The nightly baseline pass reads the same rule over its hourly series (`HOT_HISTORY_MIN_DAYS * 24` rows), so such a sensor's hot hours are learned rather than dropped as impossible and `base.unusual` judges it against its own band.
- **A Wrong whose reason names a machine state holds only in that state** (`chores.report_while` / `condition_holds` / `House._applies_now`, `server._unwatchable_condition` / `_MACHINE_STATUS`, `corrections.condition_offer_row`). "Normal while the printer is printing. Only unusual if hot while the printer is idle" was stored as `exception:base.unusual` with no condition and the check could never raise either sensor again. A rule's text IS the reason, so `House.withheld_by` reads it at check time: where `report_while` finds the state the person wants to hear about (an "only … if/when/while" or "unless" clause, else "normal while" read the other way round) and the device carries a job status (`chores.status_entity`), the rule stands down in the other state only, and a status that cannot be read stands nothing down; a reason naming no state is the plain rule it always was, which is also what keeps every rule written before this answering as it did. At the press a check's conditional reason brAIn cannot watch (no status on the device in `_MACHINE_STATUS`, or words naming no state) writes NO rule: it is kept as a fact and a correction question asks "Stop flagging … for X at all?", whose Yes writes the press's own rule (`accept_offer`'s `entity_check` scope). `base.heater_idle` stays in `NEVER_CHECKS`, so no rule about the band silences it. **`corrections.conditional` must know every shape `report_while` reads**: "normal while the dishwasher is running" (no "only") was a plain rule at the press — widened by the `correct` job to `exception:*`, or a whole-entity mute on a device with no status — while the check would have read it as a state. It also knows "except when …" and "only the ecobee sensor counts" (which of several matters, kept as a fact on a Resident case, never `exception:resident` on every entity), and `conditional_confirmation(note=)` says that one was kept as a fact (`tests/test_condition_without_only.py`).
- **A broken probe is not the season, and the trail says which it was** (`baselines.fetch_hourly`'s `min`/`max`, `_without_impossible`, `decision_trail.KINDS`' `drift`/`claimed`/`explained`, `House.gave_up(kind=)`). A probe swinging daily from a room's reading to −150 °F has a POSSIBLE hourly mean, so the nightly pass kept those hours, built the recent level out of them, and `base.unusual`'s drift guard excused it six times as *the season or the weather* while `dev.implausible` filed it as faulty. The statistics call asks for the hour's min and max in the same request, and an hour whose min, max or mean is impossible is dropped and recorded, so the recent level is never built from a broken week and `dev.implausible` claims the sensor for two days; `base.unusual` stands down for a claimed sensor BEFORE the drift guard and writes `claimed` on the trail. `gave_up` used to write `cap` for every stand-down; `cap` is now only a too-many-at-once limit that fired, `drift` is the season or the weather (the recent level, several of one kind moving together, in `forecast.decline` too), `explained` is something in the house accounting for it (the room's dehumidifier).
- **History that ends early is not evidence** (`ha_data.history_cutoffs` / `checks/_util.history_cut` / `sys.history_incomplete`). Core's history can stop at a restart while the entity kept changing — longer windows ending EARLIER is the tell — and every per-entity "silent since", "0 W all week" and "frozen" built on it is a fault of the recorder filed against a device. An entity whose last history row is more than `HISTORY_GAP_S` before its live `last_changed` (inside the window) is cut: the bundle drops the series and says so, the MCP `get_history` tool says so, closures skip it, and `dev.frozen` is `reads_history` so a probe that finds ≥2 cut entities skips it (clearing nothing) and files ONE recorder finding instead. Entities with no rows are not judged — "nothing recorded" and "recorded until Tuesday" are different claims. **And an absence is a claim the card itself has to check** (`_CARD_CONTRACT`'s "nothing for N h" line): a series can be flat for reasons the cut-off cannot see, and long-term statistics carry no such flag, so a card said a pump "had not cycled in 58+ hours" off one power sensor at 0 W while another sensor on it showed the cycle. Both card prompts now say to check related sensors and `history_incomplete` before claiming nothing happened, and to report a disagreement rather than the silence. The MCP server's `get_statistics` still carries no cut-off note; that file is outside what the development loop may change.
- **A restart re-stamps a clock; it does not cut history** (`ha_data.SHARED_CHANGE_MIN` / `_shared_seconds`). A restart or an integration reload re-publishes every entity it owns with a fresh `last_changed` and the same state, so the recorder writes no row and the logbook no line — and `history_cutoffs` called each of them cut, standing `dev.frozen` down while `sys.history_incomplete` reported a recorder missing rows it was not. A live `last_changed` that six or more states share to the second is not judged; a real cut is one entity changing on its own after its history ends. Nor is a live state that is no reading (`NO_READING`) carrying `restored: true` — Core re-publishing an orphan at startup with a fresh clock and no row — or one whose history also ends on no reading: unavailable then and unavailable now is no change missing. The MCP server's copy of the rule is outside what this loop may change and still lacks it.
- **The thing people check by hand every week was the thing no check read** (`checks/snapshot._supervisor`'s fifth path + `checks/system.update_pending`). Core, the OS, the Supervisor and every add-on publish what is waiting at `/available_updates`, and brAIn asked after backups, add-ons, the host and Core and never that — so the one question a person opens Home Assistant to answer was the one brAIn could not. It rides in the **same gather** as the other four, which is what makes it free, and it is its **own snapshot key** rather than a field on `supervisor`: a Supervisor that listed its add-ons and refused this one has answered every other system check and not this one, so folding it in would take `sys.backup_stale` and `sys.addon_down` down with it. An empty list is a real answer and a shape the unwrapper cannot read is not — `result.get("available_updates")` is required to be a **list**, or the key stays `None`, because `or []` there is "you are up to date" invented out of a 500. **One row however many updates**, `evening.left_open`'s rule: this is a single visit to one screen and a row per add-on is six cards to dismiss one at a time about one afternoon's work; the text is stable and the count that moves every week lives in `detail`, or every pass files a new finding. Its urgency is `whenever` against the `check:sys.` family's `today` — an update waiting at 23:00 is the same update at 08:00, where its siblings are a disk filling up and an add-on that is down. **It ships in `SHADOW`**, and the set is no longer empty, so each entry now carries the release its fortnight started in and the test pins the contents rather than counting them. **A new snapshot key is what proves a frozen corpus entry is frozen**: every committed house predates it, so the check is skipped on both — the honest answer — and the clean-house expectation asserts that each skip names a key that house *predates* rather than the entry being rebuilt to make the number go away. That is also what surfaced the collision underneath: `score_checks` passes `run_all`'s per-**check** skip map through under the same word `replay.render` uses for an **entry** it refused to grade, so the first check to be skipped on a frozen house turned both of them into "skipped — {...}" with nothing scored and recall 0% — two different claims under one key, invisible for as long as no checks entry had ever skipped anything, and `entry_skipped` is the line that tells them apart.
- **A correction reaches the RULE, and the check reads it off the snapshot** (`facts_store.exceptions` / `exception_map` / `House.excepted` / `server._record_exception`). Wrong settled one wording in the ledger and the same check made the same mistake in new words on its next pass — the bullet on `✕ Wrong` says as much and 2.2 is the answer it named. `_end_finding` with `kind == "ignored"` on a `check:` row writes a fact whose `predicate` is `exception:<check_id>` under that entity (`*` for the whole entity), and `checks/snapshot.collect` loads `exception_map` into `snap["facts"]` — a snapshot key like any other, `{}` on failure, so the checks stay pure over what they are handed and a store that could not be read excepts **nothing**, the direction in which being wrong shows a card. `dev.frozen`, `dev.implausible`, `chore.waiting` and `base.unusual` ask `house.excepted(eid, id)` and skip; the rest of the catalog can read it the day a house says it is wrong about them. `tests/test_facts_store.py` drives the real `_end_finding` into the real `devices.frozen` over a real snapshot, because a predicate written in one module and read in another is a wire format and only a round trip proves it.
- **Every per-entity check asks `House.should_report`, and the AST sweep holds it** (`tests/test_scoped_corrections.py::TestEveryCheckAsks`). Any function in a check module building a row with `text` and a non-empty `entity_id` must call it. A snapshot with no `corrections` key falls back to `snap["facts"]` (the WP6 exception map), so nothing standing down starts filing because of how a pass was built. `excepted` is kept for its callers' tests.
- **House checks are findings that cost nothing, and they clear themselves** (`panel/checks/`). A check is a pure function from one snapshot of the house (`checks.snapshot.collect`: states, registries, services, the YAML config files with HA's own tags tolerated, `.storage/trace.saved_traces`, a week of daily statistics, sixty days of battery means, the storage-mode dashboards) to wire-shaped findings under `source: "check:<id>"`; `run_all` files them through `findings_store.add_many` like every other producer, so they dedupe against the settled ledger and ride into the analyst's prompt block. Three rules keep them honest. **Finding text is stable across runs** — the store dedupes by it, so the number that changes ("9 days left", "since 3 Sep") lives in `detail`, and `findings_store.refresh_details` updates it in place. **Only a check that RAN may clear** — `clear_resolved` removes open rows (never `fixing`/`fixed`: those are a person's or the fixer's) whose source is in the set of checks that ran and whose key was not re-reported; a check skipped because its snapshot key was unavailable, or one that raised, is not in that set, because "I could not look" and "it went away" are different claims and only the second may delete a row. Clearing writes no memory line and no ledger entry: a problem that went away on its own is not a fact about the house, and if it comes back the check files it again. **A check that fires on a healthy house is worse than no check** — every rule has a floor or a window, `tests/test_house_checks.py` asserts each silent on the clean fixture before asserting it finds the planted row, and the scorecard is what proves it in the field. Two traps found by driving them: a service name has the shape of an entity id (`light.turn_on`), so `House.entity_refs` skips the values of `service`/`action`/`trigger`/`platform` keys and anything in the registered services set; and `age_days` of a trace from this second is `0.0`, which `or 99` turned into 99 and dropped the freshest evidence — test `is not None`, never truthiness, on an age.
- **Inside a template a `domain.object` token is not always a reference** (`checks/_util._template_spans` / `_not_a_ref`, `automations._without_field_hints`). `"switch.pump_" ~ zone` builds an id, `zone.split('-')` is a method on a loop variable, and a `{% for zone in … %}` variable's attributes are not entities; `entity_refs` skips a token followed by `~` or `(`, or whose domain a `for` in that string binds — only inside `{{ }}`/`{% %}`. `auto.dead_ref` also ignores a script field's `example`/`default`/`selector`. `states('sensor.x')` is still a reference.
- **The second set of checks reads what Home Assistant is not.** 1.29's checks all read Core; the ones that matter most read around it, so `checks.snapshot` grew two keys and a third. **`supervisor`** is `/backups`, `/addons`, `/host/info` and `/core/info`, gathered rather than awaited in turn — and each add-on row is folded together with its *own* `/addons/<slug>/info`, because the list endpoint does not carry `boot` and `boot` is the entire difference between "somebody stopped this on purpose" and "this was meant to be running": `sys.addon_down` reports a `boot: auto` add-on that is stopped, and an add-on whose `/info` did not answer carries no `boot` at all, which reads as **I could not look** and files nothing. **`recorder`** is one `stat` of `home-assistant_v2.db` plus `purge_keep_days` from `configuration.yaml` — an `!include`d recorder block reads as unset (`sys.recorder_size` then names HA's own default rather than a number this invented), and a database that is not a file under `/config` takes the whole key **unavailable** rather than reporting as small, because Postgres is not a smaller database, it is a question this cannot answer. **`zha_devices`** is `zha/devices`, which errors on a house with no ZHA and so goes unavailable: no Zigbee is not an unhealthy Zigbee. `dev.zha_unseen` keys on `last_seen` and *not* on `available`, which is the whole point — a sleepy sensor is `available` between check-ins, so availability says nothing and silence says everything. `dev.zwave_dead` reads the node status sensor the controller publishes, and `dev.unavailable` **skips a device it claims**: the same box under two fixes ("restart it" and "re-interview it, or remove the failed node") is how a list stops being read, and the two checks share `_zwave_dead_devices` so they can never disagree about which box that is. `auto.trigger_unavailable` is the one with no symptom at all — the automation is on, nothing errors, no trace is written, and it can never fire again — so it is deliberately separate from `dev.unavailable`, which reports the sensor: only the second answers "why did the hallway light stop coming on". It reads both spellings of the trigger key (`trigger:` and 2024.10's `triggers:`, `platform:` and `trigger:`), and it stands down for a missing entity (`auto.dead_ref`'s) and for a switched-off automation (`auto.forgotten_off`'s). The `reg.*` checks are the ones most at risk of the "fires on a healthy house" failure and each carries the floor that answers it: `reg.no_area` says nothing below three areas, because a house that has not set areas up is not a house with a problem; `reg.unused_helper` gives a helper 30 days to be wired up and checks the configs, the storage dashboards **and** other entities' attributes in one `entity_refs` pass (it rebuilds the services set per call, and this walks the whole house); `reg.orphan_device` spares a device another names as its `via_device`, because a hub with no entities of its own is still doing a job; and `reg.hardware_name` requires a hex run to carry both a digit and an `a-f` letter, or `Bedroom 123456789012` and `deadbeefface` both read as hardware and neither is.
- **The networks a device talks through are checks, and they ship live** (`checks/network.py`, `checks/integrations.py`; the owner's ask, with conservative floors rather than `SHADOW`). Three snapshot keys, each its own so an unreadable source skips only its own checks: **`wifi_history`** (a week of each UniFi wireless client's tracker plus one probe entity of the device its MAC joins it to through the device registry's `connections`, `network.wifi_history_candidates` shared by collector and check, at most `FLAP_FETCH_MAX`), **`zwave_nodes`** (`zwave_js/node_status` + `node_statistics` per node in one `_ws_calls` round trip: a status, and a `last_seen` a restart does not reset — `last_changed` is never read, which is how a dead battery node hid for a year) and **`core_log`** (the Supervisor's `/core/logs`, folded by `integrations.summarise_log` by logger and message with addresses, ids and numbers folded, redacted through `reports.redact`). `net.wifi_hung` is a client UniFi holds while its own entities have been unavailable two hours, ONE row per access point; `net.wifi_flapping` counts separate spells into unavailable with the tracker never leaving, and **a minute many entities dropped together is a restart or an integration, never a device's drop** (`_mass_moments`, `after_restart`) — every UniFi tracker dropping together repeatedly is `net.unifi_dropped`'s single row. `net.zwave_silent` is a battery node silent past three wake-up intervals (26 h when unknown), `net.zwave_link` RSSI ≤ −90 or a round trip ≥ 150 ms; `net.zigbee_weak` a router under LQI 40, `net.zigbee_silent` mains past 6 h or battery past 26 h, and a week is still `dev.zha_unseen`'s — one classifier (`zigbee_quiet`) so a device is never both. **One box, one check**: `dev.unavailable` stands down for a hung client and a quiet Zigbee device, `dev.battery_low` for a silent Z-Wave node, as it does for a dead one. A device disabled or labelled not in use (the label's name, or its slug id when the label list could not be read) is never raised. `integ.log_flood` is a logger repeating an error more than 100 times in a day, one row per logger naming the device or address the house knows, never brAIn's own. `sys.entry_failed` is now titled Integrations and waits a day (`ENTRY_STUCK_S`) off a ledger the collector keeps (`system.stamp_failing`, `ENTRY_FAILING_FILE`), seeded on its first pass from when the entry was created so a row already on the list is not cleared and refiled; `dev.battery_low` reads a low-battery flag (a battery-class binary sensor) from any integration, once per device. A catalog entry's `source_title` names the producer on the card (`title_for`). **One device is one drop card, and one integration-wide outage is one card** (`network.device_keys`, `findings_store._fold_devices` / `DROP_CHECKS` / `is_drop_report`, the row's `integration`). One Wi-Fi switch was three open rows — a check's on its switch, a card's on its UniFi tracker, a third inside a four-device card — and the UniFi integration losing its controller was two (#440): every fold keyed on an ENTITY. The panel puts each entity's device into `_NAMES` (`device`, a UniFi client's tracker joined to the device it is a client of through the registry's MAC, `wifi_history_candidates`' join), and after every filing a row about a device dropping folds into a live row whose devices include it (the widest first, then a house check, then the oldest), taking its evidence less any count the card's own detail contradicts (`quotes_other_counts`); a row carrying `integration` (`net.unifi_dropped`, a log flood that names nothing of its own, an overnight cause about a line that names nothing of its integration's — filed on NO entity since a blind's errors were filed on a sibling cover through the integration's first entity; a line naming the integration's own entity by its friendly name is filed on it, and several of one hub's things on the hub, `sre._subjects`) folds with every other row about that integration as a whole. `_fold_shared`'s refusals apply.
- **`base.unusual` is the check most able to fire on a healthy house, and every floor on it answers that.** Six spreads (a MAD is ~0.67σ, so the bar is higher than the number looks), nine when the answer came from the whole history rather than this hour, and a `MIN_ABSOLUTE_MOVE` because six spreads of a band 0.02 wide is 0.12 degrees. It **stands down for a reading `dev.implausible` claims** — a thermometer at 99°C is impossible before it is unusual, and the same sensor under two different fixes is how a list stops being read; they share `devices.out_of_range` so they cannot disagree, exactly as `dev.unavailable` and `dev.zwave_dead` share `_zwave_dead_devices`. And past `MAX_ROWS` it says **nothing at all**: more than a handful at once means the *baseline* has stopped describing the house (a heating season starting, a meter replaced), and fifty rows would be reporting the measurement rather than the home. `base.stale` is the companion nobody would think to write — every baseline check silently says nothing while the store is stale, which is indistinguishable from a house with nothing odd in it, so the measurement having stopped is itself a finding.
- **A season turning is not a reason for `base.unusual` to give up whole** (`checks/baseline.moved_together`). 23, 17 and 17 rows against a limit of 4 left every real anomaly unchecked. Over the cap, sensors of one kind (device class, else unit) that moved the SAME way together stand down as the season (`forecast.decline`'s rule, one shared function), and what is left is reported only if it then fits `MAX_ROWS`; otherwise it still says nothing. - **An override is the only signal a house gives about an automation being wrong for it.** A person putting something back within `OVERRIDE_WINDOW_S` of an automation moving it: the automation ran, nothing errored, and the light is off, so no check that reads Core can see it. Three rules keep it honest and all three are asserted against the cases they must NOT fire on — **the state has to actually differ** (a person pressing "on" after a rule turned it on is agreement, and counting it would put the best-behaved automation in the house at the top of the list), **one automation move is undone once** (somebody nudging a dimmer three times is one disagreement), and **an automation undoing an automation is not an override** (that is a conflict, and a different finding). `auto.overridden` reads `find_overrides` rather than recomputing any of it, and fires at three in a day: once is a one-off, twice is a coincidence.
- **A count with no denominator is not evidence, and `auto.overridden` shipped as one.** Three undos of a rule that ran three times is a rule that is wrong for this house; three undos of one that ran three hundred is somebody having an unusual Tuesday — and the check reported both identically, which is the shape of finding people learn to ignore. `actions.automation_moves` counts what each automation did over the *same* mined window (keyed the same way the overrides are, so dividing needs no join that could mismatch) and rides beside them in `collect`, because two passes over the same data is two chances to disagree about the window; the check fires on a **share** once `RATE_MIN_RUNS` makes a share mean anything, and below that the count stands alone because 3 of 3 is 100% and says nothing the count did not. **The other half of that check is the one that never reaches three in a day at all**: somebody putting the same thing back once a day for a month is the clearest signal a house gives, and a check that only looks at today cannot see it. `panel/override_ledger.py` is the deliberate exception to `actions.py` persisting nothing, and a *narrower* claim than the rule that made — what that rejected was the **timeline**, tens of thousands of rows a day and a second copy of the logbook; overrides are a handful of rows a week, and without them "you undo this every weekday morning" is unsayable. Passes overlap (every 6h over a 26h window) so every override is offered four or five times: **the id is the event, not the offering**, or one disagreement is filed as five. A pattern is about **days** — four overrides in one evening is one evening — so `MIN_DAYS` gates it whatever the count. And `_band` reports the hours that are **occupied, not the window that found them**: the first cut searched four-hour windows and took whichever start it tried first, so fifteen overrides all at 08:10 came back as *"between 05:00 and 09:00"*, which is not a loose answer but a condition somebody would write that stands the rule down for three hours nothing happens in; ties now go to the tighter span and the band is shrunk to its first and last occupied hour, wrap included (22:00–01:00 is a real bedtime). **And a pattern has to still be happening**: the ledger keeps 60 days so a shape has room to appear, but a rule somebody *fixed* goes on having a beautiful shape in that history, and a finding that cannot clear for eight weeks after the problem is gone is the list nobody reads — `RECENT_DAYS` gates on the last override, and `pattern` takes the pass's own `now` rather than the wall clock so it ages from the same instant every other check does.
- **`auto.conflict` is the finding the override rules named and deferred.** A person undoing a rule is evidence the rule is wrong for the house; two rules undoing each other is neither being wrong on its own — they disagree, the entity ends in whichever state the later trigger left it, and *which one wins depends on the order two triggers happened to fire in*. Nothing can see it: both ran, neither errored, no trace shows anything, and the result differs from one day to the next. `find_conflicts` carries `find_overrides`' three rules for the same reasons and adds a fourth — **an automation cannot conflict with itself**, or a rule that sets a light on and then off inside one run reports itself as its own opponent — and a person's move *ends the pairing*, because what follows it answers the person rather than the rule that ran before them. The pair is keyed **unordered**: A-undoes-B and B-undoes-A is one disagreement between two rules, and keying it either way round files it as two, each sitting under its own floor. `CONFLICT_MIN` is 2 rather than 3 because nobody is choosing to do this — a person overriding twice may have changed their mind, while two rules that have disagreed twice will disagree every time their triggers land in that order. **But a sequence is not a fight, and it was most of what this filed** (`checks/automations.RACE_S`): a motion-on rule and a no-motion-off rule put the light back every time, inside the window, in a different state, from a different automation — two rules doing what they were written to do, and the scorecard read 3 of 4 marked Wrong. A pair is reported only when it has undone each other in **both** directions, or when the second landed within `RACE_S` of the first (one trigger reaching two rules, where the winner is the order Core ran them in); a one-way pair slower than that says nothing whatever the count. `find_conflicts` still records every undo — the direction and the gap are the check's to read, so the miner stays one implementation of *what happened*. **And a rule a person sets off is the person** (`checks/automations._relays` / `_is_press`, `actions.find_conflicts(relayed=, triggers=)`, `RELAY_S`): an automation whose every trigger is a press (a scene controller's `event` entity, a Z-Wave value notification, a device trigger whose type is a press, a tag) is somebody's hand with a rule in between, and so is a rule answering within `RELAY_S` of a person changing what it watches (a room mode picked in the UI) — its move ends the pairing exactly as a press on the light does. - **A door being open is not wrong, which is why no check could report one** (`panel/closures.py` + `evening.left_open`). Every other check reads a state and knows whether it is wrong; a door is wrong at 23:40 in a house that has it shut then on 49 nights out of 50 and is nothing at all in one that leaves it open all summer, so the rule needs a measurement of *this* house or it is a threshold somebody guessed. `baselines.py` cannot supply it — it measures medians and spreads over numbers and a door has neither — so what a binary entity gets instead is **how much of each hour of the week it is open**, in seconds open over seconds observed. Four bounds. **Only closures** (doors, windows, locks, covers, garages, by device class and domain): a hall motion sensor is on every evening, and including it buries the one row that matters. **Time-weighted, never sampled** — a door open ten minutes and one open ten hours are identical to a sampler that catches each once, so the answer would be about the polling rather than the door. **A bucket has to have been watched**, and `usual_open` returns `None` for one that has not, which is a different answer from "never open then" and every caller branches on it. And **it decides nothing**, the same split the baselines keep. `spread_interval` is the part that had to be right: a door shut on Friday and opened on Monday is **one** interval across sixty buckets, so it walks the hour boundaries rather than charging the span to the hour it started in — which is how a rarely-changing entity would otherwise report almost every hour as unwatched — and it advances even across a DST boundary, where a clock that does not move is an infinite loop. - **A new check runs where nobody can see it, and it is a separate STORE, not a status** (`panel/shadow_findings.py` + `checks.SHADOW`). A separate file cannot. What it buys is **agreement, not precision** — nothing there has an ending on it, because nobody can press Wrong on a row they cannot see, so what is countable is whether the analyst or another check said the same thing; the count reads the settled ledger as well as the list, or a check looks worse the better the house is kept, and **days ride with it** because fourteen rows over one day is one evening. It ships **empty** (a set with something in it "for now" is how a trial becomes permanent) and **nothing is promoted automatically**: moving an id out is a code change somebody makes reading the corpus number and the shadow number, because a producer that promoted itself on a threshold would be a threshold nobody can see deciding what a house is told.

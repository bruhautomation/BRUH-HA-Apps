# brAIn: the findings store and its endings

What a finding is, how it ends (Wrong, done, To Do, mute), the settled ledger, folding and dedupe, corrections and their scope, the interpreter, the decision trail.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **"Check again" is the one press on a finding that says nothing about the house** (`h_finding_recheck`). A check reads one instant, so it can file something true of a moment that has since passed — a device unavailable while its hub rebooted, a reading implausible while a printer was hot, an add-on stopped mid-update. Every other button makes a person claim the problem is fixed or was never real, and neither is true of a state that simply went away; the scheduled pass would clear it in up to `checks_interval_hours`, which on a list you are looking at now may as well be never. Three rules and all three are `clear_resolved`'s, reached by a press rather than by a timer. **Only a check may be re-run** — a finding from the analyst came out of a Claude run over a whole category, and re-running that is Regenerate on the card: it is not free and would not answer this question anyway, so the button is absent there rather than failing. **A check that could not look clears nothing**, and the skip or the exception is named. **The whole check clears, not the row** — a re-run that finds two of its three rows gone clears both, because clearing only what was pressed leaves the others to be pressed one at a time about a thing the same look already proved is over. It settles nothing and writes no ledger entry: a problem that went away on its own is not a fact about the house, which is the difference between this and Wrong.
- **Three kinds of knowledge, and they don't mix.** Memory = what is *true* of the home. A hypothesis = what brAIn might have *wrong*. A **finding** (`panel/findings_store.py`) = what is *broken*. The generation contract keeps them apart too: `learned` feeds memory, `findings` feeds the work list.
- **Three kinds of knowledge, one list of decisions.** The last two are different knowledge and stay in different stores; they are the same *job*, which is a question only the person living there can answer, and that job has exactly one surface: the Findings tab. Open hypotheses ride down `/api/findings` (`server._findings_payload`) and `open` spans both, because "how much is waiting on me" is the only question a badge on a work list answers. They used to be answerable in three places — inline under every insight card, in the Memory tab's "Waiting on you", and counted by neither badge — so answering one left the other two rendering an open question, and the Memory badge counted work the Findings badge didn't. `questions` is gone from the stored card, the `/api/questions*` routes are gone with it, and the Memory tab has no badge: what is left there is a queue that files itself and a document to read, and a badge counting work nobody has to do is how the badge next to it stops being read.
- **A button that ends a finding has to be able to say why, and the why is the half that teaches.** "Ignore" described what happened to the row; what people mean is almost always "you have misread my house" — the sensor is not stuck, it is a contact on a cupboard nobody opens — and a key in the settled ledger suppresses one wording while the next run makes the same mistake in new words. `✕ Wrong` is the same ending with a `note` (`POST /api/finding/{ts}/wrong`, `/ignore` kept routed for a panel served before the update), `hypothesis/{ts}/reject` takes the same note for the same reason, and so does `done` — but `source` is per-verb, not "a note means a correction": waving a report off is evidence brAIn has misread the house, while saying how you fixed something corrects nothing and is simply more of the fact already being recorded. The note goes two places and **neither is a rule**: `findings_store.prompt_block` renders it verbatim as `They said: …` under the finding it corrects, and it is queued to the memory inbox with `source="correction"`, where the consolidator is told the report is not a fact, to record the standing truth the reason implies, and to record nothing if there isn't one. Deliberately a judgement call — nobody phrases a correction carefully, and a button that wrote whatever was typed into `memory.md` would file the thing being denied. **The box is never required**: "not a problem here" needs no essay, and a mandatory field turns a one-press dismissal into a chore and fills with "no". A note on an ending with no `noted` template (`done`) falls through to the ordinary memory line rather than silently costing it. The reason box opens in place of the card's buttons, inside the card, because you are correcting something and it has to stay on screen while you write about it — and the chat strip's `✕ Wrong` opens the same box, since explaining it to Claude in the conversation reaches that conversation and the note reaches every future one. `setChatFinding` clears it: the strip is one reused element, unlike the cards, which are rebuilt.
- **Findings are mirrored to the shared volume, because /data is invisible to Home Assistant.** `findings_store._write` republishes `/config/.brain/findings_state.json` on every store write — hooked there so no code path can change the store without it — and `publish_state()` re-runs it at panel startup so a boot never serves last week. The mirror is derived and never read back; the integration's `FindingsWatcher` (primed at startup, same no-replay contract as `LearningWatcher`) diffs it into `brain_finding` events, and `sensor.brain_open_findings` reads it. The publish is skipped when the shared volume's parent does not exist (a dev checkout must not grow a stray `/config`) and an OSError is a logged warning, never a lost finding — the row is already safe in /data before the mirror is touched. **Notifications go to the CREATED list only** (`server._announce_findings`): `add_many` dedupes across every status and the settled ledger, which is the whole reason a re-report cannot ring a phone twice; the notify target is the `findings_notify_service` option read live from the Supervisor snapshot with the run.sh env export as fallback, and a failed delivery is a log line because the finding is already on the list.
- **A finding leaves the list when a person ends it, and then it is gone.** Four presses end one — "I've fixed it", "Wrong", "Got it" after an automated fix, and "＋ To-do" (which defers the memory line to the moment the chore is done — see the to-do store's bullet) — and each does the same three things: a plain line into `memory.md` (both endings are facts about the house, phrased differently because they *are* different facts), a normalised key into the settled ledger (`findings-settled.json`), and the row deleted. There is no archive of dismissed cards — rendering a per-status pile beside a list that is meant to empty invited people to treat it as the record when memory already is. **The ledger is an index, not a queue** — same rule as the facts ledger, and `add`/`add_many`/`is_known` all consult it, because settling deletes the row and deduping against the list alone would turn every ending into a Forget. `unsettle` is the one thing that removes an entry, and only because a person pressed "Let brAIn raise it again" — which stops the suppression and nothing more, so nothing "comes back" unless the next analysis finds it still there. **That press lived only in this file for four releases**: the route had no caller in the panel, the CLI or the integration, because the rule as written forbade any view of the ledger at all — and a button that exists only in prose is a button nobody can press. So the rule is **narrowed to the invariants that made an archive bad**, not dropped, and `test_there_is_no_archive_of_dismissed_cards` pins each: an **Answered** filter whose `match` returns false for every live row (settling deletes the row, so a filter over the list could only ever be empty), **counted so it can hide at zero**, **capped** in what it renders, **absent from the badge** (`open` counts work waiting on a person and an answered thing is by definition not), and carrying exactly **one verb** — never a restore, a reopen or a route back into `/api/finding/`. A per-status `ignored`/`fixed`/`Everything` chip is still refused, which is what the guard was written against. `fixed` is therefore *live*: brAIn changed something in the house and news nobody has read is not settled. Dismissals from before the ledger are folded in at startup by `migrate_settled()`.
- **A finding you have accepted is not a decision any more** (`panel/todo_store.py` + `findings_store.SETTLE_KINDS`). The Findings tab is a list of DECISIONS waiting on a person, and the commonest honest answer to a finding had nowhere to go: not "I fixed it", not "you have this wrong", but *yes, that is real, and I will do it*. So a flat battery sat there as an open question for as long as it took to get round to, the badge counted it every day, and a list of decisions filled up with chores nobody could clear without lying about one of them. **＋ To-do is the fourth ending**, and it does what every ending does — the row deleted, the key settled — with one thing deliberately missing. **It writes NO memory line**, because nothing is true about the house when you put something on a list; the fact is written when the chore is ticked off, which is when it becomes true, in exactly the sentence `done` would have used. That is also why `accepted` is its own settlement kind beside `fixed` and `ignored`: the scorecard counts it as the report being **confirmed** (agreeing to do something is agreeing it was real, and counting it as nothing until the chore is finished would make a producer look worse the more of its reports people took seriously and had not got round to), and completing the chore later re-settles the *same key* as `fixed`, which is an upgrade a shared word could not express. `remember_answer` is the door for that, because `settle_and_clear` needs a row to delete and the row has been gone for weeks — and it keys on **what the item stored** rather than on a second derivation from a copy of the text, since the two agree right up until they do not. Five rules on the store. **An item carries the finding's evidence and never a pointer to it**: the whole point of the move is that the row goes away, so a reference dangles by construction, and copying the text, detail, fix, entity and producer is also what makes a hand-added item the same kind of thing rather than a second-class row. **The id is minted past what is taken** — `proposals.add`'s bug, in the module that would otherwise have repeated it. **Dropping an item undone releases the suppression** (a moved finding's key; a hand-added one has none, which is the whole of what `origin` is for), because deciding not to do something is not evidence it stopped being true — `clear_resolved`'s own argument, so if it really is over nothing comes back. **Finished chores are kept, capped and counted by nothing**: the Findings tab refuses an archive because memory is the record of a *decision*, and this is a list of chores, where forgetting what you did this week means being unable to answer "did I already do that" — its one verb is *Put it back*, which deliberately does not take the memory line with it, the same admission the undo token's five-minute life makes. And **the cap refuses the add rather than making room**, because the room would be made by dropping something somebody else put there. `h_finding_todo` creates the item **before** the row is deleted and refuses the whole press if it cannot, since a finding that vanished into a list that would not take it is the one outcome with no way back; `_complete_todo` is lifted out of the route for `_end_finding`'s reason, because the tab's Done and a tick in the To-do app are two doors on one answer.
- **A reworded report about the same entity from the same producer is the same report** (`findings_store` subject fold, `SUBJECT_FOLD_EXCLUDED`). Text dedupe holds for checks, whose text is stable by design; a model-written producer rewords every pass, so ten cards about one sensor across three weeks was the dedupe working exactly as written. Model-written producers (no colon in the source) also fold on `(entity_id, source)` against every live status and against a settled `ignored`; never a `fixed` (a fixed problem may come back), never a row with no entity, never the safety/security/correction family. The settled ledger now stores `entity_id`, so only answers given from 2.12 on fold. **And across model-written producers, against LIVE rows only** (`CROSS_FOLD_STATUSES` / `CROSS_FOLD_EXCLUDED` / `_cross_folds`): two insight cards reading one sensor each filed their own wording of one diagnosis, six rows in ten days, because the fold was keyed on the source. A model-written report about an entity that already has an `open`/`triaging`/`held`/`needs_you` model-written row folds into it whichever producer wrote it, and the newer `detail` replaces the old (status and verdict stand, so a held row absorbs every re-report). Narrower than the per-producer fold on purpose: never against a row brAIn `fixed`, never against the settled ledger (a Wrong was said to one producer about its claim), and never the Resident in either direction, because a case is the look itself and refines the row it was sent to — which is also the boundary `test_subject_fold`'s different-producer case holds.
- **A question about an entity a check already reported folds into the check's row** (`findings_store.ASKED_SOURCE_RE` / `_check_host_key` / `_fill`). An asked card (`custom-<id>`) or the chat filing about an entity with a live `check:` row is the same card twice; it folds into the check's row, whose text (the key it re-reports and clears under) and detail (rewritten every pass) stand, and the asked report's detail and fix fill only what the row lacks. Only asked producers: a scheduled card's claim about the same sensor is its own (`test_cross_producer_fold`). Never into a `fixed` row, a `sec.*` or safety check's row, and never from the Resident or the safety/security/correction family.
- **A chore marked done is checked by the rule that filed it** (`todo_store.CHORE_SETTLE_S`, `server._rerun_check`). `clear_resolved` reopens a `check:` chore finished more than two hours ago whose check still reports it ("Came back: …", the ledger back to `accepted`), and `_complete_todo` schedules a re-run for the same moment — `_verify_fix`'s rule, sharing its helper. The delayed re-run is in memory; a restart leaves it to the next scheduled pass.
- **A rule wrong about this house is muted at the DOOR, and the press clears what it already filed** (`settings_store.muted_sources` / `triage.gate(rows, muted)` / `findings_store.clear_source` / `server._mute_source`). The scorecard existed to say a producer was wrong about a house — `forecast.decline` 0 confirmed against 3 marked Wrong — and the only answer the tab had was Wrong one row at a time, which settles one *wording* in the ledger and leaves the next pass to make the same mistake in new words. "Stop raising these" is the press for the rule. Three decisions. **The rows are dropped in `gate` and nowhere else**, because it is the one door every producer files through (the AST sweep already holds that) — filing them and hiding them would put a mute into `LIVE_STATUSES`, the mirror, the badge and every dedupe, where a row that never arrives touches none of them; `gate` reads the setting itself when not handed one, so no caller has to remember to ask, and an unreadable settings file mutes **nothing**, the direction in which being wrong shows a card. **The press clears and the gate prevents**: `clear_source` takes the producer's `open`/`triaging`/`held`/`needs_you` rows and never `fixing` or `fixed` (a conversation somebody is having, a change brAIn made), settles nothing and writes no memory line — a mute is a statement about the RULE and not about the house, `clear_resolved`'s reason for writing nothing — and unmuting brings nothing back until the producer reports it again, `unsettle`'s rule. And **a muted producer is named by its own title** (`Sensors frozen on one value`, off `checks.get_check`, never the group's `Device check`, which three times over is three things nobody can tell apart); a non-check producer's title lived on the rows the press just cleared, so `_mute_source` reads it *before* clearing and `_muted_rows` falls back through the category, the ledger, that stash and the id. The mute route's flag is `ok` because `muted` is the payload's list, and the first cut spread the payload *after* the flag and returned the list under the flag's name. **"What you'd need to do" has a second author** (`findings_store.set_fix` / `fix_by` / the `advice` resolution kind): the chat's `offer_resolutions` may carry `advice`, whose label is the sentence and whose press (`POST /api/finding/{ts}/advice`) puts it on the card and settles nothing — it is deliberately NOT in `FINDING_VERBS`, has its own route ahead of the `{verb}` catch-all, hands back no undo token because nothing was taken away, and takes the store's own cap (`MAX_FIX`) rather than a button's ninety characters, since a sentence naming the hub and the automation does not fit in a button. `fix_by` is on the ROW (`""`/`triage`/`chat`) and the card says whose sentence it is, because a specific instruction and a generic one read alike until you know which looked at your house. **Two read-only tools read the panel** (`get_findings`, `get_health`, over `_panel_get`, `explain_change`'s arrangement): the Findings tab was reachable by nothing a run could call, so "what needs attention" was answered by guessing and "is brAIn OK" not at all; both trim a page of JSON to what a model can act on and neither settles anything, and they are on `ANALYST_TOOLS` because a card asking whether the house already knows about a problem is exactly the read an unattended run should make. **And a notification opens the panel** (`notify_router.open_link` / `addon_options.panel_path`): a tap landed on Home Assistant's front page with the row three taps away; the companion app takes a relative path as `url` on iOS and `clickAction` on Android, both harmless on the other, gated the way the buttons are (`can_answer`, because another notifier means something else or nothing by those keys), and the path is the Supervisor's own `slug` under `/hassio/ingress/` read off `/addons/self/info` — no slug is no link, never a guess, since a made-up path opens the wrong add-on or nothing.
- **A rule the scorecard says is wrong here is OFFERED for muting, never muted** (`panel/mute_offer.py` / `server._mute_offer_pass` / `_end_mute_offer`). `auto.conflict` 1 against 4 Wrong and `forecast.decline` 0/3 kept filing and nothing offered to stop them. A producer with at least `MIN_ENDINGS` endings, `MIN_WRONG_SHARE` of them Wrong and its latest ending a Wrong (`scorecard()`'s `last`) gets ONE question through `add_case` on `_checks_loop`'s tick (own stamp, no new timer, free, no gate); Yes is `_mute_source`, No is remembered with the record it was declined at and re-asked only when the Wrongs double. `notify_learn`'s pattern: the ending is intercepted in `_end_finding`, writes no memory line, and Undo of a Yes unmutes. `cases.UNMUTABLE_SOURCES`, producers already muted and the question-asking producers themselves are never offered. **A rule has one name** (`findings_store._check_title` / `_rule_titled`): the question asked "Stop raising 'Device check'?" because the pass read the raw scorecard, whose title was the GROUP a check files under — a word naming a dozen rules, the useful battery rule among them — while the fault list and the card said the catalog's own title. the scorecard and `source_titles` now name a check by its catalog title (`_rule_titled`), as the card's `_producer_label` already did, so the card, the scorecard, the fault list, the mute question and History agree; the stored `source_title` and the mirror's copy (which a Repairs issue shows) are untouched, and no two checks share a title (`test_one_name_per_rule`). The question says what kind of report the rule files (the scorecard row's newest `example`) and where to undo a Yes in the panel's own words — History › Ignored › Restore on "Everything like this" (`mute_offer.WHERE_TO_RESTORE`) — never "the scorecard", a word nothing on screen shows (#439). `auto.conflict`'s `except_evidence` already covers a pair with a NEW partner (`should_report` is asked of both rules; `test_checks_wrong_in_the_field` holds it), so a row filed under an automation the exception never named does not involve the one it was recorded under.
- **A finding about several things carries all of them, and its sentence is never cut inside a name** (`checks/_util.join_names(budget=)` / `LIST_BUDGET`, `findings_store.item_labels`, `cases._item_list`, `caseItemsNodes`). A dashboard row ended "the scene “…”, the select…" and an automation's "and 7 more.…": an inline list of long names ran past the store's `MAX_DETAIL` cap (whose sentence cut ends `.…`) and the card's three lines, and the rest of the list was nowhere. An inline list now stops at a character budget as well as a count, `org.dashboard_dead_ref` and `auto.dead_ref` carry the whole list as `items` (as the grouped checks already did), and a case naming two or more gets `item_labels` — each by the house's name, or the id read aloud for one that no longer exists, never the id — which the card shows as a count line ("8 entities · Show all") over the full list. `measure-today` holds both at 390 and 1200 (#437).
- **Every finding says what To Do will say** (`findings_store.todo_text` / `derive_todo_text` / `todo_text_of`). An item on To Do read as the finding's claim ("Battery at 9%") or the check's name; Morph's To Do needs the errand ("Replace the battery in the hallway motion sensor."). The producer writes it where it can — `checks.run_all` from the check's `fix` and the friendly name (`_todo_text`, one `House` per pass), the Resident's `CASE_SCHEMA.todo_text`, rewritten by `refine` — and a row without one is DERIVED on read, deterministically: the first sentence of `fix` with the first "it"/"its" turned into the thing's name, else "Look at <name>.", else "Look into: <claim>". Stored only where written (`_case_fields`' absent-not-empty rule) and never a question (`clean_todo_text` refuses one). `_move_finding_to_todo` files the item under it (or under a resolution's `fix`), with the report as the item's `claim` and the case id as `from_case`; the memory line written when the chore is done, and the settled ledger's entry, are still about the claim.
- **A chore is a decision already made, so it is not in the queue** (`cases.FEED_KINDS`). The read-model lists all four stores and a finding moved to To Do came straight back beside the real findings as a card with no way onto the list. Accepting a finding is the press that takes it OFF the queue and off its badge, so `list_cases` defaults to every kind but `chore` and `open_count` follows. It is a default and not a removal: a chore is still a case (`get` answers for it, its endings ride `CASE_HOOKS`, To Do's Done and a tick in the To-do app are the same door), and the Resident's "already said" prompt asks for `kinds=KINDS`.
- **A fix that has run is read by what it concluded, not by the row's own claim** (`cases._from_finding` carries `result`/`changed`; `answers.situation` reads `finding_status`).
  - `fixable` is the rule's guess from before anybody looked.
  - `needs_you` is the fixer saying a person has to do this. Leading with *Fix it* there bought another plan run to reach the same conclusion, so it renders as a pair of hands. It keeps the check's own situation where that already was one, because that situation decides the reason the box opens with.
  - `failed` is `fix_failed`. Trying again is a fair press, but it sits behind the ⋯, because the failure is what should be read first.
  - The card shows the report in place of "How brAIn would fix it", which on a finished fix described a plan that is over.
- **A rule's identity includes which rule it is** (`fact_id(…, predicate)` for `exception:` rows). Two checks marked Wrong on one sensor wrote the same text under the same subject, hashed to one id, and the second silently replaced the first: one check stood down, the other came back on the next pass with nothing on screen to say why. Ordinary facts still hash on subject and text, because the same sentence from two writers *is* one fact; a rule is the one row where the predicate is the meaning. The row also carries `about` (the report it was about) and `finding_key`, because "that is normal here" under no report is a sentence no run can use, and the finding key is what lets "Let brAIn raise it again" find the rule without an undo token.
- **One interpreter, and no answer is the old code** (`panel/interpret.py` / `server._interpret` / `_route_ask` / `_reply_routes` / `_repairs_routes` / `_service_routes`). Four boxes take a person's words — the ask bar, a phone Reply, the Repairs reason box, `brain.intent` — and each used to decide what words meant by itself: the ask bar by four regexes on the first word, a Reply was always a question for the Resident, the Repairs box was always a reason for Wrong, the service was always an automation. The `interpret` job (cheap tier, tool-less, `--json-schema`) maps words + SURFACE to routes out of `KINDS`. Five rules. **The model never names a case** — the surface stamps it and a route says only what to do with it (`ENDINGS`). **A surface narrows the vocabulary** (`ALLOWED`): there is no case to end on the ask bar, so a route a surface cannot carry is dropped there and a reply left with nothing is no answer. **No answer is the old behaviour, exactly** — no credential, the day's runaway cap (`MAX_PER_DAY`, in memory), a failed run, an unreadable reply: `parse` returns None and the caller runs the code it ran before the interpreter existed; the regexes are the offline answer, not a second reader. **Pressed surfaces skip the budget and nothing else** (`PRESSED`); `service` answers `auto_enabled` and the budget too. **Nothing here adds reach**: every route lands in code that already exists (the card queue, the intent drop, `_end_finding`, `onboarding.request_study`, `_design_scenes`). One message ends a case once — a second ending in the same reply is dropped, never applied over the first. `automation_edit` is a read-only card (`AUTOMATION_EDIT_FRAME`) because no producer turns a sentence into an edit of somebody's automation.
- **A correction has a scope and a lifetime, and the wide ones are questions** (`panel/corrections.py` / `server._scope_correction` / `House.withheld_by`). "It's always like that in winter" is not "never again", and "none of the garage plugs matter" is a room. The `correct` job answers one of `SCOPES` (`entity_check` < `entity` < `check_area` < `check`) and one of `LIFETIMES`; `plan` checks it, `apply_plan` writes only one entity's reach (a lifetime on the press's own rule, a `*` rule beside it) and a wider scope is `offer_row` — a findings-store `question` under source `correction` whose Yes alone writes the rule (`accept_offer`, `area:<id>` or `check:<id>` subject). **The model never names what the rule is about**: entity, check and room come off the pressed finding. **No scope covers a safety-class or protected entity** — `never_covered` at write time and `House._never_covered` at READ time (`scope_map`'s `never` table), because a room scope written in March cannot know a leak sensor was fitted there in May. **Every rule carries the report's `finding_key`**, so `_undo_finding` (which now always calls `forget_exceptions(key)` and withdraws offers) and "Let brAIn raise it again" take back what the pass added, and a pass that lands after Undo writes nothing because the press's rule it would scope is gone. Lifetimes are arithmetic, never the model's: a resume date, `expires` the day before it (`facts_store._expired` is `stamp < today`), a past or two-years-out date read as permanent, seasons meteorological and swapped south of the equator (latitude off `core.config`). The sentence a person reads is built by `confirmation`, never by a model. The tab's press scopes asynchronously (`_start_correction`); the phone reply scopes synchronously so it can quote what was applied.
- **"I need to fix this light" is a snooze, not a rule** (`corrections.temporary` / `temporary_days`, `server._for_now` / `_snooze_for_now` / `_for_now_routes`, `findings_store.snooze(wake=)` / `wake_returned`, Morph's `kept`). A dashboard clean-up only offered removal, and the household's "I need to fix this light" was stored as a general correction — nothing stayed quiet for the repair and the suggestion came back while the light was still out. A Wrong whose reason says the thing is out of use FOR NOW (being repaired, unplugged for now, "I'll plug it back in soon", "waiting on a part", "fixing it") on a check's row, a Resident case or a Morph suggestion writes no rule, no memory line and no label: the row sleeps for the period the reason names (`TEMPORARY_DAYS`, 14, when it names none; at most `TEMPORARY_MAX_DAYS`), with `snooze_wake` set to the entities it is about, and its undo wakes it. A reason that says it stays that way ("I won't fix it", "do not plan to replace it", "unless", "most of the year") is not temporary and goes the old way. A reply on any surface whose words are temporary is the same Wrong whatever the interpreter read — a memory, a correction, or nothing — unless it asked for something else (a fix, To Do, its own time). Each checks pass calls `wake_returned` with the states it already read, before `clear_resolved`: a snooze whose entities all report again is over, so a check that no longer finds the problem clears its row that pass, and a Morph suggestion to remove that thing's card is dropped and published as `kept`, which Morph closes without declining (the idea may be suggested again if the thing goes for good). Morph's suggestions carry the card's entity (`entity_id`) so this has something to watch. The answer is given in words — the reason box under Ignore, Respond, a Morph or phone reply — not a new button.
- **Why brAIn said nothing is written down by the code that chose** (`panel/decision_trail.py`, `/data/decisions.jsonl`). Every surface reports what brAIn did; none could answer "why didn't you tell me". A closed vocabulary (`KINDS`: `cap`, `dedupe`, `exception`, `mute`, `shadow`, `no_target`, `notify_quiet`, `quiet_hold`, `gate_hold`, `look_ignore`, `look_watch`, `held`), written by the checks pass (`run_all`'s `withheld` + `pass_rows`), the notifier (`_announce_findings`) and the Resident (gate holds, ignore, watch, hold-after-look). **Nothing here decides anything.** **"No record" is not "decided not to"** — `for_subject` returning nothing is the first, a row is the second, and an unreadable file is `readable: False`, a third; the explain prompt and `/api/why`'s `says` keep the three apart. An identical decision inside `MERGE_S` is one row (a paused house holds the same batch every minute), the file is capped by line count, it never creates its own directory and never raises. Read by `GET /api/why`, the `explain_decision` MCP tool (analyst read, refused on voice) and the interpreter's explain path (`interpret.EXPLAIN_SYSTEM`, job `explain`, `run_analyst`).
- **A standing decision folds; an event is written again** (`decision_trail.FOLD_KINDS`: `dedupe`, `exception`, `mute`, `shadow`, `cap`). Each checks pass made the same "you said you had fixed it" about the same row, ten lines a day. Past `MERGE_S` one of those folds into its row (`count`, `last_seen`; `ts` stays the first), found on disk so a restart folds too, and readers order by `last_seen`. A hold, a look's verdict and a notification decision are events at a time and keep their line per window.
- **Only Wrong is permanent in the settled ledger, and a right answer lapses when its evidence does** (`findings_store.lapse_settled` / `FIXED_LAPSE_DAYS`). The ledger exists so a re-report cannot reopen a decision — right for Wrong, which is a statement about the house, and wrong for "I've fixed it", which is a statement about one afternoon. A fixed problem that came back was suppressed for the life of the install. A `fixed`/`accepted` key from a `check:` source lapses when a pass of **that check** runs and does not report it — the evidence the fix held, read the way `clear_resolved` reads it, so a check that was skipped lapses nothing — and any other `fixed` lapses after ninety days, because nothing re-runs a model's judgement to say it held. A recurrence files again carrying `recurred`/`previous_at`, so the card can say how long it stayed away. `accepted` lapses with `fixed` because agreeing to do something is not evidence it stopped being true.
- **"I've fixed it" on a check's row is checked by that check** (`findings_store._hand_fixes_came_back`, in `clear_resolved` after the chores). Nothing ended a person's `fixed` while the check went on reporting the problem, so a fix that did not hold was deduped for ever. Still reported by a pass that ran, past `todo_store.CHORE_SETTLE_S` — a ticked chore's rule — the answer lapses (`came_back_at`) and the next pass files the row again as a recurrence through `triage.gate`; nothing is filed from the store. Never Wrong, never an `accepted` chore.
- **A finding's prose names things the way a person sees them, and an id lives in its evidence** (`checks/_util.House.label` / `spoken_id` / `without_mac` / `evidence_for`, `tests/test_finding_text_plain.py`). Cards told a homeowner to "run brain.delete_orphaned_devices (it is a dry run unless you tell it otherwise)", listed orphaned devices with their MAC in brackets and named a helper as "Guest mode (input_select.guest_mode)": developer vocabulary, and `prettyText` cannot rescue an id the house no longer has (a dead reference, a restored leftover). A check's `detail` and `fix` name an entity with `label` (its name, or for one with none the id read aloud: *the scene “before movie”*), a device without its MAC (one named only by its address is counted, not spelled), and a remedy as a screen or a press, never a `brain.*` service; the ids go in `evidence` (`{entity, value, when}`, under the card's closed Details). `text` is the dedupe key and was left alone except `auto.conflict`'s fallback, which now takes the house's name before the id. `refresh_details` carries a check's reworded `fix` onto rows it already filed while `fix_by` is empty, so a reworded rule reaches existing rows and never overwrites a sentence a look, a chat or a person wrote. The test wraps every catalogued check, runs the check test modules that plant each defect, and lints every row: ids of a Home Assistant domain, MACs and `brain.*` in `detail`/`fix`, and in `text` only an id the house had a name for. `reg.hardware_name` may show a MAC, because that name is the finding.
- **One source for every count, and one status line** (`cases.queue_count` / `facts_store.count` / `server._counts` / `panel/brain_status.py` / `server.publish_status` → `/config/.brain/status.json` → `custom_components/brain/status_mirror.py`). The walkthrough found every number disagreeing with another: a badge of 2 over a list of 4 (the Findings badge was painted from `/api/status` on one poll and from `/api/findings`' own sum on the next), HA's To-do holding 5, facts 99 in HA (the memory change log) against 755 in the panel (the facts store), a brief saying 677 of 721 runs failed (every failed journal row over every journal line) beside a Diagnostics count of 224 ok, and the health sensor `ok` while Diagnostics said degraded. Now: **the queue** is `cases.queue_count` — open findings, open questions, open suggestions, plus a row waiting past `triage.SHOW_AFTER_S` — and `/api/status`'s `queue_count`/`findings_open`, `/api/findings`' `open`, `/api/cases`' `open`, the mirror and `binary_sensor.brain_needs_you` all read it; **To Do** is `todo_store`'s open items (`list_count`, and `todo.brain`); **facts** are `facts_store.count` (House › What it knows' `all`, `summary()['count']`, `facts_count`, the Facts learned sensor); **run rates** divide `journal.summary`'s `claude_failed` by `claude_runs`, one set. A store that could not be counted is `None`, never 0. **The status line** is `brain_status.derive` — `signed_out` > `needs_restart` (`_integration_versions().restart_pending`) > `paused` (switched off, the account's limit with `back_at`, the budget) > `degraded` (the last health verdict, `HEALTH_CACHE`, filled wherever the diagnostics payload is built) > `watching` ("Watching · last look 9 min ago") — `{state, label, sentence, since, back_at, last_look_at}` on `/api/status`, in the diagnostics payload, and in `status.json`, rewritten every scheduler tick and at startup. `sensor.brain_status`, `binary_sensor.brain_needs_you` (on the brAIn System device; the old guesses-only *Waiting on you* is *Questions waiting* now, unique id kept) and the facts sensor read only that file: missing, garbage or older than its own `stale_after_s` is `unknown` with a `reason` — never `off`, never 0, never the last answer. Server-composed numbers go through `numfmt` ("−100 labels", "5.4 times": rounded by size, a real minus, the unit spaced) and display prose through `textclip.clip`; no check's sentence says "press Wrong" (there is no Wrong button), which `tests/test_numbers_agree.py` holds by AST.
- **The producer scorecard needs the producer on the settled entry.** Every ending on the Findings tab is a label ("I did it"/"Got it" = the report was right, "Wrong" = it was not), and `_remember_settled` recorded the ending and not who raised it, so nothing could add the labels up. It records `source`/`source_title` now and `findings_store.scorecard()` aggregates; it rides `_findings_payload` because it is read in exactly one place. The tab shows a producer only past `SCORE_MIN_ENDINGS` — "1 of 1" is an anecdote. A pre-1.29 ledger entry has no source and scores nothing rather than everything.

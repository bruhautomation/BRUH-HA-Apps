memory.md and its one writer (the consolidator), the inbox, the facts store and its reconcile, hypotheses, curiosity, occasions, the memory extractor hook, study sessions and memory clean-up.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

What each rule cost to learn is in `docs/notes/history/memory.md`. Tests named here were removed in November 2026 with the old suite; the rules they held still hold.

## memory.md and its one writer

- **Memory**: `memory.md` is the only thing that is "memory". The inbox, the hypothesis queue, and the change log are queues and audit trails, and are never injected into prompts. Every writer goes through the inbox — nothing writes `memory.md` except the consolidator. `POST /api/memory/consolidate` runs the same consolidator with `--once`; it does not become a second writer. **The facts ledger (`knowledge_store`) is a dedup index, not a queue** — no *fingerprint* may be deleted from it, or the analyst re-announces what you have already seen (bodies may go: see *Bounded stores* below), and it is emphatically not what the Memory tab lists (the tab reads the inbox itself — `server._inbox_items`; see *The queue on the page*). **Filed discoveries are not rendered anywhere** — once something is in the document, the document is the one place it is read and edited. The ledger still holds them, so nothing is re-announced. Never report a consolidation by the count you asked it to file; read the queue either side of it (a pass can exit 0 and keep the facts, and exit 75 when another pass holds the lock).
- **A consolidation pass rewrites a whole document, and is budgeted like one.** It is a single turn producing memory.md *plus* voice.md — up to 10 KB — so its Claude timeout is 480s, the same as an insight run. **Never swallow stderr on a pass that can fail for more than one reason** — 124 is `timeout`'s and says so by name; anything else carries the CLI's own last line. **And stderr is not where the CLI says why**: in `-p` text mode its own verdict on a failed run — `Error: Reached max turns (1)`, `Execution error`, an API error, a signed-out account — is printed to STDOUT with exit 1 and nothing on stderr. So the pass asks for `--output-format json`: the envelope goes to `brain_journal_record --envelope` as the authority, the answer is its `result`, an `is_error` on an exit 0 is still a failure, and the log line carries the envelope's words, then stderr, then stdout's last line. `record_shell` takes an envelope with no `result` (an `error_max_turns` one) by its `errors` and then its subtype, never `claude exited 1`. It loads no tools (`--tools ""`, the deny kept beside it): `--disallowedTools "*"` alone leaves every tool in the model's list, so a model reaching for Write spends its one `--max-turns 1` turn and the CLI ends `error_max_turns`; a CLI that rejects `--tools` loses that flag and only that one, and a retry claims a fresh session id rather than resending the spent one. `/api/memory/consolidate` **starts** a pass and does not await it (`_consolidate_task`), because a request cannot outlive a minutes-long pass; the outcome is read back from `/api/memory/state`, which is a flag, not the knowledge payload.
- **A lock file's existence is not a lock, and its mtime is not an age.** `with_lock` takes `/config/.brain/memory/.consolidate.lock` with `exec 9>` and releases it with `exec 9>&-` — which drops the flock and leaves the file on disk for good, so the file says only that a pass has run at some point and its mtime says when the last one *started*. Ask the flock (`_consolidation_running()` in the panel, `consolidator_lock_check` in `ha-selftest.sh`): probe it **shared** so that asking can never be something a real pass blocks on, and **`9<` never `9>`**, because `>` truncates the holder's file at open. Probe whether flock works *here* before reading a refusal as contention — BusyBox answers an unsupported flag with the same exit status as "the lock is held", which is the bug that once stopped memory updating at all. An flock dies with its process, so a lock still held past any plausible pass is a live process genuinely stuck, and that is the warning. Whether memory is stale is the queue's question, not the file's: facts queued past 26h with nothing filing them, the same threshold `_consolidation_stale_hours` uses.
- **Versioned memory: every change is a checked, attributed, undoable version** (`panel/memory_history.py`, `brain-memory-consolidate.sh`, plan 2.2, `docs/design/self-learning-plan-2026-11.md`). Under the plan's section 0 no person approves a memory change, so the change always applies and what stands in for the person is a deterministic check plus a history. A pass writes `memory.next.md`, and `memory_history.py check` judges it against the document on disk before anything is written: the size cap, **every line a person gave still there verbatim** (whitespace aside) unless a correction or a person's own words in the same batch supersede it (`superseded` in the diff — "the correction is newer and wins" kept), and **no `(unverified)` line made plain** without a person saying the same thing (`corroborated`). A refusal keeps the document and the inbox, records why (`rejections.jsonl`), and — because a guard that refuses has to change the next attempt — is fed back to the model once (`MAX_CHECK_ATTEMPTS`), with the person's lines already handed to it up front as PROTECTED LINES so the check is rarely what has to say it. The diff (`memory.next.diff.json`) lists added, merged, dropped and evicted lines, each with its class and sources. An applied pass is kept in the history folder (`/data/memory-history/`, the last `KEEP_VERSIONS` 30; `<memory>/history` for any memory folder that is not the real one, so a test never writes `/data`, and as the fallback when the `claude` user cannot create `/data/memory-history` — run.sh should create it claude-owned; whichever folder exists first is used by every process, so the panel and the consolidator never keep two). `brain memory history` lists the versions; **`brain memory undo` restores the previous version as a NEW version** (`--undo` under the consolidator's lock), so an undo is undoable; `brain memory undo <n>` is still the older change-log revert. A document changed by hand since the last version is kept as a `person-edit` version before the next one lands, so an undo goes back to the person's edit and not past it, and the lines they typed become person lines. **memory.md still has one writer**: `memory_history.py` is the consolidator's helper, run by it under its lock (`--once`, `--undo`, `--remove`, `--selfcheck`).
  - **Provenance** (`memory.provenance.json` beside memory.md, `memory_history.provenance`, plan 2.3). Every inbox line already carries `source`; its class is read off that, its file and its `via`: **person** (`correction`, `person`, `homeowner`, `confirmed`, `hypothesis-confirmed`, `terminal-forget`, the teach box's `panel`, a `brain memory add` line — filed in a `-typed.jsonl` file so the source word can stay `terminal` — and a line typed into memory.md), **untrusted** (a file the consolidator swept in from `/share`, renamed `share-…` whatever source it claims; `service`/`automation`; a sibling's own source word; `web`/`file`/`tool`/`assistant`, or `via` saying so; no source at all), and **machine** for brAIn's own runs. An untrusted line is filed ending `(unverified)` — the model is told so, and the check marks it whatever the model wrote — and in the facts store it is `unverified`: never a core fact (`_is_core`), never folds away or rewrites a row already held, said with "(unverified)" wherever `_line` reads it. Nobody presses to confirm it (section 0): **a person's own words about the same claim confirm it** (`facts_store._corroborate`: same subject, same negation, half the shorter claim's stemmed words), and a machine run saying it again does not. Legacy lines (in the document before versioning) are `legacy`, except where the facts store or the inbox archive says a person gave them.
  - **Bounded, not stalled** (`memory_history._evict`, plan 2.4). This amends `brain-core.md`'s "a document that will not fit is still refused whole": after the model's own overshoot retry, a document still over `memory_max_kb` has whole lines **evicted** instead of the inbox stalling — unverified lines first, then the oldest, least-referenced lines brAIn wrote (`refs` counts later inbox lines re-asserting one), then legacy lines; **never a person's line and never a fact this pass is filing for the first time** (eviction makes room for the inbox, so a pass whose own new facts do not fit still fails naming `memory_max_kb`). The eviction is in that pass's version, so `brain memory undo` brings it back. Nothing is ever *cut* mid-line; that half of the old rule stands.
  - **The nightly self-check** (`selfcheck_step` in the consolidator's daemon loop, once a day; `--selfcheck`). The newest version brAIn wrote (`consolidation`, `cleanup`) is re-judged against the one before it with today's rules — its predecessor's person lines present unless that version's diff excused them, no unverified line made plain, the cap — and a failure **rolls memory back one version** (a `rollback` version, recorded in `rejections.jsonl`). Never over a person: a document changed by hand since is kept as their `person-edit` version and left alone, and a version that is a person's action (edit, undo, rollback, baseline) is not judged. It is outside `daemon_step` on purpose (`_drive_daemon` lifts that function and counts its `with_lock` calls).

## The queue on the page

- **A queue's list and a queue's count are one read, or they are two answers to different questions.** The Memory tab's "waiting to be filed" lists and counts the memory inbox itself: `_inbox_items` serves the actual lines and `h_knowledge` reads both in one call, so corrections, confirmed guesses, facts taught from the panel, voice, study sessions and anything another add-on left in `/share` are shown as well as counted. A line's id is a content hash (`_inbox_id`), because nothing stamps one and `ts` is not unique — one insight run queues three facts in the same second — and two lines that say the same thing from the same source *are* the same fact. The rendered list is capped and the count is not, so an over-long queue says what it is not showing rather than disagreeing more quietly. **✕ drops the line and asks the consolidator for nothing**: a queued fact has by definition never been filed (the consolidator archives what it consumes). `FORGET:` itself is unchanged — `brain memory forget` still writes one.

## Clean-up

- **The clean-up applies what it is sure of** (`panel/memory_cleanup.py`, `memory_cleanup.auto_apply`, `server._run_memory_cleanup`, `/api/memory/cleanup*`, Knowledge › **Clean up**), and the rest waits for a press. One `run_analyst` pass (job `memory_cleanup`, a PRESS seat, a maintainer job so it is started and never awaited) reads the numbered document lines (`doc:N`, headings excluded) and the stored facts (`fact:<id>`) with Home Assistant's reading tools — so "wrong" is checked against the registry, not guessed — and proposes removals with a reason from a closed set (`wrong`, `useless`, `error`, `duplicate`, `stale`) and a sentence. `parse` drops an id nobody offered, a reason outside the set, an empty why and the same line twice.
  - Under section 0, `wrong`, `duplicate` and `stale` apply at once: facts through `facts_store.forget_ids`, document lines through the consolidator's `--remove` — deterministic, exact lines (the `doc:N` line number picks which copy of a repeated line), a person's line refused whatever asked, kept as a `cleanup` version that `brain memory undo` reverses. A duplicate applies only while a copy stays (`DUPLICATE_SHARE`), so two rows calling each other duplicates keep one. What could not be applied (the consolidator busy for 30s, or missing) stays on the list.
  - `useless` and `error` stay on the list for a press. **The document keeps one writer**: Apply removes facts with `forget_ids` and turns each document line into a `FORGET:` line in the memory inbox (source `cleanup`) and starts a consolidation pass, so the consolidator strikes it exactly as it does for `brain memory forget`; unticked rows stay on the list, Discard clears it.
  - **What a person said is never offered**: `correction`/`person` sources and `exception:`/`judgement:` predicates stay out of the digest (`facts_store.KEEP_SOURCES`' reason), and the document's person lines are not offered at all (`memory_cleanup.person_lines`). The one exception is an outlived brAIn-bug row (*Filing*, below), offered even when a person wrote it.

## The facts store

- **A facts store under the document, and the document stays the one thing you edit** (`panel/facts_store.py`). `memory.md` is prose and carries no provenance, and handing every run the whole document wastes it on the wrong room. The store is a **reader of the inbox and never a drain** — `ingest_inbox` files every line that passes through as one fact tagged with its subjects (`tag_subjects` over the registry the last checks pass saw, `_FACTS_CTX`; entity ids, `area:`, `person:`, `house`), its source, its `observed` date and its `run_id`, keyed by a content hash so the same fact from two writers is one row; the consolidator still archives the inbox and still has `memory.md` to itself. `retrieval_block` is what runs get: the core facts (a share, `MEMORY_HEAD` first) plus the facts about the entities, areas and domains the run is reading, under `RETRIEVAL_CHARS` — `server._memory_block` at the brief, the weekly, the first look, both investigate sites and curiosity, `ha_data._memory_for` for the bundle, with the whole document as the floor when the store is empty. Capped at `MAX_FACTS` and `PER_SUBJECT_CAP`, oldest and lowest-confidence first. `/api/facts` lists and `POST /api/fact/{id}/forget` drops — the id is a hex hash, checked before it is used — and each fact's detail carries the source, the date and **See the run** through `viewConversation` over the same `run_sources` lookup the Chats rail uses, so "why do you think that" opens the conversation that said it. Forgetting a fact touches the document not at all: a line already filed there is edited there. **And the store never creates its own directory** (`facts_store.writable`): run.sh makes `/config/.brain/memory` before the panel starts, so a missing parent is a dev checkout or a test — `publish_state`'s rule.
- **The document is the curated truth, and the store answers to it** (`facts_store.reconcile` / `server._reconcile_facts`). Whatever a person does to memory — `brain memory forget`, an edit to `memory.md`, a clear, the inbox ✕, an Undo — has to reach the store, or the store most panel runs read is curated by nobody. `reconcile` runs on the scheduler's minute and puts every row in one of three states read off the two things a person can see: **pending** (its line is still in the inbox, so the consolidator has not judged it yet), **kept** (the document reflects it: `REFLECT_SHARE` of its claim tokens in one line), **dropped** (neither, and only after a pass ran — a fact the consolidator chose not to file is a fact a person never saw). A kept row that leaves the document is forgotten, because that is somebody deleting a line; an emptied document forgets everything not pending, because that is a clear. `KEEP_SOURCES` (corrections, facts a person typed) and every `exception:` row survive all of it: the document is a summary, and a summary not quoting a correction is not the person withdrawing it. The pass is skipped when its input digest has not moved, and the digest is **re-taken after its own write**, or the pass's own write moves it and every tick runs the pass again. `FORGET:` lines in the inbox reach the store through `forget_matching` (token share, `FORGET_SHARE`), the inbox ✕ and Undo through `forget_text`, and `_queue_memory_fact` carries a subject and the run's own session id so a forgotten line can be traced to the one row it made.
- **A fact is filed as a claim about a thing, in whole words, once, and a fact about brAIn's own bugs dies with its release** (`facts_store.clean_subjects` / `resolve_area` / `clean_text` / `_folds` / `about_brain` / `outlived` / `_repair`, `memory_cleanup.OUTLIVED_WHY`).
  - **Subjects are things.** `ha_data.ENTITY_ID_RE` allows a digit-only domain, so a decimal ("69.98") and a file name ("automations.yaml") would be filed as device chips. `entity_shaped` wants a letters-only domain of two characters or more and an object id that is neither all digits nor a file suffix; where the last checks pass's registry is known (`_FACTS_CTX`, handed in as `registry`) an entity must also be in it. `person:`, `check:` and `house` stay, anything else is dropped, and a fact left about nothing is about the house. The tagger's scan applies the same shape rule when it has no registry.
  - **One room is one area id at filing**, not only on the rail (`_fold_rooms` stays as the display-side net). `resolve_area` takes the exact id, then the area's name, the id read as words, then its aliases, compared by `_room_word` (`_room_key`'s fold, one function now), and drops a room no area is called while the area registry was readable. With no registry the subject is kept as written, because "could not ask" is not "no such room".
  - **Text ends on a word and names what it means** (`settle_text`, `name_registry_ids`). Over `MAX_TEXT` is `textclip.clip`; a text exactly at the cap ending on a letter was some writer's slice and is cut back to a word with "…". A 32-hex device or config-entry id becomes the device's name or the entry's title, or its first eight characters and "…"; an entity's own hex object id is left alone. `KEEP_SOURCES` text is only ever cut at a boundary. A row whose text was cleaned or folded keeps `said` (hashes of the queued lines it came from), so the reconcile's *pending* and the inbox's ✕ still recognise it.
  - **A paraphrase or a newer reading of the same state replaces the older row** (`_folds`, at ingest through `near_dedupe`, and over the stored rows by `_repair`). Newest wording wins, `first_seen` is the earliest, and `folded` carries a short provenance list. A recovery ("live again", `_RECOVERED_RE`) supersedes older readings about a subset of its entities; a new fault supersedes only an older recovery, because a low battery and unavailable can both be true. Never a `KEEP_SOURCES` row, a row with any predicate (an exception, a judgement, an occasion) or an `occasion` source; a person's sentence absorbs its paraphrase rather than being replaced. Clean up stays the place for judgement calls.
  - **A machine's reading of one moment lives two days** (`facts_store.is_moment` / `MOMENT_DAYS` / `REPAIR_VERSION` 2). A fact naming a recent window or the present ("moved across 69–72 °F in the last 12 hours", "frozen right now"; `_MOMENT_RE`, with `_DURABLE_RE`'s habits excepted) from a machine source gets `expires` two days after it was said, through the ordinary `_expired`; never `KEEP_SOURCES`, never a row with a predicate. The repair gives a stored one the same life from its `ts`, so last month's ages out on the first pass.
  - **Every row carries the `version` it was filed under** (`ADDON_VERSION`, read at call time). `about_brain` is true only when the text says something is broken (`_BROKEN_RE`) AND the fact is about brAIn: a subject among the `brain` integration's own entities (`self_entities`, off the registry's `platform`), or text naming brAIn, "the add-on", MCP or a snake_case tool. Either half alone is a house fact ("the ESPHome add-on fails to compile", "brAIn reads the hall sensor"). Such a row is `_expired` once a newer parseable version runs, corrections included, and never a rule; `dev` expires nothing. `memory_cleanup.digest` offers an outlived row even when a person wrote it, with the two version numbers as its `stale` reason, and `parse` puts it on the table whether or not the model named it.
  - **The store is repaired once per rule set and per amount of context** (`REPAIR_VERSION`, `_repair_mark` in the reconcile state, checked ahead of the digest's early return), so the registry arriving after boot repairs again. The repair keeps a well-shaped entity the registry no longer lists (the orphan rule ages it out) and stamps an unversioned brAIn-bug row with the running version, so it expires at the next upgrade.
- **Bounded stores: the knowledge ledger keeps fingerprints and lets bodies go** (`knowledge_store._retain`, plan 2.4). Retention is age plus reference count, never position: every re-add of a fact is a reference (`hits`, `last_seen`); a body unseen for `RETAIN_DAYS` (180, four times that past `KEEP_HITS` references) leaves, and over `MAX_FACTS` the least referenced, longest unseen goes first. **What leaves keeps its digest** — facts in `seen` (`MAX_SEEN` 5000), settled questions in `asked` — so `add_fact` still answers "not new" and `is_known_question` still answers "asked"; dropping an old question outright would make it askable again, the one thing the list is for. An open question never ages, and the newest dismissed ones `prompt_block`'s dead ends read are kept.

## Knowledge on the page

- **Knowledge is browsed by what a fact is about** (`facts_store.browse(subject_areas=)` → `facets.subjects`, `paintFactSubjects`). **One room is one row however many ids it was filed under** (`facts_store._fold_rooms` / `_room_key`): area facets that name the same room (case-folded, a trailing "room" dropped) fold into one whose id is every id joined by `|`, which `browse` reads back as any-of. Every room and device brAIn has a fact about, with how many, devices grouped under the room `_NAMES` says they are in — a sticky rail beside the list on a wide screen, an optgrouped select at ≤899px — counted under the search, kind and source in force but never the subject filter itself, so picking one never shrinks the list of others. The subject chip on each fact narrows to that subject, the kind pills carry counts (All · Rooms · Devices · House · Rules you set), *Taught by* and the sort are selects, the filters in force are removable tags (`#kActive`), and Delete is a bin on the row. The teach box sits above the list; the memory document and its queue are a fold (*What each run is handed*, below, and panel.md).
- **A subject is said in household words, and an app's world comes after the house** (`facts_store.app_subject` / `subject_word`, `kSourceLabel`). `browse`'s names fall back to `subject_word`: a person by their name (the person entity's, else the slug capitalised), a check by `plain_words.producer_name`, and any other `<app>:` subject (an entity id never holds a colon; `area:`, `person:`, `check:` are the house's own) by its app ("Minecraft"). Such a fact is kind `other` (All only, never Devices), the rail and the About picker list it under **Other**, and the default Newest order puts the house first and an app's world after it. The Taught by picker names every writer in words (an unlisted one has `bruh_` and underscores taken off), and on a phone it is as wide as it reads rather than half the row.
- **What each run is handed is said on the page, read off the code that hands it** (`panel/context_map.py`, `server._context_sources` / `h_memory_context`, `GET /api/memory/context`, Knowledge › **What brAIn brings to a run**, Ask's **⋯ › What brAIn brings**). The route lists eight kinds of run — a conversation in Ask, an insight card, a voice request, a first look, an investigation, the overnight check, what brAIn tells you unprompted (the brief, the weekly report and the lock-screen wording, with the voice block they are handed) and the nightly reflection (with the Ask exchanges it reads) — each with what it is **given at the start**, what it is given **with each message**, and what it may **look up**, every part a byte count (and a ~4-chars-a-token estimate) measured now from the real text (`CHAT_IDENTITY` + the mode lines, `_personality_lines`, `_chat_house_lines`, `/config/CLAUDE.md` and the memory excerpt and your notes inside it, `ANALYST_SYSTEM`/`SYSTEM_PROMPT`, `knowledge_store`/`findings_store`/`hypotheses.prompt_block`, `resident`/`sre` rules, voice's `brain_voice_context.system_prompt`), or the cap its builder holds to, marked `upto` (`CHAT_CONTEXT_CHARS`, `RETRIEVAL_CHARS` + the document's head, `HOUSE_CHARS`). Lookups are `engine.ANALYST_TOOLS` for a card and an investigation and every tool the MCP server lists (read off its source) for a conversation, grouped by name into plain words; a read-only tool needs a group. **What the code does, said plainly**: a conversation carries the document only as the excerpt in CLAUDE.md (8 KB by default, written at start and after each filing); the facts store is pushed per message on **both** faces of Ask (`brain-chat-context.py`, defined once in `chat_session.conversation_settings`: the chat's own `--settings` and the terminal's, see *chat-terminal.md* › parity), so the page reports the chat and the terminal identically; a card, a first look, an investigation, the brief and the weekly get `retrieval_block` instead of the document (the document capped when no facts exist); voice gets `voice.md` or the document's first 2 KB and never CLAUDE.md; the overnight check gets no memory and no tools; every run with tools can search the store with `recall`. **No text leaves the route**, only names, sizes and where a part is changed. Numbers named for other processes (the voice pool's `MEMORY_MAX_BYTES`/`AREA_MAP_MAX_BYTES`, the shell's `BRAIN_CONTEXT_MEMORY_BYTES` default and CLAUDE.md headings) are copied rather than imported, because the pool starts threads on import, so a change to one is a change to both.

## Guesses

- **Hypotheses replace open-ended questions**: capped at 3 open, 14-day expiry, answered ones become plain memory lines and the record is settled. Rejected ones become a capped dead-ends block.
- **A guess is filed with the day it means** (`hypotheses.absolute_days`, `cases._from_hypothesis`'s `asked_at`). "Yesterday afternoon" read a week later is a different afternoon, so `propose` writes today / yesterday / this morning / last night / tonight / this afternoon or evening as the weekday they meant, and the question card says "Asked N ago".
- **Dismiss on a question is a snooze the hypothesis store understands** (`hypotheses.snooze` / `_asked_at`).
  - The guess stays `open`, leaves every screen, and does not hold one of the `MAX_OPEN` slots while it sleeps, so brAIn can ask something else meanwhile.
  - Its TTL runs from `max(ts, snoozed_until)`, so a guess dismissed on day 13 is not expired the morning it comes back.
  - The two shell retirers (`brain-memory.sh`, `brain-memory-consolidate.sh`) and `brain-learn.sh`'s slot count read the same rule. Three writers of one queue disagreeing about which guesses are live is the drift.
  - `/api/findings` does not hand a sleeping guess back as a loose card.
- **A guess answered in Home Assistant is a request, not a write** (`requests.write_hypothesis_request`, `finding_requests.HYPOTHESIS_KIND`, `server._apply_hypothesis_request`). `brain.answer_question` rides the finding-request queue (the order between kinds matters) and the panel closes the guess through `_answer_hypothesis`, the Findings tab's own Yes/No, so a "no" never becomes knowledge and the guess never stays open. The integration refuses what could never be applied — an answer that does not open with yes or no, a guess that is not open, two guesses matching — and the open guesses' ids ride on the *Questions waiting* sensor (renamed from *Waiting on you*, unique id kept) so an automation can name one. There is no `brain.case` service.

## Curiosity

- **Why somebody did something is the one fact a house never records, and it is the fact worth having** (`panel/manual_ledger.py` + `panel/curiosity.py`). `actions.py` can say a person turned the sprinklers on at 19:04. `routines.py` can say they do it most evenings at about seven. Neither can say **why**, and an automation built on the *when* alone fires at seven for ever and is wrong the first week it rains. So this is the one producer whose output is an **explanation** rather than a finding, a proposal or a measurement: it reads a manual action brAIn cannot account for, spends one Claude run looking at what else was true at the time, and files a durable fact or a question.
  - **The selection IS the feature and it is deterministic.** A house produces tens of manual actions a day and a run costs real money, so most of `curiosity.py` is the decision *not* to ask — and nothing asks a model which events are interesting. `worth_asking` is arithmetic over a ledger, taken before anything is spawned, and an empty answer costs nothing. The budget is `MAX_PER_DAY` 1 and `MAX_PER_WEEK` 3, numbers rather than options for the reason the turn caps are gone.
  - **A question is asked once about a subject, and the subject is settled BEFORE the run** — `_brief_loop`'s stamp: a run that crashes having spent the money must not leave the identical question to be asked again every six hours for ever. **But a guard that refuses has to change the next attempt**, so an `unknown` is re-askable, and what re-opens it is **more evidence, never the clock** (`RETRY_EVENTS` further occurrences) — a retry on a timer buys the identical answer over the identical data.
  - **A confidence that comes without the thing that makes it actionable is demoted, not believed**: an `explained` with no `fact` would settle the subject for ever having learned nothing.
  - **The three answers go to three places that already exist** — a fact to the memory inbox (never `memory.md`, which has one writer), a guess to the **hypothesis queue**, and an `unknown` to nowhere, because *"brAIn could not work out why"* is a fact about brAIn rather than about a home. A confirmed hypothesis becomes a memory line, a rejection with a note becomes a correction, and memory is injected into every future prompt.
  - **And it answers to the three gates every scheduled Claude run answers to** (`_offer_milestones`' rule — a credential, `auto_enabled`, the usage budget), where the *pressed* route skips the budget on purpose: "automatic insights pause; asking by hand always runs". Nothing is settled by a pass a gate stopped, so a paused house asks on the pass after it is unpaused.
- **Curiosity asks for room before it spends, and a refused guess is deferred rather than settled** (`curiosity.status_for` / `deferred` / `server._repropose_deferred`). The hypothesis queue's room (`MAX_OPEN`) is asked before the run, and a guess the queue refuses (`REFUSED`) is stored `deferred` with its answer, re-proposed for free when a slot frees — the run already happened, so re-running it would buy the same answer twice.
- **Some questions a house should not ask, and that is a refusal rather than a ranking** (`manual_ledger.EXCLUDED`). Locks, alarm panels and the domains that track where people are: *"why did you unlock the front door at 02:40"* is a question with a correct answer and no good reason to be asked by a piece of software. The other half is in the prompt, because a domain refusal cannot stop a *run* reasoning its way to "somebody was unwell" — the contract forbids saying anything about health, whereabouts, who was home, sleep or household, with no exception, so a reason that is about a person rather than about the house comes back `unknown`.
  - **Voice counts and `routines.py` is right to exclude it**: that module builds a **time trigger**, where this asks a **question**, and a voice command is the most informative manual action a house records, because the person said what they wanted in words. `unattributed` is excluded from both: a wall switch and a device's own integration reach Core identically, and a question about a press nobody can prove happened is one brAIn invented.
  - The domain **order** is the ranking (`chore.waiting`'s trade): a script or a valve carries a reason worth keeping and a lamp mostly does not, so lights are eligible and never outrank a pump.
  - **The floors are looser than `routines.py`'s on purpose** — a trigger is wrong if it fires at the wrong end of an hour, where a question is answerable about "most evenings" as well as about 18:40.
  - **And the odd press is the half no measurement could see**: a subject *already* having a shape is what makes "outside it" mean anything; the distance is `rhythm.circular_distance` (one implementation with `circular_spread`), because 00:10 against a usual 23:50 is twenty minutes; and the press is excluded from the shape it is judged against, or it drags the centre toward itself.

## Occasions

- **The weather is arithmetic, a calendar is somebody else's text, and an occasion is a fact that expires** (`panel/occasions.py`).
  - **The read.** It is nightly-ish (`INTERVAL_S` 12 h), over `_ws_calls` with `return_response` (`weather.get_forecasts` daily and hourly, `calendar.get_events` for the opted-in ids only). A refusal is named, never read as a quiet week.
  - **Weather needs no model.** Frost, heat, heavy rain and gale come from `notable_weather` over the forecast's own numbers, with Fahrenheit converted. A model rewriting "−3 °C" can only get it wrong.
  - **Calendars.**
    - They are opted in through `settings_store.occasion_calendars`: default none, `clean_calendars` refuses anything not shaped like `calendar.x`, and an unreadable value falls back to none.
    - Every title and description goes through `untrusted` (instruction-shaped lines, role markers, fences, tool-call shapes, unlock/turn-off lines and URLs stripped) and is fenced as numbered data.
    - The Haiku turn must cite `event:<n>`. Its numbers must be in that event, its kind is a closed set that excludes weather, its dates are clamped to the event and the window, and health words are dropped.
  - **Filing.** Occasions are filed through `facts_store.add(source="occasion", predicate="occasion", expires=…)`, the writer of `expires` that `retrieval_block` honours.
  - **A closed gate.** It keeps the calendar occasions an earlier read found rather than blanking them. "I could not ask" is not "nothing is coming".
  - **Never acts.** This module has no route to a service call or a proposal.
  - **A weather entity that is not answering is not asked, and that is not a failure** (#1007; `occasions.weather_down` / `retry_due` / `RETRY_S` / `WEATHER_DOWN`, `server._occasions_weather_retry`). A cloud forecast that cannot load (the internet is down) leaves its entity `unavailable` with nothing behind it, and Core refuses `get_forecasts` for it ("did not match any entities"); `pick_weather` still picks it when it is the only one. So no forecast is asked for, no error is stored, the store says `weather_down`, and the checks snapshot marks `forecast` read with `not_answering` beside it (no fault row, no check skipped: the frost check has nothing to look at). The forecast alone is asked again `RETRY_S` after the try, from the hourly tick, leaving `built_at` and the calendar's twelve-hour clock alone (no hourly Haiku run while an integration is down). A refusal from an entity that IS available is still the stored, reported error.
  - **A weather entity down for a day is reported** (#1515; `occasions.down_since` / `down_too_long` / `DOWN_REPORT_S` / `WEATHER_GONE`): the store keeps `weather_down_since` (the first read that found it down, carried through retries and restarts, dropped by the first read that answers), and past `DOWN_REPORT_S` the snapshot marks `forecast` unavailable with a plain reason, so the house hears it through the snapshot-key path; a shorter outage still says nothing.

## The memory extractor hook and study sessions

- **The terminal and the chat teach memory, off Claude Code's own `Stop` hook** (`scripts/brain-memory-extract.py`, wired in `run.sh`'s settings beside the `PreToolUse` snapshot). Voice files facts with `remember_fact` during the turn; this is how the two typed faces teach. Four rules. **The hook is never felt**: it parses stdin, decides in one bounded ledger read, hands the work to a detached child and exits 0 — the extraction (a transcript tail, one cheap run on the memory tier, an inbox write) happens after the CLI has moved on. **Only unclaimed conversations** — `run_sources` is the contract, so an id nobody claimed is one a person typed, and voice, study, the consolidator, doctor, the automation listener and the Resident are all skipped by having claimed theirs. **`worth_extracting` judges the PERSON's words alone** (`said`, never the assistant's reply), or "remember" in the model's canned answer spends a run on every turn. **Every writer goes through the inbox**, a `kind: correction` lands under `source: correction`, and `learning: false` switches it off through `BRAIN_ASSIST_LEARNING` — read from the environment the terminal's shell sourced, or off `/data/.brain_env` itself for the chat's process, which never sourced it.
- **The memory extractor reads what is new, from somewhere that costs nothing** (`brain-memory-extract.py`). It runs from `CLAUDE_HOME` with its own `--system-prompt`, `--tools ""`, `--strict-mcp-config`, `--setting-sources ""` and the engine's isolation settings. Those settings are written out in the script and must equal `engine.isolation_settings()`, because the hook must start without the panel. Each conversation remembers the uuid of the last message a pass read. The next window is what came after it, with the previous exchange as EARLIER context to extract nothing from. One new message has to carry teaching language. A message judged not worth a pass still moves the marker, and one held back by the spacing is read by the next pass.
- **The extractor files only what the PERSON said as theirs** (`brain-memory-extract.py` `grounded`, plan 2.3). A model can lift a "fact" out of the assistant's reply — which may be a tool's output, a file or a web page it read back. The prompt says to extract only what the USER lines said, and a deterministic check backs it: an extracted fact must have `GROUNDED_SHARE` of its own (stemmed) words in what the person said in the window (EARLIER included — `read_new_turns`'s `person`). One that does not is still filed, under source `assistant`, which the memory check files `(unverified)` and the facts store never reads to every run; dropping it would hide a model misbehaving rather than mark it. The record keeps its six keys.
- **A study session runs with the analyst's tool lists, and is refused if it cannot read them** (`scripts/brain-learn.sh`). The lists are read out of `engine.py` at run time (`ANALYST_TOOLS`, `ANALYST_DENIED`) rather than copied into the script, because two answers to "what may an unattended run touch" is how an acting tool reaches one of them; and when they cannot be read the run is **refused**, not made unrestricted, since a study that cannot be scoped is not a study that should run with Bash. A run with no tool flags would inherit `/config/.claude/settings.local.json` — Bash, Write, Edit and the whole MCP surface — on a path an automation can reach through the `brain.study` service. The facts and findings are filed afterwards by the script, out of the JSON the session returned. The study watcher passes the request's own `max_turns` through, so onboarding's lighter syllabus is a setting that does something.

## The deep check's memory probe

- **A drained queue is the proof the memory pipeline ran** (`doctor.stage_memory`, `doctor.MEMORY_FACT_PREFIX`). The probe is shaped like what it is measuring: a plain durable fact about a device, in the form the document is full of, still saying what it is so a leftover can be traced, and never describing its subject as transient or about to be deleted — the consolidator's own prompt excludes transient device states and one-off commands, and a working pass is right to drop such a line. What settles the verdict is the consolidator's own ordering: it archives the inbox **only after** `memory.md` is written, and every failure above that returns with the queue standing, so a queue that emptied proves the pass read the facts, rewrote the document and filed the inbox away. Whether this one line was worth keeping is the model's judgement, which the consolidator's log calls "a judgement, not a failure" — so a drained queue without the probe in the document is a **skip** naming the case, `clear_resolved`'s rule wherever "I could not tell" and "it is broken" are different claims. A queue that did not move is a failure, and drops the probe back out with it, or the next ordinary pass would file this check's own probe into somebody's `memory.md` with nothing left to remove it. The probe is removed by a cleanup that fails if it cannot.
- **The drain is per pass and the filing decision is per fact, and nothing reconciles them**: deciding which of twenty queued lines should have survived is the model's judgement, and re-deriving it would be a second consolidator. So the pass stops the case being silent instead: it logs when it consumed lines and left the document unchanged, and counts the corrections among them separately, because those are the ones somebody typed by hand and is waiting to see the effect of.

## The presence loop

- **The presence loop is not memory** (`presence.py`, `docs/design/presence-loop.md`). Its per-person notes (what a person likes from brAIn: three each, 120 characters, removable in ⚙ › Personality) live in `/data/presence.json` and are shown only to its own nightly run; they never go through the inbox, never reach `memory.md` or the facts store, and nothing about a person is written to the Resident's verdict log (`outcomes._is_person_scope`). Its growth notes are the personality's (`personality.add_growth(by="self")`: marked, never changing the voice, four a week at most, deduplicated against the last twenty), because how the assistant should be is who it is, not a fact about the house. The run's answer is read strictly and refuses anything sensitive (health, body, sleep, mood, beliefs, politics, identity, money, relationships, death), any judgement of a person and any entity id (`presence.refusal_of`).
  - **So is the learned paragraph, and the run that revises it reads Ask** (`_presence_exchanges`, `presence.exchanges_from`/`budget_exchanges`, `write_learned`): it is handed what a person said to brAIn and the last thing brAIn said before they spoke again (conversations sourced `you` only, `EXCHANGE_DAYS` back, each side clipped, `PROMPT_EXCHANGES` inside `EXCHANGES_BYTES`), fenced as data and stored nowhere; titles alone gave it nothing to learn from. The whole revised paragraph comes back or an empty string; `learned_refusal` reads it sentence by sentence with `refusal_of(growth=True)` plus one rule of its own (a sentence naming a person of the house and saying where they were), one refusal refuses the whole, over length is refused not clipped, `same_paragraph` (0.9 of content words, where a note's 0.6 would call every one-sentence revision the same) makes a rewording no new version, and the night's result (`learned`, `learned_refused`) is kept in `reflect` and said in ⚙. A household's own Edit is theirs and is checked only for length.
  - **What the household tells it is a list in the presence store, not memory** (`tuning` in `/data/presence.json`: `answers [{id, question, answer, at, source: question|feedback|ask}]` capped at 60, `questions` waiting, `closed` and `starter` so nothing is asked twice, `rated` keys of lines already judged, `absorbed_at`): answers are the household's words, capped and never refused, shown and removable in ⚙, and read only by the reflection (`presence.tuning_answers(state)` off `tuning.answers`, `[]` until something writes it; `load` keeps the key so a read-change-write never drops it), which revises the paragraph from them. The reflection's own `questions` are parsed like its notes (`parse_questions`) and a pressed run (`_presence_reflect(pressed=True)`, "Take this in now") takes ONLY the paragraph — its ideas, notes, growth notes and questions are dropped, so a press never spends a touch, and it does not move `reflect.at`, so the night's run still happens.

# brAIn: credentials, sign-in and usage figures

The three (four) credential stores, the sign-in flows, the usage-limits tracker, its User-Agent, backoffs and renewals, and how a missing figure is said.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **`backup_exclude` is where credentials go to not be in a backup.** HA backups are unencrypted unless the user opts in, then get copied to cloud storage and support tickets. Paths are relative to `/data`.
- **An access token that has lapsed is not a credential that is gone, and reading it as one made a verdict unclearable by obeying it** (`usage-limits-tracker._credential_state` / `MASKED_BY_REFRESH`). Reported as *"I keep signing in over and over and this message never goes away"*, with a screenshot of the popover telling somebody to perform the account sign-in they had just performed. The account sign-in writes Claude Code's own `.credentials.json`, whose access token lives for hours and whose `refreshToken` is what the CLI mints the next one from on its next run — and `_read_token_from_file` read a lapsed one as **no credential at all**. So a few hours after the sign-in landed it stopped being offered, the search fell through to the older `ha login` setup token, *that* earned the scope refusal, and the refusal was reported and settled. Signing in again worked for an afternoon and then reverted, for ever. The strict rule was half right and CLAUDE.md said so: a known-dead access token cannot be sent, and it still is not — a guaranteed 401 on an endpoint that counts requests. What was wrong is the conclusion drawn from it, because the answer to "the right credential is between refreshes" is **wait**, not *fall through to a credential that can never work and settle its verdict*. So there are three answers to "what is in this file" and not two, and a verdict in `MASKED_BY_REFRESH` — the scope refusal, and `no_oauth_token`, both of which tell somebody who is signed in to sign in — may not be the pass's answer while a store ranked above it was merely lapsed. The keying is on the **kind** of verdict and not on whether it was remembered: an earlier cut required the refusal to be settled already, so the first poll after each lapse still told the person to sign in again and only the second did not, and the first poll is the one somebody is looking at. `REFRESH_PENDING` is absent from `AUTH_PROBLEMS` and from `SETTLED_REFUSALS` — `http_429`'s rule, because it says nothing is wrong with the sign-in and so must let a good reading age out rather than blank four working sensors — and it is the one status whose remedy is to do nothing, which makes it useless as a bare code and is why it is glossed in all five places a person reads one. Every neighbouring case is pinned rather than described, because a guard that swallowed a *real* scope refusal — on a box that genuinely only ever ran `ha login` — would hide the one verdict whose remedy is real: a session with no refresh token still earns it, a box with no account credential still earns it, a working lower store still wins (the guard replaces a verdict, never data), a 401 is never masked, and the lapse flag is reset per pass because `state` outlives one and a stale `True` would go on excusing a refusal after the session was revoked.
- **A credential that is shaped right is not a credential that works, and the two orders differ on purpose.** `engine.get_auth` (the chat) reads the panel's store first and the CLI's own `.credentials.json` last; `brain-auth-env.sh` (the terminal) reads the CLI's file *first*, because a `claude /login` done in that terminal is the most recent thing the person did there and an older pasted token must not override it. That inversion is correct and deliberate — what was not is deciding the CLI's file was usable with `startswith("sk-ant-")`, which tests the shape and not the life. An expired token passes that test, so the terminal deferred to a dead credential, exported nothing, and prompted for a login while a working one sat unread two branches below; the tracker walked the same order into a 401; only the chat, with the opposite order, kept working. **Every reader checks `expiresAt` now** — `brain-auth-env.sh`, `usage-limits-tracker.py`, `engine._cli_credentials_present`, and the `run.sh` backup restore, which discards a dead backup rather than resurrecting it. That last one is why the failure could not clear: `.credentials.json` is restored from `/data/.brain_auth_backup` whenever it goes missing, so deleting the dead token brought it back every boot. A missing or zero `expiresAt` means the file records none, not that the token is past it. **But an expired access token is not a dead credential, and reading it as one was a loop with no way out.** The CLI's file also carries the `refreshToken` it mints the next access token from, by itself, on its next run — so the question the *panel* asks is "can the CLI still get a live token out of this", not "is this token live", and the two answers differ for several hours out of every day; `_cli_credentials_present` and `run.sh`'s restore both count an expired token beside a refresh token as usable, and only a past expiry with **no** refresh token stays dead, that being the revoked session the check was written for. Reading it the strict way was self-sealing: that file is the last store `get_auth` consults, so a terminal-only sign-in reported `authenticated: false`, the panel showed the sign-in screen, and every Claude run in `server.py` is gated on the same call — so nothing ever ran the CLI, which is the one thing that would have refreshed it. `brain-auth-env.sh` kept the strict rule for a while, on the argument that it is the **first** store and a wrong "no" there only falls through — and **the fall-through is the cost**: it exports the panel's or `ha login`'s token, which can run Claude and nothing else, as `CLAUDE_CODE_OAUTH_TOKEN`, so the CLI never opens its own file, never refreshes it, and Remote Control refuses for want of a full-scope login every few hours for ever. So all three readers apply one rule now — live, or a non-empty `refreshToken` whose own `refreshTokenExpiresAt` (when the file records one) is still ahead — and `test_the_shell_and_the_panel_answer_the_same_question_alike` drives the boot restore, the panel and the terminal's resolver over one fixture set; `ha login --status` says *expired, refreshes itself on next use* for such a file and warns when the only usable credential is one of those Claude-only tokens. `usage-limits-tracker.py` stays strict, because it sends the access token at the endpoint itself. The jq half and the Python half are driven over one fixture set and compared, since a boot-time reader deleting what the panel-time reader would have accepted is one file with two answers. **And a 401 ends that credential, not the search** — the tracker tries each store in turn, because "found a token" and "found a token that works" are different claims and only the second matters.
- **"Can this credential be used" and "did this sign-in just produce one" are different questions, and one answer served both.** Loosening `_cli_credentials_present` to count a lapsed access token beside a refresh token as usable is right for `get_auth` — it is what unlocked the panel — and it silently changed the answer for the two callers asking something else. `SetupTokenFlow` used it as its success signal in three places (the reader's per-tick check, `_scan`, the settle in `finally`), so a **stale** file — an access token lapsed weeks ago beside a refresh token the account has since revoked — satisfied it before the flow had exchanged anything: the guided sign-in went to `done` on the first tick after a code was submitted, the panel said *Connected! 🎉*, `get_auth` went on serving that same dead file, and every real run 401'd. Retrying could not clear it, because each retry re-read the file that caused it — **a sign-in that cannot be completed because it insists it already was**. The flow fingerprints the credential file in `start()` (mtime and size, never the contents: it is only ever compared against itself, and reading a secret into memory to answer a question about a timestamp buys a copy for nothing) and requires it to have **changed**, because a successful exchange rewrites it. The other caller is the sign-out: **there are four stores, not three** — `run.sh` keeps the last known good copy at `/data/.brain_auth_backup/.credentials.json` and copies it back whenever the live file has gone, and 1.47.0 changed that restore from *discard a lapsed backup* to *restore anything with a refresh token*. `clear_auth` only ever cleared the three `get_auth` reads, so signing out and restarting — the one recovery anybody locked out will try — put the dead credential straight back. `AUTH_BACKUP_FILE` is on that list now, and the path is pinned from both ends because a shell script and a Python module spelling it separately is a rename that goes silent on one side. Neither fix is a revert: the loosened predicate stands, and what changed is that nothing else answers a different question with it.
- **An escape sequence is a BOUNDARY, and stripping it to nothing captured four letters of prose as part of the credential** (`engine.strip_ansi` / `find_oauth_token`). `claude setup-token` writes no `.credentials.json` at all — it prints a long-lived token to export — so what the guided flow scrapes off the pty *is* the credential, and one wrong character is a 401 on every run brAIn makes afterwards. The CLI renders the token as its own Ink element and `Store this token securely.` as the next one, and **Ink separates them by positioning the cursor rather than by writing a newline**; `ANSI_RE.sub("")` deleted that escape, glued the two together, and every character of `Store` is legal in the token's own alphabet, so the greedy match ran straight on into the sentence. What shipped was `sk-ant-oat01-…Store` in the panel store — the right shape, accepted by `classify_credential`, refused by Anthropic every time — and the *only* visible trace was the redacted log line reading `sk-ant-oat… this token securely`, with `Store` missing because the match had eaten it. **A length bound would have been a number we invented**: `sk-ant-oat` appears nowhere in the CLI bundle, so the prefix and the length come from the server and would be wrong the day either moves. The boundary is real and it is the escape. So `strip_ansi` takes a separator and the reader keeps **two** accumulations of one stream: the display copy (`sep=""`, which is what puts a sentence back together where the CLI draws its spaces as cursor-forwards, and what the URL, `RETRY_RE` and the status detail are all written against) and the token copy (`sep="\n"`), and the token is read only from the second. `_scan` takes both because it is called from two places and the one that was wrong was the call site rather than the function. **The `finally` re-scan masked it from the obvious test** — it re-saved the correct token a moment later, so asserting on the *stored* value passed against the shipped bug — which is why `test_a_real_run_over_a_real_pty_stores_a_usable_token` spies on `save_auth` and asserts **every** write, not the last: a bad credential that a later pass overwrites still spent time in the file `get_auth` serves to every route. And the same accumulation fixed the redaction, which ran per chunk: a token arriving in two reads matches neither half, and both halves went to the log as plain text.
- **There are three credential stores, and anything that authenticates has to read all three.** A sign-in lands in Claude Code's own `.credentials.json`, in the panel's `/data/secrets/claude_auth.json`, or in the `/config/.brain/secrets/claude_auth.json` that `ha login` shares — `engine.get_auth` and `brain-auth-env.sh` both walk that list in that order, and so must anything else. `usage-limits-tracker.py` read only the first and reported `no_oauth_token` while the terminal, the listeners and the fixer all ran happily off a panel login: four sensors saying "not authenticated" about the one thing that wasn't wrong. It runs as **root**, not `su-exec claude`, because two of those three stores are root-owned `0700` directories — running it as `claude` is what limited it to the one store it could read, and the alternative is opening up the files that hold the token. An API key is not a failed OAuth login: it bills per token, has no subscription window, and gets its own status (`api_key_has_no_usage_limits`) rather than being reported as a missing sign-in. **A sensor that goes unavailable has to leave something behind that says why** — HA hides the attributes of an unavailable entity, so the reason went with it; the `Usage tracker` diagnostic sensor never goes unavailable because its whole job is to be readable when the other four are not. Readings expire after two hours (the window `usage_store` already applied to the same file), and a single failed poll leaves a fresh reading alone to age out rather than blanking four working sensors.
- **A credential reachable by four paths is still one credential, and a retry loop cannot tell.** `usage-limits-tracker.py` retries the next store on a 401 — right, because a dead token must not speak for a live one — but `oauth_tokens` yielded a token per *path*, and the paths collide by construction: `run.sh` exports `CLAUDE_CONFIG_DIR` as `$BRAIN_HOME/.claude`, making the first two `CREDENTIAL_PATHS` the **same string**, and symlinks `$BRAIN_HOME/.config/claude` onto `/data/.config/claude`, making the other two the same file. One sign-in, four identical requests, and with the panel and `ha login` stores usually holding that same token, six per poll — every 120s, with no pause between them. `/api/oauth/usage` is undocumented and rate-limited far harder than anything else brAIn touches, and a token hammered on it starts answering **429 with quota to spare** and keeps doing so long after the window that supposedly caused it ([#31021](https://github.com/anthropics/claude-code/issues/31021), [#30930](https://github.com/anthropics/claude-code/issues/30930), [#31637](https://github.com/anthropics/claude-code/issues/31637)) — which reads, from the sensors, as a usage cap nobody hit. Paths are collapsed by `realpath` and credentials by value — it was a SHA-256 digest first, on the instinct that a set of live tokens is a copy of the secret, and **it is not**: a Python string enters a set by reference, so the digest bought no fewer copies than the token does and cost a hash of a credential for it. CodeQL read that hash as password storage, which it never was, but a scanner asking why a token is hashed at all is asking the right question of the wrong line. **And the endpoint buckets its rate limits by User-Agent, which took two wrong theories to find.** The tracker introduced itself as `brain/1.0` — the repo's own naming rule, applied one file too far — and that UA lands in the bucket the endpoint keeps for strangers: a 429 wall after a few hours with quota to spare, which measured from inside like a daily meter ("nine working hours then a wall until the small hours") and was written up here as one. It never was. Every reporter in those issues was calling without the CLI's UA too, and the statusline-tool ecosystem polls the same endpoint at 1–5 minute cadences sustainably by sending the UA Claude Code itself sends. **Which of Claude Code's two UAs took a third theory to get right, and the wrong one looked correct for a release.** The bundle has a `getUserAgent()` that builds `claude-cli/<version> (external, cli)` — that is its *Messages-API* client, and it is what shipped; the usage endpoint's own caller (`Hqq()`) sets `"User-Agent": jH()`, and `jH()` is `claude-code/${VERSION}`, no suffix. A real Claude Code UA sent to the wrong endpoint is still a stranger, so the wall never lifted, the sensors went on ageing out into unavailable every couple of hours, and the docstring said it was fixed — read the *call site's* header, never the first UA helper the grep finds. So `user_agent()` sends `claude-code/<installed version>` (probed from `claude --version` once per process, `BRAIN_CLI_VERSION` to pin it, and a real shipped version as the fallback because a made-up version is a UA nobody else sends; the version is approximate on purpose — the CLI stamps a build-time constant that lags its release, and the bucket is keyed on the product prefix), and the poll is a 30-minute heartbeat — freshness comes from a finished run rather than from the timer, which is the bullet below. This is the one deliberate exception to "prefer `brain` over `claude` in anything we own": the request is made with that install's credential on that install's behalf, and the name on it is the difference between working sensors and a wall. **A 429 is not a failure to retry — retrying is what sustains it**, so it escalates 1/2/4 hours rather than sharing the ordinary cadence, and every step must exceed `POLL_INTERVAL` or a *failing* tracker asks more often than a working one (which is what lengthening the poll and leaving 15/30/60 alone would have done — `test_every_backoff_actually_backs_off`), and `Retry-After` may only ever *lengthen* that: the endpoint sends `Retry-After: 0` while still refusing, so obeying it literally is how a tracker retries straight back into the limit it was just told about. It is absent from `AUTH_PROBLEMS` on purpose — it says nothing about the sign-in, so it lets a good reading age out instead of blanking four sensors — and it ships a `detail` for the diagnostic sensor, because `http_429` beside a usage number is read as the number. **The backoff waits are all longer than the 2-hour staleness window, so during any 429 streak the sensors *will* go unavailable — and that moment has to arrive with its reason.** The reason used to be written only on the poll *after* the reading went stale, hours later on a 4-hour rung; in between, the diagnostic said `stale` and nothing else, which reads as "unavailable for reasons I do not understand". A failed poll now leaves `last_error`/`next_attempt_at` (and the 429 gloss) *beside* the reading it deliberately did not overwrite (`_record_failure` — the numbers and their `updated_at` untouched, so staleness still ages from the real reading, and no reader keys on `error`), the diagnostic sensor reports a stale-with-reason as the reason itself, and a restart resumes a promised quiet instead of retrying straight into the limit (`_resume_backoff` — backoff lived only in memory, and restarting the add-on is the first thing anyone does when sensors go dark). **Compare against what Claude Code itself does**: its own client calls this endpoint from the `/usage` screen and nowhere else, on demand, never on a timer — which is the shape the next bullet finally took, and why the hour-scale ladder survives the bucket fix: a 429 in the CLI's bucket is rare enough to mean something. The suite could not see any of this — every test set `CLAUDE_CONFIG_DIR: None`, and that variable *being set* is what creates the duplicate, so `TestOneCredentialOneRequest` builds the environment `run.sh` actually exports and asserts the collision exists before asserting it costs one request.
- **A figure that only moves when a run spends tokens is a figure to ask about when a run ends, not every five minutes** (`usage_store.nudge` / `journal.is_claude_run` / `usage-limits-tracker._wait`). Reported as *"the usage sensor is really bad… I'm thinking we're hammering the end point too much?"*, and the hammering half was right about the cadence and wrong about the symptom: 288 requests a day found a changed answer on the handful of occasions anything had run and re-asked an unchanged question the other 280 times, against the endpoint Claude Code itself calls only from its `/usage` screen, on demand, never on a timer. The argument that put it at 5 minutes — the five-hour window moves ~1% every three minutes at a hard sprint — was answering the wrong question, because *nothing moves it but a run*. So the timer is the floor (30 minutes) and freshness is an **event**: the panel touches `/data/usage-nudge` and the tracker's own wait wakes within `NUDGE_CHECK_S`. **The same moment is the only one the credential is certain to work**, which is the failure actually in the field and not a bonus: the access token lives hours and the CLI mints the next one from the refresh token *as part of a run*, so a quiet house has nothing to ask with however hard it polls — it reported `oauth_token_awaiting_refresh` and aged out into four unavailable sensors, and polling harder was never going to reach it. **It is a journal listener and not a call at six sites** (`reports.file_run_failure`'s arrangement): every Claude run of every kind already records itself there, so voice, the chat, a card, a fix, study, a Resident look and the consolidator are covered by having done so — and the account sign-in is covered for free, because it ends in a real `validate_auth` turn. **`is_claude_run` keys on the ROW and never on a list of source names**: a source is a string a caller passes, so a set of names meaning "a model ran" is a second place the answer lives and the drift is invisible until a new producer is missing from it; it is `any(key in row)` over the four fields only an invocation carries, by **presence** rather than truthiness, because `record` writes a key only for a value it accepted and a run that died on its first turn writes `turns: 0`. Three rules on the wait. **A nudge may only ever shorten the ORDINARY cadence** — a 429 ladder and the five-failure backoff are promises of quiet whose whole premise is that asking again cannot help, and a finished run is not news to an endpoint that has just refused us, so letting one through is `Retry-After: 0` obeyed literally in a new disguise; `heartbeat` is set beside the delay it describes rather than re-deriving the same three conditions, because a threshold moved in one of two copies is a promise a nudge quietly starts cutting short. **`MIN_SPACING_S` is a floor and not a filter** — a checks pass that triages, files and heals is several runs in a minute and one thing that happened to the figure, so a nudge inside the floor is **held** until it lifts rather than dropped, the last run of a burst being exactly the one whose spend nothing has read; that is deliberately not a coalescing debounce, which would need machinery to detect the end of a burst to buy the same answer. And **a wait cut short makes `next_attempt_at` a lie**, so it is restated — `_restate_next_attempt`'s rule, which a restart already owed for the same reason. The stamp the process has answered is **returned by the wait** rather than read after it, or a nudge landing *during* a request is lost; and it is seeded off disk at startup, because a nudge from a run this process never saw is not news. `nudged_at` rides in `/api/diagnostics`, since "the figure is 40 minutes old" and "nothing has run since Tuesday" are different reports of one number and only the second is a fault. The path is spelled in both halves — the tracker is a separate root process that imports nothing from the panel — so `tests/test_usage_nudge.py` reads both ends, `AUTH_BACKUP_FILE`'s rule, and drives the real `journal.record` into the real listener into the real file rather than writing the row shape down twice.
- **The run that was supposed to renew the account credential never opens that file, so the tracker renews it itself** (`usage-limits-tracker._renew` / `_refresh_request` / `_write_credentials`). The bullet above and the two before it all rest on one sentence — *Claude Code mints the next access token from the refresh token as part of a run* — and it is true of a run that authenticates from `.credentials.json`, which on a box holding a panel-store or `ha login` token as well is **no run at all**: `engine.get_auth` reads those stores first and `_claude_env` hands the CLI their token through `CLAUDE_CODE_OAUTH_TOKEN`, so the CLI never reads its own file, never refreshes it, and the account credential lapses a few hours after the sign-in and stays lapsed for ever. The report this was written from had twenty-seven runs in a day, a nudge answered after every one, and `oauth_token_awaiting_refresh` — *nothing is wrong, wait* — for the whole day, with the device check filing *brAIn Usage Limits has been unavailable for more than a day, check its batteries* beside it. Reordering `get_auth` was the wrong fix (the order is deliberate, one bullet down); the right one is that the tracker performs the renewal, with the request the CLI performs — the token URL, the refresh grant, the client id and the scopes, **read off the installed binary** (`grep -a` for `v1/oauth/token`, `grant_type:"refresh_token"` and `formatTokens`) rather than remembered, because a shape remembered rather than read is BRUH Print's `ETB`. The write-back is the CLI's own compare-and-swap: the block goes in only while the file still carries the refresh token the renewal was made with, and if the CLI got there first its answer is the one on disk and ours is dropped unread, since a refresh token may be single-use and the second answer to arrive is the one to keep. Owner and mode are carried over (the file is the `claude` user's and the tracker is root — `atomic_write`'s reason), a chown that cannot be done aborts the write, and the tests drive the request over a real socket into a real `HTTPServer` because a fake that accepts what it is handed proves only that it matches the code that mocked it. Three outcomes and they are three different claims: **renewed** is a token in hand; **rejected** (`invalid_grant`, or a 401/403 on the grant) is a session that is over, remembered against that refresh token the way a scope verdict is so it is asked once and not hourly, said once with the remedy, and reported as `http_401` rather than `no_oauth_token` — a found credential refused is not the absence of one, and *"nothing has signed in yet"* sends somebody to look for a sign-in that is right there; **failed** (the network, a 5xx, a 400 with no recognisable code — which is likelier OUR request than a dead session, and must not send anybody to sign in again over a bug in this file) is still the right credential merely waiting, asked again next pass. **A 429 from the token endpoint is a promise of quiet, not a failure to retry** (`RATE_LIMITED` → `oauth_renewal_rate_limited`, `RENEWAL_BACKOFF_S`, `RENEWAL_BACKOFF_FILE`): it was FAILED and asked again on the next pass, and a pass comes after every finished run, so one rate-limited renewal was a hundred requests in a day sustaining the limit while the figures went unreported. It waits on its own ladder (15 min doubling to 4 h, `Retry-After` only ever lengthening a rung), on disk so a restart keeps it, and the pass's wait is the renewal's and cannot be cut by a nudge (`_next_delay`); the verdict is needs-nothing in `usage_store` and says when the renewal is next tried, never to sign in. A refresh token is offered for renewal once per pass whichever real path holds it. **And "wait" has a clock on it now** (`_error_since` → `usage_store.STUCK_AFTER`): every failure writer rewrote its stamp, so nothing in the file said how long a verdict had stood, and *between refreshes* is a true sentence for twenty minutes and a fault after a day — `error_since` is written when the code changes and kept across every rewrite **and a restart** (a restart is the first thing anyone tries and must not make a day-old verdict look new), `needs_nothing` takes it, and past three hours the popover, the health sensor and `brain doctor` stop calling it fine and name the log. The API key gets no clock because it can never clear. **The 429 ladder gets no clock on its verdict, and a day of it gets a sentence instead** (`usage_store.OVERDUE_AFTER` / `OVERDUE_DETAIL`, `limits.overdue`): a house sat on `http_429` for thirty hours with the figure an estimate the whole time. The ladder was not stuck — every rung is at most `RETRY_AFTER_MAX_S`, a restart resumes it capped and a nudge never shortens it, so it cannot park itself — and nothing a person can do ends the wall, so the verdict stays needs-nothing at any age: making it a fault is a decision for a person reading the numbers, not for a clock. What changes past a day is the words: the detail, the popover and the brief's frame say how many hours the endpoint has refused brAIn and that the figure is an estimate, and none of them ever says to sign in. `TestADayOfRateLimitsIsSaid` drives the real writers into the real reader. `TestTheBodyIsWhatNamesTheRefusal` had been replacing `urllib.request.urlopen` on the shared module and never putting it back, so every class collected after it that made a real request got a fake 403 — a leak that only showed the day something downstream stopped mocking. **And the one writer this adds has to stand down for the other** (`engine.SIGNIN_HOLD_FILE` / `_hold_renewals` / `tracker._signin_in_progress`): the guided sign-in reads the credentials file *changing* as the exchange having succeeded (`_signed_in_here` fingerprints it in `start()`), so a renewal landing mid-flow would say *Connected!* about a code nothing had exchanged — the 1.5x bug in a new disguise, introduced by the fix for a different one. The flow touches a marker in `start()` and removes it wherever it settles (the reader's `finally`, `cancel`, and the branch where the process never started), the tracker makes no renewal while the marker is younger than the flow's own lifetime, and a marker older than that is a panel that died mid-flow and is ignored. Two processes, one path: the test drives the real engine helpers into the real tracker and pins both defaults, the nudge file's rule.
- **A status code is not a verdict, and the body is where the verdict is.** The usage endpoint answered **403 `oauth_scope_insufficient`** and `http_403` was in no table — not `AUTH_PROBLEMS`, no `ERROR_DETAIL` gloss, not in the vocabulary `sensor.py` documents, nothing in `limitsNote` — so it rendered as a bare code and was retried hourly, forever, against a verdict that can never clear. It can never clear because `ha login` is built on `claude setup-token` **deliberately** (a session credential refreshes itself and cannot be published to a shared file), and that mints a token scoped `user:inference user:ccr_inference user:file_upload` where the endpoint requires `user:profile`, which only the interactive `claude /login` asks for: the sign-in works, every Claude run works, and the one thing that cannot work is this figure — so *running `ha login` again reproduces it*, which is what makes naming the fix load-bearing rather than tidy. The status alone genuinely cannot tell that from any other permission refusal; `_error_code` narrows `http_<status>` by the API's own `error_code` and **only ever narrows**, because a verdict invented from an unrecognised string reads exactly like a real one. It parses the **whole** (bounded) body and not the log line's 200 characters — the refusal seen in the field clears that cut by fifty and one more scope named in its message would not, which is the same near-miss shape as `strip_ansi` eating four letters of prose. `oauth_token_lacks_usage_scope` is in both tables and in all four places a person reads one; a bare `http_403` is deliberately **not** in `AUTH_PROBLEMS`, because "I could not tell why" and "the token is under-scoped" are different claims and only the second may blank four readings that are still true — `clear_resolved`'s rule, one file over. **A settled refusal stops being asked**: the verdict is remembered against the credential that earned it, so the tracker sends nothing rather than a request an hour forever, and because the memory is keyed on the *credential* and not on the poll, a real sign-in is tried on the very next pass. A 401 is **not** remembered — an expired token and a five-minute hiccup are refused identically, and blacklisting a credential over the second is how a working sign-in stays unread. **And a poll that sent no request did not fail one** (`_next_failure_count`): the consecutive-failure ladder exists to stop hammering an endpoint, so a pass with nothing left to try must not be charged for it — otherwise the poll slides to the hourly rung and the one poll that would notice a *new* sign-in is an hour away, on exactly the recovery the message tells somebody to perform. A 403 moves the search to the next store exactly as a 401 does, that being the same claim (this is the wrong credential) and the half of the 401-stops-the-search bug that keying the rule on a literal code left in. And a **restart makes `next_attempt_at` true again** (`_restate_next_attempt`): every failure records when the tracker will ask next and the popover renders it by the clock, while a restart deliberately re-asks sooner than most of those promises — so the file was left claiming a wait that was never going to happen. Only a rate limit's quiet is still *resumed*, and the tempting generalisation (resume every wait asking again cannot help, which would take in the sign-in problems) is **wrong**: a restart is not a timer expiring, it is a person acting, and the thing they most often did first is sign in again — a rate limit is the one failure a restart cannot have changed.
- **The panel can perform the sign-in that reads your usage, and until 1.51.0 nothing in the UI could** (`engine.FLOW_MODES` / `SetupTokenFlow.start(mode)`). The two sign-ins differ by an OAuth **scope**, measured off the authorize URL each prints — the only place either states it: `claude setup-token` asks for `user:inference`, and `claude auth login` asks for `org:create_api_key user:profile user:inference user:sessions:claude_code user:mcp_servers user:file_upload`. `user:profile` is what `/api/oauth/usage` requires, so the first can never report a figure — which brAIn knew and said, and then named the remedy as **`claude /login` in the Terminal tab**: a shell command, in a tab `enable_terminal` removes and whose default face (`terminal_ui: "chat"`) is a chat with no shell in it. And the panel's OWN guided sign-in ran `setup-token`, so every route the UI offered minted the usage-blind credential while the only cure it could name was somewhere a person may have no way to reach. That is the complaint, in the words it arrived in: *"There is no terminal… the whole point is to login once and have that work everywhere."* **`auth login` is a plain subcommand and not the TUI's `/login`**, so it drives on a pty exactly as `setup-token` does — prints a URL, waits for a pasted code — which is what makes this a button rather than an instruction; the argv is the only real difference, because success for it arrives as the credential file being rewritten and `_signed_in_here` already was that test. **Neither replaces the other and the screen says why**: a session credential refreshes itself and so cannot be copied into the file the other BRUH add-ons read, which is the whole point of `ha login --share`, so the account sign-in leads and the token sits behind a disclosure beside it. The default matters more than the pair — a button somebody presses without reading has to be the one that works, and `DEFAULT_FLOW_MODE` is the account. Every surface that reports `oauth_token_lacks_usage_scope` names the button now (the popover, the tracker's log line and `ERROR_DETAIL`, `ha-selftest`, the HA sensor's own vocabulary, DOCS.md), and `test_no_scope_remedy_tells_you_to_open_a_terminal` scans all four for the *sentence* rather than the word — those files legitimately discuss the terminal, it being one of the three credential stores, and a grep for `Terminal` alone would fail on prose that is simply true. The load-bearing test is not the constant: `TestWhatTheFlowActuallyLaunches` drives `start(mode)` over a real pty against a stub that records its own argv, because the mode reaching `FLOW_MODES` and the mode reaching the process are different claims and only the second decides what Anthropic is asked for.
- **A fallback that is silent is a fallback read as the real thing.** When the tracker cannot report, `usage_store.budget_state` slides to the local estimate — brAIn's own insight runs against a rough plan allowance — and the pill went on rendering it as an ordinary percentage with the weekly half gone. On a home that mostly uses the terminal and the chat that estimate is **0%, forever**, which is precisely what "the usage sensor is unresponsive" looks like from the panel; and the one line the popover had about it said *sign in with your Claude subscription*, i.e. telling somebody who is signed in to redo the thing that was working. `limits_problem()` reads the tracker's own status out of the same file (`error`, or the `last_error`/`next_attempt_at` a failed poll leaves beside a reading it did not overwrite) and `budget_state` carries it as `limits` **only when `source` is not `account`** — an excuse beside a working number is noise. The pill prefixes the estimate with `~` and takes the warning dot; `limitsNote` says which failure it is, in the tracker's vocabulary, with the two codes people misread spelled out (a 429 is the *endpoint's* limit, not the account's; an API key has no window to report) and the time of the next attempt, because during a backoff the honest answer is "not broken, waiting, back at 9:40". `_fresh_payload` also stopped treating a reading with no `updated_at` as fresh — the staleness test was skipped whenever the stamp was missing, and a reading that can never go stale is a reading nothing can correct.
- **A verdict nothing re-earns is a verdict nothing can correct.** `AUTH_CHECK` ran at panel startup, after a credential was saved and after the guided sign-in, then never again — so a credential that died on a Tuesday afternoon was reported by nothing: `/api/status` served the startup verdict for days, the auth chip stayed hidden because a working login is not news, and the first symptom was voice, the automation listener and the consolidator failing off one store while the terminal worked off another. Same shape as the usage tracker's stale reading, and reachable precisely because `engine.get_auth` prefers a store whose credential it *cannot* verify: the panel store records `{type, value, saved_at}` and no expiry, so unlike `_cli_credentials_present` there is nothing to check — the only liveness signal a pasted token has is a 401 at use. So the verdict ages (`AUTH_RECHECK_S`, 6h, failures included so a terminal re-login is noticed without a restart) and is re-earned **lazily off `/api/status`**, never on a timer: `validate_auth` is a real `claude -p` turn, and an unattended timer would spend account tokens forever on a question nobody is asking, where the status poll only runs while somebody is looking. A re-check nobody asked for is **unannounced** (`announce=False`): "Verifying Claude…" answers what a person just did, and a chip appearing unbidden in the top bar — shifting its layout — every six hours while somebody reads a card is the "a permanently green chip does not belong there" rule with the timing changed; the standing verdict is served until there is a new one, which is also the more honest answer. **`start_auth_check` flips `running` synchronously**, because `asyncio.create_task` only schedules — nothing in the coroutine runs until the loop yields, so a guard reading a state its own task has not set yet is no guard: two polls in one tick both spawned a real check, already reachable through the polled `h_setup_status` and now through a harder-polled `/api/status`. It is a flag rather than the state precisely because a silent check leaves the state reading `ok`, and `_auth_verdict_is_stale` has to consult it or every poll re-asks over an unfinished one. **`save_auth` writes `saved_at` as an epoch int**, which is the shape `_read_shared_auth` documents for both files and what `ha-share-login` writes and greps (`"saved_at":[ ]*[0-9]+`); it wrote an ISO string, latent only because each reader happens to read the file it wrote. The shell half had asserted the int since it was written and the panel half had not, which is the whole reason it drifted.
- **"Where is the Claude CLI" had two answers and one of them was the bare name.** `engine.resolve_claude_bin()` walks a list precisely because run.sh installs the native binary under the `claude` user's home and the image symlinks it into `/root/.local/bin`, neither of which is on root's default PATH — and `server._cli_version` kept `["claude", "--version"]`, so every bug report from a house whose Claude was running perfectly said `claude_cli: "unknown"`, which is the one fact nobody can supply afterwards and the first line of any report about a version-dependent failure. `usage-limits-tracker.CLI_PROBE_COMMANDS` had drifted to two of the four entries for the same reason. Both walk the same list now, and the test that holds it **drives the probe** rather than grepping for the old shape, because the comment explaining the bug contains the string a grep would match — which is the one case where "this pattern is absent" is not a claim a grep can honestly make.
- **The envelope is one level deeper than the reader looked, and a fix that cannot fire is no fix** (`usage-limits-tracker._error_code`). The 403 narrowing was written, tested and documented — and read `details` and `error_code` at the **top level** of the body, where Anthropic's standard error shape puts neither: it is `{"type": "error", "error": {"type", "message", "details"}}`, and that body carries **no `error_code` at all**. So the one refusal the whole narrowing exists for came back `http_403` anyway: no gloss, absent from `AUTH_PROBLEMS`, never settled, retried hourly against a verdict that can never clear, with the health sensor stuck at `degraded` and the popover telling somebody signed in to sign in again. Same class as the `pop` that did not case-fold — the machinery was right and the path into the body was wrong — and the tests could not see it because they wrote the shape down from the same guess the code did, which is what makes a fixture **copied from a real response** the load-bearing part of the fix. What narrows it now is `details.required_scopes`: a list of scope names on a 403 is the endpoint saying in as many words which scope it wanted and did not get, which is exactly the claim `SCOPE_ERROR` makes, and it is a documented field read literally rather than a verdict invented from a string. The message text is deliberately **not** matched — prose is what gets reworded — and `required_scopes` narrows only a 403, because a 500 that happens to mention scopes is not a scope verdict.
- **A hook is not handed the credential its CLI was started with, so a Claude run started from one has to fetch it** (`brain-memory-extract.py`'s `cli_credential` / `child_env`). Claude Code builds a hook's environment from its own and drops `CLAUDE_CODE_OAUTH_TOKEN` and `ANTHROPIC_API_KEY` on the way (measured on 2.1.293: an ordinary variable reaches the hook, those two never do). The panel and `claude-run` hand the chat and the terminal their credential exactly that way, so the extractor's `claude -p` fell through to the CLI's own `.credentials.json` — the file nothing refreshes while the token in the environment is what everything else uses (the tracker bullet's arrangement) — and every pass ended `auth` beside a day of working chats and cards. The hook reads those two variables, and nothing else, off `/proc/$CLAUDE_PID/environ` — the CLI process, which names itself in `CLAUDE_PID` — **only while that pid is one of the hook's own ancestors**, and hands them to the detached child; a CLI that was handed nothing hands nothing on, which is the CLI authenticating from its own file and the child doing the same. It is read in the hook and not the child, because the child outlives the CLI. **And a refusal one face keeps meeting is a health problem the sign-in check cannot see** (`health._auth_runs`, `journal.summary`'s `last_by_source`): three `auth` runs from one source with its newest run still refused is `degraded` naming the source and **Sign in again**; one is a blip, and a source whose next run worked has already had its remedy.
- **A credential the hook cannot read is the panel's to supply, and on an AppArmor host it cannot read one** (`brain-memory-extract.read_cli_credential` / `queue_request`, `panel/extract_requests.py`, `server._drain_extract_requests`). The 2.17.3 fix read the CLI's two credential variables off `/proc/$CLAUDE_PID/environ`, and that is a ptrace READ: AppArmor asks the TRACEE's profile too, and brAIn's grants `ptrace (trace,read) peer=brain` and not `readby`, so the kernel answers EACCES between two `claude`-user processes in one profile. `cli_credential` read that as "could not look", the child kept an environment with no credential, fell through to the dead `.credentials.json`, and every pass ended `auth` beside a day of working runs (reports #81). The reader now answers three things — no CLI to ask, READ (perhaps holding nothing), UNREADABLE — and UNREADABLE leaves a request in `/data/.brain/memory-extract-requests` (claude-owned; `/data` is root's) carrying the session id, transcript and cwd and **never a credential**. The panel's scheduler tick runs the same `--extract` half as the `claude` user with `engine._claude_env()`, i.e. `get_auth`'s credential, the one every other run is handed; `/data/secrets` stays root's `0700`. Requests are validated, taken once (deleted before the pass starts), one per conversation per tick, `MAX_PER_TICK`/`MAX_PER_DAY`, dropped after `MAX_AGE_S`, and a signed-out house starts nothing. Where the read works the hook spawns its own child as before. The path is spelled in both halves and the test reads both; the refusal is reproduced by running the real script with only that one read refused the way the kernel refuses it. Not fixed here, and worth knowing: `STATE_DIR` (`/data/memory-extract`) is created by nobody as the `claude` user, so the per-conversation marker and spacing may never persist.
- **Missing usage figures that need nothing are never a reason and never a sign-in** (`brief._health_reason` / `usage_line` / `SIGN_IN_CODES`, `state_from(usage=)`). The brief's model reads the tracker's last word through `get_health`, and a verdict read from a cache or an older mirror can carry the usage problem without `needs_nothing` — so a 429 went out as "sign in again". The brief skips a usage problem while its limits need nothing, tells the model so in the frame, and its SYSTEM forbids a sign-in remedy unless a reason says a sign-in failed; a refused sign-in and an under-scoped token still say Sign in again.

# brAIn: panel UI rules

The top bar and tabs, Settings (⚙), tooltips and toasts, Undo, the 16px text floor, personality, instructions, changes history.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **A press whose only record is a toast is a press that reads as nothing** (`findings_store.mark_checked`, `checked_at`). "Check again" is seconds of work and its commonest answer is *the problem is still there* — which left the card looking exactly as it did before, so the button read as doing nothing, which is what was reported. Two halves. The control that was pressed **says what it is doing** while it runs, because a row of greyed-out buttons is the only thing on screen otherwise. And the row carries **`confirmed <when>`**, which is a more useful claim than the press: a finding filed on Tuesday and one confirmed a minute ago are different things, and only one of them is evidence about the house *now*. **Only that press writes it** — the scheduled pass re-confirms every open row every few hours, so stamping there would put "confirmed just now" under a card nobody has looked at and the line would stop meaning anything, which is `clear_resolved`'s reason for writing no memory line. A check that could not look stamps nothing, for the same reason it clears nothing.
- **A tooltip that opens off the screen is a tooltip that is not there, and CSS cannot see the edge.** `[data-tip]::after` was `position: absolute; right: -4px`, max-width 240px, so the bubble hung *leftward* from the control's right edge: anything whose right edge sat under ~236px from the viewport's left lost its text off the side. Four of the six buttons under a finding at 390px; still two at 1100px, because the findings list starts at the left margin. It is one shared `.tipbox`, `position: fixed`, measured and clamped in `placeTip` — same reasoning as `#chipPop`, and it also flips above when below would not fit, which is what the old `.card .foot` override was patching one case of. The listeners are delegated because these controls are rebuilt on every render. **`scroll` calls `dismissTip`, not `hideTip`**: a *visible* tooltip is anchored to where the control was and has to go, but one still inside its 150ms open delay is measured when it opens, after the scroll — cancelling that one is what made a tooltip vanish for good whenever the page settled a scroll just after the pointer arrived. `tests/manual/measure-tooltips.mjs` measures it; a bubble that never opens fails the same as one off the edge, because they look identical. **And a tooltip never opens on a tap, nor over a control that already says its name**: tapping a bottom tab left a dark bubble repeating *Insights* pinned above the bar over the content, because the tap fired `pointerover` and then focused the button, and both opened it. A touch `pointerover` opens nothing, `focusin` opens one only for keyboard focus (`:focus-visible`, which a tap does not set), `showTip` skips a control whose visible text is its tip (`namedAlready`), and the tabs carry no `data-tip`; the measure taps every tab at 390 and hovers a button whose name is its tip.
- **A toast is `left: 12px; right: 12px; margin: 0 auto`, never `left: 50%` with a translate.** A fixed element's containing block is the viewport, so `left: 50%` leaves it the right-hand half to lay out in — on a 390px phone the toast could never exceed ~195px and wrapped to four lines with the whole screen spare. Invisible until something sat beside the text, which is what Undo is.
- **Undo is the toast's, and it is "I misclicked" — not a history.** Every press that takes a row away hands back a token (`undo_store`, in memory, 300s, a 32-entry ring) and the toast grows an Undo. Reversing puts back all three effects of an ending, because putting back one or two is worse than none: the row (`findings_store.restore`, under its *original* ts — that id is what the chat strip and any pending token hold), the settled key (`unsettle`), and the queued memory line (`_drop_from_inbox`, which works precisely because the token is younger than any consolidation pass — once the fact is in the document, editing the document is the only honest answer, which is what the TTL admits). A hypothesis answer reverses through `hypotheses.reopen` plus retiring the ask-history entry a rejection wrote, or the guess comes back un-proposable. A token is **taken**, not read: two presses on one toast must not restore twice. `restore` refuses over an occupied id — the analyst re-reporting it means the list holds something newer — and the panel says which happened rather than claiming a success. **Fix it and snooze offer none**: the first has already sent Claude at the house, and an undo that only took the card back would lie about what it undid; the second took nothing away and has "Bring it back now".
- **⚙ is a list of sections, each saying what it is set to, and nothing in a section folds away** (`#viewSettings` › `#setModal.setpage`, `#setNav` / `.setnavbtn` / `.setnavsum`, `showSettingsSection` / `showSettingsIndex` / `renderSetSummaries` / `SET_WIDE`). ⚙ has failed three ways. It was a 640px dialog that was one flat scroll — **5,910px at 390 and 3,837 at 1,200**, a paragraph under nearly every control — so the commonest visit (change the model, read the budget, see whether the login works) meant scrolling past corpus capture and the rehearsal. Then eight disclosures, with each section's rarer half in a nested `.setsub`. Then a page of eight panes on Insights' segmented control, which on a phone was a `<select>` hiding seven of its eight names, with the model picker inside Usage's *Advanced* fold, the Ask tab's settings inside Permissions' *Advanced* and the deep check inside Diagnostics' *Developer* — the owner's words were *"really bulky, hard to navigate sections, stuff is buried under collapsible sections"*. Now: **eleven sections on a list** — Account, Model & usage, Permissions, Notifications, Cameras & calendars, Memory, Personality, Instructions, Diagnostics, Developer, Guide — **each row carrying a second line that is the section's current answer** (*Signed in*, *Claude Sonnet 4.5 · 18% of this session*, *Asks before it acts*, the notification sentence), so the weekly questions are answered on the list itself with no press, and every section is one press away. **≥900px the list is a sticky 300px column beside the section in front** (remembered, `brain.set.section`, Account the fallback because an ingress iframe may be refused storage); **below it the list IS the page until a row is pressed** (`.setindex`), and each section carries **‹ Settings** back — a phone opens on the list every visit, because remembering a section there puts every other one two presses away, which is what the select did. **No form control lives inside a `<details>`**: a section's groups are `h4.sethead` headings (Model / Usage / Insight cards; House rules / Ask tab), the notification lines learned from answers are a plain list with their Removes, and Developer is a section of its own rather than a fold at the bottom of Diagnostics (Problems stayed in Diagnostics as **Report a problem**, beside the Share its ticks feed). **A section's loaders run the first time it is shown per visit** (`SET_LOADERS`, `setShown` cleared in `openSettings`), never at page load or on the list — Diagnostics its reads, Developer the rehearsal, captures, devloop and the why-question (`loadDeveloper`), split from `loadAdvanced` so opening Diagnostics no longer reads Developer's. **The root keeps the id `setModal` and carries `open` while the page is in front**, so every guard that asks "is Settings showing" asks the same question; `closeBox("#setModal")` is `leaveSettings`, and ⚙ pressed on Settings goes back. **There is no `?` in ⚙**: a tooltip is the one place a phone cannot read, so every hint is at most two short sentences on the page. Three safety lines stay on the page whatever else is cut: the sharing box's backup warning, the shell-command caveat under *Let brAIn act without asking* (`#setSkipPermsCaveat`, its own line so the stale-session warning above it never replaces it), and the calendar note beside the calendar picker. Every button says one of the redesign's verbs — Recheck, Run, Save, Share, Delete — with *Sign in again*, *Sign out*, *Edit* and *Export* the page's own; Sign out is neutral at rest and confirms once. `#setModal`'s selects and number boxes are restated at 16px in the *scoped* coarse block, because `.edit-body .selin` outranks the bare `select` in the text floor and every dropdown in ⚙ once zoomed an iPhone into the ingress iframe. **One visual system and a search** (the 2.18.6 pass, after *"the settings page still is really ugly… the toggles under help develop brAIn aren't using space well"*): a section's content stops at **600px** (the card at 680) — the switches under Help develop brAIn had been 700px from their own names; **every switch is a row** in a `.setgroup` (a tinted surface, hairlines between rows): its name at 14px over one muted line, the switch in a right-hand column beside them, the whole row the target — the input stays first in the label so the whole row toggles it and CSS places it — and cameras and calendars take the same row from CSS because their loaders draw them; one type ladder on the panel's own scale (section 20, group heading 16, field label and switch name 14, sub-heading and hint 12, no capitals — `measure-tokens` holds the scale) and the `--sp-*` steps for spacing. Help develop brAIn is two groups of switches, then Repository, **What it sends** (one card per stream: the name and its purpose split at the label's colon, the switch beside them, when it last ran and How often · Run along the foot; two columns ≥600px, one on a phone), Daily limits, What do you want to fix? and Reports. **Search sits above the list** (`#setSearch`, `buildSettingsIndex` / `searchSettings` / `jumpToSetting`): client-side over the page's own markup, read at the moment of asking — every switch's name and the line under it, every field label and the hint after it, every heading and section name — so a setting is findable by having been added; a setting inside something hidden is not offered; while it holds words the list gives way to the matches (`.setresult`, each the setting's name and its section), a press opens the section with the setting in view, focused and marked (`setflash`, `openSettingsAt`'s landing), Enter takes the first, Escape clears, and nothing found says so. `tests/manual/measure-settings.mjs` drives the real page at 390, 768 and 1200 and fails on the open height past its budget, a section count, name or order other than the eleven, a row under the touch floor or with no second line, a list whose lines do not say the sign-in, model, usage and permission answers, **any weekly setting (sign-in, model, usage bar, budget, notification sentence, the permission switch) not visible one press after opening ⚙**, any control inside a fold, a narrow page that does not open on the list or whose ‹ Settings does not return to it, a wide page that forgets its section across a reopen or a reload, a lazy read fetched early, any `?`, a hint past two sentences, a missing safety line, a red Sign out, a button outside the verbs, a text control under 16px, sideways scroll, or any element id handlers bind to going missing — and on a search that does not find and open a setting, a switch not to the right of its words or more than 640px from the start of its label at 1200, a switch outside a group, or a camera row whose switch is on the wrong side. `measure-devloop` holds the stream cards: two columns at 1200, one at 390, the switch beside its name.
- **Who brAIn is in this house is brAIn's, and the file is the wire** (`panel/personality.py`, ⚙ › Personality, `GET`/`PUT /api/personality`, `POST /api/personality/growth`). The household's chosen personality lived in Morph's own code (a copy of `frontend/personality.js` holding `PERSONA` and `GROWTH`) and was shown only in Morph's Settings — *"not every person who uses these apps are going to use Morph, but they have to use brAIn"*. It is `/config/.brain/personality.json` now: `{name, persona, growth: [{date, at, text}], updated_at}`, oldest growth first, every field capped (`NAME_MAX`, `PERSONA_MAX`, `GROWTH_TEXT_MAX`, `GROWTH_MAX`), written through `atomic_write` under its lock, never creating its own directory, and read by a `load` that never raises (absent or broken is "none set", which changes nothing anywhere). Morph reads this file and the route; nothing writes `/config/morph`. `migrate_from_morph` runs once at panel startup, only while brAIn has no file: a tolerant reader of the object-literal subset such a module is written in (any quote, unquoted keys, comments, trailing commas), refusing a `${…}` template or a call rather than guessing, and saying in the log what it moved or why it moved nothing. **A PERSONA object is read whole** (`_render`): it kept only the top-level strings, so traits, voice rules and a nested description (lists and objects) were dropped and a house's persona came out two lines long; now the lead text comes first and every other part follows, lists as `- item` lines and nested objects as indented `key: value` lines, and growth is read under any of `GROWTH_DATE_KEYS`/`GROWTH_TEXT_KEYS` or as a plain string. `repair_from_morph` (startup, after the migration) replaces a stored file that is exactly an earlier, poorer import — the same name, every persona line and every growth entry inside a fresh read, which holds more — and never one with anything the fresh read lacks, which is somebody's edit (`tests/test_personality_rich_import.py`). `prompt_block` ("Your name is X. Your personality: …", the persona cut to `PROMPT_PERSONA_CHARS`, the newest `PROMPT_GROWTH_ENTRIES` growth lines) is the one wording, carried by `_chat_system_prompt` (so the terminal's appended prompt, rewritten on every save), by `ha-context-gen.sh` (`personality_section` runs `personality.py section`) and by `brain_voice_context.system_prompt`, where it stands in for `DEFAULT_STYLE` and an agent's own personality still wins; with none set every prompt is byte-for-byte what it was. A conversation records growth with `note_personality_change` (one panel request): it writes a file every later conversation is told, so it is on `ANALYST_DENIED`, `GATED_MCP` and its hook copy, `CONTRACT_REFUSED_TOOLS` and `VOICE_REFUSED_TOOLS`. ⚙'s **Ask** opens the terminal with the personality as the subject. `tests/test_personality.py`, `measure-settings`.
- **Every prompt brAIn sends Claude is readable and replaceable in place** (`panel/instructions.py`, ⚙ › Instructions, `/api/instructions[/{key}]`). `CATALOG` maps a key to the module attributes the runs read (`server.CHAT_IDENTITY`, `brief.SYSTEM`, `resident`'s two, `fixer`'s two…); an override is a file in `/config/.brain/instructions/<key>.md` that `apply` `setattr`s onto every carrier, so nothing that reads a prompt had to change. `shipped` captures each carrier's text before any override, `export_builtins` writes it to `builtin/` at startup so Claude in the terminal can read what ships, and `check` refuses an empty text, one past `MAX_CHARS`, or one missing a placeholder (`{x}` / `%(x)s`) the shipped text has — a prompt that loses `{findings}` silently stops seeing findings. A file that cannot be read or fails the check is said (`error`) and the shipped text stays in force. The scheduler tick calls `sync` (a stat per key), so an edit made in the terminal lands within a minute. `FILES` lists the files Claude reads (CLAUDE.md, its notes block, memory, Morph's AGENTS.md and LEARNED.md); only the notes block and Morph's two are writable here — the rest have one writer each. `server` runs as `__main__`, so `_module("server")` falls back to it. **Ask** opens Claude Code on the file through `openInTerminal`. `tests/test_instructions.py`, `measure-settings`.
- **The first hour shows what it found, as it lands, and ends on one automation to try** (`onboarding.reveals` / `parse_try` / `h_onboarding_accept`'s `try_rule`, `intents.request(trial=True)`). `reveals` reads what the study sessions filed out of the memory inbox AND `processed/` (so a consolidation pass filing a line does not take it off the screen), only `study:` sources, only since onboarding started, newest first, deduped, capped (`MAX_REVEALS`), and rides `learning_progress`, which the screen already polls. The recommend contract may offer **AT MOST ONE** automation as a sentence (never a question, never a lock), and ticking it sends the sentence through the ask bar's own drop — the standing shape ("From now on, …") — with `trial: true`, which `_one_intent` honours by starting the proposal's trial the moment it lands. One path from a sentence to a rule: `authoring.build`'s refusals and both simulations apply exactly as they do to a typed sentence, and a one-off answer ignores the flag. The flag is a field on the request rather than a `via` because `intents` refuses per-surface rules; `parse_request` keeps it only as a literal `True`. Nothing is written to the house by the tick.

**The top bar has two shapes and no third, and three tabs rather than eight.** **The logo carries the version under it, and the two are one link** (`#versionChip`, `paintVersion`): to this release's changelog entry, `CHANGELOG.md#` plus the version with its dots dropped (GitHub's anchor for `## 2.18.5` is `2185`), in a new tab — a link the person clicks, never a call brAIn makes. Stacked rather than side by side, so the bar is no wider than the logo was and every measured breakpoint stood (`measure-topbar` reported the same 129 shapes); the server writes `{{VERSION}}` in and the poll keeps it current, and while `/api/status`'s `integration.restart_pending` says Home Assistant still runs an older integration it reads `v2.18.5 · restart needed` with the restart signal's own sentence in its title and name — read off `integration` rather than the status state, which a signed-out house outranks. On a phone it is the logo's own slot in the 56px row (logo, dot, ⚙ — `measure-phone` and `measure-topbar` now name `versionChip` where they named `wordmark`). The restart wording widens it, in a state no measure covers; past 870 the one-row bar may then wrap, which it is allowed to. **On a phone the tabs leave the top** (design doc PR 10, `tests/manual/measure-phone.mjs`): the header is one row no taller than 56px holding the logo, a status dot that opens the status sentence (and any trouble chip's press) and ⚙, and Insights · Ask · Memory are a bar fixed along the bottom, safe-area aware, each a named 44px target, with every pane padded so its last line ends above it; nothing scrolls sideways at 390 or 320. The desktop shape below is unchanged. At ≥870px it is one 56px row; below that it is the two-row bar — status and actions on top, the tabs on a full-width strip beneath with each name under its icon. **A tab is a GROUP** (`data-group` on each `.viewtab` and `.subtab` in `index.html`, `groupOf`/`syncTabs` in `app.js`), and there are three: **Insights** (the insight cards, which the panel lands on; **Needs you**, the queue and To Do; and **History**, everything already answered), **Ask** (the chat and the terminal) and **Memory** (**Knowledge**, the facts; **Timeline**, what happened; and the **House book**). Insights and Memory navigate on ONE segmented control under the bar (`#segNav`, `SEG_GROUPS`/`syncSegNav` in `app.js`) that shows only the current tab's sections, buttons on a pointer and one `select.sel` (`#segNavSel`, rebuilt per group) at ≤640px; the sub-strip (`#subtabs`) is never on screen on these three tabs and stays in the markup because `subtab` buttons are where each pane's `data-view` and group are declared. **The cards are the first thing surfaced, and a decision is never more than one press away**: `#needsStrip` over the cards says how many things need you and leads with the urgent claim (or the first), reading the same `queue_count` as the badge, which also rides on the Needs you segment. A panel not ready yet (signed out, first run) lands on Needs you, where the setup card lives. The guide has no tab: ⚙ › Guide opens `#viewDocs`. **Every pane kept its id and its `data-view`**, so every handler, deep link and measure binds exactly as it did; `tests/manual/tabs.mjs`'s `openView` reaches a pane through its group, and switches to one with no visible button through `switchView` the way its own button would. Pressing a tab opens the pane the group was last on, and the panel lands on Insights. There was briefly a third band (960–1239px: one row, labels deleted, tabs shrunk to glyphs) and it was the worst possible one to have, because it is what a laptop with the HA sidebar open renders at — the compromise shape was the one most people saw, and widening the window made the tabs grow. **No width gets a row of bare glyphs.** Nothing in the bar may shrink (`.topbar > * { flex: none }`), so a fit is binary and an overflow is something a test can see; nothing hides its own words to fit, either. What gives way is the row, not the label. Tabs cap at 168px and centre so a 1200px strip isn't four 300px targets around a 20px glyph. Every target is ≥44px (chips ≥40px), the sub-tabs included. **Adding a tab moves both numbers, and removing four moved them back** — the breakpoint was 1240 until Proposals arrived, 1340 until To-do did and 1430 for the eighth, a tab being ~90px of row, and it came down to **920** with four (903px paused and 915px on a failed login, measured, which is where the number comes from), to 850 with three, and went back up to **870** when Today · House became the longer Insights · Memory (859px on a failed login). The strip **wraps** rather than shrinking (`flex-wrap` plus `min-width: 44px` on the tab, which is what makes the fit binary): the row gives way at whatever width stops holding it, the labels and the targets both survive, and `syncBarHeight` remeasures `--bar-h`; the sub-strip is sticky under the bar and in normal flow, so `--bar-h` and the terminal's height never see it. Adding anything to the bar moves the measured widths, so re-run `node tests/manual/measure-topbar.mjs` (Playwright; `CHROMIUM_PATH` if the browser isn't where it expects) and take the breakpoints from what it reports rather than guessing. All the measure scripts also run in CI as the `layout` job, so a regression fails the PR — running them locally is about reading the failure next to your editor, not about being the only enforcement. It measures three bar states per width (running / paused / failed login) because none is a superset of the others, and it fails on any target under the floor as well as on overflow. Panel heights come from `--bar-h`, which the panel remeasures at runtime. **A status chip that is permanently green does not belong there** — the auth chip renders only for trouble, and the space it used to hold pays for the usage pill's second number (`Session x% · Week y%`, each labelled in the bar).

**No text control may be under 16px on touch.** iOS Safari zooms the page in on focus below that and never zooms back out, which inside an ingress iframe strands the panel at an arbitrary scale — the docs search box at 14.4px is how it was found. The floor is set once in a `@media (pointer: coarse)` block, not per control, so anything added later is covered by having been added.

**Every control in the bar does its own job, and nothing is in it twice.** Three controls used to open Settings, so a bar reporting three different things answered all of them with one dialog. The usage pill renders only when it is news (`usagePillWanted`: past 80% of either window, or automatic insights paused by the budget) — the numbers live in ⚙ → Model & usage the rest of the time — and opens a disclosure popover (`#chipPop`) with both windows, their resets and what the budget gates — a *press*, never a hover, because a `title` is unreadable on the device where that pill matters most. The paused chip presses straight through to `saveSettings({auto_enabled: true})`; it renders **only** for that, because "usage budget reached" had a chip of its own beside a pill already showing the number it was about, and saying it twice is what wrapped a phone bar onto a third row. A reached budget is now the pill's own warning dot plus a line in its popover. ⚙ is the only route to Settings. Storage access goes through `prefGet`/`prefSet` — a browser may refuse an iframe its `localStorage`, and a throw at the top level takes out every handler declared below it.

**A popover whose anchor has gone is dismissed, not relocated.** `positionChipPop` bails on a zero-sized anchor: ⋯ → Model opens `#chipPop` from a menu item and the same press closes the menu behind it, so there is nothing left to measure against and the next reposition put the popover at (8, 6) — the top-left corner of the screen. Same call `scroll` already makes, for the same reason.

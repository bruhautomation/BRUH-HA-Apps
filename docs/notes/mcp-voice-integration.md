# brAIn: MCP server, voice and the HA integration

The MCP server's tools and chokepoints, voice exposure and agent levels, the custom integration (services, events, AI Task, LLM API, admin gates), tasks and the listeners, ESPHome, Music Assistant, the other BRUH add-ons' tools.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **Free text from outside is wrapped as data in the MCP read tools** (`ha_mcp_server.untrusted` / `tag_attributes` / `tag_state`).
  - What is wrapped:
    - `UNTRUSTED_KEYS` attributes (media titles, descriptions, messages, bodies…);
    - a state that is free text (a newline, or over 24 characters with a space and not a number);
    - logbook messages.

    Each becomes `{"untrusted": true, "text": …}`, and `INSTRUCTIONS` and `VOICE_INSTRUCTIONS` say so.
  - `get_error_log` is deliberately not wrapped yet: wrapping changes its return type and several tests key on it. It can quote integration-provided strings, so it is the next one to wrap, with those tests updated.
- **A task may hand brAIn pictures, and they arrive as pictures, never as paths** (`automation-listener.sh`'s `task_images_message` / `task_feed` / `task_envelope_from_stream`, `TASK_IMAGE_DIR`). A narrow scope denies `Read`, so a read-only task could not look at a camera frame by opening it, and lifting `Read` for one file would lift it for `secrets.yaml` too. So the listener reads the task's `images` itself — at most four, each a plain name directly inside `/config/.brain/task_images` after `realpath`, a regular file under 5 MB, a JPEG/PNG/GIF/WebP by its magic bytes and never its name — deletes each one, and feeds the run a stream-json user message of image blocks and the prompt (`--input-format stream-json --output-format stream-json --verbose`); the last `result` line is moved into the output file so the journal, the landing and the extraction read the envelope they always did. All three attempts (the run, a lost resume, the MCP retry) feed the same message; a task with no usable picture runs as text, byte for byte as before. BRUH Bambu Studio's print failure detection is the caller (`design/brain_link.submit(images=, kind="look", scheduled=True)`), and `scheduled` puts every look nobody pressed for under brAIn's own pause and budget.
- **An automation branches on data, so `brain.ask` answers with the shape it asked for** (`__init__.handle_ask` / `bridge.async_send_task_full` / `automation-listener.sh`'s `--json-schema`). `brain.run_task` answers in prose, which is right for a person and wrong for a template; `brain.ask` takes a `question` and a JSON `schema`, the listener passes the schema to the CLI, and what comes back is `structured_output` — the object the CLI validated before it was sent — returned as `data` beside `response`. Read-only by default (`tools: read_only`), because a question is not a change. The events are one catalogue (`const.EVENT_CASE` / `EVENT_CASE_ENDED` / `EVENT_CHANGE`, fired by `FindingsWatcher` off the mirror's roster): `brain_case` carries the case, `brain_case_ended` fires for a row that left the mirror, `brain_change` for one that went `fixed`, and the older `brain_finding` still fires beside `brain_case` so nothing written against it breaks.
- **Voice sees what Home Assistant exposes to Assist, and one module answers for the map, every read and every act** (`scripts/brain_exposed.py` / `ha_mcp_server.EXPOSED_ONLY` / `assist-worker-pool.apply_exposure` / the agent's own level). Settings → Voice assistants → Expose is the switch Home Assistant already has for exactly this question, and until 2.3 it had no effect on brAIn: the area map listed every controllable entity and the MCP server would read or act on any of them, so un-exposing the front door lock did nothing a person could see — the design page names it as the real surprise for an integration that registers as a voice assistant. **The rule is Core's own, copied rather than invented**: `expose_entity/list` answers only for entities somebody (or HA's default agent) has settled, and for the rest Core applies a default — a dozen domains, a few sensor device classes, never anything hidden or with an entity category, never a lock — and `brain_exposed.default_exposed` is that list, so a house that has never touched the switch gets the answer Assist gives. Three processes that cannot import each other's copies read the one module: the pool and the classic listener filter the map through `filter_map` (the listener over a pipe into the script's own `filter` verb), and the MCP server launched for a voice turn — `BRAIN_EXPOSED_ONLY=1`, set by the pool and the listener and by nothing else — refuses `call_service` for an unexposed entity, refuses area/device/label/floor targets outright (the protected list's reason: a hidden entity reached through its room is the bypass) and gates `get_entity_state`, `get_all_states`, `get_history` and `get_statistics`. **An exposure that cannot be read fails CLOSED**: the map is emptied with the reason in the log, acting is refused, and an agent set to Whole house is the way past it — a voice command refused with a sentence is better than one that reaches an unexposed lock because a WebSocket was down. The module borrows the MCP server's own `_ws_command` (siblings in `/opt` exactly as in the repo) rather than writing the handshake down a third time. `tests/test_assist_exposure.py` drives Core's rule over shapes copied from its answers, the gate through the chokepoints and never the helper, the pool's env into a real spawn, and the listener's route as the subprocess it is.
- **A voice agent's reach is set on the agent and nowhere else** (`assist-worker-pool.resolve_access` / `assist-listener.resolve_agent_access` / `const.ACCESS_LEVELS`). 2.9 gave each agent a level and kept the add-on's `assist_tool_access` and `assist_exposure` as the answer for an agent set to "Follow the add-on" — two settings on two screens for one question, and the add-on-wide one was the one that looked authoritative. 2.10 removed both options: `addon` is still a word an old agent carries and the integration still reads it, but it is no longer offered, and every reader — the pool, the classic listener, the conversation entity, the options flow — reads it (and a missing level, and any word it does not know) as `voice`, the narrowest. That is a narrowing on update for anybody who had widened the old options, and it is the right direction for the surprise to go: a request that did not say must never be read as permission. `tests/test_assist_exposure.py` asserts the options are gone from `config.yaml`, the translations and every script, and drives the shell half with the old env vars set to prove they no longer do anything.
- **Who may ask is asked in the integration, because Home Assistant does not** (`power_tools.async_require_admin`, `__init__._require_admin_for` / `NON_ADMIN_TOOLS`). Only `async_register_admin_service` is admin-gated and it cannot return response data, so `brain.run_task`, `brain.ask` and the memory writers were callable by any login — and a task's reach is the Supervisor token's plus, at `full`, a shell in /config, whatever the caller's account is. The power tools' gate is lifted out of `_admin_gated` and asked for every scope wider than `read_only`, for `add_memory`/`study`/`intent`/`answer_question` (what they file is handed to every later run), and **not** for `send_prompt` (the conversation channel with no access level is the voice level, which Assist gives any user). A context with no `user_id` is the system and passes — the power tools' rule — and an unknown user is refused, never read as the system. `RESERVED_MEMORY_SOURCES` is asked of the *sanitized* name, because that is what lands in the inbox. `tests/test_ha_service_gates.py` drives the real handlers through `tests/brain_ha_env.py` and fails against the old `__init__.py`.
- **A wide agent asked by a non-admin is NARROWED, not refused** (`conversation.turn_access`). HA lists every agent in every user's Assist picker and lets `conversation.process` name any of them, so a household member's app could reach a Full-admin agent. The voice level is exactly what HA's own Assist gives any signed-in user, so narrowing keeps their lights working and gives them nothing an admin's agent adds; a refusal would have broken the commonest case (a family member using the house agent from the app) to protect against the rarer one. `narrowed_from` rides in the context so the turn can say why it cannot do more, and a satellite or automation (no user) keeps the agent's own level — who may stand near the satellite is the decision the level already is.
- **A failure crosses the boundary as a failure, in one shape on both wires** (`automation-listener.write_task_result(…, error)`, the pool's `write_response(…, error)`, `bridge._poll_for_result` / `BrainRunError`, `__init__._failed`). The listener wrote `status: completed` on every result and the bridge read `.result` and nothing else, so an expired login reached `brain.run_task` as an answer, `brain.ask` as `{response: <apology>, data: None}` (which `| default(false)` reads as a real "no"), and an insight job as that morning's report. A failure is `status: failed` + a closed `error` word beside the sentence, a completed result is byte-for-byte what it always was (so an older reader is unaffected and BRight, which already raised on any non-`completed` status, needed nothing), and one reader serves both directories so neither can stop reading the failure. `is_error` on the CLI's own envelope is read before any words: "API Error: 529" is not an answer, and an `error_max_turns` envelope has an empty `.result` that used to surface as raw JSON. The remedy for a sign-in failure names the panel's **Sign in again** button and never `/login`. `tests/test_task_failures.py` drives the real `process_task` into the real bridge.
- **Voice context is resolved in the integration and WORDED in one module, in the turn** (`conversation.describe_place` / `describe_speaker` / `foreign_turns`, `scripts/brain_voice_context.py`). HA hands an agent the device/satellite, the user, `extra_system_prompt` and a chat log, and brAIn dropped all four. The entity resolves ids to names (an entity's own area beats its device's, HA's rule; floors only where `floor_registry` exists; the person whose `user_id` attribute is this user) and sends them as `context`; `brain_voice_context.preamble` is the only place they become words — the pool imports it, the classic listener runs it — because two copies of what a voice turn is told about where it is are two answers the day one is edited. **The voice system prompt lives there too** (`system_prompt`, the `system-prompt` verb for the listener): one operational prompt, the area map with whether it was cut to fit (a flag file, `area_map.cut`, since a marker line in the map would be filtered out), and a `remember_fact` line only while `learning` is on. There is no reflection pass after a voice turn any more; a fact is filed during the turn or not at all. Voice processes start isolated (`--setting-sources ""`, brAIn's MCP config and `--strict-mcp-config`, each only where the CLI takes it), so `/config/CLAUDE.md` and a user's own settings do not ride every spoken command. **It goes in the TURN, never the system prompt**: the pool hands a pre-warmed spare to a new conversation only when the system prompts match, so a prompt naming the room would match no spare and every satellite command would pay the cold start the pool exists to avoid. Every field is another process's data — capped, one line, labelled as context rather than the person's words — and a lookup that raises is a request with less context, never one that fails. `continue_conversation` is feature-detected on the result DATACLASS's fields rather than a version string, and the classic path mints the conversation id it returns (it returned the caller's `None`, so on cores without a chat log nothing ever continued). `tests/test_voice_context.py` drives a satellite turn through the real entity, the real bridge's file IPC and the real pool, and asserts the room is in what the fake CLI was handed.
- **A turn that reached a tool is never run again** (`Worker.acted`, `PARTIAL_MESSAGE`). The pool's fallback for a worker that died was a one-shot of the same request, which is right for a worker that died before touching anything and wrong for one that had already called `control_light` — the one-shot starts from a session with no record of it, so a toggle happened twice. `acted` is set on a `tool_use` block start, an assistant `tool_use` block or a `tool_result`, whichever the stream shape shows first; such a turn answers "may have partly happened" coded `partial`, the bridge's own rule for an accepted stream that broke. **A turn the CLI closed `success` is never `partial`** (`Worker.ask`, `QUIET_DONE_MESSAGE`): the result's `result` is only the closing message's text, and a model that says "Turning it off.", calls the tool and closes with no text has an empty one — which read as a turn that died, so a light that went off was answered "some of it may already have happened", journaled `error`, and its worker dropped. Such a turn answers with the last thing it said that turn (else "Done."); one that acted nothing and said nothing still falls back. `test_voice_run_contract`'s `_quiet_turn` is that stream, driven through `Worker.ask` and `Pool.process_full`. The classic listener reads `-p` text output and has the same blind spot (an empty answer after a tool is `empty`, and in resume mode is retried), not fixed here.
- **Insight jobs are unattended runs and answer to the same rules** (`_async_run_insight(scheduled=)`, `automation-listener.task_gate` / `task_memory_block`). `tools: read_only`; `memory: true` asks the listener for `ha_data._memory_for` (the panel's retrieval) instead of the integration's 2 KB byte-cut; `scheduled: true` makes the listener check `auto_enabled` and `usage_store.budget_state` first and answer `paused`/`budget` without spawning — an unreadable panel lets the run go, because the gate is a budget and not a safety scope. A failure is recorded as `error`/`error_code` beside the last good report and never notified as one.
- **The integration's tests load the integration for real** (`tests/brain_ha_env.py`). What the code branches on is a real class there — the exceptions, `IntentResponse`, the result dataclass (with or without `continue_conversation`), the registries — and only what it merely imports is an auto-module; a missing helper (`floor_registry`, `chat_session`) fails its import the way an old core does. `sys.modules` is restored after the load except for the package's own modules, which handlers import lazily at call time.
- **A narrow task scope denies what the analyst never had** (`automation-listener.task_tool_flags`). `read_only` and `house` are derived from `engine.ANALYST_TOOLS`/`ANALYST_DENIED`, and the analyst never needed `Read` denied: it runs from `CLAUDE_HOME` with no `--add-dir` and no project settings, so a file in `/config` is out of its reach by construction. A task runs IN `/config` with `headless_settings.json` (which `claude-run` hands every `-p` run that names no settings of its own) pre-approving `Read`, so the same pair handed `secrets.yaml` to any task that asked a question — and a non-admin may still ask for `read_only` through `brain.ask`. `Read`, `Glob`, `Grep`, `LS` and `NotebookRead` are added to the deny list for both narrow scopes there, and not to `ANALYST_DENIED`, because study sessions read the same pair and a change to the analyst's contract is a different decision. `tests/test_task_tool_scope.py` drives the lifted function.
- **brAIn is Home Assistant's AI Task entity, read-only and validated twice** (`custom_components/brain/ai_task.py`). Feature-detected with `getattr(Platform, "AI_TASK", None)`, `todo`'s rule, so an older core never imports the module; one entity per house (`_ai_task_added`, cleared on unload). `_async_generate_data` sends a `read_only` task with `memory=True` (the panel's retrieval), the requested structure converted to a JSON Schema the way HA's own LLM integrations convert one (`voluptuous_openapi` + `llm.selector_serializer`; a structure that will not convert is asked for in words), and validates what comes back against the structure itself before returning it — a misfit or an unreadable reply is a `HomeAssistantError` with the reason, never data shaped nearly right. A `BrainRunError` or a timeout is a `HomeAssistantError` naming the automation listener. Attachments are said and not read. It is treated as unscheduled: an automation calling `ai_task.generate_data` on a timer is not held by `auto_enabled` or the budget, because the task has no way to say it was scheduled.
- **Other agents get brAIn's measurements through Home Assistant's LLM API, and exposure is checked where HA knows who is asking** (`custom_components/brain/llm_api.py` / `bridge.async_llm_tool` / the pool's `POST /llm/tool`). Three tools (`brain_what_is_normal`, `brain_recall`, `brain_explain_change`), answered by the MCP server's own functions inside the pool process (`llm_tool`, an explicit `LLM_TOOLS` list, entity ids checked against a regex, numbers clamped), so a measurement has one implementation whichever agent asks. Exposure is asked in the integration with `async_should_expose(hass, assistant, entity_id)`: an unexposed entity is refused before the add-on is asked, `recall`'s facts about entities the assistant cannot see are filtered out, and an exposure that cannot be checked refuses. Feature-detected (`llm.async_register_api`), registered account-wide beside the watchers and unregistered with them. It needs the pool (fast mode); a pool that is not up answers in a sentence the asking model can repeat, never an exception in somebody else's conversation.
- **An echo is not a report, and the word it echoed was one it refused** (`ha_mcp_server._dashboard_named` / `_dashboard_wire_path`). `get_dashboard` answered `url_path or "default"` in all four of its exits, which says nothing a caller did not already know and cannot tell *I asked for nothing and got the default* from *I asked for a dashboard called default* — and `lovelace/config` has never heard of `"default"`, so passing back the word the answer printed came out as **Dashboard not found: default**. The documented workflow is fetch, edit, save, and `brain.update_dashboard` takes exactly that literal for the default dashboard (`power_tools._dashboard_key` maps it and `None` to the same storage key), so one half of the pair handed out a token the other rejected and the round trip broke at its first step. The report is now what was actually read — the token that fetches it again, `is_default`, and a name off the config's own `title` (or the registry row's) — and the wire never carries the word. A name is worth having and **not worth a second round trip on every read**, so a config with no title reports none rather than the tool going to look; the `url_path` is what is always there. The other half is a narrowing: a `config_not_found` whose dashboard list could not be read fell through to *"registered but has no stored config yet"*, which is a claim about registration it had no way to check and sends somebody to `take_control: true` on a dashboard that may not exist — that is `clear_resolved`'s rule in a third place, so there are three answers now and the middle one says the list is unreadable. The default dashboard never consults the list at all, having no registry row of its own.
- **ESPHome is three things reached three ways, and the module keeps them apart** (`panel/esphome.py` and the `esphome_*` MCP tools — there is no ESPHome screen in the panel since 2.10; the routes stay because the tools are one panel request each). The **files** are `/config/esphome/*.yaml`, which brAIn maps read-write, so listing, reading, writing, creating and archiving need nothing else running; every write goes through `automation_writer.snapshot` first, so `brain undo` reverts a device file exactly as it reverts a Claude edit — one journal, one reverter — and a write carrying the `mtime` the editor opened at is **refused when the file changed since** (saved from the ESPHome dashboard meanwhile), because the edit that silently loses somebody's work is the one that wins a race nobody could see. A file that does not parse is **saved and says so** with the parser's line: it is somebody's file. The **builds** — validate, compile, install (`run`), upload, logs, clean — are the ESPHome dashboard's, because PlatformIO's toolchains are glibc binaries and this image is Alpine. **Two dashboards answer to that name and brAIn speaks both**: ESPHome 2026.9's Device Builder takes every command over one `/ws` (`{command, message_id, args}`; validate and logs stream on the command's id, compile/install/clean are persistent jobs followed with `firmware/follow_job`, and an install answers with its COMPILE job only — the flash is an upload job with `depends_on`, found with `firmware/get_jobs` and followed too, or "done" would mean compiled rather than flashed), while the old dashboard took a WebSocket per command (`{"type": "spawn"}` in, `{"event": "line"}`… `{"event": "exit"}` out). Which one is there is learned from the Builder's hello — its first `/ws` frame carries `server_version` — and remembered on the cached `Route`, because the Builder answers the old paths with its web page and a WebSocket handshake against a web page failed every install in milliseconds while HTTP listing kept working. The Builder protocol was read off esphome-device-builder 1.15.0's source rather than guessed, and `tests/test_esphome.py` drives both against real aiohttp servers run as an in-memory `Job` the panel polls, one per configuration at a time, stopped within a second of a press, and a log stream is capped and stopped when its dialog closes however it closed. **Reaching the add-on's dashboard took reading its nginx rather than guessing**: it runs on the host network and its ingress server allows only the Supervisor and loopback, so this container's own requests are refused by design — what works is the Supervisor's ingress proxy (`/ingress/<token>/…`) with an `ingress_session` cookie minted the way HA's own frontend mints one, Core's `supervisor/api` WebSocket command posting `/ingress/session` (the Supervisor mints sessions for Core and nobody else). `esphome_dashboard_url` is tried first for a dashboard elsewhere, and a dashboard nobody can reach is **a sentence naming everything tried**, never an empty list — "no dashboard" and "no devices" are different answers. The **HA side** is the registries: which device a file is (matched on the registry's own `name` against the file's node and friendly names — never `name_by_user`, which a rename moves), and whether it carries a protected entity, because **flashing a device is acting on every entity it has** — `protected_entities` refuses install, upload, the HA-update route and delete, a device HA has never seen carries nothing (a real answer), and a registry that could not be read refuses while the list is non-empty. When no dashboard is reachable, `update` installs a waiting firmware update through HA's own `update.install` (Core's ESPHome integration is linked to the dashboard even when we are not) and says so rather than claiming an install it cannot make. `secrets.yaml` is **keys out, values in**: nothing reads a value back, and `set_secret` replaces one top-level line and nothing else. The MCP tools are one panel request each (`_panel_send`, which reads a refusal's JSON body instead of reporting "the panel did not answer"), and the analyst gets the reading half — list, read, validate, logs, job — while every tool that writes a file, spends minutes of CPU on a build or replaces firmware is on `ANALYST_DENIED`. `tests/test_esphome.py` drives the dashboard half against a real aiohttp server speaking the protocol and the ingress half against a fake Supervisor that refuses a request without the cookie.
- **Music Assistant is reached where Home Assistant reaches it, with the token Music Assistant gave Home Assistant** (`panel/music_assistant.py` and the `music_assistant_*` MCP tools — no screen in the panel since 2.10, for the ESPHome reason: the add-on has its own, and a second copy inside brAIn was clutter). Its WebSocket API is the only door into what it holds, and a player it *remembers* comes back however often its Home Assistant entity is deleted: the config lives in Music Assistant, which is why "remove the aircast players" was a thing the registry tools could not do. **Reaching it took reading its source rather than guessing**: from schema 28 every connection sends `auth` with a token before anything else; Music Assistant announces a token for Home Assistant's integration through Supervisor discovery together with the address of its *ingress site* (port 8094, bound on the hassio network), and that token's system user is refused on 8095 and accepted on 8094 — so brAIn reads the `music_assistant` entry's `url` and `token` out of `/config/.storage/core.config_entries` and connects exactly there. The Supervisor ingress proxy that ESPHome goes through is deliberately not the route: Music Assistant signs an ingress request in only by its `X-Remote-User-*` headers, both of which it requires, and nothing guarantees a session minted for brAIn's system user carries a username. **The token's role decides what is possible and the status line says which**: `service` can control, configure, group and remove players and write the library; providers, server settings and users are an admin's, so `music_assistant_token` (an admin's long-lived token) is tried before the integration's, and an `InsufficientPermissions` (22) answer is explained naming that option rather than reported as a failure. The wire is Music Assistant's own: server info first, `{message_id, command, args}` out, results joined across `partial` chunks, pushed events skipped. **A stale player is two different things** — `remembered` (a config with no registered player: `config/players/remove` ends it for good) and `unavailable` (registered: removable only where the provider supports it, answered `ActionUnavailable` (19) otherwise, which is reported as *held* and can be disabled with `disable_if_held`) — and removal is a **dry run by default** with `stale_only` keeping a working player out of any provider filter. `protected_entities` is asked of every player a command names (`players_named` reads every argument spelling: `player_id`, `queue_id`, `target_player`, `child_player_ids`…), mapped through the device registry's `("music_assistant", player_id)` identifier and the entity's own `unique_id`, with a Home Assistant provider player checked as the entity id it is; an unreadable registry refuses while the list is set. The analyst gets `status`, `search` and `query`, and `query` is held to `is_read_only` in the panel — an explicit table plus `music/<type>/<read>` with a verb guard, because `add_playlist_tracks` ends in `tracks`. Voice gets none of them (`EXPOSED_ONLY` refuses with the sentence that sends it to `music_assistant.play_media` on an exposed entity, which the exposure gate can check). `tests/test_music_assistant.py` drives it against a real aiohttp server speaking the protocol, auth refusals and scope codes included.
- **The other BRUH add-ons are driven through their own integrations' services, and the voice split is held twice** (`ha_mcp_server.minecraft_*` / `print_label` / `label_printer_status` / `bright_*`, `VOICE_ADMIN_SERVICES`). brAIn does not talk to BRUH Minecraft, BRight or BRUH Print any other way: each tool is one `call_service(..., return_response=True)`, so an agent's Blocked services list, the deny-list and `protected_entities` apply exactly as they do to anything else, and the add-on holds the one implementation of every action. Each integration grew a response-only `get_status` for it, because a model asked to "print a freezer label" or "start the Friday party" has to name a stock, a template or a set that exists, and guessing is how it meets the refusal. **Spoken names are resolved against who is online** (`_mc_resolve`): case, spaces and a Bedrock player's `.` prefix ignored, a unique partial match accepted, and two candidates returned as a question — teleporting the wrong child is the failure. **A voice-level agent may play and may not administer**: op, ban, kick, the whitelist, a raw console command, stopping the server and installing server add-ons are refused in the tool AND in `call_service` (`VOICE_ADMIN_SERVICES`), because a rule held only in the tool is a rule the generic tool walks round. A speaker or scene handed to BRight in a field other than `entity_id` is checked against exposure and the protected list by hand (`_entity_arg_refusal`), since the chokepoint only reads `entity_id`/`target`. Voice prints at most `PRINT_VOICE_MAX_COPIES` labels. **BRUH Bambu Studio is the exception the owner made**: voice may design a part and start a print (`bambu_design`, `print_file`, `print_part`, `design_part` on `VOICE_UNTARGETED`, at most `BAMBU_VOICE_MAX_COPIES` copies), and stopping a print, G-code, a slice, Open in Bambu Studio and importing a link stay in `VOICE_ADMIN_SERVICES`. `bambu_design`'s way to "design it and print it" is to put the print in the description, so the design conversation prints it once built (`print.go`) and a voice turn never waits on a build. **An add-on's tools are listed only where its integration is** (`ADDON_TOOL_DOMAINS` / `_service_domains`, Core's `get_services` over the WebSocket, cached `SERVICE_DOMAINS_TTL_S`): a house without `bruh_bambu` is offered no `bambu_*` tool, on any channel. A list that could not be read lists them — "could not ask" is not "not there", and a call to a missing integration answers in words — and a call to a tool not listed is still answered. `tests/test_mcp_bruh_addons.py` fakes Core at the WebSocket and drives the real chokepoint.
- **GardenRX is driven the same way, and what the garden grew is a fact any run can recall** (`ha_mcp_server.garden_*`, `panel/garden_facts.py`, `facts_store.replace_keyed`). Eight tools over the `gardenrx` integration's own services, listed only where that domain is: `garden_status` (its sensors' `gardenrx` attribute, exposed ones only on voice) and `garden_harvests` read and are on `ANALYST_TOOLS`; the six writes are on `ANALYST_DENIED`, `GATED_MCP` (both copies) and `CONTRACT_REFUSED_TOOLS`. Voice may log a harvest, a spray and a note (`VOICE_UNTARGETED`); queueing a spray, changing inventory and adding a crop or variety are `VOICE_ADMIN_SERVICES` and hidden from voice. A garden note is somebody's free text and comes back wrapped as untrusted. Each checks pass turns the harvest sensor's `by_crop` into one fact per crop with the season's totals (`source: gardenrx`, `expires` four days on) and **replaces** the last pass's set: a keyed row carries `keyed`, `replace_keyed` drops the source's keyed rows not written this time, and `recall`'s per-subject cap counts keyed rows per predicate so ten crops on one sensor are not cut to three. A sensor that is unavailable, or a `by_crop` that is not a list, writes nothing and removes nothing — "could not read" is not "nothing grew".
- **What a device shows as is four tools over four brain services, not a second implementation** (`ha_mcp_server.set_device_class` / `show_switch_as` / `stop_showing_switch_as` / `set_sensor_display` / `_brain_call`).
  - Each is one `call_service("brain", …, return_response=True)`, so an agent's Blocked services list (every new agent's carries `brain.*`), `protected_entities` and the voice service rule all stand in front of it at the one chokepoint. `_voice_service_refusal` refuses a brain service naming another domain's entity, and the four are also in `VOICE_HIDDEN_TOOLS`, so a voice turn does not pay for their schemas.
  - **They change the house, so the action gate stands in front of them**: they are on `consequence.GATED_MCP` and the hook's copy, which a test holds equal to `engine.ANALYST_DENIED` less the four that change nothing. Being on `ANALYST_DENIED` keeps them from every unattended run; `test_security`'s acting-name regex covers `show_`/`stop_`.
  - **A refusal is the Power Tool's own sentence.** `_ws_command` hands Core's error back as a dict's repr, with `Validation error: ` in front of a ServiceValidationError, and `_ws_error_parts` takes the code and the sentence out. A `not_found` naming the service says Home Assistant has not loaded the new integration yet and needs a restart.
  - `set_device_class` requires `device_class`, and an empty string is the reset: leaving the argument out must not read as "wipe the override". `set_sensor_display` spells "put back the integration's own" as `-1`, because a JSON-schema integer cannot also be null.
  - **`protected_entities` holds across a `switch_as_x` pair** (`_switch_pair_refusal` / `_switch_pair`, in `call_service` right after the ordinary protected check). `show_switch_as` and `stop_showing_switch_as` act on the other half of the pair from the one the payload names: named by the switch, they replace or remove the helper entity that shows it as something else; named by that entity, they re-wrap or unhide the switch (and Core's `async_remove_entry` hands the switch's Assist exposure back). So asking about the named id alone let a protected lock made from a relay be deleted by naming the relay. While the protected list is non-empty, the entity registry is read FRESH, never off `_protected_scopes`' 60-second cache, because these two services are what change the pair, and the call is refused when the wrapper or the switch on the other side is protected. The switch a helper stands in for comes off the helper's registry options (an entity id, or a registry uuid resolved). It fails closed: an unreadable registry refuses, a named helper whose switch the registry does not say refuses, and a protected helper whose switch is unknown refuses because it may be the one this would replace. The generic `call_service` tool meets the same check, and with no protected list the registry is not read at all.
  - `set_device_class` sends `confirm_safety: true` only when the argument is a yes (a bool, or one of `_TRUE_WORDS`); an absent flag is no, and the refusal that follows is the Power Tool's.
  - **`get_registry` says what an entity is shown as.** `config/entity_registry/list` is `as_partial_dict` and carries no device class, so a list narrowed to `MAX_TYPED_ENTITIES` (100) rows is read again through `get_entries` (`extended_dict`) in one round trip for `device_class`/`original_device_class`. A wider list says how to get them, and a failed second read says so rather than dropping the list. `shows_switch`, `display_precision` and `display_unit` come off the options the listing already carries.
  - `ha-context-gen.sh` names the four under the Power Tools' entities line. `tests/test_mcp_device_types.py` drives them through the real dispatcher with Core faked at the WebSocket.
- **`protected_entities` is enforced in the MCP server and nowhere else.** `DENIED_SERVICES` restricts a *channel* (voice may not unlock); `PROTECTED_ENTITIES` restricts an *entity* for every channel, and the terminal, the chat, the fixer, voice and automations all reach the house through that one process, so `call_service` — the chokepoint every `control_*` tool routes through — is the one place to ask. run.sh exports `BRAIN_PROTECTED_ENTITIES` and writes it to `/data/.brain_env`, which is every route an option has into a Claude process. An area or device target is resolved through the entity and device registries (`_protected_scopes`, cached 60s) and refused if it contains a protected entity; the registry unreadable fails **closed**; labels and floors cannot be resolved here and are refused outright while the list is non-empty — the same conservatism `_meta_call_denied` applies. Read-only tools are untouched: a protected entity can be looked at, not acted on. `tests/test_protected_entities.py` drives `call_service` and `control_lock`, not the helper, because a helper that answers correctly while the chokepoint forgets to ask it is the bypass.
- **Which entities reach the voice assistants and each HomeKit Bridge is a read and a bulk change** (`ha_mcp_server.assistant_exposure` / `set_assistant_exposure`, `gate.exposure_floor`). The read lists, per assistant (Assist; Alexa and Google Assistant when Home Assistant Cloud is set up), controllable entities in use that are not exposed (Core's default rule for an entity nobody set, `brain_exposed.default_exposed`) and exposed ids that are unavailable or gone, and per HomeKit Bridge its accessories (off its diagnostics, else estimated from its filter) against `HOMEKIT_ACCESSORY_LIMIT` with a warning within `HOMEKIT_WARN_WITHIN`, what its filter leaves out and its stale entries; a bridge whose diagnostics do not answer says so rather than guessing. The change is `homeassistant/expose_entity` for the assistants and the bridge's own options flow for HomeKit, each form filled from what was asked and the form's own defaults, a whole domain listed out when one of its entities is left out, and aborted (`DELETE`) whenever it cannot be finished. `protected_entities` and the tripwire are asked of every entity named; it is on `ANALYST_DENIED`, `GATED_MCP` and the hook's copy, `CONTRACT_REFUSED_TOOLS` and `VOICE_REFUSED_TOOLS`, and the gate refuses exposing a lock, an alarm or a garage, door or gate cover (one whose kind cannot be read counts) unless the person's words name it, after the floors and before *Let brAIn act without asking* (`tests/test_mcp_assistant_exposure.py`).
- **The voice level scopes SERVICES as well as entities, and it is an allow-list** (`ha_mcp_server._voice_service_refusal` / `VOICE_UNTARGETED` / `VOICE_CROSS_DOMAIN` / `VOICE_REFUSED_DOMAINS`).
  - **The failure.** The exposure gate asked about the entities a call named, so a call naming none passed it with the Supervisor's admin token behind it. A default voice agent, the kitchen satellite's, could run `homeassistant.restart`, `hassio.host_shutdown`, `update.install` and `brain.create_user {admin: true}`, while the same `reload_config` was refused as a tool. `homeassistant.turn_off {}` on voice reached every entity in the house: the exposure gate had nothing to check, and Core reads it as "all".
  - **Three rules at the chokepoint.**
    - A call naming no target is refused unless its service is on `VOICE_UNTARGETED`: notify, `persistent_notification.create`, and the BRUH play services voice's own tools already use.
    - A targeted call may name only its own domain's entities, unless the service exists to cross domains: the meta-services, tts, Music Assistant playback, `scene.apply`/`create`. This keeps `brain.delete_entity {entity_id: light.x}` and `zwave_js.set_config_parameter` on an exposed lock out of reach.
    - `update` is the one domain whose same-domain service is administration.
  - **Why an allow-list.** A deny-list of admin domains lists only the ones somebody thought of, and every integration installed afterwards brings more.
  - **"Target" means the service's own target.** That is every entity-holding key at the top level or under `target` (`_top_named`), never one riding in a script's `variables` or a notification's `data`. Reading those as targets was the bypass again: `hassio.addon_stop` with a light tucked into `data`.
  - **Order.** Exposure is checked before this rule, because "that lock is not exposed" is the sentence a person can act on.
  - **New agents.** They are created with `config_flow.NEW_AGENT_DENIED_SERVICES` ticked: the administration half of the curated list, never `cover.open_cover` or `script.*`. That is what reaches a "Whole house" agent and makes the policy visible. "Open the blinds" stays possible, because a new agent that refused it would teach people to clear the list.
- **`get_history` sends `end_time`, and the logbook keeps its newest rows** (`ha_mcp_server._history_query` / `get_logbook`).
  - `get_history` is the panel's `history_params` rule, copied because the MCP server cannot import the panel. Core's default for a missing `end_time` is start plus one day, so `hours=72` answered with the day that ended two days ago.
  - The MCP tests could not see the bug: they mocked `ha_api_request` and grepped the endpoint. `tests/test_mcp_history_query.py` drives the real request against a real HTTP server.
  - The logbook returned `result[:50]` of a window Core answers oldest first, which is the part of "what just happened" nobody asked about. Its test asserted only the count, which both cuts satisfy.
- **What the server costs a conversation before it does anything** (`tools_for_channel` / `ALWAYS_LOAD_TOOLS` / `INSTRUCTIONS` / `_compact`).
  - A voice process is offered only what voice is not refused outright. The dispatcher refusals stay as the backstop, and `test_mcp_tool_surface` calls every hidden tool to prove it.
  - Results and the JSON-RPC envelope carry no padding.
  - The tools a voice turn acts with carry `_meta["anthropic/alwaysLoad"]` (`ALWAYS_LOAD_TOOLS`: the control tools, history, statistics, the forecast, `remember_fact` and the BRUH add-ons' play tools); elsewhere only the two state readers do (`ALWAYS_LOAD_ELSEWHERE`). Claude Code defers MCP tools behind tool search by default, and a voice worker told to act in its first response would otherwise spend a ToolSearch turn first. A voice process gets narrower schemas for a few tools (`VOICE_TOOL_VARIANTS`).
  - `offer_resolutions` is listed only where `BRAIN_CHANNEL` is `chat` (`CHAT_ONLY_TOOLS`), the one face that renders its buttons; it is still answered if called.
  - `initialize` returns instructions, a shorter set on voice, because they ride every turn.
  - A renamed tool keeps its old name in `TOOL_ALIASES`, answered and listed nowhere.
- **A ledger row and a remembered fact say which face asked** (`ha_mcp_server._channel` / `_run_id`, `actions.PERSON_CHANNELS`).
  - **The channel.** `BRAIN_CHANNEL` from the launcher. Failing that, the voice launchers are known by the `BRAIN_ASSIST_ACCESS` / `BRAIN_EXPOSED_ONLY` they already set. Anything else is `""`.
  - **The session.** It is Claude Code's own `CLAUDE_CODE_SESSION_ID`, which the CLI puts in every stdio MCP server's environment (read off the 2.1.288 bundle).
  - **The miner.** `actions.classify` files a voice row as `voice` and a chat or terminal row as `person`, both with `via: brain`. Everything else stays `brain`, the safe direction: an unattended run filed as a person would invent overrides and habits, where a person filed as brAIn only loses one. The nearest matching call explains a change.
  - **Overrides.** `find_overrides` counts `voice` as a person putting something back (`PERSON_CAUSES`), which also covers Home Assistant's own Assist.
  - **Facts.** `remember_fact` files under the channel, or "conversation", never "voice" for a face it cannot name. A voice agent may not file a fact whose subject it cannot see.
  - **The directory.** The ledger writer never creates `/config/.brain`: `facts_store.writable`'s rule. Its `makedirs` grew a stray `/config` on every machine the suite ran on.

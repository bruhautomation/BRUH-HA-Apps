# brAIn: insight cards, reports and the brief

Card generation and refresh, verdicts, live data, the card contract, prompts preview, ideas, milestones, the morning brief, the weekly report and synthesis, deep review.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

What each rule cost to learn is in `docs/notes/history/insight-cards.md`. The tab is Insights (sub-tabs Cards, Needs you, History); these notes, like the panel's own words, call the card list *Reports*.

## Generation and refresh

- **A card refreshes when its inputs moved, not when a timer expired** (`server._card_inputs` / `_inputs_change` / `REFRESH_HOLDS`). The age floor alone meant a card regenerated over identical inputs produced the identical card at full price, every day, which is how a dashboard teaches people it is a timer.
  - The fingerprint is over the five things a run actually reads — the findings block for the domains that card covers, memory, the measurement stores, its feedback, its focus — and `refresh_mode` (`changed` | `always` | `never`) is the setting, with `changed` the default and `always` being what every release before it did.
  - The change is a **callable** evaluated only once the age floor has passed, because on most ticks no card has aged out and computing a whole-house fingerprint for one that has not is a read nobody asked for; the shared halves are fetched **once per tick** rather than once per card, or nine categories ask the same question nine times.
  - **A fingerprint that cannot be read falls through to the old behaviour** — "I could not tell" must not become a card that never refreshes again.
  - Every card records **`made_because`** in the words a person would use ("a finding it reads changed", "on its refresh interval", "first run since inputs were tracked") while a card that skipped records the **hold** instead, because a dashboard that has not moved in three days is otherwise indistinguishable from a scheduler that has stopped.
  - `open_findings` rides beside the hash and is deliberately **not** part of it: it is derived from the same text the `findings` part already covers, and counting it twice would let a re-worded finding read as a new one.
- **A refresh gate fingerprints what the run reads, never when a store was written** (`server._store_stamp` / `_memory_stamp` / `_card_inputs`).
  - Each store is its `progress()` state plus the ready sentence, never a build stamp or an mtime that moves every night whether or not a number did.
  - Memory is a digest of what the card would be told (the retrieval block when the store has rows, the document's fact lines otherwise), never the file's mtime, which every consolidation moves.
  - The findings block leaves the card's **own** source out, so a card filing a finding does not schedule its own regeneration.
  - `CATEGORY_STORES` (`categories.py`) must equal the shipped category ids: a category missing from it has no store part at all.
- **A card that failed is a card that waits** (`CARD_FAILURES` / `_card_backoff_until`, 15 min doubling to 12 h). `_refresh_due` and `_next_due` read the same backoff, so the card and the scheduler agree about when it is next due. The search→snapshot floor is skipped when the search was refused by the account or the service (`_no_fallback`: auth, rate limit, 529). That floor exists for tool and turn failures, and a snapshot asked of a refusing account is the same refusal at full price.
- **A card fetches what it needs; it is not handed the house** (`gather_mode`, default `search`).
  - `collect_orientation` sends a *map* — domain counts, area counts, a few anchors — and `run_analyst` searches for the rows the question actually needs (`get_all_states` takes a `domain` and a `name_filter`, so nothing has to enumerate ids). Measured: 1,449 prompt chars where the snapshot sent ~100,000.
  - **The middle option was measured and rejected**: handing Claude an index of every entity to pick from costs about what the slimmed rows cost, because every id has to be in it — searching by name skips the index entirely.
  - `snapshot` is the old single-turn path, kept as a setting **and as the floor**: a failed or turn-exhausted search falls back to it so a card always appears, and the fallback is logged because a run that keeps taking it is a run worth reading the log about.
  - Search is also the only path that can afford **history on a typed question** — the one-shot path never could.
  - `_framing` is shared by both prompt builders, and `_CARD_CONTRACT` by both system prompts: two preambles, one contract, because a second copy of 10 KB of output rules is a second copy that drifts.
- **A row in the bundle is 500 rows in the prompt, so its encoding is a cost.** `slim_state` spends the fewest characters that still carry each signal (72,943 → 52,086 chars on a 500-entity home).
  - `lc` is **minutes since**, not a 19-character ISO stamp: staleness is the only thing `last_changed` is read for — minutes rather than hours because "6 minutes ago" and "an hour ago" are different facts and cost the same.
  - `n` is dropped when `_slug(n)` equals the object id, which is what HA names an entity by default; a *renamed* entity keeps it, which is the case the field exists for.
  - An `unavailable`/`unknown` row keeps only `e`/`s`/`a` — its unit and device class describe a reading that is not there.
  - All three are in the prompt's field contract, because a field that is conditionally absent and undocumented reads as missing data.
  - **Retrieval was measured and does not pay here**: a two-step "index, then fetch what Claude picked" costs an index (~29k chars) *plus* the picked rows, which lands above simply sending all 500 slimmed rows; and an agentic loop re-sends its conversation every turn and can die on `--max-turns`. What retrieval would buy is *history on an asked question* — a capability argument, not a cost one.
- **A card comes only from an analysis of the house** (`card_claims.read_nothing`, checked in `_generate` against the run's transcript tool calls). A search run that called no reading tool is a routing note ("no data needed"), not a card: no card, no fault row, the card backs off. A headline of "nothing unusual", "nothing happened" or "no comparison possible" is dropped by `blind_lead` whatever tiles sit under it; the contract says a card names one thing to do or says all is normal in one sentence, and explains or leaves out specialist terms (aux, defrost).
- **Reports shows only cards whose run read the house, decided from what the run did** (`card_claims.not_an_insight`, `server._card_run_reads`, `gather`/`reads_house` on the stored card).
  - `_generate` records which path made the card (`gather`) and, for a search run whose transcript was found, whether it called a house read (`reads_house`; a snapshot run was handed the house, so True; a card kept only because its answer could not reach Ask records nothing and stays shown).
  - `_insights_listing` drops a card whose `reads_house` is False and that offers nothing.
  - A card stored before the fields is judged by its own transcript (`meta.session_id`, read once per id and remembered) only when it was asked and the house runs in search mode — a snapshot run calls no tool either, so a category card or a snapshot house is never judged this way. No words are read.
  - The Schedule line under the cards says what runs in words (`schedSummary`: "Two daily cards are on", "One card is on, one is off"), never "2 of 2 on".
- **A question that is not about the house is answered in Ask, never on Reports** (`interpret` route `chat` → `out["chat"]` in `server._route_ask`, `CARD_SCHEMA.about_house`, `server._not_a_card`, `noteChatHandoffs` in app.js).
  - The `chat` route opens the chat with the words.
  - A reply whose typed `about_house` is false (and that filed and offered nothing: a reply that did is a house card, its findings filed), or a search run that read nothing, is no card: the question starts a chat (not again when it came from the chat's Save as report, `to_chat: "from_chat"`) and the job ends `done` with `to_chat`, which the panel says once in a toast with Open.
  - An answer in words with no tile is still a card ("shut since 6:10 PM"): reading empty fields as "not about the house" throws real answers away and pays for a second run.
  - When the chat cannot be started the card is stored, so no toast claims an answer that reached nowhere. A category card that read nothing keeps the error and the backoff. A card stored before this stays until someone deletes it.
- **"Custom" is not a producer's name** (`findings_store.SOURCE_TITLE` / `_titled`, `server._asked_title` / `_card_source_title`). An asked card files its findings under the card's title (else its eyebrow), and a row or ledger entry already written as "Custom" is named off the stored card by a resolver the panel hands the store (a deleted card reads "Your question").
- **Deleted cards do not come back.** There is no restore list: brAIn proposes the cards a given home should have, so the answer to "I want that card again" is to ask for it and let brAIn build it for the house it now knows. Shipped categories are still `hidden` under the hood because their definitions live in the code, but that is a mechanism, not an offer.

## What a run costs

- **A run that costs something has to say so, on the thing it cost it for.** Generating a card is the most expensive thing the add-on does — a bundle out, a rendered visualization back, typically 25–45k tokens.
  - `usage_store.split_from_meta` derives it **once, server-side**, `total` being `tokens_from_meta` and nothing else: the log line, the stored `meta.cost` and the budget are one number, and a second copy of "which fields count, and that a cache read does not" written in JavaScript would be a second answer waiting to drift from the one the budget uses.
  - The job carries `prompt_chars` so the spinner can say `500 entities · ~33k tokens sent` *before* the answer exists (the only place a `CHARS_PER_TOKEN` estimate is allowed, and it is prefixed `~`).
  - The usage popover itemizes `budget_state`'s `breakdown`. The breakdown is **capped with the tail folded into one row, never truncated**, or the itemization sums to less than the percentage it is explaining — and it is labelled as brAIn's own runs, because when `source` is `account` the pill covers the terminal, the chat and voice too and a list read as exhaustive is how you conclude a terminal session is free.
  - The card's own foot no longer shows the tokens: it says one age (*The card on screen*), and tokens and the reason it ran are Diagnostics' business (the foot in `makeCard`).
  - `positionChipPop` bounds the popover's height to what is below the chip and lets it scroll.
- **An asked question is the expensive kind**: `collect_bundle` gives a category its slice and a question the *whole* home (`filter_states(states, registries, [], [])`, up to `MAX_ENTITIES`) plus device context, because the question could be about anything — so a handful of questions costs what a dozen scheduled refreshes do, and that belongs in the docs rather than in a support thread.

## The card contract

- **The title says what was counted, and brAIn's own limits are not news** (`_CARD_CONTRACT`). The title names the device, door or room measured, a title's number appears in the summary with the same meaning, and the recorder, retention, missing history and a comparison that could not be made go unmentioned unless they change what to do — make the one the data allows. The contract is kept short: room for a new line comes from cut examples, never from a rule.
- **Every figure in a card's title is in its body, with the same unit** (`card_claims.title_figures` / `title_figures_agree`, run by `card_verdict.review` BEFORE `_finish`, because `drop_title_echo` then takes a summary sentence that restates the title off and the body read must be the one the model wrote).
  - A title figure (in the claim after "Subject:"; a subject's number is a name) that the summary or a tile does not state with the same value — a whole title number may be the body's rounded — and the same measurement unit (°F/°C/°, kWh, %, gal, h…; a counted noun needs only the value), or a bare number with no unit, no counted noun beside it, no pair partner ("openings 14 → 5") and no earlier figure whose unit it takes ("1.2 kWh, down from 49.3"), is cut out of the title with the words that framed it ("over the last", "at", "from").
  - A claim left as one word or opening on a preposition leaves the subject alone.
  - Dates, ranges of days, years and ordinals are not figures; a clock time and "N h M min" are one figure each. The contract's title line says the same.
- **A card carries no note about brAIn's own run, and "worth a look" carries a reason or a step** (`card_claims._RUN_NOTE` / `trim_gaps` / `blind_lead`, `card_verdict.review`). A sentence about whether the reply needed data or a check could be made is a gap that is never kept beside real content (`trim_gaps`), and a card whose whole body is such notes with no tile is blind (held, or stored folded). The notes are the one lexical part (`_RUN_NOTE`); what stays structural is the typed `about_house`, the transcript's reads and the card's own fields.
- **A stored card is read by the rules a new one is, and a limit stays only where it changes what to do** (`card_verdict.legacy(open_rows=)` / `folds_quiet(open_rows=)`, `card_claims.trim_gaps(verdict=)`, `_SENTENCE_END`, `devloop/streams.design_context`, `.carddetails`).
  - `legacy`, which the listing, the dashboard page and the quiet fold read, drops a worth-a-look with no step and nothing marked to a plain note, gives one with an open row it names that row's step, and trims the summary — so a card kept by a hold or stored before a rule shows what a new one would.
  - Gaps (`trim_gaps`): on every card the summary keeps at most one gap sentence of at most `GAP_LINE_MAX` characters and drops tiles whose value is a gap ("no data", "n/a"). A gap sentence beside real content stays only on a worth-a-look or needs-action card and never as the last sentence; on an all-fine card a limit changes nothing anybody does. A card that is only gaps is left whole for `blind_lead` to decide.
  - A sentence opening "brAIn …" is split from the one before it (`_SENTENCE_END`), so its run notes and gaps are read as such, not as content.
  - The contract's first sentence is what the card means for the household in everyday words with the measurements after it, `next` is required with worth a look or needs action, and the panel puts the sentences after the first under a Details fold. Tile labels and the dashboard page's tiles wrap a long word instead of running out of the tile.
- **A place is its name, never its coordinates** (`categories._CARD_CONTRACT`). The contract says to call a place by the name the data gives it (a room, a zone, a place named in a game or on a map) and never to put coordinates in a tile, and the panel keeps an all-fine card's tiles behind Details (`docs/notes/panel.md`).
- The contract also says the verdict's comparison is the unit's own history, a range says what it ranges over, and a weather station is never its code.

## Verdicts and the quiet line

- **A card carries ONE verdict, as a chip, and its prose never says it again** (`CARD_SCHEMA.verdict`, `card_verdict.VERDICTS` / `lead_verdict` / `legacy`, `verdictChip`, `_whole_card_page`).
  - The reply carries `verdict` (`all fine` / `worth a look` / `needs action`; offered and not required, because an existing reply shape without it must still validate and is read off its own first sentence), and the contract says the summary never repeats it.
  - `review` takes a first sentence that is a verdict and nothing else off the front (when another sentence follows) and reads it as the chip, and the paths that took a "fine" off a card (a rise, an open finding, a disagreeing figure) set it to worth a look; "nothing new since" gives no chip.
  - A card stored before the field existed is read the same way at the listing and on the dashboard page (`legacy`), the file untouched.
- **A card's opening verdict is read against its own evidence** (`panel/card_verdict.py`, `_generate`).
  - A "fine" over a card that says it read nothing new is rewritten to "Nothing new since <the last card's date>" with no verdict.
  - A "fine"/"nothing needs action" over the card's own figures rising by more than half (`A vs B`, `B → A`, `from B to A`, `+N%`, "doubled") loses the verdict and the figures lead.
  - A SCHEDULED card whose whole content is that nothing happened (no findings, no status, zero counts or its own words) keeps the previous card, stamps it `checked_at` with a fresh fingerprint and records a `REFRESH_HOLDS` sentence — the scheduler counts age from `_due_stamp` (the later of `generated_at` and `checked_at`), or the next tick would queue the same run again.
  - A press is never held, a first card is never held, and a rewrite only removes a clause or adds the date the card already carried.
- **A "worth a look" its own card contradicts is not the card's verdict, and a tile's "now" ages** (`card_verdict.calm_lead` / `departs` / `_pairs`, `tileNow`, `_TILE_NOW`).
  - A model leaving out a step is not evidence nothing is wrong, so a LOOK card is never calmed merely for having no `next` or finding.
  - The rise check's `_pairs` skips a day of the month beside a month name (a date is not a figure), and also reads "A, usually B".
  - The reasoned lead ("Normal, because …") wins over the reply's `verdict` field only when nothing typed on the card supports LOOK (no finding, offer, attention tile, `next`, open finding named, disagreeing count) and no figure it states departs by half from the norm it cites; any opening that says worth a look or needs action (any punctuation) keeps or now sets LOOK/ACTION, and anything ambiguous stays as it was. `legacy` applies the same to stored cards, and a quiet card never holds a last card that said worth a look or needs action.
  - Tiles are readings from when the card was written, so an hour on the panel's tiles (card, share image) and the dashboard page say the age in place of "now" ("Indoor 9 h ago").
- **A card that is not all fine says what to do, and a card about nothing is not a card** (`CARD_SCHEMA.next`, `card_verdict.next_step` / `folds_quiet`, `card_claims._only_gaps`, `.nextstep`).
  - A worth-a-look or needs-action card carries `next`, ONE step: its own, else the fix of a finding it filed, the open finding it is about (its fix, or "See the open finding: …"), or a suggestion it made — never made up, and dropped on an all-fine card; the panel draws it as "Next: …" under the summary.
  - A worth-a-look verdict with no step, no finding, no offer, no tile marked warning or worse and no open row it names is dropped to a plain note ("worth a look with no reason or step"); "needs action" is not touched. A worth-a-look card with a tile marked warning and no step keeps its chip: a step is never made up and a missing one is not evidence nothing is wrong.
  - A card with NO verdict folds into the quiet line like an all-fine one when it is only that nothing changed ("Nothing new since <date>"); `_NO_CHANGE` reads "has not regenerated/opened/been used since" beside its old verbs, never any verb: "hasn't reported since 3am" is a sensor gone silent and stays a card.
  - A card whose every summary sentence is a gap and whose tiles hold no reading is blind: kept-last when scheduled, folded when first.
- **A card about nothing happening does not take a card's place** (`card_verdict.quiet_now` / `no_change` / `folds_quiet` / `QUIET_WHY`, `quiet` on the stored card, `quietLine`). A SCHEDULED card whose `verdict` is all fine, with nothing filed, offered or marked, and nothing changed (its own words, or every figure as last time) keeps the last card under `QUIET_WHY` and marks it `quiet`; a pressed card is stored but marked too; and Reports folds every quiet card, unless a finding on Needs you is about it, into one "All quiet: <names>" line whose names open each.
- **An all-fine card nobody asked for is a name on the quiet line, and the design review reads Reports, not the store** (`card_verdict.folds_quiet`, `server._insights_listing`, `devloop/streams.design_context`).
  - A category card whose verdict is all fine folds whether or not its figures changed (an asked one stays: it is the answer).
  - The house's design review reads the Reports listing (folded cards as one "All quiet" line, superseded and twin cards left out, the verdict and Next beside the words), never `load_insights()`, and cuts by whole sentence (`textclip.shorten`), never `clip`. It names folded cards as Reports does, never by their headline.
  - **Its findings are the rows on the list too**: the server passes only `LIVE_STATUSES` rows, never `findings_store.listing()` whole.
- **A blind spot is never a card's headline, and a card and a finding about one thing are one item** (`panel/card_claims.py`: `blind_lead` / `BLIND_WHY` / `trim_gaps` / `finding_twin`; `card_verdict.review(asked=)`, `blind` on the stored card, `told_in` on the listing, `twinLine`).
  - A card whose TITLE claims missing data, no comparison or no event — with no finding, suggestion or status, no worth-a-look verdict and nothing compared in the title (`_NEWS`) — keeps the last card when there is one (a scheduled run; a press stores it) and is otherwise stored `blind` and `quiet`, so `folds_quiet` folds it into the quiet line.
  - An ASKED card is never blind: "it stayed closed" answers the question.
  - The gap rules are under *The card contract* (`trim_gaps`). The contract's Thin-data line says the same.
  - The twin rule is under *Cards and findings*.

## Cards and findings

- **A card answers for its own rows on its next run** (`findings_store.own_reports` / `clear_unreported`, `prompt_block(own=)`).
  - The card's own live rows (`open`/`triaging`/`held`, up to `PROMPT_OWN`) are shown apart and the run is told to report one again only if what it read still shows it; after a run that answered, a row it was shown and did not report again (by text, or by the entity it named) is removed — `clear_resolved`'s ending, no memory line and no ledger entry.
  - Never on a failed run, never a row it was not shown, never a check's or one of `OWN_EXCLUDED` (the Resident, safety, corrections), and never a row a person touched: snoozed, put back, carrying a plan or a conversation's advice, in a fix or fixed.
  - **And a card is handed the OTHER live rows with their name, figures and window** (`prompt_block(figures=True)`, the two card prompt builders only): each row carries its device's name off `_NAMES` and its detail, and the block tells the run to quote that row's figures and window, use its name and mention it in one clause rather than retell it.
  - The refresh fingerprint reads the block without `figures`, because a check rewrites its detail every pass and a moved number on somebody else's row is not news to a card.
- **A card and an open finding about the same thing say the same thing** (`card_verdict.disagreeing_row` / `claims_fixed`, `CARD_SCHEMA.fixed`, `server._spawn_fixed_rechecks`). The prompt block says a count over a different window names its window in words; a sentence about a device an open row names whose count (times, runs, gal, kWh…) disagrees with the row's is taken off and the row leads; and a card that reads a row as already fixed — in `fixed` or in words — has that row's own check asked again through `_rerun_check`, so the rule that filed it clears or rewords it. A model's row has no rule and is left alone.
- **A card's headline decides whether it is a finding's story** (`card_claims.finding_twin(headline=)`, `h_insights`). A card every entity of which is an open finding's entity (or on its device) — or every entity its TITLE names (`_card_entities({"title": …})`) — is listed with `told_in: "f:<ts>"`: Reports draws it as an "On Needs you" line, and the finding's "From" link opens the card whole. A title naming something else too stays a card.
- **Two cards about one device or system tell one story** (`server._other_cards_block(covers=)` / `_shares_subject` / `_superseded`, `card_verdict.review(others=, names_in=)`, `_NAMES`' `device`).
  - A run is handed the cards about the same device or system (an entity it named, a device one belongs to, its domains and classes) first and in full — figures and when they were read — and told to quote them or say why its own differ.
  - A first summary sentence naming only another card's subject, and nothing else this card names, is dropped when more follows.
  - An older card whose every entity a newer card names, or sits on a device the newer names, is listed `superseded_by` and drawn as one line under the newer card (`foldedUnder`).
- **A report and a finding about the same thing link to each other** (`_card_entities` → `entities` on `/api/insights`, `casesForInsight` / `insightForCase` in `app.js`). A card shows "Also on Needs you: <finding>" and the finding "From <card>", joined by a finding's entity or evidence that the card names (its `live` list and the ids in its title, summary, tiles and learned facts — never its `html`, and only ids the house has once a checks pass named it) or a finding the card itself filed (`source` is the card's id); `renderIfChanged` keys on the links because the cases arrive on their own fetch. `measure-today` drives both.
- **A card's suggested automation goes through the ask bar's own drop** (`server._offer_card_opportunities` → `intents.request`).
  - `CARD_SCHEMA.opportunities` is a sentence plus the entities it names.
  - Each one is drafted, replayed, graded and offered exactly as a typed sentence is. There is one path from a sentence to a rule.
  - It is an unattended producer, so it answers to `_resident_gate`, caps at `MAX_CARD_OPPORTUNITIES` per card and `CARD_OPPORTUNITIES_PER_DAY` per day, and never re-offers what the same card queued last run.
  - A question is not a rule, and a sentence that is not yet routable is put in the standing shape ("From now on, …").
  - Each row stays on the card with `queued` and `why`, because a suggestion that went nowhere and one that is on Proposals look identical otherwise.
  - The menu's "Make this an automation" only fills the ask bar. Sending is the person's press.

## Live data

- **A count or a sum over the history is brAIn's figure, not the model's** (#1499; `card_figures`, `figures` in `CARD_SCHEMA` / `_CARD_CONTRACT`, `server._card_figures` / `_refresh_card_figures`). A card may declare up to four `figures` beside `live`: an entity, a state (default on) or one attribute's value, and `times` (changes into it) or `hours` (time in it), over the last `WINDOW_DAYS` (7). brAIn counts them from `/history/period` (one read, attributes only when a figure needs one), puts them first among the highlights marked `computed` (a run's tile with the same label is dropped), and counts them again into the stored card whenever a later run fails or is held by the usage limit, stamping `figures_at`; the prose stays the last run's. A figure with no history rows is left out, never shown as zero. A card that has never had a successful run has no spec yet, so it still has no figures: a category that declared its own `figures` would close that, and is the next step.
- **A card is written once, so a card about NOW is frozen at then** (`live` in `_CARD_CONTRACT`, `_clean_entity_ids`, `h_insight_live`, `LIVE_SNIPPET`/`watchLive`). A card may declare the entities whose state its visualization wants kept up to date; the panel refreshes those and hands them in through `window.brainLive(cb)`.
  - **The list is the card's OWN and is fixed when the card is written** — that is the whole security argument, because the frame is a sandboxed `srcdoc` running model-authored script and a route that took entity ids from the caller would let that script read any entity in the house through the panel's credential. The channel is one-way for the same reason.
  - **The page must render correctly with no live data at all**, which the contract states: the callback may never fire (an older panel, a lost connection, an entity since removed), so the snapshot values are drawn first and the callback updates them.
  - One timer for every live frame rather than one each, or six live cards are six polls drifting against each other.
  - A frame rendered nowhere — a closed modal, a tab you are not on — is **skipped and not dropped**, because `renderIfChanged` deliberately does not rebuild an iframe it does not have to, so a dropped entry would never be re-registered and the card would come back permanently frozen.
- **A live card's foot says one age, and its readings speak only when they stop** (`cardage`, `liveAgeText` / `paintLive` / `makeFrame(insight, live)`). The numbers in a live chart are seconds old while every sentence Claude wrote *about* them is from whenever the analysis last ran.
  - The foot says **Updated N ago** (or **From <run>** on a pinned run), a claim about the prose.
  - The live line renders only on a fault — `· N live readings not updating since …` — because waiting and fresh are the ordinary states and a line saying so on every card is a line nobody reads; the failure is the one state that must not read as the others, because a frozen number under a live label is the reading nothing can correct.
  - A failure **keeps the arrival stamp**, so the line ages from the last real reading rather than resetting.
  - The words carry the state and the warning colour only reinforces it (status by colour alone is what the design system forbids).
  - It is painted from the live tick rather than by re-rendering — a re-render every 15s to move one word would rebuild every visualization on the page — and there is **no second timer**, since the poll is already the only clock this needs.
  - **And a card pinned to a PAST run is offered no live data at all**: pushing today's door state into March's chart makes it a hybrid of that run's prose and this afternoon's numbers with nothing on screen able to say so. This applies to the expanded view too.
  - `tests/manual/measure-cardlive.mjs` drives the real `makeCard` rather than rebuilding it and asserts the empty line in both ordinary states; every wait in it notes rather than throws.

## The card on screen

- **A card leads with its answer, and the two things people want from one are named buttons** (`makeCard` / `card_tags.eyebrow` / `h_insight_refine` / `h_card_to_dashboard` / `snapInFrame`).
  - **The eyebrow is derived once, on the server** (`eyebrow` on `/api/insights` for an asked card: a hand-given name, else its topic tags spelled as words, else "Your question" — never "Custom", which is where the card came from and the one thing nobody needs telling); a recurring card is headed by its category, read live so a rename shows at once.
  - The question is shown only while the card is being made or has failed, because then it is all there is; afterwards it is one press away in the Edit dialog, and the contract tells an asked run the question is never shown, so the title names the finding and the summary opens with the answer — which the panel sets in ink (`splitLead`, the server's `_lead_split` for the dashboard page).
- **Refine is a regenerate that was told why** (`POST /api/insight/{id}/refine`, the dialog `openRefine` opened from ⋯ › Edit).
  - The note rides the job as `refine`, `_framing` states it as the run's task and shows the card as it stands under `THE CARD AS IT STANDS` rather than "do not repeat it", and `remember` (the default) files it in `feedback_store` — one store for both kinds of card, which is what stops the next scheduled run quietly undoing it, and deduped out of the feedback block so it is not said twice.
  - `_enqueue` resets `refine` and `because` on every queue, because `_set_job` merges and a job dict outlives its run: without that the next plain Regenerate is told last week's change and writes it on the card as its reason.
  - Regenerating an asked card sends `{id}` and re-runs it IN PLACE, and asked cards keep history, since the version a refine replaced is the one somebody may want back (the custom trim takes the history, feedback and mirror with the card).
- **The head is Ask · ⋯ and nothing else** (`cardask`, `cardMenuButton` in `makeCard`). Ask is a conversation with brAIn about the report (`askAboutReport` → `askAbout`, which follows the saved face; `docs/notes/chat-terminal.md`). ⋯ is Edit, Share, Past versions, Run, Delete, each with a name and a line of what-it-does. ⤢ is gone because a press on the card body opens it. Edit opens the dialog that refines the card; Make it recurring and the automation suggestions are links in it (`fillRefineMore`). Tag chips and the tag editor left the card; Reports gets a search box past `REPORT_SEARCH_AFTER` (8).
- **On an insight card the title gets the row, and two controls sit beside it.** The eyebrow is the part that gives way (one line, ellipsis); the title wraps to two lines and is never truncated. The head is a container query on the card, not the window: under 600px the title takes a row of its own under the buttons. Re-run `node tests/manual/measure-cardhead.mjs` after touching the head — it fails on a truncated or clamped title, a wrapped category, an overflowing head, or a target under 40px.
- **There is no "refresh everything" control**: it queued a Claude run for every card, beside the pill reporting the usage it spends.
- **A card is as tall as what it holds** (`.grid` and `#findList` are `align-items: start`; the frame follows `bruh-size`). A card's frame reports 0 and collapses when its page draws nothing (`.viz.blank`, kept laid out so a late chart can still report) and is otherwise exactly its page's height; the expanded view keeps its 120px floor, and the `/local` page's fit-its-frame rule is untouched.
- **The chart sits on the card**: no border, no background, `body` transparent in `CARD_STYLES` and `--bg` matching the panel's surface in both schemes, and the contract forbids a panel inside the frame, asks for fluid SVG and a pair that stacks at 260px, and puts the legend above the plot. Tiles are a grid whose columns come from the count (`data-n`), two on a card under 520px with an odd one out taking the row.
- **Share has two halves and neither sees the chart's DOM.**
  - The picture: the chart is model-authored script in an opaque-origin frame, so a fresh frame at one fixed width (`SNAP_FRAME_WIDTH`, so a phone and a desktop share one picture) is given `snapInFrame` as source text, clones itself, inlines the computed styles only for elements with animations (a draw-in's dash offset is invisible once animations are off) and posts back a PNG; `composeCardImage` lays the face out in the panel's own colours and draws it through a foreignObject. A browser that refuses the image clipboard (the ingress frame often does) gets the picture on screen to long-press, never a silent failure, and a chart that could not be drawn is said, not dropped.
  - The dashboard: `/api/dashboards` lists every dashboard with its views and, for one brAIn cannot write, the sentence why (YAML mode, auto-generated, a strategy) — `_unwritable_reason` is one function asked by the listing and by the save, so the two cannot disagree. The card is a Webpage card pointing at the `/local` mirror, which writes `<id>-<token>.card.html` (the whole face, the chart in a sandboxed srcdoc frame of its own, because `/local` is Home Assistant's origin) beside the chart-only file every older dashboard card already points at. A sections view gets the card as a section of its own rather than dropped into somebody's grid.
  - That page says **Updated N ago** beside its eyebrow, re-worked every minute against the viewer's clock (past two days the warning line above the card says how old it is), and it **fits its frame**: the page is exactly the Webpage card's height with nothing to scroll, the summary clamps at three lines and the chart's frame takes what is left (`flex: 1`).
- **A card is drawn in the dashboard's look unless somebody asked for another** (`categories.CARD_STYLES`, `refresh_styles`, `cardDoc` in app.js).
  - Inside the shell the panel writes the shell's theme onto the card's own `<html>` as `data-theme` before anything in it draws (just inside `<head>`, never before a doctype), and the sheet's three `:root[data-theme=…]` blocks restate every variable with Morph's surfaces, inks and hues and its font, with `color-scheme` per theme so a framed card is never a white box on a dark page; outside the shell prefers-color-scheme decides.
  - A card saved under an older copy of the sheet is served with the current one by `h_insights`, so a change to the sheet reaches every card on screen; a card from before 2.0 (no sheet) is left alone. The design paragraph of the contract says the dashboard's look is the default.
  - **Every palette runs in one order of hues, and the contract names them**: `--c1`…`--c6` are blue, teal, amber, violet, red, green in the default light and dark sheets and Morph's sky, teal, amber, violet, rose, lime in its three themes (`--c7`, `--c8` spare), so the design paragraph can say amber is heat or "on", blue is cooling, teal water, red open or alarm, green good, violet people, and be right in every theme; diverging is `--c1 ↔ --c5`. Reordering the series recolours old cards that used the variables, since `refresh_styles` serves every card the current sheet.
  - Morph's themes carry their own status colours (lime, amber, peach, rose) and `--font` / `--font-num` (Manrope and Bricolage Grotesque under `data-theme`, system-ui elsewhere; nothing is fetched).
  - In the shell the card itself wears Morph's shapes too (style.css's *insight cards in Morph's look*: a hairline, a 20px radius, quiet uppercase tile labels, no hover glow), on the page's own type scale. The contract also asks for a pair of charts in an auto-fit grid, hit targets bigger than the mark, a draw-in under 800 ms, and the quiet marks of Morph's look.

## The ask bar and the prompt

- **The ask bar has two verbs.** A question becomes a card; a line starting "learn/study/research/figure out" is routed server-side (`LEARN_RE`) to a study request the CLI-side watcher picks up. There is no separate "new insight" dialog — asking makes the card, and "＋ Make recurring" turns it into a scheduled one.
- **Reports carries no ask box of its own**: `/api/ask` and `LEARN_RE` are unchanged, a card's **Ask** opens a conversation about it, its ⋯ › Edit dialog refines it, and "Make it recurring" is a link in that dialog.
- **The ask bar's third verb ate its own questions, and the fix is one word further along.** *"when did the boiler last run?"* opens with the same word as *"when the guests leave, turn the porch light off"*, so `INTENT_RE` alone would send the question down the one-off path and spend a Claude run on a **refusal card**. `INTENT_QUESTION_RE` is the negation the route carries: an **auxiliary verb straight after the opener** (*when did*, *once was*) is somebody asking, and an instruction never has one there — *"when the guests leave"* and *"tell me when the dishwasher is done"* both put a noun phrase next. It is a second pattern rather than a hole in the first because the two rules are about different things, and it is deliberately not trailing-`?` detection: nobody types one on a phone.
- **And "already gone" is a removal that happened**: `automation_writer.remove` answers `missing` when the entry is not in the file, and since Remove is an intent's *only* ending, a 409 there would leave a card nothing could ever clear — so the row leaves the list and the undo token skips the revert it has no snapshot for.
- **A prompt nobody can see is a prompt nobody can argue with** (`server._prompt_preview` / `h_prompt_preview`). The prompt is a dozen blocks — the contract, the standing feedback, what brAIn has measured, the work list, the previous run, the budget, the data — every one assembled at run time.
  - **It is rebuilt, never replayed**: a stored copy starts drifting the moment it is written, and what somebody iterating needs is *what will be sent if I press Regenerate now*, which this answers exactly by calling the same builders the run calls. The data section is reported by SIZE rather than pasted.
  - **The editable part stays the focus**: offering the assembled text as a textarea would freeze those live blocks at whatever they said the day it was saved — the honest split is to show the whole thing and let you edit the part that is yours, which is the focus and the feedback, both of which already reach every future run.
  - It calls `resolve_category`, never `get_category`: the second answers with the SHIPPED definition and ignores every override, so a preview built on it would show a rewritten focus back as the shipped one.

## Ideas, milestones and deep review

- **An idea costs nothing until it is taken, which is why it is a separate PAGE** (`panel/ideas.py` / `server._run_ideas`). The separation that matters is the run, not the URL: eight ideas nobody takes cost one run, where eight cards nobody reads cost a run each, every refresh interval, for ever. Five rules.
  - **An answered idea is never offered again** — the fingerprint of everything accepted or dismissed is kept and consulted on every pass, an index never drained; accepting is remembered for a second reason of its own, since the category now exists and proposing it again is brAIn offering to build what it already built.
  - **A card this home already has is not an idea**, and the blocked set is seeded from the LIVE categories rather than from what this module has watched, because a card made through the ask bar, through onboarding or by hand is still a card.
  - **The cap refuses rather than making room** (`todo_store`'s rule).
  - **A pass that proposed nothing is an answer**, so `last_error` is written only where a run actually failed; an empty row is its name and Run, and a failed look still says so (`measure-ideas` asserts both halves).
  - And **the weekly top-up only ever ADDS**: it never clears the page, re-orders it or removes an idea nobody has answered.
  - The run is **started and never awaited** (`h_baselines_run`'s clock) with `IDEAS_STATE["starting"]` flipped synchronously (`start_auth_check`'s rule), and the top-up sits past every gate the scheduler already keeps while the press skips the budget — "automatic insights pause; asking by hand always runs" is one promise with two halves.
  - `system_prompt` substitutes its cap with a plain `.replace` and never `%`: prose about a house says "60% of your winter usage".
  - `tests/manual/measure-ideas.mjs` drives the real renderer and fails on a card missing either of the two blocks that make an idea judgeable, or on a meta row laid out with no gap.
- **Deep review and Suggested reports are Memory's, as folded lines** (`.kfold`). Suggested reports is a fold on Memory › Knowledge under the Teach box (`#ideasRow`, `#ideasMeta`, **Run**, and **Save · Ignore** on each idea); the deep review is *Review the whole house* inside its Tools fold (`#kReviewFold`, `#kReviewRun`). Each line is its name, when it last ran with its price or how many are waiting, and Run, and the name opens it. Switching to Memory is what reads both, and a running review is polled only while Memory is on screen (`refreshDeepReview`). Insights carries cards, and a press-to-open line saying how an insight card differs from the dashboard (`renderAboutCards`).
- **A deep review is a press, priced on the button, and files nothing** (`panel/deep_review.py` / `h_deep_review_run`, job `deep_review`, `PRESS_ONLY`).
  - Fable over the findings block, the house measurements, the memory retrieval and the last weekly report, with reading tools only; `engine.planned(job, pressed=True)` is the one route to a press-only job, and the run takes a PRESS seat.
  - The cost shown is the median of past reviews' tokens, or `FIRST_GUESS_TOKENS` labelled as a guess: **Run** with "~N% of a session" beside it and the token figure in the tooltip, each review dated ("4 Oct") and carrying no model name.
  - It observes (`KINDS`, `MAX_OBSERVATIONS`) and never writes a finding, a fact or a proposal — a review that filed rows would be an unscheduled producer with a Fable price.
  - Kept in its own capped store (`MAX_REVIEWS`); an unreadable store is answered as such and a save over one keeps a `.unreadable` copy. Started, never awaited (`h_baselines_run`'s clock); the running flag is flipped synchronously.
- **The moment a measurement first has an answer is the only moment it is news** (`panel/milestones.py`). `house.py` says *when*, and never *what*; this is the other half: each of the seven fires **once**, when its own predicate first turns true, and produces an ordinary insight card out of that store's own numbers. Four rules, each about not becoming a category.
  - **These are not the Insights tab's**: no `prompt_store` entry, no hidden shipped category, no schedule and no refresh interval, and they live on the Knowledge tab — a category is a standing question somebody asked to have answered, this is a fact that became knowable on a Tuesday.
  - **Once, and the settled key is what makes it once**: the card can be deleted, regenerated by hand or fail outright, and none of those may let the next checks pass file it again, so what blocks a re-fire is an entry in `_settled.json` written the moment the card is saved — the same arrangement `findings_store` keeps a ledger beside a list that is meant to empty.
  - **"Materially changed" is per milestone, in that measurement's own units** (a wake time that moved eleven minutes is the same house; one that moved ninety is a different household), because a single threshold over seven different units is a number nobody could argue with.
  - And **the extra bar is a CARD's, not the measurement's**: every predicate reads `progress()` rather than re-deriving readiness, and what lives here is only "one baseline is a measurement and twenty-five is a picture of a house".

## The weekly report, the brief and their schedule

- **A weekly report is not a brief with a longer timer** (`panel/weekly.py`). The brief asks *is there anything* and is silent most mornings on purpose. A report asks *what happened*, and a report that lists everything is the dozen unread cards with the covers off. So every section is gathered deterministically and **capped** before a model runs, and the model's job is to say four things rather than to choose which four.
  - **"One thing to do this week" is chosen before the report's model runs, not by it** — asked to pick while writing, a model picks the row it can write the best sentence about rather than the one of most consequence; it is the synthesis job's pick when that ran (next bullet) and otherwise the worst open severity, then the longest open, and the prompt says which one it is writing about.
  - **"Still open" is not "filed"**: a finding raised and settled inside the same week has left the store, so nothing can count what was filed; name the number for what it is.
  - **The day is the gate and the hour only ever opens the window** — `brief.due` shuts 45 minutes after the house gets up because a brief at lunchtime is not a morning brief, while a weekly report on Sunday afternoon is still that week's, so `weekly.due` never closes; a week missed entirely waits for the next of that day rather than going out on a Monday about eight days.
  - `worth_reporting` floors it on **material** rather than urgency, and an unreadable memory log is `available: false` rather than "nothing was learned".
  - Sending one by hand (`brain weekly send`, `POST /api/weekly/run`) stamps `last_sent` exactly as the loop does, because two reports about overlapping weeks make the numbers in both meaningless.
- **The one thing to do this week is chosen across the week, and the rank it replaced is journaled beside it** (`panel/synthesis.py` / `server._weekly_pick`). `weekly.one_thing` ranks by severity, which is a property of one row. The `synthesis` job (Opus, high) reads up to `MAX_CANDIDATES` open rows plus the week's own lines (`weekly.week_lines`) and answers `{ts, why}` under `--json-schema`. Four rules:
  - **the candidates are the list** (an id it was not shown is no answer);
  - **a critical floor** (any open critical row means only critical rows are offered);
  - **the severity pick is computed first and journaled beside the choice** (`weekly_pick`, `ok` when the synthesis chose, `fallback` with the reason when it did not — `ok=True` either way, because a fallback is not a failure), so "does this earn its run" is a number;
  - **every way of not running is the old pick** (fewer than two candidates spends nothing).
  - A scheduled report answers to `_resident_gate`, and its pick and its own run take SCHEDULED seats; a send pressed by hand needs only a credential, and both take PRESS seats. The frame's "Chosen because" line carries the sentence into the report.
- **The weekly report says where the measured energy went, and keeps what is not a lived-in room apart** (`weekly.energy_share`, `energy.device_sources` / `week`'s `devices`, `server._energy_where`).
  - The Energy dashboard's individual devices (`device_consumption`) ride the same statistics fetch as the grid meters, this week only, a device short of `MIN_DAYS` left out.
  - Each is placed by the last checks pass's room, and kept apart, never ranked, when it is in a space the household said nothing heats (`_said_unconditioned_areas`, the reader the heat model's rows use) or on a device whose thermometer the heat model set aside as a machine's (`thermal` store `unmeasured` kind `not_air`).
  - The line is "most went to the Lounge: 34% of the week's", of every device measured, only with two rooms to rank, and what was kept apart follows it by name with its share.
  - It is energy, not heat: no measurement brAIn holds says how much heat a room took (the heat model's `k` is a rate, not an amount), and a line naming heat would be invented.
- **A restart is not a new morning** (`panel/schedule_store.py`). The morning brief's and the weekly report's "once a day"/"once a week" stamps are two floats in `/data/schedule.json` and no schema, because **every way of failing reads as "never sent"**: a lost stamp costs one duplicate message, where a stamp wrongly read as *sent* would silence a real report, and a stamp that could not be **written** must never fail the message it was recording. Same shape as the usage tracker's `_resume_backoff`. The evening pass is deliberately not persisted — a second checks pass files nothing new, because the store dedupes.

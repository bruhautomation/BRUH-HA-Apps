# brAIn: insight cards, reports and the brief

Card generation and refresh, verdicts, live data, the card contract, prompts preview, ideas, milestones, the morning brief, the weekly report and synthesis, deep review.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **The moment a measurement first has an answer is the only moment it is news** (`panel/milestones.py`). `house.py` is the smallest possible answer to the silence — it says *when*, and never *what*. This is the other half: each of the seven fires **once**, when its own predicate first turns true, and produces an ordinary insight card out of that store's own numbers. Four rules, each about not becoming a category. **These are not the Insights tab's**: no `prompt_store` entry, no hidden shipped category, no schedule and no refresh interval, and they live on the Knowledge tab — a category is a standing question somebody asked to have answered, this is a fact that became knowable on a Tuesday, and mixing them puts seven cards nobody chose onto a dashboard whose whole design is that you chose what is on it. **Once, and the settled key is what makes it once**: the card can be deleted, regenerated by hand or fail outright, and none of those may let the next checks pass file it again, so what blocks a re-fire is an entry in `_settled.json` written the moment the card is saved — the same arrangement `findings_store` keeps a ledger beside a list that is meant to empty. **"Materially changed" is per milestone, in that measurement's own units** (a wake time that moved eleven minutes is the same house; one that moved ninety is a different household), because a single threshold over seven different units is a number nobody could argue with. And **the extra bar is a CARD's, not the measurement's**: every predicate reads `progress()` rather than re-deriving readiness, and what lives here is only "one baseline is a measurement and twenty-five is a picture of a house".
- **A card refreshes when its inputs moved, not when a timer expired** (`server._card_inputs` / `_inputs_change` / `REFRESH_HOLDS`). The age floor alone meant a card regenerated over identical inputs produced the identical card at full price, every day, which is how a dashboard teaches people it is a timer. The fingerprint is over the five things a run actually reads — the findings block for the domains that card covers, `memory.md`'s mtime, the measurement stores, its feedback, its focus — and `refresh_mode` (`changed` | `always` | `never`) is the setting, with `changed` the default and `always` being what every release before it did. Three details are load-bearing. The change is a **callable** evaluated only once the age floor has passed, because on most ticks no card has aged out and computing a whole-house fingerprint for one that has not is a read nobody asked for; the shared halves are fetched **once per tick** rather than once per card, or nine categories ask the same question nine times. **A fingerprint that cannot be read falls through to the old behaviour** — "I could not tell" must not become a card that never refreshes again. And every card records **`made_because`** in the words a person would use ("a finding it reads changed", "on its refresh interval", "first run since inputs were tracked") while a card that skipped records the **hold** instead, because a dashboard that has not moved in three days is otherwise indistinguishable from a scheduler that has stopped. `open_findings` rides beside the hash and is deliberately **not** part of it: it is derived from the same text the `findings` part already covers, and counting it twice would let a re-worded finding read as a new one.
- **A prompt nobody can see is a prompt nobody can argue with** (`server._prompt_preview` / `h_prompt_preview`). The Edit dialog's box was labelled *"Analysis focus (the prompt for this category)"* and it is one paragraph of a dozen blocks — the contract, the standing feedback, what brAIn has measured, the work list, the previous run, the budget, the data — every one of them assembled at run time and shown nowhere, so a card that kept coming back wrong could only be argued with by guessing. That is issue #300. Two decisions. **It is rebuilt, never replayed**: storing the prompt that produced the card on screen was the obvious design and is the wrong one, because half those blocks are live and a stored copy starts drifting the moment it is written — what somebody iterating needs is *what will be sent if I press Regenerate now*, which is a thing this can answer exactly by calling the same builders the run calls. The data section is reported by SIZE rather than pasted, because a hundred kilobytes of entity rows is not something anybody reads and its size is the fact people actually want. **The editable part stays the focus**: offering the assembled text as a textarea would freeze those live blocks at whatever they said the day it was saved, so the card would stop seeing new findings and go on citing a measurement from March with nothing on screen to say so — the honest split is to show the whole thing and let you edit the part that is yours, which is the focus and the feedback, both of which already reach every future run. It calls `resolve_category`, never `get_category`: the second answers with the SHIPPED definition and ignores every override, so a preview built on it would show a rewritten focus back as the shipped one — the same failure this route exists to end, one layer further in.
- **A card is written once, so a card about NOW is frozen at then** (`live` in `_CARD_CONTRACT`, `_clean_entity_ids`, `h_insight_live`, `LIVE_SNIPPET`/`watchLive`). Right for "last week's energy" and wrong for the ones people pin to a dashboard: a door that is open, a machine running, a room being held at a temperature all read as current and are not. A card may declare the entities whose state its visualization wants kept up to date; the panel refreshes those and hands them in through `window.brainLive(cb)`. **The list is the card's OWN and is fixed when the card is written** — that is the whole security argument, because the frame is a sandboxed `srcdoc` running model-authored script and a route that took entity ids from the caller would let that script read any entity in the house through the panel's credential. The channel is one-way for the same reason. **The page must render correctly with no live data at all**, which the contract states and which is not a nicety: the callback may never fire (an older panel, a lost connection, an entity since removed), so the snapshot values are drawn first and the callback updates them. One timer for every live frame rather than one each, or six live cards are six polls drifting against each other; a frame rendered nowhere — a closed modal, a tab you are not on — is **skipped and not dropped**, because `renderIfChanged` deliberately does not rebuild an iframe it does not have to, so a dropped entry would never be re-registered and the card would come back permanently frozen.
- **A live card has TWO ages, and the foot reported one of them** (`liveAgeText` / `paintLive` / `makeFrame(insight, live)`). `live` lets a card keep up to a dozen entities current while it is on screen, which is right — and it means the numbers in the chart are seconds old while every sentence Claude wrote *about* them is from whenever the analysis last ran. The foot said `Updated 3 d ago`, once, for both, which is wrong in both directions at the same time: it invites somebody to distrust a reading that is current, and to trust a conclusion written three days ago against data that has since moved. So a card that declares `live` says **`Analysed`** — a claim about the prose, and nothing else — and the readings get their own line naming how many are live and when they last **arrived**, which is the one age nothing could report. **Three states and they are three different claims**: `waiting` before the first fetch lands, the age after it, and `not updating` when a fetch fails — the third is the one that must not read as the second, because a frozen number under a live label is the reading nothing can correct. A failure **keeps the arrival stamp** so the line ages from the last real reading rather than resetting to `waiting`, which would read as a card that has never been live; the words carry the state and the warning colour only reinforces it (`status by colour alone` is what the design system forbids, on a line read at 11.5px in a muted row). It is painted from the live tick rather than by re-rendering — `renderIfChanged` deliberately does not rebuild an iframe it does not have to, and a re-render every 15s to move one word would rebuild every visualization on the page — and there is **no second timer**, since the poll is already the only clock this needs. **And a card pinned to a PAST run is offered no live data at all**: paging back is how you see what the card said in March, so pushing today's door state into March's chart makes it a hybrid of that run's prose and this afternoon's numbers with nothing on screen able to say so — the same two-ages confusion in its worst form, and it applied to the expanded view too. `tests/manual/measure-cardlive.mjs` drives the real `makeCard` rather than rebuilding it (measure-activity's rule) and was verified against the old behaviour first: nineteen failures, including the pinned-run overlay nothing had noticed. Its own first run found a flaw in itself — a thrown timeout abandoned every finding already gathered and reported only the missing helper — so every wait in it notes rather than throws. **House › Reports folded the foot to one claim** (`cardage`, `liveAgeText`): it says **Updated N ago** (or **From <run>** on a pinned run, which is still offered no live data), and the live line renders only on a fault — `· N live readings not updating since …`, the arrival stamp kept — because waiting and fresh are the ordinary states and a line saying so on every card is a line nobody reads; the failure is still the one state that must not read as the others. `measure-cardlive` asserts the empty line in both ordinary states.
- **A card answers for its own rows on its next run** (`findings_store.own_reports` / `clear_unreported`, `prompt_block(own=)`). A card's rows were listed under "do NOT report these again", so its next run could not say the data still showed one and nothing cleared it: rows stayed open long after the data stopped supporting them. The card's own live rows (`open`/`triaging`/`held`, up to `PROMPT_OWN`) are now shown apart and the run is told to report one again only if what it read still shows it; after a run that answered, a row it was shown and did not report again (by text, or by the entity it named) is removed — `clear_resolved`'s ending, no memory line and no ledger entry. Never on a failed run, never a row it was not shown, never a check's or one of `OWN_EXCLUDED` (the Resident, safety, corrections), and never a row a person touched: snoozed, put back, carrying a plan or a conversation's advice, in a fix or fixed. **And a card is handed the OTHER live rows with their name, figures and window** (`prompt_block(figures=True)`, the two card prompt builders only): a card and a finding about one freezer told one story with two numbers and two names, so each row carries its device's name off `_NAMES` and its detail, and the block tells the run to quote that row's figures and window, use its name and mention it in one clause rather than retell it. The refresh fingerprint reads the block without `figures`, because a check rewrites its detail every pass and a moved number on somebody else's row is not news to a card. `tests/test_card_contract_words.py`.
- **A card's opening verdict is read against its own evidence** (`panel/card_verdict.py`, `_generate`). A "fine" over a card that says it read nothing new is rewritten to "Nothing new since <the last card's date>" with no verdict; a "fine"/"nothing needs action" over the card's own figures rising by more than half (`A vs B`, `B → A`, `from B to A`, `+N%`, "doubled") loses the verdict and the figures lead; a SCHEDULED card whose whole content is that nothing happened (no findings, no status, zero counts or its own words) keeps the previous card, stamps it `checked_at` with a fresh fingerprint and records a `REFRESH_HOLDS` sentence — the scheduler counts age from `_due_stamp` (the later of `generated_at` and `checked_at`), or the next tick would queue the same run again. A press is never held, a first card is never held, and a rewrite only removes a clause or adds the date the card already carried. `tests/test_card_verdict_post_check.py`.
- **A card carries ONE verdict, as a chip, and its prose never says it again** (`CARD_SCHEMA.verdict`, `card_verdict.VERDICTS` / `lead_verdict` / `legacy`, `verdictChip`, `_whole_card_page`). A house's cards wrote their judgement six ways into the summary ("Verdict: normal.", "Needs action.", "Nothing to fix.", "This needs one change.", "Neither unit is broken."), so the one thing a dashboard is scanned for was a sentence to read, worded differently on every card. The reply carries `verdict` (`all fine` / `worth a look` / `needs action`; offered and not required, because an existing reply shape without it must still validate and is read off its own first sentence), the contract says the summary never repeats it, `review` takes a first sentence that is a verdict and nothing else off the front (when another sentence follows) and reads it as the chip, and the paths that took a "fine" off a card (a rise, an open finding, a disagreeing figure) set it to worth a look; "nothing new since" gives no chip. A card stored before the field existed is read the same way at the listing and on the dashboard page (`legacy`), the file untouched. `tests/test_card_one_verdict.py`, `measure-reports`.
- **Two cards about one device or system tell one story** (`server._other_cards_block(covers=)` / `_shares_subject` / `_superseded`, `card_verdict.review(others=, names_in=)`, `_NAMES`' `device`). A water card opened on the septic pump's figure beside the pump card's own different one, and a new heat card sat beside an older air-handler card still worded as live about the same heat pump. A run is handed the cards about the same device or system (an entity it named, a device one belongs to, its domains and classes) first and in full — figures and when they were read — and told to quote them or say why its own differ; a first summary sentence naming only another card's subject, and nothing else this card names, is dropped when more follows; and an older card whose every entity a newer card names, or sits on a device the newer names, is listed `superseded_by` and drawn as one line under the newer card (`foldedUnder`). `tests/test_card_siblings.py`.
- **A card and an open finding about the same thing say the same thing** (`card_verdict.disagreeing_row` / `claims_fixed`, `CARD_SCHEMA.fixed`, `server._spawn_fixed_rechecks`). A card counted a plug's dropouts as 7 since Saturday beside a finding counting 14 in 7 days, and another said an interlock automation now handled a case the open finding still told the owner to fix. The prompt block says a count over a different window names its window in words; a sentence about a device an open row names whose count (times, runs, gal, kWh…) disagrees with the row's is taken off and the row leads; and a card that reads a row as already fixed — in `fixed` or in words — has that row's own check asked again through `_rerun_check`, so the rule that filed it clears or rewords it. A model's row has no rule and is left alone. `tests/test_card_finding_figures.py`.
- **A card about nothing happening does not take a card's place** (`card_verdict.quiet_now` / `no_change` / `folds_quiet` / `QUIET_WHY`, `quiet` on the stored card, `quietLine`). Reports was mostly "no cooling since 17 Oct" in heating season and "neither unit has run since". A SCHEDULED card whose `verdict` is all fine, with nothing filed, offered or marked, and nothing changed (its own words, or every figure as last time) keeps the last card under `QUIET_WHY` and marks it `quiet`; a pressed card is stored but marked too; and Reports folds every quiet card, unless a finding on Needs you is about it, into one "All quiet: <names>" line whose names open each. `tests/test_card_quiet_fold.py`, `measure-reports`.
- **A card's suggested automation goes through the ask bar's own drop** (`server._offer_card_opportunities` → `intents.request`).
  - `CARD_SCHEMA.opportunities` is a sentence plus the entities it names.
  - Each one is drafted, replayed, graded and offered exactly as a typed sentence is. There is one path from a sentence to a rule.
  - It is an unattended producer, so it answers to `_resident_gate`, caps at `MAX_CARD_OPPORTUNITIES` per card and `CARD_OPPORTUNITIES_PER_DAY` per day, and never re-offers what the same card queued last run.
  - A question is not a rule, and a sentence that is not yet routable is put in the standing shape ("From now on, …").
  - Each row stays on the card with `queued` and `why`, because a suggestion that went nowhere and one that is on Proposals look identical otherwise.
  - The menu's "Make this an automation" only fills the ask bar. Sending is the person's press.
- **A refresh gate fingerprints what the run reads, never when a store was written** (`server._store_stamp` / `_memory_stamp` / `_card_inputs`). The `changed` mode was a 24-hour timer with extra steps: the stores' parts hashed build stamps and mtimes that move every night whether or not a number did, memory hashed the file's mtime (moved by every consolidation), and the findings part included the card's **own** rows, so a card filing a finding scheduled its own regeneration. Each store is now its `progress()` state plus the ready sentence, memory is a digest of what the card would be told (the retrieval block when the store has rows, the document's fact lines otherwise), and the findings block leaves the card's own source out. `CATEGORY_STORES` is held equal to the shipped category ids by a test, because a category missing from it has no store part at all and two that no longer existed were still in it.
- **A card that failed is a card that waits** (`CARD_FAILURES` / `_card_backoff_until`, 15 min doubling to 12 h). `_refresh_due` and `_next_due` read the same backoff, so the card and the scheduler agree about when it is next due. The search→snapshot floor is skipped when the search was refused by the account or the service (`_no_fallback`: auth, rate limit, 529). That floor exists for tool and turn failures, and a snapshot asked of a refusing account is the same refusal at full price.
- **A card fetches what it needs; it is not handed the house** (`gather_mode`, default `search`). `collect_orientation` sends a *map* — domain counts, area counts, a few anchors — and `run_analyst` searches for the rows the question actually needs (`get_all_states` takes a `domain` and a `name_filter`, so nothing has to enumerate ids). Measured on a real run: 1,449 prompt chars where the snapshot sent ~100,000. **The middle option was measured and rejected**: handing Claude an index of every entity to pick from costs about what the slimmed rows cost, because every id has to be in it — searching by name skips the index entirely. `snapshot` is the old single-turn path, kept as a setting **and as the floor**: a failed or turn-exhausted search falls back to it so a card always appears, and the fallback is logged because a run that keeps taking it is a run worth reading the log about. Search is also the only path that can afford **history on a typed question** — the one-shot path never could, which is why asked questions were always answered from a single instant. `_framing` is shared by both prompt builders, and `_CARD_CONTRACT` by both system prompts: two preambles, one contract, because a second copy of 10 KB of output rules is a second copy that drifts.
- **The ask bar has two verbs.** A question becomes a card; a line starting "learn/study/research/figure out" is routed server-side (`LEARN_RE`) to a study request the CLI-side watcher picks up. There is no separate "new insight" dialog — asking makes the card, and "＋ Make recurring" turns it into a scheduled one. **Reports carries no ask box of its own** since the House redesign cut the second one: `/api/ask` and `LEARN_RE` are unchanged, a card's **Ask** dialog refines that card or carries the question into the chat (`seedAsk` fills `#chatInput`), and "Make it recurring" is a link in that dialog.
- **An idea costs nothing until it is taken, which is why it is a separate PAGE** (`panel/ideas.py` / `server._run_ideas` / the Home group's Ideas tab). Onboarding studies a home once and proposes a card set, and that was the only moment brAIn ever offered an idea of its own — the ask bar and "＋ Make recurring" both start with somebody already knowing what to ask, so a house that has since grown a solar array and four months of history goes on generating whatever was chosen in its first twenty minutes. The split from Insights is the whole safety argument and not a layout choice: eight ideas nobody takes cost one run, where eight cards nobody reads cost a run each, every refresh interval, for ever. Five rules. **An answered idea is never offered again** — the fingerprint of everything accepted or dismissed is kept and consulted on every pass, an index never drained, `findings_store`'s ledger beside a list that is meant to empty; accepting is remembered for a second reason of its own, since the category now exists and proposing it again is brAIn offering to build what it already built. **A card this home already has is not an idea**, and the blocked set is seeded from the LIVE categories rather than from what this module has watched, because a card made through the ask bar, through onboarding or by hand is still a card and none of them told this module anything. **The cap refuses rather than making room** (`todo_store`'s rule). **A pass that proposed nothing is an answer**, so `last_error` is written only where a run actually failed and the empty page says which of three silences it is — nobody has asked, the last look failed, or brAIn looked and had nothing to add — which is `house.py`'s rule about a measurement that has not started, one tab over. And **the weekly top-up only ever ADDS**: it never clears the page, re-orders it or removes an idea nobody has answered. The run is **started and never awaited** (`h_baselines_run`'s clock) with `IDEAS_STATE["starting"]` flipped synchronously (`start_auth_check`'s rule), and the top-up sits past every gate the scheduler already keeps while the press skips the budget — "automatic insights pause; asking by hand always runs" is one promise with two halves. `system_prompt` substitutes its cap with a plain `.replace` and never `%`: this is a page of prose about a house, prose about a house says "60% of your winter usage", and a template that breaks on its own content is one the next person to edit it breaks again — which its own test caught. `tests/manual/measure-ideas.mjs` drives the real renderer and fails on a card missing either of the two blocks that make an idea judgeable, on the three silences collapsing into one sentence, or on a meta row laid out with no gap — the last added after the first cut used `findline`, a class the stylesheet has no rule for, which rendered "⚡ ideasuggested 1 h ago" and which every other check in the file passed straight over. **It is a row now, not a page** (`#ideasRow` under House › Reports, `#viewIdeas` gone, `switchView("ideas")` lands on Reports): the separation that matters is the run, not the URL, and the row is its name and **Run** with **Save · Ignore** on each idea. Two of the three silences were cut as prose nobody needed — an empty row is its name and Run — and the one that is a fault, a failed look, still says so; `measure-ideas` asserts both halves.
- **Deleted cards do not come back.** There is no restore list: brAIn proposes the cards a given home should have, so the answer to "I want that card again" is to ask for it and let brAIn build it for the house it now knows. Shipped categories are still `hidden` under the hood because their definitions live in the code, but that is a mechanism, not an offer.
- **The ask bar's third verb ate its own questions, and the fix is one word further along.** *"when did the boiler last run?"* opens with the same word as *"when the guests leave, turn the porch light off"*, so `INTENT_RE` matched it and the question went down the one-off path — spending a Claude run to produce a **refusal card** about an intent it could not arm, for something a card would have answered. `INTENT_QUESTION_RE` is the negation the route carries: an **auxiliary verb straight after the opener** (*when did*, *once was*) is somebody asking, and an instruction never has one there — *"when the guests leave"* and *"tell me when the dishwasher is done"* both put a noun phrase next. It is a second pattern rather than a hole in the first because the two rules are about different things, and it is deliberately not trailing-`?` detection: nobody types one on a phone. **And "already gone" is a removal that happened**: `automation_writer.remove` answers `missing` when the entry is not in the file, and since Remove is an intent's *only* ending, a 409 there left a card nothing could ever clear — nothing to splice, nothing to reload, nothing to put back, so the row leaves the list and the undo token skips the revert it has no snapshot for.
- **A weekly report is not a brief with a longer timer** (`panel/weekly.py`). The brief asks *is there anything* and its whole design is a refusal — it is silent most mornings on purpose. A report asks *what happened*, and its failure mode is the opposite one: a report that lists everything is the dozen unread cards with the covers off. So every section is gathered deterministically and **capped** before a model runs, and the model's job is to say four things rather than to choose which four. **"One thing to do this week" is chosen before the report's model runs, not by it** — asked to pick while writing, a model picks the row it can write the best sentence about, which is the one carrying the most detail rather than the most consequence; it is the synthesis job's pick when that ran (next bullet) and otherwise the worst open severity, then the longest open, and the prompt says which one it is writing about. **"Still open" is not "filed"**: a finding raised and settled inside the same week has left the store, so nothing can count what was filed without counting it twice or not at all, and the honest fix is to name the number for what it is rather than dress it up as the one nobody can compute. **The day is the gate and the hour only ever opens the window** — `brief.due` shuts 45 minutes after the house gets up because a brief at lunchtime is not a morning brief, and a weekly report on Sunday afternoon is still that week's, so `weekly.due` never closes and skipping a week to protect an hour is the trade it deliberately does not make; a week missed entirely waits for the next of that day rather than going out on a Monday about eight days. `worth_reporting` floors it on **material** rather than urgency, and an unreadable memory log is `available: false` rather than "nothing was learned" — the same "I could not look" the checks carry. Sending one by hand (`brain weekly send`, `POST /api/weekly/run`) stamps `last_sent` exactly as the loop does, because two reports about overlapping weeks make the numbers in both meaningless.
- **The one thing to do this week is chosen across the week, and the rank it replaced is journaled beside it** (`panel/synthesis.py` / `server._weekly_pick`). `weekly.one_thing` ranks by severity, which is a property of one row: three warnings about one hub never outrank anything, and a `serious` row that is a fact of the house tops every week. The `synthesis` job (Opus, high) reads up to `MAX_CANDIDATES` open rows plus the week's own lines (`weekly.week_lines`) and answers `{ts, why}` under `--json-schema`. Four rules: **the candidates are the list** (an id it was not shown is no answer); **a critical floor** (any open critical row means only critical rows are offered); **the severity pick is computed first and journaled beside the choice** (`weekly_pick`, `ok` when the synthesis chose, `fallback` with the reason when it did not — `ok=True` either way, because a fallback is not a failure), so "does this earn its run" is a number; **every way of not running is the old pick** (fewer than two candidates spends nothing). A scheduled report answers to `_resident_gate`, and its pick and its own run take SCHEDULED seats; a send pressed by hand needs only a credential, and both take PRESS seats. The frame's "Chosen because" line carries the sentence into the report.
- **A deep review is a press, priced on the button, and files nothing** (`panel/deep_review.py` / `h_deep_review_run`, job `deep_review`, `PRESS_ONLY`). Fable over the findings block, the house measurements, the memory retrieval and the last weekly report, with reading tools only; `engine.planned(job, pressed=True)` is the one route to a press-only job, and the run takes a PRESS seat. The cost shown is the median of past reviews' tokens, or `FIRST_GUESS_TOKENS` labelled as a guess. It observes (`KINDS`, `MAX_OBSERVATIONS`) and never writes a finding, a fact or a proposal — a review that filed rows would be an unscheduled producer with a Fable price. Kept in its own capped store (`MAX_REVIEWS`); an unreadable store is answered as such and a save over one keeps a `.unreadable` copy. Started, never awaited (`h_baselines_run`'s clock); the running flag is flipped synchronously. It is a row under House › Reports (`#kReview`, polled while Reports is in front): **Run** with "~N% of a session" beside it and the token figure in the tooltip, each review dated ("4 Oct") and carrying no model name.
- **A restart is not a new morning** (`panel/schedule_store.py`). The morning brief and the weekly report are each guarded by a "once a day"/"once a week" stamp, and both kept it in memory only — so restarting the add-on set it to zero and the next window sent a second one, about the same morning or the same week. Restarting is the first thing anybody does after changing an option, which makes that the ordinary case rather than the unlucky one; same shape as the usage tracker's `_resume_backoff`. Two floats in `/data/schedule.json` and no schema, because **every way of failing reads as "never sent"**: a lost stamp costs one duplicate message, where a stamp wrongly read as *sent* would silence a real report, and a stamp that could not be **written** must never fail the message it was recording. The evening pass is deliberately not persisted — a second checks pass files nothing new, because the store dedupes.
- **"Custom" is not a producer's name** (`findings_store.SOURCE_TITLE` / `_titled`, `server._asked_title` / `_card_source_title`). An asked card filed its findings under its synthetic category's title, so the Findings tab and the scorecard said *Custom* with nothing tying the row to its card. It files under the card's title (else its eyebrow), and a row or ledger entry already written as "Custom" is named off the stored card by a resolver the panel hands the store (a deleted card reads "Your question").

**A card leads with its answer, and the two things people want from one are named buttons** (`makeCard` / `card_tags.eyebrow` / `h_insight_refine` / `h_card_to_dashboard` / `snapInFrame`). Reported as *"cards are strange… they all say custom… they list the raw question which is of no value… there isn't an easy way to edit the card… no way to export it… charts don't use space correctly"*, and each half of that had one cause. **The eyebrow is derived once, on the server** (`eyebrow` on `/api/insights` for an asked card: a hand-given name, else its topic tags spelled as words, else "Your question" — never "Custom", which is where the card came from and the one thing nobody needs telling); a recurring card is headed by its category, read live so a rename shows at once. The question is shown only while the card is being made or has failed, because then it is all there is; afterwards it is one press away in Refine, and the contract tells an asked run the question is never shown, so the title names the finding and the summary opens with the answer — which the panel sets in ink (`splitLead`, the server's `_lead_split` for the dashboard page). **Refine is a regenerate that was told why** (`POST /api/insight/{id}/refine`): the note rides the job as `refine`, `_framing` states it as the run's task and shows the card as it stands under `THE CARD AS IT STANDS` rather than "do not repeat it", and `remember` (the default) files it in `feedback_store` — one store for both kinds of card, which is what stops the next scheduled run quietly undoing it, and deduped out of the feedback block so it is not said twice. `_enqueue` resets `refine` and `because` on every queue, because `_set_job` merges and a job dict outlives its run: without that the next plain Regenerate was told last week's change and wrote it on the card as its reason. Regenerating an asked card sends `{id}` and re-runs it IN PLACE — it used to re-ask the question and leave a second copy beside the first — and asked cards keep history now, since the version a refine replaced is the one somebody may want back (the custom trim takes the history, feedback and mirror with the card). **Share has two halves and neither sees the chart's DOM.** The picture: the chart is model-authored script in an opaque-origin frame, so a fresh frame at one fixed width (`SNAP_FRAME_WIDTH`, so a phone and a desktop share one picture) is given `snapInFrame` as source text, clones itself, inlines the computed styles only for elements with animations (a draw-in's dash offset is invisible once animations are off) and posts back a PNG; `composeCardImage` lays the face out in the panel's own colours and draws it through a foreignObject. **A card is as tall as what it holds** (`.grid` and `#findList` are `align-items: start`; the frame follows `bruh-size`): stretched to their row, a text-and-tiles report beside a chart carried 250–450px of blank above its foot and a question's Yes/No sat ~100px under the question; a page that drew nothing kept the frame's 320px (the size snippet never reported 0) and a one-line page was held at 120px. A card's frame now reports 0 and collapses (`.viz.blank`, kept laid out so a late chart can still report) and is otherwise exactly its page's height; the expanded view keeps its 120px floor, and the `/local` page's fit-its-frame rule is untouched. **A report and a finding about the same thing link to each other** (`_card_entities` → `entities` on `/api/insights`, `casesForInsight` / `insightForCase` in `app.js`): they told one story twice with nothing between them, so a card shows "Also on Needs you: <finding>" and the finding "From <card>", joined by a finding's entity or evidence that the card names (its `live` list and the ids in its title, summary, tiles and learned facts — never its `html`, and only ids the house has once a checks pass named it) or a finding the card itself filed (`source` is the card's id); `renderIfChanged` keys on the links because the cases arrive on their own fetch. `measure-today` drives both. A browser that refuses the image clipboard (the ingress frame often does) gets the picture on screen to long-press, never a silent failure, and a chart that could not be drawn is said, not dropped. The dashboard: `/api/dashboards` lists every dashboard with its views and, for one brAIn cannot write, the sentence why (YAML mode, auto-generated, a strategy) — `_unwritable_reason` is one function asked by the listing and by the save, so the two cannot disagree — and the card is a Webpage card pointing at the `/local` mirror, which now writes `<id>-<token>.card.html` (the whole face, the chart in a sandboxed srcdoc frame of its own, because `/local` is Home Assistant's origin) beside the chart-only file every older dashboard card already points at. That page says **Updated N ago** beside its eyebrow, re-worked every minute against the viewer's clock (the old 11px "analysed …" foot is gone; past two days the warning line above the card says how old it is), and it **fits its frame**: the page is exactly the Webpage card's height with nothing to scroll, the summary clamps at three lines and the chart's frame takes what is left (`flex: 1`), where a frame sized to the chart's own content inside a fixed-ratio card was the inner scrollbar. A sections view gets the card as a section of its own rather than dropped into somebody's grid. **The chart sits on the card**: no border, no background, `body` transparent in `CARD_STYLES` and `--bg` matching the panel's surface in both schemes, and the contract forbids a panel inside the frame, asks for fluid SVG and a pair that stacks at 260px, and puts the legend above the plot. Tiles are a grid whose columns come from the count (`data-n`), two on a card under 520px with an odd one out taking the row. The head is a container query on the card, not the window: Refine and Share lose their words under 600px and the title takes a row of its own under the buttons, and `measure-cardhead` now fails on a title clamped at all, which is what the first cut of this did on a 1024px two-column grid. **The title says what was counted, and brAIn's own limits are not news** (`_CARD_CONTRACT`): "evenings eased from 14 openings to 5" never said openings of what, a kWh in a title named no appliance while the summary led with another figure, and a card told the household the recorder kept only seven nights. The contract now has the title name the device, door or room measured, a title's number appear in the summary with the same meaning, and the recorder, retention, missing history and a comparison that could not be made go unmentioned unless they change what to do — make the one the data allows; the old "say so in the summary" on thin data is gone with it. The contract is held under `test_model_plan`'s 9100-character ceiling, so the room came from cut examples (the OfficeNet phone, a hypothesis's afterlife), never from a rule.

**On an insight card the title gets the row, and two controls sit beside it.** The head used to be one flex line — icon, category, title and six `flex: none` icon buttons — so on a phone the buttons took ~250px of a 390px card, the category wrapped to three lines and the title truncated to `Upstair…`. The eyebrow is the part that gives way (one line, ellipsis); the title wraps to two lines and is never truncated. `⤢` stays on the card because it is the only action on *what is on screen*; Regenerate/Edit/Feedback/Add to dashboard/Delete live in `⋯` (`cardMenuButton`) with a name and a line of what-it-does each. Re-run `node tests/manual/measure-cardhead.mjs` after touching the head — it fails on a truncated title, a wrapped category, an overflowing head, or a target under 40px. **There is no "refresh everything" control**: it was an unlabelled circular arrow in the top bar that queued a Claude run for every card, beside the pill reporting the usage it spends. **Since House › Reports the head is Ask · ⋯ and nothing else** (`cardask`, `cardMenuButton`): ⋯ is exactly Share, Past versions, Run, Delete, ⤢ is gone because a press on the card body opens it, and Edit, Make recurring and the automation suggestions are links in the Ask dialog (`fillRefineMore`). Tag chips and the tag editor left the card; Reports gets a search box past `REPORT_SEARCH_AFTER` (8).

**A run that costs something has to say so, on the thing it cost it for.** Generating a card is the most expensive thing the add-on does — a bundle out, a rendered visualization back, typically 25–45k tokens — and the numbers came back in every result envelope, were used to add to a total, and were rendered nowhere. The only visible effect was the usage pill moving, attributable to nothing, which is how "insights use a lot" becomes a suspicion rather than a reading. `usage_store.split_from_meta` derives it **once, server-side**, `total` being `tokens_from_meta` and nothing else: the card, the log line and the budget are one number, and a second copy of "which fields count, and that a cache read does not" written in JavaScript would be a second answer waiting to drift from the one the budget uses. Four surfaces, all the same figure — the job carries `prompt_chars` so the spinner can say `500 entities · ~33k tokens sent` *before* the answer exists (the only place a `CHARS_PER_TOKEN` estimate is allowed, and it is prefixed `~`); the card's foot carries `meta.cost`; the usage popover itemizes `budget_state`'s `breakdown`, which the run ledger has recorded an id per run for since the budget existed and nothing ever read back. The breakdown is **capped with the tail folded into one row, never truncated**, or the itemization sums to less than the percentage it is explaining — and it is labelled as brAIn's own runs, because when `source` is `account` the pill covers the terminal, the chat and voice too and a list read as exhaustive is how you conclude a terminal session is free. **An asked question is the expensive kind**: `collect_bundle` gives a category its slice and a question the *whole* home (`filter_states(states, registries, [], [])`, up to `MAX_ENTITIES`) plus device context, because the question could be about anything — so a handful of questions costs what a dozen scheduled refreshes do, and that belongs in the docs rather than in a support thread. `positionChipPop` bounds the popover's height to what is below the chip and lets it scroll: it held two rows and a sentence when it was written, and a list whose last rows are under the bottom of the screen is the tooltip bug sideways.

**A row in the bundle is 500 rows in the prompt, so its encoding is a cost.** `slim_state` spends the fewest characters that still carry each signal, and the three that were overpaying are measured, not guessed (72,943 → 52,086 chars on a 500-entity home). `lc` is **minutes since**, not a 19-character ISO stamp: staleness is the only thing `last_changed` is read for, and the absolute form also made the model diff it against `meta.now` to get there — minutes rather than hours because "6 minutes ago" and "an hour ago" are different facts and cost the same. `n` is dropped when `_slug(n)` equals the object id, which is what HA names an entity by default; a *renamed* entity keeps it, which is the case the field exists for. An `unavailable`/`unknown` row keeps only `e`/`s`/`a` — its unit and device class describe a reading that is not there. All three are in the prompt's field contract, because a field that is conditionally absent and undocumented reads as missing data. **Retrieval was measured and does not pay here**: a two-step "index, then fetch what Claude picked" costs an index (~29k chars — the ids dominate and every one has to be listed) *plus* the picked rows, which lands above simply sending all 500 slimmed rows; and an agentic loop re-sends its conversation every turn and can die on `--max-turns`, which the docs already call the most expensive setting in the add-on. What retrieval would buy is *history on an asked question*, which the single-shot path cannot afford — a capability argument, not a cost one.

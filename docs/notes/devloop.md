# brAIn: the development loop (house half)

The devloop streams, issue filing and redaction, verdicts coming home, follow-ups, screenshots and the harness, sibling add-ons' reports.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **Self-improvement and development are two switches, and only one sends anything** (⚙ › Features, `panel/features.py`). The **Learning loop** is brAIn changing itself on this house — Morph's learning pass, its lessons, the changes it proposes to its own dashboard code — and nothing leaves it; it is Morph's `learning` setting, read off the switch. The **Development loop** is this file: reports to the private repository so the code is fixed upstream. Its switch is the devloop's own `enabled` (`features.save` writes it through `devloop.save_settings`), shown in Features and nowhere else, and Morph's `report_code_issues` reads it too, so a Morph fault and a brAIn fault leave the house by the same switch. The autopilot switch's label is **Report everything without asking**: it was "Development mode: brAIn works on itself", which read as self-improvement and is the opposite. Morph is no sibling any more (`siblings.CATALOG`): its faults come through its own outbox, `streams.morph`, and its screens are drawn in the harness while its switch is on (`screen_targets.morph_on`).
- **Development mode is the devloop's `enabled` + `autopilot`, and every session is told which** (`server.development_mode` / `DEVELOPMENT_MODE_ON`/`_OFF`, `ha-context-gen.sh`'s "Development mode" section). Opt-in, off by default, and an unreadable settings file reads as off. When on, a session files bugs it notices with `report_bug` unasked; when off, only when asked. A devloop PUT rewrites the terminal's prompt file.
- **The harness draws Morph's own custom cards with their own code** (`devloop/harness.py`'s `customCard`, `/morph_cards/{name}`). A card under `/config/morph/cards` is a custom element the page defines; `createCardElement` waits for the definition (bounded) and mounts it with the read-only `hass`, and a card whose `setConfig` or `hass` throws, or whose file fails to load, is a labelled box saying so — never a blank, and never the whole page. A Lovelace card still draws as its placeholder, and the write guard and the WS stub hold for the card's own requests (`test_morphs_own_custom_cards_are_drawn_by_their_code`).
- **A picture waits for the questions a chart draws from, and a phone's press is a finger** (`harness.py`'s `__harnessIdle`, `screens._answers` / `_focus_press`, `tests/test_devloop_history_and_press.py`). The harness counts every question a card puts to Home Assistant while it is out; the capture waits (`ANSWERS_MAX_S`, ONE budget per picture, so a question that never comes back costs the bound once) after the page is ready, after it unfolded a room (the cards in it only then ask for their history, and a picture taken at once had charts with no lines), and after a press. History, statistics and logbook reads were always on `READ_COMMANDS`; the bug was the moment of the picture. On a touch view the press is `Input.dispatchTouchEvent`, not a mouse: a card built on Home Assistant's action handler listens to touch alone once the device has touch, so a mouse tap or hold never reached it and `press: open|tap` left it folded.
- **The harness's question to Home Assistant is bounded by the server, not only by the page** (`server.HARNESS_WS_TIMEOUT_S`, under `screens.ANSWERS_MAX_S`; `tests/test_harness_ws_bounded.py`). The page stopped waiting at its own budget, but `h_harness_ws` still awaited Core with no bound, and aiohttp's runner cleanup at the end of a capture waits for every open handler, so a question Core never answered held the whole capture. In the suite that made `test_a_question_that_never_comes_back_does_not_hold_the_picture` take ~56 s against the 60 s per-test timeout. Under CI load it went over, and `timeout_method = thread` ends the whole xdist worker ("node down: Not properly terminated"), after which xdist hung the job until it was cancelled — on `main` and every PR. A handler the harness calls answers within its own bound (a 504) whatever Core does.
- **The development loop is a dormant developer feature, and every stream is its own switch** (`panel/devloop/`, `brain/DEVLOOP.md`, `docs/design/devloop.md`). Off for everyone, read at call time (`devloop.enabled()` / `stream_on`), deliberately a panel switch (⚙ › Features; the repository, token and streams are in ⚙ › Developer) and NOT an add-on option, because an option is documented to every user. It files `reports.faults` rows as issues in a **private** repo the user owns (`github.check_repo` refuses a public one), one issue per fingerprint for its whole life: the fingerprint is the RAW `where|what` with digits folded, so a count moving or a rename never splits one fault into two issues, and a body marker (`github.MARKER`) finds the issue again after a reinstall. It finds its issues by that marker and never by label, because GitHub drops labels silently when a token may not set them. Everything that leaves goes through `upstream.scrub` (the reports' rules plus GitHub tokens) and then `aliases.Aliases.apply`: ids are parked behind placeholders while names run, and names are one alternation pass, because a room called "Kitchen" otherwise rewrites `light.kitchen` and a shorter name rewrites an alias just written. The alias map stays in `/data/devloop`; the token is in `/data/secrets` (backup-excluded, `0600`) and is never served back. Review holds a new fingerprint `pending` until a press; Delete is for good. **A `ready` row that has not gone says why** (`server._devloop_held` → `held` on `/api/devloop`, `devHeldReason` in `app.js`): Send sends at once, so a row still `ready` was held — by a day's cap the owner set (named with when the oldest of the day's issues frees a slot and that Daily limits ends it; no cap is never full), by a failed send (its error), or by a missing repository or token — and the Send toast reads the route's own `capped`. It said "will be sent", which read as brAIn stalling; `tests/test_devloop_held.py` and `measure-devloop` hold it. The preview and the sender call one `compose`. After the first send it says only WHEN (*Not seen since*, *Back again*, *Still happening on x.y.z*); "not seen" is claimed only while the stream is on, because a switched-off stream looked at nothing. `STREAMS` lists only streams that are built (faults, scorecard, wrongs, outcomes, unmet, snapshot, gaps, ideas, design, screens, liked, morph, siblings, walkthrough, look, canary, corpus), so the panel renders no switch that does nothing. Each has its own schedule and Run, ticked on `_checks_loop` by `_devloop_tick`; the Claude streams spend one of `max_runs_per_day` and a scheduled one answers to `_resident_gate`, while `max_issues_per_day` holds new issues back rather than dropping them — and only when the owner sets it. **No issue cap unless the owner sets one** (#797, `CAP_LIMITS`, `ISSUE_CAP_MARK`, `tests/test_devloop_no_daily_cap.py`): the owner called the 10-a-day default, the 50 ceiling and 5 per pass "silly — if there is an issue to send, just send it". 0 (the default) is no limit, `MAX_SENDS_PER_PASS` is gone, the cap has no ceiling, and autopilot no longer raises it. A stored 10 or 20 with no `issue_cap_chosen` mark was the old default or autopilot's reading saved back by the panel, so it reads as 0; every save writes the mark, so a number set after that is kept. **A rolling issue (the scorecard per release, the house shape) is keyed and digested EXACTLY** (`upstream._digest`), never through `fingerprint`: folding digits is right for a fault and filed every release's scorecard into the first one and never rewrote a body whose only change was a count. The cloud half is `.claude/skills/fix-from-house/SKILL.md` (a run drains the whole queue: every issue ends it closed with a reason, and the fixes go in batched PRs merged one after another under a run lock, by the routine through the GitHub tool because a `GITHUB_TOKEN` merge starts no workflow on `main`), and `devloop-guard` is the part that does not depend on a model reading it: it holds the test rules and the manifests' version-only rule, reading `version_only_files` from the BASE branch so a PR cannot loosen it. No file is off limits to the fixer: `needs_human_paths` and the `needs-human` ending are gone, and a fix it cannot land is closed declined with the plan. **The cloud's verdict comes home** (`upstream._refresh_verdicts` / `verdicts.json` / `STAND_DOWN_STREAMS` / `SLOW_WINDOW`): hourly, with the listing call the marker search already makes, the labels the routine closes issues with are stored per report; a `declined`/`not-brain`/`duplicate` report from gaps, ideas, design, unmet or walkthrough is not filed again for `stand_down_days` (90; its fingerprint, and a Claude stream's title too — see the stand-down bullet below), a stream with 6 of its last 8 resolved reports noise runs at twice its interval with the reason in the payload and an Undo, and `fixed` is never noise (Back again is unchanged). Unmet is keyed on what brAIn said it could not do (`capability_key`), never the person's words, and filed once it recurs in two conversations. Every non-rolling issue opens with an **Impact** section (rendered through scrub and aliases like the rest), and new reports are filed in `impact_score` order under the cap. **The `look` stream is the owner's "What do you want to fix?" box, and it is the one stream that is not a search** (`streams.LOOK_SYSTEM` / `LOOK_ROWS`): somebody who lives with brAIn has already found the problem, so the run's job is to find what is behind their words, judge it against what brAIn is for (junk output is a bug), and file ONE issue — two only for two named problems — with their words quoted and a `Done when:` line; `ui: true` rides as `entry["ux"]` and files with `devloop:ux`, which is how the cloud half knows to look at that pane: in the house's own Screens pictures, and on a fixture before and after its fix. A complaint that matches something already filed is still filed, prefixed "Still a problem:", since saying it again is how the owner says a fix did not land. **A look with no run to write it up is filed as typed** (`server._devloop_stream`): with no Claude credential, or the day's cap spent between the press and the run, the request is `verbatim_rows(topic)` ingested, and the line under the box says why (`note`; a pass that did not run reads its `skipped` as the reason). Both branches returned `skipped` before the fallback, so the press answered 202, nothing was filed and the status line said nothing (`tests/test_devloop.py::TestALookIsNeverDropped`). The wire name stays `look` because verdicts, schedules and stand-downs are keyed on it. `tests/test_devloop.py` drives it against a real loopback HTTP server speaking GitHub's calls, and the guard over a real git repository.

- **A follow-up says something only when something is new** (`upstream._follow_up` / `_retire_superseded`, `streams.morph`'s `seen_at`). Every brAIn update reopened every closed report at once with "Back again", because the house reopened on any version change and every update re-stamps every row a window still holds — a 24-hour journal, an all-time scorecard, a restart owed after each install — so each run of the cloud loop spent its first hour re-closing forty issues that carried no news, and the open list was never empty. A not-brAIn, duplicate or declined verdict is final (no comment, no reopen); a fixed report reopens only when its fault went away and came back after the close, or has gone on for `REOPEN_AFTER_S` on a release first seen after the close (`version_since`, `closed_at` read back with the verdicts); a row that says when it last happened is seen then, not when it was re-read; a new rolling issue closes the one it replaces and only that add-on's (`_rolling_owner`: the Screens stream files one per add-on, and filing Morph's closed brAIn's, `tests/test_devloop_screen_paths.py`); Morph's count is `impact.count` (it published `times`, which `IMPACT_KEYS` dropped, so its issue counted passes; `_clean_impact` still reads `times` off an outbox already on disk); and a still-happening report's body is rewritten, because the body was written once and a live count read off ten-day-old text is a fault nobody can aim a fix at. The producer row (`reports.faults`) is a fault only while somebody has marked the rule Wrong inside `SCORE_RECENT_S`: the scorecard is all-time, so a fixed rule kept its pre-fix Wrongs for ever. `tests/test_devloop_restamp.py`.
- **The loop is closed by evidence at both ends, and the fix version is what makes a follow-up evidence** (`upstream._fetch_fixed_in` / `FIXED_IN_RE` / `running_at_least` / `awaiting_update` / `cloud_last_seen`, `devloop/verify.py`, `streams.faults(log_text)` / `log_excerpt`, `streams.outcomes`, `server.crash_middleware`). Four seams were open. **The house read nothing off "Fixed in brAIn x.y.z"**, so a fault still seen on a release OLDER than the fix reopened the issue a day after any unrelated update, and a house with auto-update off was read as a house where every fix held; the version is read off the closing comment once (`FIXED_IN_PER_PASS`, three tries, then unknown — and unknown is never "arrived"), compared with the release the house RUNS (the queue's `version`, stamped by every sweep, never the entry's own, which for a fault that stopped is the old release by definition — the first cut used the entry's and said "Held … on 2.17.0" about a fix in 2.17.2), a fixed report seen on an older release says nothing, one installed and gone says **Held**, and the wait is counted on the scorecard body and in ⚙. **After an update, a question the update made moot is withdrawn** (`verify.moot`, `server._devloop_verify_settle`, run in front of every ask): one whose report was reopened, re-fixed in a newer release or has left the queue is withdrawn with nothing posted (`record_moot`), and everything else is the person's. It also answered Yes for brAIn (*brAIn checked on brAIn V*) on a report whose stream clears and had not been seen since the install — and no such question is ever asked: only `look` and `unmet` are (`VERIFY_STREAMS`), neither clears, because a request with no fingerprint has nothing to stop, and nobody asking again is not evidence. Never a gap or an idea, which would be a quiz about a model's sentence; never a memory line; settled under its own kind so no scorecard counts it. **A fault issue carried one sentence and no evidence**: the journal rows a `Run (…)` row was folded from and the add-on log's trouble lines (fetched by the server on the hourly pass, `reports.redact` in the stream, `scrub` and the aliases once more in `compose`) ride the body, and the body is rewritten on *Still happening* so the excerpt is current. **The Resident's judgement reached the cloud through nothing**: the `outcomes` stream is `outcomes.candidates` as keyed rows (one issue per lopsided scope, `clears` so a confirmed case ends it with *Not seen since*), free, off by default because it quotes what a person typed.

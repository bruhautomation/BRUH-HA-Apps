# brAIn: the development loop (house half)

The devloop streams, issue filing and redaction, verdicts coming home, follow-ups, screenshots and the harness, sibling add-ons' reports.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **Self-improvement and development are two switches, and only one sends anything** (⚙ › Features, `panel/features.py`). The **Learning loop** is brAIn changing itself on this house — Morph's learning pass, its lessons, the changes it proposes to its own dashboard code — and nothing leaves it; it is Morph's `learning` setting, read off the switch. The **Development loop** is this file: reports to the private repository so the code is fixed upstream. Its switch is the devloop's own `enabled` (`features.save` writes it through `devloop.save_settings`), shown in Features and nowhere else, and Morph's `report_code_issues` reads it too, so a Morph fault and a brAIn fault leave the house by the same switch. The autopilot switch's label is **Report everything without asking**: it was "Development mode: brAIn works on itself", which read as self-improvement and is the opposite. Morph is no sibling any more (`siblings.CATALOG`): its faults come through its own outbox, `streams.morph`, and its screens are drawn in the harness while its switch is on (`screen_targets.morph_on`).
- **Development mode is the devloop's `enabled` + `autopilot`, and every session is told which** (`server.development_mode` / `DEVELOPMENT_MODE_ON`/`_OFF`, `ha-context-gen.sh`'s "Development mode" section). Opt-in, off by default, and an unreadable settings file reads as off. When on, a session files bugs it notices with `report_bug` unasked; when off, only when asked. A devloop PUT rewrites the terminal's prompt file.
- **The harness draws Morph's own custom cards with their own code** (`devloop/harness.py`'s `customCard`, `/morph_cards/{name}`). A card under `/config/morph/cards` is a custom element the page defines; `createCardElement` waits for the definition (bounded) and mounts it with the read-only `hass`, and a card whose `setConfig` or `hass` throws, or whose file fails to load, is a labelled box saying so — never a blank, and never the whole page. A Lovelace card still draws as its placeholder, and the write guard and the WS stub hold for the card's own requests (`test_morphs_own_custom_cards_are_drawn_by_their_code`).
- **The development loop is a dormant developer feature, and every stream is its own switch** (`panel/devloop/`, `brain/DEVLOOP.md`, `docs/design/devloop.md`). Off for everyone, read at call time (`devloop.enabled()` / `stream_on`), deliberately a panel setting in ⚙ › Developer and NOT an add-on option, because an option is documented to every user. It files `reports.faults` rows as issues in a **private** repo the user owns (`github.check_repo` refuses a public one), one issue per fingerprint for its whole life: the fingerprint is the RAW `where|what` with digits folded, so a count moving or a rename never splits one fault into two issues, and a body marker (`github.MARKER`) finds the issue again after a reinstall. It finds its issues by that marker and never by label, because GitHub drops labels silently when a token may not set them. Everything that leaves goes through `upstream.scrub` (the reports' rules plus GitHub tokens) and then `aliases.Aliases.apply`: ids are parked behind placeholders while names run, and names are one alternation pass, because a room called "Kitchen" otherwise rewrites `light.kitchen` and a shorter name rewrites an alias just written. The alias map stays in `/data/devloop`; the token is in `/data/secrets` (backup-excluded, `0600`) and is never served back. Review holds a new fingerprint `pending` until a press; Delete is for good. **A `ready` row that has not gone says why** (`server._devloop_held` → `held` on `/api/devloop`, `devHeldReason` in `app.js`): Send sends at once, so a row still `ready` was held — by the day's cap (named with when the oldest of the day's issues frees a slot and that Daily limits ends it), by a failed send (its error), or by a missing repository or token — and the Send toast reads the route's own `capped`. It said "will be sent", which read as brAIn stalling; `tests/test_devloop_held.py` and `measure-devloop` hold it. The preview and the sender call one `compose`. After the first send it says only WHEN (*Not seen since*, *Back again*, *Still happening on x.y.z*); "not seen" is claimed only while the stream is on, because a switched-off stream looked at nothing. `STREAMS` lists only streams that are built (faults, scorecard, wrongs, outcomes, unmet, snapshot, gaps, ideas, design, screens, morph, siblings, look), so the panel renders no switch that does nothing. Each has its own schedule and Run, ticked on `_checks_loop` by `_devloop_tick`; the Claude streams spend one of `max_runs_per_day` and a scheduled one answers to `_resident_gate`, while `max_issues_per_day` holds new issues back rather than dropping them. **A rolling issue (the scorecard per release, the house shape) is keyed and digested EXACTLY** (`upstream._digest`), never through `fingerprint`: folding digits is right for a fault and filed every release's scorecard into the first one and never rewrote a body whose only change was a count. The cloud half is `.claude/skills/fix-from-house/SKILL.md` (a run drains the whole queue: every issue ends it closed with a reason, and the fixes go in batched PRs merged one after another under a run lock, by the routine through the GitHub tool because a `GITHUB_TOKEN` merge starts no workflow on `main`), and `devloop-guard` is the part that does not depend on a model reading it: it holds the test rules and the manifests' version-only rule, reading `version_only_files` from the BASE branch so a PR cannot loosen it. No file is off limits to the fixer: `needs_human_paths` and the `needs-human` ending are gone, and a fix it cannot land is closed declined with the plan. **The cloud's verdict comes home** (`upstream._refresh_verdicts` / `verdicts.json` / `STAND_DOWN_STREAMS` / `SLOW_WINDOW`): hourly, with the listing call the marker search already makes, the labels the routine closes issues with are stored per report; a `declined`/`not-brain`/`duplicate` report from gaps, ideas, look or unmet is never filed again (its fingerprint, and a Claude stream's title too), a stream with 6 of its last 8 resolved reports noise runs at twice its interval with the reason in the payload and an Undo, and `fixed` is never noise (Back again is unchanged). Unmet is keyed on what brAIn said it could not do (`capability_key`), never the person's words, and filed once it recurs in two conversations. Every non-rolling issue opens with an **Impact** section (rendered through scrub and aliases like the rest), and new reports are filed in `impact_score` order under the cap. **The `look` stream is the owner's "What do you want to fix?" box, and it is the one stream that is not a search** (`streams.LOOK_SYSTEM` / `LOOK_ROWS`): somebody who lives with brAIn has already found the problem, so the run's job is to find what is behind their words, judge it against what brAIn is for (junk output is a bug), and file ONE issue — two only for two named problems — with their words quoted and a `Done when:` line; `ui: true` rides as `entry["ux"]` and files with `devloop:ux`, which is how the cloud half knows to look at that pane: in the house's own Screens pictures, and on a fixture before and after its fix. A complaint that matches something already filed is still filed, prefixed "Still a problem:", since saying it again is how the owner says a fix did not land. The wire name stays `look` because verdicts, schedules and stand-downs are keyed on it. `tests/test_devloop.py` drives it against a real loopback HTTP server speaking GitHub's calls, and the guard over a real git repository.
- **The other BRUH add-ons reach the loop from outside, and a fix to one is waited for in ITS release** (`devloop/siblings.py`, the `siblings` stream, `upstream.product_of` / `running_for`, `h_bruh_addons` / `h_devloop_report`, the `bruh_addon_status` / `report_bug` MCP tools). GardenRX, BRUH Bambu Studio, BRUH Print, BRight, BRUH Minecraft and Morph had no route from breaking to a fix but the owner opening a cloud session, while brAIn, the Supervisor's admin, could already read each one's state and log and Home Assistant's error log for its integration. `collect` reads them (an add-on is ours by its slug tail AND its name, so a stranger's `_bright` is not) and never raises; `rows` is pure: a `boot: auto` add-on not running, each distinct log error (a traceback is its exception line; clocks, uppercase level markers, hex runs and uuids folded out; WARNING is not an error), ERROR-level `system_log` rows under its integration's logger, and an optional self-published outbox at `/config/.bruh/devloop/<key>.json` in Morph's row shape. **Every row's `where` begins with the add-on's name and carries `product` and `product_version`**, the issue is labelled `devloop:<key>`, and the cloud routine's table maps that to the directory. **`fixed_in` is per product** (`FIXED_IN_RE` names every product and a batch comment's matching product wins; `data["products"]` holds each add-on's installed version, written by the stream): comparing a "Fixed in Morph 1.0.5" against brAIn's 3.x read every Morph fix as installed on close, and the same would have been true of every sibling. "Not seen since", "Back again", "Held", the owner's question and `awaiting_update` all name and read the report's own product; a brAIn report is byte-for-byte what it was. **An add-on this pass could not look at is `unlooked`** (not installed, or its info refused), and `_follow_up` says nothing about it, `clear_resolved`'s rule. The chat's `report_bug` is one `look` row with no second Claude run — the conversation already looked — under the same review setting, caps and redaction, and so gets the owner's "is it fixed here?" afterwards. **Its fields were sliced, and the issue was the slice** (`REPORT_FIELDS`, `streams.OWNER_WORDS_CHARS`/`WHAT_CHARS`): a chat that put the owner's words and its diagnosis into `what` filed a 300-character fragment ending mid-word and nothing else, and the look stream cut the owner's words at 500 the same way. The owner's words keep 4,000 characters, `what` keeps its short cut for the title line while the whole of it rides in the body, every cut is `textclip.clip` (in `upstream.ingest` and the title too), and the tool's schema says which field is the verbatim words, which the summary and which the diagnosis (`tests/test_devloop_owner_words_whole.py`); `report_bug` is acting (it sends text off the box), so it is on `ANALYST_DENIED`, `GATED_MCP` and its hook copy, `CONTRACT_REFUSED_TOOLS` and refused on voice. brAIn **never patches another add-on's code in its container**: the next update wipes it and the fix never reaches the repository, which `CHAT_IDENTITY` and the generated `/config/CLAUDE.md` say. `tests/test_devloop_siblings.py`.
- **A follow-up says something only when something is new** (`upstream._follow_up` / `_retire_superseded`, `streams.morph`'s `seen_at`). Every brAIn update reopened every closed report at once with "Back again", because the house reopened on any version change and every update re-stamps every row a window still holds — a 24-hour journal, an all-time scorecard, a restart owed after each install — so each run of the cloud loop spent its first hour re-closing forty issues that carried no news, and the open list was never empty. A not-brAIn, duplicate or declined verdict is final (no comment, no reopen); a fixed report reopens only when its fault went away and came back after the close, or has gone on for `REOPEN_AFTER_S` on a release first seen after the close (`version_since`, `closed_at` read back with the verdicts); a row that says when it last happened is seen then, not when it was re-read; a new rolling scorecard closes the one it replaces; and a still-happening report's body is rewritten, because the body was written once and a live count read off ten-day-old text is a fault nobody can aim a fix at. The producer row (`reports.faults`) is a fault only while somebody has marked the rule Wrong inside `SCORE_RECENT_S`: the scorecard is all-time, so a fixed rule kept its pre-fix Wrongs for ever. `tests/test_devloop_restamp.py`.
- **The loop is closed by evidence at both ends, and the fix version is what makes a follow-up evidence** (`upstream._fetch_fixed_in` / `FIXED_IN_RE` / `running_at_least` / `awaiting_update` / `cloud_last_seen`, `devloop/verify.py`, `streams.faults(log_text)` / `log_excerpt`, `streams.outcomes`, `server.crash_middleware`). Four seams were open. **The house read nothing off "Fixed in brAIn x.y.z"**, so a fault still seen on a release OLDER than the fix reopened the issue a day after any unrelated update, and a house with auto-update off was read as a house where every fix held; the version is read off the closing comment once (`FIXED_IN_PER_PASS`, three tries, then unknown — and unknown is never "arrived"), compared with the release the house RUNS (the queue's `version`, stamped by every sweep, never the entry's own, which for a fault that stopped is the old release by definition — the first cut used the entry's and said "Held … on 2.17.0" about a fix in 2.17.2), a fixed report seen on an older release says nothing, one installed and gone says **Held**, and the wait is counted on the scorecard body and in ⚙. **After an update, brAIn answers what it can prove** (`verify.proof`, `server._devloop_verify_settle`, run in front of every ask): a report whose stream clears, whose fixed release is installed (`upstream.installed_at`, the first sweep that saw that release, `_note_installed`), not seen since that install, with that stream swept since and switched on, is answered Yes through `_end_devloop_verify(by="brain")` and posted as *brAIn checked on brAIn V: … (Not answered by the owner.)*, never as the owner confirming it; a question whose report was reopened, re-fixed in a newer release or has left the queue is withdrawn with nothing posted (`record_moot`); a request with no fingerprint (`look`, `unmet`) is left for the person, because nobody asking again is not evidence. And `_update_recheck` runs a second checks pass `UPDATE_RECHECK_S` after an update (the release in `schedule_store` under `UPDATE_VERSION_KEY`, recorded only once it ran; a checks interval of 0 is respected), so findings filed while the house was still coming back are cleared (`tests/test_devloop_verify_after_update.py`). **The owner's own request was never verified**: a `look` or `unmet` report has no fingerprint to stop, so once its release is installed ONE question case is filed (`verify.due`, once per `fixed_in`, through `findings_store.add_case`, source `devloop_verify` in `UNMUTABLE_SOURCES` and `SUBJECT_FOLD_EXCLUDED`), Yes posts *The owner confirms this is fixed on brAIn V*, No posts *Not fixed on brAIn V: <words>* aliased and reopens; the answer is recorded on the queue entry by the press and POSTED by the send pass, because posting needs the token and the lock the send pass already holds and a press must not wait on GitHub; the version on the comment is the running one for the same reason the Held wording is. Never a gap or an idea, which would be a quiz about a model's sentence; never a memory line; settled under its own kind so no scorecard counts it. **A fault issue carried one sentence and no evidence**: the journal rows a `Run (…)` row was folded from and the add-on log's trouble lines (fetched by the server on the hourly pass, `reports.redact` in the stream, `scrub` and the aliases once more in `compose`) ride the body, and the body is rewritten on *Still happening* so the excerpt is current. **The Resident's judgement reached the cloud through nothing**: the `outcomes` stream is `outcomes.candidates` as keyed rows (one issue per lopsided scope, `clears` so a confirmed case ends it with *Not seen since*), free, off by default because it quotes what a person typed. And **the panel's own 500s were invisible to every surface**: `crash_middleware` writes one journal row per route and exception type per `CRASH_SPACING_S` — the route PATTERN as the stage, the deepest panel frame that is not the middleware's own in the error — and re-raises, so the browser's answer is unchanged and the row reaches the fault list, a problem file and the loop by the doors every failure takes. `devloop-guard` fails a `devloop/` PR that changes code with no change under `tests/`, the skill's "failing test first" held by the half that does not read the skill. `tests/test_devloop_closed_loop.py`, `tests/test_panel_crash.py`.
- **The house photographs its own panel, and the page is redacted before the picture, never after** (`devloop/screens.py`, the `screens` stream, `h_devloop_screen`). Chromium (in the image, `--no-sandbox`, loopback only) is driven over CDP: each screen in a fresh tab at 390 light/dark (touch) and 1200, every rendered string in every reachable frame collected, sent through ONE Python `redact` (calendar-entity titles/descriptions/locations, occasion texts, non-home zone names and any address-shaped state blanked whole; addresses, emails, phones, coordinates, credential- and key-shaped runs blanked; then the aliases) and written back, then canvases, video, non-panel images and any frame not reached covered as *not captured*. Chart frames are reached through isolated worlds, which needs site isolation off for sandboxed frames; one that cannot be reached is covered, not trusted. A house whose `/states` cannot be read is not photographed (an event that could not be looked up could not be blanked), and a screen whose main frame did not redact is dropped. The audit measures against the configured width, never `innerWidth`, which a phone's zoom-out makes lie; a bar that is fixed or sticky is not an overlap and a disabled control is exempt from contrast. Pictures go up through the contents API (`github.put_file`, only under `screens/brain-<version>/`, skipped when git's blob sha matches) BEFORE the rolling issue that links them, and a failed upload files nothing; the gallery is built outside `compose`'s aliasing, because an aliased URL leads nowhere. The review preview serves the local files (`local_file` refuses anything but a kept capture's own names). `tests/test_devloop_screens.py` drives a real Chromium over a planted page and asserts the text left on it.
- **Every BRUH screen is photographed, and nothing photographed can act** (`devloop/screen_targets.py`, `devloop/harness.py`, `screens.request_allowed` / `_NO_SOCKETS_JS`, `h_harness_*`, `h_devloop_screenshot`, the `screenshot_panel` MCP tool). The Screens stream photographs the other add-ons' panels and the Lovelace cards and Morph too, each into its own rolling issue (`screens:<product>:<version>`, `product`/`product_version`, labelled `devloop:<key>`, pictures under `screens/<product>-<version>/`). **A panel is opened over the hassio network, never ingress**: minting an ingress session needs an admin's token on a current Supervisor (`esphome.py`), and every BRUH panel answers 172.30.32.0/23 because the ingress proxy reaches it from there, so `locate` reads `/addons/<slug>/info` (`ip_address`, or the gateway for `host_network`; `ingress_port`; GardenRX under its `ingress_entry`, which its gateway passes through) and an answer that does not say where is no URL, never a guess. Tabs are pressed by the panel's own button (`.tab[data-view|data-tab]`, held equal to each `index.html` by a test) and GardenRX's routes by URL. **The write guard is the browser's, not the page's**: `Fetch.enable` pauses every request and `_paused` fails anything but GET/HEAD/OPTIONS unless `reads` names it (BRUH Print's previews; GardenRX's `/api/db` only when the body's `action` is `select`, because the same route writes), and the held requests are listed in the issue so a part that says it could not save reads as the guard. **A WebSocket is not a request Fetch sees and Chromium's blocked-URL list does not stop its handshake** — the real-browser test proved it — so `WebSocket` is replaced in every frame before the page's script runs. **The cards and Morph are drawn in brAIn's own harness page** (loopback only): a browser here cannot sign into Home Assistant's frontend, so the page builds the `hass` a card is handed out of the house's real states, `callService`/`callApi` refuse, every WS question goes through `/devloop/harness/ws`, which asks Core only `READ_COMMANDS` (and `weather.get_forecasts` with a response), a hosted Lovelace card is a labelled box, and Morph is given no panel version so it offers no Reload the page could not mean. Files are served by a fixed name table (`CARD_FILES`) or a name pattern under one root (`module_file`), never a path off the URL. **Redaction, covering and the audit walk open shadow roots** (`_DEEP_JS`'s `deepAll`/`up`), because every card and all of Morph draw inside one. The chat's `screenshot_panel` is one picture on demand through the same capture, redacted and guarded, kept nowhere, needing no loop switched on — a read on `ANALYST_TOOLS` (the look stream uses it), refused on voice. **It can photograph one card** (`screens.parse_focus`, `morph-dashboard#<id>` or `element`, with `press: tap|open`): Morph was one screen, scrolled to the top and cut at `MAX_HEIGHT` from there, so a card further down could never be in the picture and none could be opened. The element is found by its `data-tile`/`data-sec` id through every open shadow root, pressed with a real pointer down and up (held `HOLD_S` to open) BEFORE redaction so an opened card is redacted as photographed, and the picture is cropped to it (`ELEMENT_MAX_HEIGHT`, not the page's ceiling); an id the page does not have is `MissingElement`, a 404 with a sentence. `tests/test_devloop_screenshot_card.py`. `tests/test_devloop_screen_targets.py` drives a real Chromium with the guard on (no write and no socket reach a real server; shadow text redacted) and the real harness routes drawing Morph's and BRUH Print's own code.
- **A fix question is the report's own title, and its detail is the report** (`devloop/verify.question_row`). The card ended "…(Fix: Findings never" over a detail starting "say who acts:": the text ran past the store's 200-character cap (`findings_store.MAX_TEXT`) and `split_overlong` moved the tail into the detail. The text is now composed to fit (`TEXT_CHARS`), the title cut on a word with "…" only when cut; the detail is the report less any sentence written for a developer (code quotes, a call, a CONSTANT, a snake_case name, a file) and where to look. It does not explain where an answer goes — the buttons say that.
- **Account ids are redacted with the credentials** (`journal.ACCOUNT_ID_RE`, `capture._TEXT_RULES`, `brain-report.sh`'s `redact()`): "accountId: 884213", "customerId=…", `"user_id": "…"` keep their key and lose their value, in the overnight check's records, the flood summary and everything `upstream.scrub` sends.

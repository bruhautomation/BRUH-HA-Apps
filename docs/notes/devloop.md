# brAIn: the development loop (house half)

The devloop streams, issue filing and redaction, verdicts coming home, follow-ups, screenshots and the harness, sibling add-ons' reports.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

What each rule cost to learn is in `docs/notes/history/devloop.md`.

## Switches and modes

- **Self-improvement and development are two switches, and only one sends anything** (⚙ › Features, `panel/features.py`).
  - The **Learning loop** is brAIn changing itself on this house — Morph's learning pass, its lessons, the changes it proposes to its own dashboard code — and nothing leaves it; it is Morph's `learning` setting, read off the switch.
  - The **Development loop** is this file: reports to the private repository so the code is fixed upstream. Its switch is the devloop's own `enabled` (`features.save` writes it through `devloop.save_settings`), shown in Features and nowhere else, and Morph's `report_code_issues` reads it too, so a Morph fault and a brAIn fault leave the house by the same switch.
  - The autopilot switch's label is **Report everything without asking**, because the old label read as self-improvement, which is the opposite.
  - Morph is no sibling any more (`siblings.CATALOG`): its faults come through its own outbox, `streams.morph`, and its screens are drawn in the harness while its switch is on (`screen_targets.morph_on`).
- **Development mode is the devloop's `enabled` + `autopilot`, and every session is told which** (`server.development_mode` / `DEVELOPMENT_MODE_ON`/`_OFF`, `ha-context-gen.sh`'s "Development mode" section). Opt-in, off by default, and an unreadable settings file reads as off. When on, a session files bugs it notices with `report_bug` unasked; when off, only when asked. A devloop PUT rewrites the terminal's prompt file.
- **The development loop is a dormant developer feature, and every stream is its own switch** (`panel/devloop/`, `brain/DEVLOOP.md`, `docs/design/devloop.md`).
  - Off for everyone, read at call time (`devloop.enabled()` / `stream_on`), deliberately a panel switch (⚙ › Features; the repository, token and streams are in ⚙ › Developer) and NOT an add-on option, because an option is documented to every user.
  - It files `reports.faults` rows as issues in a **private** repo the user owns (`github.check_repo` refuses a public one). The token is in `/data/secrets` (backup-excluded, `0600`) and is never served back; the alias map stays in `/data/devloop`.
  - `STREAMS` lists only streams that are built (faults, scorecard, wrongs, outcomes, unmet, snapshot, gaps, ideas, design, screens, liked, morph, siblings, walkthrough, look, canary, corpus), so the panel renders no switch that does nothing. Each has its own schedule and Run, ticked on `_checks_loop` by `_devloop_tick`; the Claude streams spend one of `max_runs_per_day` and a scheduled one answers to `_resident_gate`.
  - `tests/test_devloop.py` drives it against a real loopback HTTP server speaking GitHub's calls, and the guard over a real git repository.

## Filing: fingerprints, review and caps

- **One issue per fingerprint for its whole life** (part of the dormant-feature rule above): the fingerprint is the RAW `where|what` with digits folded, so a count moving or a rename never splits one fault into two issues, and a body marker (`github.MARKER`) finds the issue again after a reinstall. It finds its issues by that marker and never by label, because GitHub drops labels silently when a token may not set them.
- **A rolling issue (the scorecard per release, the house shape) is keyed and digested EXACTLY** (`upstream._digest`), never through `fingerprint`: folding digits is right for a fault but would file every release's scorecard into the first one and never rewrite a body whose only change was a count.
- Review holds a new fingerprint `pending` until a press; Delete is for good. The preview and the sender call one `compose`.
- **A `ready` row that has not gone says why** (`server._devloop_held` → `held` on `/api/devloop`, `devHeldReason` in `app.js`, `tests/test_devloop_held.py`, `measure-devloop`). Send sends at once, so a row still `ready` was held: by a day's cap the owner set (named with when a slot frees and that Daily limits ends it), by a failed send (its error), or by a missing repository or token. The Send toast reads the route's own `capped`.
- **No issue cap unless the owner sets one** (#797, `CAP_LIMITS`, `ISSUE_CAP_MARK`, `tests/test_devloop_no_daily_cap.py`).
  - `max_issues_per_day` holds new issues back rather than dropping them, and only when the owner sets it. 0 (the default) is no limit, `MAX_SENDS_PER_PASS` is gone, the cap has no ceiling, and autopilot no longer raises it.
  - A stored 10 or 20 with no `issue_cap_chosen` mark was the old default or autopilot's reading saved back by the panel, so it reads as 0; every save writes the mark, so a number set after that is kept.
- After the first send a report says only WHEN (*Not seen since*, *Back again*, *Still happening on x.y.z*); "not seen" is claimed only while the stream is on, because a switched-off stream looked at nothing.
- Every non-rolling issue opens with an **Impact** section (rendered through scrub and aliases like the rest), and new reports are filed in `impact_score` order under the cap.
- **Every issue carries its facts as one parsed block, and every machine comment its own kind** (`devloop/blocks.py`, `upstream.block_object` / `compose` / `_fit`, plan 3.2, `tests/test_devloop_blocks.py`).
  - The body keeps its marker and its prose for a person, and ends with ```` ```json brain-devloop ```` holding `{"v":1,"fp","stream","product","release","where","what","done_when","evidence_refs","owner_words","log_excerpt","digest"}`.
  - `product` is `brain` (Morph's reports included) or the sibling's slug. `done_when`/`owner_words`/`log_excerpt` are a stream's own fields when it stores them and are otherwise read out of its body (`**Done when:**`, `The owner said:` quotes, the add-on log `<details>`); `done_when` is `""` and the two quoted fields `null` when absent (the cloud half types every field: `.claude/skills/fix-from-house/scripts/issue_parse.py`'s `REQUIRED`).
  - **The digest is the contract**: sha256 of `json.dumps(obj_without_digest, sort_keys=True, separators=(",",":"), ensure_ascii=False)`, and `parse_block` refuses a block whose digest does not check, so a body cut at GitHub's limit is no block rather than a short one — which is why `_fit` shortens the human half to keep the block whole.
  - Every string is built from `clean` (scrub, then aliases) before the block, never after. A backtick is written as ``` inside the JSON, so a fence in somebody's words cannot end the block and any JSON parser reads the same string back.
  - The other kinds are `brain-canary`, `brain-held`, `brain-after` and `brain-corpus`; a canary issue carries only its own. The cloud reads the block as the task.
- **No report carries a control character, and a block is held to parsing back** (`upstream.plain`/`scrub`, `streams.log_excerpt`, `blocks.make_block`, `tests/test_devloop_block_escapes.py`). `scrub` (every string of a report) and `log_excerpt` (before it picks the trouble lines) drop ANSI sequences, their `^[[…m` caret spelling, and every control character but the line break and the tab. `make_block` checks its text parses back to the object it sealed and writes it all-ASCII if not; the digest is over the object, so the spelling does not move it.
- **A filed report keeps its issue when the queue prunes it, and a second issue for one fingerprint folds back into the first** (`upstream._prune` / `_restore` / `KEEP_WHEN_PRUNED`, `_refresh_verdicts`). The queue holds sixty entries and prunes the oldest sent one first.
  - A pruned entry with an issue leaves its issue, verdict and dates behind in the queue's `gone`, and an fp with neither is rebuilt from `verdicts.json`'s `resolved` (which keeps `closed_at`), read as it stood at the close (last seen then, already told so), so its row is read against the old issue: old evidence says nothing, and only a sighting after the close says *Back again* there.
  - An open second issue does not erase the first one's verdict, and when the cloud closes it as a duplicate the report goes back to the first issue (its verdict, or the install record in `held` when the verdict was already lost).

## The cloud half and its verdicts

- The cloud half is `.claude/skills/fix-from-house/SKILL.md`: a run drains the whole queue (every issue ends it closed with a reason), and the fixes go in batched PRs merged one after another under a run lock, by the routine through the GitHub tool because a `GITHUB_TOKEN` merge starts no workflow on `main`.
- `devloop-guard` is the part that does not depend on a model reading it: it holds the test rules and the manifests' version-only rule, reading `version_only_files` from the BASE branch so a PR cannot loosen it, and it fails a `devloop/` PR that changes code with no change under `tests/` (the skill's "failing test first", held by the half that does not read the skill).
- No file is off limits to the fixer: `needs_human_paths` and the `needs-human` ending are gone, and a fix it cannot land is closed declined with the plan.
- **The cloud's verdict comes home** (`upstream._refresh_verdicts` / `verdicts.json` / `STAND_DOWN_STREAMS` / `SLOW_WINDOW`). Hourly, with the listing call the marker search already makes, the labels the routine closes issues with are stored per report.
  - A `declined`/`not-brain`/`duplicate` report from gaps, ideas, design, unmet or walkthrough is not filed again for `stand_down_days` (its fingerprint, and a Claude stream's title too).
  - A stream with 6 of its last 8 resolved reports noise runs at twice its interval with the reason in the payload and an Undo, and `fixed` is never noise (Back again is unchanged).
- **A noise verdict silences for `stand_down_days`, not for ever** (`upstream.live_stood` / `stand_down_s` / `_reopen_for_refile`, plan 0.5, `tests/test_devloop_stand_down_days.py`).
  - A stand-down lasts the house's own `stand_down_days` setting (90, in the devloop settings beside the caps: the house never reads `.claude/devloop.json`).
  - After it, a recurrence is a NEW issue (`_file` ignores the marker match on `previous_issue`) whose body says **Filed again:** #N was closed as declined on its date, and `verdicts.json`'s `refiled` records it.
  - The days count from the verdict: `_refresh_verdicts` keeps the first date, because restamping `at` every hour would make 90 days never end. A stand-down recorded without a date starts its days the first time `_vload` reads it.
- **A follow-up says something only when something is new** (`upstream._follow_up` / `_retire_superseded`, `streams.morph`'s `seen_at`, `tests/test_devloop_restamp.py`). Every update re-stamps every row a window still holds, so a version change alone is not news.
  - A not-brAIn, duplicate or declined verdict is final (no comment, no reopen).
  - A fixed report reopens only when its fault went away and came back after the close, or has gone on for `REOPEN_AFTER_S` on a release first seen after the close (`version_since`, `closed_at` read back with the verdicts).
  - A row that says when it last happened is seen then, not when it was re-read.
  - A new rolling issue closes the one it replaces and only that add-on's (`_rolling_owner`: the Screens stream files one per add-on, `tests/test_devloop_screen_paths.py`).
  - Morph's count is `impact.count` (`_clean_impact` still reads the old `times` off an outbox already on disk, which `IMPACT_KEYS` dropped).
  - A still-happening report's body is rewritten, because a live count read off ten-day-old text is a fault nobody can aim a fix at.
  - The producer row (`reports.faults`) is a fault only while somebody has marked the rule Wrong inside `SCORE_RECENT_S`: the scorecard is all-time, so a fixed rule would keep its pre-fix Wrongs for ever.

## Evidence, the fix version and the house's answers

- **The loop is closed by evidence at both ends, and the fix version is what makes a follow-up evidence** (`upstream._fetch_fixed_in` / `FIXED_IN_RE` / `running_at_least` / `awaiting_update` / `cloud_last_seen`, `devloop/verify.py`, `streams.faults(log_text)` / `log_excerpt`, `streams.outcomes`, `server.crash_middleware`, `tests/test_devloop_closed_loop.py`, `tests/test_panel_crash.py`).
  - **The house read nothing off "Fixed in brAIn x.y.z"**: the version is now read off the closing comment once (`FIXED_IN_PER_PASS`, three tries, then unknown — and unknown is never "arrived") and compared with the release the house RUNS (the queue's `version`, stamped by every sweep, never the entry's own, which for a fault that stopped is the old release by definition). A fixed report seen on an older release says nothing, one installed and gone says **Held**, and the wait is counted on the scorecard body and in ⚙.
  - **After an update, a question the update made moot is withdrawn** (`verify.moot`, `server._devloop_verify_settle`, run in front of every ask): one whose report was reopened, re-fixed in a newer release or has left the queue is withdrawn with nothing posted (`record_moot`), and everything else is the person's.
  - Only `look` and `unmet` are ever asked (`VERIFY_STREAMS`): neither clears, because a request with no fingerprint has nothing to stop, and nobody asking again is not evidence. A clearing stream's fix is answered by its issue (**Held**), never by a question, and brAIn never answers one for the owner.
  - `_update_recheck` runs a second checks pass `UPDATE_RECHECK_S` after an update (the release in `schedule_store` under `UPDATE_VERSION_KEY`, recorded only once it ran; a checks interval of 0 is respected), so findings filed while the house was still coming back are cleared (`tests/test_devloop_verify_after_update.py`).
  - **The owner's own request was never verified**, so once a `look` or `unmet` report's release is installed ONE question case is filed (`verify.due`, once per `fixed_in`, through `findings_store.add_case`, source `devloop_verify` in `UNMUTABLE_SOURCES` and `SUBJECT_FOLD_EXCLUDED`). Yes posts *The owner confirms this is fixed on brAIn V*, No posts *Not fixed on brAIn V: <words>* aliased and reopens. The answer is recorded on the queue entry by the press and POSTED by the send pass, because posting needs the token and the lock the send pass already holds and a press must not wait on GitHub; the version on the comment is the running one. Never a gap or an idea (a quiz about a model's sentence); never a memory line; settled under its own kind so no scorecard counts it.
  - **A fault issue carried one sentence and no evidence**: now the journal rows a `Run (…)` row was folded from and the add-on log's trouble lines (fetched by the server on the hourly pass, `reports.redact` in the stream, `scrub` and the aliases once more in `compose`) ride the body, and the body is rewritten on *Still happening* so the excerpt is current.
  - **The Resident's judgement reached the cloud through nothing**: the `outcomes` stream is `outcomes.candidates` as keyed rows (one issue per lopsided scope, `clears` so a confirmed case ends it with *Not seen since*), free, off by default because it quotes what a person typed.
  - And **the panel's own 500s were invisible to every surface**: `crash_middleware` writes one journal row per route and exception type per `CRASH_SPACING_S` — the route PATTERN as the stage, the deepest panel frame that is not the middleware's own in the error — and re-raises, so the browser's answer is unchanged and the row reaches the fault list, a problem file and the loop by the doors every failure takes.
- **A fix question is the report's own title, and its detail is the report** (`devloop/verify.question_row`). The text is composed to fit the store's cap (`TEXT_CHARS` under `findings_store.MAX_TEXT`), the title cut on a word with "…" only when cut; the detail is the report less any sentence written for a developer (code quotes, a call, a CONSTANT, a snake_case name, a file) and where to look. It does not explain where an answer goes — the buttons say that.
- **A fix question waits for the fix to be RUNNING, and one release's fixes to one area are one question** (`verify.live_version` / `due_groups` / `group_row` / `fps_for_finding`, `tests/test_devloop_verify_grouped.py`, #535).
  - brAIn's release for a fix question (asking and withdrawing alike) is the older of the add-on's and the integration Home Assistant has loaded (`server._integration_versions`), and "could not tell" while a restart is owed and nothing says what is loaded.
  - Due reports are grouped by add-on, release and place ("Chat", "Today"; the owner's own requests share one) and each group is ONE row listing what changed, each change once; one report is the question it always was.
  - Every report in a row is recorded under its id, so Yes or No answers each of them, Undo forgets each, and brAIn withdraws the row only when every one is moot.
- **A fix question says what brAIn could not check and the one thing to try, and does not linger** (`verify._checking` / `_reported` / `QUESTION_TTL_DAYS`, `moot(now=)`, `tests/test_fix_question_says_what_brain_checked.py`, #605). The detail says brAIn cannot check this kind itself, which release it was reported on, and one step — open the place, or ask the chat again — with the report's own "Done when" as what counts as fixed. An unanswered question older than `QUESTION_TTL_DAYS` is withdrawn by the settle pass as moot, with nothing posted.
- **Seven days after a fix is installed, the house says once whether it held** (`upstream._held_check` / `efficacy`, verdicts' `held`, plan 1.3/1.4, `tests/test_devloop_held_seven_days.py`). 
  - For a report from a stream that `clears`, the first send pass that sees the house run `fixed_in` records the install; the fault seen again (on a release at least `fixed_in`) posts `brain-held` with `held: false` at once, and seven silent days post `held: true` — only while the stream is on and looked, because silence from a switched-off stream is not evidence.
  - ⚙ › Developer's **Did the fixes hold?** shows `efficacy()`: held^7d (of the decided), came-back (of the installs seen), how many are inside their seven days, fixes awaiting an update, and the newest canary verdicts — counted by code, never estimated.
- **A fixed screen is photographed again once its fix is here, and nothing waits on the owner** (`devloop/after.py`, `server._devloop_after_pass`, plan 3.4, `tests/test_devloop_after.py`). 
  - For a `look`/`unmet` report closed fixed whose release the house runs, the screen it names (the longest screen label, or its last part, found as whole words in its place and title — never guessed) is captured through `screens.capture` at 390 light, redacted and guarded as the Screens stream is, and put at `screens.repo_path(running, …)`.
  - One `brain-after` comment names `before` (the newest Screens picture of that screen from a release older than the fix, or `""` — a string, as the cloud types it) and `after`, once per report and fix (`after.json`).
  - The owner's "is this fixed?" is still asked as an extra signal; its card shows no picture because Today's cards draw no images.
- **The canary is the house telling the cloud a release broke something** (`devloop/canary.py`, the `canary` stream, `upstream._compose_canary` / `_post_canary_final`, section 0 of the self-learning plan, `tests/test_devloop_canary.py`, `tests/test_devloop_canary_server.py`).
  - An install is a version that MOVED (the queue's brAIn `version`, a sibling's in `products`); a first reading is a baseline, brAIn's included, because the loop may be switched on a year after an install and every fault already there would read as the release's.
  - For `canary_window_hours` (24) one rolling issue per release, `[canary] <slug> <version>`, carries a `brain-canary` block, rewritten hourly: `new_faults` (first seen on the release and on at least two passes), `came_back` (`came_back_at`, set when `_follow_up` reopens or the held check sees a fix fail), `scorecard_drops` (a producer's right-share 20 points down on the settled ledger's `release` field; nothing is claimed when the ledger has no `release`), `start_crash` (`note_start` from `on_startup`, `note_ready` from the first stream pass: four starts on the release, or two that never reached the loop).
  - Any signal is `regressed` at once; none by the window's end is `healthy`; the verdict is final, posted once as a comment, and the release files nothing more. A canary is never held for review (no human gate under section 0) but goes through the day's cap, and only a `healthy` canary is closed as superseded.
  - The siblings get the same from what the siblings stream reads (their "not running" row is the start crash; no scorecard).

## Redaction and aliases

- Everything that leaves goes through `upstream.scrub` (the reports' rules plus GitHub tokens) and then `aliases.Aliases.apply`: ids are parked behind placeholders while names run, and names are one alternation pass, because a room called "Kitchen" otherwise rewrites `light.kitchen` and a shorter name rewrites an alias just written.
- **Account ids are redacted with the credentials** (`journal.ACCOUNT_ID_RE`, `capture._TEXT_RULES`, `brain-report.sh`'s `redact()`): "accountId: 884213", "customerId=…", `"user_id": "…"` keep their key and lose their value, in the overnight check's records, the flood summary and everything `upstream.scrub` sends.
- **A one-word name that is also a common English word is aliased where it is a name, never where it is the word, and privacy decides first** (`aliases.is_ordinary` / `ordinary_words.txt` / `_typed_words` / `_used_as_name`, `Aliases.apply(strict=)`, `upstream._typed` / `block_object(strict=)`, `tests/test_redaction.py::TestOrdinaryWordsSurviveAliasing`).
  - A name is exempt only when it is one ASCII word whose lower case is on `ordinary_words.txt` (built once offline from this repository's own prose, kept only where they appear lower case more than capitalised, with given names, pets' names, rooms and code tokens taken out; removing a word is always safe) and it is not a person's, tracker's, zone's or room's.
  - Only then is an occurrence written all lower case in running prose left; one written with a capital (the household's spelling, which every field built from entity data carries), quoted or in a code span, followed by its domain word or `entity`, beside an entity id, between `·`/`›`/`|` separators, or alone on its line, list item or `Name:` field is aliased.
  - A person's typed words and a log are never prose: `owner_words`, `log_excerpt`, a `what` that is the owner's words (a look filed as typed) and the owner's "Not fixed" note go through `apply(strict=True)`, and in a body any line quoted with `>` or inside a ``` fence keeps the whole-word rule (every line of the typed-look body is quoted).
  - It lives in `apply`, the one function compose, the owner-answer and canary comments and the Screens text all go through; do not add a second path.
- **A first name is learnt where the house defines it, never guessed from text** (`aliases.name_parts` / `dashboard_names` / `house_config_names`, run inside `Aliases.learn`, the one place every path fills the map).
  - `learn` takes whole friendly names, persons and areas, and also every word of a person's name, the owner in a possessive name, the words of a sleep, door, window or room-presence sensor's name that are neither `GENERIC_WORDS` nor on `ordinary_words.txt`, and the names Morph's dashboard.yaml and `dashboards/*.yaml` give (a card's or section's name, a group's label, any `person`/`sleeper`/`people`/`who` value; a dashboard's and a floor's title are the page's, not the household's).
  - A common English word is never learnt from these, so "Doors", "People" and "Kids" stay readable, and a brand in a lamp's name ("Sonos Lamp") is not split out. A gamertag that is not a name the house defines is still not caught.
- **A report's product identity never passes through the aliases** (`aliases.is_product`, `PRODUCT_NAMES`; `upstream.canary_object`). The cloud matches a canary to the add-on a merged PR bumped by it, so a mangled product means a regression can never be reverted.
  - The vendor word, every BRUH add-on's name and slug (from `siblings.CATALOG`), brAIn and Morph are never learnt and `apply` writes them as themselves (a map that learnt one earlier included); a longer household name around one ("BRUH Hall Motion") is still aliased whole.
  - The canary block's `product` is `product_slug(entry)`, never cleaned text, and its title is built from the block (`[canary] <product> <release>`), so title and block always agree; the digest is taken after, so the block stays verifiable.

## The streams

- **The `look` stream is the owner's "What do you want to fix?" box, and it is the one stream that is not a search** (`streams.LOOK_SYSTEM` / `LOOK_ROWS`). Somebody who lives with brAIn has already found the problem, so the run's job is to find what is behind their words, judge it against what brAIn is for (junk output is a bug), and file ONE issue — two only for two named problems — with their words quoted and a `Done when:` line.
  - `ui: true` rides as `entry["ux"]` and files with `devloop:ux`, which is how the cloud half knows to look at that pane: in the house's own Screens pictures, and on a fixture before and after its fix.
  - A complaint that matches something already filed is still filed, prefixed "Still a problem:", since saying it again is how the owner says a fix did not land.
  - The wire name stays `look` because verdicts, schedules and stand-downs are keyed on it.
- **A look with no run to write it up is filed as typed** (`server._devloop_stream`, `tests/test_devloop.py::TestALookIsNeverDropped`): with no Claude credential, or the day's cap spent between the press and the run, the request is `verbatim_rows(topic)` ingested, and the line under the box says why (`note`; a pass that did not run reads its `skipped` as the reason).
- Unmet is keyed on what brAIn said it could not do (`capability_key`), never the person's words, and filed once it recurs in two conversations.
- **The other BRUH add-ons reach the loop from outside, and a fix to one is waited for in ITS release** (`devloop/siblings.py`, the `siblings` stream, `upstream.product_of` / `running_for`, `h_bruh_addons` / `h_devloop_report`, the `bruh_addon_status` / `report_bug` MCP tools, `tests/test_devloop_siblings.py`). brAIn, the Supervisor's admin, can read each one's state and log and Home Assistant's error log for its integration.
  - `collect` reads them (an add-on is ours by its slug tail AND its name, so a stranger's `_bright` is not) and never raises. `rows` is pure: a `boot: auto` add-on not running, each distinct log error (a traceback is its exception line; clocks, uppercase level markers, hex runs and uuids folded out; WARNING is not an error), ERROR-level `system_log` rows under its integration's logger, and an optional self-published outbox at `/config/.bruh/devloop/<key>.json` in Morph's row shape, whose `last` (or `seen_at`) is when the row was last true: read without `last`, a row in the documented shape was seen now on every pass.
  - **The catalog is every add-on `.claude/devloop.json` guards** (`TestTheCatalogIsTheRepository`).
  - **Morph is brAIn's wherever it is named**: `report_bug(addon="Morph")` and a look reply naming Morph (the prompt asks for it, `reply_schema`'s enum holds it) file a brAIn report whose `where` leads with "Morph · ", which routes the fix to brAIn's Morph half.
  - **Every row's `where` begins with the add-on's name and carries `product` and `product_version`**, the issue is labelled `devloop:<key>`, and the cloud routine's table maps that to the directory.
  - **`fixed_in` is per product** (`FIXED_IN_RE` names every product and a batch comment's matching product wins; `data["products"]` holds each add-on's installed version, written by the stream). "Not seen since", "Back again", "Held", the owner's question and `awaiting_update` all name and read the report's own product; a brAIn report is byte-for-byte what it was.
  - **An add-on this pass could not look at is `unlooked`** (not installed, or its info refused), and `_follow_up` says nothing about it, `clear_resolved`'s rule.
  - The chat's `report_bug` is one `look` row with no second Claude run — the conversation already looked — under the same review setting, caps and redaction, and so gets the owner's "is it fixed here?" afterwards. `report_bug` is acting (it sends text off the box), so it is on `ANALYST_DENIED`, `GATED_MCP` and its hook copy, `CONTRACT_REFUSED_TOOLS` and refused on voice.

- **The corpus stream files first looks the household disagreed with** (`devloop/corpus.py`, the `corpus` stream, plan 1.7, `tests/test_devloop_corpus_stream.py`). Off by default and silent while capture is off. Each first-look capture labelled `wrong` or `missed` is one issue keyed on its run id, carrying a `brain-corpus` block that is itself a schema-valid corpus entry (`kind: first_look`, only those labels, `source: house`, plus `v` and `digest`). Too big for an issue, it drops its `inputs`, then is not filed. Review, caps and redaction are the other streams'.

Off, nothing leaves and the suggestion keeps its Send.
- **Liked is the one stream that says what to protect, and it carries counts and brAIn's own names only** (`streams.liked` / `_liked_name` / `discussions`, `server._devloop_liked`, the `liked` entry in `devloop.STREAMS`, `tests/test_redaction.py::TestLikedCarriesCountsOnly`, the skill's *What the household likes is evidence*). Every other stream is a fault, a Wrong or a gap, so a cloud that fixes only from them makes brAIn quieter each run.
  - Free, off by default (it is drawn from what people did), daily on autopilot, and rolling: one `[Liked] brAIn <version>` issue per release.

There is no store of "insight cards kept" or "card asked about", so cards appear only as producers in the ledger.
  - A producer or kind is printed only when it is spelled the way the code spells one (lower case, `_` and `-`; a `check:` id may be dotted); a producer keyed on an entity (`baseline:sensor.x`) is counted under its family and anything sentence-shaped is dropped, before `compose` scrubs and aliases the whole issue like any other. A house with nothing counted files nothing.
  - The cloud half is told it is evidence, not work: read before triage, and a fix that removes or quietens something it lists says so.

## Screens: capture and redaction

- **The house photographs its own panel, and the page is redacted before the picture, never after** (`devloop/screens.py`, the `screens` stream, `h_devloop_screen`, `tests/test_devloop_screens.py` drives a real Chromium over a planted page and asserts the text left on it).

Every rendered string in every reachable frame goes through ONE Python `redact` and is written back: calendar-entity titles/descriptions/locations, occasion texts, non-home zone names and address-shaped states blanked whole; addresses, emails, phones, coordinates, credential- and key-shaped runs blanked; then the aliases. Canvases, video, non-panel images and any frame not reached are covered.
  - Chart frames are reached through isolated worlds, which needs site isolation off for sandboxed frames; one that cannot be reached is covered, not trusted.
  - A house whose `/states` cannot be read is not photographed (an event that could not be looked up could not be blanked), and a screen whose main frame did not redact is dropped.
  - Pictures go up through the contents API (`github.put_file`, only under `screens.repo_path`'s `screens/<product>-<version>/` for every product, skipped when git's blob sha matches; `tests/test_devloop_screen_paths.py` runs every product through both) BEFORE the rolling issue that links them, and a failed upload files nothing; the gallery is built outside `compose`'s aliasing, because an aliased URL leads nowhere.

- **Every BRUH screen is photographed, and nothing photographed can act** (`devloop/screen_targets.py`, `devloop/harness.py`, `screens.request_allowed` / `_NO_SOCKETS_JS`, `h_harness_*`, `h_devloop_screenshot`, the `screenshot_panel` MCP tool; `tests/test_devloop_screen_targets.py` drives a real Chromium with the guard on and the real harness routes drawing Morph's and BRUH Print's own code).

Tabs are pressed by the panel's own button (`.tab[data-view|data-tab]`, held equal to each `index.html` by a test) and GardenRX's routes by URL.

## Screens: the audit and the pass

- The audit measures against the configured width, never `innerWidth`, which a phone's zoom-out makes lie; a bar that is fixed or sticky is not an overlap and a disabled control is exempt from contrast.
- **The Screens audit measures only what is drawn** (`screens._AUDIT_JS`'s `shown`, `checkVisibility`, #1181). Controls inside a closed `<details>` or under a hidden or opacity-0 ancestor still answer a box of their own size; every audit (overlap, small targets, contrast, cut-off text) reads the same `shown`.
- **The layout check reads a colour by painting it, never by its numbers** (`screens._AUDIT_JS`'s `rgb`, #820). Chromium answers a `color-mix()` colour as `oklab(…)`, not 0–255, so a colour is painted on a 1px canvas and read back as sRGB with its alpha; the plain `rgb()` reading is kept only for a browser without a canvas. A contrast fault on a mixed colour from before this is not evidence.
- **A stream that could not look says so, in the cloud and on the house** (`upstream.note_blind` / `blind_rows` / `blind_notes` / `BLIND_REASONS`, `server._devloop_stream`'s `screens` branch, `tests/test_devloop_walk_switches.py`).
  - `_devloop_screens` names a reason CLASS (`blind`: browser, states, ha, capture, redaction, own-panel; `ha` is the states refusal because Home Assistant did not answer, which Faults says on its "did not answer" row instead of as its own, see `docs/notes/diagnostics.md`) on every return that filed nothing; the branch records it (one record per stream, a count and a since-date, the newest error's words kept as detail) and the **Faults** stream files it as `Screens | could not photograph: <reason>`.
  - The fingerprint is the class, never the exception's words, so it is one issue while it lasts, and because Faults clears, a successful capture (`note_photographed` drops the record) ends it with "not seen since". ⚙ › Developer says the same under the stream (`notes` on `/api/devloop`).
  - It rides on Faults rather than `ingest` under its own stream because ingesting one row into a clearing stream stamps the stream as run and tells every other fault it was not seen. The no-browser skip is stamped as run too, or the record would count every tick.
- **Screens is owed once per release, never more than every `SCREENS_RELEASE_GAP_H` hours** (`upstream.due_streams` / `unphotographed` / `note_photographed`). 
  - For `screens` only, a pass is also due when the queue's `version` (a dev build is never "new") is not the one brAIn's own panel was last photographed on and 6 hours have passed since the last try; a schedule of "only when asked" is still only when asked.
  - "Photographed" needs a kept picture of brAIn's OWN panel: a capture that only got the other add-ons files their issues and is recorded as blind (`own-panel`).
- **A Screens pass is as long as what it has to photograph, keeps what finished, and an error line is never blank** (`screens.planned` / `pass_budget` / `order_targets` / `SCREEN_MAX_S` / `TARGET_MAX_S`, `capture`'s `deadline`/`progress`/`left`/`unfinished`, `upstream.screens_left` / `note_screens_left`, `server.DEVLOOP_SCREENS_GRACE_S`, `textclip.said`; #890).
  - The pass's time is `SCREEN_BUDGET_S` a picture (never under fifteen minutes or over `PASS_MAX_S`); each target is photographed at every view before the next begins, brAIn's own panel first (only the pass's end stops it), each screen is bounded by `SCREEN_MAX_S` and each other target by `TARGET_MAX_S`.
  - At the deadline the capture stops and returns what it has, which is filed, and the products it did not finish are passed to `ingest` as `unread` (their reports say nothing rather than "not seen since"). The targets left go first next time and keep the stream owed after `SCREENS_RELEASE_GAP_H` (`due_streams`).
  - The outer `wait_for` is only for a browser that stopped answering; its line, like the deadline's, says "timed out after N s, X of Y screens captured".
  - Every devloop error line built from an exception goes through `textclip.said` (its text, else its type's name), because a timeout's text is empty and an exception is always truthy.

# BRUH Print specifics

The DYMO protocol, calibration, rendering, stocks and rolls, the panel and card.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **There is no CUPS in the container, and that is the design.** `panel/dymo/` speaks the LabelWriter's own raster protocol over a bulk USB endpoint — about 300 lines and no daemon — where a print server would add a spooler, a PPD, a filter chain and a second place for a job to get stuck, to produce the same bytes. What is sent is `ESC q` (roll select), `ESC L` (length), `ESC D` (bytes per line), one `SYN` line per row, and `ESC G`/`ESC E` to feed — the shape cups-filters' DYMO path has printed with for twenty years. **Density and print quality ARE sent now, and for one release they deliberately were not.** The first cut left out `ESC c/d/e/g` (density) and `ESC h`/`ESC i` (text-speed / barcodes-and-graphics mode) on the theory that a byte sent to the wrong firmware is a wedged printer rather than a lighter label — and what shipped was every label printing at the printer's own defaults, which is the fast mode at normal density, and on ordinary thermal stock that reads as faint. The complaint was the labels, not the theory, so `standard` and `compact` send `ESC g` and `ESC i` by default (`density` and `quality` in `settings_store`, both a fixed choice list, both on the Printer tab) in the order cups-filters' `rastertolabel.c` has sent them for twenty years: density, quality, `ESC L`, `ESC D`. **Graphics mode is 300×600, and that changes the body, not just the preamble**: the printer steps the paper 600 times an inch, so a 300-dpi raster sends every line twice (`protocol.LINE_REPEAT`) and the `ESC L` length doubles with it — the repeat and the length are one fact, named once, so they cannot drift apart; sent as-is the label would come out half its length. `bare` sends neither and stays the escape route, because the 550 generation's command set differs and nothing in a container can ask a firmware which commands it takes. **`ETB` run-compression is off, and turning it on is what shipped a printer that could not print.** A label is mostly white, so replacing each repeated blank line with one byte took a 375-line label from 31,886 bytes to 474 — of which about 370 were `ETB`, the one opcode in `protocol.py` written from memory rather than from something unambiguous. A firmware that does not read `0x17` as "repeat the previous line" gets a valid preamble and then 370 bytes it cannot use, and prints nothing: **there is no error to report, because the bytes were accepted** — the write returns its count, the status read answers, and the panel says `Printed 1 on the left roll`. The saving is real and it is three milliseconds of USB 2.0, which is not worth a guess. **`ESC B 0` (dot tab) IS sent, and the reasoning that kept it out was wrong.** It was called "a no-op by construction — the renderer already knows where the left edge is", which mistakes *our* state for the *printer's*: the manual says the dot tab and bytes-per-line "are held by the control electronics until they are changed by a new command sequence or are reset to default values by a power-on reset or a software reset". It is a value the printer keeps, not one we compute, so anything that ever set it — DYMO's own software on the same machine, another driver, an earlier job — leaves every later label starting that many bytes to the right. A preamble states where the line begins rather than inheriting a stranger's answer; `bare` still drops it, because that mode exists to send the minimum. Both live behind the `print_mode` setting (`standard` / `compact` / `bare`), which exists because whether a given firmware accepts every command in the preamble is not something an add-on in a container can find out — and a printer that takes a job and prints nothing is otherwise a guessing game played one release at a time. The test that was supposed to hold this asserted the compression *happens*; what replaces it walks a finished job the way a printer would, knowing only `SYN` and the escape commands, and fails on any byte such a reader cannot use.
- **Read the manual. Three of this file's bytes were written from memory and all three were wrong.** `ETB` was the first and shipped a printer that could not print; `ESC L` and `ESC q` were the other two, found together only once DYMO's *LabelWriter 450 Series Technical Reference* was actually extracted and read rather than recalled. **`ESC L` is not a length**: "nl, n2 = number of dot lines **from sense hole to sense hole**… this command indicates the **maximum distance the printer should travel while searching for the top-of-form hole or mark**. **Print lines and lines fed both count towards this total**." It is a search budget measured hole to hole, and this add-on sent the height of its own raster — wrong twice, because hole-to-hole is the label *pitch* (the label plus the inter-label gap) and because printed lines are charged against the budget, so a full label exhausted the whole allowance exactly where the artwork ended, short of the hole it was meant to reach. The search gave up early on every label and the error accumulated down the roll, which is what a person sees as "the alignment is off". It carries headroom now (a fraction of the label with a floor, because the gap is not in the catalog and nothing here can measure it; over-long is free on marked stock because the hole re-syncs the counter, which is why DYMO's own power-up default is 3058 = 10.2"), and it is expressed in dot lines **at the current mode**, so it scales with the graphics-mode doubling exactly as the raster does. **Continuous stock got the mechanism the manual gives it**: a negative two-byte length (`0x8000`–`0xFFFF`) selects continuous-form mode, where `ESC E` feeds far enough to clear the tear bar — never sent before, so the shipped continuous stock was wrong in a second way; and because `0xFFFF` is now a *mode*, the positive clamp moved to `0x7FFF` so a mistyped measurement cannot put a printer into continuous feed by accident. **`ESC q` takes an ASCII digit**, not a binary one: the manual spells out "30 (ASCII '0') = Automatic selection, 31 (ASCII '1') = Left roll, 32 (ASCII '2') = Right roll", and the fact that it spells the encoding out *at all* — where `ESC D n` is documented as plainly "1 <= n <= 84" — is the author flagging the exception. We sent binary 1 and 2, so on a Twin Turbo roll select may have been a no-op, which with two different stocks loaded means labels on the wrong-size roll and reads as bad alignment. `ROLL_LEFT`/`ROLL_RIGHT` stay the panel's vocabulary and the translation happens at the wire. `ROLL_WIRE_AUTO` is documented and deliberately wired to nothing: the printer "assumes that both rolls have the same media and will toggle back and forth as rolls become empty", which is precisely the 2.25"-raster-onto-a-0.56"-roll accident the stock check exists to prevent. What the manual **confirmed correct**: the graphics mode "steps half as far when printing each dot line", so sending every line twice is right; 84 bytes per line is 672 dots, "the number of dots in the print head"; and the density commands.
- **Four knobs could not answer where the printing starts, and the printer had already written the answer down.** The third report of "they aren't aligned" was the first one measured, and the measurement is why this is a feature rather than a fourth guess: a ruler printed through the real renderer and the real printer came out 672 × 375 dots with its ink inset **exactly 24 dots on all four sides**, and the photograph — deskewed against the printed ruler's own 5mm ticks, the one scale in the picture that cannot be wrong — read 18.26 px/mm across and 18.36 down against a die cut at 18.32 and 18.20. The renderer and the wire bytes were **proved correct before anything was changed**. What was left was one number: top margin 9.9mm where it should have been 5.2, bottom 0.3mm — the printer begins laying ink **4.7mm after the leading edge**, every label, with the last 4.7mm of the raster running off the end into the gap. 0.6.0 answered that with a signed feed and across offset, 0.7.0 added a lateral media position and a die-cut gap beside them, and 0.8.x had four boxes with four signs and four meanings and no way for a person holding a wrong label to tell which one was theirs. The owner printed, measured, typed, printed again, and asked for them to go. **They were right, and `gap_mm` is what proved it**: it was plumbed correctly, it changed the bytes, and it moved nothing — which is an answer and not a null result, because it means the printer *is* finding the sense hole on this roll and positioning every label relative to it. `ESC L` was only ever the maximum search distance the manual says it is. Three primary sources settle the rest: the manual's top of form is "the inter-label gap over the cutter bar", **beyond the head**, and a form feed "places the next label beyond the starting print position. Therefore, a reverse-feed will be automatically invoked when printing on the next label"; DYMO's own CUPS driver sends 156 `ESC` bytes as a reset, `ESC q` once per *document*, `ESC L` as the exact page height, blank rows as `ESC f` skips, `ESC G` per page and `ESC E` per document; and DYMO's PPD for the 2¼″ × 1¼″ label declares 1.5mm unprintable at each feed end. So a 4.7mm band is not firmware behaviour on DYMO stock — it is **this roll's hole sitting where DYMO's does not** (every label starts late, and no command reverses paper) or **the reverse feed after a tear-off not happening** (the first label of a job and nothing after it), and only a two-copy print tells them apart. Nothing typed into a box can.
- **So the four knobs are one `Calibration`, and every field on it is measured** (`panel/calibration.py`, `stores/stock.py`). Six numbers read off two printed labels — where the label's left and right edges cut an across ladder drawn head dot 0 outwards, and where each copy's leading and trailing die cuts fall on the feed ladder — and `derive` is pure, with **one branch per HYPOTHESIS and not per symptom**, because the three are identical from a photograph and only the arithmetic separates them. The same start on both copies is a dead band the layout is drawn inside (`dead_leading_mm` / `printable_feed_mm`); a level copy 2 with a late copy 1 is the missing reverse feed, answered by a second print opened with `ESC @` ("sets top-of-form as true") and otherwise recorded as `after_tear_mm`, charged to the first copy of a job and only when `at_tear_off` says the paper is there; a drift between the copies is the hole not being found at all, and the drift measures the pitch that makes `ESC L` exact. Two of those **store nothing** until a second print settles them — a half-answer on disk is a roll calibrated by a guess, which is the thing this replaced. **The two signs are read from different ends, and the first cut of this had it backwards.** Nothing can print before where the printer begins, so a LATE start leaves a blank band at the top of the label with the ladder's own 0 and its heavy bar at the bottom of it and nothing inside the band to measure it with: the top reading is **0** — a reading, not a missing one — and the size comes from the trailing die cut falling short of the label's catalogued length. An EARLY start is the directly measurable one, because its rows land before the leading die cut and that die cut cuts the ladder; both cuts are then on the ladder, so `D − C` is the label's real length (`length_mm` is measurable there and nowhere else, and a late roll's length is confirmed by the check label instead). A **5mm pre-skip** was added on the theory that it made a negative start measurable and it did the opposite — the skip pushes the ladder's 0 further down a band that is blank either way, so both signs read 0 at the top and the one number that separated them was the one nothing printed; it also lengthened the sheet past one label, which lands copy 1's tail on copy 2's leading edge, where the second copy's top is read. The job feeds nothing now, and `MAX_LATE_MM` is the floor the new rule owes: a late start is derived FROM the catalogued length, so past any plausible registration fault the likelier answer is a roll that is not the length its stock row says, and that is what it says. **The correction is a shorter sheet, never a shift** — `crop_leading` drops the rows the printer will not lay, so the first row sent is the first that can carry ink and the last still lands at the die cut; `ESC f` is one-directional and can only answer the other sign, which is why it is what an EARLY roll's job feeds and never what a late one's corrects. `ESC B n` is the same shape on the across axis. All of it is applied in `_send` and nowhere else, so the document, the preview and the designer show the label somebody drew — the designer *draws* the band instead (hatched, at the sheet's leading edge, turned by `LEAD_EDGE` exactly as `CLIP_EDGE` turns the clipped strip) and outlines any box lying in it, client-side, **never a refusal**: the stock/roll mismatch is still the only one. Ink lost to the crop is a note on lost ink and not on a non-zero crop, because a note on every print is a note nobody reads by the second roll. `Calibration.measured` is why "this printer needs no correction" is a different state from "nobody has asked" — seven default numbers otherwise read as never measured, and the panel would offer the wizard for ever to the person who least needs it. A roll nobody has lined up gets **byte-for-byte the job that shipped**, which is the promise every measurement here is added under and what `Forget` puts it back to; old rows migrate rather than being dropped (the two across numbers were always one edge, so they add; an offset that moved artwork back toward the leading edge described a printer starting late, so `start_mm` is its negation).
- **The instrument is a label and it was rebuilt once, from its own rendered bitmap.** `_calibration_label` is drawn to the **full print head** against a zero-margin copy of the stock with **none of the roll's own calibration applied** — a ladder that moved with the numbers it measures reads the same thing however wrong they are, so left alone it is absolute and printing it again after saving an answer is a check rather than a ritual. Its first version put the copy number and the across ruler in the top 14mm and started the feed numbers at 15, which is exactly the band the top reading is taken in on the roll it was built for (9.7mm) — so a 4.7mm dead zone would have been typed in as 10, and the across ruler's own "0 5 10" sat where somebody would look for a feed number. **An instrument that is unreadable where it is read is worse than no instrument**, because the wrong reading is stored and printed against for ever. Now one rule: the feed ladder owns the sheet from row 0, numbered every 5mm from 0, each number centred on its own tick so "the first number you can see, less one per short tick above it" is true rather than approximately true; everything else lives in the gaps *below* the reading band, and the across ruler is drawn **white on black** so it cannot be read as a feed number. The column period is set by the narrowest stock in the catalog (`period <= width - column`, so a window as wide as the paper always holds a whole column), and every one of those constraints is asserted off the rendered bitmap rather than described. The **check label** is the opposite and has to be: a 1mm frame around whatever the calibration says is printable, sent through the ordinary path with the same crop and the same lateral placement, so a complete frame is the answer being right and a missing side says which way it is out. It is drawn at the canvas's own 0,0 and to the canvas's own size now — it used to add the dead band back in by hand and subtract the held one at the other end, and both are inside `printable_box`. Two prints, because a measurement nobody can check is a measurement nobody can correct.
- **One control per bay, and it prints** (`lineUpBlock` / `lineUpDialog` in `app.js`). Where the printing starts is a property of a **roll**, not of a printer and not of a catalog row, so the button lives on the bay: a fourth button on the printer card would have to ask which bay it meant, which is the question the bay has already answered by being the bay, and the stock Edit dialog offers no route to it at all. Each bay carries the sentence `calibrationSentence` builds off the stored numbers — `Not lined up yet` is deliberately a different sentence from `Lined up: prints from the die cut`, which is `Calibration.measured` showing through — plus `Print a check label`, and `Forget` **only where there is something to forget**, because a button that clears nothing is a control asking to be understood. `Feed` renders only for a roll whose calibration ends `hold`. The wizard is three steps in the panel's one `#modal`: print, type what you see, done. Its drawing is **inline SVG built in JS** rather than an asset, for the same reason nothing else here is one — a picture of the calibration label in the container is a second copy of what that label looks like, and it goes stale the day the ladder moves; the six read points carry badges A–F and the same badge rides on the box that takes each number, which is what ties the picture to the form on a phone where they cannot sit side by side. **Nothing here does arithmetic on a reading**: what is typed goes to the server as it was typed (an empty box as `null` and never as `Number('')`'s zero, because the derivation branches on differences under a millimetre and a silent zero is a different hypothesis), and every sentence a person reads afterwards is `derive`'s own. Both endings that store nothing are handled where they happen — a `next` variant re-prints with the reset and comes back to the same six boxes prefilled, an impossible set of readings re-renders the step with the reason above it — because a wizard that closed on a refusal would be a person starting again. `bruh_print.print_test` keeps its service id and prints the check label: a service that vanishes turns an automation written last week into a validation error, which is worse than a name one release behind what it prints.
- **The question is where the printable area is, and every release up to 0.9.1 asked it as an OFFSET** (`panel/calibration.py`, `server._calibration_label`). That is the failure under all of them, and it survived two rewrites that were each about the right thing. 0.6.0–0.8.x answered a misaligned label by adding a box to type a millimetre into until there were four with four signs; 0.9.0 replaced them with one measured `Calibration`; 0.9.1 rewrote the instructions for reading it. None of them changed the shape of the question, which was *how far is raster row 0 from the die cut, and which way* — **and a distance-with-a-direction is not a thing drawn on a label**. It has to be inferred, from which end of a ladder got cut and from one copy compared against another, and the sign is exactly the part nobody can see. Hence three hypotheses that are identical from a photograph, six readings, two prints, and two of the six read from the opposite end of the label to the thing they were about. No wording could reach it: the instructions were vague because the question was.
- **A rectangle IS drawn on a label, so print a grid over the whole printable area and read the four coordinates of the paper on it.** `X1`/`X2` across, `Y1`/`Y2` down; the printable area of a label on this printer, in the printer's own axes, is that rectangle, and everything the print path needs is arithmetic on it — `across_mm` is `X1`, the length is `Y2 − Y1`, and where the printing starts is `Y1`, **signed by which side of the grid's own zero the top edge landed on rather than by anything a person decides**. The stored `Calibration` and the whole send path are unchanged, which is the measure of how much of this was the question rather than the answer. **The one thing the grid cannot show costs nothing**: nothing prints before row 0, so a printer starting *after* the die cut has the label's leading edge above the grid and `Y1` reads 0 — which is not an exception to be explained but what reading a coordinate off a scale does at the end of the scale, and it is also the useful answer, because the printable area starts at the first row that can carry ink. The dead band is `catalog − (Y2 − Y1)`, derived and reported; 0.9.x asked for it directly and could not have it, that being the one region of the label with nothing printed in it. `length_mm` is measurable only where `Y1` is non-zero, and stored only where it disagrees with the row.
- **The sheet is ONE label and longer than the label, and the overrun is the instrument** (`CAL_OVERRUN_MM`). A sheet exactly one label long begins at the die cut, which is what made the leading edge unreadable; running past the trailing die cut is what puts it on a scale instead of leaving it to be inferred. The across bands repeat every 15mm rather than 0.9.x's pair-then-every-30, because **an across coordinate is read AT a vertical edge** and a 4" shipping label had its whole middle with no across scale on it; 15 is a multiple of the feed numbering step, so every band lands in the same gap between two feed numbers. The copy number went with the second copy. **What this deliberately stops measuring is `after_tear_mm` and `gap_mm`** — both needed two printed copies compared against each other, neither has ever been confirmed on a real printer (`gap_mm` was plumbed correctly, changed the bytes and moved nothing, which is the measurement proving this printer *does* find the sense hole), and chasing them is what made the wizard unusable. Both fields stay on `Calibration` so a roll measured under 0.9.x keeps them and the print path is untouched; nothing sets them any more.
- **Lining a roll up is a LOOP, and 0.10.0 shipped it as a form.** The only route from a wrong reading back to a printed label was to close the dialog, find the bay, press a button on the card and re-open the wizard to an EMPTY form — so a millimetre out meant reading all four coordinates again. Both prints are at the top of the step that reads them now (`calPrintRow`), neither leaves the step, and the done step has a way back. **The prefill is the half that needed proving**: `calStoredReadings` reconstructs three of the four from the stored answer — X1 *is* `across_mm`, Y1 is 0 for a late roll and `-start_mm` for an early one, Y2 is the catalogued length less the dead band or Y1 plus the measured one — and re-applying them is a **fixed point**, measured over four passes for every shape a roll can be in, which is what makes changing ONE number a small adjustment rather than a re-measurement. That is not free and is why the display rounds to a tenth: a reading is a tenth, `start_mm` is `catalog − Y2` and carries two, and showing back a number nobody could have read off the scale is what would make each visit move it. X2 is the one that cannot come back and that is not an oversight — it sets **nothing** on a `Calibration`, being read to say whether the roll measures what its stock row claims, so an empty box is the honest answer. A roll calibrated by an older release settles on its nearest tenth at the first Apply, which is under one dot of the head.
- **A printable area somebody CHOSE is a different claim from the paper's edges, and one field could not hold both** (`Calibration.holds()`). Typing a short `Y2` to shrink the area was refused past `MAX_LATE_MM` — and the refusal was the *visible* half. The quiet half is worse: `Y2` is where the paper's bottom edge falls, so pulling it in is read as a printer starting further in, `start_mm` grows, the crop grows with it, and the artwork comes out the right SIZE in the wrong PLACE on every label with nothing on screen saying so. Relaxing the bound would have made that reachable rather than fixing it. So the choice gets its own fields, its own heading and a rule across it, and the readings keep their meaning. **0.11.0 shipped ONE of them — the trailing band — and the argument for that was wrong in a way worth writing down**: it said the printer starts where it starts, so the only band worth having is the one that evens out a late start, and asking for more at the top would only push the artwork further from centre. True of the feed axis, and it answers the wrong question — a person setting a border is saying where on the label the printing goes, not compensating for a machine, and the across axis has no dead band to compensate for at all. There are four (`hold_leading_mm`/`hold_trailing_mm`/`hold_left_mm`/`hold_right_mm`), `margin_mm` remains the EVEN border on all four sides and this is the uneven one, and **the cap is per AXIS** because the two bands on one share the label between them: 20mm at each end of a 31.75mm label is one pair that does not fit, and `_clamp_holds` **scales it evenly rather than truncating whichever came second**, since the commonest reason to set two at once is to centre something. **Evening the ends up is an ADDITION and lives in one place** (`evenTrailing`): the top of a label loses the dead band *and* whatever is held at the top, so a button that typed the dead band alone left them uneven on exactly the roll somebody had set a top band on — and there are two such buttons, on the reading step and on the done step, which is the kind of disagreement nobody would think to look for. It is passed to `derive` as an argument rather than a fifth reading, floored, capped with the cut-down SAID **naming what was asked for as well as what it became** (a note carrying only the new value leaves somebody re-typing the same 99 to find out why it did not take), dropped by `swapped()` because the swap changes which physical dimension the feed axis is, and the plausibility refusals name it.
- **One rectangle, and the designer draws it rather than drawing around it** (`Stock.printable_box`). Four things used to be drawn on the canvas to aim away from — the stock's own `margin_mm` as a tinted band, a dashed rectangle inside it, a hatched strip where a 2.25" label overhangs a 2.24" head, and a hatched band at the leading edge this roll cannot reach — plus the held band beside it. Each was honest and each asked the same thing of a person: lay a label out, then move it off the parts that were never yours. They are **four insets on one box** now (the margin, the dead band, the head's shortfall, the four holds), `render` lays the canvas inside it and pastes it onto the sheet, and `Rendered.png(box=)` crops the designer's preview to it — **cropped BEFORE the turn**, because the box is in sheet coordinates and the turn is what leaves them. So the picture IS the canvas: everything on it prints, and there is nothing left to warn about. **The head's shortfall stopped being a NOTE**, which is the shape of answer that tells somebody about a region after they have laid artwork into it. **It also removed an offset rather than fixing one**: the drag overlay's millimetres have always been the canvas's while the image under them was the whole sheet, so every box was offset by the margin in five places in `app.js` — a millimetre of drift that only showed on the smallest labels. **Nothing is left under the canvas.** A caption survived that removal for two releases — `Drawing on 34 × 12.4mm of a 50.8 × 25.4mm label` — and it was the same shape of answer one layer up: two measurements with no relationship between them, where what makes them differ is a margin, a lined-up roll and any held edges, none of which is on that tab. So it could only raise the question it could not answer, on a line read every time the designer opens. The picture is the printable area, which is what the caption was there to say. **The crop and the box cancel on the wire**: the canvas begins below the dead band and the first rows of the sheet are cut off the front, so calibrating a roll no longer moves anybody's ink and the "ink lost to the crop" note is unreachable except on the after-tear path. **A box on a raster is two EDGES and each is rounded once** — rounding the left edge and the width separately left a 2mm border coming out 24 dots on one side of the 0.56" wrap and 23 on the other — so the width is the difference between two rounded edges. And the box rides on `Rendered` (`box_dots`) rather than being re-derived by the route that crops: on continuous stock the sheet's length is the artwork's rather than the stock row's, so a second computation would agree on every die-cut label and quietly disagree on those. `printable_feed_mm` and `drawable_mm` are the box's size, which means they now carry the margin too — they used to be the label less the dead band, and one name for two areas is how the designer's canvas and the check label's frame drift apart.
- **Which label you are drawing on is the paper, not a setting, and it is a BUTTON because a `<select>` measurably could not fit.** It decides the canvas, the direction the text runs and which boxes are off the edge, so burying it in `⋯ Label setup` had somebody opening the sheet three times a session. Moving it back to the bar is where the width trap that put it there bites: `width: auto` sizes a select to its widest option and the names run to `2.25" × 1.25" — Chemical-Resistant Cryo Labels`, so capped to 116px it still laid out at **164px** — and with `⋯` beside it the add strip, the primary control on that tab, came out **32px wide with its own buttons rendering underneath the picker**, where a click on one hits the picker and times out on a control that is there and covered. `setStockButton`/`openStockPicker` are the font picker's own pattern one control over: the button shows what the roll is CALLED, capped, and the dialog holds the sizes. `.design-bar` **wraps** and `.addbar` carries a `min-width` rather than `0`, because a floor of 0 lets the strip shrink to nothing and keeps the row one row — the failure is then a sliver nobody measured rather than a wrap a test can see. Two rows on a phone costs the canvas 40px (254 → 294, and 306 with an element on the label) and the desktop shape is unchanged at 900 and 1440; `CANVAS_TOP_MAX` moved with the measurement rather than the measurement being trimmed to the budget. Stocks are named in ONE place (`stockOptionText`), because three copies of that join is three chances for two pickers to disagree.
- **A greyed-out example in an empty box is read as content.** The Quick tab's placeholder was `Chest freezer — chili`, chosen to show the autofit breaking a phrase across two lines, and what it did was have somebody ask why their label said chest freezer — on the one box in the panel whose emptiness must not need explaining. It is `Enter label text here...`, on the panel and on the Lovelace card together, because they are one control in two places and two prompts for one thing is how they drift.
- **One picture, where 0.9.1 needed two.** The map of six read points plus a second figure for the two procedures the top reading was are one drawing: the label lies on the grid and its four edges are read off it. It is drawn **overlapping the top of the grid**, because that is the ordinary roll and a picture that put the label tidily inside would show the rarer case and leave the common one to prose. And the label is an **outline** rather than a fill (`.calpaper`): a filled one hides the marks the readings are taken from, and the black strip — the one thing `X1` and `X2` are read against — would be visible only on the parts of the sheet that miss the paper. `CAL_HOLDING` keeps 0.9.1's three things a person cannot get off the paper, with "which of the two labels" replaced by "which of the two scales" now that there is one sheet.
- **The head is 672 dots whatever is loaded, and nothing knew where narrow media sits on it.** A solid fill on the 0.56" wrap printed across **49% of the label** — measured off the photograph, 335 inked pixels of a 687-pixel label, ink starting 0.7mm in from one edge and stopping dead — while the 2.25" stock was perfect. `pack_line` pads a short line on the RIGHT, so a rendered sheet always lands flush against head dot 0: invisible for a 672-dot raster that covers the whole head, and half a label for a 168-dot one that is a quarter of it, because `printers.py` knew `dots`, `bytes_per_line` and `dpi` and nothing at all about lateral media position. **And the 0.6.0 across offset could not express the fix, which is why the reporter's "I try and try and it doesn't do anything" was exactly right**: `offset_raster` shifted artwork *within* the sheet, and the sheet here is 168 dots — pushing right only shoved ink off that sheet's own edge, and could never move the sheet further along the head. That is why the two were separate numbers, and why they are now **one**: there is a single left edge, and `calibration.across_mm` is where it sits on the head — read off the calibration label's across ladder rather than typed, which is what makes the two impossible to confuse. `place_on_head` applies it in `_send` and nowhere else, and ink pushed past the head's last dot is a note rather than the silent truncation `pack_line` used to justify by a renderer that could no longer guarantee it. **The old calibration label could not measure this either, structurally** — it drew to the *sheet*, and every mark it made was inside the 168 dots whose position is the question — so the one that replaced it is drawn to the whole print head by construction, and the part that misses the paper prints on the liner, which is what a calibration pass across a head does.
- **Printing is a service call, and the card gated it on the sensors** — which is how 0.4.0's "say what is missing" block turned into a card that could not print at all. `bruh_print.print_text` exists whenever the integration is loaded, whatever the entities are called, so a renamed device, a renamed entity or a second config entry (whose ids all carry `_2`) disabled Print on a working printer. Two different questions, asked separately now: **the service decides whether Print works** (`hass.services`, failing open on anything that is not a map — a diagnosis may never become a gate, the same rule `_local_is_served` follows) and **the sensors decide only whether status can be shown**, which is a readout that never disables anything and names the `printer_entity`/`left_roll_entity`/`right_roll_entity` options that point the card at renamed ones. Those options existed in `_find` from the first release and were documented nowhere. **And the card announced prints it was never told about**: `answer.printed || data.copies || 1` over `result?.response || {}` meant a call that came back with nothing to say rendered as `Printed 1` — driven against the shipped card, the add-on answering `printed: 0` with the note "The printer did not answer." produced **`Printed 1. The printer did not answer.`** in green. A print nobody confirmed is its own sentence, not a success with a number invented for it. Twenty-one of these were reproduced as failures against the shipped card before anything was changed, which is the only reason to believe the tests hold them.
- **Every copy but the last gets the SHORT form feed.** A long feed between copies advances a whole label past the head, so a run of ten came out as ten printed and ten blank — the printer wasting half the roll, because it was. The preamble is re-sent per copy for seven bytes, so a label after a power cycle or another process's job starts from a known state.
- **A printer that is not in the table is driven, not refused.** Matching is on DYMO's vendor id alone; an unrecognised model gets the 450's geometry and the twin flag is read from the device's own product string, so a Twin Turbo with a new product id keeps its second roll. Guessing narrow prints with margin to spare, guessing wide prints onto the other roll's liner — and guessing `twin: True` would put a roll switch in the panel that does nothing, which is worse than a missing one. A saved printer is keyed on its **serial**, not its bus address, so a reboot that renumbers the bus is still the same printer.
- **A LabelWriter cannot tell you what is loaded, so `stores/loaded.py` is what remembers.** This is the feature, not the bookkeeping: sending a 2.25″-wide raster to a 0.56″ roll prints across the liner, once per copy, with no error anywhere — a run of fifty ruins fifty labels. So a stock/roll mismatch is the one thing a print is refused for (409, naming both stocks), and everything else that could be wrong — a barcode that will not fit, a fixed font size that clips, an element type a release retired — comes back as a **note** beside a label that still prints. A refusal is always a person unable to work. The remaining count is an **estimate** and says so everywhere it appears, because nothing on a LabelWriter reports a real level.
- **A stock is two measurements and they are not interchangeable.** `across_in` lies across the print head, `feed_in` travels past it, and getting them the wrong way round is the single most common way a label comes out rotated with the text off the edge. Nothing can work it out for you — the printer feeds to the next die-cut gap and has no idea what shape the label was — so `swap()` is one press. **The ruler that used to answer it is gone**: it drew millimetre ticks *inside the stock's own margin*, so on a roll somebody had given a 5mm border there was nothing within 5mm of the die cut to hold anything against — and lining a roll up measures both dimensions of the actual paper on its way past, so `_looks_transposed` offers the swap off a measurement rather than off somebody's eye. Offered and never applied, for the same reason: a stock row is somebody's. An edited built-in is saved as an override so a future release correcting one cannot undo somebody's own measurement.
- **The 450's head is 672 dots at 300dpi, which is 2.24″, and the cryo stock is 2.25″.** The three extra dot columns are clipped, not scaled away, and a note says so: scaling every element down half a percent to hide it makes a barcode's module width fractional, and that is the one thing that must not happen — a fractional module rounds each bar independently, so five 1.4-dot bars come out 1,1,2,1,2 and the scanner reads the wrong widths. Same rule for QR. A symbol that cannot fit at one whole dot per module is **reported**, never drawn smaller, because an unreadable barcode looks exactly like a readable one.
- **One rendering, two consumers.** `render.image.render()` is the only route from a label to dots; the preview PNG and `raster_lines()` are the same bitmap with different endings. A preview drawn a second way would look right while the label came out blank. Nothing is anti-aliased anywhere — a thermal head is one bit deep, so a 50% pixel is a black one and an anti-aliased hairline comes out solid. Text is supersampled 4× and thresholded, which is about *placement* (a 2mm glyph is 23 dots) rather than smoothness. **Ink is 1 and paper is 0**, and the flip from PIL's convention happens exactly once in `raster_lines`; per-element it is one element printed as its own negative.
- **The autofit is the product, and it chooses the arrangement, not just the size.** Every way of breaking the words across lines is rendered and the largest glyphs win — `Buffer A` is biggest on two lines and `9912` on one — because trying a single arrangement is what makes an autofit label look like it did not try, and people go back to the designer. It is exponential in the word count, so above eight words it falls back to greedy-per-line-count. `max_mm` exists because filling the label is not always the goal: a single `9` at thumb height reads as a mistake.
- **A template's fields come from the label, never from the request.** The placeholders in the document are the truth about what it needs; a declared field that no longer appears is a box on the form that fills nothing. Substitution is plain string replacement into `text`/`data` and nowhere else, with no expression language — a template that can evaluate is one that can be made to evaluate something else by whoever sends the automation payload, and the value of a label expression language is nearly zero against that. An empty field **refuses** through the API and **warns** in the panel, deliberately: the panel has somebody looking at the preview, and the API call is usually an automation about to print fifty labels with a hole in them.
- **The image element was never completable, which is why it is gone rather than finished.** The panel had no upload control anywhere — no file input, no `FormData`, no request to `POST /api/assets` — so the only UI the feature ever had was a `<select>` listing `/data/assets`, and `/data` is reachable from neither the Terminal, Samba nor the File Editor: those all see `/config`. The picker could only ever be empty on a real install, the only way to fill it was to already be inside the container, and the README and DOCS advertised uploaded images the whole time. A half-feature that cannot be finished is worse than no feature: an always-empty picker, a documented capability that does not exist, and a multipart upload, a size cap, a suffix allow-list, a path-escape guard and a Pillow decoder taking bytes off the wire, all serving nobody. **A retired type and an unknown type are different claims and only the second may refuse.** `Element.from_dict` refuses a type it does not know because rendering it as nothing would be a label silently missing its barcode — but letting `image` merely fall out of `CATALOG` would apply that to every saved label, history entry and `print_label` payload holding one, making the whole document unopenable over a box that could never have held a picture. `label.RETIRED` names what we took away, `Label.from_dict` drops it and puts the reason on the label's notes, and an unknown type goes on refusing exactly as before; the filter is at the *Label* level because an element cannot express "drop me" — it returns one or it raises. Nothing on disk is touched: `/data/assets` is somebody's files, and an add-on that tidies up after itself unasked is an add-on that loses data.
- **The panel runs as root and the bridge does not.** There is no udev in the container, so `/dev/bus/usb` is the host's device tree bind-mounted in and its nodes carry the host's root:root ownership — a process at UID 1000 cannot open them for writing. The alternatives are worse: chmod-ing the tree writes to the host's real device inodes and still misses a printer plugged in afterwards, and a setuid helper is a setuid binary to get right. The cost is bounded — no port is published, ingress is authenticated, and `panel_admin: true` means the caller already holds the Supervisor API. The bridge, which reads files written from outside the container and never touches USB, stays at UID 1000. `usb: true` only takes effect on a **restart** after it is granted, which is the most common "cannot see my printer", so `usb_link` words that failure as a restart rather than as a permissions error.
- **You pick the label; the add-on remembers which roll it is in.** A roll is not a thing anybody wants to choose — it is where a label happens to be, and `loaded.py` already knows. So there is no roll picker on the Quick tab, in the designer, on a template row, on the card, or in the four print services: naming the stock has already named the bay, and two ways to say where a label goes is one way to contradict the other. The services still *accept* `side` quietly, because a field vanishing from a schema turns an automation written last week into a validation error — a worse outcome than an argument nobody is offered; `set_roll` keeps it visibly, since saying what is loaded is a statement about a bay by definition.
- **Only what is loaded can be picked, and the Printer tab is the exception that makes it work.** The catalog is fourteen stocks of which two are in the printer, so offering all of them on the Quick tab made the commonest first action a choice between twelve wrong answers followed by a refusal for picking one. `loadedStocks()` is what every picker outside the Printer tab reads, and `loaded`/`loaded_side` ride on the stock row rather than being joined in the panel — three copies of that join is three chances to disagree about what is in the printer. A printer with nothing recorded falls back to the whole catalog: an empty picker is a panel that looks broken, and somebody who has not filled the tab in yet still wants to print.
- **Which way text sits on a label belongs to the STOCK, not the job, and it is asked in ONE place** (`Stock.natural_turn`, the Printer tab's **Text direction**). A 0.56 × 3.44 cryo wrap reads along the roll and a 2.25 × 1.25 label reads across it, always — so asking on every print is asking a question whose answer never changes. It was nonetheless asked in three places for a release: the per-stock picker, a `Turn` select on the Quick tab and another in the design bar, plus a `Swap to 1.25" × 2.25"` button — and the person using it said, correctly, that they did not understand any of them. The Quick tab and the designer now *say* what will happen (`Text runs along the roll (change it on the Printer tab)`) and offer no control; a new label takes the stock's `turn` as its `rotate` and a saved label keeps its own, because a saved layout is somebody's work and the direction is the roll's property. `turn: None` means "derived from the shape" and a number means somebody corrected it; the two are a different state on purpose, and `swapped()` deliberately drops an override back to `None` because the shape is what the derivation reads. The ratio is 1.6 rather than 1.0 because a stock only slightly taller than it is wide reads the ordinary way round. **"Automatic" says what it decided** in the closed picker (`Text direction: automatic — along the roll`), because a setting you cannot check without printing one is a setting people override blindly. Swap lives in the stock's **Edit** dialog as `These are the wrong way round`, beside the two measurements labelled in words — and `h_stock_put` carries over what the dialog does not show (`turn`, `notes`), or a Save there would undo a correction made one control away. An element's own `rotate` is a different thing (the box's contents, within the label) and the designer's ⟳ Rotate is what sets it, for the types that have one — read off the catalog, not a list in the panel.
- **The remaining count is a control, not a readout, and it is optional.** It is an estimate — nothing on a LabelWriter reports a real level — so it drifts the moment somebody prints from another machine, and a number you can see and cannot correct is a number you stop reading: the bar IS the button. `track_remaining` turns the whole thing off, and the decrement goes through `Panel.consume` rather than the store directly, because five call sites asking separately is five chances for a new print path to keep counting a number the panel has stopped showing — and a hidden count that goes on moving is worse than none, since turning it back on reveals a number that has been quietly wrong for a month. The gauge is a `<button>` wrapping a 6px track rather than a styled 6px bar, so the target is a real 40px; `.strow .turnpick` sets no font-size, because a smaller one there would beat the touch floor on specificity — the `.btn.tiny` bug one selector over.
- **A control that needs a tooltip to have a purpose gets a name instead.** "Check it" and "Swap" were both verbs with no object. "Check it" is **Ask the printer** (and its tooltip says it prints nothing); Swap became `Swap to 1.25" × 2.25"`, which named the numbers and still explained nothing — a person reading it asked what the whole across/along business was for — so it is now a sentence in the Edit dialog, `These are the wrong way round`, under the two measurements labelled in words, where the thing it exchanges is on screen. **In use** is disabled when there is only one printer, because a toggle that cannot be toggled is a control asking to be understood.
- **`config[(0, 0)]` is not "the printer's interface", and hardcoding it took the read channel away.** The USB printer class defines two protocols and devices routinely expose both as ALTSETTINGS of one interface: `01` unidirectional (bulk OUT only) and `02` bidirectional (OUT and IN). Altsetting 0 is very often the unidirectional one, so `Ask the printer` could only ever answer that it had nothing to report — there was no endpoint to read from, and the printer was fine. `_pick_interface` walks every interface and altsetting, prefers one with both directions, falls back to one that can at least print, and **reports which it chose**, because a choice nobody can check is a choice nobody can correct: this one was wrong for two releases with no way to see it. Note what it is NOT: a printing fix. A unidirectional altsetting prints perfectly well.
- **Two silences, two sentences.** "No status reported" meant both *the printer did not answer* and *there is no channel to ask on*, so somebody read it and went to check hardware that was working. `Status.unreadable` splits them; only the second is about the printer, and neither is ever rendered as ready. Same rule as a house check that could not look versus one that found nothing.
- **The descriptors are always readable, even from a device that answers nothing** — which is why there is a **USB details** button. This add-on has now been debugged twice by somebody standing at a printer reading a panel that could not say what it had found, and both times the missing information was in the descriptors the whole while.
- **It prints labels for a house, and it was written for a bench.** Every placeholder was `Buffer A pH 7.4`, the sample template was a "Cryo vial" with a "Sample id" field, the docs talked about reagent names. That is not a small thing: the examples are the first sentence anybody reads about what a tool is for, and lab vocabulary tells a person putting a name on a storage box that they are holding somebody else's tool. It is a chest freezer, a freezer bag, spare keys and a pantry jar now. The two stock NAMES stay — "Chemical-Resistant Cryo Labels" is what is printed on the roll and what you reorder by, and renaming somebody's stock to sound friendlier is a different and worse mistake.
- **`ingress_port` is pinned here and dynamic in BRight, for the same reason.** BRight needs `host_network` for LIFX discovery, which makes its port a real host port somebody else may own; a LabelWriter is on USB, so this add-on's port lives in its own namespace, cannot collide, and `config.yaml` can name it in a `watchdog:` URL.
- **The Lovelace card reads the sensors and calls the services, and never the panel.** It runs in whoever's browser is looking at the dashboard, which may be a phone on mobile data through Nabu Casa — it has no route to the ingress port and no business having one. It is plain custom elements with no build step and no imports: a card that needs a bundler cannot ship inside an add-on image, and one that pulls LitElement off a CDN breaks the day the CDN is unreachable. It re-renders only when something it displays has moved, because `hass` is set on every state change in the house and a rebuild mid-word takes the cursor out of the text box.
- **Every URL the panel emits is relative, because ingress mounts it under a prefix.** Home Assistant serves an add-on panel at `/api/hassio_ingress/<token>/`, so an absolute `/style.css` is a request to *Home Assistant's* root. 0.1.1 shipped three absolute asset references and twenty-odd absolute `fetch` calls, which reached a real install as unstyled HTML with all five views stacked down the page and every preview a broken image — the CSS, the JS and the whole API 404ing together. `api()` strips the leading slash the way brAIn's does; that convention was already in the repo and reading it was the whole job. **Serving at `/` is the one arrangement in which the bug is invisible**, and it is the arrangement the demo panel and `measure-print-panel.mjs` used — so both now mount the panel under a prefix, and the measure asks whether the CSS and the JS *arrived* before it drives anything, because a page whose stylesheet 404s still lays out and every click then times out on a control that was never built, which reads as a flaky selector rather than as "the panel did not load".
- **The panel serves four named files, never a directory.** `add_static("/static/", PANEL_DIR)` answered `GET /static/server.py` with this file, and every module under `stores/` and `dymo/` with itself. Nothing in there is a secret and the panel is admin-only behind ingress, so nothing leaked that matters — but an add-on serving its own source tree is a mistake waiting to become one, and the name at each call site is a literal rather than anything off the wire.
- **`build_app` is not `main`, and 0.1.0 shipped a panel that could not start.** Every route had a test, every width had a measure, and the add-on bound its port, logged `listening on 0.0.0.0:8097` and died on the next line: `run_app` type-checks `access_log_class` and `QuietAccessLogger` was a plain class with a duck-typed `log`. Nothing caught it because nothing ever handed the class to aiohttp — the tests constructed it directly (with one argument, where `AbstractAccessLogger.__init__` takes two and `log_format` has no default) and the demo panel CI boots called `run_app` without an access logger at all. The demo now serves exactly the way `main()` does, which is the actual guard; the test that reproduces it drives `AppRunner.setup()`, because the `issubclass` check lives in `Application._make_handler` and a synchronous `AppRunner(...)` construction passes against the broken code. **A test that constructs a collaborator itself is a test of the constructor it wrote, not of the one the framework calls.**
- **Nothing says it is listening above the call that would make it so.** That line printed whether or not the server came up, so the one log anybody would read said `listening on 0.0.0.0:8097` directly above the traceback proving it was not — which is BRight's `panel_port` bullet word for word, repeated in a new add-on by writing the obvious line in the obvious place. It is the callback `run_app` invokes once every site is up; what precedes the call says `Starting`.
- **`usb: true` is a manifest permission, not a setting, and four places told people to go and find it.** The Supervisor maps the host's USB device tree in when it creates the container; the Configuration tab has no switch and never did. The README, DOCS.md, run.sh's startup warning and `usb_link`'s own "may not open it" message all said some version of "enable USB access and restart" — confidently specific about a place to look that does not exist, which is worse than saying nothing. They name the power brick, the cable and a CUPS add-on holding the printer now, and `test_bruh_print_addon` greps all four for the old claims, because the wrong sentence is what gets copied into the next release note.
- **Four CSS failures here were all invisible to reading and obvious to measuring**, which is what `tests/manual/measure-print-panel.mjs` exists for. `[hidden]` is a UA rule at the lowest specificity, so `.toast { display: flex }` beat it and left an empty black bar across the bottom of the panel. The touch-floor block sat *above* `.btn.tiny` in the stylesheet and equal specificity is settled by order, so every small button stayed 32px on touch — it is the last block in the file now, and that position is load-bearing rather than tidy. A flex item's floor is its max-content, so the top bar's chips laid out 513px wide in a 390px window instead of wrapping. And `width: auto` sizes a `<select>` to its **widest option**, so the stock picker took the design tab's page-width with it.
- **A text box is fitted and placed by its INK, and the margin is 2mm.** `draw.textlength` is the advance width — where the *next* glyph starts, not where this one ends — and `(ascent+descent)*spacing` is the font's line box, which reserves room for ascenders and descenders the word may not have (DejaVu's is ~1.29em against a cap height of 0.73em). Fitting to those is how a word came out touching the edge *and* filling barely half its box at the same time — "kind of falling off edges". `_ink_extent` measures the block by `textbbox` for the fit (a cheap, true bound) and by `getmask2` for the placement (the bound carries the last glyph's right side bearing, which centred "Jam" six dots left), and `_text_extent` keeps its name because `fit_text`, the fixed-size check and `quick._measure` are one measurement with three consumers. Measured on "Rice" in a 40 × 12mm box: 0.60 of the height before, 0.96 after. `text_inset` takes 2% of the shorter side off every box *before* fitting, because a stem touching its box reads as clipped even when every dot is there. `DEFAULT_MARGIN_MM` is 2.0: a LabelWriter's registration wanders and the 450's head is three columns short of a 2.25" label, so 1mm was text at the die cut every other label. It is a default — a saved stock carries its own `margin_mm` and keeps it, which is what lets the default move without undoing anybody's measurement.
- **The designer previews the CANVAS, and everything else previews the sheet.** `render` turns the design canvas by `-rotate` on its way to the sheet, so the sheet of a 90° tube wrap is a tall strip with its words on their side — the right picture on the Quick and Templates tabs, and the wrong one under a drag overlay whose coordinates are the canvas's. For as long as the designer existed, a turned label put the box being held and the ink it described in two different places; latent while `rotate` was a select nobody touched, and reachable the moment every new label on a wrap stock took 90° from its stock. `POST /api/preview` takes `view: "canvas"` and `Rendered.png(turn=)` rotates the finished sheet back by `+rotate` — the same bitmap, margins and clipping included, never a second render — and `X-Label-View` says which came back. `measure-print-panel.mjs` switches the design stock to the wrap and fails if the preview is taller than wide. **`select()` may not rebuild the overlay**: it did, so `begin()` called `setPointerCapture` on a node it had just detached (`InvalidStateError`), capture was lost, and a drag never worked from the first press; it toggles a class now, and the live preview during a drag calls `markProblems` rather than `drawOverlay` for the same reason. Snapping (drawable edges and centres, other boxes, then a 1mm grid — the grid ranked last and drawing no guide), the red outline from `X-Label-Problems` (collected by watching the notes list grow per element, so a new drawer cannot forget to report), and the align/nudge tools all live in `app.js`; the font picker's rows are `GET /api/font/{key}/sample.png`, drawn by `_draw_text` itself, because a CSS `font-family` preview shows the browser's idea of Monospace beside a label that prints in DejaVu Sans Mono.
- **The Lovelace card is registered under a URL that changes with the file** (`const.card_url`, a content hash), and for two releases that was a fix to the wrong layer. Core serves `/local` with `Cache-Control: max-age=2678400`, so hashing the URL is what makes an update reach a browser that has already cached one — but **`/local` is a route only if `/config/www` existed when Home Assistant STARTED** (one `os.path.isdir` in the frontend's setup), and `run.sh` creates `/config/www/bruh_print` when the *add-on* starts, which is afterwards. On a house that never had a `/config/www` — you only have one if you already installed a custom card or HACS — the whole prefix 404s, the dashboard says "Custom element doesn't exist", and restarting the add-on cannot fix it; only restarting Core can, once. `_register_card` checked that the *file* existed, which passes happily, so it registered a URL it had no reason to believe was reachable — the one thing its own docstring claimed to prevent, and a fix that could not work sitting on top of it. `_local_is_served` asks the running app's router (never a fetch: a request has to guess a base URL and cross a proxy, and can fail for half a dozen reasons that are not the question) and `_sync_local_issue` raises a repair naming the one restart, deleting it once the check passes. It **fails open on every path** — a diagnosis may never become a gate that stops a working card from registering. A hash of the *content* rather than of `CARD_VERSION`, because the version is what somebody remembers to bump; the version is nonetheless tested against `config.yaml`, so the console banner cannot lie.
- **Nothing had ever executed the card, which is why it shipped broken twice.** Every test it had was a grep of its source — the same failure `terminal_proxy`'s `pop` test is the canonical example of. `tests/manual/measure-print-card.mjs` loads the real file into a real browser behind a stubbed `hass` (only `ha-card` is stubbed) and drives it: the happy path renders and prints, Print sends a `stock` and **never** a `side`, the no-integration case says what is missing and disables Print, and nothing is under 44px. It was verified against the old behaviour first — reverting the trouble block produced fifteen failures — and it runs in CI's `layout` job. The card's own silence was the other half: with no integration it drew a text box, a Print button that failed with a service-call error, and a pill reading `ready`, and its one explanatory sentence lived *inside* the rolls block, so `show_rolls: false` turned off the only thing that could explain an empty card.
- **The panel was built at 1440px and used at 390px.** Measured on the demo panel at 390 x 780 — an iPhone once Home Assistant's own header has taken its share — the top bar was **247px, a third of the viewport, before any content**: a `.wordmark` duplicating the host header one row above it, three status chips totalling 497px in a 362px row (so they wrapped) that **all three called `show('printer')`**, and tabs on a second row. `.design-bar` was another 269px in five rows, putting the canvas at y=590 with 166px of height; on Quick the `.preview-frame` began at **y=899, below the fold**, on the one tab whose whole purpose is type, look, print. The wordmark is dropped below 700px, the three chips become the one control they always were, and `.topbar` takes a **negative sticky `top` of exactly the status row's measured height** (`syncBarHeight` -> `--barmain-h`, measured at runtime because whether the chips wrapped depends on width and content, and an over-estimate takes the tabs off the top) so the status scrolls away while the tab strip stays pinned. Chrome above content 247 -> 153px, pinned chrome 247 -> 96px, the design bar 269 -> 62px, the canvas top 590 -> 279, the Quick preview 899 -> 362. Quick is three grid items — say, **see**, do — with everything else behind one `<details>` whose summary names the nouns (`Label, copies, font - 2.25" x 1.25"`) so nobody has to hunt for the picker; it opens at boot above 900px so the desktop shape is unchanged. `measure-print-panel.mjs` carries the budgets as constants with the old numbers in the comment, measures the pinned chrome **after scrolling**, and gained a `phone-printer` run — no run had ever visited that tab narrow, which is how a 413px page in a 390px window survived: a `<select>` sized to its widest option was setting the row's min-content, and `.strow` needed `min-width: 0`, which is the same bug as the design tab's picker one selector over.
- **A control that is a mode does not deserve a slot on a phone's primary row, and `⌗ Snap` was both.** A hash glyph and a verb with no object — the person using it asked what it was, which is the whole test. It is `Line boxes up as I drag` in the label-setup sheet now, with the sentence that says what it does, because you set it once. `⟳ Rotate` moved the other way, into the props pane: it acts on the *selected element*, and every other per-element control already lived there (it sits with Duplicate and Delete — see the bullet on the three named rows). **Explanatory prose costs a row every time you look at the screen, not just the first time**, so every `.lede` was judged one at a time — deleted where the control beside it already said the same thing (Quick's duplicated its own h2, placeholder and fit line), shortened where it carried a single fact, and kept whole where the fact is available nowhere else (`A LabelWriter cannot tell what stock is in it` is why the feature exists). Deleting them is the sort of change that quietly comes back, so `TestPanelUI` asserts the deleted sentences stay deleted.

- **A word is what a tab is called, and five glyphs beside five words needed 485px.** Measured on the real strip: at 390px the five tabs came out on two rows and at 320px on three — a third of a phone screen spent on navigation, above a tab whose whole job is type, look, print. A glyph is 23px of that row (the icon plus its gap) and the only thing on a tab that says which tab it is, is its name, so **the glyphs are what give way** below 500px and never the words; one row from about 352px, and 320px still wraps to two, which is the one width that pays. Two things were in the way. The tabs were pinned to 16px by the touch-floor block, whose rule is about **iOS zooming a control that takes focus and shows a caret** — a `<button>` is not one, so a tab never belonged on that line and being there is what put the strip on three rows; it keeps the 44px target, which is the rule that is about a thumb. And the strip **wraps rather than shrinking**, so the fit stays binary and a test can see it: `phoneBudget` in `measure-print-panel.mjs` asks for one row, for every tab still rendering a name, and for every target still 44px — three questions, because a height budget alone passes a strip that dropped its words to fit.
- **Eight glyphs in a line is one illegible strip, not eight controls** (`alignTools`). `⇤ ⇔ ⇥ ⤒ ⇕ ⤓ ↔ ↕` with what each did in a tooltip, on the pane whose commonest device has no hover — the person using it said so, which is the same test `⌗ Snap` failed. The same eight actions are three named rows now (**Across**, **Down**, **Nudge 1 mm**), and the name is the half that was missing: what separates the first six is not what they look like but which axis they are about, and saying the axis is also what lets the two fills be called `Fill` rather than `↔ Fill` and `↕ Fill`. The four number boxes are **Left / Top / Width / Height** with the unit said once above them, because `X (mm)` names the axis and not the rectangle. **Everything steps in whole millimetres** — the arrows moved half a millimetre and left boxes sitting at 6.5, and they now round to the millimetre *before* they move: an arrow that carries the fraction a drag left behind can never reach a round number, which is the whole reason somebody reaches for one. **`⟳ Rotate` sits with Duplicate and Delete**, which is the row of verbs that act on the box rather than on where it is — and the element's own `rotate` `<select>` is no longer rendered, because two controls for one thing is one too many and **these two disagreed about what the thing was**: a quarter turn swaps which dimension the contents run along, the button swaps the box with it, and the dropdown left turned text in a box that stayed wide.
- **A roll's name is somebody's, and nothing on the screen said so.** Renaming has worked since the Printer tab had an Edit dialog — the field is the first thing in it — and the button was called `Edit`, which is a verb with no object, with a tooltip that listed the two measurements, the margin and the count and never the name. It is `Rename or resize`, which is the same rule that turned "Check it" into `Ask the printer`, and the Name field says what it is for: a built-in row arrives called what is printed on the box you reorder by, which is right for a supplier and wrong on a picker six months later when the roll is the freezer labels. **Showing the name on the design bar's picker button was tried and measured and reverted**: the bar is one flex line whose base sizes are the controls' own content, so a picker wide enough for a name pushes the add strip onto a row of its own — one row to two at 900px, two to three at 390px, 52px of chrome above the label being designed. 147px is what that row has. `designStockFits` asserts the row count now, at 390 and at 1100, because the budget it protects (`CANVAS_TOP_MAX`) is only measured on the phone.

- **A picker answers "which of my rolls is this", and it was answering "what size is it".** The size led everywhere — the dialog's rows, the Quick tab's `<select>`, the design bar's button — on the argument that these controls are width-bounded so the tail is what a narrow window loses, and that two rolls of one brand truncated name-first come out as the same string. True of the CATALOG's names, and beside the point: somebody opening this list is not shopping, and the release before this one made a roll something you can **rename**, which makes the name the answer to the only question being asked. `Address Labels` and `Removable 3/4" x 2"` are two rolls; `2.25" × 1.25"` and `1.0" × 2.0"` are two measurements to compare before you have chosen anything. The dialog's row is the surface that settles it, because a row has two lines and so does not have to choose: the name is the heading and the size is what it is a size *of*. **The button's cap is the fix the earlier reasoning could not see** — a control that must not grow needs a CAP, not a shorter fact, so `.designstock` is capped and the name ellipsises inside it while the caret sits outside the truncation. **150px, and the width it is measured at is the whole story**: 180 was tried first off a sweep that started at 900px (where the bar holds one row up to 220) and 390px takes a *third* row at 180 — the phone is the binding width precisely because its bar has already given way to two, and those two are what `CANVAS_TOP_MAX` was measured against. `designStockFits`' row-count check caught it one release after it was written, which is the only reason that is a paragraph here rather than a shipped regression.
- **A `Stock` cannot know which print head it is on, and `as_dict` answered as if it did.** `drawable_mm` came off the stock alone while the designer's preview is cropped to the box the **renderer** built — which carries the head's own shortfall — so every row on a 2.25" stock over a 2.24" head reported a canvas a quarter of a millimetre wider than the picture under it. That is exactly the class of disagreement `printable_box` exists to end, so `server._stock_row` recomputes the size against the attached printer and `printable_across_mm`/`printable_feed_mm` ride off that one answer. The measure had the same hole: it computed its expectation as `label − holds − margin`, which passes on the wrong number, and it reads the head off the attached printer now rather than writing the geometry down a second time.
- **A summary is what is behind the fold, and nothing else.** The Quick tab's closed disclosure read `Label, copies, font — 1.25" × 3.44" · printer starts 2.4 mm`, and every word of it was paid for on every visit to the tab. Both extras were answered better one line down: the picker inside names the stock and the picture beside it *is* that label, and the leading dead band stopped being a fact about the job at all when the canvas became the printable box — it was describing a correction that no longer moves anybody's artwork.

# brAIn: measurements

Baselines, drifts, appliances, thermal model, closures, rhythm, routines and habits, the action miner and overrides, episodes and Activity, energy, world model, situation, history cut-offs.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **A nightly measurement nobody can ask for is a fix nobody can check** (`h_baselines_run`). `POST /api/baselines/run` has existed since the loop did and had **no caller in the panel, the CLI or the integration** — the "a button that exists only in prose is a button nobody can press" rule with the prose missing too. It is why the doors-and-windows fix took a day to become visible and could not be verified at all: the store went on reading `0 of 18` because the pass had not come round, which is indistinguishable from the fix not working. There is a control in ⚙ → Diagnostics now, beside the rows it is about, and the route **starts** the pass rather than awaiting it — a month of hourly statistics over every numeric sensor is minutes of recorder work, longer than ingress will hold a request open, which is BRight's `_claude_job` failure with a different clock — with the outcome read back off `/api/baselines`. The start guard is a second flag (`starting`) flipped **synchronously**, for `start_auth_check`'s reason: `create_task` only schedules, so two presses in one tick would both pass a guard reading the flag their own task has not set yet, and `build_baselines` owns `running` and is also called by the loop, so one function setting another's guard is how the two callers stop agreeing about what is in flight.
- **A floor's cost is silence, and silence is indistinguishable from broken** (`panel/house.py`). Seven measurements sit under nearly everything brAIn says and every one has a floor, for the reason every floor here exists: a confident answer over data that holds none is worse than none. The cost is that a fresh install says nothing for weeks, and nothing anywhere said *that* — the tabs simply had nothing on them. So every store answers one question about itself in one shape: `progress()` → state, `have`/`need` in a named unit, a `reason`, a `ready_at` and one sentence true in that state. Three rules keep it from becoming a second copy of the measurements. **A store's floor lives in the store** — `progress()` is a method on the module that owns `MIN_DAYS`/`MIN_SAMPLES`/`MIN_BUCKETS` and never a number restated in `house.py`, because a second copy of a floor is a floor that drifts and the drift is invisible until the two disagree about whether a house is ready. **`ready_at`'s arithmetic is here and its RATE is the store's**, since only the store knows whether its unit is a nightly pass (a day), an hour of watching, or a weekday (five in seven, which is why the weekday rhythm takes two weeks and the weekend one five) — one division, so two tabs cannot disagree about when a house will be ready. And **"I could not look", "there is nothing here to measure" and "not enough days yet" are three different answers**: a build that was refused and a house with no outdoor thermometer are both `unavailable` carrying the *store's own* sentence and **no date**, never `collecting`, which promises an answer that is not coming; `stale` is the fourth and the only one worth going and fixing. A store that raises is reported `unavailable` naming the exception rather than taking the payload down, because six measurements and a sentence about the seventh is a screen somebody can read and a 500 is not. `energy` is the one with no store behind it, so its fetch (and the hour-long cache in front of it) belongs to the caller and `progress()` stays pure over what came back — and it has deliberately no `stale`, because it is computed from the recorder each time it is asked.
- **`end_time` has no default, and the argument that is NOT there cost two features** (`ha_data.history_params`). Core's `/history/period/<start>` does not run to now when `end_time` is absent — it answers with **start plus one day**. `closures.fetch_history` asked for 28 days that way and got a single day four weeks back, outside the recorder's 10-day retention on any default install: `[]` for every door in the house, every night. And `[]` is a list, so the fetch counted the batch as answered and returned `{}` — "this house's history holds nothing for these ids" rather than "I could not look" — so `build` wrote an empty store with no error, `snapshot` marked the key unavailable, and **`evening.left_open` was skipped for the life of the feature** while diagnostics read `measured: 0, asked: 18` and nothing anywhere said why. `get_history` omitted it too, which is the same bug where it is much harder to see: every insight card on the snapshot path got one day of history from `history_days` ago and presented it as current. `baselines`/`appliances`/`thermal` were untouched because they go over the WebSocket to `recorder/statistics_during_period`, which has no one-day default — the same omission with the opposite consequence, which is why one nightly pass measured 258 of 299 and 0 of 18 in the same breath. The parameter is positional and required now: a caller that genuinely wants Core's own default has to write the date that produces it, where `None` would be the invisible spelling that could not be grepped for. Driven against a real aiohttp server, because the defect is a parameter that is not on the wire and a fake that accepts `params` and discards it — which is exactly what the shipped closures test did — cannot see it.
- **The Timeline is narrowed on the server, before a block is capped** (`server._activity_narrow`, `area`/`kind`/`q` on `/api/activity`). A room (off `_NAMES`, `-` for none), a kind of thing (an `episodes` subject) and words in a device's name; the room and kind facets are counted before those filters, and `away` is read over the whole window first because an empty house is about people, not the lounge. The window is 6, 12, 24 or 48 hours (`ACTIVITY_MAX_HOURS`), and its select sits on the Earlier/Later row sized to its words (`.actnav #actHours`) — on a phone it was a full-width row of its own above a label saying "Last 24 hours", one fact twice. The label between the buttons says what the select does not (`actDayLabel`): **Now** for the current window, the window's own dates for one paged back to; `measure-activity` holds both and the row at 390.
- **A bus frozen at boot is held to the fallback for ever** (`eventbus.EventBus(rhythm_payload=, known_ids=)`). `rhythm.py` needs a fortnight before it has a measured night and the registry changes whenever somebody adds a device, so both are **callables** resolved on the existing `CTX_REFRESH_S` timer; a dict still works, and a raising callable keeps what it had rather than blanking the window. `resident` is a claimed `run_sources` source (`store: "engine"`) in both halves, or a case's "see what it looked at" opens nothing.
- **A device's role is read once per fingerprint and checked in code, and below the floor the word list still answers** (`panel/world_model.py` / `attribute` / `view`).
  - **Why.** `_HOT_WORDS`, `WAITING_KINDS`, `OUTDOOR`/`DERIVED_WORDS`, `WATER_WORDS`, `NIGHT_WORDS` and the rechargeable guess were all English name gates. A house that names its stopcock `hoofdkraan` had no shutoff in its leak playbook. Its dew point became the outdoor reference unless it happened to contain "dew".
  - **The reading.** The `entity_model` job (Haiku, low effort, tool-less, `--json-schema`) reads about 60 candidates a call. A candidate is an entity some word list asks about: temperature/power/battery sensors, binary sensors, switches, valves and lights. Rows are numbered and names are fenced as data.
  - **What the reply may hold.** Every field is a closed vocabulary validated in `parse`. A word outside it is `unknown`, never the nearest match. A field outside its domain (`APPLIES`) is forced to its default. `space` must be one of the house's own areas.
  - **Re-reading.** The store is keyed by a fingerprint over name, manufacturer, model, platform, area, unit and device class. `view` serves only rows whose fingerprint still matches, so a renamed entity falls back to the word list until it is read again rather than wearing its old name's role.
  - **Rows the reply skipped.** They are stored at confidence 0, so they are not paid for every night. They still read as no answer.
  - **What a reader gets.** `attribute(world, eid, field, fallback)` returns the fallback (a value, or a callable so the word match is paid only when needed) when there is no row, the row is under `CONFIDENCE_FLOOR`, or the value is `unknown`. Every call site keeps its old list as that fallback, so an empty or unreadable store is byte-for-byte the old behaviour. The snapshot carries it as `snap["world"]`, `{}` on any failure.
  - **When it runs.** It rides the nightly baseline loop behind `_resident_gate`. It stops on the first failed batch with a backoff (`RETRY_BASE_S` doubling to a day), saves after every batch so an interruption loses one batch at most, and caps itself at `MAX_BATCHES_PER_PASS`.
  - **Where it may widen a check.** It may widen a check whose cost of being wrong is one finding: a nozzle read as a heater is not "implausible". That is the same direction-of-cheapness trade `measures_something_hot` already wrote down.
- **The house's mode is a guess about a frame, and every guess is checked against the frame** (`panel/situation.py`).
  - **The frame.** `build_frame` is deterministic, from one REST `/states` read per refresh (`REFRESH_S`, 180 s) plus the closures/appliances stores and the world view. It never fetches history. It holds presence (person.*, or GPS device trackers only when there is no person entity), rooms with recent motion, media or lights, closures open against their `usual_open` share, running appliances, the weather, opted-in calendar titles and occasions.
  - **When the model is asked.** The `situation` Haiku turn runs only when the material `fingerprint` changes (the part of the day, who is home, rooms, unusual closures, running appliances, the weather condition, the calendar, occasions — never the minute), at most every `MIN_RUN_SPACING_S`, under `MAX_RUNS_PER_DAY`, and behind `_resident_gate`.
  - **`parse` refuses, in code:**
    - a mode outside the closed set (it becomes `unknown`);
    - `away` without presence data, or with anybody home;
    - rooms that are not the frame's;
    - "unusual together" items that cite no frame key;
    - a sentence with a number or an entity id not in the frame (`grounded`), or with body, health or sleep words (`_BODY_RE`). That sentence is replaced by the previous one marked `sentence_stale`.
  - **What `reading` serves:**
    - `unknown` for a missing, failed or stale frame (`FRAME_STALE_S`), never `away`;
    - the deterministic `presence_mode` with `source: "presence"` when the stored answer was about a different fingerprint, because an answer about an older house is not served as current.
  - **Safety.** The mode is context in the first look's prompt and nowhere else. A wrong `away` cannot lower a never-ignore floor, which `TestAWrongModeNeverSilencesSafety` drives through the real Resident loop.
- **`sensor.brain_house` is aged by its file, and its rule lives in a module with no HA imports** (`custom_components/brain/house_state.py`).
  - The panel mirrors the reading to `/config/.brain/situation.json`. This is skipped when `/config`'s parent is missing, `publish_state`'s rule.
  - The reader judges freshness by the file's **mtime** against the `stale_after_s` the file itself carries. That is `BrainHealthSensor`'s rule, and for its reason: a corrected clock must not keep a stamp from the future fresh.
  - A missing, garbage or stale file is `unknown` with a `reason` attribute, never unavailable.
  - The reader is pure so the test drives it without a Home Assistant install. The entity is driven separately through permissive stubs that restore `sys.modules`.
- **Every measurement is a tool, over the panel's own routes** (`ha_mcp_server.what_is_normal` / `room_physics` / `appliance_status` / `house_rhythm` / `door_habits` / `habits` / `simulate_automation` / `recall`). Phase 2's argument is that a run handed a block has to hope the block covers the question, where a run with a tool asks. Each one reads the route the Knowledge tab already reads (`_panel_get` over loopback, `explain_change`'s arrangement), so there is one implementation of each answer and a store that has not measured yet says so **in a sentence** rather than answering with a number it does not have — `room_physics` names the rooms it does know when asked for one it does not. `simulate_automation` is `_replay_config` plus `trials.evaluate` behind `POST /api/simulate`, days clamped to `SIMULATE_MAX_DAYS`, and a refusal is whole, `shadow`'s rule. All eight are on `ANALYST_TOOLS` because every one of them reads; `tests/test_measurement_tools.py` drives each with `_panel_get` answering the shape its route really sends (copied off `_thermal_payload`, `_appliance_detail`, `_closure_rows`, `_facts_payload`) because a payload key guessed in the tool and guessed the same way in its test is the `_error_code` envelope failure again — and the first cut had two of them wrong.
- **One habits arithmetic behind three ledgers** (`panel/habits.py`). `routines.py`, `override_ledger.py` and `manual_ledger.py` each measured "the shape of when something happens" — days, share of the days it could have happened on, a circular median, an occupied band, still happening — with a private copy, and the three had already drifted in what counted as a weekday. `habits.grade` is the one implementation and each ledger keeps its file, its floors and its vocabulary and delegates (`routines._grade`, `override_ledger.pattern`, `manual_ledger.shape` / `off_pattern`); `habit_lookup.habit_of(entity_id)` reads all three for `/api/habits` and the `habits` tool — in its own module, because a module the ledgers import may not import the ledgers back. **The borrow closed an import ring, and CodeQL was the one that saw it**: `habits` read the circular median off `rhythm`, `rhythm` reads `house` for its progress sentence, `house` reads `routines` for the same, and `routines` delegates to `habits`; a ring is not a crash but a module whose answer depends on which neighbour was imported first, which nobody reproduces on purpose. The clock arithmetic is `panel/circular.py` now, a leaf that imports nothing of the panel's (its median is the standard library's, because `baselines.median` would close the ring one module over through `baselines → house`), and `rhythm` re-exports it under every name a caller or a test already uses. `tests/test_habits.py` runs the old arithmetic beside the new over the same fixtures and asserts they agree, greps that the old copies are gone — a delegation the measure cannot see is a delegation that quietly changed an answer — and imports each of the eight modules alone in its own interpreter, which is the order a ring breaks in.
- **"Unusual" is a word until something measures it** (`panel/baselines.py`). It is behind most of what people want a smart home to notice — water running at night, a freezer drifting, a boiler on twice as long as usual — and every rule that used it was a threshold somebody guessed. The engine measures, per numeric entity, what it normally reads **at this hour of this day of the week** and how far it normally strays, from a month of long-term statistics, nightly, for no Claude turn. Five rules make it honest. **The bucket is an hour of the week in the HOUSE's timezone** (from the cache `run.sh` writes) — a weekday 7am is not a Sunday 7am, and UTC smears every household's morning across two buckets and moves it twice a year; an unreadable or unknown zone falls back to UTC and *says which*, because a wrongly bucketed baseline is somebody's evening filed as their morning and looks exactly like a working one. **Spread is a MAD, not a standard deviation** — one meter that spiked when the oven came on sets a σ wide enough that the band it draws is a band nothing can fall outside; same reasoning as BRight's p99-not-max. **A reading that never moves has no spread, and dividing by it makes every change infinite**, so `spread_floor` is a fraction of the reading's own size *and* an absolute (a reading whose normal is zero is the same divide-by-zero in a disguise), and an entity whose whole history is one value is reported `flat` — no baseline — rather than as an exquisitely sensitive one. **A bucket under `MIN_SAMPLES` says nothing**, and `deviation` falls back to the whole history *labelled* `source: "overall"`, because "no baseline at all" and "no baseline for 3am on a Tuesday" are different answers. **And nothing here decides anything** — it answers "how far outside its own normal, in its own spreads", and the checks and the model decide what is worth saying; a baseline that also raised alarms would be two rules in one place with the threshold invisible. `candidates` sorts before capping so the cap takes the *same* entities every night: an arbitrary set that changed nightly would give half the house a baseline that keeps appearing and disappearing. Built by a nightly loop in the panel and only ever *read* by the checks snapshot — a checks pass that rebuilt them would spend minutes of statistics queries every six hours on an answer that changes over weeks.
- **A drift is invisible to the band, structurally, and the number says how much** (`baselines.trend` + `forecast.decline`). `base.unusual` buckets by hour of the week, so a *drift* moves the bucket along with the reading: a freezer 6°C warmer than a month ago has samples of 0, 2, 4, 6 in its bucket — a median of 3 and a spread of 2 — and today's 6 comes out at one and a half spreads. Measured on a real-shaped month it is **2.3 spreads to the band and 16 to the trend**, and the band needs six, so it is not badly tuned, it *cannot* see this however far it goes. The line is fitted to what is left once the week's own pattern is taken out (each hourly mean minus the median for its hour of the week — subtracting a constant per bucket removes the daily and weekly shape and leaves a slope untouched), and the noise it is graded against is the spread **about that line**, which is the one estimate the drift cannot inflate; grading against the entity's own MAD would be circular, since the drift is what widened it. Every floor answers "does this fire on a healthy house": **both halves of the window must agree on a direction**, which is what tells a drift from a V (a season turning) and from a step (a meter replaced) — both have a slope and neither is a drift; a move smaller than its own noise is not a move; **five thermometers drifting together is the weather rather than a device**, so the whole `device_class` stands down and what is left is the one room doing something the others are not; and past a handful of rows it says nothing, the same cap `base.unusual` carries. **The `state_class` gate is the one that would otherwise have fired in every house**: a `total_increasing` meter is higher than it has ever been every hour of its life, so a line through one finds a slope every time (measured at 11 spreads) — the gate is in `build`, not in the check, because a trend nothing should read is a trend nothing should store. It also caught `base.unusual` being quiet on those meters **by accident rather than on purpose**: the band's own spread widens along with the ramp, which is not a guarantee — a meter that resets has no such protection — so both checks now require `measurement`. And a reading far outside its band on a sensor that has been drifting is reported once, as the drift: the two share `baselines.trend` and one `eligible()`, the same rule `dev.unavailable` and `dev.zwave_dead` follow. **And a drift with an outside cause is not a device going wrong** (`forecasts.outside_cause`): 0 confirmed against 3 Wrong was the grid's carbon intensity, a car's charge level and soil drying in a dry spell — real drifts about things the house does not control. Excluded by what is checkable: an outdoor class (`OUTSIDE_CLASSES`: weather, soil moisture, money, distance), a unit per kWh (a tariff or an intensity), a weather/grid/phone platform, a device that also has a `device_tracker` (somebody carries it), a name that cannot mean indoors, or an area called outdoors. The narrowing is an exclusion list on purpose — the check fires on unclassed readings (a label roll's count) and an allow-list by class would silence those. One least-squares fit lives in `baselines.least_squares`; `checks/forecasts.py` had its own copy for the battery runway, and two answers to "the slope of these points" is one too many.
- **Nothing in Home Assistant says a cycle ended, and every rule on a smart plug is a wattage somebody typed** (`panel/appliances.py` + `chore.waiting`). `> 10 W` is a running dishwasher in one house and a phone charger in the next, so the numbers are measured per machine from ten days of its own five-minute statistics — `baselines.py`'s argument about "unusual", applied to a distribution of a different shape. A power reading is not a band with a middle and a spread, it is **bimodal**, and a sensor without that shape (a router, a fridge's standing draw) gets **no profile** rather than a guessed threshold: `MIN_SPAN_W` and `MIN_SPAN_RATIO` both have to hold, because a ratio alone passes a 3W-to-9W phone charger and a span alone passes anything large. **The floor is a low percentile, never the minimum** — one zero during a power cut would set the idle level for good. **"Below the threshold" is not "finished"**: a dishwasher's dry phase draws almost nothing for twenty minutes, so a machine that reports done when the draw drops reports done three times a cycle — and the wait is measured too, because the gaps between draws are *themselves* bimodal (lulls of minutes inside a cycle, idles of hours between them) and **the widest jump in that sorted list is the appliance saying how long its own quiet phases last**. The unit of `MIN_DRAWS` is a draw and not a cycle, deliberately: a cycle with a lull is two draws, three draws is two gaps, and two gaps is the fewest a jump can be found in — the floor is the arithmetic needing something to work on rather than a taste. **A blip is not a cycle** (`MIN_RUN_MIN`: every compressor, kettle and inrush clears a threshold for a moment). And **"unloaded" cannot be seen from power at all** — an emptied machine and a full one draw exactly the same watts — so there are three states and the fourth is a person pressing something, which is what 1.38's To-do list and notification buttons are for; a state machine that inferred it would be inventing the one fact the chore is about. The check adds the floors that answer "does this fire on a healthy house": `QUIET_MIN` on top of the measured settle (a cycle that ended four minutes ago is somebody standing at the machine), `STALE_HOURS` (yesterday's washing is a fact about the week), `MAX_ROWS`, and **the name gate** — the measurement is universal and the chore is narrowed to a washer, a dryer and a dishwasher by matching the sensor's name, longest phrase first. That is the one guess in the file, made in the direction where being wrong is cheap: a missed chore costs nothing, and a notification telling somebody to empty their television is how the whole feature gets switched off. Its urgency is `whenever` for the opposite reason to `evening.left_open`'s `now`: a chore arrives in the evening by construction and an emptied dishwasher at eight in the morning is the same dishwasher, so quiet hours must be able to hold it. The shapes are read from the nightly store like the baselines and the closures, but what each machine is doing *now* is a live question — so this is the one measurement the checks pass fetches for itself, and it is cheap by construction: a handful of profiled sensors over fourteen hours, never the house over a month. **A device whose integration SAYS its job ended is the same chore read off a different signal** (`checks/chores.job_done`, `chore.job_done`, `snapshot._job_history`): a 3D printer publishing a print status (or a washer an operation state) and no power sensor was invisible to a check that reads power, on the one house that asked for exactly this. It reads a **transition**, never a word: a `sensor` whose live state is in the closed `JOB_FINISHED` vocabulary is a *candidate* (`job_candidates`, pure, shared by the collector and the check so they agree on what a missing history leaves unread), and it is a chore only when the recorder shows a `JOB_RUNNING` word before that finish, walked newest first through further finished words and the `JOB_PASS_THROUGH` ones (a restart's `unavailable`, a pause) — anything else (idle, failed) breaks the chain, because a status that has said `finish` since Tuesday, or since a restart re-published it, is not a job that ended. Walking back through every finished word is what keeps a restart from making a forty-minute-old print look two minutes old. The same `QUIET_MIN`, `STALE_HOURS` and `MAX_ROWS`, and `house.should_report` for every row. The printer is `PRINTER_WORDS` matched on the status entity's own name ("Print status", never bare "printer", which is a label or an office printer), and it is **not** in `WAITING_KINDS`, so the power path's behaviour does not move (a plug called "3D printer" draws like anything with a heater); a washer with both a profiled plug and a status on one device is the power path's (`_power_owns`). The fetch is the appliance one's shape — only the candidates, at most `JOB_FETCH_MAX`, over `STALE_HOURS` + 1h, and **no request at all** when nothing says finished — so the check needs no snapshot key up front and is not skipped on the clean house; when something has finished and the history could not be read it raises `CouldNotLook`, which `run_all` files as skipped (never an error), so it clears nothing. **And a tick cannot be contradicted by it** (`todo_store.UNSEEN_DONE_SOURCES`): the status says `finish` until the next job whatever was taken off the bed, so re-running it after Done would report what it reported before and put the chore back as "came back" — the check overruling a person on the one fact it cannot read. `chore.waiting` has the same shape (a machine emptied and not re-run stays FINISHED for fourteen hours) and was deliberately left as it was. **And power cannot say a drum is full** (`chores.FINISHED_TEXT` / `FULL_TEXT` / `_door_since`, `findings_store.add_many`'s `was`): "The washing machine has finished and is still full" was marked Wrong every time, because a plug sees a machine stop and nothing run since, never what is inside it. The row says that ("… finished a cycle and nothing has run since", the clock time in the detail), and says still full only where a door or opening sensor on the same machine has stayed shut since the cycle ended; a door that has moved since files nothing. A reworded check text is a new dedupe key, so the row carries the old wording as `was` and `add_many` drops a row whose `was` is a suppressing settled key: an answer given to the old words stands.
- **Every climate question is the same two numbers about a room, and brAIn held neither** (`panel/thermal.py` + `checks/thermal.py`). Pre-heat so the bedroom is warm when we get up, a window open rather than a cold day, pipes freezing by morning, what a 17°C setback costs: each was a threshold somebody guesses, and a threshold right in one house is wrong in the next — a stone cottage and a new flat lose heat an order of magnitude apart, and so do two rooms of one house. The numbers are Newton's: `k`, the loss coefficient per hour (its reciprocal is the time constant, which is the number people have an intuition for), and `h`, the gain in degrees per hour. Both are measured per room from a month of hourly statistics against **one** outdoor reference, and **the reference is recorded in the payload** — every `k` in the house is measured against that one choice, and a reference nobody can check is a reference nobody can correct (the same argument as BRUH Print's `_pick_interface`). **The sun is the confounder and night is the gate**: a south-facing room warms with the heating off, so a fit that includes an afternoon reports a room that gains heat as it gets colder outside — measured, an all-day fit on a sunny room is refused outright while the night fit lands on the physics. The gate lives in `build`, not in the check, for the same reason `baselines.trend`'s `state_class` gate does: a measurement that would be wrong in every house is a measurement nothing should store. **A fit is not a measurement until it is graded** — a month whose outdoor temperature barely moved has no leverage, every point sits at the same x, and the line through them is whatever the noise says, which looks exactly like a real answer; so the delta has to span something, the slope is graded against the scatter about its own line, and one that does not clear it is no slope. **`device_class: temperature` is carried by readings that are not a temperature anybody stands in** (`thermal.DERIVED_WORDS` / `is_derived`) — a dew point, a feels-like, a wet bulb, a heat index, a frost point — and a weather integration publishes several of them with **no area**, which is exactly the branch `pick_outdoor` falls through to when nothing is named "outside". So the reference was settled by whichever sorted first, and `dewpoint` sorts before `temperature`: a real house had every `k` in it measured against `sensor.astroweather_2m_dewpoint`, a number that tracks humidity and sits well above the night air, and the visible cost was `climate.window` reporting an irrigation pump manifold as a room with a window open. The refusal is checked **before** the outdoor words, because "Outdoor Dew Point" satisfies both and only one of them decides whether the number means what the model needs; it is asked of `room_candidates` too, since an indoor dew point has an area, carries the class and reads inside the band people live in, so the band alone lets one through as a room. It is a name gate, which is a guess, made where being wrong is cheap (`measures_something_hot`'s trade): refusing a real sensor with an odd name costs the model and **the payload says it found no reference**, where accepting a derived one costs every room's physics silently. **A number outside physics is not a room** (`MIN_TAU_H`/`MAX_TAU_H`: twenty minutes is a thermometer in a draught, a fortnight is one inside a wall), **indoors and outdoors have to agree what a degree is** (`k` is unit-free only while both halves of the difference are, so a Fahrenheit reference against a Celsius room is a loss rate wrong by 1.8 and nothing downstream could tell), and **a freezer carries `device_class: temperature` too** — a room is a reading that spends the month inside a band people live in. `hours_to_warm` returns `None` for a target above the room's ceiling because "it cannot get there" and "it takes a long time" are different answers and only one of them is a slow morning. **And nothing here decides anything**, the same split `baselines.py` and `closures.py` keep. The two checks that read it are both invisible from any single state. `climate.underheated` needs the arithmetic **and the evidence** — the room must never once have been seen at what it is asked for — because a thermostat that switches off at its setpoint never lets a room show what it could have done, so a well-heated room's measured ceiling understates it and a check reading the ceiling alone would fire on the healthiest houses first; and it says nothing at all when the month held no cold night, rather than extrapolating January out of August. `climate.heat_loss` needs four measured rooms before one can be unusual against the others and needs the room fast in absolute terms too, because twice the loss rate of a very well insulated house is still a good room. They share `underheated_rooms` so a draughty room that also never warms is one card with one fix — `dev.unavailable` and `dev.zwave_dead`'s arrangement. Both are `whenever`: a room two degrees short all winter is not two degrees shorter at 3am. **Three more read the model against what a room is doing now, or against every morning.** `climate.preheat` is what the model was built for: a schedule set to a fixed hour warms the bedroom to its setpoint at 07:40 in a house that is up at 07:00, every weekday, and nothing records a fault — the automation ran, the thermostat called, the room got warm. It needs three of brAIn's own measurements to agree (`rhythm` for when the house gets up, `baselines` for what the room reads at that hour of the week, the model for how long the climb takes), reports **weekday mornings only** because that is where a schedule exists and where `rhythm` has the days, and says nothing until the wake time is *measured* — a preheat time pinned to a typed-in 07:00 is a guess wearing a number. **The proof the heating does arrive is required**: a room still short two hours later is `climate.underheated`'s, and "start earlier" is advice that cannot work on one. `climate.window` fires on a fall more than twice what the room's own `k` allows, and is only sayable *because* the model exists — the same half-degree in ten minutes is a draught in one room and an ordinary evening in another. Its allowance is read where the fall **started**, not where it ended: a room's allowed loss shrinks as it cools, so the end sets a lower bar, and the start gives the model the benefit of the doubt (`test_the_allowance_is_read_where_the_fall_STARTED` pins it, because nothing else did). **And a fall that ENDS below the reference is refused**, which is the same physics read as a guard: a room cooling toward the outdoors approaches that reading asymptotically and cannot pass it, so a span that crosses under it disproves the premise `expected_fall` was computed from — this is outdoors itself, or refrigerated, or being cooled on purpose, or the reference is wrong (a dew point, one module over). It costs one comparison, and the test that pins it needs an outdoor reference **above `FREEZE_FLOOR_C`** or `climate.freeze` claims the room first and the case passes for somebody else's reason — which is exactly what the first cut of that test did, and the mutation is what caught it. `climate.freeze` asks when the room reaches the floor water in an outside wall is at risk at, and only about a room **already falling** — `coast` describes an unheated room and no state says the heating is off, so the fall is the evidence. Both live checks read **five-minute** statistics (`thermal.recent`, fetched by the checks pass exactly as `appliances` does), because an hourly mean cannot see a window opened forty minutes ago: it is still inside the hour that has not closed. Both are `now` and may break quiet hours — a freeze warning at 3am is when it is wanted — while `preheat` is `whenever`, because a schedule that starts late starts late again tomorrow; and they stand down for each other's room, freeze first.
- **A probe on a heating or cooling machine is not a room, by name or by what it does** (`thermal.NOT_ROOM_AIR_WORDS` / `equipment_jumps`). One area's only "room" was a heat pump's coil probe that jumps about 25 °C at the same hour every morning, and `climate.heat_loss` filed it as a room losing heat fast. The words now cover the refrigerant line, the flue, the burner and the rest of the machine (whole words), and a reading whose largest rise across one or two hourly means passes `EQUIPMENT_JUMP_C` on most days at nearly the same clock hour is left out of the build with that sentence in `unmeasured` — no room warms that fast and the weather does not run on a timer. The area is then measured from its ordinary air sensor or not at all. Pure over the hourly means the pass already fetched.
- **A night belongs to the day it started in** (`rhythm.DAY_START_MIN` / `house_day` / `PERSON_CAUSES`).
  - **The bug.** `record` filed each action under its calendar date. Anything after midnight became the next date's *first* action and could never be a settle. A house up until 00:40 was measured waking at 00:40 and settling at 22:00: inverted, not imprecise.
  - **Who inherited it.** `brief.due`, `signals.night_window`, `healing`'s settle+60, `evening.left_open` and `climate.preheat`.
  - **The fix.** A house day runs 04:00–04:00. The boundary is fixed on purpose, so a night is never refiled as the store ages. `first`/`last` are taken in that day's order and stored as clock minutes, so no reader changed.
    - `settle_minute` reads the house day: 00:30 on Saturday is Friday night's settle.
    - `wake_minute` reads the calendar day: the wake still to come.
  - **Repair of old stores.** A store with no `day_start` marker is repaired once on read. The two rows each post-midnight night was split across are dropped; rows the new rule would write identically are kept.
  - **`voice` is a person** (an Assist command is the most deliberate thing a person does to a house). `unattributed` still is not.
- **An appliance's busy level is read off its RUNNING readings, never off the whole window** (`appliances.noise_floor` / `BUSY_PCT` / `select`).
  - The 95th percentile of ten days of five-minute buckets is the idle level for anything that ran under ~145 buckets. Measured: nothing up to eight 90-minute cycles at 1 W / 500 W got a profile, which is an ordinary washer.
  - The busy level is now the median of readings above both bimodality floors at once (`MIN_SPAN_W` above idle and `MIN_SPAN_RATIO` times it). The median rather than the peak, so a heater phase does not lift the threshold over the motor phase.
  - The 40-sensor cap ranks sensors `chores.kind_of` names first, then by id. The store records `eligible`, `cut_count` and a sample of the cut, because a washer cut before profiling is `chore.waiting` silent with nothing to say why.
- **The outdoor reference is RANKED, the ranking is shown, and a person can overrule it** (`thermal.rank_outdoor` / `choose_outdoor` / `daily_swing` / `settings_store.thermal_outdoor`).
  - `pick_outdoor` took the alphabetically first name with any outdoor word, whatever its area. "Ambient" and "garden" counted, so a heat pump's coil, a pool and an indoor ambient reading could each become the reference every room's `k` is fitted against.
  - Each candidate now carries sentences:
    - an area not called outdoors rules it out;
    - an outdoor-named area or no area counts for it;
    - a strong or weak outdoor name counts for it;
    - the weather entity's own integration counts for it;
    - reading what the weather entity reads counts for it. This is the one signal that needs no word, so it works in any language.
    - a coil, pool or pipe name, or reading far from the weather entity, counts against it.
  - The nightly build reads the leading candidates' month and lets the daily swing decide, because air swings and a probe in a wall does not.
  - The setting overrides the ranking. A choice that is not a thermometer here is said and ignored, never silently swapped.
  - The store carries `outdoor_source` / `outdoor_why` / candidates, and the drill-down renders them.
  - A confident `world_model` reading of `measures` replaces the NAME's evidence in `rank_outdoor` (outdoor +2, machine −3, room air −2, derived excluded) and never the area, integration, weather or swing evidence.
- **A cap is spent AFTER the eligibility filter, and what it cut is said** (`baselines.select` / `BASELINE_STATE_CLASSES` / `BACKGROUND_CATEGORIES`).
  - **The bug.** `candidates` sorted every `state_class` entity and kept 400 before asking whether a baseline could be built (a `total`/`total_increasing` meter has no `mean` statistic) or read (`checks/baseline.eligible` drops diagnostic and config entities). The slots went alphabetically to rows that could never be measured, and the cut was invisible.
  - **The fix.** The filter is the readers' own rule moved ahead of the cap, and a test holds the two sets equal.
    - The nightly pass fetches the registries once, before the baselines.
    - A registry that did not answer costs the category filter only, and the store says `categories_read: false`.
    - `eligible`, `cut_count` and a sample of the cut ride the store, `progress()`, `/api/baselines` and `/api/diagnostics`.
  - **The unit floor.** `MIN_ABSOLUTE_MOVE` is now per unit (`checks/baseline.min_move`, °C still 0.5), shared with `forecast.decline`.
  - **The wording.** The whole-history fallback's detail counts hourly readings, not "weeks".
- **A state carries no cause, and the logbook is the only place Home Assistant records one** (`panel/actions.py`). Nothing in `light.kitchen` being on says whether a person pressed a switch, an automation fired, a voice command asked, or brAIn did it — which is the question behind most of what people actually ask their house, and it was unanswerable from every surface brAIn had. The miner reads the logbook, walks each event's context chain, and files every change under a cause out of a closed vocabulary (`CAUSES`, switched on by the check, the tab's filter and the MCP tools alike). **Proximate and root cause are different and both are recorded**: an automation somebody started from the UI carries a `context_entity_id` *and* a `context_user_id`, so reporting only the user turns every automation into "you did this" and reporting only the automation loses the one fact that explains an unexpected run. **`context_domain` is not the runner** — it is `light` for a plain `light.turn_on`, so the authority is the context *entity's* domain and only then the three domains that run something. **A change with no context is `unattributed`, in as many words**: a wall switch and a device's own integration reach Core identically, naming either is a guess, and a timeline that guesses is not evidence. **`when` is an ISO string over REST and a float over the WebSocket stream**, out of the same processor, so a reader that handles one works right up until somebody points it at the other. **Nothing is persisted** — every question here is about a window, so every function is pure over one fetch, and the accumulating store that would buy longer windows would be a second thing to keep true.
- **brAIn knows what brAIn did because it wrote it down, not because it can tell.** The MCP server calls Core over REST with the Supervisor's token exactly like every other add-on, so a light brAIn turned on is indistinguishable in the context chain from a light any integration turned on — there is no id to match. `ha_mcp_server.record_action` appends every service call to `/config/.brain/actions.jsonl` at the same `call_service` chokepoint `protected_entities` is enforced at, and `actions.read_ledger` joins the logbook against it inside `BRAIN_MATCH_S` (a bulb answers in well under a second, a thermostat takes several). An **area or device target is recorded and deliberately not resolved** — resolving one needs the registries as they were at the time of the call, and a wrong expansion would attribute somebody else's change to brAIn, which is the one mistake the ledger exists to prevent. The writer and the reader are **different processes running as different users and neither can import the other**, so `tests/test_actions.py` drives the real writer into the real reader rather than writing the shape down twice — the same reasoning that put `saved_at` back to an epoch int.
- **A schedule is a timer; a rhythm is measured** (`panel/rhythm.py`). Everything brAIn did on a schedule happened at an hour somebody typed into a box, and 07:00 is early on a Sunday and late on a Tuesday in the same house — somebody who keeps correcting when a message arrives stops reading it. The house already answered this and nothing was asking: the action miner files every change under a cause, and **the first one caused by a `person` is the house waking up** — not a motion sensor (it fires for a cat and for the heating), not a light (an automation does that at dawn), but somebody actually doing something. Two numbers a day are kept, which is not a timeline, and the same exception the override ledger claims for the same reason. Four floors, all of them the ones the baselines already carry: `MIN_DAYS` before it answers at all; **weekdays and weekends measured apart**, because one number over both is wrong on all seven days rather than on none — and the cost is worth naming, since a weekend accrues two days a week and so takes about five weeks to exist, which looks like a bug from outside and is the floor doing its job; `MAX_SPREAD_MIN`, because a house that stirs anywhere between 05:00 and 11:00 has no wake time and a median of it would be a confident answer over data that holds none; and a day already recorded is **widened, never replaced**, or an overlapping pass that starts at 04:00 walks the wake time forwards all morning. **And the median is CIRCULAR**: settle times sit either side of midnight, and four of them inside forty minutes of it have a straight median of **12:00** — not a small error, the opposite side of the day — so everything is measured around the clock and `circular_spread` takes the short way round (23:50 is twenty minutes from 00:10, not twenty-three hours and forty). `tests/test_rhythm.py` asserts that failure against `statistics.median` on the same data rather than describing it.
- **Which meters is the half that produces a number nobody can tell is wrong** (`panel/energy.py`). Summing "every sensor with `device_class: energy`" double-counts by construction — a whole-home clamp, the inverter and every smart plug behind them all carry that class — so a house with six plugs reports roughly twice what it used and nothing on screen says so. The set is **Home Assistant's own** (`energy/get_prefs`, grid `flow_from` only: solar, battery, gas and water are each a different unit and a different sentence), and no energy configuration is a sentence rather than a plausible group picked here. **Cost only where a cost STATISTIC exists** — a `flow_from` carrying a price to multiply means HA made its own cost sensor under a derived id, and guessing that id is how a report quotes a number belonging to a different sensor. **Both windows are seven complete local days**, ending at midnight and never at `now`, because half of today against seven full days is a 45% fall that is nothing but the clock — and the day count is the **fewest any one meter gave**, not the average, or two meters each missing a different day leave a window that reports itself complete. **A negative day is a meter reset, not a negative amount of electricity**: it is dropped, which shortens the window and stands the comparison down rather than reporting a plausible fall. Where the recorder can answer consumption itself (`types: ["change"]`) it is asked and the cumulative `sum` is the fallback — deriving from it costs the first row of any range, which is why the fetch reaches a day further back than the report does; without that day the earlier window would be six against seven and the whole comparison would be a one-seventh fall that is nothing but the fetch.
- **The Activity tab is the fourth kind of knowledge, and it has no badge.** Memory is what is *true*, a finding is what is *broken*, a hypothesis is what brAIn might have *wrong*, and this is what *happened*. It is a record rather than a queue — nothing on it is waiting on anybody — so the one badge in the strip stays Findings', which counts exactly that. Fetched per visit and never cached: a timeline showing the house as it was when you last looked is the one thing a timeline may not do, and a cache of a stream is a second copy of the logbook to keep true. The overrides ride above the list because they are evidence rather than history. The cause **moves to its own line** on a phone rather than being deleted — the name of the automation that did something is the whole row. `tests/manual/measure-activity.mjs` drives the real `renderActivity` behind a stubbed fetch (a copy of the renderer in the test would only ever agree with itself) and fails on a cause hidden rather than moved, a row repeating "no cause recorded" (an unattributed row shows nothing in the cause slot and the foot says once how many there were — 14,000 rows each saying it was the list), and an evidence block shown over a window with nothing in it. **The sixth tab needed no new breakpoint** — `measure-topbar` reports all 96 cases at the same two shapes — but it found two tests measuring the wrong thing: that script asserted *five* tab labels by number, which says nothing about whether a sixth kept its name, and `test_brain_addon`'s band scan ran to the end of the stylesheet, so it was really testing where the last `@media` in the file happened to sit. **An unreadable logbook says so in plain words and hides the room and cause filters** (nothing to choose is an unnamed caret; the sentence names no file or check, only that the Logbook should be turned on in Home Assistant). **House › What happened** opens on the situation sentence (`#actNow`, off `/api/situation`, a stale one prefixed "Earlier:"; no sentence, no line — the mode alone was a bold heading over nothing), the tab's intro and each group's blurb are cut (the server still sends `blurb`; a group is its name), the cause chips are one **Caused by** `select.sel` with no counts (the row that scrolled sideways on a phone), and the paragraph's press reads **Ask**. Earlier / Later stay.
- **A logbook with a cause column is still a logbook, and nobody thinks in state changes** (`panel/episodes.py`). Reported as *"the activity tab is really worthless… basically zero utility in its current form"*, and the diagnosis is in the shape rather than the styling: one row per state change, newest first, filtered by who did it, is Home Assistant's own logbook with a column added — and on a real house it is hundreds of rows an hour of a sensor reporting a number. What a person thinks in is **episodes**: the TV was on in the lounge from eight until eleven, somebody got home at 17:40, the hall sensor saw something nine times between two and three. Every one of those is derivable from the logbook this already reads and not one was on any screen, in brAIn or in Core. Five rules. **A reading is not an event** — `READINGS` is dropped whole and **counted**, because a list that silently discards nine tenths of its input is one nobody can trust, and the foot says what it left out; a `button` is in that set for the other reason, being stateless, so what the logbook calls its state is a timestamp and a row reading `Doorbell → 2026-09-15T20:14:03` is noise wearing an event's clothes. **An episode is a run, and a gap only ends one that had already STOPPED** — the half a first cut gets wrong: a subject's own `gap_s` merges a burst (a door opened twice in a minute is one trip), and an episode whose last state is **active** is extended across any gap at all, because the thing did not stop. Without the second, an `off` three hours later is filed as a fresh episode of *off* and the row reads `Lounge TV, off, 0 seconds` under a heading about what played; the test demonstrates the gap-only arithmetic on the same fixture before asserting the fix, and `duration_s` is one number with one meaning in both states (`open` is carried, never inferred from it). **The sort is by SUBJECT and not by cause** — "who did it" is a debugging question and it was the only filter there was — and the matcher is domain-first with the device class consulted only where the domain genuinely cannot answer: an unclassed `binary_sensor` is a door, a motion sensor, a leak detector or a plug's power flag, so it goes to *Everything else* rather than to the likeliest, `closures.is_closure`'s refusal for its reason, since the cost of guessing is the front door filed under Motion. An unclassed **cover** is the one that may fall through, the domain having already answered. `reads` (`span`/`count`/`moment`) is on the subject table rather than derived in the panel, because a momentary sensor's span is an artefact of when it last fired and a renderer reading it as a duration reports a hall sensor as *on for 83 minutes*. **Nothing here asks a model** — `curiosity.py`'s rule, and a test scans the module for the imports that would break it, because this runs on every visit to a tab. And **`away_spans` refuses more than it claims**: the roster of people is taken FIRST and a span cannot open until every one of them has been seen, since walking the changes and claiming an empty house off whoever has been met so far opens one the instant the first person leaves and closes it when the second is met still at home — a span that never happened; a `device_tracker` is a phone and not a person, an ongoing span ends at `now` rather than at the last person's own move (which is where it started), and a window in which nobody moved says nothing at all. The **paragraph** is the only part that spends and it is a press (`h_activity_summary`, cached against the window, `brief.py`'s deterministic-gather-then-one-sentence split, and its contract forbids writing about the person rather than the house); a run behind a tab that refreshes on arrival is the "refresh everything" control this panel deleted, with a nicer name. `measure-activity.mjs` was rewritten with the tab and found two layout failures reading could not: the row needed to **wrap** rather than shrink (a narrow width that ellipsised the automation's name would be deleting the row's whole point), and `.actlist` needed `grid-template-columns: minmax(0, 1fr)` — an implicit `auto` column is sized to its content's min-content, so one `nowrap` cause made the whole column 1.45px wider than the page.
- **Activity agrees with the house NOW, and names what explains a burst** (`episodes.group(live=)` / `actions.lifecycle` / `server._house_now`). An ongoing episode whose last state differs from the entity's live state ends at the live `last_changed` and the live state becomes its own row (`from_live`) — "heat_cool for 17 h" about a thermostat unavailable since 11:11 is the reading nothing could correct; only a window that ends now is touched. Home Assistant's own start/stop lines (which `mine` drops, correctly) become a "Home Assistant restarted" row, and uncaused rows near it carry `near_restart`. Six or more uncaused changes to one state in one second are ONE row naming the integration only when every entity shares it (an integration reload is one event, not forty); a change with a recorded cause is never collapsed. People is `person.*`, and a `device_tracker` only when the house has no person entity and only a GPS/mobile_app one — a UniFi AP is not a person. The current window is labelled "Now" (the select beside it says how long it is) and one paged back to by its dates.
- **`/api/activity` still answers with rows when a caller asks by `limit`** (`server._activity_rows`). The MCP `get_activity` tool reads `total` and `actions` and always sends `limit`; the Timeline never does. A request carrying `limit` gets the mined rows newest first, narrowed by `cause`, capped at 1000 (default 200), with `overrides`; one without carries none, as the tab expects.
- **`explain_change` and `get_activity` call the panel over loopback rather than re-implementing attribution.** Same reasoning as `brain findings` going through the API instead of the store files: one implementation, one answer. Both are read-only and on `ANALYST_TOOLS`, so an unattended card can ask what caused something; a panel that is not up is reported as such rather than as a quiet house.
- **Traces are read live and keyed by config id** (`get_automation_trace` over `trace/list` + `trace/get`).
  - `.storage/trace.saved_traces` is written only at shutdown, and Core keys a trace by `<domain>.<unique_id>`: a timestamp for a UI-made automation, never its entity id.
  - `get_automations` returns the `id`.
  - `get_automation_config` uses the WebSocket `automation/config` / `script/config` by entity id, which reaches YAML and package automations. The REST editor endpoint knows only automations.yaml. This matters because unattended runs have no file access.
  - The panel's trace checks share the keying and row-shape bugs. They are WP5's, not fixed here.

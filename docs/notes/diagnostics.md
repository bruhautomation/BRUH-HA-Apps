# brAIn: health, doctor, reports and the corpus

The health verdict and sensor, brain doctor and --deep, the rehearsal, problem reports and faults, diagnostics payload, capture and the corpus.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **One problem, one text file, written when it happens** (`panel/reports.py`). Every tool for answering "what went wrong" was **pull-shaped** — `brain doctor` if you knew to run it, ⚙ → Diagnostics if you knew to open it, `brain report` if somebody had already asked you for one — so by the time anybody looked, the journal row that would have explained it was one of two thousand and the log line had scrolled off. Three producers and one writer: a journal row ending in a `FAILURE_OUTCOMES` outcome (**a listener on `journal.record`**, which every Claude run, checks pass, baseline build and overnight heal already passes through, so nothing new has to remember to report), the health verdict *leaving* `ok` (the daemon that died, the credential that expired on a Tuesday), and a notification that could not be delivered (the one failure whose only symptom was silence on a phone). A refusal doing its job is not a fault and writes nothing — `heal_skipped` and `denied` are out of that set on purpose, as is `fallback`, which still produced a card. **A repeat is a line, not a file**: the same `fingerprint(kind, source, outcome, error)` inside `DEDUP_HOURS` appends `seen again at HH:MM` to the file it already has, because forty files about one dead credential is how a folder stops being opened; the folder is capped at `MAX_REPORTS`, oldest first and never the one just written. **Redaction is one function over the WHOLE composed file**, never per section — a regex skipped for the part that "cannot hold a token" is the one that misses the day it does — and `file_incident` **never raises**, because it is called from accounting code and a report that took down the run it was reporting on is worse than no report. It writes to `/share/brain/reports` rather than `/data` precisely so the file editor and the Samba share can reach it without the panel, which is the same reason it is **not** in `backup_exclude` and therefore the reason the redaction has to be unconditional. It must not import `server`: the diagnostics it abridges arrive as a dict or a callable from whoever has one. `brain report` writes the same single file — no directory, no tarball — and assembles it itself when the panel is down, which is exactly when a report is most wanted; ⚙ → Diagnostics → Report a problem lists them with a checkbox each (Share sends the ticked ones), and HA's Repairs carries `health_degraded` while the verdict is not `ok`, deleted the moment it returns.
- **A report whose faults are buried is a report nobody reads** (`reports.faults` / `faults_text`, `_diagnostics_payload`'s `faults`). What shipped opened with *"Nothing failed to produce this file"* and then six hundred lines of JSON, and the install that prompted this carried seven distinct faults inside it — a rehearsal that could not clean up, a usage credential refused for a reason nothing recognised, a deep check that had failed, a check that could not look, a measurement store reading zero, a notification that would not deliver, and a producer the homeowner had marked Wrong six times out of six. Every one was in the file. None was *findable*, because finding one meant already knowing which of a dozen sections it would be in. So the sweep is deliberately exhaustive rather than clever — every surface the payload can say something went wrong on, read in one pass — and the rows go at the **top**, above the log and the JSON, and at the top of ⚙ → Diagnostics. **It is the inventory and `health` is the VERDICT**, which are different questions and both are wanted: the verdict is the worst thing found and names a switch, while a check that could not look, a rehearsal that left something behind and a rule that is wrong about this house are all faults and none of them is brAIn failing to work. Three rules. **Pure over what it is handed** — no imports of `server`, no fetches, no clock beyond the payload's own stamps — so it runs when the panel is down, which is exactly when a report is most wanted, and one derivation means a person and a machine reading the same file cannot disagree (`abridge` carries the same rows the prose renders). **A refusal doing its job is not a fault**: `heal_skipped`, a `denied` run, a producer standing down because it could not read a file, a scorecard row that is mostly *confirmed* — a section that listed those is one people learn to skim, which is the failure it was written against. And **it never raises**, `file_incident`'s rule one function over: a sweep that took down the report it was summarising is worse than no sweep, so a payload it cannot read is a row saying so. `compose` resolves the callable **once**, because two sections building the same payload is two chances to disagree about a house that is still moving.
- **A failed run's fault row names what it was about and when** (`reports._run_subject` over `extra.title`/`label`/`category_title`/`about`/`id`). The subject is in `what`, which is stable per card; the latest occurrence's time is in `detail`, because the devloop fingerprint folds digits and keeps words and a weekday is a word. `_generate`'s journal lines carry `title` (`_card_label`); an engine run's line carries no subject because `engine.py` is the human's to change, and its row reads as before.
- **A guard that refuses has to change the next attempt, and the rehearsal's could not** (`rehearsal.sweep`). One run that failed to clean up left `brain_test_dead_ref` in `automations.yaml`; `automation_writer.apply` refuses a duplicate id — correctly, since two entries under one id is a config Core will not load — so every run after it ended on the first row with nothing planted, and `_remove_all` could not clear it either, because it takes back what THIS run created and this run created nothing. Identical failure, for ever, with the one thing that would end it sitting in a file the panel is perfectly able to edit and nothing on the page saying so. The sweep runs **before** planting and three things keep it from being a licence to delete: it removes only what `leftovers` sees **under the prefix** — the same scan the cleanup proves itself against and the same one `brain doctor` warns about, so nothing here decides for itself that something looks like a leftover; it runs **inside the consent already given**, `brain_test_*` being brAIn's own litter; and it is **reported**, never silent, because a sweep that quietly removed things is indistinguishable from a house that never had them and the line that says what it took is also the only evidence the run before it failed. A sweep that cannot finish **refuses the run** naming what is in the way, which is the answer the loop never gave. Three removals are one function each now (`_take_out_automation`/`_take_out_registry`/`_take_out_helper`) shared with `_remove_all`, and the first of them fixed a second bug: `_remove_automation` answers "already gone" as a removal that happened, the hook flattens that to `(False, "")`, and reading the first value alone reported a success as a failure **with no reason on it** — `brain_test_dead_ref: ` is the sentence that produced, and a fault with an empty explanation is the one nobody can act on.
- **The sweep was a step inside a run, so the only way out of its failure was the run.** `sweep` clears the litter *before planting*, which fixed the loop — and left the remedy for "a rehearsal left something behind" as **another whole rehearsal**: two automations written into somebody's `automations.yaml`, a helper created, a checks pass and a Claude turn, to delete three things. `brain doctor`'s other suggestion was to open `automations.yaml` and edit it by hand. Both are heavier than the fault, and one of them is the panel asking a person to do what the panel is perfectly able to do — the `unsettle` route's failure in a new place, where the machinery existed and nothing could reach it. So `sweep_only` is a press of its own (⚙ → Developer, `brain doctor --sweep`, `POST /api/doctor/rehearse/sweep`) that creates nothing, asks no model and spends nothing. **It needs no consent step** precisely because of that: the 428 exists because a rehearsal WRITES, and what this removes is what `leftovers` already sees under brAIn's own prefix, which is the warning that sent somebody here. **And it re-earns the verdict** — `cleanup_ok` was written once by the run that failed, so after the litter was gone the report went on opening with *Rehearsal: left something behind* for ever, which is the auth re-check's rule with the timer taken off. A sweep is recorded as `cleared` **beside** the cleanup and never over it: the run's own failure is the evidence that a cleanup failed, and it is the one thing editing the record would lose. `_cleared_ok` requires the sweep to have both **run** and **seen nothing left**, because "I could not look" and "it went away" are different claims here too; `outstanding()` is the one derivation of "is there litter", read off the record rather than a live snapshot (this is asked on every poll of an open dialog), so the button that offers to clear it and the fault row that reports it cannot disagree. The button renders only while there is something to take out — BRUH Print's `Forget` rule — and the two presses carry **separate** in-flight states, because a button that greys itself out while the other one runs is a pair of controls nobody can tell apart. `sweep` stays deliberately silent on a clean house (it runs before every plant, and a "nothing to clear up" row above every rehearsal is what makes the one that DID remove something skimmable) and `sweep_only` supplies the sentence for that one case, because a press always has an answer.
- **A successful mutation answers `result: null`, which is the same value as a refusal** (`ha_data._ws_calls`). `_ws_commands` hands back Core's `result` field per command and `None` for anything that went wrong, which is right for every command that ASKS for something and wrong for one that CHANGES something: `input_number/delete` answers `result: null` on success. The rehearsal read that as the failure sentinel and reported *"Home Assistant would not delete input_number.brain_test_reading"* on every clean run — while its own leftovers scan, reading the states where the helper really had gone, disagreed with it in the same sentence. `_ws_calls` reports `{ok, result, error}` and `_ws_commands` is layered on it, one round trip, because two would be two chances to disagree about what Core said. The fake could not produce the bug: it returned a truthy `{}` where Core sends `null`, so the branch that fired in the field was unreachable in the suite.
- **Removing an automation does not remove its entity, and verifying otherwise reverted the removal** (`server._wait_for_gone` / `_is_restored_orphan`). Every automation brAIn writes carries an `id`, so Core gives it a `unique_id` and therefore an entity registry entry — and a registry entry outlives its provider: splice the entry out of `automations.yaml`, reload, and Core unloads the automation and re-publishes the orphan as `unavailable` carrying `restored: true`. `GET /api/states/<id>` answers 200 for that, for ever. So `_wait_for_gone` polled a 200 that was never going to become a 404, spent the whole `ACCEPT_VERIFY_S`, reported that the automation "was not really removed" — and `_remove_automation` then did the honest thing with a failed verification and **put the entry back**. The removal worked every time; the check condemned it and the revert undid it, which is why a rehearsal's cleanup listed its own planted automations as left behind in the file AND in the states. `checks/devices.restored` already reads exactly that shape and names it. What is being verified is that nothing provides it any more, and a restored orphan is Core saying so in as many words — and the rehearsal deletes the registry entry too, because half a cleanup is a leftover under a prefix `brain doctor` warns about. `input_number/delete` keys on the item id Core MINTED, carried from the create call rather than derived from the entity id: `IDManager.generate_id` slugifies a name only while the slug is free and appends `_2` otherwise, so a guessed id deletes nothing on exactly the house that already has a leftover from last time. And `leftovers` reads `snap["entities"]`, which is the key the collector emits — it read `snap["registry"]`, which it never has, so one of its three places iterated over nothing in production while the suite's own fake built the key to match.
- **"Is brAIn working" is one press at the top of Diagnostics, and its answer is the header** (`#deepBox` / `renderDeep` / `deepCountLine`, `doctor.run_deep`'s per-stage `at`). The owner asked to *"run all the development tests"* from the panel; the deep check already was that (`brain doctor --deep`, every face, one real round trip each) and lived at the bottom of a Developer fold as `✓`/`✗`/`–` glyphs beside stage names with the verdict in a line under the button. It is **Run all tests** now, first in Diagnostics, still a press and never a timer (it spends Claude runs). The header reads **"N of M passed · K skipped"**, M counting the stages that RAN: a stage skipped over a failed precondition or a switch that is off did not pass and did not fail, and folding it into either number is the misreading the old line invited. Each stage is a row: **Passed / Failed / Skipped in words** (a mark alone was the part nobody could read at a glance; skipped is muted, never red), the stage's own sentence as the reason, and **the time it ran** — `run_deep` stamps `at` on every stage, skipped ones included, because a row with no time reads as one that never got to run; an older payload with no `at` shows the run's finish. While a run is in flight the stage catalog fills the rest as Running/Waiting rows. `tests/test_doctor_deep.py::test_every_stage_says_when_it_ran` holds the stamp; `measure-settings` holds the header, the words, the reasons and the times over a stubbed run with a failure and two skips.
- **A verdict on the add-on itself, because every failure it has shipped was a quiet one** (`panel/health.py`). A listener that died, a credential that expired on a Tuesday afternoon, a consolidator running and landing nothing — each visible from inside for hours before anybody noticed from outside, and each answerable only by somebody running `brain doctor`. The verdict is **a state and a sentence, never a score**: one number over a house hides its worst problem inside an average, and an average moving from 92 to 88 is not something anybody can act on, so the state is the worst thing found, the reason names *that*, and the rest rides underneath. Every problem names the switch rather than the symptom. **Optional is not broken** — the daemon roll-call is descriptive by design, so the interpretation happens here and against the options, and voice is asked about as a *job* rather than by daemon name because `assist_fast_mode` decides which of two implementations is correctly absent. **"I could not look" is its own answer**: an empty roll-call is `/proc` unreadable rather than seven dead daemons, and a missing `.last_consolidated` is a fresh install rather than a stale one. **A verdict whose remedy is to do nothing is not a verdict** (`usage_store.NEEDS_NOTHING` / `needs_nothing`): `problems` reported *any* `usage.limits` code as `degraded`, and the commonest one by far is `oauth_token_awaiting_refresh` — the status whose own gloss says nothing is wrong with the sign-in and that signing in again will not make the figure arrive sooner, because Claude Code mints the next access token itself on its next run. So `sensor.brain_health` went `degraded`, HA's Repairs raised `health_degraded` and `reports.file_incident` wrote a problem file, several hours out of every day, about a credential doing what credentials do — the check catalog's own first rule (a check that fires on a healthy house is worse than no check) broken by the module that IS the verdict. It is absent from the tracker's `AUTH_PROBLEMS` for that exact reason and health was the one reader that had not been told. `api_key_has_no_usage_limits` is in the set for the opposite reason — it can never clear, so degraded is permanent over an account that is working — and `http_429` because the tracker answers it with a backoff ladder built for it, which is a refusal doing its job at any age (past a day only its sentence changes, `OVERDUE_AFTER`, the tracker bullet); everything else names something a person can do and stays a fault, and **a code the set does not recognise is a fault**, because "I could not tell what this means" and "there is nothing to do" are different claims. The vocabulary lives beside `limits_problem`, which owns that file, and the answer is **stamped on the payload** rather than imported: `health.py` is stdlib-only and pure over the dict it is handed (`reports.py` imports it and must run with the panel down), so an older mirror with no flag reads as False and the fault surfaces, which is the safe direction. `reports.faults` stands the row down on the same flag, its own "a refusal doing its job is not a fault" rule broken by the row it produced most often. The fixture could not see any of it: `test_health` had written `limits` down as a bare **string** for four releases where `limits_problem` returns a dict, so `if usage.get("limits")` passed on it — the `_error_code` envelope failure again, which is why the replacement is copied from a real report. It is derived once, at the end of `_diagnostics_payload`, so the panel, the mirror, the sensor, `brain doctor` and `brain report` cannot disagree.
- **A pool process is not a pool answering, and a restart owed is something to do** (`health._assist_daemon` / `_restart_owed` / `POOL_HEARTBEAT_STALE_S`, `server._daemon_rollcall`'s `heartbeat_age_s`). A house read `ok` with "everything brAIn runs is running" while `sensor.brain_status` said `needs_restart`. Two gaps, neither the faults-vs-verdict split. `_assist_daemon` asked only whether a pool PROCESS was in `/proc`; the roll-call now carries the pool's heartbeat age off `pool_status.json`'s mtime, and a running pool whose heartbeat is past 150s is `failed` (`assist_pool`) — `workers: 0` is an idle pool (workers are per conversation), not a fault, and a payload with no age accuses nobody. A pending integration restart is `degraded` naming the restart (`restart`), so the health sensor and the status line agree; `reports.faults` keeps its own versioned row and skips the health copy (`HEALTH_ROWS_OF_THEIR_OWN`), `BrainHealthSensor` raises no second Repairs entry when the restart is the only problem, and `reports.note_health` records a restart-only verdict as `ok` (`NOT_INCIDENTS`) so an ordinary update writes no problem file while a real fault beside it still does. The quiet sentence says "everything brAIn runs is running" only when the roll-call was read.
- **"Assist healthy" follows whether voice answers** (`custom_components/brain/assist_health.judge`, no HA import). The pool's `/health` is served by its HTTP thread, which answered `ok` whatever its main loop was doing; the pool now stamps `loop_at` every loop and `health_status` says `stalled` with `loop_age_s` past `LOOP_STALL_S` (150, held equal to `HEARTBEAT_FRESH_S` and `health.POOL_HEARTBEAT_STALE_S` by tests). The order: a live HTTP answer, then a fresh diagnostics mirror whose verdict says voice is down (`assist`/`assist_pool`), then the heartbeat file aged by its **mtime** (a `ts` from a corrected clock read fresh for ever), then the roll-call for a classic listener. Never unavailable: nothing to read is unknown with a `reason`.
- **`sensor.brain_health` never goes unavailable, and a stale verdict is not a healthy one.** HA hides the attributes of an unavailable entity, so an entity that vanishes takes its own explanation with it — and this is the entity somebody looks at precisely when the others have gone, so "the panel has published nothing" is a *state*. The reader has one question the panel cannot ask itself: the mirror is rewritten after every checks pass and hourly in between, so a file that has stopped changing means the panel has stopped running, and serving its last good verdict would be a reading nothing can correct (the usage sensors' own bug). The freshness window is **published in the payload** (`stale_after_h`) rather than agreed twice, and the sensor stats the **file's mtime** rather than trusting `generated_at`, because a corrected clock leaves a stamp in the future and a verdict that can never go stale is a verdict nothing can correct.
- **`brain doctor` says the plumbing is connected; `--deep` does the thing** (`panel/doctor.py`). A token present, an MCP handshake, a daemon with a pid — every one of those is true on an install whose credential died on a Tuesday, whose automation listener is holding a folder open with nothing behind it, or whose allow-list has stopped letting a read through. So eight stages, each a real round trip with its own budget and its own sentence naming the switch or the log to look at, and BRight's `director_check` is the shape. Two differences, both because there are eight faces rather than one chain: **every stage is reported**, since "the chat works and the automation listener does not" is the answer and the first break hides it; and **a stage whose precondition failed is SKIPPED with the reason**, since eight identical auth failures is a report nobody reads past line one. **Opt-in, costed and never on a timer** — the auth re-check's rule, for the auth re-check's reason. **Every stage cleans up and the cleanup is verified**, and a leftover is that stage's failure: the synthetic fact is not in `memory.md`, the synthetic finding is in neither the store nor the settled ledger, the helper is deleted. **Optional is not broken** (`health.py`'s rule): Assist off, the automation listener off and `protected_entities` covering the helper `fixer_dry` renames are all *skips* naming their switch — a list doing its job is not a fault. The **chat stage never joins the registry and never evicts**: an answer surviving you looking elsewhere is the point of holding several, and a check that closed somebody's conversation to prove the chat works would be exactly wrong, so a full registry is a skip carrying the cap's own sentence. **A timeout is reported by name** and never as "not authenticated". The three operations only the panel can do arrive as `Hooks` — `_end_finding`, `_undo_finding` (lifted out of `h_undo`'s closure for the reason `_end_finding` was lifted out of `h_finding_verb`) and `_consolidate_now` — because a second implementation of an ending here would be the same press teaching brAIn two different things depending on who asked. Runs claim the `doctor` source before they start, so the Chats rail does not offer a probe as a conversation somebody had, and they ride the generation queue like a fix run. They take no `run_queue` seat — `doctor.py` calls the engine through `asyncio.to_thread` — which the comment above `DOCTOR_JOB` says out loud, because a costed check that is pressed by hand and capped at a handful of turns is not what that bound is for. The last verdict — when, what, which stage — rides `/api/diagnostics`; the stage list is a page of prose and belongs on the screen that asked.
- **A storage collection's id comes from the NAME, and the deep check stated both** (`doctor.FIXER_HELPER_NAME` / `_ensure_helper`). `IDManager.generate_id` slugifies whatever a helper was called while the slug is free and appends `_2` otherwise, so the entity id is a consequence to be read back and never a second constant. `fixer_dry` created its helper as `"brAIn deep check"` — `input_boolean.brain_deep_check` — and then polled ten seconds for the `input_boolean.brain_test_doctor` the other constant named, reporting **"brAIn could not create ... check that the Supervisor token is valid"** about a token that had just done exactly what it was asked. That is the visible half. The quiet half is that the cleanup keyed on the same guessed id and deleted nothing, and `brain_deep_check` is not under `PREFIX`, so neither `rehearsal.leftovers` nor the sweep could see it: one helper per run, accumulating in the one place nothing was looking for litter. The id is read off the create call now — `rehearsal._take_out_helper`'s rule, one module over — and the prompt handed to the fix run, the verification and the delete all key on it; the two names are chosen so a free slug lands under the prefix, which is what makes a future leftover visible at all. `_sweep_helpers` runs before each create, matched on the **name** brAIn gave (`rehearsal._helper_items`' reason: an item whose slug collided is exactly the one a derived id cannot name), covering the legacy name as well so an install carrying the shipped bug's litter is tidied; it asks `protected_entities` about each one (the stage's own ask is about `FIXER_HELPER`, and these carry ids an older build chose — an unattended delete must not fall through the gap between two spellings of nearly the same entity), and it is **reported in the stage's detail**, `rehearsal.sweep`'s rule, because a sweep that quietly removed things is indistinguishable from a house that never had them — and it clears the collision rather than surviving it, since the litter otherwise holds `brain_test_doctor` and the next create comes back `_2`. The suite could not see any of it: its fake answered `input_boolean/create` by appending a row whose entity id was the constant, writing down the same guess the code did, which is why the fix's load-bearing part is a fake that **mints the id from the name**, `_2` and all.
- **The suite tests the checks on fixture houses; the rehearsal tests them on YOURS** (`panel/rehearsal.py`). Every late bug in this add-on's history lived in the one place the suite cannot see: this install's HA version, its integrations, its data shapes. So `brain doctor --rehearse` plants a small set of `brain_test_*` defects through the paths brAIn already owns (automations through `automation_writer`'s write-reload-verify, so the rehearsal is also a round trip of the writer), runs the checks and the analyst against them, scores both, and removes everything. **Consent is a named step, and it is a 428**: a call without `{"consent": true}` is answered with the exact list of what would be created — ids, what each is for — and nothing is created before the answer comes back. **It calls `checks.run_all`, never `server.run_checks`**: the second files to the store, notifies, and clears, which would ring somebody's phone about a defect brAIn planted and let a planted row clear a real one. **A check whose floor is measured in days is named as not rehearsable rather than counted as missed** — `auto.forgotten_off` needs thirty days off and `dev.frozen` a week of statistics, and a rehearsal that pretended otherwise would report a working check as broken every time. **The analyst score is the point**: "on this house, this HA version, this model, it found 3 of 4 and reported 1 that was not there" is what makes a prompt change measurable somewhere other than the developer's own home, and it runs the automations card's own prompt builder in a mode that persists no card and files no findings. **Removal is in a `finally` and is verified against a fresh snapshot** — a rehearsal that fails halfway still cleans up, and a cleanup that fails is the loudest line in the report. **And the plain `brain doctor` is what catches the one that did not clean up**: it warns on any `brain_test_*` automation, entity or helper and names the command that removes it, which is the design page's own recommendation for shipping this at all. `health.py` deliberately does NOT carry it as a `degraded` reason — a left-behind test helper is a tidy-up, not brAIn failing to work, and the health sensor's whole value is that its states mean something. Its scoring arithmetic is `panel/scoring.py`'s, shared with the corpus replay, because "precision against labels" having two answers is the drift `_CARD_CONTRACT` is shared to avoid.
- **A run journal nothing reads back is a run journal that only exists in somebody else's bug report.** `journal.summary` was written for the ⚙ dialog's Diagnostics section and shipped a release before it, so for one release the only route to it was `brain report` — which is to say, the only people who ever saw it were the ones who had already been asked for it. The section renders `/api/diagnostics` (the same payload as the mirror and HA's Download-diagnostics button), fetched when the dialog opens and on ⟳ and **never on a timer**: this is something you look at, and a poll behind a dialog nobody has open is a request per viewer per interval for an answer that changes hourly. It names **which checks could not run and why**, because a skipped check did not find nothing — it could not look, and it is the same check that `clear_resolved` may not clear a row for, so "12 ran, 3 skipped" and "15 ran" are different reports of the same quiet house. Copy falls back to a selected `<textarea>`: an ingress iframe may be refused `navigator.clipboard` outright with no way to ask in advance, and a failure that only says "could not copy" leaves the text nowhere a person can reach it.
- **The run journal counts what the log only mentions** (`panel/journal.py`). One JSONL line per Claude run of any kind and per checks pass, hooked in `engine._run_cli` (every `-p` run, whatever happened to it), `chat_session._normalise` (the `result` event) and `server.run_checks`, with a fixed outcome vocabulary (`journal.OUTCOMES`) so a bundle can say "3 of 12 insight runs ended `unparseable`". `fallback` is an outcome — the search→snapshot slide is recorded at the point it is logged — because a fallback nobody counts is a fallback read as the real thing. Never prompts or replies; error text goes through `journal.scrub` before it lands, because this file is what `brain report` attaches to an issue. `record` never raises: accounting must not fail the run it is accounting for.
- **Diagnostics is one payload with three doors** (`server._diagnostics_payload`): `GET /api/diagnostics`, the mirror at `/config/.brain/diagnostics.json` (written after every checks pass and hourly from `_checks_loop`, skipped on a dev checkout with no `/config` — same rule as the findings mirror), and the integration's `diagnostics.py`, which is what puts something behind Home Assistant's own **Download diagnostics** button. `brain report` bundles the mirror's source, `brain doctor --json` and the add-on log tail into `/share/brain/reports/`, and `redact()` runs over *every* file whether or not it "can" hold a token — a regex skipped for the file that can't is the one that misses the day it does. `ha-selftest.sh` records every pass/fail/warn/info line either way and only the printing changes under `--json`; `tests/test_doctor_json.py` lifts the report block out of the script and drives it, the same way `consolidator_lock_check` is tested.
- **A prompt is the one part of this add-on no test has ever run** (`panel/capture.py` + `tests/corpus/`). `_CARD_CONTRACT` is ten kilobytes of output rules shared by two prompt builders, and nothing in the repository puts either of them in front of a real house or a real model — which is BRight's `detect_hits` exposure exactly: zero results on every real track for the feature's whole life, with a green suite behind it, because the only fixture was synthetic. So `capture` records what the analyst was sent and what came back, and **the ending is the label**: an ending on the Findings tab already says whether the report was right, so pairing it with the prompt that produced it turns a house into a graded example. It is hooked in `_end_finding`, the one door every ending comes through, so the label is a property of the ANSWER rather than of the surface it was given on. **Off by default** — the design page's own "not building" list says *any capture that is on by default*, because a house's entity names are a floor plan — **redacted on the way IN** (a redaction applied on the way out never ran for the file somebody found another way; the shell's `redact()` and `capture.redact` are driven against the same fixture strings in `tests/test_capture.py`), **capped** at fifty files, named in `backup_exclude`, and reaching `/share` only through a press. The id is the one Claude Code already minted — `engine._run_cli`'s session id, claimed in `run_sources` before the run — so a capture, a journal line (`run_id` is a column), a transcript and a Chats rail row name the same run; a house check carries none, which is honest, because nothing was asked and there is no prompt to grade. A run id off the wire is not a filename: `safe_id` plus `chat_session.transcript_path`'s normpath-and-prefix barrier, spelled the same way for the same reason.
- **A corpus entry is frozen, and nothing regenerates it.** `tests/corpus/build.py` writes the two that ship — the suite's own clean fixture house, whose whole label is *nothing fires here*, and that house with `rehearsal.PLAN` planted in it — and then nothing asserts the committed files still match what the builder would produce today, because **an entry whose expectations are regenerated from the current code cannot fail when the code changes**, which is the one thing it exists to do. Every timestamp inside one is relative to the snapshot's own `now`, which is stored with it, so a replay next year grades what a replay today does. The **checks** half of `replay.py` is `run_all` and nothing else and rides ordinary CI (`tests/test_corpus.py`): it is what fails when a floor moves, and it names the *house* that went quiet or loud. The **analyst** half rebuilds the prompt with the current builder — a stored prompt would grade the release that captured it — caps spend three ways with `--max-tokens` checked *before* each run (a cap that stops once it has been passed has already spent the run that passed it), and **skips a `search` entry rather than faking it**, because that run read the house with tools and grading the prompt where they reach nothing measures a model that cannot look anything up. `schema.json` says out loud that nothing validates against it (no `jsonschema` dependency for two files agreeing about a shape) and a test asserts the structural validator's required keys, kinds and ending words are the *same lists* it publishes. One scorer, in `panel/scoring.py` rather than under `tests/`, because `rehearsal.py` ships inside the add-on and cannot import from the test tree while the test tree already has `panel/` on its path; nothing over nothing answers 0.0, never 1.0. **The ending words are one list published in three places** (`tests/corpus/score.py`'s `CONFIRMED`, `schema.json`'s enum, `test_corpus.VERBS`) and `accepted` is the fourth of them — moving a card onto the to-do list is somebody agreeing the report was real work, which is the same evidence about the producer as having done it, so the chore finishing later re-labels nothing.

# brAIn: health, doctor, reports and the corpus

The health verdict and sensor, brain doctor and --deep, the rehearsal, problem reports and faults, diagnostics payload, capture and the corpus.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

What each rule cost to learn is in `docs/notes/history/diagnostics.md`. Tests named here were removed in November 2026 with the old suite; the rules they held still hold. The eval harness (`tests/evals/`, `evals.yml`) went with it, and its rules are kept in the history file.

## Problem reports and faults

- **One problem, one text file, written when it happens** (`panel/reports.py`). Every other tool for answering "what went wrong" is pull-shaped (`brain doctor`, ⚙ → Diagnostics, `brain report`), so by the time anybody looks, the journal row that would have explained it is one of thousands. Three producers and one writer: a journal row ending in a `FAILURE_OUTCOMES` outcome (**a listener on `journal.record`**, which every Claude run, checks pass, baseline build and overnight heal already passes through, so nothing new has to remember to report), the health verdict *leaving* `ok` (the daemon that died, the credential that expired), and a notification that could not be delivered (the one failure whose only symptom was silence on a phone). A refusal doing its job is not a fault and writes nothing — `heal_skipped` and `denied` are out of that set on purpose, as is `fallback`, which still produced a card. **A repeat is a line, not a file**: the same `fingerprint(kind, source, outcome, error)` inside `DEDUP_HOURS` appends `seen again at HH:MM` to the file it already has, because forty files about one dead credential is how a folder stops being opened; the folder is capped at `MAX_REPORTS`, oldest first and never the one just written. **Redaction is one function over the WHOLE composed file**, never per section — a regex skipped for the part that "cannot hold a token" is the one that misses the day it does — and `file_incident` **never raises**, because it is called from accounting code and a report that took down the run it was reporting on is worse than no report. It writes to `/share/brain/reports` rather than `/data` precisely so the file editor and the Samba share can reach it without the panel, which is the same reason it is **not** in `backup_exclude` and therefore the reason the redaction has to be unconditional. It must not import `server`: the diagnostics it abridges arrive as a dict or a callable from whoever has one. `brain report` writes the same single file — no directory, no tarball — and assembles it itself when the panel is down, which is exactly when a report is most wanted; ⚙ → Diagnostics → Report a problem lists them with a checkbox each (Share sends the ticked ones), and HA's Repairs carries `health_degraded` while the verdict is not `ok`, deleted the moment it returns.
- **A report whose faults are buried is a report nobody reads** (`reports.faults` / `faults_text`, `_diagnostics_payload`'s `faults`). The sweep is deliberately exhaustive rather than clever — every surface the payload can say something went wrong on, read in one pass — and the rows go at the **top**, above the log and the JSON, and at the top of ⚙ → Diagnostics, because finding a fault must not mean already knowing which of a dozen sections it would be in. **It is the inventory and `health` is the VERDICT**, which are different questions and both are wanted: the verdict is the worst thing found and names a switch, while a check that could not look, a rehearsal that left something behind and a rule that is wrong about this house are all faults and none of them is brAIn failing to work. Three rules. **Pure over what it is handed** — no imports of `server`, no fetches, no clock beyond the payload's own stamps — so it runs when the panel is down, which is exactly when a report is most wanted, and one derivation means a person and a machine reading the same file cannot disagree (`abridge` carries the same rows the prose renders). **A refusal doing its job is not a fault**: `heal_skipped`, a `denied` run, a producer standing down because it could not read a file, a scorecard row that is mostly *confirmed* — a section that listed those is one people learn to skim. And **it never raises**, `file_incident`'s rule one function over: a payload it cannot read is a row saying so. `compose` resolves the callable **once**, because two sections building the same payload is two chances to disagree about a house that is still moving.
- **Home Assistant not answering is one fault however many reads it took down, including the ones that do not say so** (`reports._ha_down_keys`, `snapshot.collect`'s `_mark(..., core=True)` and `core_failed`, the summary's `snapshot_core_failed`, `upstream.blind_rows(data, faults)` and the Screens `ha` reason class). Each read says at its own call whether it asked Core, rather than being matched against the words of an outage, because the reads that fail *because of* an outage say so in their own words (a recorder query that handed back nothing, a history read skipped because the registry was not read, the logbook, the Screens stream refusing to photograph). When Core's anchor reads (`states`, `registry`) did not answer, every Core read that failed in that pass is listed on the one "Home Assistant did not answer" row; files, brAIn's stores and the Supervisor never fold. A Screens refusal for the same reason is said on that row and files nothing; with no such row it files only on a second try in a row. A Core read that fails while the anchors answered keeps its own row: that is a broken query, not an outage.
- **A failed run's fault row names what it was about and when** (`reports._run_subject` over `extra.title`/`label`/`category_title`/`about`/`id`). The subject is in `what`, which is stable per card; the latest occurrence's time is in `detail`, because the devloop fingerprint folds digits and keeps words and a weekday is a word. `_generate`'s journal lines carry `title` (`_card_label`); an engine run's line carries no subject because `engine.py` is the human's to change, and its row reads as before.

## The health verdict

- **A verdict on the add-on itself, because every failure it has shipped was a quiet one** (`panel/health.py`). A listener that died, a credential that expired, a consolidator running and landing nothing — each visible from inside for hours before anybody noticed from outside. The verdict is **a state and a sentence, never a score**: one number over a house hides its worst problem inside an average, so the state is the worst thing found, the reason names *that*, and the rest rides underneath. Every problem names the switch rather than the symptom. **Optional is not broken** — the daemon roll-call is descriptive by design, so the interpretation happens here and against the options, and voice is asked about as a *job* rather than by daemon name because `assist_fast_mode` decides which of two implementations is correctly absent. **"I could not look" is its own answer**: an empty roll-call is `/proc` unreadable rather than seven dead daemons, and a missing `.last_consolidated` is a fresh install rather than a stale one. It is derived once, at the end of `_diagnostics_payload`, so the panel, the mirror, the sensor, `brain doctor` and `brain report` cannot disagree.
  - **A verdict whose remedy is to do nothing is not a verdict** (`usage_store.NEEDS_NOTHING` / `needs_nothing`). `oauth_token_awaiting_refresh` — the commonest `usage.limits` code, whose own gloss says nothing is wrong with the sign-in because Claude Code mints the next access token itself on its next run — is not `degraded`, raises no Repairs and files no problem; it is absent from the tracker's `AUTH_PROBLEMS` for the same reason. `api_key_has_no_usage_limits` is in the set because it can never clear, and `http_429` because the tracker answers it with a backoff ladder built for it, which is a refusal doing its job at any age (past a day only its sentence changes, `OVERDUE_AFTER`, the tracker bullet); everything else names something a person can do and stays a fault, and **a code the set does not recognise is a fault**, because "I could not tell what this means" and "there is nothing to do" are different claims. The vocabulary lives beside `limits_problem`, which owns that file, and the answer is **stamped on the payload** rather than imported: `health.py` is stdlib-only and pure over the dict it is handed (`reports.py` imports it and must run with the panel down), so an older mirror with no flag reads as False and the fault surfaces, which is the safe direction. `reports.faults` stands the row down on the same flag. `limits_problem` returns a dict, never a bare string; a fixture for it is copied from a real report.
- **A pool process is not a pool answering, and a restart owed is something to do** (`health._assist_daemon` / `_restart_owed` / `POOL_HEARTBEAT_STALE_S`, `server._daemon_rollcall`'s `heartbeat_age_s`). The roll-call carries the pool's heartbeat age off `pool_status.json`'s mtime, and a running pool whose heartbeat is past 150s is `failed` (`assist_pool`) — `workers: 0` is an idle pool (workers are per conversation), not a fault, and a payload with no age accuses nobody. A pending integration restart is `degraded` naming the restart (`restart`), so the health sensor and the status line agree — and "pending" is by the code's fingerprint, not the version, so an update that changed no integration code degrades nothing (`docs/notes/architecture.md`, the custom integration); `reports.faults` keeps its own versioned row and skips the health copy (`HEALTH_ROWS_OF_THEIR_OWN`), `BrainHealthSensor` raises no second Repairs entry when the restart is the only problem, and `reports.note_health` records a restart-only verdict as `ok` (`NOT_INCIDENTS`) so an ordinary update writes no problem file while a real fault beside it still does. The quiet sentence says "everything brAIn runs is running" only when the roll-call was read.
- **"Assist healthy" follows whether voice answers** (`custom_components/brain/assist_health.judge`, no HA import). The pool's `/health` is served by its HTTP thread, which answers `ok` whatever its main loop is doing, so the pool stamps `loop_at` every loop and `health_status` says `stalled` with `loop_age_s` past `LOOP_STALL_S` (150, equal to `HEARTBEAT_FRESH_S` and `health.POOL_HEARTBEAT_STALE_S`). The order: a live HTTP answer, then a fresh diagnostics mirror whose verdict says voice is down (`assist`/`assist_pool`), then the heartbeat file aged by its **mtime** (a `ts` from a corrected clock reads fresh for ever), then the roll-call for a classic listener. Never unavailable: nothing to read is unknown with a `reason`.
- **`sensor.brain_health` never goes unavailable, and a stale verdict is not a healthy one.** HA hides the attributes of an unavailable entity, so an entity that vanishes takes its own explanation with it — and this is the entity somebody looks at precisely when the others have gone, so "the panel has published nothing" is a *state*. The mirror is rewritten after every checks pass and hourly in between, so a file that has stopped changing means the panel has stopped running, and serving its last good verdict would be a reading nothing can correct. The freshness window is **published in the payload** (`stale_after_h`) rather than agreed twice, and the sensor stats the **file's mtime** rather than trusting `generated_at`, because a corrected clock leaves a stamp in the future and a verdict that can never go stale is a verdict nothing can correct.
- **A Resident held by an allowance is not "everything is running"** (`RESIDENT_STATE["held_since"]`, `health._resident_problems`, #631). A look refused by the ledger or the day's count starts the hold, a look ends it; past an hour it is `degraded` with the refusal's own sentence, and a queue over 80% is `degraded` too. A gate a person chose (paused, the usage budget) is not a hold. The status line's "last look" is the Resident's own, never a checks pass.

## The diagnostics payload and the run journal

- **Diagnostics is one payload with three doors** (`server._diagnostics_payload`): `GET /api/diagnostics`, the mirror at `/config/.brain/diagnostics.json` (written after every checks pass and hourly from `_checks_loop`, skipped on a dev checkout with no `/config` — same rule as the findings mirror), and the integration's `diagnostics.py`, which is what puts something behind Home Assistant's own **Download diagnostics** button. `brain report` bundles the mirror's source, `brain doctor --json` and the add-on log tail into `/share/brain/reports/`, and `redact()` runs over *every* file whether or not it "can" hold a token — a regex skipped for the file that can't is the one that misses the day it does. `ha-selftest.sh` records every pass/fail/warn/info line either way and only the printing changes under `--json`.
- **A run journal nothing reads back is a run journal that only exists in somebody else's bug report.** ⚙ → Diagnostics renders `/api/diagnostics` (the same payload as the mirror and HA's Download-diagnostics button), fetched when the dialog opens and on ⟳ and **never on a timer**: this is something you look at, and a poll behind a dialog nobody has open is a request per viewer per interval for an answer that changes hourly. It names **which checks could not run and why**, because a skipped check did not find nothing — it could not look, and it is the same check that `clear_resolved` may not clear a row for, so "12 ran, 3 skipped" and "15 ran" are different reports of the same quiet house. Copy falls back to a selected `<textarea>`: an ingress iframe may be refused `navigator.clipboard` outright with no way to ask in advance, and a failure that only says "could not copy" leaves the text nowhere a person can reach it.
- **The run journal counts what the log only mentions** (`panel/journal.py`). One JSONL line per Claude run of any kind and per checks pass, hooked in `engine._run_cli` (every `-p` run, whatever happened to it), `chat_session._normalise` (the `result` event) and `server.run_checks`, with a fixed outcome vocabulary (`journal.OUTCOMES`) so a bundle can say "3 of 12 insight runs ended `unparseable`". `fallback` is an outcome — the search→snapshot slide is recorded at the point it is logged — because a fallback nobody counts is a fallback read as the real thing. Never prompts or replies; error text goes through `journal.scrub` before it lands, because this file is what `brain report` attaches to an issue. `record` never raises: accounting must not fail the run it is accounting for.

## brain doctor and --deep

- **`brain doctor` says the plumbing is connected; `--deep` does the thing** (`panel/doctor.py`). A token present, an MCP handshake, a daemon with a pid — every one of those is true on an install whose credential died, whose automation listener is holding a folder open with nothing behind it, or whose allow-list has stopped letting a read through. So eight stages, each a real round trip with its own budget and its own sentence naming the switch or the log to look at, and BRight's `director_check` is the shape. Two differences, both because there are eight faces rather than one chain: **every stage is reported**, since "the chat works and the automation listener does not" is the answer and the first break hides it; and **a stage whose precondition failed is SKIPPED with the reason**, since eight identical auth failures is a report nobody reads past line one. **Opt-in, costed and never on a timer** — the auth re-check's rule, for the auth re-check's reason. **Every stage cleans up and the cleanup is verified**, and a leftover is that stage's failure: the synthetic fact is not in `memory.md`, the synthetic finding is in neither the store nor the settled ledger, the helper is deleted. **Optional is not broken** (`health.py`'s rule): Assist off, the automation listener off and `protected_entities` covering the helper `fixer_dry` renames are all *skips* naming their switch — a list doing its job is not a fault. The **chat stage never joins the registry and never evicts**: an answer surviving you looking elsewhere is the point of holding several, and a check that closed somebody's conversation to prove the chat works would be exactly wrong, so a full registry is a skip carrying the cap's own sentence. **A timeout is reported by name** and never as "not authenticated". The three operations only the panel can do arrive as `Hooks` — `_end_finding`, `_undo_finding` (lifted out of `h_undo`'s closure for the reason `_end_finding` was lifted out of `h_finding_verb`) and `_consolidate_now` — because a second implementation of an ending here would be the same press teaching brAIn two different things depending on who asked. Runs claim the `doctor` source before they start, so the Chats rail does not offer a probe as a conversation somebody had, and they ride the generation queue like a fix run. They take no `run_queue` seat — `doctor.py` calls the engine through `asyncio.to_thread` — which the comment above `DOCTOR_JOB` says out loud, because a costed check that is pressed by hand and capped at a handful of turns is not what that bound is for. The last verdict — when, what, which stage — rides `/api/diagnostics`; the stage list is a page of prose and belongs on the screen that asked. The memory stage's probe and verdict are in `memory.md` › *The deep check's memory probe*.
- **"Is brAIn working" is one press at the top of Diagnostics, and its answer is the header** (`#deepBox` / `renderDeep` / `deepCountLine`, `doctor.run_deep`'s per-stage `at`). The deep check is **Run all tests**, first in Diagnostics, still a press and never a timer (it spends Claude runs). The header reads **"N of M passed · K skipped"**, M counting the stages that RAN: a stage skipped over a failed precondition or a switch that is off did not pass and did not fail, and folding it into either number is a misreading. Each stage is a row: **Passed / Failed / Skipped in words** (skipped is muted, never red), the stage's own sentence as the reason, and **the time it ran** — `run_deep` stamps `at` on every stage, skipped ones included, because a row with no time reads as one that never got to run; an older payload with no `at` shows the run's finish. While a run is in flight the stage catalog fills the rest as Running/Waiting rows. `measure-settings` shows the header, the words, the reasons and the times over a stubbed run with a failure and two skips.
- **A storage collection's id comes from the NAME, and the deep check stated both** (`doctor.FIXER_HELPER_NAME` / `_ensure_helper`). `IDManager.generate_id` slugifies whatever a helper was called while the slug is free and appends `_2` otherwise, so the entity id is a consequence to be read back off the create call and never a second constant; the prompt handed to the fix run, the verification and the delete all key on it (`rehearsal._take_out_helper`'s rule, one module over). The helper's name is chosen so a free slug lands under `PREFIX`, which is what makes a future leftover visible to `rehearsal.leftovers` and the sweep at all. `_sweep_helpers` runs before each create, matched on the **name** brAIn gave (`rehearsal._helper_items`' reason: an item whose slug collided is exactly the one a derived id cannot name), covering the legacy name as well; it asks `protected_entities` about each one (an unattended delete must not fall through the gap between two spellings of nearly the same entity), and it is **reported in the stage's detail**, `rehearsal.sweep`'s rule, because a sweep that quietly removed things is indistinguishable from a house that never had them — and it clears the collision rather than surviving it, or the next create comes back `_2`. A fake of `input_boolean/create` must be one that **mints the id from the name**, `_2` and all, or it writes down the same guess the code does.

## The rehearsal

- **The suite tests the checks on fixture houses; the rehearsal tests them on YOURS** (`panel/rehearsal.py`). Every late bug in this add-on's history lived in the one place a suite cannot see: this install's HA version, its integrations, its data shapes. So `brain doctor --rehearse` plants a small set of `brain_test_*` defects through the paths brAIn already owns (automations through `automation_writer`'s write-reload-verify, so the rehearsal is also a round trip of the writer), runs the checks and the analyst against them, scores both, and removes everything. **Consent is a named step, and it is a 428**: a call without `{"consent": true}` is answered with the exact list of what would be created — ids, what each is for — and nothing is created before the answer comes back. **It calls `checks.run_all`, never `server.run_checks`**: the second files to the store, notifies, and clears, which would ring somebody's phone about a defect brAIn planted and let a planted row clear a real one. **A check whose floor is measured in days is named as not rehearsable rather than counted as missed** — `auto.forgotten_off` needs thirty days off and `dev.frozen` a week of statistics. **The analyst score is the point**: "on this house, this HA version, this model, it found 3 of 4 and reported 1 that was not there" is what makes a prompt change measurable somewhere other than the developer's own home, and it runs the automations card's own prompt builder in a mode that persists no card and files no findings. **Removal is in a `finally` and is verified against a fresh snapshot** — a rehearsal that fails halfway still cleans up, and a cleanup that fails is the loudest line in the report. **And the plain `brain doctor` is what catches the one that did not clean up**: it warns on any `brain_test_*` automation, entity or helper and names the command that removes it. `health.py` deliberately does NOT carry it as a `degraded` reason — a left-behind test helper is a tidy-up, not brAIn failing to work. Its scoring arithmetic is `panel/scoring.py`'s, shared with the corpus replay, because "precision against labels" having two answers is the drift `_CARD_CONTRACT` is shared to avoid.
- **A guard that refuses has to change the next attempt, and the rehearsal's could not** (`rehearsal.sweep`). `automation_writer.apply` refuses a duplicate id, correctly, so litter left by an earlier run must be cleared before planting or every run after it fails identically. The sweep runs **before** planting and three things keep it from being a licence to delete: it removes only what `leftovers` sees **under the prefix** — the same scan the cleanup proves itself against and the same one `brain doctor` warns about, so nothing here decides for itself that something looks like a leftover; it runs **inside the consent already given**, `brain_test_*` being brAIn's own litter; and it is **reported**, never silent, because a sweep that quietly removed things is indistinguishable from a house that never had them and the line that says what it took is also the only evidence the run before it failed. A sweep that cannot finish **refuses the run** naming what is in the way. The three removals are one function each (`_take_out_automation`/`_take_out_registry`/`_take_out_helper`) shared with `_remove_all`; "already gone" counts as removed, and a failed removal always carries its reason, because a fault with an empty explanation is the one nobody can act on.
- **The sweep was a step inside a run, so the only way out of its failure was the run.** So `sweep_only` is a press of its own (⚙ → Developer, `brain doctor --sweep`, `POST /api/doctor/rehearse/sweep`) that creates nothing, asks no model and spends nothing; a person is never asked to edit `automations.yaml` by hand for what the panel can do. **It needs no consent step** precisely because of that: the 428 exists because a rehearsal WRITES, and what this removes is what `leftovers` already sees under brAIn's own prefix, which is the warning that sent somebody here. **And it re-earns the verdict** — `cleanup_ok` was written once by the run that failed, so a sweep is recorded as `cleared` **beside** the cleanup and never over it: the run's own failure is the evidence that a cleanup failed, and it is the one thing editing the record would lose. `_cleared_ok` requires the sweep to have both **run** and **seen nothing left**, because "I could not look" and "it went away" are different claims here too; `outstanding()` is the one derivation of "is there litter", read off the record rather than a live snapshot (this is asked on every poll of an open dialog), so the button that offers to clear it and the fault row that reports it cannot disagree. The button renders only while there is something to take out — BRUH Print's `Forget` rule — and the two presses carry **separate** in-flight states, because a button that greys itself out while the other one runs is a pair of controls nobody can tell apart. `sweep` stays deliberately silent on a clean house (it runs before every plant, and a "nothing to clear up" row above every rehearsal is what makes the one that DID remove something skimmable) and `sweep_only` supplies the sentence for that one case, because a press always has an answer.
- **A successful mutation answers `result: null`, which is the same value as a refusal** (`ha_data._ws_calls`). `_ws_commands` hands back Core's `result` field per command and `None` for anything that went wrong, which is right for every command that ASKS for something and wrong for one that CHANGES something: `input_number/delete` answers `result: null` on success. `_ws_calls` reports `{ok, result, error}` and `_ws_commands` is layered on it, one round trip, because two would be two chances to disagree about what Core said. A fake must return `null` where Core does, not a truthy `{}`.
- **Removing an automation does not remove its entity, and verifying otherwise reverted the removal** (`server._wait_for_gone` / `_is_restored_orphan`). Every automation brAIn writes carries an `id`, so Core gives it a `unique_id` and therefore an entity registry entry — and a registry entry outlives its provider: splice the entry out of `automations.yaml`, reload, and Core unloads the automation and re-publishes the orphan as `unavailable` carrying `restored: true`. `GET /api/states/<id>` answers 200 for that, for ever. What is being verified is that nothing provides it any more, and a restored orphan is Core saying so in as many words (`checks/devices.restored` reads the same shape) — and the rehearsal deletes the registry entry too, because half a cleanup is a leftover under a prefix `brain doctor` warns about. `input_number/delete` keys on the item id Core MINTED, carried from the create call rather than derived from the entity id: `IDManager.generate_id` appends `_2` when the slug is taken, so a guessed id deletes nothing on exactly the house that already has a leftover from last time. `leftovers` reads `snap["entities"]`, the key the collector emits.

## Capture and the corpus

- **A prompt is the one part of this add-on no test has ever run** (`panel/capture.py` + `tests/corpus/`). `_CARD_CONTRACT` is ten kilobytes of output rules shared by two prompt builders, and nothing in the repository puts either of them in front of a real house or a real model. So `capture` records what the analyst was sent and what came back, and **the ending is the label**: an ending on the Findings tab already says whether the report was right, so pairing it with the prompt that produced it turns a house into a graded example. It is hooked in `_end_finding`, the one door every ending comes through, so the label is a property of the ANSWER rather than of the surface it was given on. **Off by default** — a house's entity names are a floor plan — **redacted on the way IN** (a redaction applied on the way out never ran for the file somebody found another way; the shell's `redact()` and `capture.redact` must agree on the same strings), **capped** at fifty files, named in `backup_exclude`, and reaching `/share` only through a press. The id is the one Claude Code already minted — `engine._run_cli`'s session id, claimed in `run_sources` before the run — so a capture, a journal line (`run_id` is a column), a transcript and a Chats rail row name the same run; a house check carries none, which is honest, because nothing was asked and there is no prompt to grade. A run id off the wire is not a filename: `safe_id` plus `chat_session.transcript_path`'s normpath-and-prefix barrier, spelled the same way for the same reason.
- **A corpus entry is frozen, and nothing regenerates it.** Nothing may, because **an entry whose expectations are regenerated from the current code cannot fail when the code changes**, which is the one thing it exists to do. Every timestamp inside one is relative to the snapshot's own `now`, which is stored with it, so a replay next year grades what a replay today does. `replay.py` (on demand, `replay.yml`) has two halves. The **checks** half is `run_all` and nothing else: it is what fails when a floor moves, and it names the *house* that went quiet or loud. The **analyst** half rebuilds the prompt with the current builder — a stored prompt would grade the release that captured it — caps spend three ways with `--max-tokens` checked *before* each run (a cap that stops once it has been passed has already spent the run that passed it), and **skips a `search` entry rather than faking it**, because that run read the house with tools and grading the prompt where they reach nothing measures a model that cannot look anything up. `schema.json` says out loud that nothing validates against it (no `jsonschema` dependency for two files agreeing about a shape). One scorer, in `panel/scoring.py` rather than under `tests/`, because `rehearsal.py` ships inside the add-on and cannot import from the test tree; nothing over nothing answers 0.0, never 1.0. **The ending words are one list published in three places** (`tests/corpus/score.py`'s `CONFIRMED`, `schema.json`'s enum, and the replay's verbs) and `accepted` is among them — moving a card onto the to-do list is somebody agreeing the report was real work, which is the same evidence about the producer as having done it, so the chore finishing later re-labels nothing.
- **How a house failure becomes a case.** A first look that ended Wrong or missed reaches the corpus through the devloop's `corpus` stream, which files a `brain-corpus` issue through the same Review/Send gate; the cloud loop adds it to `tests/corpus/entries/` frozen.

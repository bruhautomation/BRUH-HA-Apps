# Morph specifics

Morph's service, files, Tells, salience, cases, learning loops, frontend and measures.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`. How each rule was learned (the reports, the owner's words, the first attempts and the old tests) is in `docs/notes/history/morph.md`.

- **5.3.0 shipped one house's design as Morph's own, and retired what that house had switched off** (`frontend/` copied from `/config/morph/frontend`, then cut). What came in: `scrub.js` (the room rail, everywhere: Morph's page through `panelHost`, and HA views through the host each view builds — `rail.js` is deleted), `haptics.js`, `polish.js`, `pull.js`, the one width rule, one-card sections, segmented scenes, the colour track, group All sliders, the tap/hold grammar, the history view, Coming up's tap-to-open and zoom. What went, for every house: the Now band and every reorder (habits, anchors, prediction dots, per-viewer weighting, `notePredictions`, tallest-first packing), room folding and the still form, header chips and marks (`room_marks`), Morph's own Feed/Settings/Personality pages, cases and To Do on the page (they are brAIn's Needs you), Then, the story's hard-coded entities, `dayDrift`, the island strip (`islandbar.js`, `chrome.js`) and the SOFT spring. **Bullets below that describe those systems are history.** House data is `dashboard.yaml`: `sleep_guard`, `icon` on a section, `when` on a group, `coming_up_lanes`, climate `options.actions` (which replaced `drop_humidity`). `store.normalize` has to keep any new key or the panel never sees it. The rail reads only a host (`scrub.js` header: root, scroller, rooms, hidden, board, cover, reduce, still): `panelHost` is Morph's page, and each Lovelace view builds its own from HA's `.section` wrappers inside a sticky zero-height box, so the rail stays on screen while the window scrolls. On HA views it is touch-only, because HA keeps its own scroll bar. Order and fold are gone from every surface, the Lovelace layer included.
- **Morph is part of brAIn since 4.0, and the halves kept their jobs** (docs/design/brain-morph-merge.md). The service, `brain/morph/service/morphd.py`, runs in brAIn's container (run.sh's `start_morph`, root, loopback health on `127.0.0.1:8096`, restarted by its own watch loop) and is the only writer of `/config/morph`; it reads brAIn's switches (`/config/.brain/features.json`) every few seconds and does nothing while the Morph dashboard is off — `main` waits before `bootstrap`, the loops skip, a request is answered `OFF_ERROR`. Its state is `/data/morph`. The panel half is `custom_components/brain/morph/`, set up by the `brain` integration (`hass.data["brain_morph"]`, the websocket names `morph/*` and the static paths unchanged); the sidebar entry is brAIn's shell (`frontend/shell.js`), which mounts `<morph-boot>` as the Home tab with `shell = true` (Morph then draws NO bar — brAIn's header is the one header, carrying Morph's Edit/Done/YAML through `morph-chrome` and `chromeAct`, and drawn in Morph's theme; panel.md has the contract) and alone, full height, for somebody who is not an administrator. `--morph-h` is the height the shell gives it. Talk to the service by file IPC under `/config/.morph` (`requests/` → `responses/`, with the mirrors `dashboard.json` and `state.json` read directly), from the integration (`bridge.send_request`) and from brAIn's panel (`panel/morph_service.py`, ⚙ › Dashboard's kinds only). Writes are `morph/request`, `require_admin`; `WRITE_KINDS` in `websocket.py` and the `kind ==` branches in `morphd.handle` are kept equal. `learning` and `report_code_issues` are brAIn's switches (Learning loop, Development loop), read on every `settings.load`; a stored value for either is ignored. ⚙ › Dashboard draws the service's mirror, and Morph's "See the changes" opens it through the shell (`brain-open`). With Personality on, every region's HTML goes through `speak` (never inside a `<textarea>`). **The name Morph says is the switch's, on both halves**: the panel's `who()` reads `features.name` and nothing else ("brAIn" before the first load), and the service's `brain.who()`, which names the assistant in a Tell's and a conversation's steps, is "brAIn" when `settings.features()["personality"] is False`. Never a second name beside brAIn's. Switches never written leave the name on, `personality.enabled`'s rule. The `morph/personality` command stays, for an older copy a house may still run.
- **Every change is one commit, and nothing else is history.** `gitrepo` serialises git under one lock (a tell's commit, a save and the watcher are different threads), authors each commit by who made it (`person`, `brain`, `learning`, `outside`, `morph`), commits a hand edit as *Edited outside Morph* before anything else touches the tree, and reverts or restores as a NEW commit so an undo is undoable. `head()` and `log()` both answer 12-character ids, so the commit a Tell reports is one the History page can name. `/config/morph` is chowned to brAIn's `claude` user after each commit so brAIn's next edit is an in-place write. brAIn is told never to run git there (`ha-context-gen.sh`'s Morph section and `defaults/AGENTS.md`).
- **A file that does not parse is somebody mid-edit** (`store.publish`'s `held`). The mirror keeps the last dashboard that read and carries the parser's line; the panel shows it above the notes. The revision is the hash of the file's text, so a fix is noticed the moment it is saved.
- **Ids survive a round trip** (`store._pre`, `normalize`). Undo, notes, suggestions and the usage log key on card and section ids, so `dump → load_text → normalize` is the identity.
- **Every task Morph writes says it came from Morph** (`brain.ORIGIN`, `"origin": "morph"` on every task `brain.submit` writes — a Tell, a conversation, a learning pass, a code redo — and nothing else in the service writes into the task folder): brAIn lists Morph's conversations under its own pill, and a field is the one thing it can read without guessing from a prompt's wording.
- **A person's words reach brAIn whole, from the first character** (`wording.fit` / `clip`). The words are never cut; only the context sent beside them gives way, on a line break (else between words) and marked, or is left out with a sentence saying so. Text Morph itself writes into a request (a suggestion's change, a question's option, a summary handed back as history) is cut between words with an ellipsis (`wording.clip`).
- **Tell acts at once, and the commit is what makes that safe** (`service/tell.py`). A Tell is a `tools: full` brAIn task through brAIn's task folder (claimed by rename; 30s unclaimed is "nothing is listening" and the task is withdrawn so it cannot run an hour later); when it answers, Morph commits the dashboard half as ONE commit and Undo reverts exactly that one, then sends brAIn a follow-up Tell naming the house changes to put back. `protected_entities`, the action gate and brAIn's edit snapshots hold whatever the prompt says.
- **A Tell's result names every place it could have reached** (`whatHtml`: Dashboard, Home Assistant, Morph's code, brAIn's memory, GitHub), each with *Not changed* / *Nothing sent* when untouched, because "it only changed the dashboard" has to be read, not inferred; the composing box says the same before Send. **A choice that is the person's is `question` in the answer** (`tell.clean_question`: two or three `{label, request, home_assistant}` buttons, a literal `true` only), and a value a card works out from other sensors is NOT one of them: brAIn makes the template sensor and shows it (AGENTS.md). `tell_answer` starts the next tell from the option STORED with the tell, never from words off the wire, with scope `house` only when the pressed option said so; one answer per question.
- **A Tell starts with a picture, and is about the dashboard** (`frontend/snap.js`, `morph/shot`, `tell.build_prompt`). `snap.prepare` clones what was held SYNCHRONOUSLY in `openTell` (holding a card opens it, and the picture has to be the card as it was), with computed styles inlined against the parent (inherited) or the tag's default (the rest), shadow roots and slots flattened, canvases/images as data URLs and Morph's two fonts embedded, then `render()` draws it through an SVG foreignObject; an OPEN card is photographed by its `[data-face]`, never the tile with the editor cut out. The integration files the PNG under `/config/.morph/shots` (admin, PNG magic, under HA's 4 MB websocket frame, owned by UID 1000 with owner-only modes so brAIn's `claude` user can Read it and nobody else needs to) and the prompt puts its path BEFORE the YAML; a shot id is checked for shape and existence before it becomes a path, and a picture that could not be taken is said, with `viewText` (the element's text through every shadow root) sent instead. The scope is `ui` unless the caller is Undo's follow-up (`scope="house"`): `morphd` never reads a scope off the wire, and either scope does the whole job: the Home Assistant changes the result needs (a template sensor, an automation, a helper) are made too and listed in `home_assistant` for Undo. House facts go to `remember_fact`, never `LEARNED.md`. A `code_issue` in the answer is ASKED ("send this as an issue?", `tell_issue`), never filed by the model.
- **A Tell's house facts ride in its answer** (`facts`, `tell.queue_facts`). A Tell is a task run, and brAIn's action gate refuses `remember_fact` there because the words asked for no memory. Morph writes them to brAIn's memory inbox as source `morph`, only when `/config/.brain/memory` exists.
- **What brAIn is doing is read off brAIn's own hook** (`brain/scripts/brain-task-progress.sh`, `tell.progress`/`_follow`/`describe_call`). The automation listener exports `BRAIN_TASK_PROGRESS` per task and the headless settings run the hook on every tool call; it is sh, exits on its first line without the variable, prints nothing and records a call's subject, never its content. Morph turns lines into steps (repeats folded, to-do bookkeeping dropped, capped with a count) and publishes running tells as `activity` in `state.json`, so a tell stays visible after its box is closed. The tell box's elapsed time is written by a one-second tick into `[data-since]` spans and never into the compared HTML, and only the newest step has `rise`, so a box rebuilt every second does not replay its blur-in.
- **A Tell is read back, never taken at its word** (`tell.read_back` / `describe_change` / `outcome`, `ON_PUBLISH`). When brAIn answers, Morph diffs dashboard.yaml at the Tell's base commit against the file now and lists what a person would see (`shows`), republishes the mirror at once through morphd's own `publish` (`tell.ON_PUBLISH`, since tell cannot import morphd) and records its `revision`; the panel always reloads on done and offers **Refresh** while its mirror is behind. Three endings are said in words: nothing changed (`unchanged`, *Nothing on the dashboard changed* with brAIn's summary quoted), a rewrite that changes nothing on screen, and a file that no longer reads (`failed`, *Not applied*, the commit kept so Undo reverts it). The phase is written only with the final save, because a state file reading "done" is the panel's signal that the lesson and outcome have landed. brAIn's "changed" lines that name a Morph file (`_morph_file`) are not house changes, so Undo never asks brAIn to put back a house change nobody made. `greeting: false` hides the hello line; the prompt says a Morph dashboard is dashboard.yaml and never a Lovelace one.
- **A dashboard change is a Tell wherever it is typed, and brAIn decides which it is** (`morph/ask` → `/config/.brain/morph/asks/` → brAIn's interpreter on the `morph` surface → `answers/<id>.json` `{do: done|conversation|tell_dashboard|tell_code|fallback, say}`). The house's conversation agent cannot write /config/morph, so the Ask line never goes straight to it. The interpreter's `dashboard`/`code` kinds are the Tell; `conversation` is a brAIn chat task (`converse.py`, below); `done` is a rule or a fact brAIn filed; `fallback` (brAIn could not read it) keeps the old `DASH_CHANGE` word test and then the house's agent. Every answer offers **Change the dashboard instead**. `ws_ask` waits 40s for brAIn's answer and says `fallback` past that, because a line nobody answers is worse than the old path. `brain-protect-hook.py`'s `is_morph_dashboard` exempts dashboard.yaml (on real paths) from the refusal of YAML naming a protected entity, because a dashboard names the locks.
- **Ask is the one door to a Tell outside Edit, and the mark is only the brand.** No hover mark, opened-card mark or section-title mark opens a Tell beside Ask (vision §13.3). `MARK` in util.js is still the drawing (`branding/morph/`, the README's Morph section): squares and tiles are the mark alone and carry no BR ligature; the wide lockups keep the ligature with the mark where the roof stood.
- **A conversation is brAIn's chat by task** (`service/converse.py`, `brain.submit(kind="conversation", session_id=)`). Ask's `conversation` answer starts one: the automation listener runs it on the chat channel, resumes the session the last turn used, and does not claim it in `run_sources`, so it is the person's own conversation in brAIn's Ask tab too. The state rides beside the Tells' (`/config/.morph/tells`) so the panel follows it with `tell_status`; a session id off the wire is matched against `SESSION` before it reaches the task.
- **Ask stacks: every question keeps running and its answer stays** (`s.asks`, `askAdd`/`askSet`/`askDrop`, `answerHtml`). Each question is its own entry with its own conversation id and poll, newest first, the last `ASK_KEEP` (5) kept (a finished one is dropped before a running one); `[data-ask]` is `aria-busy` with a pulse while ANY is in flight; a tap outside folds only the finished ones; and the session is resumed only when no other conversation from the page is in flight, because two turns resuming one session would race for it (the second starts its own; whichever lands last names the session the next question resumes). The service runs them in parallel: `converse.start` gives each its own asyncio task and id, and the automation listener runs every task file as its own background process (`process_task &`), so nothing queues behind the first. **A Tell replaced while it runs is parked, not lost** (`parkTell`, `tellsAway`): `s.tell` is a setter, and a tell it stops showing while brAIn is still at it (another Tell, the box closed) is polled until it lands and then said in the strip at the top with **Show**, which opens its box again with Keep and Undo.
- **Morph is brAIn's face, and the page is ONE salience list drawn five ways** (`frontend/salience.js`, docs/design/morph-vision.md §4–§11). Every card and every case gets inputs (deviation off brAIn's `feed.json` normals, urgency, progress, recency), one score (`score`), and a band with hysteresis (`BANDS`, `bandFor`); everything drawn from it reads that one result, so no two parts disagree. Since 5.3.0 salience colours and words what is there and never moves it. **It is pure** — `compute(items, ctx, prev)` reads only what it is handed. **The page takes a new result only at a quiet moment** (`quietMoment`: no pointer down, nothing open, 1.2s after a touch, 600ms after a scroll, 8s after the last rearrangement) unless something urgent arrived, and a period change (night/away) skips only the spacing — `maybeApply` keeps `salState` (newest) apart from `salApplied` (what is drawn), and a because line reads the newest. **At night Now holds only what the night floors lift** (an open closure or unlocked lock, an urgent trip, a rose case, a pin): armed at 11:30 PM with one unlocked lock shows exactly one card. A lifted card is MOVED (`engine.moveTile`, travel without a fade), never copied, and its room keeps a trace. A feed older than its own `stale_after_s` is used and said; past a week it is not used (`feedHealth`), and nothing in a because line names a measurement brAIn did not send.
- **brAIn's cases are drawn where their subject is, and a reply is read, not pressed** (`frontend/cases.js`, `ws_case` → `requests.write_morph_request`). The one list is brAIn's (`/config/.brain/morph/cases.json`, `_brain_feed` in websocket.py); Morph keeps none. A card is the claim, the ask, the last three turns of its thread and a reply line (16px, `.morph .replyin` — `.morph input{font:inherit}` outranks a bare class) plus the presses; no Yes, No or Wrong, because brAIn's interpreter reads the words. **A card reads as brAIn's Needs you reads it**: brAIn's one chip word (`caseChip`, `answers.chip`'s rule for a row with no `chip`), the title and detail with friendly names for ids, and `casePresses`: the row's own `answers` labels in brAIn's order, with Snooze put back before the ending that waves a card away because cases.json leaves it out; Check again and Ignore are not offered until brAIn's queue takes them from Morph. Two fields only Morph can act on ride back (`followReplies`): a brAIn turn's `tell` (a page change the reply also asked for, which brAIn cannot run — run once, only on the page that sent the reply) and `said` (brAIn's last word on a case the reply ENDED, said as the card leaves, because the row took its thread with it). A family tablet shows a question's reply line only after a tap. To Do is brAIn's to-do list as a section (`ws_todo`: done, drop, snooze 1–60 days).
- **Two learning loops, the way brAIn has them.** Loop 1 (`service/learning.py`): the panel logs uses (`USAGE_KINDS`, equal in the integration and the service), and a scheduled brAIn pass — `tools: read_only`, `scheduled: true` so brAIn's gates apply — returns at most five suggestions and the COMPLETE lesson list. Suggestions are **brAIn's cases** (`learning.sync_brain`, on morphd's tick): each open one is filed once as a `morph_case` request on brAIn's queue (`case_body`, key = the suggestion's id) and withdrawn when it ends here; brAIn publishes how it ended in `cases.json`'s `ended_morph` (`accepted|declined|dismissed|todo`, read once per `key@at`), and `accepted` starts the Tell (`_start_suggestion`, settled by its tell: a failed run reopens it) while `declined` keeps the reason as evidence for the next pass. Morph keeps no list of its own on the page, and brAIn writes nothing to memory about a Morph suggestion. **It is about the dashboard only** — brAIn learns the house — so the schema's `kind` is `dashboard`, the prompt asks for no Home Assistant changes and no house facts as lessons, and carries AGENTS.md's design rules as text, because a `read_only` task is denied Read. The pass's `code_reports` become suggestions of kind `code` (**Send as issue**, `decide(…, "send")`), never faults filed on the model's word; `learning.send_code_reports()` also files them after each pass while the Development loop is on, through the same outbox, redaction and caps (the Send button stays for a person who wants one out sooner, and the filing is not recorded as the household agreeing). Lessons live in `LEARNED.md`, committed as `learning`, read by every Tell and pass. A pass with nothing new (`fingerprint`) spends nothing, and the fingerprint is written only by a pass that ANSWERED, so a failed pass never marks the evidence read. Loop 2 (`service/devloop.py`): Morph's own faults — a card that threw, an overlap at rest reported by the panel's `audit()`, an answer from brAIn Morph could not read, and what somebody chose to Send as an issue — are a ledger (brAIn slow, signed out or paused is not Morph's fault and files nothing) keyed on the digit-folded `where|what`, published to `/config/.morph/devloop/outbox.json` in brAIn's row shape with `where` starting "Morph". brAIn's devloop reads it as the `morph` stream (`streams.morph`, `server._devloop_morph`, which writes `ack.json` back), files it with `devloop:morph`, and the fix-from-house skill fixes it under `morph/`. `None` from the reader is "Morph absent", never an empty pass.
- **A lesson is never cut** (`learning._rows_of`, `restore_clipped_lessons`). Every rewrite of LEARNED.md goes through `_rows_of`, which never cuts a line; `MAX_LESSONS` bounds the file, not a line. Once per house `restore_clipped_lessons` gives back a clipped line only when Morph's git history holds a longer line starting with exactly its words (marker `lessons-restored` in the data dir; the commit message lists them).
- **An answer to a proposal is kept against the card or section it was about** (`learning.py`'s `keeps`, `_keep`, `kept_ids`, `record_reverted`, `rests_on_disuse`). A No (here or from brAIn's Today), or a done suggestion whose commit was reverted, stores a keep: a card's holds while it shows the same entities (`_subject`; renaming it or changing an option does not undo a No, pointing it at another entity makes it another card — #1262, #1316), a section's place and presence for good. A kept card is not shown to the pass as dead or unused, `add_suggestions` drops a row about one, and a row to remove, hide or move something whose only ground is that nobody pressed it is dropped (`rests_on_disuse`; an unavailable card is not that). **What a suggestion does is a typed field, and a control is never proposed for removal** (#1198, `learning.proposals`). The schema's `action` (`add|change|move|remove`) and `moves` (every section a reorder changes) decide what a No keeps, not the title's verbs: "Put Climate above Security" matched none of `_CHANGE`'s verbs, so its No was kept against nothing and the reorder came back reworded; a No to a move now keeps every section in `moves`, and `record_declined_moves` keeps such an answer given before the field existed (`_PLACE`, once). `removes_control` drops a removal of a card that holds a control (`CONTROL_TYPES`, or an entity in `CONTROL_DOMAINS`), or of a group or section with one in it, even while it is unavailable (the owner put a dead light's card back); only a control whose entity Home Assistant no longer has may go (`missing` in the digest). **A removal is offered only for a card that is dead, checked against the live house, and says how long** (#1262, #1316; `learning.removal_why`, `track_down`, `DEAD_AFTER_S`). Dead is every entity the card shows gone from both Home Assistant's states and its entity registry (`missing`; with no registry read nothing is gone, because a disabled entity has no state), or every one `unavailable` (not `unknown`, which a never-pressed button is) for 30 days. When it went is `down_since` in the suggestions file, seeded from `last_changed` and kept across passes, because `last_changed` starts again at every restart. A removal of anything else (still working, briefly away, never pressed, or naming no card or section) is dropped, and Morph writes the why itself ("… has been unavailable for 40 days, since Oct 14, though Home Assistant still has it. Nothing is removed unless you say yes, and Undo puts it back."); a Tell commits what is pending first, so the dashboard before the removal is a commit. Each suggestion says what it rests on in a typed `ground` (`gone|unavailable|asked|layout|use`), and a move or removal whose ground is `use` is dropped: a card pressed rarely is not moved lower either. The model sees the keeps, and the prompt says use alone is never a reason. A suggestion with no `card` or `section` is held by its words only. **A Restore counts as an undo, a kept card keeps its section, and the keeps are on screen** (`gitrepo.restore` / `is_restored_over`, `learning._section_of` / `kept_ids` / `keeps_listing` / `clear_keep`, request `keep_clear`, ⚙ › Dashboard › Learning loop › Kept as they are). A restore commit names the version it went back to ("This restores commit <sha>"), and a done suggestion whose commit is newer than a restored version is undone. A card's keep also records its section and `kept_ids` returns that section, so a section-level reorder that would move the card is not proposed. Each keep that still holds is listed with what kept it (a No, or putting it back) and Forget.
- **"What do you want to fix?" is Ask, and Morph's own reports are still a ledger** (`devloop.note_request` / `mine` / `withdraw`). Words about Morph are a Tell about Morph's code, which Ask routes; the request kinds `report`/`report_withdraw` remain, so a report already filed can be listed with **Take back** until brAIn's ack is newer than it, and `rows()` gives a person's report its own body — a Tell's issue sent by a press (`Morph · Tell`) included (`PERSON_WHERE`). Nothing is sent while `report_code_issues` is off.
- **Morph's service faults are Morph's own to report** (`devloop.note_exception`, called from `morphd`'s request loop, `_one`, the watcher and the tick). Every handler in `morphd.py` files what it catches as a row: the exception's type, the deepest frame in Morph's own code and the message as `what` (digits fold in the fingerprint, so a line that moves is the same fault), the traceback as `detail`, under the Development loop switch (⚙ › Features) like every other row.
- **The screenshot preview unfolds every room** (`devloop/harness.py`'s `morphSettled`): with no one home and nothing on, the salience list folds rooms to a line that draws none of their cards, so a picture of the dashboard would leave cards out.
- **Morph can change itself, one module at a time** (`service/morphcode.py`, `custom_components/brain/morph/static.py`, `frontend/boot.js`). Nothing about Morph is out of reach: brAIn copies a module from `/config/custom_components/morph/frontend/` (`paths.SHIPPED`: what HA serves; read-only) to `/config/morph/frontend/<same name>` and edits the copy.
  - **One commit, recorded.** `gitrepo` calls `morphcode.record_bases()` before every commit, so the copy goes in with `.base.json` saying which version of Morph's file it was last written against (re-recorded whenever the copy's own hash moves), and Undo puts both back.
  - **Paused by an update.** An update that moves Morph's own file under a copy PAUSES it (Morph's own is served), because last release's module beside this release's others is how a panel breaks. Writing the copy again un-pauses it. **So does an update that moves any OTHER module** (`others` in the record, every shipped hash at write time; `status()` reports `why: others` and `moved`): a copied morph-panel.js imports engine.js. A record without `others` is filled in on the next commit rather than guessed. **A copy that reads the retired `personality.js`, and that file itself, are paused whatever the record says** (`morphcode.RETIRED`, `why: personality`); the old file offers Remove and never Update, and making the copy again tells brAIn to start from Morph's own and leave the file behind. A code-redo tell brAIn ANSWERED is `morphcode.accept`ed before the tell's commit — brAIn either edited the copy or judged it fits — so Undo takes the record with it and the copy pauses again; a failed one stays paused, and "no longer needed" means brAIn deletes the copy. **A merge brAIn would not guess at is a `question`** (`redo_words` tells it not to write the copy when the update rewrote the code the change was in): an answer carrying one is NOT accepted, so the copy stays paused until a button is pressed, and each option's request names the whole merge with its paths because it is sent on its own; the answered tell is kind `code` too and is accepted when it finishes without a question.
  - **One verdict.** `code.json` (`morphcode.publish`, every `publish_state`) is the one verdict the integration reads. `static.pick` serves a copy only when that says `active`, Morph's own under `shipped/`, and never `boot.js`. Every answer is `no-cache`, because one URL can now be two files.
  - **Making a paused copy again is a press with a box, and a three-way merge.** `code_redo` starts a Tell of kind `code` (`REDO_PATH`), and the panel opens brAIn's box inside the paused note, which stays until the box is closed. A second press while one runs returns that one (`already`). The press is held in `this.s.redo` until the service answers, never written onto the button, because the panel redraws on every state change. A refusal stays in the note with Try again. `record_bases` keeps Morph's own file each copy was written against at `frontend/.base/<name>` (`kept_base`), so `redo_words` hands brAIn the original, the copy and the new release, plus the commits that touched the file. The kept original is not a change: `code_files` skips anything below `frontend/`'s top level, and the issue patch excludes `frontend/.base/`.
  - **A broken copy is not a blank page.** `boot.js` (the `module_url`) imports the panel and, if that throws, imports `shipped/morph-panel.js` and leaves `window.__morphFallback` for `codeProblemsHtml`.
  - **Then it asks.** A Tell whose commit touched `frontend/` sets `state.code`. The box offers **Reload to see it**, and asks to open an issue whether or not brAIn filled `code_issue`, with the patch attached (`gitrepo.diff`; `devloop` does not fence a detail that carries its own fence).
  - **The rest.** A code suggestion's Do it is a Tell. `code_reset`/`code_redo` are the Settings and note presses. `measure-morph` serves a working and a broken copy through the fixture's `overrides`.

A No is kept; a house with no cards only records the rules.
- **Morph on Home Assistant's own dashboards (5.0) is Home Assistant's dashboard plus a layer, never a copy of it** (docs/design/morph-on-lovelace.md). Every file under `frontend/` that runs on HA's own pages is loaded by `morph-ha.js` (`frontend.add_extra_js_url`, registered whatever the switches say, so a Morph card on a dashboard never turns into an error when the panel is off), and each part is imported on its own so one that fails leaves the others and the dashboard drawing. `morph-ha.js` is in `FIXED` on both halves: a house's copy never replaces it.
- **A dashboard is HA's, and its YAML is Morph's copy kept in step** (`custom_components/brain/morph/lovelace.py` in Core, `service/lovelace.py` in morphd). Core mirrors what HA holds to `/config/.morph/lovelace/<key>.json` on every `lovelace_updated` and saves what morphd drops in `lovelace-apply/` with `LovelaceStorage.async_save`; morphd keeps `/config/morph/dashboards/<key>.yaml` and reconciles the two against the hash they last agreed on (`/data/morph/lovelace-sync.json`): HA moved → the file is rewritten and committed *Edited in Home Assistant*; the file moved → sent to HA once, and again only after `RESEND_S` unconfirmed; both moved → HA wins (morphd commits pending file edits first, so the file's version is in git); a file that does not parse is held and said once. The hash is canonical JSON on both halves and must stay equal, because a hash that differs by key order reads every pass as a change. While a Tell runs the sync still applies (the person watches it) but commits nothing: the Tell's one commit takes it. The event handler reads the Morphed list from `hass.data`, never a file, because it runs on the loop. `key` is `default` for the default dashboard, power_tools' word; the layer matches by `url_path`, because a migrated default dashboard is `lovelace` on newer cores.
- **A converted dashboard is HA's own sections view, and Morph's extras are switches on it (5.1)** (`convert.py`, `morph-view-layer.js`). Adding, moving, deleting and resizing sections, badges, `max_columns` and the view editor's type picker all live in HA's `hui-sections-view`, which a custom view never gets. So a tab is `type: sections` and Morph's extras are the view's `morph:` switches, drawn by `morph-view-layer.js` over HA's own view through attributes on its `.section` wrappers plus one adopted stylesheet, never by moving or adding nodes HA's renderer owns; since 5.3.0 the one switch is `rail` (order and fold are gone). The brAIn button's **Morph on this tab** saves a switch with `lovelace/config/save`. Each 5.0 dashboard's `custom:morph-view` tabs are migrated once by morphd's sync (`convert.migrate`, `sections_view` in the sync state, committed *Morph's views are Home Assistant's sections views now*); a house that writes `custom:morph-view` again afterwards keeps it, and `morph-features.js` still defines it. A section's index is the `hui-section`'s `path` on current HA and its `index` on 2025.1: read both.
- **A press is never a Tell's way in to a card** (`brain-layer.js`). HA cards own tap and hold (`tap_action`, `hold_action`), so the layer's "Tell brAIn about a card" is a pick mode: every pointer, mouse, touch and click event is caught on `window` in the capture phase until a card is chosen, so the press never reaches the card. The card's place in the config is found by IDENTITY first — HA hands each `hui-card` the very object from `lovelace.config` — and by equal JSON within the view only as a fallback. Every lookup into HA's page (`findPanel`, `cardAt`, `urlPathOf`) answers null rather than throwing.
- **Rule 1 does not apply to the layer, and the exemption is bounded.** The layer is on HA's page, where HA's own add-card button and dialogs float, and fitting into HA's layout would reach into its internals every release; it floats exactly its button, its sheet, the pick bar and the ring, and nothing else. `morph-view-layer.js`'s room rail is NOT one of them: its box is the first child of the view's shadow root, a sticky line of no height under HA's toolbar with the rail hanging from it, so a swipe on it chains to the view's own scroller (in the Home Assistant app the document is not what scrolls the dashboard); the tick puts it back after a redraw. After a landing the rail's glide lets go as soon as the page is moved under it, rather than pulling it back to the room.
- **morph-dom never descends into a custom element, so `<ha-card>` is made once** (`morph-cards.js`). The card element owns one `ha-card` and redraws only the `div` inside it; an `<ha-card>` drawn as part of the redrawn HTML keeps its insides as they were.
- **Never patch Home Assistant's element registry** (`morph-cards.js`, `morph-types.js`). `util.guardDefine` replaces `customElements.define` page-wide, which is Morph's own page's business; on HA's page it would change how every card and every HACS card defines itself. The HA-page modules define a tag only when it is free. An element card type's new code is a new tag (`morph-type-<slug>-v<n>`), because a page defines a name once.
- **HA's card picker has no section of its own for a vendor**: every custom card is under *Custom cards*, sorted by name (`hui-card-picker`), so every Morph card and card type is named "Morph · …" to sit together. `getConfigForm` is the visual editor (HA draws `ha-form` from it), so no Morph card ships an editor element.
- **A card type is the type as it is NOW, everywhere** (`cardtypes.py`, `morph-types.js`). A copy holds only its variables; `morph/types` answers the folder and `types` on `morph/subscribe` says it moved, and every live copy rebuilds. Only `types/<slug>.js` is served (`/morph_types/`, unauthenticated like every module), never a type's YAML. Usage across dashboards is morphd's (`types-usage.json`), and a Tell about a copy names the type and its copies so "this one or every copy" is the person's choice (the layer asks before sending, and the answer rides as `context`).
- **Morph's themes are added to HA's, not configured** (`themes.py`). `/config/morph/themes/*.yaml` go into the frontend's themes dict (`frontend.DATA_THEMES`, a HassKey on newer cores) beside configuration.yaml's, and `themes_updated` repaints every screen; `frontend.reload_themes` replaces the dict, so the integration's own listener adds them back before any screen asks, and ignores the event it fired itself. A house default theme set to Morph falls back at a restart, because HA checks it before the integration has loaded the theme: set it per user or per view.
- **Size is Home Assistant's, and a Morph card fills it** (`morph-cards.js`, `SIZES`). Every kind declares rows and columns (`sizeOf`, measured in real HA: strips one row, readings, thermostats and players two, cameras and forecasts three, a list `auto`), HA sets `layout = "grid"` on a card in a sections view (`:host([grid])`), and every wrapper down to the face is the cell's height: a strip stretches, the last picture in a box (a sparkline, bars, a chart, a camera) takes what is left, extra space falls between the header and the foot, and the measured height (`data-h`: `xs` under 80px, `s` under 136px, from a ResizeObserver) drops lines rather than spilling. Every link in the chain needs the cell's height, the `div` inside `ha-card` included.
- **Opening a card at a fixed size grows its cell** (`_grow`/`_shrink`). HA gives the cell a fixed height (`.card.fit-rows`) and `config.grid_options` beats anything the element answers, so the card cannot ask for more rows. While it is open it sets `height:auto`, a min-height and `grid-row: span n` on its own cell (the parent of `hui-card`, found by class within three steps; inline properties HA's `styleMap` does not manage, so a redraw keeps them) and every card after it makes room; closing removes exactly those. The opened card's height is measured with `:host([opened])` letting it be its content's, never while the card is the cell's height (which feeds the cell its own growth). Without the cell (a release that renamed it) the opened part scrolls inside the card.
- **Every key a Morph card reads is in HA's visual editor** (`configForm`): entity or entities, name, `icon` (swapped in for the face's first Morph icon as `ha-icon`, `withIcon`), room, colour, `actions` on a thermostat, `tap_action`/`hold_action`/`double_tap_action` (HA's `ui_action`, under an expandable *Interactions*; set, they fire `hass-action` as HA's cards do, and unset leave Morph's own grammar) and `detail` (an `object` selector; a Lovelace card mounted under the opened card, made once and kept). The converter writes `options.detail` as `detail`, a header switch onto its room's heading as a toggle entity, and `span` as `grid_options.columns` (span × 3), so no converted card has an `options` key. A kind a house's ACTIVE copy of `cards.js` adds is registered as its own `custom:morph-<kind>-card` (the copy is what HA's page was served) and the converter keeps it (`house`, `morphcode.card_types`).
- **brAIn sees Home Assistant's own dashboards** (`custom_components/brain/morph/eyes.py`, `screen_targets.ha_targets`). See `devloop.md`.
- **`tests/manual/measure-morph.mjs`** drives the real panel against `morph-fixture.mjs` (a fake `hass` answering every `morph/*` command, history, statistics, logbook, conversation and service calls) at 1440 and 400: overlaps at rest and while cards open and fold, same-row heights, taps, slides, Edit → hold → Tell → Keep/Undo, case replies, the rail, Coming up, the design rules and the reports blocks. **`measure-morph-cards`, `measure-brain-layer` and `measure-morph-features`** drive the HA-page modules on stand-ins for HA's page (a `hui-card` carrying the config object, `ha-panel-lovelace`, `loadCardHelpers`). All are hand tools, run when they help to see a change.
- **And Morph is checked in a REAL Home Assistant** (`tests/realha`). `ha_rig.py up` installs nothing: it configures and starts the `homeassistant` in its interpreter with the `demo` house, serves Morph's frontend from `/local/morph` through `frontend.extra_module_url` (what `add_extra_js_url` does), loads `eyes.py` in a stand-in integration, onboards an owner by script and waits for `RUNNING` (onboarding answers while integrations load, and a page opened then is "Loading data"); `check-morph.mjs` signs in through `hassTokens` and checks the converted dashboard, every size, opening, the editor, the view switches and the eyes, one PASS/FAIL line each. It uses HA's own port: an `http:` block that moves it makes HA ask, in a dialog over every page, whether to keep the change. Run it locally with a venv holding `homeassistant` (2026.x needs Python 3.14; 2025.1 needs `--pre` for one dependency).

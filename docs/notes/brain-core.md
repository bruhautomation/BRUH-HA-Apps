# brAIn: rules for any change

Cross-cutting rules every brAIn change is held to: ports and ingress, option translations, the two CLI dispatchers, quiet access logs, atomic writes, edit snapshots instead of git, guards that change the next attempt, how brAIn names itself and its prose, and module hygiene in a large server.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- One ingress port (8099, the panel). The panel reverse-proxies `/terminal/` through to ttyd on 7681 (`brain/panel/terminal_proxy.py`), so the terminal is a tab. The assist worker pool's internal API moved to **8098** to free 8099.
- **Ingress authenticates its own callers and nobody else's.** A port is either published or it is not, and a published one answers the LAN with no Home Assistant login in front of it — which is what [GHSA-gh5m-4m97-c95h](https://github.com/home-assistant/core/security/advisories/GHSA-gh5m-4m97-c95h) was about. brAIn shipped 7681 published with ttyd on `--writable` and no `--credential`: a root shell with `/config` and a signed-in Claude, for anything on the network. It is `null` in `ports:` now (declared, so the Network panel can still assign it) **and** ttyd always takes a generated `--credential` from `/data/terminal-credential`, which `terminal_proxy` presents upstream so ingress users never meet a prompt. The proxy **drops the client's `Authorization` header before adding its own** — otherwise a browser holding a credential for the ingress origin could present it to ttyd instead — and strips `WWW-Authenticate` on the way back, because a Basic-auth dialog inside the ingress iframe asks for a password the user has never been shown. **That drop has to case-fold, and for a long time it did not**: it was `headers.pop("Authorization")` plus `headers.pop("authorization")` over a plain dict that `_clean` keys by whatever case the client sent — and HTTP considers every spelling of a header name identical, so `AUTHORIZATION: Basic …` survived both pops and rode upstream *beside* the credential added on the next line, leaving ttyd to pick. It is `HOP_BY_HOP | CLIENT_DROPPED` now, filtered by the same lower-cased pass the hop-by-hop headers already got. The test that was supposed to hold this asserted the source contained that literal `pop` line, and passed for the whole life of the bug: **a grep for a line is not a test of what the line does**, which is why `tests/test_terminal_proxy.py` drives the function with five spellings and stands the bridge up against a real aiohttp server speaking ttyd's handshake. BRUH Minecraft has the same shape and a worse case: `host_network: true` (Bedrock LAN discovery needs it) put its `0.0.0.0:8099` management API — arbitrary RCON, world delete, restore — directly on the LAN, so `panel/server.py`'s `_lan_gate` middleware now allows only the Supervisor's networks and loopback. It reads the **socket's peer address**, never `X-Forwarded-For`, which a direct caller sets themselves; `/pack/` and `/api/health` are the only public prefixes, and `_peer_ip` returns `None` for anything that is not an `(host, port)` tuple so a unix-socket peer refuses instead of matching on `peer[0]`'s first character. Both add-ons ship `apparmor.txt` (profile name = slug, or the Supervisor won't load it) denying the host-escape set; Minecraft's needs `ixm`, not `ix`, or the JIT cannot map executable memory and Java never starts. Both rate **6/6** — `tests/test_addon_hardening.py` recomputes the Supervisor's arithmetic so a regression shows up there rather than in the store weeks later.
- **Every option needs a line in `translations/en.yaml`, or the UI shows the raw key.** `config.yaml`'s inline comments are for whoever edits `config.yaml`; they are not documentation, because nobody installing an add-on reads them. `test_addon_hardening` fails on an option with no entry, an entry with no option, and an entry missing a name or description — the drift is otherwise invisible.
- `enable_terminal` switches the Ask tab off. `enable_insights` gates the **scheduler** and hides House › **Reports** — the one pane only a scheduled Claude run ever fills — while **Today** stays whole, suggestions included, because the house checks cost nothing and still file there, and the checks pass fills the proposals store too; `insights_enabled()` is read at call time (the way `terminal_proxy._enabled` reads its twin) so a test can drive the scheduler either way, and it shipped exported and unread for two releases, switching a face off in the docs and nowhere else. The panel always runs because it is the ingress target.
- **No git auto-backup.** It was removed along with `auto_backup` / `backup_interval_minutes`. In its place, a `PreToolUse` hook (`scripts/brain-edit-snapshot.py`) snapshots files before Claude edits them, and `brain undo` restores them. The same hook first hands an unwritable file under `/config` (or another tree brAIn hands over) back to the `claude` user (`make_writable`, the ownership bullet below). Never touch a user's existing `/config/.git`.
- **Two CLI dispatchers**, not fourteen scripts: `brain` (memory, findings, learn, ask, undo, own, doctor) and `ha` (log, reload, entity, service, addon, notify, share, check, context). Both delegate to `/opt/scripts`. Adding a command = a script plus one dispatcher line — and the chat palette parses `brain help`/`ha help`, so the usage text IS the announcement. `brain findings` goes through the panel's API on 8099, never the store files: a second writer would race the panel's own, and the API is what writes the memory line, the settled key and the undo token an ending owes.
- **A guard that refuses has to change the next attempt, or it is a loop.** The size check (`memory_max_kb`, 32 KB) rejected an over-cap document and returned, so the daemon re-ran the identical prompt every 5 minutes and got the identical answer — while the queue grew, asking each attempt to fit *more* into a document already full. An overshoot now feeds the measured excess back to the model and only the second one fails, with a message naming the setting that ends it. The proportional shrink guard is skipped on that retry: it exists to catch a rewrite pretending to be a merge, and a pass we explicitly told to drop facts is neither. **A pass writes TWO capped files and from 1.18.0 until 1.52.1 only one of them was retried** — an over-long `voice.md` returned on its first overshoot with no note fed back and no attempt spent, which is this bullet's own bug left standing in the sibling branch six lines below the fix, and worse in one way: `memory_max_kb` is an option the message could name where `VOICE_MAX_BYTES` is a constant in the script, so that failure named no remedy anybody could perform and the queue could not drain by any route. Both caps are measured together now and either sends the pass round again, naming **both** when both overshot, because a note about one half invites an answer that fixes that half and breaks the other and so spends the last attempt learning nothing. What differs is the ending, and it differs because the two files are not the same kind of thing: `memory.md` IS the memory, so a document that will not fit is still refused whole, while `voice.md` is **trimmed** to its budget on whole bullets and filed — it is derived from the document and rewritten from scratch by every pass, so its tail costs one voice turn's nicknames until the next one where refusing cost the whole pipeline; whole bullets because half a line is a nickname that maps to nothing, measured the way the check that sent it there measures, so the trim satisfies that check by construction rather than by two arithmetics agreeing, and **reported**, because a file quietly missing its tail is worse than a short one. The shrink guard is the thing that had to be re-keyed: `retry_note` is the same string for two different requests, and a retry that asked only for a shorter distillate excused nothing about the document — read loosely it would wave through a wiped memory.md because a sibling file was over its own budget, which is the one answer that guard exists to catch. **The cap is not a latency setting** — voice reads the 2 KB `voice.md` on every request and never the document, so shrinking memory.md buys nothing where speed is felt. In the insight bundle memory has its own budget (`MEMORY_CHARS`), not a share of `CONTEXT_CHARS`: they used to split 4 KB with memory first, which truncated any real document mid-fact *and* starved the house context whenever memory filled it.
- **Who ran a conversation is a contract, not a guess** (`panel/run_sources.py` + `scripts/brain-run-source.sh`). Claude Code files every conversation under its working directory and records nothing about who asked; voice, the automation listener, study sessions and the consolidator all drive it from `/config`, so the Chats rail was the person's own chats buried under machine ones — and `adopt` (which takes "the most recently written conversation") routinely picked up the consolidator's. Each background caller **claims its own session id before running**; an unclaimed id is yours, so the default costs no inference and cannot drift when a prompt is reworded. Claim it by whatever route that caller already has: `--session-id` for the consolidator, study, and `engine._run_cli` (each with a fallback for a CLI that rejects the flag — the label is optional, the run is not), the uuid voice already mints, the `session_id` in `--output-format json` for automation tasks, the stream's own `session_id` in the worker pool. Filtering happens in `conversations.listing`, not the panel, or a page of 30 is spent on voice turns. Insight and fix runs (`card`/`fix`, `store: "engine"` in `SOURCES`) live in a different project directory because `engine` runs them from `CLAUDE_HOME` — the server lists that store under `?source=card`/`fix` (Ask's kind pills, beside `you`) and marks the rows `view_only`: they replay into a reader (`/api/chat/conversation/{id}/view`) and are never resumed, since their turns ran under the analyst's or fixer's scoping and the chat's permissions are a different contract. An unclaimed id in the engine's directory belongs to nobody (the auth self-check) and is dropped, not defaulted. The ledger is an index, not a queue: capped, never drained. **Both halves write the same file as different users** — the panel is root, the consolidator and study watcher are `su-exec claude` — so `run.sh` creates `/data/run-sources.jsonl` claude-owned before either starts; root can write a claude-owned file, not the reverse, and the failure is silent by design, which is how it went unnoticed. Silence means the shell's message too: `cmd >> file 2>/dev/null` hides the command's stderr, not the shell's own "cannot open", so every redirect in that library is wrapped in `{ }`.
- **A poll that succeeded is not news.** `QuietAccessLogger` drops successful GETs to the endpoints the panel asks for on a timer and logs everything else, with failures at warning; `log_level: debug` is the one switch that turns everything back on (it also raises ttyd's `--debug` mask, whose default 7 includes NOTICE — three lines per socket). Both halves of the terminal's websocket bridge get a `heartbeat`: pinging only the ttyd leg left the browser leg idle, so ingress and Nabu Casa closed it after a minute or two, ttyd killed the session's process, and the client reconnected forever. **And when a bridge does drop, it has to say why.** The two pumps race under `asyncio.wait(FIRST_COMPLETED)`, which does neither of the things that ending them needs: cancelling the loser only *asks*, so it was still inside `dst.send_*` when the `async with` closed the upstream socket under it; and an exception inside a task never reaches `asyncio.wait`, so a bridge that broke mid-frame was indistinguishable from a browser closing politely — `except (ClientError, OSError)` never saw it, the log said nothing about the reason, and Python printed a bare `Task exception was never retrieved` at some later collection, attributed to nothing. `_settle` waits the cancellations out and re-raises the winner's exception. It waits with `asyncio.wait` rather than `await task`, and reads *every* outcome rather than the winner's: a pump cancelled mid-send can come back carrying a `ConnectionResetError` of its own, and a first cut that awaited each loser under `suppress(CancelledError)` let that propagate — reporting the loser's incidental error while the winner's reason went unread and unretrieved, which is the same bug one case narrower. It is a named function precisely so it can be driven directly, because through a real socket "one pump fails while the other is mid-send" is not something a test can schedule.
- **A guard keyed on an option that does not exist is a guard that is off, silently** (`health.DAEMONS` / `_assist_daemon`). The table asked after `enable_assist` and `enable_automations`; the add-on's options are `enable_assist_integration` and `enable_automation_integration`, which is what `run.sh` reads when it decides whether to start either. `options.get()` answers `None` for a name that is not there, so both entries were skipped on every real install: **the automation listener dying was reported by nothing** (severity `failed`), and `_assist_daemon` — the one `failed` verdict about voice, and the reason the roll-call is asked as a *job* rather than by daemon name — returned on its first line and could never fire. Nothing errored; two guards were simply never asked. `enable_terminal` and `learning` were right, which is exactly what made the other two invisible. The suite could not see it because the fixture wrote the same names down that the code did — the `_error_code` envelope failure again — so `tests/test_health.py` reads every name out of `config.yaml`'s own schema and **drives `_assist_daemon` over every option in it** to prove at least one switches it on. **And the fault sweep reads the roll-call against the options too** (`health.expected_daemons`, asked by `reports.faults` rather than answered again): a daemon whose option is off was not asked for, and the assist channel is one job with two implementations, so the classic listener is *correctly* absent on every fast-mode install — read raw, the report opened with `not running: assist_listener` softened by a sentence sending the reader up to a verdict that had deliberately not mentioned it, which is "a refusal doing its job is not a fault" broken by the one function whose docstring states it. It is a **set** rather than a verdict because the two callers want different loudness from one fact: `problems` turns a missing one into a state and a sentence, `faults` only needs to know it was wanted. `reports.py` imports it as `health_rules`, because `health` is already a local name there three times over and a module shadowed by a dict fails at the attribute, a long way from its cause.
- **`tmp + rename` is atomic against a reader and a race against a writer, and every store had the second one** — the voice area map too (`assist-worker-pool._write_atomic`, the listener's `area_map_scratch`, the tracker's `_write_json_atomic`): two refreshes at once shared one `.tmp` and the second raised `FileNotFoundError`. The scratch name was derived from the target (`path.with_suffix(".tmp")`), so every writer picked the *same* name: two writers both create `findings.tmp`, the first `replace()` moves it, the second gets `FileNotFoundError` — and the loser's bytes went into a file the winner had already renamed away, so **one write is silently lost**. Reachable in the panel as shipped: `h_finding_fix` writes the findings store from a request thread (`asyncio.to_thread`) while `_generate` writes it from the event loop. It surfaced as `test_fix_and_snooze_offer_no_undo` failing about one full-suite run in three, which read as CI flakiness for as long as nobody traced it. Everything goes through `panel/atomic_write.py` now (`mkstemp` in the target's own directory, so the rename is still same-filesystem and still atomic), and `test_atomic_write.py` reproduces the old recipe failing before asserting the new one does not — a guard measured against a demonstrated failure rather than a described one, plus a grep-level test so a new store cannot copy the pattern back in. **Preserving mode and owner is not a nicety, it is the fix not regressing**: `mkstemp` creates `0600` where `write_text` made `0644`, and several of these files are written by root and read by the `claude` user; and `os.replace` swaps the inode, which is how the old prune quietly took `/data/run-sources.jsonl` away from the `claude` user that `run.sh` had created it for. `fsync` before the rename is the one addition — the rename was always ordered, the data behind it was not.
- **brAIn speaks as "brAIn", and its parts have no names a person reads** (`tests/test_one_voice.py`). Cards said "I", findings said "brAIn" and "it", and a fault row quoted "what the Resident last said": four narrators for one assistant. The card and investigation contracts say to write "brAIn" in the third person, never "I", and never name an internal part (the Resident, a first look, an investigation); fixed strings a person reads say "brAIn's check" or "brAIn looked". **And where brAIn's own fixed words name the assistant to a person — the who-acts line on a card, the Repairs dialog, a notification's title, the History filter — they use the household's chosen name** (`personality.assistant_name()`: `personality.load()["name"]` when one is set, else "brAIn"; one helper, read per sentence, so a house that named its assistant does not meet two of them). The panel passes it to `answers.who_acts`, the mirror carries it as `assistant` for the integration, and `notify_router.assistant()` reads it per message. **Since 4.0 the name is a switch** (⚙ › Features › Personality, `personality.enabled`, read straight off `/config/.brain/features.json` because this module is also a CLI and a voice-side import): off, `assistant_name` is "brAIn" and `prompt_block`/`section` are empty whatever is stored; no file is on, so a house that never chose keeps what it had. `personality.speak(text)` is the server side of "nothing says brAIn": the word in exactly that spelling becomes the name in prose about to reach a person (a notification's lines, `notify_router._speak`); the panel and Morph do the same as they draw. A model's prose and the add-on's own diagnostics are still written saying brAIn, and say the name only where a surface speaks them. Identifiers, the `resident` source id and wire values are unchanged, and a sentence already stored in the old words (`triage.LEGACY_STOCK`, the old `RESIDENT_TITLE`) is still recognised on read.
- **Who brAIn is has ONE stored answer, and a model's prose about brAIn reads it** (`personality.identity()` / `identity_line()`, `voice` in `personality.json` beside the name — set in ⚙ › Personality, or by a growth note that says the voice changed (`voice_named`); `house_words.self_said`; `findings_store.IDENTITY` / `SELF_CARE`; `self_care.py`; `tests/test_one_identity.py`). A house's findings said "My spoken voice changed from A to B", another that the household chose C, a card that B was already the voice, and one told the owner to edit "line 27 of chat_identity.md" and call `note_personality_change`. Every model-written row (`_plain_row`) and a card's title and summary (`_generate`) go through `self_said`: "I"/"my"/"me" and the household's name for brAIn become "brAIn" (the surfaces speak the name, so one name, never two), quoted words left alone; a sentence about brAIn's voice becomes "brAIn's spoken voice is <stored>." or goes when none is stored (a name claim goes: the surfaces already say the stored name); and a row about brAIn itself (`about_self`) loses every sentence holding a file path, line number, tool name, entity id or model id (a row's `text` is cleaned, never emptied). A model row pointing at a line of one of brAIn's instruction overrides that brAIn can find (by number or a quoted piece) is filed as `self_care`'s yes/no question — "Shall brAIn take that line out?" — whose Yes takes the line out through `instructions.drop_line` (`_end_self_care`), with no memory line; a line brAIn cannot find leaves an ordinary row, scrubbed. The card prompt carries `identity_line`, and `prompt_kit.IDENTITY` and the Resident's rules say brAIn's upkeep is its own.
- **Prose is never stored ending mid-word**: every cap on a finding's text, claim, detail or fix, an overnight cause, a correction offer, a follow-up's refiled text and a guess read back goes through `textclip.clip` (`tests/test_finding_prose_clipped.py`).
- **A test that patches a module patches the one the server holds.** Several test files pop and re-import panel modules (`intents`, `server`), so a module a test imported at collection time can be a different object from the one the code under test writes through. Bind `self.server.<module>` in `setUp`. `tests/test_card_opportunities.py` failed five ways in a full run and passed alone for exactly this reason.
- **In a fifteen-thousand-line module a second `def` of the same name is a silent replacement, so grep before you name a helper.** W2C added `_today` and `_house_snapshot` to `server.py`. Both names were already taken, by `/api/status`'s date and by the insight bundle's house block. Python kept the later definition, so `/api/status` and three insight tests broke far from the change that broke them. Nothing errored at import. They are `_house_date` and `_registry_snapshot` now. `ruff`'s F811 catches this only when both definitions are module-level and unconditional, so that rule is not a substitute for looking.
- **A local that shadows a parameter is a feature that does nothing, silently** (`ha_data.collect_orientation`'s `counts`). The new `domains` argument was rebound by the per-domain count dict three lines later, so the search path handed retrieval every domain in the house and the card's own did nothing — every test of the parameter passed because they asserted it was *accepted*. `tests/test_card_refresh.py` drives the real `collect_orientation` over faked Core reads and asserts what reaches `_read_context`, which is the only way that bug shows.
- **`/api/status` reads off the loop** (`_status_payload` under `asyncio.to_thread`, `_GENERATED_AT_CACHE` keyed on mtime and size). It is polled every 2.5 s per viewer while a job runs, and it parsed every stored card (up to 400 KB of HTML each) on the event loop to read one date.
- **Naming**: prefer `brain`/`ha` over `claude` in anything we own. `CLAUDE.md`, `CLAUDE_CONFIG_DIR`, the `claude` user, and the `claude-run` wrapper keep the name because they *are* Claude Code's file, env var, user, and binary. Everything else (`panel/engine.py`, `scripts/brain-*.sh`) is brAIn-named.

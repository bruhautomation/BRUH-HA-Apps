# BRUH Cooking

BRUH Cooking specifics: where it came from, the brAIn requirement, the services brAIn calls, the rename, its two test suites, and the rules kept from upstream.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **It is kedube/ha-breville-cooking, renamed and wrapped** (imported from upstream 0.11, commit `ed21dd7`, 2026-10-27). The integration (`custom_components/bruh_cooking/`), the panel's source (`frontend/`), its tests (`tests/`), the protocol notes (`docs/api.md`) and the probe script came across whole. Upstream is GPL-3.0 and this repository is MIT, so `bruh-cooking/` carries upstream's LICENSE and its image is labelled `GPL-3.0-only`: a file copied from there stays under GPL whatever directory it moves to. Breville's icon and logo did **not** come across (trademarks, used by upstream "only to identify the appliances"); `branding/cooking/` is the family lockup with a pot under the roof.
- **The domain is `bruh_cooking`, never `breville_cooking`**, so the add-on can sit beside a HACS install of the original without two integrations claiming one folder. The rename reaches the websocket commands (`bruh_cooking/panel/*`), the panel's URL (`/bruh-cooking`), its element (`bruh-cooking-panel`), its storage key and every translation. The sidebar title is "BRUH Cooking" for Breville and Sage accounts alike (upstream switched to "Sage" when every account was Sage). `tests/test_cooking_addon.py::TestTheRename` greps for a leftover, and the built bundle is checked for the new command names.
- **The add-on is a script and has no panel** (`run.sh`). It finds brAIn in `/supervisor/info` by slug tail AND name (the jq `BRAIN_FILTER`, the rule `devloop/siblings.spec_for` uses), exits with a fatal line when the answer was read and brAIn is not in it, and carries on with a warning when the Supervisor could not be asked — "I could not ask" is not "it is not there". It copies the integration when the shipped manifest version differs from the deployed one, posts the `bruh_cooking` discovery, then wakes every ten minutes to put a deleted integration back and to stop if brAIn was removed. No ingress and no port, so `TestWatchdog` exempts it: there is no panel to hang.
- **brAIn calls services that name the appliance** (`services.py`). Upstream's `start_cook` targets a Cook switch, which suits an automation and not a sentence; `get_status`, `get_presets`, `start`, `stop` and `continue_cook` take `appliance` (the person's device name, the app's, the device id or the serial; omitted when there is one), answer in words, and raise `ServiceValidationError` with a translation key on every refusal — an unknown or ambiguous appliance names the ones there are. `start` refuses over a running cook rather than replacing it, and `start_settings` is the one place a start's settings are worked out: the Cook switch's `start_cook` calls it too, so the two paths cannot drift. Every rule the entities keep is the coordinator's and applies here unchanged: untested models are monitor-only unless the options allow control, a running oven cook cannot be edited, stop always works.
- **brAIn's two tools** (`ha_mcp_server.cooking_status` / `cooking_control`). Listed only where the `bruh_cooking` domain is (`ADDON_TOOL_DOMAINS`). `cooking_status` is on `ANALYST_TOOLS`; `cooking_control` is on `ANALYST_DENIED`, both `GATED_MCP` copies and `CONTRACT_REFUSED_TOOLS`, because a start heats an oven or a bath. Voice may read, start, stop and continue (`VOICE_UNTARGETED`), both tools `ALWAYS_LOAD`: the owner asked for the appliances by voice, and the appliances are the last check (the oven waits for Start on its panel; a UL Joule for its button above 85 °C). `minutes` becomes an `HH:MM:SS` duration, a mode is folded to the oven's option id, and nonsense is refused before anything reaches Core.
- **Two suites the repository's stubbed Home Assistant cannot run**: `bruh-cooking/tests` stands up a real Home Assistant (`pytest-homeassistant-custom-component`, pinned in `requirements_test.txt`, Python 3.13) and the panel's is vitest. CI's `cooking` job runs both when `bruh-cooking/` changed, and fails when the committed bundle is not the one the source builds — the integration serves `custom_components/bruh_cooking/frontend/bruh-cooking-panel.js`, so a panel change is `npm run build` and that file committed. `test_drawings` outgrows Node's default heap on a small machine: `NODE_OPTIONS=--max-old-space-size=4096`. `tests/test_addon_service_responses.py` also imports the integration under its stubs to prove every service brAIn calls is registered to answer, which is why its stub list names the Home Assistant modules this package imports, and why the package must stay importable on Python 3.11 (no `type X = …`).
- **The devloop knows it as a sibling** (`devloop/siblings.CATALOG`, key `bruh-cooking`, label `devloop:bruh-cooking`). `devloop_guard` counts `bruh-cooking/tests/` and `bruh-cooking/frontend/test/` as tests, so a fix there with a test beside it is not "a code change with no test change".
- **run.sh says a restart of Home Assistant only when the integration's code changed** (`integration_fingerprint` / `integration_restart_verdict` against `/config/.bruh_cooking/integration.json`, which the integration writes in `async_setup` from `fingerprint.py`). A panel-only update is a page reload: `frontend.async_follow_bundle` (every 60s per entry, `cancel_on_shutdown`) registers the panel again under the new bundle hash, held by `tests/test_panel.py::test_a_new_bundle_gets_a_new_url_without_a_restart`. The rule for every add-on: `docs/notes/architecture.md`, the custom integration.

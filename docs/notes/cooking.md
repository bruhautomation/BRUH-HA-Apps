# BRUH Cooking

BRUH Cooking specifics: where it came from, the brAIn requirement, the services brAIn calls, the rename, its two test suites, and the rules kept from upstream.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **It is kedube/ha-breville-cooking, renamed and wrapped** (imported from upstream 0.11, commit `ed21dd7`, 2026-10-27). The integration (`custom_components/bruh_cooking/`), the panel's source (`frontend/`), its tests (`tests/`), the protocol notes (`docs/api.md`) and the probe script came across whole. Upstream is GPL-3.0 and this repository is MIT, so `bruh-cooking/` carries upstream's LICENSE and its image is labelled `GPL-3.0-only`: a file copied from there stays under GPL whatever directory it moves to. Breville's icon and logo did **not** come across (trademarks, used by upstream "only to identify the appliances"); `branding/cooking/` is the family lockup with a pot under the roof.
- **The domain is `bruh_cooking`, never `breville_cooking`**, so the add-on can sit beside a HACS install of the original without two integrations claiming one folder. The rename reaches the websocket commands (`bruh_cooking/panel/*`), the panel's URL (`/bruh-cooking`), its element (`bruh-cooking-panel`), its storage key and every translation. The sidebar title is "BRUH Cooking" for Breville and Sage accounts alike (upstream switched to "Sage" when every account was Sage). `tests/test_cooking_addon.py::TestTheRename` greps for a leftover, and the built bundle is checked for the new command names.
- **The add-on is a script and has no panel** (`run.sh`). It finds brAIn in `/supervisor/info` by slug tail AND name (the jq `BRAIN_FILTER`, the rule `devloop/siblings.spec_for` uses), exits with a fatal line when the answer was read and brAIn is not in it, and carries on with a warning when the Supervisor could not be asked — "I could not ask" is not "it is not there". It copies the integration when the shipped manifest version differs from the deployed one, posts the `bruh_cooking` discovery, then wakes every ten minutes to put a deleted integration back and to stop if brAIn was removed. No ingress and no port, so `TestWatchdog` exempts it: there is no panel to hang.
- **brAIn calls services that name the appliance** (`services.py`). Upstream's `start_cook` targets a Cook switch, which suits an automation and not a sentence; `get_status`, `get_presets`, `start`, `stop` and `continue_cook` take `appliance` (the person's device name, the app's, the device id or the serial; omitted when there is one), answer in words, and raise `ServiceValidationError` with a translation key on every refusal — an unknown or ambiguous appliance names the ones there are. `start` refuses over a running cook rather than replacing it, and `start_settings` is the one place a start's settings are worked out: the Cook switch's `start_cook` calls it too, so the two paths cannot drift. Every rule the entities keep is the coordinator's and applies here unchanged: untested models are monitor-only unless the options allow control, a running oven cook cannot be edited, stop always works.
- **brAIn's two tools** (`ha_mcp_server.cooking_status` / `cooking_control`). Listed only where the `bruh_cooking` domain is (`ADDON_TOOL_DOMAINS`). `cooking_status` is on `ANALYST_TOOLS`; `cooking_control` is on `ANALYST_DENIED`, both `GATED_MCP` copies and `CONTRACT_REFUSED_TOOLS`, because a start heats an oven or a bath. Voice may read, start, stop and continue (`VOICE_UNTARGETED`), both tools `ALWAYS_LOAD`: the owner asked for the appliances by voice, and the appliances are the last check (the oven waits for Start on its panel; a UL Joule for its button above 85 °C). `minutes` becomes an `HH:MM:SS` duration, a mode is folded to the oven's option id, and nonsense is refused before anything reaches Core.
- **Two suites the repository's stubbed Home Assistant cannot run**: `bruh-cooking/tests` stands up a real Home Assistant (`pytest-homeassistant-custom-component`, pinned in `requirements_test.txt`, Python 3.13) and the panel's is vitest. CI's `cooking` job runs both when `bruh-cooking/` changed, and fails when the committed bundle is not the one the source builds — the integration serves `custom_components/bruh_cooking/frontend/bruh-cooking-panel.js`, so a panel change is `npm run build` and that file committed. `test_drawings` outgrows Node's default heap on a small machine: `NODE_OPTIONS=--max-old-space-size=4096`. `tests/test_addon_service_responses.py` also imports the integration under its stubs to prove every service brAIn calls is registered to answer, which is why its stub list names the Home Assistant modules this package imports, and why the package must stay importable on Python 3.11 (no `type X = …`).
- **The devloop knows it as a sibling** (`devloop/siblings.CATALOG`, key `bruh-cooking`, label `devloop:bruh-cooking`). `devloop_guard` counts `bruh-cooking/tests/` and `bruh-cooking/frontend/test/` as tests, so a fix there with a test beside it is not "a code change with no test change".
- **A restart nobody made is said where people and brAIn look, not only in the add-on's log.** 0.1.9's fixes did not show on the house that reported them: every number the walkthrough quoted (132.8, 134.6, 125.6 °F) is what 0.1.8's `get_presets` answered and 0.1.9's cannot, so Home Assistant was still running the integration it loaded before the update, and the only thing that said a restart was owed was a line in the add-on's log (inferred from those numbers; the house's own record was not read). Now the loaded integration checks the copy on disk every 5 minutes (`restart.py`, by `fingerprint`) and raises a non-persistent Repairs issue (`restart_required`) while they differ, and run.sh writes `/config/.bruh_cooking/deployed.json` (version and fingerprint) beside the integration's `integration.json` (which now carries the loaded version too), so a reader outside Home Assistant can tell the two apart even while the old integration, which has no such check, is the one running. brAIn is that reader: `cooking_status` adds `restart_needed` (a sentence for the person) when both files carry a fingerprint and they differ (`ha_mcp_server._cooking_restart_owed`); a Cooking older than 0.1.10 writes no `deployed.json`, so nothing changes there. **And brAIn's integration says it in Repairs** (#1185; `custom_components/brain/cooking_restart.py`, issue `cooking_restart_required` under brAIn): Cooking's own issue can only come from a loaded copy that has `restart.py`, so the first restart after updating from an older one was said nowhere in Home Assistant. Every five minutes (in the account-wide watcher slot) it compares `deployed.json` with `integration.json` while `bruh_cooking` is loaded, and a record with no fingerprint counts as owed (run.sh's `integration_restart_verdict` rule, the one place it is stricter than `_cooking_restart_owed`). It stands aside while Cooking's own `restart_required` exists (dismissed included), and clears when the fingerprints match, the integration is not loaded or `deployed.json` is gone. Its own reader, not an import: the MCP server is another process.
- **run.sh says a restart of Home Assistant only when the integration's code changed** (`integration_fingerprint` / `integration_restart_verdict` against `/config/.bruh_cooking/integration.json`, which the integration writes in `async_setup` from `fingerprint.py`). A panel-only update is a page reload: `frontend.async_follow_bundle` (every 60s per entry, `cancel_on_shutdown`) registers the panel again under the new bundle hash, held by `tests/test_panel.py::test_a_new_bundle_gets_a_new_url_without_a_restart`. The rule for every add-on: `docs/notes/architecture.md`, the custom integration.
- **An offline appliance reports no readings, and the registry is never asked by identifiers.** `describe` (`services.py`) answers `current_temperature` and `time_remaining_minutes` as `None` unless the appliance is online and the cloud connected: the status object keeps the last reading, and brAIn repeated it as if it were now. Devices are found with `coordinator.device_for` (this integration's own devices, matched on the serial) rather than `DeviceRegistry.async_get_device(identifiers=…)`, which Home Assistant deprecates and logs at every start. Held by `tests/test_services.py`; the real-HA suite could not be run where this was written (the pinned test package does not build there), so run it in CI before trusting it.
- **A sous vide preset cooks the whole degree it shows, on every path that says it.** In a °F house the panel shows a built-in preset's °C converted and rounded to a whole °F, and `presets.applied_settings(fahrenheit=True)` rounds the °F value (`builtin_fahrenheit`) and converts back for the device (56 °C is 132.8 °F, shown and cooked as 133 °F, sent as 56.1 °C); Celsius houses are untouched. `get_presets`, what brAIn reads, answers through `presets.display_temperature` with the same rounding (an oven preset's own `temperature_f`, a saved preset to the nearest half degree) and the unit, and its `note` is one line on the doneness or food (`DESCRIPTIONS`) plus the raw-fish caution. 0.1.4 rounded the panel and the cook and left `get_presets` converting unrounded (125.6, 132.8 …): a rounding rule has to reach every reader, so there is one function per rule.
- **Offline says why, from what is observed** (`coordinator.offline_report`): Breville refusing the sign-in (an auth error from the refresh, the websocket or a command), the cloud connection down, or the connection fine while the appliance reports offline — each with one thing to try. **How long is said from `last_contact`, the time shown beside it**, never from a clock that starts with Home Assistant: 0.1.9 counted from `offline_since`, which is set only when the change to offline is seen, so an appliance already offline when Home Assistant started said "Offline for under a minute" on every read, beside a cook days old (#1117). `last_contact` is kept in `.storage`, moves to now when the cloud drops while the appliance was online (it was in contact until then), so the text reads "Offline for 3 days, counted from when it was last heard from", and with none "Offline for an unknown time: not heard from since Home Assistant started". The status sensor stays available (state `offline`) so its attributes carry `offline_reason`, `offline_since`, `offline_cause`, `last_contact` and `last_cook`; `get_status` carries the same. The problem and cooking binary sensors stay available while the appliance is on the account: problem keeps its last error, cooking reads off offline, or unknown when a cook was open when contact went (the offline text says so); every live reading still goes unavailable. `last_cook` is `coordinator.cook_summary`: "no cook yet" before one, otherwise only the fields known (a blank target or time is left out, and filled in from later reports of the same cook), the target in the house's unit, and `settings_from`. Losing contact is not the end of a cook: `last_cook` keeps `ended_at` empty and gains `finish_at` (the finish last seen) when the appliance or the cloud drops during a cook. Contact coming back is not a new cook either: the same cook id running again carries on the last cook with its source, and an appliance seen idle after contact was lost closes the cook it left open (`ended_at` is when that was seen). The cook id is kept beside the last cook in `.storage`, so a restart mid-cook carries on the same way. Last contact and last cook are kept in `.storage` (`bruh_cooking.<entry>.appliances`, saved on unload too), so a restart while the cooker is offline still says them. Sign-in, cloud, online/offline and cook start/stop are logged once per change at info, never with a token or an email.
- **Every cook says where its settings came from** (`settings_from`, on `last_cook` and on `get_status`'s `next_cook`). Every start goes through `coordinator.async_start_cook(…, source)`, which holds the source until the cook is seen, for 15 minutes at most (`START_WAIT`: the cloud can accept a start the appliance never begins, and that must not label a cook someone starts by hand later, which reads "started on the appliance or in the app"). The source is a preset named to `start` (", changed at the start" when other settings were given beside it), or `settings_source`: the preset the panel last applied while the settings are still exactly what it made (`note_settings_preset` keeps a copy), else "the cook settings in Home Assistant".
- **The account says how it stands, in Home Assistant and in the add-on's log.** One service device per entry, "Breville account" (or "Sage account", `coordinator.brand`, which the log line, the account file and the add-on's log line use too), with one sensor: the connection as the state (`connected`, `not_connected`, `sign_in_refused`), and `appliances_found`, `last_poll` (the last good read of the appliance list) and `not_driven` (each appliance on the account the integration does not drive, by name, with the reason: a model it does not know, or no serial) as attributes. It lives on its own device so the appliances' entity maps, the panel and its fixtures do not see it, and `get_status` keeps its shape (`{"appliances": []}` with nothing set up). The coordinator logs it once per change and writes it to `/config/.bruh_cooking/accounts/<entry_id>.json` (one writer at a time, newest last; deleted when the entry is removed), which `run.sh` (`report_accounts`) logs a minute after start, on a change, and hourly — the add-on's log is not Home Assistant's, and 0.1.4's add-on log said nothing.
- **Entity ids are never renamed on their own.** Home Assistant fixes an id when the entity is created, so an appliance renamed later keeps ids from the old name while the friendly names follow the new one. The device takes the app's new name at the next poll (`_follow_name`, unless a person named it in Home Assistant), and `BrevilleEntity.device_info` is a property built from the appliance's name now: built once in `__init__` it re-registered the old name every time an entity was re-added, which a rename of one id does, and undid the rename for the rest. For the old ids `entity_ids.py` raises a fixable Repairs issue per appliance and `repairs.py` renames them only when the owner submits it, with `EntityRegistry.async_regenerate_entity_id` (Home Assistant's own rule, as its "Recreate entity IDs").

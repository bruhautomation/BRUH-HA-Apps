# brAIn: notifications, Repairs and HA-side answers

Tiers and escalation, quiet hours, the dispatcher, the delivery ledger, swipe learning, speak first, requests from HA (To-do, Repairs, phone buttons, Reply), the findings mirror and watcher.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **A finding waiting on somebody is a Repair, and an issue is STATE where an event is NEWS** (`findings.FindingsWatcher.sync_issues` / `REPAIR_STATUSES` / `repairs.FindingRepairFlow`). The mirror already fired a `brain_finding` per new row and counted the open ones; what nothing did was put them where Home Assistant puts the things that need a person, which is read by people who never open the panel. Three statuses raise one (`open`, `needs_you`, `failed`): `fixing` is a repair brAIn is running right now, and `fixed` is news to READ whose one honest answer is the tab's "Got it" — not a verb a request can carry, so a dialog offering *I've fixed it* over a row saying brAIn already did would ask somebody to claim somebody else's work. **`info` raises nothing at all**, which is the check catalog's own first rule applied to a surface rather than to a rule: a Repairs row nobody has to act on is how the page holding the row that matters stops being read. **The issues are reconciled and not diffed, and that is exactly why they are not primed the way the events are** — `prime` adopts the open list so a restart does not replay it onto the bus, and the same restart *cleared* every non-persistent issue, so the first poll after a boot is what has to put them back; re-raised only when the sentence moves (a check refreshes its `detail` in place and a dialog quoting last week's figure is a reading nothing can correct), which is what stops a registry write every sixty seconds over an answer that has not changed. **The cap is 25 and takes the OLDEST**, after every Urgent card (`urgent` on the mirror row, `notify_router.is_urgent`: critical and a `now` producer or `stakes: high`), which always raises one, at CRITICAL — because the row that has waited longest is the one at risk of never being looked at and taking the newest would delete and re-create the set under somebody's cursor on every pass. **The dialog IS the card** (#452): the issue's title is the card's own title (`answers.request_view` → the mirror's `views`, keyed by ts BESIDE the rows so a row keeps the wire shape every reader has read — `test_cases` pins it), its description opens with the card's who-acts line (`who`, and where brAIn can act, where Go ahead is — Home Assistant cannot start a fix that shows its change first) and its menu carries the add-on's words for each press (`labels` on the issue, off the mirror's `labels` table, through `FindingRepairFlow.menu_labels` as a dict `menu_options`); an issue an older add-on raised has none and falls back to the translated words, which are the same words. The press writes a **request** through the same `requests.write_request` the To-do app and the notification buttons use — `_end_finding`'s whole reason for existing — and it is **remembered as answered until the row leaves the mirror** (`mark_answered`/`_forget_answered`): the add-on drains within seconds and the row is still there until it has, so without the memory the next poll raised the issue again and the dialog reappeared the moment it closed. A write that failed **aborts and leaves the issue up**, because an entry that vanished over an answer nothing recorded is the one ending with no way back, and `sync_issues` never raises, since a Repairs page that could not be updated is not a reason to stop announcing findings. **And `brain.check` is the same queue's one non-ending** (`finding_requests.CHECKS_KIND` / `server._start_requested_checks`): it rides there rather than in a directory of its own because the ORDER between kinds matters — an ending given in the same burst is applied first, or the pass re-files what was just settled — and the drain **starts** the pass rather than awaiting it (`h_baselines_run`'s clock: a run is minutes of work and the loop owes the next answer fifteen seconds), which is what makes coalescing load-bearing rather than tidy, since `create_task` only schedules and two tasks made in one tick would both clear `run_checks`' own guard. `CHECKS_REQUEST_STATE["starting"]` is a second flag flipped synchronously for `start_auth_check`'s reason, and a pass already running **consumes** the request and logs it rather than queueing a second look at the same house. `button.brain_run_checks` presses the service through the registry rather than writing its own file, so there is one implementation of what asking for a pass means.
- **A notification that cannot be answered twice is one people learn to ignore, and one that arrives for everything is one people delete** (`notify_router.tier_of` / `ESCALATION_S` / `server._escalation_tick`). Every row above `findings_notify_min_severity` was pushed once and never again, so the floor was the only dial anybody had: lowering it to hear about a freezing pipe let a dying battery through the same door, and raising it silenced both — *"only very critical things need to be escalated; otherwise users can see info in a card"*. Three tiers now, decided per row from severity **and** the producer's urgency, which is the pair rather than either: severity alone escalates a battery three weeks out, urgency alone escalates every sensor that blinked. **Escalate** is `critical` and `now`, pushed through quiet hours (the window protects a bedroom from a forecast, and a freeze warning at 3am is when it is wanted) and then **repeated** on a ladder; **notify** is everything else above the floor, exactly what shipped before; **quiet** is below it and is not lost, the row being on the Findings tab, in `todo.brain` and in Repairs. The floor's default moved to `critical`, which is what makes the tiers mean anything rather than being a louder copy of the same list, and it is **one constant read by the panel and by run.sh's env fallback** — a default that disagrees with itself is a second answer that wins exactly when nobody is looking, so a test reads `config.yaml`, `run.sh` and `DEFAULT_MIN_SEVERITY` together. Five rules on the ladder. **Its rungs are offsets from the FIRST message, not gaps between them**, which is what makes a ledger read off disk land on the minute the process that wrote it would have — `_resume_backoff`'s reason, and a restart is the first thing anybody does when their phone is going off. **It ends**, three reminders and the last one says so, because a notification that will go on arriving for ever is one people silence, taking the next real emergency with it. **A repeat is cancelled by the live store and never by the ledger's own copy** — fixed, dismissed, snoozed, moved to the to-do list and cleared by the check that filed it are five endings and all of them mean stop, and snoozed is deliberately among them because "remind me later" is somebody answering and reminding them anyway is the notifier arguing. **A store that could not be read HOLDS the reminder**, which reverses `take_queue`'s rule on purpose: a held row is announced once, so a wrong send there costs one message, where a ladder that cannot tell whether a problem is over goes on ringing three times about one somebody fixed an hour ago — and the next pass is minutes away. And **the cap refuses rather than making room** (`todo_store`'s rule): the room would be made by dropping the row that has been escalating longest, which is the one most likely to still matter. It ticks inside the flush loop that already recomputes its wait — one loop, because "is anything waiting to be said" has one answer — and that wait now takes the soonest `next_at`, or a reminder due in ten minutes waits out a nine-hour night. `/api/diagnostics` carries what is escalating and when the next one is due, because a queue nobody can see is a queue that silently swallows, and this one can fail in two directions.
- **The notify tier is a judgement and the escalate tier is not, and the dispatcher only ever sees the first** (`panel/dispatch.py` / `server._dispatch_notify_tier`). `notify_router` decided a row's loudness and its timing from tables keyed on producer names, which is right at both ends — under the floor nothing, a leak always — and was nobody's judgement in the middle: a freezer drifting at 22:40 went out under "brAIn found a problem" with `[warning]` in front, or was held to 07:00 because its producer was not on a list. Now one tool-less Haiku call (`dispatch` job, `--json-schema`) per batch decides `now | hold_until | digest | feed_only` and writes ≤160 characters for a lock screen, reading the household's sentence (`settings_store.notify_policy` + the learned clauses), the house clock, quiet hours, the last day's deliveries and each row's evidence. **It is called after the escalating rows have been sent and is never handed one** — structure, not a filter, so a dispatcher that is slow, wrong or absent cannot delay or reword a leak (`test_an_escalating_row_is_sent_first_and_never_shown`, mutation-checked by moving the call above the escalate branch). **Silence is the deterministic path**: `_resident_gate`'s three gates, a batch past `MAX_ROWS`, a failed or raised run and an unreadable reply hand back the whole batch, a row the reply skipped or answered outside the vocabulary hands back that row, and `_announce_findings` sends what it handed back exactly as before — never `feed_only` on a failure, which is driven over eight failure modes inside and outside quiet hours against a baseline taken with the gate closed. Three refusals in `dispatch.parse`: **`feed_only` on a critical row is no decision** (a learned clause can move a battery to Saturday and cannot make a critical alert into none); **a hold must land inside `HOLD_MAX_S` and not in the past, refused rather than clamped** (a model that answered a time it was told it could not use has not answered); and **the words may name only the row's own entity, its evidence entities, and anything its own sentence already names**, by id or by friendly name off `_NAMES` (a name inside a longer allowed name is excused) — otherwise the decision stands and the words are the deterministic composer's. A hold rides the existing quiet-hours queue with `until` and its words (`notify_router.hold_timed`); `take_queue` releases only what is due, the flush runs only outside quiet hours so a hold due inside them leaves when they end, `next_hold_at` wakes the loop, and `compose_released` sends an untimed release exactly as before. `DISPATCH_STATE` rides `/api/diagnostics` with the last fallback's reason, because a dispatcher that always stands down and one that works send the same messages.
- **Every message is a line in a ledger, and the tag is the thread back to it** (`panel/deliveries.py`). `_send_notification` records every send and every failed send (`kind`: notify/escalate/held/reminder/brief/weekly/reply, plus `accepted` for `_announce_accepted` and `notice` for the safety lane's persistent notification, the two senders that do not go through `_send_notification`) and puts `brain-d-<id>` in `data.tag` on a companion-app message — which is why `test_a_batch_carries_none_because_it_could_not_say_which` now asserts *no buttons* rather than *no data*. Outcomes are FOLDED from append-only lines rather than rewritten: *answered* is the request drain's `via: notification` (`_deliveries_note_requests`, a To-do tick is an answer to the row and not to a message), *cleared* is `mobile_app_notification_cleared` (now subscribed by the bus, delivered through `server._on_bus_event`, which calls `_note_safety` FIRST and never turns a swipe into a signal), *ignored* is derived after a day, *opened* is not reported by Home Assistant and the summary says so rather than recording zero. Android reports a swipe and iOS does not, so `clears_ever` rides beside the counts. Capped like `run_sources`, `None` for an unreadable file, never raises, and named in `backup_exclude` because it holds lock-screen sentences about the house.
- **A pattern in what somebody swipes is a question, never a setting** (`panel/notify_learn.py` / `server._notify_learn_pass` / `_end_notify_suggestion`). Weekly and deterministic: ≥8 finished single-row sends of one entity (or of a producer, over sends its qualifying entities did not claim) with ≥80% dismissed (`snooze`) or cleared unanswered files ONE question case through `findings_store.add_case` under source `notify_policy`. Critical rows, `safety`/`resident` producers, digests, escalations, reminders, replies, pending and failed sends are not counted, and *ignored* is not a dismissal (an iPhone never reports a swipe). Its ending is intercepted at the top of `_end_finding`: Yes appends the clause to `settings_store.notify_policy_learned` (shown one per row in ⚙ with its own Remove; a full list REFUSES the Yes before settling, `todo_store`'s rule), No is remembered so the subject is never asked again, and **neither writes a memory line** — a preference about notifications belongs to the sentence, and the confirm template would have filed "Confirmed by the homeowner: You dismissed 9 of 10…" into memory. `_undo_finding` takes the clause back with the card. `add_case` is not the gate, so the pass reads `muted_sources` itself, or "Stop raising these" on one of its cards would clear rows and mute nothing.
- **The brief and the weekly report are not findings** (`notify_router.compose_brief` / `compose_weekly`). Both were handed to `_send_notification` as a one-row "finding", so the two messages designed NOT to be a list of problems arrived as "brAIn found a problem" with "[info]" in front.
- **Speak first is announce-only, and the refusals are the feature** (`panel/household.py` / `server._speak_first`, `speak_first` off by default). A serious, `now`, notify-tier `check:` row is announced on the `assist_satellite` in the freshest occupied room (motion/occupancy/presence within 10 minutes, or on), as well as sent to the phone. Never: an empty house (every tracked person away), a room with no satellite, quiet hours, an escalating row (the phone's ladder), a model's sentence (Resident claims), words naming a tracked person, a protected satellite, or a Core without `assist_satellite.announce` (feature-detected off `/services`); once per finding and spaced `SPEAK_SPACING_S`. It does **not** call `start_conversation`: a spoken answer has to be tied to its case by the panel, which needs the satellite and caller identity on the voice turn. That context now rides every voice turn (`conversation.describe_place`), so the conversational half is buildable and simply not built yet: until it is, an answer would reach the agent with no case attached.
- **The Repairs reason box cannot carry a fix** (`interpret.SURFACE_ENDINGS`). It sits under "Not a problem" with the dialog's own "I've fixed it" beside it, and an interpreter reading "it's mains powered, there is no battery" as `done` settled the row as fixed: no `exception:` rule on the entity, the trail saying "you said you had fixed it" every pass, and the answer lapsing into a recurrence while the check still reported it (with `done`'s `hint` filing only the Resident's `memory_hint`). On that surface the words may make the press a to-do or a snooze, or give the Wrong its reason; never `done`. The SYSTEM prompt now says why a report does not apply is a `wrong`'s note. A phone reply keeps `done` (nothing was pressed), and the dialog's own fixed step still means fixed.
- **A phone reply that ends a case is answered with an Undo** (`PHONE_UNDO` / `_undo_from_phone` / the `undo` notification action, both `ACTIONS` tuples). The confirmation carries the toast's own token, found by the finding's ts within `undo_store.TTL_S`, so the phone's Undo puts back the row, the settled key, the memory line and every rule the correction wrote. `undo` is absent from `VERBS` (it takes an ending back) and from the Repairs menu (it is offered nowhere a case is still open).
- **Reply continues the case, and nothing about it settles anything** (`notify_router.ACTION_BEHAVIOUR` / `finding_requests.ACTIONS` / `server._reply_to_finding`). The companion app opens its own text box for a button carrying `behavior: textInput` and sends what was typed as `reply_text`; the integration files it as a request under the same queue every ending rides, and the panel's drain hands it to `run_analyst` (reading tools only — a reply must not be able to change the house) with the finding it was typed under and the words, and pushes the answer back to the same service about the same row, so the exchange carries the same buttons and can go on. **`reply` is in `ACTIONS` and not in `VERBS`**: it is a turn in the conversation and maps to no ending on the tab. A run that failed still answers, in one sentence, because a reply that vanished into silence is worse than one that says brAIn could not look; an empty reply is not a turn and spends nothing. `tests/test_finding_requests.py` drives the real drain with the analyst and the notifier stubbed and asserts the row is exactly where it was afterwards.
- **The findings watcher's roster is primed in full, and a snooze is not an ending** (`findings.FindingsWatcher.prime` / `_rows`, `findings_store._publish_state`'s `snoozed`). `prime` adopted the id watermark and left the status snapshot empty, so the first poll after every restart compared against nothing and replayed `brain_change` for every `fixed` row. And the mirror dropped snoozed rows, so Dismiss read as an ending (`brain_case_ended`, the Repairs issue removed) and the row's return as a new case. Snoozed rows are published under their own key — old readers never see it — kept in the watcher's roster, counted by nothing and raised as no issue. The mirror carries the whole live list (`STATE_MAX_ROWS = MAX_FINDINGS`) because it kept the newest 50 while Repairs takes the OLDEST 25; the reader's cap is 1 MB.
- **A notifier that wakes the house is a notifier that gets deleted, and severity is the wrong axis for it** (`panel/notify_router.py`). There was a sender and no router: five callers handed new findings straight to one notify service and the whole policy was a service name and a severity floor, so `sys.disk_low` at 03:40 was a phone lighting a bedroom about something still true at breakfast. **Urgency is not severity** — a `critical` battery forecast is three weeks out and a `warning` about a boiler that has stopped answering is now — so it is declared per **producer**, never per row, because a producer is a line of code and a row is a sentence a model or an f-string wrote and will reword. **A quiet hour is a HOLD, not a silence**: dropping is a notifier silently deciding some problems were not worth mentioning, so held rows queue on disk and leave as one message when the quiet ends — but anything settled or cleared while it waited is dropped from that queue rather than announced, because being told at seven about a problem that went away at four is exactly how these messages stop being about anything, and an *unreadable* store sends everything, since not knowing whether a problem is over is not evidence that it is. The window crosses midnight in the ordinary case (22→7), which a plain `start <= h < end` answers backwards at every hour, and `start == end` reads as **no quiet hours** rather than a permanent silence — somebody has set both boxes the same by accident and a notifier that switched itself off is the unrecoverable reading. The flush loop recomputes its wait every pass rather than sleeping once, or a Configuration-tab edit would be honoured only tomorrow. What is deliberately **not** here is coalescing across those five callers: each already hands its whole batch over at once, so a checks pass is one message however many rows it filed, and a debounce holding the urgent ones back to merge them would be machinery paying for a failure nobody can produce. The hold queue rides in `/api/diagnostics` because a queue nobody can see is a queue that silently swallows — "quiet hours are working" has to be tellable from "the flush loop died holding four findings since Tuesday".
- **The decision to send a brief is made before any model is asked** (`panel/brief.py`). "All quiet" every morning is the message people mute, and it costs a Claude turn — the most expensive thing the add-on does — to produce; so `worth_saying` is deterministic and reads what is already counted (findings filed since the last brief, a health verdict that is not `ok`, a night with an unusual share of changes nothing can attribute), and an empty answer costs nothing and sends nothing. What the model is for is the *sentence*: under `MAX_WORDS`, one paragraph, no greeting and no markdown, because this is read on a lock screen — and it gets read-only tools to make a reason **specific** rather than to find new material, since a brief that goes looking is a brief that reports what it found instead of what mattered. A reply under `MIN_CHARS` is not sent, because a four-word brief is worse than the silence it replaced. `due` opens the window at the measured wake (the fallback hour until there is a measurement) and closes it 45 minutes later, so a panel restarted at 09:00 does not deliver breakfast at lunchtime; `BRIEF_STATE["last_sent"]` is stamped **before** the run, because a pass that takes three minutes must not let the next tick start a second one and a failed brief is still this morning's. It is **off by default** and gated on a notify service existing, because a scheduled Claude run nobody receives is the "refresh everything" button with a timer on it. Both halves ride in `/api/diagnostics`: a rhythm that never gathered enough days looks exactly like one that did and chose 07:00.
- **An answer given somewhere else is a REQUEST, never a write** (`panel/finding_requests.py` + `custom_components/brain/requests.py`). The panel owns the findings store and Home Assistant cannot reach it — 8099 is `null` in `ports:` on purpose, and an HTTP transport is a decision nobody has made — so a tick in the To-do app and a button on a notification cross the gap as a small JSON file on the shared volume, which the panel drains every 15s and applies **through the same code the tab's own buttons use**. `_end_finding` was extracted from `h_finding_verb` for exactly that: an ending is three things (the row deleted, the key in the settled ledger, the memory line in the homeowner's own words), and a second implementation would be the same answer teaching brAIn two different things depending on where it was given — which is why `test_the_two_doors_produce_the_same_ledger_entry` drives both and compares. Four rules, each about the two sides being a few seconds apart rather than about anything going wrong. **A request naming a finding that is gone is an ordinary race** — somebody's phone was out of date — so it is dropped and logged, never retried and never resurrected. **Applying twice has to be harmless**, because the delete can fail on a read-only `/config` and the next pass finds the same file: settling an already-settled finding changes nothing, so there is no ledger of applied ids and there does not need to be. **Every field is data from another process** (the id is an int or the request is dropped, the verb is one of a closed set, the note is capped). And **the queue is bounded**, so an add-on off for a week does not spend its first minute on a directory nothing drained. The integration writes to a scratch name and renames, because the panel globs `*.json` and would otherwise be able to read half a request; the name carries a millisecond stamp **and a process counter**, because several ticks in one burst land inside the same millisecond and the stamp alone does not order them.
- **`todo.brain` is To Do and nothing else** (`custom_components/brain/todo.py`, named "brAIn to-do", unique id unchanged). It used to show the open findings beside the accepted chores, so the app held five where the panel's list held four and an undecided finding sat among agreed work; a finding is a decision, which is the queue's (Today, Repairs, `binary_sensor.brain_needs_you`), and it joins this list when somebody presses Add to To Do. Nothing is stored on the HA side: the to-do mirror's open items are the list. Completing one is the To-do tab's Done (the moment the memory line is written) and deleting is taking it off the list undone. The uid is `t:<id>`; an `f:<ts>` (or bare integer) uid an app still holds from before is answered as a finding (`fixed`/`wrong`), because ticking it must not answer about the wrong row. **Adding an item IS offered**, because there is a store behind it; `brain.add_todo` is the same drop. **No due dates** (a date parsed out of a sentence is a guess). The entity is **unavailable until the to-do mirror has been read at all** — the findings mirror alone is not a list — and then holds its last list forever, because an add-on restarting for ten seconds must not read as all-clear. The platform is `getattr(Platform, "TODO", None)`: `todo` arrived in core 2023.11 and this integration's floor is 2023.6.
- **Buttons on a notification are gated on the one signal that is not a guess** (`notify_router.can_answer` / `actions_for`). Only a `mobile_app_*` service gets `data.actions`: every other notifier takes `data` and means something different by it or nothing at all, and a payload built on a guess is how a working notification stops arriving — a missing button is the much smaller loss. A notify **group** containing mobile apps is deliberately not detected, because it cannot be from a name and guessing wrong is that failure. And only a message about **exactly one finding** gets them, because a digest is several problems and a button on it would have to guess which; `send_notification` omits `data` entirely rather than sending `{}`, since several notifiers read the key's presence as a request to be parsed. `parse_action` lives in `requests.py` rather than the integration's `__init__` for one reason: that module imports `homeassistant.core` and nothing else, so `tests/test_brain_todo.py` drives the add-on's own writer straight into it — a wire format written down twice with only one side tested is a format that drifts.
- **`todo.brain` lists what To Do shows — open and not snoozed** (`todo_store.SNOOZED` / `shown` / `publish_state(only_if_changed=)`). Snooze on a To Do row lives in the cases' sidecar the mirror never read, and the mirror was rewritten only on a to-do write, so snoozed chores stayed in the To-do app. The panel hands the store `cases.snoozes` (the store may not import `cases`), the mirror carries the awake items with `open` their count and `snoozed` beside it, the scheduler tick republishes when that moved, a `t:` snooze or wake republishes at once, `list_count` is `counts()["shown"]`, and `todo.py` lists only rows that are open and not snoozed. The queue (findings, questions, suggestions) is a different list on purpose and its count is not To Do's.
- **The Open findings sensor counts the queue too** (`findings_store.QUEUE_COUNT`, set to `server._queue_count` at import; `sensor.BrainOpenFindingsSensor` reads `queue_count` off `status.json`). It read the findings mirror's findings-only `open`, so an open question or suggestion was a badge of 3 beside a sensor of 2. The store cannot ask `cases` (which reads the store), so the panel hands it the callable, `open` is the queue when it can be counted, and the findings alone ride as `findings_open`.

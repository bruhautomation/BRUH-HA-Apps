# brAIn: Ask (the chat and the terminal)

The chat's sessions and registry, permissions and approval cards, discussions, adopt/handoff, replay budgets, the model picker and context pill, the terminal's mobile input and voice mic.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **The chat's row states are seven words and ONE derivation** (`chat_session.ROW_STATES` / `SessionRegistry.state_of`). With several live conversations, "which of these is actually running" stopped being answerable by looking: a paused conversation, one the cap stopped to make room, and one whose context the CLI has dropped are three different things a person has to do three different things about, and all three rendered as a row with nothing on it. So there is a closed vocabulary — `live`, `answering`, `needs_ok`, `paused`, `paused_room`, `context_lost`, `record` — each with a label and a hint, and one function that decides which, for a held session and for a bare `meta` alike, so a row and the composer above it can never disagree. **The order is the argument**: a `record` is a record whatever else is true; `context_lost` outranks a live process on purpose, because the process is fresh and the transcript on screen is not its, and that is the one thing worth saying until the next message makes them agree; everything else is only reachable off a process. `paused` deliberately renders **no pill and no composer line** — a conversation with no process is the ordinary case and is not news, and sending is what resumes it (the old "Your next message resumes…" line and its **Resume now** were a second control for Send, cut in the redesign; `paused_room` keeps its sentence because it says what sending costs, and offers no button either). The state is kept in the transcript's own `meta` (`evicted_at`, `context_lost`, `lost_from`, through `_clean_meta`, which admits those keys and nothing else) so a reload agrees with what you were just looking at rather than reporting every backgrounded conversation as merely paused, and `_stored_meta` caches it against the file's mtime because the rail asks about every row on every render.
- **The conversation about a finding can end it, and the label is the record** (`chat_session.resolution_offer` / `RESOLUTION_VERBS`, `ha_mcp_server.offer_resolutions`, `chatResolutionsNode`). Discussing a card is how you work out what to actually do about it, and the answer had nowhere to go: the strip above the composer carries the four endings EVERY finding has, while the useful answer is the specific one the conversation just reached — so agreeing at the end of a discussion meant retyping it into the reason box. Claude offers them by calling an MCP tool that **changes nothing**: the panel is already streaming that conversation, so **the call itself is the offer**, read off the stream in `_normalise`. That is why it is a tool and not a fenced block in the reply — prose is what gets reworded, a tool call is schema-validated by the CLI before it is sent, and nothing model-authored lands in the bubble where the card belongs; a call this cannot read falls through to the ordinary tool chip, so the MCP server's own refusal is on screen and Claude can correct it rather than a card rendering empty. Four rules. **The press is the consent** — nothing settles until one happens, and it goes to the same `/api/finding/{ts}/{verb}` route the tab's buttons use, because an ending that meant two different things depending on the surface is `_end_finding`'s whole reason for existing. **The label IS the note**: one string per option, so there is no second string a person cannot see before they press, which is what makes a model-written memory line acceptable at all. **No resolution touches the house** — the verbs are the three that record a decision, so the worst a mis-tap can do is settle a finding, which the toast's Undo takes back whole; `fix` is deliberately not offerable (it is the one press that sends Claude at a house, it belongs on the strip where it is pressed on purpose, and it does not end a finding anyway — it moves it to `fixing`, a different lifecycle from *dismissed*). And **the subject is the session's, never the model's** (`ChatSession.finding_ts`, set by the Discuss route after its `reset` and stamped onto the event at emit): a model retyping a timestamp can name the wrong finding, so it is not asked for one — and stamping at emit rather than resolving at render is what makes a replayed transcript still know what its buttons were about after a panel restart. Whether there is anything left to press is **derived** from the findings list on every paint, because that card comes back on a reload and by then the row may have been settled on the tab or from a phone; a `todo` resolution also sends its label as the item's `fix`, since what the conversation worked out beats what the check could say without looking. `tests/manual/measure-chatres.mjs` drives the real renderer and fails on an option that does not say where its press lands — three labels sharing one consequence included, because that is what a card looks like when it has stopped distinguishing them.
- **Ask is Claude Code's terminal, and anything in the panel can be asked about** (`terminal_ui` default `classic`, migrated by `TERMINAL_UI_VERSION`; `POST /api/terminal/open`; `askableAt`/`openAskAbout` in `app.js`). The handoff carries a first message as `prompt_b64`, and `brain-terminal-start.sh` hands it to the CLI as ONE argument (a leading `-` gets a space, so it is never a flag) beside `--append-system-prompt` read from `TERMINAL_PROMPT_FILE`, which `_write_terminal_prompt` fills with `_chat_system_prompt` — one identity for the chat and every window. Discuss on a card opens a window with the card as its first message; right-click or a 550ms hold opens a box quoting the thing pressed. `tests/test_terminal_ask.py`, `measure-askabout`.
- **Discuss opens a conversation; it never resets one** (`SessionRegistry.new(finding_ts=)`).
  - It used to `reset` the attached session. That killed a busy chat's answer and its approval card, the one loss the registry exists to prevent.
  - The subject is in the transcript's `meta` (`finding_ts`, admitted by `_clean_meta` as a positive int, restored by `_kept_meta` on resume), so a reload and a resume both still know what the buttons are about.
  - The cap is still the only 409.
- **A discussion's "do not act" is a permission rule, not a prompt sentence** (`chat_session.DISCUSS_ASK` / `_settings`).
  - A Discuss session spawns with `--settings` carrying `permissions.ask` for every tool on `ANALYST_DENIED`, except the costed reads and `offer_resolutions` (`_DISCUSS_FREE`), plus `MultiEdit`. So a change is a permission card.
  - In Claude Code an ask rule outranks an allow rule, which is what makes this hold over `settings.local.json`'s pre-approvals.
  - A CLI that refuses `--settings` falls back to `--disallowedTools` for the same list. The direction is closed: losing the rule must not mean losing the guard.
  - `_OPTIONAL_FLAGS` drops a refused flag and respawns, `--permission-prompt-tool`'s arrangement generalised.
- **A discussion names its own permission mode, and the switch decides its RULES** (`ChatSession._permission_mode` / `_discuss_rules`). **A discussion is the chat, and the switch decides whether it asks.** With *Let brAIn act without asking* off, a Discuss session spawns with `--permission-mode default` (never inheriting bypass from a `defaultMode` in `settings.local.json`) and its rules ask before every tool on `DISCUSS_ASK`; a CLI that refuses `--settings` gets that list disallowed. With it on, it spawns as the chat does (`CHAT_BYPASS`) and its rules only pre-approve (`DISCUSS_FREE_RUN`) — no ask rule, so the change somebody asks for is made in the conversation. It was "only changing Home Assistant asks" for a release, which in use meant a discussion answering *"press Plan to do that"* to somebody who had just asked for the change: the household's rule is that the chat does what it is asked, and a card's conversation is the chat. `DISCUSS_OFFER` says so in words — make the change, an approval card may appear first, a plan is an extra route and never a reason not to. The rules ride `--settings`, so a flip respawns the conversation on its next message (`_spawned_settings`). `tests/test_discuss_safety.py::TestWithTheSwitchOnADiscussionActsLikeTheChat`. A discussion's approval card offers neither "Always allow" nor "Stop asking…": a standing rule is the wrong answer inside a conversation whose contract is "ask before every change".
- **A plan is an extra route for an agreed change, never the only one** (`RESOLUTION_VERBS["plan"]`, `PLAN_AGREED`).
  - `offer_resolutions` takes `kind: "plan"`, whose label is the change said exactly.
  - The press POSTs the card's own `/api/finding/{ts}/fix` with `{change}`. `_run_plan` hands it to the read-only plan run as the agreed change, and the card waits for Apply, with Undo.
  - It is not an ending, so the finding stays on the list.
  - `_enqueue` always passes `change`, so a plain Fix it press resets it rather than inheriting last time's.
  - The tool's description offers a plan for when somebody wants to read the steps first; a change they simply asked for is made in the conversation (the bullet above).
- **Adopt prefers the handoff, and the panel keeps its own copy of it** (`chat_session.pick_adopted` / `read_handoff` / `_LAST_HANDOFF`).
  - `brain-terminal-start.sh` deletes the handoff file when it takes it up. So by the time somebody switched back, the record adopt was meant to prefer was usually gone, and "newest file" picked up whatever wrote last.
  - Ids another registry slot holds are excluded, so a conversation is never live twice.
  - Adopt goes through `registry.open`, so nothing is stopped and the mid-answer refusal is gone.
  - A round trip that the terminal carried on is re-read, but only when nothing is running on our side to lose.
- **The chat is primed twice, and both halves fail open** (`PROMPT_PROVIDER` → `--append-system-prompt`; `scripts/brain-chat-context.py` → `POST /api/chat/context`).
  - The prompt is short: identity, open cases, health, rhythm.
  - The `UserPromptSubmit` hook injects `facts_store.retrieval_block` for the message. Each fact line goes to a conversation once (`_CHAT_CONTEXT_GIVEN`, keyed by the CLI's session id, bounded), because the hook's answer stays in the conversation and `retrieval_block` leads with the core facts every time.
  - The hook is wired only in the chat's own `--settings`, and only when the script exists: a missing hook script exits 2, which blocks every prompt.
  - Every path in the script exits 0, so a panel that is down or slow is a chat that works as before.
- **A run ended on purpose is `stopped`, never a failure** (`journal.classify` / `chat_session._was_stopped`). `claude exited 143` (or `-15`) is SIGTERM, and nothing in the panel sends an engine run one — its deadline is `subprocess.run`'s timeout, which kills with SIGKILL and arrives as `TimeoutExpired`, i.e. `timeout` — so TERM is the container stopping. SIGKILL stays `crash`. The CLI closes a turn a person stopped as `error_during_execution` with `is_error` set, the same subtype a turn that broke carries; the session remembers it asked for the interrupt, and the CLI's own `terminal_reason` (`aborted_streaming`/`aborted_tools`) is the second signal, and either makes the result `stopped` and a plain "Stopped." notice. `tests/fake_claude_chat.py` answered an interrupt with `success`, which is why nothing saw it.
- **The project settings file is the terminal's and the chat's, so it pre-approves reading and two things that change nothing in the house** (`setup_claude_settings`). It is filled at boot from `engine.ANALYST_TOOLS` plus `offer_resolutions` and `Bash(brain own:*)`: the first only puts buttons on the chat's own screen, the second only hands a file back to the user that owns its folder, and an approval card in front of either is a press for nothing. The old allow-list (Bash, Write, Edit, every HA tool) moved to `/config/.brain/headless_settings.json`. `claude-run` adds that file to a `-p` run that names no `--settings` and no `--permission-prompt-tool` (the automation listener, a full-access voice worker, `brain ask`), and the fixer names it explicitly. `assist_settings.json` carries its own `mcp__home-assistant__*`, because a voice worker cannot be asked. Before this, `dangerously_skip_permissions: false` was close to a no-op and the chat's approval card could not appear.
- **A reply is answered off the drain** (`server._start_reply` / `_REPLY_TASKS` / `_settle_replies`). The request drain applies a burst of answers in order every 15 s, and it awaited a Reply's Claude run (up to `REPLY_TIMEOUT_S`). So every ending ticked after a reply waited for the whole run. The reply is a held task now, and an empty one is still refused synchronously. A reply that could not be answered or delivered is logged by the done-callback.

**The phone's microphone is Claude Code's microphone** (`panel/voice_mic.py`, `scripts/brain-arecord.py` installed as `/usr/local/bin/arecord`, the toolbar's **Talk** in `ttyd-assets/inject.html`). Claude Code's `/voice` records the machine it runs on. With no card in `/proc/asound/cards` (Docker masks it) it runs `arecord -f S16_LE -r 16000 -c 1 -t raw -q -`, probes it once against `/dev/null`, reads raw PCM from stdout and stops it with SIGTERM (read off the 2.1.307 bundle). The stand-in answers those three calls: `--version` and the probe exit 0, and a recording streams the panel's loopback-only `/api/voice/listen`. The page captures the mic, box-averages it to 16 kHz S16LE and sends it over `/api/voice/mic`, an ingress WebSocket. The hub keeps one source (a newer page replaces an older one and is told), a half-second pre-roll for the gap between the tap and arecord connecting, and whole samples only. A listener with no page waits `WAIT_FOR_SOURCE_S` and then ends with a 409 that says so, because a space pressed on a desktop keyboard must end the recording, not hang it. The page drives the CLI the way a keyboard does in voice mode's **tap** setting: one space to start, one to stop and send, because a phone cannot hold a key. Before the first recording it reads `/api/voice/state` (the CLI's own `voice`/`voiceEnabled` user settings, nested key first; unreadable is `known: false`, never "off") and types `/voice tap` when that setting is not tap, so the CLI's own checks (claude.ai sign-in, language) give their own messages. The mic and the `AudioContext` start from `click`, like Paste. `#termFrame`'s `allow` names `microphone`. A refused or insecure context is a sentence, never a silent failure. Nothing here transcribes: the words are Claude Code's. `tests/test_voice_mic.py` runs the real stand-in against the real routes. `tests/manual/measure-terminal-voice.mjs` taps Talk in Chromium with its fake microphone against `voice_harness.py`, which plays the CLI. The harness reads arecord's stdout as it arrives: a pipe left unread fills at 64 KB, two seconds of audio, which is how the first run measured audio "lost" that the CLI would have had.

**A user turn the CLI wrote is not a user turn the person wrote** (`conversations.injected_event` / `injected_events`, the `background` event). Claude Code injects `<task-notification>` (a background task finishing) and `<system-reminder>` blocks as `user` turns; the replay's list of "not typed by a person" never had the first, so 4 KB of raw XML, literal `\n` and entities rendered as right-aligned bubbles the person had supposedly sent. One classifier serves the replay, the live stream (`_normalise`) and old saved chats (`ChatSession._load` → `_reclassified`): a task notification is a collapsed "Background task finished" row with its summary as markdown, a system reminder stays hidden, and neither can title a conversation. **Opening a conversation is reading it** (`resume(spawn=False)`, `SessionRegistry.open(spawn=)`): the panel attaches the transcript with no process and the first send starts one, after `registry.room_for` so it still answers to the cap — a Claude process per conversation somebody scrolled through was a process nobody asked for. The stream never answers an error status for "no session yet": it sends an empty snapshot and `switched` once one exists.

**A shortened tool input or result says it is the SCREEN that shortened it** (`textclip.shown`, behind `chat_session._clip` and `conversations._clip`). These copies are drawn from what the CLI already holds and are never sent back to it, but a bare "… (truncated)" cut mid-word read as Claude cutting off its own context. A block (a budget of `NOTE_FROM` or more) is cut on a line break, else a word, and ends "… display truncated: 1,240 of 3,000 characters shown here — Claude has the full text."; a one-line label takes `clip`'s ellipsis. `tests/test_display_clip.py`. **And only tool traffic is shortened at all** (`conversations._speech`): the same 4,000-character cut was applied to every user turn and every reply, and a request Morph hands brAIn runs to tens of thousands of characters with the person's own words LAST, so the one sentence that was the point of the conversation was never on screen. What a person said and what Claude said back are sent whole, in the live stream and in the replay, and the panel folds a long turn behind **Show all** (`LONG_TURN`) rather than cutting it. `tests/test_conversation_words_whole.py`, `measure-ask`.

**A replayed conversation is budgeted on speech, not events.** `conversations._budget` keeps every `user`/`text`/`thinking` event first and spends what's left on the newest tool calls. A flat newest-N looks right and is badly wrong: measured on a real transcript, 92% of replay events were tool calls, so a 400-event window carried 3 of 17 user turns — which is what "switching faces loses messages" actually was. `_pair_up` keeps a call and its result together or drops both; half a pair is a spinner that never stops or an invisible event still costing a slot.

**The Terminal tab has two faces and as many live conversations as the cap allows.** `terminal_ui` (`settings_store`, default `chat`) picks between the chat renderer and ttyd; `body.term-classic` is the switch, and `#termMode` in ⋯ on BOTH faces (**Switch to terminal** / **Switch to chat**) flips it as well as ⚙'s **Chat or terminal** — the classic face hid its own switch, and ⚙ called it *Opens as*, which a search for "terminal" or "chat" never found, so a house on the terminal face could not find the way back anywhere (`measure-ask`, `measure-settings`). **The switch carries the conversation, both ways, and it is the only control that does** — a second "continue in the terminal" button beside a switch that also moves you is how you end up unsure which one actually moves you. Every route in goes through `switchTermMode`: chat→classic runs the handoff (stop our process, write `/data/terminal-handoff.json`, open a tmux window on `--resume`), classic→chat calls `/api/chat/adopt`. Adopt exists because the tmux Claude is not ours and has no API — but Claude Code writes its transcript as it goes, so **the most recently written conversation in the project directory is what the terminal was last doing**, and that is what gets resumed. It is a hand-off, not a mirror: one process owns a conversation at a time — which is a fact about the CLI, and is *not* the reason the chat used to hold only one session. The terminal's shell is never killed to make the switch work — it is somebody's shell — and adopt is refused mid-answer, because losing an answer being written is worse than waiting for it. Chat drives the *same* Claude Code — `chat_session.py` runs a long-lived `claude -p --input-format stream-json --output-format stream-json` in `/config`, so it inherits the same `settings.local.json` the terminal reads: the pre-approvals that file has held since 2.11 (reading Home Assistant, `offer_resolutions` and `brain own`), with *Let brAIn act without asking* deciding whether the rest is asked about. The automation listener and the fixer use `/config/.brain/headless_settings.json` instead, and a voice worker its own `assist_settings.json` (the headless file at full access). **There is one process per open conversation and a view attached to one of them** (`SessionRegistry`; `session()` still means the attached one, so every caller that knows about one conversation kept working). It was a module singleton, so switching was `stop()` + `--resume` and `resume()`/`set_model()` refused mid-answer with a 409 saying Claude was still responding — honest for one process, and the wrong shape for the question, because native Claude Code is one process per terminal tab and that is precisely what was being asked for. **`attach` stops nothing**: it changes which session the stream serves and which one `send` goes to, and the one left behind carries on answering into its own transcript and its own subscribers. **The cap is on live PROCESSES, not conversations** (`chat_max_sessions`, a `settings_store` key rather than a `config.yaml` option because it is changed while looking at the chat; 3, clamped 1–8) — a conversation with no process is a transcript and an id the CLI can resume, so what the cap governs is memory on a Pi. **Eviction takes the least recently active IDLE session and never a busy one**, because an answer surviving you looking elsewhere is the entire point and an LRU that could take the busy one would break the thing it exists to protect; the evicted session keeps its transcript, keeps its registry row and gets a `notice` saying why, so switching back is instant and explains the gap rather than reading as a crash. With every live session busy there is nothing to take, and **that is the one 409 left** — about the cap, naming the count and the setting, never about an answer you can still watch being written. `ChatSession.resume` keeps its own mid-answer refusal because it is still the destructive path (stop, clear, replay) and the registry never uses it for a switch; `set_model` keeps its because the model is an argv flag and applying it is a restart, and its sentence now says which conversation is busy and offers switching. `open()` on a session we already hold is an attach and a `start()`, never a replay — replaying over it would wipe the notice that explains the gap. `_on_change`/`_on_ask` are the two hooks the registry installs, so the rail's marks are **pushed** (`sessions` on the attached stream) rather than polled, and a `can_use_tool` in a background conversation raises a toast on the attached view as well as a badge on its row — the card declines itself after `PERMISSION_TIMEOUT`, and there is no rail at all on a phone. `attach` emits `switched` on the OLD stream and the panel reconnects through the path it already has for a dropped one, so the first frame is the new snapshot and the stream's contract is unchanged. `/api/diagnostics` carries the registry, because a session the cap stopped and one that crashed leave the same silence. **Everything that knows the CLI's wire shape lives in `_normalise`**; the panel only ever sees `text`/`text_delta`/`thinking`/`tool`/`tool_result`/`notice`/`result`/`state`, and an unrecognised event is dropped rather than rendered raw. Deltas and run stats carry `_keep: False` because the `assistant` event that follows repeats the same text whole — keeping both doubles every answer on the next reload. The transcript is *ours* — **one file per conversation** (`/data/chat/<session id>.json`, `BRAIN_CHAT_TRANSCRIPT_DIR`, capped in events and in files); a single file was the shape of a single session, and two live ones writing it would each hold half a scrollback. Claude Code owns the real conversation and resumes it by `session_id`, so losing the file costs a scrollback and never context. The old single file is migrated **once**, guarded by the directory's own existence — creating it *is* the migration — so an upgrade does not blank the pane somebody was reading, and `config.yaml`'s `backup_exclude` names the directory as well as the old file. A session the CLI has not named yet is **not persisted at all** rather than parked under a temp name and renamed on `init`: every transcript worth keeping already has an id by the time it has anything in it (`resume` sets it before it replays; a live process announces its own inside its first event), and the one thing that can exist without one is a failed spawn's notice, which the next attempt writes again. A session id becomes a filename and arrives off the wire, so `transcript_path` refuses anything `safe_id` rejects **and** anything that does not normalise to a path under the transcript directory — deliberately redundant, and only the first is reachable by mutation; the second is the same rule written where it can be followed from the `open()` at the end of it, spelled with `os.path.normpath` and a string prefix because that is the form a static analyser reads as a barrier (a `Path`-parts comparison is correct and is not one), and a guard nothing can see is a guard somebody deletes. Stopping asks with a `control_request` and kills-then-`--resume`s if nothing answers within `INTERRUPT_GRACE` — an older CLI ignores the request silently, which is indistinguishable from thinking. One SSE stream per viewer, opened only while the tab is in front; the first frame is the snapshot, so no client has to stitch "what it was" onto "what happened next". **A spawn is watched until the CLI says its first word** (`START_GRACE`): a process that dies before speaking with `--resume` on its argv means the CLI no longer holds that conversation — the store prunes old sessions — and the old behaviour was a chat that spawned, died silently, and errored on every send, while the restored resume id respawned the same failure forever. The id is dropped, a notice says the context is gone (the replayed transcript stays), and the session opens fresh; `resume()` returns `resumed: false` so the panel can say so out loud rather than letting the next answer reveal it. Died-before-speaking with nothing to resume is an error state carrying the stderr tail. **The chat picks its own model** (`chat_model`, a panel setting; `POST /api/chat/model`): the picker opens from the model name in the meta line and from ⋯ → Model, offers the same `MODEL_CHOICES` ⚙ does (its empty-id "CLI default" row filtered out — in the chat, "" means "follow ⚙ Settings" and a Default row already says that), and never touches the global `model` option, which would silently change what every insight run costs. Applying it is a stop and a `--resume` — the model is an argv flag — refused mid-answer. **Every "is a restart needed" question is asked of `_spawned_model`, never `session.model`**: the server refreshes `session.model` from settings on every request, so intent routinely agrees with a pick the live process has never seen — which is how the picker answered "already that model" about a session still running the old one, forever, because a long-lived process never respawns on its own. `send()` runs the same comparison, so a ⚙ edit lands on the next message; and `--model` stays on a `--resume` argv on purpose, because a resumed session otherwise keeps the model it remembers. **`set_model`'s response carries `model_label`**, because the event that refreshes the meta line (`init` → `info`) does not arrive until the next message — a restarted `--resume` process says nothing until spoken to — and the meta line is the only confirmation a pick landed, so waiting for it is how the picker looked like it did nothing. **`error_max_turns` marks `_respawn_pending`** and the next send restarts with `--resume`: the cap is a per-process runaway guard, and a guard that refuses has to change the next attempt — "start a new chat to carry on" was charging the person's conversation for it. **`thinking_delta` streams like `text_delta`** (live-only, sealed by the assistant event's whole block): the panel keeps a FIFO of streamed think boxes and the final block replaces the streamed copy in place, because the block only arrives when the message closes, and retro-inserting reasoning after its conclusion is what "the chat doesn't show thinking" actually was. The three dots are a status line now — verb, current tool, elapsed seconds — for the whole turn, not just until the first token. **Chat sessions can never appear in the Claude app** ("connected" is Remote Control, which requires an interactive session — anthropics/claude-code#30447): not brAIn's to fix, so the session popover and the docs say it out loud and point at the face switch, which moves the same conversation into a terminal session that can register. **Deleting a conversation is a move, not an unlink** (`conversations.delete` → `/data/chat-trash`, TTL'd and capped): a row's ⋯ › **Delete** hands back an `undo_store` token and the toast's Undo moves the file back, refusing over an occupied path. **Any** conversation the registry holds is refused server-side ("close it first", `POST /api/chat/session/{id}/close`) — and closing the one **on screen** has to satisfy that refusal, which it did not: `close` removed a background session from the listing and left the attached one in it, stopped but still held, so the delete answered with the same sentence the person had just obeyed. It detaches now; the view lands on a fresh conversation that has spawned nothing and the old stream is told `switched`, which is the path the panel already has — deleting the ground a live session stands on either kills it or quietly forks it, and now that several may be live "the one on screen" is no longer the same question as "the ones in use". Delete offers the close rather than leaving a refusal nothing can satisfy, and asks first, because closing one mid-answer loses what it was writing. This is the one mutation `conversations.py` makes in the CLI's store, and it never edits file contents. **Batch delete is the same move, per row, with one token** (`/api/chat/conversations/delete`, undo kind `conversations`): a conversation with a live session is *skipped and reported*, not a reason to fail the batch — a select-all that refuses outright teaches people to deselect one row by trial and error — and the batch is capped at `TRASH_MAX`, because accepting more than the trash holds would make the oldest of the batch unrestorable while the toast still offers to restore it. The panel's selection mode and the ⋯ conversations dialog were cut in the redesign (one list, one ⋯ per row); the batch route stays for whoever needs it. **The meta line under the composer is measured, not assumed visible**: `#viewTerminal`'s negative margins cancel `.wrap`'s padding, so they follow the breakpoint the *padding* changes at (640px), and the bottom margin is 0 — `body.term-open` has already zeroed the wrap's bottom padding, and a leftover negative margin shortens `.wrap`, whose `overflow: hidden` clipped the last ~20px of the view: the model-and-context line, half-swallowed at every width and worst on a wide screen. Geometry can't see it (`getBoundingClientRect` was right; the paint wasn't), so `tests/manual/measure-chatmeta.mjs` checks with `elementFromPoint`. Its second pass drives the real list behind a stubbed fetch at 1200 and 390 (the rail beside the transcript, and the page Ask opens on below 900px) and fails on a missing mark, a hidden one, one that hangs off the list, a row under the touch floor, or a page that scrolls sideways.

**Ask is your conversations, and a reply's working is one line** (`chatStepsFold` / `chatOfferReport` / `askShow` / `server._discussion_row`). The redesign's Ask rows, each for the reason the walkthrough gave. **The list opens on yours, and the machines' are a pill away** (`renderConvKinds` / `pickConvSource`): the redesign moved the run-type chips into ⚙ › Diagnostics › Runs on the argument that they made the list of your conversations the place to audit the machines, and in use that buried them three presses deep — so they are back over the list, `pillseg` pills off the route's own `sources` (Chats, then every face that has run here, each with its count), the default `you`, the pick remembered (`brain.ask.source`) and dropped back to `you` when that kind no longer has runs. The heading names the kind and its blurb sits under the pills. The approval card, the question card and the resolutions card are appended to the log and never into a fold — the CLI is blocked on the first two, and a decision folded away is one nobody makes. **"Save as report"** sits on a reply's LAST answer (so never on a "let me look" preamble) and posts the reply's question to `api/generate` with `report: true`, which `h_generate` takes straight to a card job — not `_interpret`, not the ask bar's patterns, so a question opening "when" or "learn" cannot become a rule or a study because somebody pressed Save; a discussion's opener and a slash command offer none. **A discussion is titled by its card**: `_discussion_row` strips `DISCUSS_PROMPT`'s "Discussing: " and adds `finding_ts`, read off the conversation's kept meta (`SessionRegistry.finding_of`) and never parsed from the title, so a person who types the word links nowhere; the snapshot carries `finding_ts` too, so the strip above the composer follows the conversation on screen (it used to follow `localStorage`), shows the card's title as the link back to it on Today, and carries the card verbs Fix · Done · Snooze · Ignore. **The context pill measures the conversation, not the work.** Its numerator is one model call's `usage`, taken off the `assistant` event — never the `result` envelope, whose `usage` is the whole turn added up. A turn is many calls and each one re-sends the conversation, so summing them measured how hard Claude worked and reported a ten-tool turn as ten conversations. Its denominator comes from the model's **version**, not its family: the table used to say 200K for every Opus and every Sonnet, which was true when it was written and is wrong for every model the add-on now runs — both went to 1M at 4.6, Haiku stayed at 200K. The two failures multiplied, and the pill routinely claimed several hundred percent of a window five times too small. A model whose version cannot be parsed reports its token count and no percentage: the candidate answers are 5× apart, and a percentage of a guessed denominator is worse than none. `BRAIN_CONTEXT_WINDOW` is the escape hatch for a model that ships before the table learns about it. **The denominator is re-derived the moment the model changes** (`_rewindow`, off the `init` event), not on the next turn: `--resume` carries the conversation, so the token count survives a pick and the window does not belong to it — moving to Haiku left 42k being divided by 1M and reported as 4% of a window it fills 21% of, and it stayed wrong until something else happened to refresh it.

**A model id is turned into a name in exactly one place, and it is the server** (`chat_session.pretty_model`, on the same version parser the window uses; shipped as `info.model_label` and `default_model_label`). The panel had a second regex for it and the two drifted the way a second copy always does: it read `claude-haiku-4-5` as "Claude Haiku 4" and took the leading digits of a date stamp for a version, so `claude-3-5-sonnet-20241022` came out "Claude Sonnet 2". The minor version is the whole point — every 4.x model of a family printed the same name, and **the label under the composer is the only confirmation a pick landed**, so a working selector was indistinguishable from one that did nothing. A tier alias (`opus`) prints no version, because the account resolves it; an unreadable id prints itself, because a made-up name for a model we cannot read is worse than the id. **The picker's Default row names the global model, so ⚙ has to hand it back** — `/api/settings` returns `model_label` and `saveSettings` refreshes `chatState.defaultModel`. ⚙ is reachable from the Terminal tab and the stream's opening snapshot is not reopened by it, so that row — the *highlighted* one whenever no override is set — went on naming the model you had just replaced.

**Two things float over the terminal, and no more.** `#termMenu` (⋯) and `#termExpand` (⤢) — everything else is a menu item in `#termMenuPop`, whose buttons are static markup carrying the ids their handlers are bound to (rebuilding a menu's controls on open drops every listener). ⤢ is alone because it is also the way back from a folded bar. Five translucent squares stacked over someone's output was the clutter the chat view exists to avoid.

**The terminal folds the bar away.** `body.term-immersive` hides `.topbar` and zeroes `--bar-h`; `body.term-kb` marks the automatic case. Two independent reasons, tracked separately in `termChrome` so neither clobbers the other: ⤢ (`#termExpand`, remembered in `localStorage`) and the software keyboard being up right now. Only the ttyd frame can detect that keyboard — iOS does not resize an iframe's visual viewport, and `inject.html` already does the measuring for its own toolbar — so it posts `{type: "brain-keyboard"}` up and the panel accepts it only from `#termFrame.contentWindow`. tmux drops its status line under 90 columns via `client-attached`/`client-resized` hooks; the width test is a shell `[` because tmux does not expand a nested `#{client_width}` inside its own `#{<:a,b}`, which silently answers "narrower" at every width.

**On a phone the classic terminal's input is the injected script's, and its three failures were all silent** (`ttyd-assets/inject.html`, `tests/manual/measure-terminal-mobile.mjs`). **Paste reads the clipboard on `click`, never `pointerdown`**: for a finger a pointerdown is not an activation-triggering event (HTML lists pointerup, touchend and click), so `readText()` was refused on phones and the refusal went into an empty catch — "I can't paste". A refused or absent read opens a real, visible, 16px text box you can long-press Paste into, because the body is `touch-action: none` and xterm's input is an off-screen textarea iOS offers no Paste bubble on, so without it there is no other route. **Pasted text goes through xterm's own paste** — `window.term.paste` (ttyd publishes it), then a synthetic `paste` event xterm cancels when it takes it, then a hand-built bracketed paste as the floor (safe because tmux is always in front and forwards the markers only to a pane that asked) — never straight down the socket, where every newline was an Enter and a two-line paste submitted its first line. **The dictation diff is taken against the TEXTAREA, not against what the handler last sent**: ordinary typing moves the box through xterm without telling the handler, so the next keydown-less input (autocorrect, a predictive tap, swipe typing) diffed against a stale baseline and re-sent the word (`teh` → `tehthe`); `lastValue` is re-read a tick after every keydown and every input it leaves alone, and only text-editing input types are diffed — a paste is xterm's. **The keyboard is one resize, not one per sample**: the toolbar's transform moves on every visualViewport sample (it costs nothing) while `syncHeight` and the report to the panel are committed together once the samples have settled (`SETTLE_MS`), because each height change is an xterm refit, a PTY resize and a full tmux + Claude Code redraw. **An unfocused frame's height is its baseline, down as well as up** (`captureBaseline`): the panel folding its bar makes the frame taller, grow-only kept that as the baseline, and on a WebView that resizes for the keyboard the unfolded frame then read as "shrank for a keyboard", folded the bar, grew, unfolded — the old script flapped the bar ~45 times in a second after one keyboard close. **A toolbar tap refocuses the terminal only if it was focused**, and asks again on `click` because the blur can land after pointerdown; refocusing unconditionally opened a keyboard somebody had put away. `#termFrame` carries `allow="clipboard-read; clipboard-write"`, which is necessary and not sufficient: HA's own ingress frame is above it and not ours.

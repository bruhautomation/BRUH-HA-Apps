# brAIn: Ask (the chat and the terminal)

The chat's sessions and registry, permissions and approval cards, discussions, adopt/handoff, replay budgets, the model picker and context pill, the terminal's mobile input and voice mic.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

What each rule cost to learn is in `docs/notes/history/chat-terminal.md`.

## Two faces and the switch

- **The Terminal tab has two faces and as many live conversations as you open.** `terminal_ui` (`settings_store`, default `classic` since 4.0) picks between the chat renderer and ttyd; `body.term-classic` is the switch, and `#termMode` in ⋯ on BOTH faces (**Switch to terminal** / **Switch to chat**) flips it as well as ⚙'s **Chat or terminal**, so a house on either face can find the way back (`measure-ask`, `measure-settings`).
- **Ask is Claude Code's terminal, and anything in the panel can be asked about** (`terminal_ui` default `classic`, migrated by `TERMINAL_UI_VERSION`; `POST /api/terminal/open`; `askableAt`/`openAskAbout` in `app.js`).
  - The handoff carries a first message as `prompt_b64`, and `brain-terminal-start.sh` hands it to the CLI as ONE argument (a leading `-` gets a space, so it is never a flag) beside `--append-system-prompt` read from `TERMINAL_PROMPT_FILE`, which `_write_terminal_prompt` fills with `_chat_system_prompt` — one identity for the chat and every window.
  - Discuss on a card opens a window with the card as its first message; right-click or a 550ms hold opens a box quoting the thing pressed (`measure-askabout`).
- **Ask follows the SAVED face, one rule for every ask-about** (`POST /api/ask` → `server.h_ask` / `_ask_in_chat`; `askAbout` in `app.js`). A report's Ask, the press-and-hold box, Personality's and Instructions' Ask, and Discuss all go through it.
  - The server reads the saved `terminal_ui`: on the chat face it opens a NEW chat conversation (the asking viewer's own empty one reused) and sends the prompt, answering with the conversation's key; on the classic face it opens a terminal window.
  - Never flip the face locally without saving it: the next status refresh (`syncTermMode`) puts the saved face back and leaves the question running where nobody is looking.
  - The Ask button is held while its POST is in flight, so a double tap is one conversation. `measure-askabout` reproduces the flip and the double tap.
- **The switch carries the conversation, both ways, and it is the only control that does** — a second "continue in the terminal" button beside a switch that also moves you is how you end up unsure which one actually moves you.
  - Every route in goes through `switchTermMode`: chat→classic runs the handoff (stop our process, write that request's own `terminal-handoff-<nonce>.json`, open a tmux window on `--resume` handed its path), classic→chat calls `/api/chat/adopt`.
  - Adopt exists because the tmux Claude is not ours and has no API — but Claude Code writes its transcript as it goes, so **the most recently written conversation in the project directory is what the terminal was last doing**, and that is what gets resumed.
  - It is a hand-off, not a mirror: one process owns a conversation at a time — which is a fact about the CLI, and is *not* a reason for the chat to hold only one session.
  - The terminal's shell is never killed to make the switch work — it is somebody's shell.
- **Adopt prefers the handoff, and the panel keeps its own copy of it** (`chat_session.pick_adopted` / `read_handoff` / `_LAST_HANDOFF`).
  - `brain-terminal-start.sh` deletes the handoff file when it takes it up, so the panel's own copy is the record; "newest file" alone picks up whatever wrote last.
  - Ids another registry slot holds are excluded, so a conversation is never live twice.
  - Adopt goes through `registry.open`, so nothing is stopped and there is no mid-answer refusal.
  - A round trip that the terminal carried on is re-read, but only when nothing is running on our side to lose.
- **Chat sessions can never appear in the Claude app** ("connected" is Remote Control, which requires an interactive session — anthropics/claude-code#30447): not brAIn's to fix, so the session popover and the docs say it out loud and point at the face switch, which moves the same conversation into a terminal session that can register.

## One Claude Code, launched the same way

- **The chat and the terminal are one Claude Code, launched the same way** (`server._terminal_settings` / `TERMINAL_SETTINGS_FILE`, `brain-terminal-start.sh`).
  - The chat is `chat_session.py` running a long-lived `claude -p --input-format stream-json --output-format stream-json` in `/config`, so it reads the same project settings the terminal does.
  - `_write_terminal_prompt` writes, beside the appended prompt, `/data/brain-terminal-settings.json`: `conversation_settings()` (the hook), `permissions.deny` = `PLATFORM_DENIED`, and `model` = `eff_chat_model()`. `brain-terminal-start` passes its contents as `--settings` only when it parses (a CLI handed settings it cannot read refuses to start). It is rewritten wherever the prompt is, and on a model pick (`h_chat_model`).
  - The session picker (auto-launch off) starts its sessions through `brain-terminal-start --no-handoff`, so it is the terminal too.
  - What is the same, field by field: the appended prompt (`_chat_system_prompt`: identity, development/YOLO mode, personality, the house as of the start), `/config/CLAUDE.md` and the project settings (both stand in `/config`: the MCP server from `.mcp.json`, its pre-approval, the read-only allow-list, the platform deny-list, the PreToolUse edit snapshot, action gate and protect hook, the memory extractor's Stop hook), the per-message facts hook, the model (the chat's picker decides both), the permission switch (bypass in both when on: `--permission-mode bypassPermissions` + `--disallowedTools` in the chat, `--dangerously-skip-permissions` + the settings deny in the terminal; asking in both when off), the conversation store (one `~/.claude/projects/-config/`, so the Chats rail and `--resume` list both faces' conversations), and an ask-about (`h_ask` hands the same prompt and context to either face).
  - Discuss on the terminal is told to make a change it is asked for (`DISCUSS_ACT_TERMINAL`), as the chat is.
- **What still differs, and why it cannot not** (the terminal is Claude Code's own TUI on a tty; the panel neither renders it nor reads its stream):
  - **How a permission is asked.** The chat turns the CLI's question into an approval card (`--permission-prompt-tool stdio`), with "Always allow" kept to the add-on's own destinations; the terminal asks in Claude Code's own prompt, with its own "don't ask again" choices. The same rules decide *whether* it asks.
  - **A discussion's ask rules and buttons.** A chat Discuss carries `DISCUSS_ASK` (or `DISCUSS_FREE_RUN` with the switch on) in its `--settings` and is told to end with `offer_resolutions` and may offer a `plan`; the terminal's Discuss window carries neither, because there is nothing to draw the buttons on, and with the switch off every acting tool already asks there (the project allow-list is read-only), so the rules would add nothing.
  - **A switch flip or a model pick mid-conversation.** The chat respawns an idle conversation on its next message (`_spawned_mode`, `_spawned_model`); a terminal session keeps what it started with until it ends (the `permission_sessions` line in ⚙ says so), and `/model` changes it there.
  - **The run journal.** Each chat turn is a `chat` row (`journal.record` off the stream's `result`); a terminal turn has no row, because the panel never sees its result. Both are in the account's usage figures, which are the ones that count against limits.
  - **The picker's Custom command and background task** stay the person's own `claude-run`: a command somebody typed is run as typed, and a background `-p` task is a headless run.
- **The project settings file is the terminal's and the chat's, so it pre-approves reading and two things that change nothing in the house** (`setup_claude_settings`).
  - It is filled at boot from `engine.ANALYST_TOOLS` plus `offer_resolutions` and `Bash(brain own:*)`: the first only puts buttons on the chat's own screen, the second only hands a file back to the user that owns its folder, and an approval card in front of either is a press for nothing. *Let brAIn act without asking* decides whether the rest is asked about.
  - The broad allow-list (Bash, Write, Edit, every HA tool) is `/config/.brain/headless_settings.json`. `claude-run` adds that file to a `-p` run that names no `--settings` and no `--permission-prompt-tool` (the automation listener, a full-access voice worker, `brain ask`), and the fixer names it explicitly.
  - `assist_settings.json` carries its own `mcp__home-assistant__*`, because a voice worker cannot be asked.
- **The chat is primed twice, and both halves fail open** (`PROMPT_PROVIDER` → `--append-system-prompt`; `scripts/brain-chat-context.py` → `POST /api/chat/context`).
  - The prompt is short: identity, open cases, health, rhythm.
  - The `UserPromptSubmit` hook injects `facts_store.retrieval_block` for the message. Each fact line goes to a conversation once (`_CHAT_CONTEXT_GIVEN`, keyed by the CLI's session id, bounded), because the hook's answer stays in the conversation and `retrieval_block` leads with the core facts every time.
  - The hook is defined once (`chat_session.conversation_settings`) and is in both faces' own settings — never the project file, which voice and the listeners read too — and only when the script exists: a missing hook script exits 2, which blocks every prompt.
  - Every path in the script exits 0, so a panel that is down or slow is a chat (or a terminal) that works as before. The CLI's ceiling is `CONTEXT_HOOK_TIMEOUT` and the script's own budget is 2 s, on both faces.
- **A new conversation is told what brAIn said lately without being asked** (`server._chat_said_lines` in `_chat_system_prompt`, `presence.said_lately` / `chat_said_block`).
  - The appended prompt carries the newest five of: the morning brief's and the weekly report's opening sentence, each notification whose words the dispatcher wrote, and its touches (to whom, by first name, only for a touch), each with a dated stamp (never "today": the terminal's copy is a file written when a window is opened or a setting saved) and how it was answered where the ledger knows, inside `CHAT_SAID_BYTES`.
  - The same reader ⚙ › Personality's feedback rows use. A source that cannot be read is lines left out, nothing said is no block, and the terminal gets it because it shares the prompt.
- **A conversation records how the household wants brAIn to be with `brain tune "<asked>" "<answered>"`** (`scripts/brain-tune.sh` → `POST /api/presence/tuning`, source `ask`), the CLI rather than an MCP tool: the panel owns the store, and the usage text in `brain help` is the announcement.

## Sessions and the registry

- **There is one process per open conversation and a view attached to one of them** (`SessionRegistry`; `session()` still means the attached one, so every caller that knows about one conversation kept working). Native Claude Code is one process per terminal tab, and that is the shape.
- **`attach` stops nothing**: it changes which session the stream serves and which one `send` goes to, and the one left behind carries on answering into its own transcript and its own subscribers.
  - `attach` emits `switched` on the OLD stream and the panel reconnects through the path it already has for a dropped one, so the first frame is the new snapshot and the stream's contract is unchanged.
  - `_on_change`/`_on_ask` are the two hooks the registry installs, so the rail's marks are **pushed** (`sessions` on the attached stream) rather than polled, and a `can_use_tool` in a background conversation raises a toast on the attached view as well as a badge on its row — the card declines itself after `PERMISSION_TIMEOUT`, and there is no rail at all on a phone.
  - `/api/diagnostics` carries the registry, because a session the cap stopped and one that crashed leave the same silence.
- **Each viewer's conversation is its own** (`ChatSession.key`, `SessionRegistry.by_key` / `hold`, `server._chat_for`; `chatWho` / `chatReconnect` in `app.js`).
  - The panel names its own conversation on every call — `send`, `stop`, the model picker and the approval answer — as `session_key` (the session object's handle, which a fresh chat has before the CLI names it) and `session_id`, and the server routes to that one. Nothing a viewer does may land in `registry.attached()` because another device moved it.
  - A named conversation the registry is not holding (a restart, a trim) is held again to be read (`hold`: transcript, no process, **never attached**, so no other view moves) and the send starts it through `room_for`. A name that matches nothing is a 404, never quietly another conversation. A caller that names nothing (an older panel, a CLI) keeps the old meaning.
  - The stream takes the same names as query parameters; a named stream drops `switched` (another device's doing), and the panel moves itself by reconnecting with the key its own POST answered with. `sessions` and `session_asks` go to every session somebody's stream is on, not only the attached one.
- **Opening a conversation is reading it** (`resume(spawn=False)`, `SessionRegistry.open(spawn=)`): the panel attaches the transcript with no process and the first send starts one, after `registry.room_for` so it still answers to the cap — a Claude process per conversation somebody scrolled through was a process nobody asked for. The stream never answers an error status for "no session yet": it sends an empty snapshot and `switched` once one exists.
- **No request waits out a spawn** (`server._send_promptly`, `SEND_HOLD_S`). A send, an Ask and a Discuss that have to start a process run it as a task, because `START_GRACE` per spawn attempt is long enough for a proxy in front of ingress to give up. Done within `SEND_HOLD_S` (3 s), its own answer or refusal is the response; otherwise the response is `{accepted, pending, key}` and the user turn, the state and any failure arrive on the stream — a failure as `send_failed` carrying the words, which the composer puts back. Discuss and Ask open their conversation with `new(spawn=False)` for the same reason.
- **There is no cap unless a person sets one, and memory is what puts a conversation to sleep** (`chat_max_sessions`, a `settings_store` key rather than a `config.yaml` option because it is changed while looking at the chat; `None` = no limit, the default, or 1–32).
  - Every conversation can run at once, so nothing is refused or queued for lack of a slot.
  - What keeps a Pi safe is `MEM_FLOOR_MB` (600, `BRAIN_CHAT_MEM_FLOOR_MB`): before a process starts, with `/proc/meminfo`'s MemAvailable under it, the least recently active IDLE conversations are put to sleep (the same eviction, reopened with `--resume`) until it is back above, each logged; with nothing idle the new one starts anyway and the log says memory is short. A number a person sets still applies.
  - A conversation with no process is a transcript and an id the CLI can resume.
- **A stored 3 from before is reset to no limit, once** (`settings_store.CHAT_SESSIONS_VERSION`, the `terminal_ui_v` pattern): a 3 stored without `chat_max_sessions_v` reads as no limit, because every settings save wrote the effective values back and an older install holds it whether or not anybody chose it. The next save records the version, so a 3 somebody picks after that is kept, and any other old number was a choice and is kept as it is.
- **Eviction takes the least recently active IDLE session and never a busy one**, because an answer surviving you looking elsewhere is the entire point and an LRU that could take the busy one would break the thing it exists to protect.
  - The evicted session keeps its transcript, keeps its registry row and gets a `notice` saying why, so switching back is instant and explains the gap rather than reading as a crash.
  - With every live session busy at a person's cap there is nothing to take, and **that is the one 409 left** — about the cap, naming the count and the setting, never about an answer you can still watch being written.
  - `ChatSession.resume` keeps its own mid-answer refusal because it is still the destructive path (stop, clear, replay) and the registry never uses it for a switch; `set_model` keeps its because the model is an argv flag and applying it is a restart, and its sentence says which conversation is busy and offers switching.
  - `open()` on a session we already hold is an attach and a `start()`, never a replay — replaying over it would wipe the notice that explains the gap.
- **A spawn is watched until the CLI says its first word** (`START_GRACE`): a process that dies before speaking with `--resume` on its argv means the CLI no longer holds that conversation (the store prunes old sessions). The id is dropped, a notice says the context is gone (the replayed transcript stays), and the session opens fresh; `resume()` returns `resumed: false` so the panel can say so out loud rather than letting the next answer reveal it. Died-before-speaking with nothing to resume is an error state carrying the stderr tail.
- **`error_max_turns` marks `_respawn_pending`** and the next send restarts with `--resume`: the cap is a per-process runaway guard, and a guard that refuses has to change the next attempt — "start a new chat to carry on" would charge the person's conversation for it.
- Stopping asks with a `control_request` and kills-then-`--resume`s if nothing answers within `INTERRUPT_GRACE` — an older CLI ignores the request silently, which is indistinguishable from thinking.
- **A run ended on purpose is `stopped`, never a failure** (`journal.classify` / `chat_session._was_stopped`).
  - `claude exited 143` (or `-15`) is SIGTERM, and nothing in the panel sends an engine run one — its deadline is `subprocess.run`'s timeout, which kills with SIGKILL and arrives as `TimeoutExpired`, i.e. `timeout` — so TERM is the container stopping. SIGKILL stays `crash`.
  - The CLI closes a turn a person stopped as `error_during_execution` with `is_error` set, the same subtype a turn that broke carries; the session remembers it asked for the interrupt, and the CLI's own `terminal_reason` (`aborted_streaming`/`aborted_tools`) is the second signal, and either makes the result `stopped` and a plain "Stopped." notice.
- **A viewer that hangs up is a cancel, not a crash** (`h_chat_stream`, `crash_middleware`). A phone locking or a tab closing ends the stream with a reset, a broken pipe or aiohttp's "Connection lost"; all are `ConnectionError`, caught around `prepare` and the loop, and the middleware answers any such error from a closed caller connection quietly (499, one info line) with no journal row. Only the stream's own queue is dropped: the session and transcript stay, so a reconnect gets the snapshot.
- **The chat's row states are seven words and ONE derivation** (`chat_session.ROW_STATES` / `SessionRegistry.state_of`). A paused conversation, one the cap stopped to make room, and one whose context the CLI has dropped are three different things a person has to do three different things about.
  - So there is a closed vocabulary — `live`, `answering`, `needs_ok`, `paused`, `paused_room`, `context_lost`, `record` — each with a label and a hint, and one function that decides which, for a held session and for a bare `meta` alike, so a row and the composer above it can never disagree.
  - **The order is the argument**: a `record` is a record whatever else is true; `context_lost` outranks a live process on purpose, because the process is fresh and the transcript on screen is not its, and that is the one thing worth saying until the next message makes them agree; everything else is only reachable off a process.
  - `paused` deliberately renders **no pill and no composer line** — a conversation with no process is the ordinary case and is not news, and sending is what resumes it. `paused_room` keeps its sentence because it says what sending costs, and offers no button either.
  - The state is kept in the transcript's own `meta` (`evicted_at`, `context_lost`, `lost_from`, through `_clean_meta`, which admits those keys and nothing else) so a reload agrees with what you were just looking at rather than reporting every backgrounded conversation as merely paused, and `_stored_meta` caches it against the file's mtime because the rail asks about every row on every render.
- **A reply is answered off the drain** (`server._start_reply` / `_REPLY_TASKS` / `_settle_replies`). The request drain applies a burst of answers in order every 15 s, so a Reply's Claude run (up to `REPLY_TIMEOUT_S`) is a held task, never awaited there; an empty one is still refused synchronously. A reply that could not be answered or delivered is logged by the done-callback.

## The stream and the transcript

- **Everything that knows the CLI's wire shape lives in `_normalise`**; the panel only ever sees `text`/`text_delta`/`thinking`/`tool`/`tool_result`/`notice`/`result`/`state`, and an unrecognised event is dropped rather than rendered raw. Deltas and run stats carry `_keep: False` because the `assistant` event that follows repeats the same text whole — keeping both doubles every answer on the next reload.
  - One SSE stream per viewer, opened only while the tab is in front; the first frame is the snapshot, so no client has to stitch "what it was" onto "what happened next".
- **`thinking_delta` streams like `text_delta`** (live-only, sealed by the assistant event's whole block): the panel keeps a FIFO of streamed think boxes and the final block replaces the streamed copy in place, because the block only arrives when the message closes. The three dots are a status line — verb, current tool, elapsed seconds — for the whole turn, not just until the first token.
- **A user turn the CLI wrote is not a user turn the person wrote** (`conversations.injected_event` / `injected_events`, the `background` event). Claude Code injects `<task-notification>` (a background task finishing) and `<system-reminder>` blocks as `user` turns. One classifier serves the replay, the live stream (`_normalise`) and old saved chats (`ChatSession._load` → `_reclassified`): a task notification is a collapsed "Background task finished" row with its summary as markdown, a system reminder stays hidden, and neither can title a conversation.
- **A shortened tool input or result says it is the SCREEN that shortened it** (`textclip.shown`, behind `chat_session._clip` and `conversations._clip`). These copies are drawn from what the CLI already holds and are never sent back to it, and a bare "… (truncated)" cut mid-word reads as Claude cutting off its own context. A block (a budget of `NOTE_FROM` or more) is cut on a line break, else a word, and ends "… display truncated: 1,240 of 3,000 characters shown here — Claude has the full text."; a one-line label takes `clip`'s ellipsis.
- **And only tool traffic is shortened at all** (`conversations._speech`): a request Morph hands brAIn runs to tens of thousands of characters with the person's own words LAST. What a person said and what Claude said back are sent whole, in the live stream and in the replay, and the panel folds a long turn behind **Show all** (`LONG_TURN`) rather than cutting it (`measure-ask`).
- **A replayed conversation is budgeted on speech, not events.** `conversations._budget` keeps every `user`/`text`/`thinking` event first and spends what's left on the newest tool calls; a flat newest-N is mostly tool calls and drops user turns. `_pair_up` keeps a call and its result together or drops both; half a pair is a spinner that never stops or an invisible event still costing a slot.
- The transcript is *ours* — **one file per conversation** (`/data/chat/<session id>.json`, `BRAIN_CHAT_TRANSCRIPT_DIR`, capped in events and in files); two live sessions writing one file would each hold half a scrollback. Claude Code owns the real conversation and resumes it by `session_id`, so losing the file costs a scrollback and never context.
  - The old single file is migrated **once**, guarded by the directory's own existence — creating it *is* the migration — so an upgrade does not blank the pane somebody was reading, and `config.yaml`'s `backup_exclude` names the directory as well as the old file.
  - A session the CLI has not named yet is **not persisted at all** rather than parked under a temp name and renamed on `init`: every transcript worth keeping already has an id by the time it has anything in it (`resume` sets it before it replays; a live process announces its own inside its first event), and the one thing that can exist without one is a failed spawn's notice, which the next attempt writes again.
  - A session id becomes a filename and arrives off the wire, so `transcript_path` refuses anything `safe_id` rejects **and** anything that does not normalise to a path under the transcript directory — deliberately redundant, and only the first is reachable by mutation; the second is the same rule written where it can be followed from the `open()` at the end of it, spelled with `os.path.normpath` and a string prefix because that is the form a static analyser reads as a barrier (a `Path`-parts comparison is correct and is not one), and a guard nothing can see is a guard somebody deletes.
- **Deleting a conversation is a move, not an unlink** (`conversations.delete` → `/data/chat-trash`, TTL'd and capped): a row's ⋯ › **Delete** hands back an `undo_store` token and the toast's Undo moves the file back, refusing over an occupied path.
  - **Any** conversation the registry holds is refused server-side ("close it first", `POST /api/chat/session/{id}/close`) — and closing the one **on screen** has to satisfy that refusal: `close` detaches it, the view lands on a fresh conversation that has spawned nothing and the old stream is told `switched`. Deleting the ground a live session stands on either kills it or quietly forks it, and with several live "the one on screen" is not the same question as "the ones in use".
  - Delete offers the close rather than leaving a refusal nothing can satisfy, and asks first, because closing one mid-answer loses what it was writing.
  - This is the one mutation `conversations.py` makes in the CLI's store, and it never edits file contents.
- **Batch delete is the same move, per row, with one token** (`/api/chat/conversations/delete`, undo kind `conversations`): a conversation with a live session is *skipped and reported*, not a reason to fail the batch — a select-all that refuses outright teaches people to deselect one row by trial and error — and the batch is capped at `TRASH_MAX`, because accepting more than the trash holds would make the oldest of the batch unrestorable while the toast still offers to restore it. The panel has no selection mode; the route stays for whoever needs it.

## The model and the context pill

- **The chat picks its own model** (`chat_model`, a panel setting; `POST /api/chat/model`): the picker opens from the model name in the meta line and from ⋯ → Model, offers the same `MODEL_CHOICES` ⚙ does (its empty-id "CLI default" row filtered out — in the chat, "" means "follow ⚙ Settings" and a Default row already says that), and never touches the global `model` option, which would silently change what every insight run costs. Applying it is a stop and a `--resume` — the model is an argv flag — refused mid-answer.
- **Every "is a restart needed" question is asked of `_spawned_model`, never `session.model`**: the server refreshes `session.model` from settings on every request, so intent routinely agrees with a pick the live process has never seen, and a long-lived process never respawns on its own. `send()` runs the same comparison, so a ⚙ edit lands on the next message; and `--model` stays on a `--resume` argv on purpose, because a resumed session otherwise keeps the model it remembers.
- **`set_model`'s response carries `model_label`**, because the event that refreshes the meta line (`init` → `info`) does not arrive until the next message — a restarted `--resume` process says nothing until spoken to — and the meta line is the only confirmation a pick landed.
- **A model id is turned into a name in exactly one place, and it is the server** (`chat_session.pretty_model`, on the same version parser the window uses; shipped as `info.model_label` and `default_model_label`). No second regex in the panel: a second copy drifts. The minor version is the whole point, because **the label under the composer is the only confirmation a pick landed**. A tier alias (`opus`) prints no version, because the account resolves it; an unreadable id prints itself, because a made-up name for a model we cannot read is worse than the id.
- **The picker's Default row names the global model, so ⚙ has to hand it back** — `/api/settings` returns `model_label` and `saveSettings` refreshes `chatState.defaultModel`. ⚙ is reachable from the Terminal tab and the stream's opening snapshot is not reopened by it, so without that the row — the *highlighted* one whenever no override is set — names the model you just replaced.
- **The context pill measures the conversation, not the work.** Its numerator is one model call's `usage`, taken off the `assistant` event — never the `result` envelope, whose `usage` is the whole turn added up: a turn is many calls and each one re-sends the conversation.
  - Its denominator comes from the model's **version**, not its family (Opus and Sonnet went to 1M at 4.6, Haiku stayed at 200K).
  - A model whose version cannot be parsed reports its token count and no percentage: the candidate answers are 5× apart, and a percentage of a guessed denominator is worse than none. `BRAIN_CONTEXT_WINDOW` is the escape hatch for a model that ships before the table learns about it.
- **The denominator is re-derived the moment the model changes** (`_rewindow`, off the `init` event), not on the next turn: `--resume` carries the conversation, so the token count survives a pick and the window does not belong to it.

## Discussions and resolutions

- **Discuss opens a conversation; it never resets one** (`SessionRegistry.new(finding_ts=)`).
  - Resetting the attached session would kill a busy chat's answer and its approval card, the one loss the registry exists to prevent.
  - The subject is in the transcript's `meta` (`finding_ts`, admitted by `_clean_meta` as a positive int, restored by `_kept_meta` on resume), so a reload and a resume both still know what the buttons are about.
  - A cap the person set is still the only 409; with no limit (the default) there is none.
- **The conversation about a finding can end it, and the label is the record** (`chat_session.resolution_offer` / `RESOLUTION_VERBS`, `ha_mcp_server.offer_resolutions`, `chatResolutionsNode`). The strip above the composer carries the four endings EVERY finding has; the useful answer is the specific one the conversation just reached.
  - Claude offers them by calling an MCP tool that **changes nothing**: the panel is already streaming that conversation, so **the call itself is the offer**, read off the stream in `_normalise`. It is a tool and not a fenced block in the reply because prose is what gets reworded, a tool call is schema-validated by the CLI before it is sent, and nothing model-authored lands in the bubble where the card belongs; a call this cannot read falls through to the ordinary tool chip, so the MCP server's own refusal is on screen and Claude can correct it rather than a card rendering empty.
  - **The press is the consent** — nothing settles until one happens, and it goes to the same `/api/finding/{ts}/{verb}` route the tab's buttons use, because an ending that meant two different things depending on the surface is `_end_finding`'s whole reason for existing.
  - **The label IS the note**: one string per option, so there is no second string a person cannot see before they press, which is what makes a model-written memory line acceptable at all.
  - **No resolution touches the house** — the verbs are the three that record a decision, so the worst a mis-tap can do is settle a finding, which the toast's Undo takes back whole; `fix` is deliberately not offerable (it is the one press that sends Claude at a house, it belongs on the strip where it is pressed on purpose, and it does not end a finding anyway — it moves it to `fixing`, a different lifecycle from *dismissed*).
  - And **the subject is the session's, never the model's** (`ChatSession.finding_ts`, set when Discuss opens the conversation and stamped onto the event at emit): a model retyping a timestamp can name the wrong finding, so it is not asked for one — and stamping at emit rather than resolving at render is what makes a replayed transcript still know what its buttons were about after a panel restart.
  - Whether there is anything left to press is **derived** from the findings list on every paint, because that card comes back on a reload and by then the row may have been settled on the tab or from a phone.
  - A `todo` resolution also sends its label as the item's `fix`, since what the conversation worked out beats what the check could say without looking.
  - `tests/manual/measure-chatres.mjs` drives the real renderer and fails on an option that does not say where its press lands — three labels sharing one consequence included, because that is what a card looks like when it has stopped distinguishing them.
- **A discussion names its own permission mode, and the switch decides its RULES** (`ChatSession._permission_mode` / `_discuss_rules`). **A discussion is the chat, and the switch decides whether it asks.**
  - With *Let brAIn act without asking* off, a Discuss session spawns with `--permission-mode default` (never inheriting bypass from a `defaultMode` in `settings.local.json`) and its rules ask before every tool on `DISCUSS_ASK`.
  - With it on, it spawns as the chat does (`CHAT_BYPASS`) and its rules only pre-approve (`DISCUSS_FREE_RUN`) — no ask rule, so the change somebody asks for is made in the conversation. `DISCUSS_OFFER` says so in words — make the change, an approval card may appear first, a plan is an extra route and never a reason not to.
  - The rules ride `--settings`, so a flip respawns the conversation on its next message (`_spawned_settings`).
  - A discussion's approval card offers neither "Always allow" nor "Stop asking…": a standing rule is the wrong answer inside a conversation whose contract is "ask before every change".
- **A discussion's "do not act" is a permission rule, not a prompt sentence** (`chat_session.DISCUSS_ASK` / `_settings`). This is the switch-off half of the bullet above.
  - A Discuss session spawns with `--settings` carrying `permissions.ask` for every tool on `ANALYST_DENIED`, except the costed reads and `offer_resolutions` (`_DISCUSS_FREE`), plus `MultiEdit`. So a change is a permission card.
  - In Claude Code an ask rule outranks an allow rule, which is what makes this hold over `settings.local.json`'s pre-approvals.
  - A CLI that refuses `--settings` falls back to `--disallowedTools` for the same list. The direction is closed: losing the rule must not mean losing the guard.
  - `_OPTIONAL_FLAGS` drops a refused flag and respawns, `--permission-prompt-tool`'s arrangement generalised.
- **A plan is an extra route for an agreed change, never the only one** (`RESOLUTION_VERBS["plan"]`, `PLAN_AGREED`).
  - `offer_resolutions` takes `kind: "plan"`, whose label is the change said exactly.
  - The press POSTs the card's own `/api/finding/{ts}/fix` with `{change}`. `_run_plan` hands it to the read-only plan run as the agreed change, and the card waits for Apply, with Undo.
  - It is not an ending, so the finding stays on the list.
  - `_enqueue` always passes `change`, so a plain Fix it press resets it rather than inheriting last time's.
  - The tool's description offers a plan for when somebody wants to read the steps first; a change they simply asked for is made in the conversation.

## The conversation list

- **Ask is your conversations, and a reply's working is one line** (`chatStepsFold` / `chatOfferReport` / `askShow` / `server._discussion_row`). `tests/manual/measure-ask.mjs` drives all of it at 390 (touch) and 1200, and `measure-chatres`/`measure-permcard` assert their cards stay out of the fold.
- **The list opens on yours, and the machines' are a pill away** (`renderConvKinds` / `pickConvSource`): `pillseg` pills over the list off the route's own `sources` (Chats, then every face that has run here, each with its count), the default `you`, the pick remembered (`brain.ask.source`) and dropped back to `you` when that kind no longer has runs.
  - One kind at a time is what keeps your chats from being buried under forty voice turns; a house where nothing but you has run gets no pill row, because one pill is a label.
  - The heading names the kind and its blurb sits under the pills. Diagnostics has no Runs block: one place to read them.
- **One ⋯ per row** with Delete and the toast's Undo, never a ✕ on every row.
- **With no conversations at all, a phone opens on the message box** (`body.ask-empty`, set by `refreshChatRail` when your list and every machine kind are empty, cleared by the first send): ⋯ reads **Options**, and the head has no Back to an empty list.
- **On a phone Ask opens on the list** (`body.ask-list`, below the rail's 900px breakpoint, chat face only — the classic face is one shell with no list), a row opens the transcript, and `#chatHead`'s back button returns; `discussFinding` opens the transcript, because Ask on a card is about that card.
- **Tool calls, results, thinking and a background task finishing fold into ONE closed "Worked through N steps" per reply**, placed where the first step landed and above an answer still streaming; the line counts what failed and what was not permitted. The approval card, the question card and the resolutions card are appended to the log and never into a fold — the CLI is blocked on the first two, and a decision folded away is one nobody makes.
- **A step is named in words** (`toolDisplayName`): `mcp__home-assistant__get_all_states` is a wire name, the fold says *Get all states* and keeps the raw name in the tooltip.
- **"Save as report"** sits on a reply's LAST answer (so never on a "let me look" preamble) and posts the reply's question to `api/generate` with `report: true`, which `h_generate` takes straight to a card job — not `_interpret`, not the ask bar's patterns, so a question opening "when" or "learn" cannot become a rule or a study because somebody pressed Save; a discussion's opener and a slash command offer none.
- **A discussion is titled by its card**: `_discussion_row` strips `DISCUSS_PROMPT`'s "Discussing: " and adds `finding_ts`, read off the conversation's kept meta (`SessionRegistry.finding_of`) and never parsed from the title, so a person who types the word links nowhere. The snapshot carries `finding_ts` too, so the strip above the composer follows the conversation on screen, shows the card's title as the link back to it on Today, and carries the card verbs Fix · Done · Snooze · Ignore. The opener bubble shows the title with the rest of what brAIn told Claude one press down.
- The list groups rows under **Live now** (answering, waiting on an OK, or a terminal window), then Today / Yesterday / This week / the month (`convGroups`).
- **A row carries a word only while its chat is answering or waiting on an OK** (`CONV_PILLS`): an idle process, a pause to make room, lost context and a record would put the same pill on row after row; the composer line says those states once the chat is open, and an idle chat sorts under its day with only its age.
- The list's bottom clearance is a `::after` spacer, not padding: WebKit leaves a scrolling flex column's bottom padding out of the scroll range, so on an iPhone the last row sat flush under the message box. The house's overlap audit (`devloop/screens.py` `_AUDIT_JS`) measures what is drawn, a control's box cut by every clipping ancestor.

## Titles

- **A chat's title is the person's words, or what brAIn opened it about; never the prompt** (`conversations.title_for` / `known_title` / `clip_title`, `run_sources.record_title` / `titles`, `server._ask_in_chat`'s `title`, `askAbout(prompt, btn, title)`, `brain_title_session`).
  - An opener that knows its title records it on the run-sources ledger as it opens (a line with `title` and no `source`): the panel's Ask sends the person's words or "About <what was pointed at>", a discussion its card, the automation listener a Morph task's `person_words`. A new opener records its title where it opens the conversation.
  - Conversations that already exist, and the classic terminal's, are named by the openers brAIn writes, **each only under the source the registry recorded for that conversation**: the card, ideas and asked-card openers only on `card` runs, Morph's only on `morph`, voice and memory only on theirs — a person who types "Propose insight cards worth adding to my garden" or "INSIGHT CATEGORY: Energy" is titled by those words.
  - The panel's openers that run under the person's own source (ask-about, Personality's and Instructions' Ask, Talk it through) are matched WHOLE, fixed head and fixed closing words, never by prefix.
  - Nothing is recognised by how it reads: a first message that is none of these is the person's own, and their words are the title folded to one line and clipped for length — ":)", "> why" and "- add milk" keep their punctuation. A machine-claimed run whose opener is not one of ours is named by its source's blurb.
- **Machine runs are titled by what they were about** (`conversations.display_title`): a card run's first message is the prompt brAIn built, so the list shows the card's title or the asked question; `title_of` stays the literal opener because `adopt_machine_runs` classifies by it, and the run reader folds a prompt past `REPLAY_PROMPT_FOLD` under its first line.
- **A chat is titled by the short title Claude Code already wrote for it, before the first words** (`conversations._generated_title` / `title_for(generated=)`). The CLI writes an `ai-title` entry into a session's transcript (a `custom-title` one if it was renamed, which wins); the list reads it for the person's own chats and the placeholder-titled machine ones ("A conversation brAIn started"), so a row costs a read and never a run. Recorded titles and brAIn's own openers still win; a chat with none falls back to its first words.
- **Headless chats have no CLI title, so the panel builds one from the request** (`conversations.short_title` / `_request_after_context`). brAIn's chat runs `claude -p`, whose transcripts carry no `ai-title`; with none, the row is the first request's subject: polite lead-in taken off ("Can you tell me why"), first clause, seven words, capitalised. A brAIn context block in front of the request is skipped (the request is the last paragraph), so "A conversation brAIn started" is only left for a transcript with no request after the block. No run is made.
- **A person's chat is named by one small run after its first reply** (`server._title_after_reply` / `_title_chat`, the `chat_title` job, `ChatSession._on_reply`). After the first successful reply, a conversation no source claimed, no opener titled and that is not one of brAIn's own openers gets a two-to-six-word topic from a Haiku run, recorded with `run_sources.record_title` so the list reads it as it reads every opener's title. Once per conversation per add-on run; a failed run leaves the first words.

## The classic terminal

- **The terminal's Claudes are listed, counted and never opened twice** (`chat_session.terminal_windows` / `terminal_holds` / `select_terminal_window` / `close_terminal_window`; `POST /api/terminal/select`).
  - Every window brAIn opens is tagged with tmux user options (`@brain_nonce`, and `@brain_session` when it resumed a conversation), so the panel can tell its windows from somebody's own shell, which is never listed, counted or closed.
  - The conversation list carries them: a row a window holds says **In the terminal** and pressing it brings that window forward on the classic face (saved, so the next status refresh agrees); a window on a conversation with no row yet is listed on its own.
  - Opening an id a window already holds selects that window instead of a second `--resume`, and the chat refuses to open a process on it (`resume` answers `in_terminal`, a send 409s with `TERMINAL_HOLDS`) — two processes on one conversation fork it.
  - A person's cap counts the windows; when the cap or the memory floor needs room and no chat process is idle, the quietest window idle for `TERMINAL_IDLE_S` (15 min of no output or input — tmux cannot see whether Claude is thinking, so anything recent is busy) is closed.
  - The window is opened in the session ttyd shows (`BRAIN_TMUX_SESSION`, else `claude-picker`, else `claude`), so Ask opens with `auto_launch_claude: false` too; with no session at all run.sh's panel may create it (`BRAIN_TERMINAL_CREATE`), anywhere else the request waits for the terminal's first launch.
- **One handoff file per request** (`chat_session.handoff_path`, `brain-terminal-start --handoff <path>`). Each request writes `terminal-handoff-<nonce>.json` and the window it opens is handed that path, which it alone reads and deletes; the script takes only a file of that name beside the fixed one. A request that could not open a window is moved onto the fixed `/data/terminal-handoff.json`, which the terminal's first launch reads — still read for a terminal opened directly or an older panel.
- **The terminal frame retries instead of keeping a 502** (`loadTerminalFrame` / `termFrameIsError` in `app.js`; the proxy's page carries `data-terminal-starting`). The terminal is probed first (`terminal/token`), and a frame that lands on an error page anyway is loaded again with a backoff (1 s doubling to 10 s) under "The terminal is starting…".
- tmux drops its status line under 90 columns via `client-attached`/`client-resized` hooks; the width test is a shell `[` because tmux does not expand a nested `#{client_width}` inside its own `#{<:a,b}`, which silently answers "narrower" at every width.
- **On a phone the classic terminal's input is the injected script's, and its three failures were all silent** (`ttyd-assets/inject.html`, `tests/manual/measure-terminal-mobile.mjs`).
  - **Paste reads the clipboard on `click`, never `pointerdown`**: for a finger a pointerdown is not an activation-triggering event (HTML lists pointerup, touchend and click), so `readText()` is refused there. A refused or absent read opens a real, visible, 16px text box you can long-press Paste into, because the body is `touch-action: none` and xterm's input is an off-screen textarea iOS offers no Paste bubble on, so without it there is no other route.
  - **Pasted text goes through xterm's own paste** — `window.term.paste` (ttyd publishes it), then a synthetic `paste` event xterm cancels when it takes it, then a hand-built bracketed paste as the floor (safe because tmux is always in front and forwards the markers only to a pane that asked) — never straight down the socket, where every newline is an Enter.
  - **The dictation diff is taken against the TEXTAREA, not against what the handler last sent**: ordinary typing moves the box through xterm without telling the handler, so a keydown-less input (autocorrect, a predictive tap, swipe typing) diffed against a stale baseline re-sends the word (`teh` → `tehthe`); `lastValue` is re-read a tick after every keydown and every input it leaves alone, and only text-editing input types are diffed — a paste is xterm's.
  - **The keyboard is one resize, not one per sample**: the toolbar's transform moves on every visualViewport sample (it costs nothing) while `syncHeight` and the report to the panel are committed together once the samples have settled (`SETTLE_MS`), because each height change is an xterm refit, a PTY resize and a full tmux + Claude Code redraw.
  - **An unfocused frame's height is its baseline, down as well as up** (`captureBaseline`): a grow-only baseline reads a frame that got taller for any other reason as "shrank for a keyboard" once it is back.
  - **A toolbar tap refocuses the terminal only if it was focused**, and asks again on `click` because the blur can land after pointerdown; refocusing unconditionally opens a keyboard somebody had put away.
  - `#termFrame` carries `allow="clipboard-read; clipboard-write"`, which is necessary and not sufficient: HA's own ingress frame is above it and not ours.
- **The phone's microphone is Claude Code's microphone** (`panel/voice_mic.py`, `scripts/brain-arecord.py` installed as `/usr/local/bin/arecord`, the toolbar's **Talk** in `ttyd-assets/inject.html`). Claude Code's `/voice` records the machine it runs on.
  - With no card in `/proc/asound/cards` (Docker masks it) it runs `arecord -f S16_LE -r 16000 -c 1 -t raw -q -`, probes it once against `/dev/null`, reads raw PCM from stdout and stops it with SIGTERM. The stand-in answers those three calls: `--version` and the probe exit 0, and a recording streams the panel's loopback-only `/api/voice/listen`.
  - The page captures the mic, box-averages it to 16 kHz S16LE and sends it over `/api/voice/mic`, an ingress WebSocket. The hub keeps one source (a newer page replaces an older one and is told), a half-second pre-roll for the gap between the tap and arecord connecting, and whole samples only.
  - A listener with no page waits `WAIT_FOR_SOURCE_S` and then ends with a 409 that says so, because a space pressed on a desktop keyboard must end the recording, not hang it.
  - The page drives the CLI the way a keyboard does in voice mode's **tap** setting: one space to start, one to stop and send, because a phone cannot hold a key. Before the first recording it reads `/api/voice/state` (the CLI's own `voice`/`voiceEnabled` user settings, nested key first; unreadable is `known: false`, never "off") and types `/voice tap` when that setting is not tap, so the CLI's own checks (claude.ai sign-in, language) give their own messages.
  - The mic and the `AudioContext` start from `click`, like Paste. `#termFrame`'s `allow` names `microphone`. A refused or insecure context is a sentence, never a silent failure. Nothing here transcribes: the words are Claude Code's.
  - `tests/manual/measure-terminal-voice.mjs` taps Talk in Chromium with its fake microphone against `voice_harness.py`, which plays the CLI. The harness reads arecord's stdout as it arrives: a pipe left unread fills at 64 KB, two seconds of audio.

## Layout of the Terminal tab

- **One thing floats over the terminal, and no more.** `#termMenu` (⋯) — everything else is a menu item in `#termMenuPop`, whose buttons are static markup carrying the ids their handlers are bound to (rebuilding a menu's controls on open drops every listener).
- **Nothing folds the bar away**. There is no full-screen button, no `body.term-immersive` and no fold on the composer's focus or on ttyd's keyboard; no code path may hide `.topbar`. The composer above the keyboard is `kb-lift`'s job, which never touches the header (`inject.html` still measures the keyboard for its own toolbar). A stale `brain.termFull` in a browser's storage is read by nothing.
- **The chat lifts itself over the keyboard by asking the page above it** (`installKbLift`/`measureKbOverlap` in `app.js`, `body.kb-lift` + `--kb-overlap` in `style.css`, the keyboard block in `tests/manual/measure-ask.mjs`). On an iPhone in the companion app the keyboard covers HA's ingress frame without resizing it, so the frame's `dvh` and visualViewport never move.
  - The ingress frame is same-origin, so the overlap is `window.top.visualViewport`'s bottom (`offsetTop + height`) against our frame's bottom in the top page's coordinates (each `frameElement`'s rect summed up the chain); under 60px or a pinch zoom (`scale` > 1.05) is not a keyboard.
  - The chat view (never the classic terminal, whose `inject.html` keeps its own toolbar above the keys) gives that much height up.
  - It is re-measured on the top viewport's `resize`/`scroll` and on `focusin`/`focusout` (now and 350ms later, as the keyboard animates), every cross-frame read is in a `try` because `top` is this window outside ingress and can be another origin behind a proxy, unframed or unreadable installs nothing, and `pagehide` takes the listeners off the top page, which outlives the frame.
  - The measure serves the panel over http inside a parent whose visualViewport is a stand-in that shrinks, and checks the composer ends right above the keys, with the page panned too, gives the height back on close, ignores 40px, leaves no listener behind when the frame goes, and does nothing under another origin or unframed.
- **The meta line under the composer is measured, not assumed visible**: `#viewTerminal`'s negative margins cancel `.wrap`'s padding, so they follow the breakpoint the *padding* changes at (640px), and the bottom margin is 0 — `body.term-open` has already zeroed the wrap's bottom padding, and a leftover negative margin shortens `.wrap`, whose `overflow: hidden` clips the model-and-context line.
  - Geometry can't see it (`getBoundingClientRect` is right when the paint isn't), so `tests/manual/measure-chatmeta.mjs` checks with `elementFromPoint`.
  - Its second pass drives the real list behind a stubbed fetch at 1200 and 390 (the rail beside the transcript, and the page Ask opens on below 900px) and fails on a missing mark, a hidden one, one that hangs off the list, a row under the touch floor, or a page that scrolls sideways.

# brAIn: how Claude runs are made and counted

model_plan and jobs, the run queue, turn caps and landing, flags and session ids, the journal and shell rows, rate limits, loop supervision.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **A turn cap is a runaway GUARD and never a budget, and the three that were options are gone** (`engine.LANDING_*` / `hit_turn_cap` / `scripts/brain-landing.sh`). `assist_max_turns`, `automation_max_turns` and `study_max_turns` asked a person to choose a number whose only two settings are *wrong*: low enough to bind and the run stops mid-thought, having paid for every token it spent and produced nothing parseable; high enough not to bind and it is a number nobody should have been asked for. What actually bounds a run's cost is the wall clock, which is a thing people have an intuition about, so that is what is left on the Configuration tab and the caps are large and invisible — 40 for voice, 200 for an automation task, 40 for a card, 60 for a fix, 24 for the brief, the weekly report and an intent, and **none at all** for `brain ask` and the chat, where depth is the deliverable; study takes 60, which is far past any real session and catches only a run looping on a failing tool. **And a guard that trips has to change what happens next**, the same rule the memory size check owes: a run that ends on `error_max_turns` is *landed* — one more invocation, `--resume` on the same session, `LANDING_TURNS` of room, and a prompt that says finish now with what you have in exactly the format the task asked for. The resumed conversation still holds everything the run read, so what comes back is a partial that files instead of a thorough one that never did, and the journal line says `extra.landed` so a run that keeps needing it is countable. Two things it must not do: land inside the *remaining* wall clock only (`LANDING_MIN_S`, or the landing is itself killed and costs a second run for nothing), and land on the **CLI's own** session id rather than the minted one — after the older-CLI `--session-id` retry the minted id names no conversation at all. The shell half is `brain-landing.sh`, sourced by study, `brain ask` and both listeners, with `BRAIN_LANDING_TURNS`/`BRAIN_LANDING_MIN_S` matching `engine.py`'s constants, because two answers to "what does landing look like" is the drift a second copy always produces. It judges a JSON envelope by its `subtype` and never by its words — an answer that happens to mention turns is an answer — and every failure in it is silent and non-zero, leaving the caller the ending it had before this existed.
- **`outcome != "ok"` is not "this run failed", and five of the fourteen words are successes** (`journal.FAILURE_OUTCOMES` / `is_failure`). `applied` and `healed` are successes, `heal_skipped` and `denied` are refusals doing their job, `fallback` is a quieter path that still produced a card — and `journal.summary` put every one of them in `failures`, where `reports.faults` renders the list. So the report that prompted 1.50.0 opened *what is wrong right now* with **`Run (healing): ended healed`** — an overnight repair that worked — carrying **no detail**, which is the fault shape CLAUDE.md already names as the one nobody can act on. The row was carrying the answer the whole time: `record` takes `ok` from the caller and writes it down, `healing` passes `ok=True`, and the summary read past it. `ok` is the authority now and the outcome set is the floor under a row written before `ok` was on one. The set moved **into `journal.py`** and `reports.py` reads it: `reports` had its own copy and `summary` had a different rule, so a successful heal was simultaneously not worth a report and worth the top row of the fault list — two answers to "did this run fail", which is the drift a second copy always produces.
- **A rate limit is not a failure and is still said** (`reports._rate_limited_row`, `RATE_LIMIT_STATE`). 2.11.1 took `rate_limited` out of the failure count and health stays `ok` over it — but a day where the account refused most runs is a fact, so a fault row names the share and the reset once it is ≥10% and ≥5 runs. The pause it drives ends only on a success on the **refused tier** (a Haiku look succeeding every ten minutes was reopening it for the Opus cards), the listener reads `journal.outcome_of` rather than the stored word, and a scheduled card queued in the same tick is let go while the pause is on (`scheduled=True`, recorded in `REFRESH_HOLDS`); a pressed card is never held. The pause also runs to the account's own reset when the tracker reports 100%.
- **Every run is planned by JOB, and the shell half reads the same table** (`panel/model_plan.py` / `engine._run_cli(job=, effort=, schema=)`). Haiku looks, Sonnet thinks, Opus acts, Fable is a press: one `model` option used to answer every run, so triage — a yes/no over a hundred rows a day — cost what a repair cost, and a repair ran on whatever was cheap enough for triage. `JOBS` is one table (`job → tier, effort, may step down, may step up`), `resolve` is the one derivation, and `PRESS_ONLY` is the set a scheduler may never name — `resolve` raises on it unless the caller says a person pressed. **A typed `model` still overrides every job**, which is exactly what it did before 2.0, so nobody's configuration changes meaning; `engine.planned` reads the override and the `thinking` dial out of `settings_store` at call time. The dial's asymmetry is the argument: `light` steps down only where being wrong costs a card and never the apply run, `generous` steps up only the reasoning jobs and never a naming call. `--effort` and `--json-schema` are **optional requests and the run is not**: `_rejected_flag` reads the CLI's own "unknown option" line and the run is retried without that one flag (and only that one — `--session-id` stays), because a CLI a version behind must not fail every scheduled run over a flag. The shell half — the consolidator, study, both listeners — cannot import the plan, so `model_plan.py` prints its tier answers as exports and run.sh appends them to `/data/.brain_env` at boot: one table, two readers, never a copy in shell. `tests/test_model_plan.py` drives a fake `claude` that records its argv, because "the job reached `JOBS`" and "the job reached the process" are different claims and only the second decides what Anthropic is asked for; and it greps every `job="…"` the panel passes against the table, since an unknown job lands on the fallback tier silently.
- **A reply the CLI validated beats a reply parsed out of prose** (`server._answer`). First-look verdicts, fix plans and results, intents, curiosity answers and the card contract each carry a schema, and a run that carried one answers with `data` — the object the CLI checked before it was sent — which `_answer` prefers over `extract_json` of the text. The text parsers stay, as the floor for a CLI too old for the flag, and a `data` that is not a dict is read as absent rather than as an answer. The card's design system is `categories.CARD_STYLES`, injected into the saved HTML once by `inject_styles` rather than re-sent as 1.5 KB of hex per run and copied into every card; the contract names the variables. **First looks are capped per local day** (`triage.MAX_PER_DAY`, `TRIAGE_STATE["runs"]`): past it the queue waits for tomorrow rather than surfacing unjudged, the batch cap's trade one clock up, and the counter is deliberately in memory — it is a runaway guard and not a budget.
- **There is no turn cap on a panel run, and the wall clock is the only guard** (`engine._run_cli` sends no `--max-turns`; `OVERLOAD_RETRY_S` / `overloaded`). The bullet above on landing called the caps "large and invisible", and one of them was neither: the Resident's first look ran under `resident.MAX_TURNS = 4`, a structured reply the CLI validates against `--json-schema` is itself a tool turn, and a look that needed one more try ended `error_max_turns` — every token spent, nothing filed, and *Run (resident): ended max_turns* at the top of the next report, which is where this arrived from (*"I really don't want to get 'max number of turns errors'. Get rid of that constraint."*). Raising the number would have been the same bug with a later date. So `_run_cli` passes none: every runner keeps its `max_turns` argument and ignores it, so no caller changes shape, and a run that loops on a failing tool is ended by its timeout, which is what ended it past the cap anyway. The landing stays for a CLI that carries a cap of its own, and `LANDING_TURNS` is the one number left that is a guard rather than a budget. The shell half (the listeners' 40 and 200, study's 60) is untouched and still lands. **And a 529 is not the run's ending while its budget is unspent**: the CLI retries inside a call and gives up on a wall it cannot see past, so a card that died on *529 Overloaded* with fifteen minutes left was a card nobody asked for twice — `_run_cli` waits `OVERLOAD_RETRY_S` and tries the whole run once more, inside the run's own clock (no retry is started without room for it), and the journal says `extra.retried`. Once, because a second refusal in a row is the service saying wait longer than any run can. `tests/fake_claude.py`'s `overloaded_then_ok` mode remembers "first" in a file rather than in the process, because each call is a fresh process.
- **A run made outside the panel is journaled through the panel's own journal** (`scripts/brain_run_journal.py`). The pool, the classic listener and the automation listener run Claude in processes of their own and none was recorded, so the highest-traffic Claude path was invisible to diagnostics and to the usage nudge. The script imports the panel's `journal` and `usage_store` (appended to `sys.path`, so a panel module cannot shadow a stdlib one) rather than writing the row shape twice, nudges only when `journal.is_claude_run(row)`, and never raises; shell callers run it in the background after their answer is written. What it cannot do from there is the panel's in-process listeners — the report writer needs the panel's diagnostics, and a second copy here would be the drift this exists to avoid — so every row it writes carries `extra.shell` and the panel books it on its scheduler tick, `journal.py record`'s arrangement (below): a failed voice turn files its report from the panel, once. A gated scheduled task (paused, budget) writes no row: nothing ran, and a refusal doing its job is not a fault.
- **An optional CLI flag is asked of the CLI before it is sent** (pool `cli_supports`, classic listener `CLI_HELP`). `--effort` and `--system-prompt-snapshot` are probed once from `--help`; an unknown flag ends a run unspoken, and a voice turn has no retry-without-the-flag the way `engine._rejected_flag` does because the user is waiting. `--effort` rides with the plan's model only (an agent that chose a model chose what it gets — engine's rule), and `--system-prompt-snapshot off` only on a resume, which is the only spawn that would otherwise answer under the system prompt its first turn recorded. The pool reads `BRAIN_MODEL_VOICE`/`BRAIN_EFFORT_VOICE` from the environment or `/data/.brain_env` (it does not source the file), and `model_plan.env_exports` now exports the effort.
- **A structured answer needs the tool that carries it** (`engine.run_claude` / `--tools ""`). `--json-schema` is answered through the CLI's own `StructuredOutput` tool. `--disallowedTools "*"` denies that tool too, so a "no tools" run with a schema spent four to six turns asking for a tool it could not have. About 40% of measured runs then answered in prose, and a first look that could not be read put the whole batch on `watch`. `--tools ""` loads no built-in tools and leaves the structured answer working. The old deny stays as the fallback for a CLI that rejects `--tools`. `run_analyst` uses the same flag plus `--strict-mcp-config`, which drops ~22k tokens of agent harness while the MCP server's tools stay. `tests/fake_claude.py`'s `structured` mode refuses `StructuredOutput` under a `*` deny, so the old flags fail on the same fake.
- **A session id is spent by the first attempt that reached the API** (`engine._run_cli`). The 529 retry and a flag retry reused the minted `--session-id`. The CLI refuses a transcript id that already exists ("already in use") before sending anything, so the documented retry could never retry. Every re-spawn mints and claims a fresh id. "Session ID … already in use" is recognised and answered with one more. Optional flags are recognised off the arg parser's own sentence and dropped with their real arity. `fake_claude` refuses a reused id (`FAKE_SESSIONS_DIR`), and the old behaviour is shown failing first.
- **A usage limit is a pause, not a failure** (`journal` outcome `rate_limited`, `server.RATE_LIMIT_STATE` / `_journal_rate_listener`). It is not in `FAILURE_OUTCOMES`, because a limit is the account doing its job and a problem file per refused card is forty files about one fact. The listener holds every scheduled card on 30 min doubling to 4 h, and it is keyed on `journal.is_claude_run`. `_generate`'s summary row about the same failure ran no model and must not double the streak. The first successful run ends the pause. A press is never held.
- **Claude runs have one queue, and it is not the store's** (`panel/run_queue.py`, `server._claude`). Since 2.0 about fourteen call sites spawned runs on the default `to_thread` executor, beside every store read, with no limit and no order. The single-flight invariant in this file had stopped being true. Every engine run the server starts now takes a seat: its own executor, `SLOTS` (3, `BRAIN_CLAUDE_SLOTS`) at once, one seat never given to scheduled work, and waiters served safety, then press, then scheduled. `pressed` reaches the engine too, which is what lets a typed model reach a job a timer may not run on it. `doctor.py` and `rehearsal.py` still call the engine through `asyncio.to_thread` and take no seat, and the comment above `DOCTOR_JOB` now says so. The action gate's model call (`_gate_decide`) takes none on purpose: it is asked from inside a run that already holds a seat, and `tests/test_run_queue.py` exempts exactly it.
- **A loop nobody watches is a loop that stops silently** (`server._supervise` / `LOOPS` / `_loop_health`, `health._loop_problems`). `_worker` had no `except`. A failed fix whose own error-path store write raised (`atomic_write` re-raises `OSError`) killed it for good. Cards then queued for ever while `/api/status` said "queued" and health said ok. The worker now marks the job errored and carries on. Every long-lived task is started through `_supervise`, whose done-callback logs a death at warning with the reason. Beating loops stamp when they last went round. `/api/diagnostics` carries `loops`, and health turns a dead worker into `failed` and anything else into `degraded`, naming the loop.
- **The shell half records its own runs, and the panel books them once** (`journal.py record` / `record_shell` / `book_shell_rows`, `brain-run-source.sh`'s `brain_journal_record`). Study, the consolidator and the memory extractor cannot call `journal.record`, so their failures filed nothing, nudged nothing and spent tokens nothing counted. The command line judges a run the way `_run_cli` does:
  - the envelope when there is one, the exit status when there is not;
  - 124 is `timeout` by name;
  - a failure carries the CLI's last stderr line;
  - a text run's tokens are read off its transcript, once per message id and never a cache read.

  It appends the row with `extra.shell`, nudges the tracker and always exits 0. The voice pool, the classic voice listener and the automation listener write through `scripts/brain_run_journal.py` instead, because they decide the outcome themselves (a task's `fail_code`, a voice turn's verdict) rather than reading it off an exit status; that script marks its rows `extra.shell` too, so they are booked by the same pass. One door per caller and one mark for both: two task rows for one run, or a row the panel never books, is what two definitions of `journal_task` in one script produced when the halves were merged. The panel books unbooked shell rows on its scheduler tick through `_SHELL_HANDLERS`, the listeners an in-process row meets less the nudge. The mark (newest booked second, plus how many rows share it) sits beside the journal, so a restart neither re-books nor drops. **A shell row never meets the in-process listeners** (`record` skips `_notify` for one), or one run would be reported and counted twice. `run.sh` creates the journal and the nudge file claude-owned, because the shell half runs as `claude`.
- **A budget keyed on the plan is a budget the plan walks round** (`model_plan.run_tier` / `tier_of` / `guard_override`, `resident.Ledger(tz=callable)`). The Resident ledger charged each run to its job's table tier. So `generous` put investigations on Opus against the Sonnet allowance, and a typed Opus put first looks on Opus against nothing. It now charges the tier of the model actually sent (`meta.model`) and asks `allows` about the tier the run will really take. Its day is the house's timezone, read lazily, because a zone frozen at import is UTC for the process's life. A typed Fable is refused on any job nobody pressed for (`guard_override`, in the panel and in the shell exports), falling back to the job's own tier with a sentence. `PRESS_ONLY` refuses by job and this refuses by model.

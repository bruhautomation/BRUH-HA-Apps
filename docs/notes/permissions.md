# brAIn permissions architecture

How permission prompts, bypass, the approval card and settings files fit together.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

### Permissions Architecture
- **A security default may only fail closed, and `${VAR:-default}` cannot express one** when the safe value is the empty string. `run.sh` writes `BRAIN_CLAUDE_PERMS_FLAG=""` for the OFF case, so `brain-menu.sh`'s `${BRAIN_CLAUDE_PERMS_FLAG:-$PERMS_FLAG}` — with `PERMS_FLAG` initialised to `--dangerously-skip-permissions` — substituted the dangerous default on the *normal* path, not just when the env file was missing. Every picker session ran with prompts disabled whatever the option said. The flag starts empty now, and the picker no longer reads `BRAIN_CLAUDE_PERMS_FLAG` itself: it asks `brain_perms_flag` (`scripts/brain-permissions.sh`) as each session starts, so the value is current and can only be the flag or nothing. That function reads the variable only as the absent-file fallback, out of `/data/.brain_env` with `sed` rather than by sourcing it, and only the exact flag counts there.
- **A refusal is not a failure, and the chat has to say which.** Headless `-p` cannot prompt, so a call outside the allow-list never runs; it used to arrive as a plain red Error, indistinguishable from a crash. `_DENIED_RE` in `chat_session` marks it and the panel renders it amber as "Not permitted". The match is on the CLI's own wording because nothing structured comes back — which is why bare `Permission denied` is deliberately **not** on the list: that is an ordinary EACCES from a permitted `Bash` call, and mislabelling it sends people to change a setting that was never in the way.
- **"Let brAIn act without asking" is one switch with two doors, and it reaches the terminal and the chat** (`panel/permission_mode.py` / `scripts/brain-permissions.sh` / `server.eff_skip_permissions`). Default **off**; it never reaches insights, the listeners, voice or a fix run.
  - **The key is unchanged.** It is still `dangerously_skip_permissions`, so every existing configuration keeps its meaning. It is in `addon_options.OPTION_KEYS` and `settings_store.OPTION_BOOLS`, so ⚙ → Permissions and the Configuration tab are one setting.
  - **The precedence has one turn, about which stale value is safe** (`eff_skip_permissions` / `_options_sync` / `h_settings_put`). A local override exists only because a write to the Supervisor failed, and it outlives whatever is done on the Configuration tab afterwards. A stale "ask" costs a prompt; a stale "act" goes on acting after somebody turned the switch off there. So a local `False` wins, a live Supervisor value outranks a local `True`, then `BRAIN_SKIP_PERMISSIONS`; only an explicit `True` acts. A ⚙ save of ON the Supervisor refused is a **409** ("still asking") and the box goes back, because a local `True` would outrank nothing and be promoted nowhere — a toast saying on over a switch that stays off. A refused OFF is kept locally and takes effect, and the response carries `saved_locally` so the toast says the Configuration tab did not move. `_options_sync` promotes a local OFF like any other override and drops a local ON.
  - **How the terminal gets it.** Not as a flag baked into ttyd's launch command, which is what made a change wait for a restart. The panel publishes one word (`bypass` or `ask`) to `/data/brain-permissions` at startup, after a ⚙ save and after every options poll (`OPTIONS_POLL_SECONDS`, 15s), and `run.sh`'s `publish_permission_switch` writes the same file at boot, before ttyd starts.
  - **Why boot writes it too.** The file is in `/data` and outlives a restart, and a `bypass` left over from the last boot is the one stale value that fails open.
  - **A failed write must never leave the path empty of a file**, because an ABSENT file is the one case the reader falls back on, and the fallback is the boot value — the flag, on an add-on started with the switch on, which is exactly what a failed OFF was trying to take away (`test_the_old_recipe_did_fail_open` shows the old delete doing it). So a failed write leaves an EMPTY file, which reads as asking whatever the boot value says (`permission_mode._clear`, and `publish_permission_switch`'s `: > "$file"`). Truncating needs no free space, which is the likeliest reason the write failed, and creating one needs only an inode. A symlink at the path is removed first rather than truncated through (`O_NOFOLLOW`), and a directory already there is left (it reads as asking). Removing the path is the last resort: the panel does it only while `boot_flag_set()` says the fallback would not act, reading `/data/.brain_env` exactly as the shell reader's `sed` does, and run.sh only for a path it cannot even truncate.
  - **How a session reads it.** `brain-terminal-start` calls `brain_perms_flag` when a session starts, and the session picker's sessions (new, continue, resume, new window) start through it with `--no-handoff`; only the picker's background task and a Custom command call `brain_perms_flag`/`claude-run` themselves. `brain-terminal-start` strips any `--dangerously-skip-permissions` handed in, so an old baked command line cannot outvote the file, and no library is no flag.
  - **A session already running keeps the flag it started with, and ⚙ says which** (`permission_mode.terminal_sessions`, `permission_sessions` on `_settings_payload`). ttyd's `tmux new-session -A` reattaches the open session on every visit, so a flip reaches the terminal only when that session ends, in both directions. `terminal_sessions` reads `/proc` (the panel is root) and counts the TOP Claude process of each chain with `tmux` among its ancestors — which is what keeps the chat's processes, engine runs, the listeners and a guided sign-in out — as `acting` (started with the flag or a bypass mode, a picker background task included) or `asking` (interactive, started without). `None` is "could not look", never "none open". ⚙'s line under the switch and the toast after a flip say which open session kept the old setting and to end it with `/exit`; nothing here ends one, because the terminal's shell is somebody's work. Turned OFF with one still acting is `sec.brain_posture`'s row.
  - **The reader's rules.** The file holding exactly `bypass` is the only thing that acts. `ask`, empty, garbage, a directory, a dangling symlink or an unreadable file all ask. Only an ABSENT file falls back, to `BRAIN_CLAUDE_PERMS_FLAG` in `/data/.brain_env`, and only the exact flag counts there: "something is here that I cannot read" and "nothing has been written yet" are different claims.
  - **How the chat gets it.** It spawns with `--permission-mode bypassPermissions` (the value names were read off the installed CLI's own option table, not remembered), so no approval card appears. An idle conversation respawns with `--resume` on its next send through `_spawned_mode` (`_spawned_model`'s rule); one that is mid-answer keeps its mode until then. `permission-mode` is on `_OPTIONAL_FLAGS`, so a CLI that refuses it drops it and the chat asks as before — the direction a dropped guard may fall. A stopped session the registry still holds (the cap stopped it, or a handoff) is started again with the switch's current value, `_adopt`'s rule, or a flip made while it was stopped would spawn the old way and respawn on the first message.
  - **What bypass does not reach**, read off the 2.1.289 bundle's permission check:
    - deny rules are evaluated before the mode, so the platform deny-list holds, and bypass also puts `PLATFORM_DENIED` on the argv as `--disallowedTools` for a box whose settings could not be written;
    - PreToolUse hooks run in every mode, so `brain-protect-hook.py`, the edit snapshot and the action gate still fire (the gate's own answer to the switch is in *brAIn specifics*);
    - the MCP server's `protected_entities` chokepoint is a refusal inside the tool;
    - unattended engine runs load no setting sources, and voice has its own `--settings` deny-list.
  - **What it does NOT cover, and the option text and the caveat under the switch say so** (`#setSkipPermsCaveat`, its own line, so the stale-session sentence above it never replaces it; the toast and the posture row do not say it): `brain-protect-hook.py` matches the obvious shell shapes, so a shell command that reaches a protected entity some other way (a heredoc into `automations.yaml`, a URL built in pieces) runs unasked with the switch on, and a change a shell command makes reaches no undo journal.
  - `tests/test_permission_mode.py` drives the shell reader over every file shape, lifts `publish_permission_switch` out of the real run.sh, runs the real `brain-terminal-start.sh` and `brain-menu.sh` against a recording `claude-run`, and drives both doors through the real routes, the real `_options_poller` and `_options_sync`, the chat through `fake_claude_chat.py`, the failed-write recipes in Python and shell against the old one, and `terminal_sessions` over fake process tables and a real one.
- **The chat asks over the wire the TUI asks over a TTY.** `chat_session._argv` passes `--permission-prompt-tool stdio` and `_spawn` sends the `initialize` control request — the same pair the Agent SDK's `canUseTool` rides, and without the handshake the CLI never asks (its own SDK bundle is the wire-format authority; the docs don't spell it out). A `can_use_tool` control_request becomes an approval card; `POST /api/chat/permission` answers it. Three details are load-bearing: an allow must hand back the **raw** input as `updatedInput` (the CLI schema-validates it, so the clipped display copy must never go); the deny message is worded to match `_DENIED_RE` so the eventual tool_result renders amber, not as a crash; and an unanswered card declines itself after `PERMISSION_TIMEOUT`, because a chat tab — unlike a TTY — may have nobody in front of it and a turn that can never end is worse. Rules still short-circuit (the CLI only asks where the TUI would have prompted), a CLI that rejects the flag at startup gets it dropped and the chat runs exactly as before, and `stop()` withdraws the card because a question the dead process asked can no longer be answered.
- **"Always allow" hands back the CLI's own suggestion, and only one that ends with the add-on** (`chat_session.permission_updates` / `SUGGESTION_DESTINATIONS`, `respond_permission(always=)`).
  - **The wire.** A `can_use_tool` request may carry `permission_suggestions` (PermissionUpdate objects in the SDK's schema), and an allow may answer with `updatedPermissions`.
  - **What is kept:** `addRules` that allow, `addDirectories`, and `setMode` to `acceptEdits`, each only for destination `session` or `localSettings`. `localSettings` is `/config/.claude/settings.local.json`, which run.sh rewrites at every start; a `userSettings` or `projectSettings` suggestion would outlast that rewrite and reach runs nobody was looking at.
  - **What is dropped:** `replaceRules` (it would replace the reading allow-list run.sh writes), every removal, any other mode, and anything malformed — the CLI drops a malformed update itself, and a card offering to always allow what the CLI then throws away is a press that does nothing it said.
  - **The press carries a yes, never a rule.** The rule sent is the one stored when the card was raised, and an `always` with nothing offered is a 400 that leaves the question pending. The card says what the press adds and for how long (`always` / `always_until`: the conversation, or the terminal and every chat until the add-on restarts).
  - **"Stop asking…"** opens ⚙ at the switch (`openSettingsAt`) rather than flipping it, because the dialog is where what stays guarded is written down. It is offered only where it would change something: not on a question, not in a discussion, and not where the process is already in `bypassPermissions` (a card there is a rule or a safety check of the CLI's own).
  - `fake_claude_chat.py` validates `updatedPermissions` against the SDK's shape and fails the turn on anything else, so a test cannot pass on an update the real CLI would throw away. `tests/manual/measure-permcard.mjs` drives the real card at 390 and 1200 in CI's `layout` job.
- **`AskUserQuestion` is a question wearing a permission request's clothes, and the answers ride back inside `updatedInput`.** It arrives as `can_use_tool` like any other ask, but a generic Allow hands the tool an empty answer sheet and the turn falls over — which is exactly what happened. The CLI's own permission component answers with `{...input, answers: {"<question text>": "<answer>"}}` (multi-select comma-separated; its bundle is the wire authority), so `question_spec` parses the questions into a card the panel renders as *the questions* — options, multi-select, free-text "other" — and `respond_permission` refuses to allow one with no answers. A malformed ask degrades to the ordinary permission card, and a skipped one denies with wording `_DENIED_RE` matches (`declined to answer`) so it renders amber, not as a crash. **And an unknown control request is answered, never dropped**: a `control_request` is a question the CLI is *waiting on*, so `_refuse_control` sends back an error response for any subtype the panel doesn't implement — the alternative is a turn that hangs forever on a feature shipped after this panel was written (`FAKE_CHAT_MODE=oddcontrol` refuses to move the turn until something comes back).
- **Background listeners (Assist, Automation)**: Do NOT use `--dangerously-skip-permissions`. Their pre-approvals (MCP, Bash, Read, Write, Edit, WebFetch, WebSearch) live in `/config/.brain/headless_settings.json`, which `claude-run` adds to any `-p` run that names no `--settings` and no `--permission-prompt-tool`; a voice agent's own settings file carries its MCP grant. This avoids root-user restrictions of the flag.
- **The chat and the terminal do what they are asked** (`server.CHAT_IDENTITY`, the generated `/config/CLAUDE.md`'s *How to work here*): they edit the automation, script, scene or dashboard directly, check and reload, and say what changed; `brain undo` is the way back. `brain.intent`'s replay is OFFERED for a new standing rule when the evidence helps, never as the route every automation must take — that was the household's decision, and a chat that sent people to another screen for what they had asked it to do was the complaint.
- **Project settings**: Written to `/config/.claude/settings.local.json` at startup by `setup_claude_settings()` in `run.sh`, and since 2.11 it pre-approves only reading Home Assistant, `offer_resolutions` and `brain own` — it is the terminal's and the chat's, so anything broader there made `dangerously_skip_permissions: false` a no-op
- **The action gate is a third PreToolUse hook, and it never prints allow** (`scripts/brain-action-gate.py`). It sits beside `brain-edit-snapshot.py` and `brain-protect-hook.py` in both `/config/.claude/settings.local.json` and `/config/.brain/headless_settings.json`. A PreToolUse `allow` would bypass every permission rule behind it, so an allowed call is the hook printing nothing. Unreachable is never allow: `ask` on `chat`/`terminal`, `deny` on every other channel, including an unmarked one.
- **Non-root execution**: Claude Code runs as UID 1000 (`claude` user) via a wrapper script at `/usr/local/bin/claude-run` that uses `su-exec`
- **`/data/.brain_env` has to be sourced before it is read, and "after" looks exactly like "never".** The `with-contenv` shebang reloads the s6 container environment and drops whatever `run.sh` exported, so that file is the only route an add-on option has into a background process. Sourcing it works; sourcing it *late* does not. `automation-listener.sh` set `MAX_TURNS="${BRAIN_AUTOMATION_MAX_TURNS:-10}"` sixteen lines above the source, so the alias kept the fallback for the life of the process — the real value landed afterwards under its own name and nothing read it again. `automation_max_turns` was pinned to 10 and `assist_max_turns` to 5 for every install, whatever the options said, and the only trace was the `MaxTurns:` line in the task log (`--max-turns 10` surfaces as `num_turns: 11` in the SDK result). Note what the failure is *not*: sourcing late still fixes anything used under its own `BRAIN_*`/`HOME` name, which is why `assist_tool_access` worked and the turn caps did not — only the **aliased** reads freeze. `brain-learn.sh` had it too, invisible because its fallbacks happened to equal the shipped defaults and the study watcher exports the vars anyway; a direct `/learn` from the terminal got the fallback. Same class as the `${VAR:-default}` bullet above, and the reason both fallbacks now equal `config.yaml`'s defaults: a fallback that disagrees with the shipped default is a second answer that wins exactly when nobody is looking. `TestBrainEnvIsSourcedBeforeItIsRead` checks the ordering in every script that sources the file, and reproduces the two orderings in a shell rather than describing them.
- **Listener speed**: Both listeners use `--max-turns` to limit agentic loops (defaults: 8 for Assist, 30 for Automation, from `config.yaml`; the in-script fallbacks match, and only apply if `/data/.brain_env` is unreadable). The assist path splices a cached area→entity map (controllable domains + Weather/People) into the system prompt so most voice commands skip lookup turns. With `assist_fast_mode` (default) the assist channel runs as a worker pool (`assist-worker-pool.py`): persistent `claude --input-format stream-json` processes per conversation plus a pre-warmed spare, falling back to one-shot spawns on any worker error

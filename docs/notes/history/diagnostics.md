# brAIn: health, doctor, reports and the corpus: history moved out of docs/notes/diagnostics.md

What each rule in `docs/notes/diagnostics.md` cost to learn. None of it is needed to follow the rules; it is here for the next person who wonders why a report, a verdict or a sweep works the way it does. Pointers to tests under `tests/` name files that were removed in November 2026 with the old suite; the rules they enforced still hold.

## Problem reports and faults

- **One problem, one text file, written when it happens.** Every tool for answering "what went wrong" was **pull-shaped** — `brain doctor` if you knew to run it, ⚙ → Diagnostics if you knew to open it, `brain report` if somebody had already asked you for one — so by the time anybody looked, the journal row that would have explained it was one of two thousand and the log line had scrolled off.
- **A report whose faults are buried is a report nobody reads.** What shipped opened with *"Nothing failed to produce this file"* and then six hundred lines of JSON, and the install that prompted this carried seven distinct faults inside it — a rehearsal that could not clean up, a usage credential refused for a reason nothing recognised, a deep check that had failed, a check that could not look, a measurement store reading zero, a notification that would not deliver, and a producer the homeowner had marked Wrong six times out of six. Every one was in the file. None was *findable*.
- **Home Assistant not answering is one fault however many reads it took down, including the ones that do not say so.** The first fold matched each read's error against the words of an outage (502, refused, timed out), so the reads that failed *because of* the outage in their own words escaped it. One Core restart filed seven faults.

## The health verdict

- **A verdict on the add-on itself, because every failure it has shipped was a quiet one.** The credential that expired on a Tuesday afternoon is the example the note grew from; each failure was answerable only by somebody running `brain doctor`. An average moving from 92 to 88 is not something anybody can act on.
- **A verdict whose remedy is to do nothing is not a verdict.** `problems` reported *any* `usage.limits` code as `degraded`, so `sensor.brain_health` went `degraded`, HA's Repairs raised `health_degraded` and `reports.file_incident` wrote a problem file, several hours out of every day, about a credential doing what credentials do — the check catalog's own first rule (a check that fires on a healthy house is worse than no check) broken by the module that IS the verdict. Health was the one reader that had not been told about `AUTH_PROBLEMS`. `reports.faults`' row for it broke its own "a refusal doing its job is not a fault" rule more often than any other. The fixture could not see any of it: `test_health` had written `limits` down as a bare **string** for four releases where `limits_problem` returns a dict, so `if usage.get("limits")` passed on it — the `_error_code` envelope failure again.
- **A pool process is not a pool answering, and a restart owed is something to do.** A house read `ok` with "everything brAIn runs is running" while `sensor.brain_status` said `needs_restart`. Two gaps, neither the faults-vs-verdict split: `_assist_daemon` asked only whether a pool PROCESS was in `/proc`, and a pending restart was not a problem at all.
- **"Assist healthy" follows whether voice answers.** Tests held `LOOP_STALL_S`, `HEARTBEAT_FRESH_S` and `health.POOL_HEARTBEAT_STALE_S` equal.
- **`sensor.brain_health` never goes unavailable, and a stale verdict is not a healthy one.** Serving a last good verdict from a stopped panel was the usage sensors' own bug.

## The diagnostics payload and the run journal

- **A run journal nothing reads back is a run journal that only exists in somebody else's bug report.** `journal.summary` was written for the ⚙ dialog's Diagnostics section and shipped a release before it, so for one release the only route to it was `brain report` — the only people who ever saw it were the ones who had already been asked for it.
- **Diagnostics is one payload with three doors.** `tests/test_doctor_json.py` lifted the report block out of `ha-selftest.sh` and drove it, the same way `consolidator_lock_check` was tested.

## brain doctor and --deep

- **"Is brAIn working" is one press at the top of Diagnostics, and its answer is the header.** The owner asked to *"run all the development tests"* from the panel; the deep check already was that (`brain doctor --deep`, every face, one real round trip each) and lived at the bottom of a Developer fold as `✓`/`✗`/`–` glyphs beside stage names with the verdict in a line under the button. A mark alone was the part nobody could read at a glance. `tests/test_doctor_deep.py::test_every_stage_says_when_it_ran` held the stamp.
- **A storage collection's id comes from the NAME, and the deep check stated both.** `fixer_dry` created its helper as `"brAIn deep check"` — `input_boolean.brain_deep_check` — and then polled ten seconds for the `input_boolean.brain_test_doctor` the other constant named, reporting **"brAIn could not create ... check that the Supervisor token is valid"** about a token that had just done exactly what it was asked. That was the visible half. The quiet half was that the cleanup keyed on the same guessed id and deleted nothing, and `brain_deep_check` is not under `PREFIX`, so neither `rehearsal.leftovers` nor the sweep could see it: one helper per run, accumulating in the one place nothing was looking for litter. The legacy name is still swept so an install carrying the shipped bug's litter is tidied. The suite's fake answered `input_boolean/create` by appending a row whose entity id was the constant, writing down the same guess the code did.

## The rehearsal

- **A guard that refuses has to change the next attempt, and the rehearsal's could not.** One run that failed to clean up left `brain_test_dead_ref` in `automations.yaml`; `automation_writer.apply` refused the duplicate id, so every run after it ended on the first row with nothing planted, and `_remove_all` could not clear it either, because it takes back what THIS run created and this run created nothing. Identical failure, for ever, with the one thing that would end it sitting in a file the panel is perfectly able to edit and nothing on the page saying so. Sharing the removals fixed a second bug: `_remove_automation` answered "already gone" as a removal that happened, the hook flattened that to `(False, "")`, and reading the first value alone reported a success as a failure **with no reason on it** — `brain_test_dead_ref: ` is the sentence that produced.
- **The sweep was a step inside a run, so the only way out of its failure was the run.** The remedy for "a rehearsal left something behind" was **another whole rehearsal**: two automations written into somebody's `automations.yaml`, a helper created, a checks pass and a Claude turn, to delete three things. `brain doctor`'s other suggestion was to open `automations.yaml` and edit it by hand — the `unsettle` route's failure in a new place, where the machinery existed and nothing could reach it. Before `cleared`, the report went on opening with *Rehearsal: left something behind* for ever after the litter was gone, which is the auth re-check's rule with the timer taken off.
- **A successful mutation answers `result: null`, which is the same value as a refusal.** The rehearsal read `null` as the failure sentinel and reported *"Home Assistant would not delete input_number.brain_test_reading"* on every clean run — while its own leftovers scan, reading the states where the helper really had gone, disagreed with it in the same sentence. The fake could not produce the bug: it returned a truthy `{}` where Core sends `null`, so the branch that fired in the field was unreachable in the suite.
- **Removing an automation does not remove its entity, and verifying otherwise reverted the removal.** `_wait_for_gone` polled a 200 that was never going to become a 404, spent the whole `ACCEPT_VERIFY_S`, reported that the automation "was not really removed" — and `_remove_automation` then did the honest thing with a failed verification and **put the entry back**. The removal worked every time; the check condemned it and the revert undid it, which is why a rehearsal's cleanup listed its own planted automations as left behind in the file AND in the states. `leftovers` read `snap["registry"]`, which the collector never emits, so one of its three places iterated over nothing in production while the suite's own fake built the key to match.
- **The suite tests the checks on fixture houses; the rehearsal tests them on YOURS.** The plain `brain doctor` warning is the design page's own recommendation for shipping the rehearsal at all.

## Capture and the corpus

- **A prompt is the one part of this add-on no test has ever run.** That is BRight's `detect_hits` exposure exactly: zero results on every real track for the feature's whole life, with a green suite behind it, because the only fixture was synthetic. Off by default because the design page's own "not building" list says *any capture that is on by default*. `tests/test_capture.py` drove the shell's `redact()` and `capture.redact` against the same fixture strings.
- **A corpus entry is frozen, and nothing regenerates it.** `tests/corpus/build.py` wrote the two that first shipped — the suite's own clean fixture house, whose whole label is *nothing fires here*, and that house with `rehearsal.PLAN` planted in it — and nothing asserted the committed files still matched what the builder would produce. The checks half rode ordinary CI as `tests/test_corpus.py`; a test asserted the structural validator's required keys, kinds and ending words were the *same lists* `schema.json` publishes, and `test_corpus.VERBS` was the third copy of the ending words. `build.py` and `test_corpus.py` went with the old suite.
- **How a house failure becomes a case.** For the eval jobs the cloud loop wrote a case by hand from the issue (below).

## The eval harness (removed with the old suite)

`tests/evals/` and `.github/workflows/evals.yml` no longer exist. What they were:

- **Every LLM job the house runs has an eval suite, and the regression half is a gate** (`tests/evals/`, plan 1.6). The corpus graded the analyst and the first look; the memory extractor, the consolidator, reflect, Morph's learning pass and the devloop's Claude streams had no number at all, so a prompt edit to any of them shipped on a green suite that never ran it. A **case** is one JSON file under `tests/evals/cases/<job>/` — `{id, job, kind, input, expect, origin}` — and `schema.validate` is its schema (no `jsonschema`, the corpus's reason). A **grader** per job in `tests/evals/graders/` is a pure function `(case, output) -> pass | fail | unknown` with a reason, and `tests/evals/test_graders.py` shows every one a good and a bad output in ordinary CI. The **runner** (`tests/evals/run.py`) builds each case's prompt with the job's OWN builder — imported, never copied (`evals/jobs.py`): `EXTRACT_PROMPT` and `read_new_turns`/`worth_extracting`, `outcomes.candidates`/`reflect_prompt`, `outcomes.replay_prompt`, `learning.build_prompt` in a `MorphEnv`, `streams.analyst_prompt` — asks the job's pinned model through `claude -p` with no tools, no MCP and no settings, and grades the answer. **The consolidator is run whole**: `brain-memory-consolidate.sh --once` against a scratch memory directory with `evals/claude_tee.py` as its `BRAIN_CLAUDE_BIN`, so its own guards (size, shrink, empty template) are part of what is graded and the output is the file it left. `--dry-run` builds every case's prompt and asks nothing; CI runs it on every trigger, and it is what names a builder that moved or broke.
- **The rules of the harness.** **Deterministic first**: a string match, a count or a parse decides wherever it can, and a grader that cannot read the output says `fail`, never `unknown`. **The LLM judge is a last resort and pinned** (`graders/judge.py` `JUDGE_MODEL`): it is asked only when a grader answered `unknown` AND the case carries an `expect.judge` rubric, it may itself answer `unknown` (kept, never rounded to a pass), and it never overrules a pass or a fail. **The agent models are pinned too** (`evals/model.py` `PINNED_MODELS`, full ids on the job's `model_plan` tier, never an alias the account can move), the CLI version is pinned in `evals.yml`, and the report records the models asked, the models the CLI says it ran, the judge, and the runner's machine (CPUs, memory, cgroup limits when readable) — a score with no machine is not distinguishable from infrastructure noise. **pass^3 is the gate, pass@1 the diagnosis**: three trials per case; pass@1 is the share of graded trials that passed, pass^3 the share of cases whose every trial passed, because an unattended loop needs the job right every time. An errored trial (the CLI did not answer) is not a disagreement and is left out of both, but a regression suite with no gradable case, or with more than half its trials errored, fails the run. **Regression versus capability**: a regression case comes from something that happened and names it in `origin` (a CHANGELOG entry, a note's anecdote, the test that encodes a shipped bug, an issue); `"synthetic"` is only ever a capability case, and the validator refuses the other combination. Regression suites must reach 0.95 pass^3 (`--threshold`) or the run exits 1; capability suites are tracked and never fail it. **A capability case is promoted** by changing its `kind` to `regression` once it has passed pass^3 on the nightly run for a week, and only if its `origin` can name a real failure — a synthetic case that keeps passing is a capability the job has, not a regression anyone saw. **A regression case is frozen like a corpus entry**: never loosen its `expect` to make a run pass; a case that is wrong is removed in its own pull request saying why.
- **How a house failure became a case.** An eval case pointed at a corpus entry with `{"corpus": "<entry id>"}` (`graders/first_look.py` scored it with `outcomes.replay_look`, the corpus replay's own scorer). For the other jobs the cloud loop wrote the case by hand from the issue: the conversation, the memory and inbox, the tallies, the digest or the stream's context as `input`; what was wrong as `expect`; the issue (or the Wrong ending, the came-back, the owner's "Not fixed") as `origin`; `kind: regression`. Seed counts as first written (2026-11-04): 13 extractor (3 regression), 10 consolidator (3), 11 reflect (5), 5 first look (2), 6 Morph learning (2), 8 devloop streams (3) — short of the plan's 20–50 per job because the repository held few documented model failures for these jobs.
- **The gate's wiring** (`.github/workflows/evals.yml`, `tests/evals/selection.py`). It ran nightly, on dispatch, and on a pull request whose paths `selection.workflow_paths()` listed — a test held the workflow's `paths:` equal to it, and on a pull request the runner narrowed itself further to the jobs the diff reached (`--changed`, two-dot against the base tip like `ci.yml`; a diff it could not compute ran everything). It needed the `BRAIN_REPLAY_TOKEN` secret; without it the job passed with a notice after the dry run, the corpus replay's rule. It carried `timeout-minutes` and a token cap (`--max-tokens`, checked before each trial) and ran four cases at once (`--workers`; Morph's environment, which patches the process, was taken under a lock). It was named `selection.py`, not `select.py`: any script run from `tests/evals/` (the consolidator runs `claude_tee.py` there) has that directory first on `sys.path`, and a `select.py` in it shadowed the standard library module `subprocess` imports — the consolidator case failed in CI with "module 'select' has no attribute 'select'". Making the check required was a ruleset on `main`; a required check behind a path filter never reports on a pull request outside those paths.

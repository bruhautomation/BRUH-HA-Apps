# brAIn: upkeep jobs

Tidy (names and rooms), upgrade advice, the overnight check, the house book, access checks, the maintainer loop.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **A rename is a registry write, so it is reviewed as one table and undone by what it changed** (`panel/tidy.py`, House → Upkeep).
  - **The run proposes and nothing applies.** One run on the `tidy` job reads the hardware-named entities first, then the entities with no room, then a sample of names this house chose, so the style it copies is the house's and not the model's. `parse` refuses:
    - an id that was not offered;
    - a room that does not exist;
    - a protected entity, or a device that carries one;
    - a name still shaped like hardware;
    - a name another entity already answers to (in the house or earlier in the same batch).
    It drops a no-op rather than offering it.
  - **Apply re-reads every field from Core first** (`config/entity_registry/get`), and records before/after only for what Core accepted. A batch that half-applied undoes exactly the half that happened.
  - **Undo is field-wise and conditional.** A field goes back only while it still holds what Apply wrote, and only the aliases this batch added are removed. A rename somebody made since is theirs, and an undo that overwrote it would be a second unreviewed change.
  - **The window is `UNDO_DAYS` (30), on disk.** Unlike the toast's `undo_store`, which is five minutes in memory, this is a registry write somebody may notice a fortnight later.
  - **A room move lists the automations it changes** (`area_reach`). An `area_id` target follows the room, so moving the lamp out of the lounge stops the lounge's "evening" automation reaching it. It matches on the service's domain, because a light service never reaches a sensor in the same room. That makes it a reading of the configs, not a guess.
  - **"No, do this instead" is a row changed in place** (`tidy.revise` / `POST /api/tidy/row/{id}`). The value goes through `parse` itself over a fresh digest — an offered id, a room that exists, no protected entity, no hardware name, no name another entity answers to — and through the names the other rows on the table propose, keeps the row's id (a tick stays a tick) and carries `edited`. The proposal stores the house's `areas`, so a room row's Change is a picker of real rooms. A room row names the thing that moves (`tidyRowText`), an identical refusal is one line (`parse`'s `seen_refusals`, and a count in the card for two entities sharing a label), and the card's ticks are keyed on the proposal (`todayState.tickedKey`), because a set kept from the last table ticked ids that named different rows and left Apply greyed out.
  - **`reg.hardware_name` and `reg.no_area` are the `tidy` situation in `answers.py`.** Their Fix it is `POST /api/tidy/run`, the press that answers them, rather than a plan run that would invent the same table one row at a time.
- **An upgrade verdict is two quotes checked as substrings, and everything else is "not sure"** (`panel/upgrades.py`).
  - **What makes a verdict.** `safe_tonight` and `wait` stand only with one line of the release notes and one line about this house, each at least `MIN_QUOTE` characters. Each must appear in exactly what was read, not in what the model says it read. The house's line is a line of the configuration or the inventory it was handed, or a line a reading tool RETURNED (`quote_from`: `config` or `device`). A `wait` also needs a reason.
  - **Demoted answers.** An answer missing either quote is `unknown`. So are notes that will not fetch: no run is spent on them, because a verdict on notes nobody read is a guess.
  - **It reads the device before it answers** (#663, `server._advise_run`, `engine.ADVISOR_TOOLS`, the MCP server's `get_device_details`). A Z-Wave switch's firmware notes changed one parameter's default; the run held no tools, the facts sat in the node's configuration parameters, a correct answer resting on one was demoted because it was not a line of YAML, and the model guessed a parameter name. The run is now `run_analyst` scoped to `ADVISOR_TOOLS` — the device, its entities, the registry, history and logbook, recall, the configuration and ESPHome reads; every other analyst read is denied to it by name (`run_analyst(allow=)`, which refuses a name outside `ANALYST_TOOLS`). `get_device_details` reads the entity's registry row, the device row and, for a `zwave_js` device, `zwave_js/get_config_parameters` — each parameter one line, `parameter 3: LED indicator = Always off (value 2) — what it does` — three reads on the socket the MCP server already uses, nothing that writes, refused on voice. The prompt names the update entity and tells the run to read it first. `MAX_TURNS` is 24 and `TIMEOUT_S` 600.
  - **What a quote is checked against** (`conversations.tool_reads`, `upgrades.tool_lines`). The tool RESULTS off the run's own transcript, never its final reply and never its tool inputs: a quote of the question it asked a tool is the run's own words. Each result is decoded from the MCP server's escaped JSON into lines (a string, or `key: value`); a result that is an `error` is dropped whole, and a line holding a string the run sent a tool (a search echoing its query) is dropped. A transcript that cannot be read widens nothing: the quote must then be in the configuration, as before.
  - **The notes are data.** The system prompt says so, and nothing in them can widen what the run may do: its tools read and nothing else, so notes that tried to steer it could make it read, never act.
  - **The reason is stored whole** (`MAX_REASON` 4000, `clip_words`, which only ever cuts a runaway reply at a word, with "…"). The 500-character cut was made here mid-word and was the only copy (#660). The card clamps the body to three lines like every card and Details opens it in full.
  - **"Can't tell" says what it could not reach** (`could_not_reach` in the schema, `unreached` on the verdict). A run that called no tool at all says it read nothing beyond the notes and the configuration; notes that would not fetch say the release notes.
  - **Who thinks how hard.** The timer's run is the `upgrade_advice` job's planned tier with tools; a person's **Check again** (the ⋯ on a card that is not a checked safe) is a PRESS seat on the chat's model (`eff_chat_model`, Opus when none is set). Neither is charged to the Resident's ledger: the timer asks once per new version (`UPGRADE_TRIED`) behind `_resident_gate`, so it cannot spend the Resident's Sonnet or Opus allowance.
  - **Matching.** A domain is matched with word boundaries and a code span as a substring, because `light` must not match `highlight` while `white_value` must match `white_value_template`.
  - **What is read.** `secrets.yaml` is never read, any line whose key looks like a credential is blanked, `.storage` and the recorder's database are skipped, and the read is capped in files and bytes.
  - **Installing is a person's press on a checked safe verdict, and nothing else installs** (`server.h_upgrades_install`, `POST /api/upgrades/install`). The card leads with **Apply** when the stored verdict for exactly the waiting version is `safe_tonight` and `checked`, with *What could go wrong* on its face; the press goes through `typed_fix.execute` (the protected list and the tripwire asked at the moment of acting, a `channel: panel` ledger row), with `backup: true` where the update offers one. A Wait, a Can't tell, an unchecked verdict or a version that moved on is a 409. The module itself never calls `update.install` (the AST test in `test_upgrades.py`), and `tests/test_upgrade_advisor_reads.py` reads off the server's AST that the one function naming the install service is the route's own, reached from nothing a loop calls — so no timer, YOLO or not, installs an update. "brAIn never installs an update itself" stays in Details where no Apply sits under it.
  - **An update card opens by its id** (`GET /api/case/{id}`, `_case_or_card`). It answered 404 for every id, and `/api/cases` listed no cases while its `open` counted Today's own two cards; the route answers a case or an `update:`/`tidy:` card whole, and the listing carries `today` beside `cases`.
- **The overnight check cites records by an id it handed out, and a cause that cites nothing is not a cause** (`panel/sre.py`).
- **A finding's "what to do" is what brAIn read, or nothing** (`sre._evidence_fix` / `_siblings_said` / `_not_yours`, `states_now` in the digest; `house_words.without_self_checks` / `without_network_blame` / `readings_agree` / `calm`; `checks.chores.dehumidifier`, `checks.integrations._flood_fix`; `tests/test_fix_from_evidence.py`). A Music Assistant connection error with one player failing was told "Restart the router or DNS server", an integration error "check that integration's settings, or report it to its author", a plug finding "check that it is switched on" about a plug brAIn reads, and "Stop the pump now" stood on one reading. The per-category sentences (`_record_fix`, `_not_your_template_fix`, `_error_fix`, `_source_fix`, the flood check's "read the log, reload it", the dehumidifier's "check it is switched on") are deleted. The digest carries what each record's entities and every entity of a record's integration read tonight (`states_now`, never in the prompt), and the fallback fix says that — "Kitchen Roku reads unavailable now; the other 2 Roku entities answer, so the trouble is at Kitchen Roku, not the network" — or, with nothing read beyond the lines, that brAIn looks at the thing again tomorrow night (`_looks_again`) — never a canned step. A model's overnight fix loses every sentence asking somebody to check what brAIn reads (switched on, powered, reachable, a state, a log) and, when the integration's other entities answer, every sentence sending them to the router, DNS or the internet. Every model-written row (`findings_store._plain_row`) loses its urgent words ("now", "immediately", "right away") unless its evidence holds two agreeing readings of one entity. The self-check gate is the overnight check's alone, because only there does brAIn hold tonight's states: a card's offline device (`CARD_FAULT_FIX`) is one brAIn cannot read. The overnight prompt says the same.
  - **The digest.** `system_log/list`, `zha/devices`, the Z-Wave `statistics_*` sensors and node status, and the automations whose actions switch a plug that the ZHA mesh says a router hangs off. Each record gets an id (`log:<hash>`, `zha:<ieee>`, `zw:<node>`, `auto:<hash>`).
  - **Parsing.** `parse_causes` keeps a cause only when it cites at least one real id, its `entity_id` is one the records name, and its severity is in the closed set. Everything dropped is counted (`refused`, `invented`).
  - **Stable text.** A finding's text is reused by its **anchor**, the sorted record ids, so a cause re-worded tomorrow is the same row rather than a new card every night.
  - **One cause, one problem, one entity** (`_named_in` / `_groups` / `read_user_text`). A log record carries the entities its message names (ids the house has) and the devices whose own name it contains, so a cause about one sensor or plug is filed under it rather than under `""` or an arbitrary entity of the integration; the model's `entity_id` counts only when the cause's OWN records name it. Cited records are grouped by the problem they are evidence of (the Zigbee mesh is one, each Z-Wave node its own, a log line the device it names): records about another problem are taken off the cause with the sentences naming them, counted as `bundled`. A log record says `referenced_by_you` (absent when the config could not be read) — whether anything the owner wrote refers to the entity, read as text off the top-level YAML, `packages/`, `!include_dir_*` folders and the UI template helpers, never `secrets.yaml`; a template entity is theirs by construction. A fix or detail telling them to edit a template over a record saying nothing of theirs refers to it is replaced with one naming the integration (`rewritten`). **A log line resolves only to its own integration's things** (`log_subjects`, `RULE_DOMAINS`, #434): "LIFX is logging the same error" was filed on an unrelated motion sensor whose name was in the message, and an automation's error on whichever automation sorted first. A device is named by a line only when it carries an entity of the logger's integration (none when the logger names no integration); the subject is the automation the logger names, an entity id the message writes out of that integration, or that device's own entity of it; a rule integration (automation, script, scene, template) never stands in for itself; `integ.log_flood`'s `_device_named` follows the same rule (an address the line names keeps the entity it was found on while that device carries one of the integration's — `test_network_checks` pins the tracker). **A log-only cause says what failed** (`_log_said`, `_fix_follows` / `_error_fix`, #444): the detail carries the line's message in plain words (`integrations.shown`), how many times and when it last happened, a cause whose lines say nothing is held back (`unstated`), and a fix sharing no word with the error, an entity it names or a caller is replaced (`unfollowed`). In the not-your-template case the message is said by who, how often and when, without the quote, because the quote is the word that sends somebody looking for their own template.
  - **What a log finding says, and who it is filed on** (`_log_said`, `house_words.log_meaning`/`without_log_text`, `_name_the_callers`, `_subjects`). A cause made of log lines never quotes the line: a status code, JSON and a URL are the integration developer's words, and a card that pasted them and then said the count again in other words said everything twice. It says what the error means in plain words and each count once (`says_count`), and the run's own sentences that paste a line go; `integ.log_flood` says it the same way. A line about calls to an unavailable entity is titled "<device> is offline and N automations and scenes still use it", names each caller once in the detail ("(automation, 5 calls)" when the logbook counted, no word about counting when it did not) and names them in the fix only when there are two or fewer. A line names an entity of its own integration by the house's friendly name as well as by id; several of one hub's things named is the hub's entity; a line naming nothing of the integration's is filed on NO entity with the integration as its fold key — never the integration's first entity, which filed a blind's errors on a sibling cover.
  - **A passing error is held, not filed** (`hold_transient` / `_judge_log` / `trail_rows`, `tests/test_sre_transient.py`). The pass filed "needs you" problems for bursts round a restart — a cloud reconnect, a Bluetooth drop, a Cast retry, an add-on coming back — while everything the integration provides was working when the card was read, and its fix told the owner to reload the integration. Before a log-only cause is filed the house is asked as it is now (`digest`'s `health`, `entry_states`, beside the records and never in the prompt): it is filed only when the integration's things (the entities the line names, else every entity of its platform) are `unavailable`, the error was logged within `PERSIST_H`, and they have been down for `BROKEN_H` — or, with nothing of its own to ask (a library logger), the burst has lasted `BROKEN_H` (`lasted_hours`, off Core's `first_occurred`, raw timestamps rather than ages so a clock skew cannot zero it). Everything else is held with a `transient` decision-trail row saying which; an integration whose entry failed setup is `claimed` (`sys.entry_failed` reports it and `healing` reloads it when self-healing is on). "Could not look" holds nothing: an unread state list keeps the cause, and a line about calls to a missing entity, a rule integration's or the frontend's is never judged here. The held row is not reported, so an earlier night's card about it clears. **brAIn does not reload a loaded integration unattended**: `healing` is a closed playbook whose only reload is an entry that failed setup, and a loaded entry with unavailable entities is not one — so every log cause's fix offers the reload as brAIn's step from the chat (`_brain_reloads` / `_reload_is_brains`), never the owner's. **A media player that sleeps when switched off is held too** (`sleeps_when_off`, `collect`'s `history`, `digest`'s `asleep`, `tests/test_sre_explained.py`, #612): a TV that left the network whenever it was turned off was filed as "unreachable for Google Cast for hours" off the integration's error counts. Each media player unavailable at the review has its own week read; one whose current stretch began straight after an off (or standby), has lasted under `ASLEEP_MAX_H`, and which came back on a power-on from such a stretch before is held as `transient` with that sentence. Unavailable out of an on or playing state, a first ever drop, a stretch past the cap, or a history that could not be read is still judged as before.
  - **A load failure is re-checked before it is filed** (`sre._LOAD_FAILED_RE` / `_config_record` / `_judge_load_error` / `_downgraded`, `house_words.without_files`; `tests/test_sre_load_error_rechecked.py`, #723). One "Invalid config … at templates.yaml, line 27" line became a serious "cannot load because of a typo" while the sensor it named reported a state. A cause made only of configuration lines (Core's config loader or helpers, a template, an automation, a script, "Invalid config"; never an integration whose setup failed, which `sys.entry_failed` answers) that reads as a load failure is filed as written only when what it names is unavailable or missing now AND the error came back after it last loaded (more than one occurrence, and nothing it names has changed since the last). Everything it names reporting is held as `transient`; anything short of both is filed as information with every file and line said as "a configuration file".
  - **An explained automation error stays explained** (`explain_key` / `explained` / `digest(explained_keys=)`, `state["explained"]`, `tests/test_sre_explained.py`, #578). An automation filed as failing at a step, answered Wrong with why ("it switches the bulb and leaves the lamp powered so it keeps routing"), came back the next night in new words: the ledger key is the card's text and `answered_down` holds only a thing that is still down. Every record about an automation or a script — its own log line, or the mesh cross-reference that it switches off a router — has an identity: the automation and the error's own words (counts, times and ids taken out; the step and entity ids kept), or for the cross-reference what it switches off. The anchor keeps the identities a card stood on, a Wrong WITH a reason on an overnight card writes them into the check's own state (capped at `MAX_EXPLAINED`, outliving the anchor), and the next pass does not hand those records to the run (`explained` in the summary). A different error on the same automation is another identity and is filed; a Wrong with no reason explains nothing.
  - **Clearing.** `keep_keys` holds open the rows anchored in a source that was unreadable this pass: `clear_resolved`'s rule, in the producer that writes the rows.
  - **Gates.** Rows go through `triage.gate` like every producer. The pass is nightly between `SRE_HOUR` and three hours later, the stamp is written before the run (`_brief_loop`'s reason), and it answers to `_resident_gate`.
- **The house book is cited sentence by sentence, redacted unconditionally, and published under its OWN token** (`panel/house_book.py`). **It is a pane of its own** (`#viewHousebook`, Memory › House book): "How this house works.", **Add info** leading the head and on every chapter (`POST /api/house_book/add` `{text, section}` — words are written in cited to `note:request`, blank fills the book or the chapter in), **Edit**/**Delete** on every line (`/api/house_book/entry/{id}`, a 12-hex `entry_id` off the words), **Add as written** (`/api/house_book/write`, cited to `you`), and sharing behind ⋯ with the link and **Stop sharing** on the meta line; the line "Every sentence names what it came from; codes and passwords are left out." is rendered on every state, shared or not — `measure-upkeep`'s book pass fails on it missing or reworded. **What a person wrote or corrected survives every rewrite** (`house_book.merge`: `rewrite` keeps edited and `you` lines, `section` replaces only that chapter, `add` only appends), and the merge is made against the book as it is when the run lands, so an edit made while it ran is kept. Search, a room filter (`rooms` stamped per entry off its area/entity sources and `_NAMES`) and the chapter pills are Knowledge's filter system, each counted under the others.
  - **Citations.** `digest` hands out the index (`automation:<id>`, `script:<id>`, `fact:<id>`…), and `parse` keeps an entry only if it cites one of them. Uncited entries are counted and dropped. Redaction runs over every kept sentence: secret keys, token-shaped strings that carry both letters and digits, and a code/PIN/password followed by a value with a digit in it. Redaction ran over-eager at first and ate entity ids and "the code the house uses", which is why `_TOKENISH` refuses underscores and `_CODE_NEAR` needs a digit.
  - **Gap questions.** These are `kind: question` cases from source `house_book` (the `gap` situation). They have a typed **Answer** whose note goes through `_end_finding`'s confirm and lands in memory as the homeowner's words. At most `MAX_QUESTIONS_PER_RUN` per run and `MAX_OPEN_QUESTIONS` open, and a subject asked once is never asked again (`asked`, capped). **A question the registry already answers is not asked** (`digest`'s `placed` / `automated`, `_about_entity`): "where" (and "what room", "located") about anything with an area id of its own or its device's — the id, because an area the list could not name is still a room, which is how a sensor placed through its device was asked about — or about the entity a cited fact was filed under; and "how do you…" about an entity an automation operates. **One lookup, `registry_answers`, and it reads the words too** (#561): "Where is <a motion sensor>?" came in under an automation subject and "How is the alarm disarmed?" was passive, so neither was caught. A where-question whose object (after "where is", or "which room is … in") IS a placed entity's or its device's name, give or take "the", "sensor", "mounted", is not asked — naming one beside something else ("the fuse for the hall sensor") still is; a how-question (active, or passive with an operation in it) about an entity an automation's ACTIONS operate the way asked (`_OPERATIONS`: disarm → `alarm_disarm`, unlock → `unlock`…; `operated_by`, automations with a trigger) is answered by that automation. An investigation's `question` case goes through the same lookup over `_NAMES` and `_OPERATED` (`server._registry_answers`). `tests/test_question_registry_answers.py`. **A gap reads as a question everywhere** (#502): its `fix` says where the answer goes and what the house book is (`house_book.FIX`, an older row's "Answer it here" read as it by `findings_store.shown_fix`), never "answer it here" — that sentence reaches the mirror and the devloop's review, which have no box — its `why` may not cite notes the reader has not seen, and Needs you puts it under **Questions for you** even when no case covers it. Filed open, a question is still offered to the first look, and a look's `ignore` HOLDS it with the look's reason (`findings_store.look_may_set_aside` / `LOOK_MAY_SET_ASIDE`) — the one producer whose open row a verdict may set aside; any other verdict leaves it and spends no investigation (`_resident_apply`). `tests/test_house_book_self_answer.py`. **And the facts the house holds answer it too** (`_fact_answers`, #697): a where-question about a thing a fact filed under it or naming it places (an earlier answer, "<name>: on the Landing ceiling", among them), and a how-question whose operation a fact about the thing describes ("double-press disarm on the hall keypad"), are not asked. A fact places a thing only when it names a room of the house or says where in space (`_PLACED_RE`: a placing verb — mounted, kept, sits — with any preposition, or "is" with under, above, behind, beside…): "is in use", "is on the list to replace" and "is at 4%" answer no where-question. The Resident's question cases ask the same lookup with the facts store (`server._registry_answers`).
  - **Regeneration.** Weekly regeneration happens only after somebody has pressed for a book (`opted_in`) and only when the fingerprint of what it reads has moved. A held week records why.
  - **Why its own token and subfolder.** The book is published to `/config/www/brain/book/house-book-<token>.html`, with the token at `/data/secrets/house_book_token` (inside `backup_exclude`'s `secrets/**`). It does not share the card mirror's token because a revoke rotates the token, and rotating the cards' token would break every dashboard card in the house to un-share one page. It is in its own subfolder because `_sync_card_mirrors` deletes any top-level `*.html` it does not recognise.
  - **Revoke.** It deletes AND rotates, because a URL somebody kept is the thing being revoked.
  - **The page.** It is escaped, has no script, and is `noindex`. While published, every regeneration republishes.
- **The access checks read what an add-on can see, and the users check is the one that is not written** (`checks/security.py`).
  - **The four checks.** `sec.lock_cloud_voice`, `sec.brain_posture`, `sec.addon_unprotected` and `sec.login_bans`. Each `needs` its own snapshot key, so an unread exposure list, posture, Supervisor answer or ban file skips the check rather than clearing it.
  - **`sec.brain_posture` files only when the setting and the house disagree** (`brain_posture` / `STILL_ACTING_TEXT` / `permission_mode.terminal_sessions`). *Let brAIn act without asking* turned ON is a choice with its own label and files nothing; it rides in the weekly digest. What files a row is the switch OFF while `posture.terminal_acting` says a terminal session begun with it on is still running: the switch reaches a session only when it starts, and ttyd's `tmux new-session -A` reattaches the old one. **Its text is new on purpose**: the old "switched off" row is the one people answered Wrong to when they had turned the switch on deliberately, and that settled key must not suppress this one. The detail counts the sessions and the fix is `/exit` (a background task the picker started ends when it finishes).
  - **Posture is read live.** `collect` takes `/data/options.json` and overlays `permission_mode.published()` — the word a terminal session starting now reads, rewritten the moment the switch moves, where options.json is what the Supervisor wrote at boot — and an empty or unreadable file is no answer, so options.json stands. `terminal_acting` comes from `terminal_sessions()`. The key is `unread` only when neither file can be read. The collector test mocks `terminal_sessions` rather than reading the real `/proc`, which a test running beside it could own.
  - **`sec.addon_unprotected`.** It fires only on an explicit `protected: false`; a missing field is "could not tell".
  - **Why there is no admin-token check.** A check on admins holding long-lived tokens was not written because the add-on cannot see other users' refresh tokens. A rule built on half the evidence would report the visible half as the whole house.
  - **The weekly review.** It is one sentence on the `access_review` (Haiku) job, off the digest the last checks pass kept (`ACCESS_DIGEST`, `_note_registry`'s arrangement), with no snapshot of its own. A sentence under `REVIEW_MIN` is not stored.
  - **Failure.** Its stamp is written only by a review that landed, so a separate `access_tried` stamp holds a failing review to one attempt per `ACCESS_RETRY_S`. Otherwise a failure that does not clear is a paid run every ten-minute poll.
- **The maintainer is one loop and five flags** (`server._maint_*`).
  - **Flags.** `MAINT_STATE[name]["running"]` is flipped synchronously in `_maint_start`, for `start_auth_check`'s reason: `create_task` only schedules. Tasks are held in `_MAINT_TASKS` so the loop cannot collect them.
  - **Gates.** Pressed runs check only for a credential (`_maint_pressed_refusal`), and scheduled ones answer to `_resident_gate`.
  - **Journal.** Every run claims the `maintenance` source (engine store, both halves).
  - **Diagnostics.** `/api/diagnostics` carries `maintainer` (each job's running, held, last error and last note), because a nightly pass that stopped and one with nothing to say leave the same empty section.
  - **The page.** The Upkeep pane is `#viewUpkeep` in the House group. `tests/manual/measure-upkeep.mjs` drives the real renderers at 390 (touch) and 1200, and the unreadable, running and empty states. It was verified against a deliberate regression first (six failures) and runs in CI's `layout` job.
- **Home Assistant's long-term statistics are a closed playbook, and only what cannot lose anything runs unattended** (`panel/stats_upkeep.py`, `server._run_statistics` / `_end_statistics` / `h_statistics_undo`, the maintainer's `statistics` job, #576).
  - **What runs alone.** `recorder/validate_statistics` daily, on the first maintainer tick after brAIn starts, and when `automation_writer.CORE_VERSION` moves (a Core update). A `units_changed` whose live state reports the unit the issue names is relabelled with `recorder/update_statistics_metadata` — **with `unit_class`**, which Core stops accepting the call without in 2026.11 — and keeps the metadata unit and class as its undo. A `no_state` is cleared only when the entity registry, read in the same WebSocket round trip, has **no entry** or a **disabled** one: an enabled entry with no state is an integration that has not loaded yet (a restart), and an unreadable registry is "could not tell".
  - **Review of #576: nothing converts unattended, and nothing is cleared on one sighting.** A `units_changed` whose two unit classes match (Wh → kWh) is left with its reason: a relabel would make every old value mean something else, and converting is the owner's press in Core. No clear is made unless `get_config`'s `state` is `RUNNING`, and a `no_state` for an entity the registry does not know (a YAML or template sensor with no `unique_id`) is cleared only when the store's `missing` saw it at least `MISSING_FOR_S` (6 h) earlier; a sensor that reports again drops out of `missing`, so its clock starts over.
  - **What is asked.** `state_class_removed` and `mean_type_changed` on a live sensor have one fix in Core, a delete, so they are a question (source `statistics`, `ask_row`, kind `question`, in `SUBJECT_FOLD_EXCLUDED` so two cards about two sensors are deduped on their words alone); Yes (`_end_statistics`) validates again and clears only what is still flagged, live and unprotected.

Doesn't apply records nothing (its settled key already keeps the words from being filed again).

# brAIn: changing the house safely

Fix plans and typed ops, apply and undo, the action gate, protected entities, the tripwire, house rules, YOLO and the act-without-asking switch, proposals, trials, the automation writer, playbooks, scenes, one-offs, healing, camera policy, file ownership.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **A playbook's identity included a list the snapshot might not have been able to fetch** (`server._offer_playbooks`). `proposals.key_for` hashes the whole config, and a playbook's config ends in one notify step per target — with no `findings_notify_service` set, every `notify.mobile_app_*` the snapshot could see. `snap["services"]` is a best-effort REST fetch that degrades to an empty set and flags itself unavailable, so a pass where `/services` timed out composed the same three playbooks with their notify steps missing, hashed them to three DIFFERENT keys, and offered every one the homeowner had already declined — buying a Claude paragraph for each. Measured: flipping only that field moves all three keys and drops `freeze` entirely, since it is notify-only. Both passes look successful in the log, which is why it reads as the add-on simply ignoring a decline with nothing to point at. This is `clear_resolved`'s rule in the half that OFFERS, and its sibling producers already carried it — `_offer_scene_schedule` returns on an unreadable `scenes.yaml`, `conditions.propose` on unreadable automations — while this one did not. The fixture could not see it either: it built a snapshot with no `available` map at all, so every test ran the one case the producer must stand down on. `scenes.schedule` had the same class of instability one door over and now rounds to `routines.TRIGGER_GRAIN_MIN`, because a wake median that wanders a minute re-offers at 07:11 what was declined at 07:10.
- **A press that changes a house says what it will change FIRST, and what it changed can be put back** (`fixer.PLAN_SYSTEM` / `server._run_plan` / `panel/unfix.py`). "Fix it" queued the one tool-enabled run on the press, with nothing on screen but the rule's own one-line guess at a remedy — so what a person consented to was *go and sort it out*, and the only way back afterwards was `brain undo` in a tab `enable_terminal` can remove. The press now buys a **plan**: `run_analyst`, reading tools only, which is a promise the CLI keeps where "change nothing" in a prompt is one a model keeps. Four rules on it. **The press is the consent** — `apply` refuses a row with no plan and one whose `can_fix` is false, so the card and the route hold the same rule; the plan is read off the ROW and never off the request, because what the run carries out has to be what was on the screen that was pressed; and `plan_block` tells it to do exactly those steps or stop, since a fix nobody approved is worse than a fix that did not happen; a file it cannot write is neither a substitute step nor a reason to stop, and it runs `brain own` on it and carries on (the ownership bullet). **`planning` and `planned` are two words because they are two claims** — a run in flight is not a decision (live, absent from the badge, absent from `CLEARABLE`, and demoted to `open` by `reconcile_running` rather than to `failed`, because a read-only run that died changed nothing) where a plan on a card is exactly what a badge counts, and it IS clearable, since a plan about a problem the check stopped reporting is a plan about nothing. **Cancel keeps the plan**, the run being paid for already. And **a refusal carries no steps** (`parse_plan`), because a list of changes under *brAIn cannot do this* reads as a plan somebody can approve — which is also why an unreadable reply comes back `can_fix: false` rather than raising: a plan that could not be read must never be read as permission. The undo is the other half and is deliberately **not** the toast's token: `undo_store` is five minutes and in memory, right for a mis-clicked row and wrong for bytes in `/config` and a reload Core has done, so this is a button for as long as the row says `fixed`. It reverses out of the two files the run already writes — the edit journal through `automation_writer.revert` (never a second reverter, or `brain undo` and the panel disagree about the same line) and the action ledger through `actions.read_ledger` — over the window stamped on the row either side of the run, the start written to disk *before* the spawn so a panel that dies mid-fix still leaves a window somebody can ask about. **The asymmetry is the design**: a file has a snapshot, so putting it back is exact, where reversing a service call is acting on the house a second time — so Undo LISTS calls, and putting one back is a separate press over the before-state the chokepoint recorded (*A restore is a press*, below), never something Undo or brAIn does unattended. Only the hook's own tools are reverted, because the journal is shared and a panel write in the same minute is a different press with its own undo; an edit made with a shell command reaches no journal at all, which is why the card reports how many files came back rather than claiming the house is as it was. `automation_writer.revert` widened with it — it asked whether the file sat *directly* in `/config`, true of the two files it writes and false of `packages/heating.yaml`, so `in_config_tree` answers it on **real** paths (`/config/../etc/passwd` is lexically under `/config` and is not in it). Three answers nothing may collapse: an empty window says *nothing to put back*, a fix from before the window was recorded says **that** and is refused (the card offers no button), and what the undo managed is reported by the undo rather than by the counts the card showed. `tests/test_fix_plan.py` pins it by driving the routes with `run_agent` rigged to FAIL the test unless a case opts in, and by driving the REAL writers for the undo — the journal line out of `brain-edit-snapshot.py`'s own `main` over a real PreToolUse payload, the ledger row out of `ha_mcp_server.record_action` — because those are processes the panel cannot import, and a shape written down twice is a shape that drifts.
- **A plan is a list of typed operations, and the steps on the card are those operations written out** (`panel/plan_ops.py` / `fixer.PLAN_SCHEMA` / `findings_store._clean_plan`).
  - Six ops, a closed set. Five the panel performs itself:
    - `edit_automation`, through `automation_writer.apply_edit`, the byte splice with its snapshot, reload and verify;
    - `reload`;
    - `call_service` on named entities;
    - `rename_entity`;
    - `set_area`.

    `agentic` is the only one that spawns `run_agent`.
  - Everything is validated in code, and **one bad op refuses the whole plan**: a dropped op is a step on the card that would not happen. The rules:
    - entities by id only, never a scope;
    - a deterministic `call_service` only on its own domain's entities;
    - no `REFUSED_DOMAINS` (Home Assistant administration, shell, brAIn's own registry services);
    - no `SECURITY_REDUCING` service (unlock, open, disarm);
    - an `agentic` op must list the calls and files it may touch, and never `secrets.yaml` or `.storage`.
  - **The steps a person reads are `plan_ops.describe(op)`, never the model's prose**: what is approved is what will run.
  - A plan with no ops is not approvable, which leaves the legacy `_run_fix` path kept but unreachable through Apply. A stored step-only plan, written before ops existed, reads as `LEGACY_PLAN`.
  - Stored ops are **re-validated on every read** (`clean_stored`), because Apply reads them off the row.
  - `verify_by` is checkable or None. It never refuses a plan.
- **The floors are asked at the plan and again at apply** (`plan_ops.protected_refusal` in `server._typed_plan_extras` and `typed_fix.execute`).
  - This includes the tripwire, and the actions of an edited automation, read with `shadow.would_do`.
  - A device-level `set_area` is refused while the protected list is non-empty: which entities it moves is the registry's answer, not the op's.
  - An `edit_automation` op carries its preview:
    - the diff, cut with `automation_writer.locate` and re-indented with its own `_dump`, so the bytes shown are the bytes written;
    - `shadow.replay` of the old and new config over `typed_fix.REPLAY_DAYS`.
  - An edit that cannot be located is refused at the plan, not at Apply.
- **The panel carries out the deterministic ops and stops at the first failure** (`typed_fix.execute`).
  - Edits and registry changes made before a failure are put back, newest first.
  - **Service calls are not**: reversing one is acting on a recorded before-state, which is a press (`h_finding_restore`). It is never something the panel does because a different op failed.
  - A panel service call writes the MCP server's ledger row shape, with the before-state read first (`typed_fix.ledger_row` / `before_of`). The test drives `ha_mcp_server._read_before` and `record_action` to hold the shapes equal.
- **The agentic op runs under a change contract carried in its environment** (`plan_ops.contract_for` → `engine.run_agent(env=)` → `_RUN_ENV` thread-local → `_claude_env`).
  - The contract is the agentic ops' own calls and files only. A deterministic op on the contract would let the run make it a second time.
  - `BRAIN_CHANGE_CONTRACT` reaches the MCP chokepoint, which refuses off-contract calls after every floor. It also reaches the action gate, which checks file edits and shell commands against it: a shell command may only read, with one exception, `brain own` naming only files the contract edits (the ownership bullet's last rule).
  - `BRAIN_CHANNEL=fix` and `BRAIN_INTERVENTION_ID` ride with it. The env is thread-local because a run is one thread from start to finish, which holds on the run queue's executor too; it is cleared in `finally`.
  - The fix run takes a PRESS seat through `server._claude`, `env=` passed through like any other keyword: somebody pressed Apply and is waiting.
- **Before-state on every action** (`ha_mcp_server._read_before` / `record_action`).
  - One state read per named entity, `MAX_BEFORE_STATES`, entities only. An area target is recorded and never expanded, as before.
  - Kept attributes are `BEFORE_ATTRS`: what `reproduce_state` can be handed back.
  - A read that failed is `{"unknown": true}`, which a restore says it could not use. It is never treated as off.
  - Every chokepoint test that asserted exactly one Core request now counts service POSTs.
- **A restore is a press, per entity, and four things are never restored** (`unfix.restore_plan` / `restore_report`).
  - Never restored:
    - a protected entity or a tripwire;
    - a lock to unlocked or an alarm to disarmed;
    - a garage, door or gate cover to open;
    - a reading (not in `RESTORABLE_DOMAINS`).
  - The FIRST before-state per entity in the window wins: a fix that turned a light off and on again has two, and only the first is how the house was.
  - It is applied with one `scene.apply`, then **read again**. Core accepting the call is not the entity being back.
  - The restore is itself recorded on the ledger under `channel: restore`.
  - Undo never restores a call. It now names the press that can.
- **Interventions: every applied plan is watched, and "could not check" is never a pass** (`panel/interventions.py`, `/data/interventions.jsonl`, `server._followup_tick`).
  - Looks at +1, +7 and +30 days (`LOOK_DAYS`), in order.
  - **Deterministic where `verify_by` is**, with no model:
    - `trace_within_h` reads `last_triggered`;
    - `state_is` reads the state;
    - `finding_clears`, or a check's row with no verify, re-runs the originating check over a fresh snapshot.
  - Otherwise a `followup` look (Haiku, `run_analyst`, schema, closed vocabulary, a SCHEDULED seat) gated by `_resident_gate`. A look the gates hold waits up to `LOOK_GRACE_S`, then records `could_not_check`.
  - The last look decides, and `could_not_check` there is the status, whatever the earlier looks said.
  - **The problem coming back** (`came_back`: the original row reopened, or the same key refiled after the fix) is a regression before any look.
  - A regression reopens the row with `came_back_text` citing the intervention id. A row that is gone is refiled through `triage.gate` with a distinct text, so the settled ledger cannot swallow it.
  - **Two regressions of one key is a maintenance interval** (`interval_days`: the median gap, whole days), filed as a finding, not a third fix.
  - The ledger is capped and never cuts a watched row. Undo marks a row `undone`.
  - `_followup_loop` is started through `_supervise("followups", …)` with a `health.LOOPS` row, so a dead loop reads as `degraded` and names itself.
- **The action gate decides from the person's words, the call and the consequence set, and never from a tool result** (`scripts/brain-action-gate.py` → `POST /api/gate` → `server._gate_decide`, `panel/consequence.py`, `panel/gate.py`).
  - **The hook never prints allow.** A PreToolUse `allow` bypasses the permission system (the chat's Discuss ask rules, deny rules, the terminal's prompt), so an allowed call is the hook printing nothing.
  - **Unreachable is never allow**: `ask` on `chat`/`terminal`, `deny` on every other channel, including an unmarked one. `BRAIN_CHANNEL` is set by:
    - the chat (`chat_session._spawn`);
    - `claude-run` when stdin is a TTY (the terminal);
    - fix runs;
    - the voice launchers and the automation listener, which already did.
  - **A hook `ask` in the chat relies on the CLI turning it into the `can_use_tool` approval card.** That path has not been driven against a real CLI; if the CLI reads a hook `ask` in `-p` mode as a deny, the chat refuses rather than asks, which is still not an allow.
  - **Only acting tools are sent.** `GATED_MCP` is held equal in the hook and in `consequence`, and equal to `ANALYST_DENIED` minus the four that change nothing in a house. Built-in Bash/Write/Edit are sent only under a contract: outside one the terminal and the chat are somebody's shell, a gate on every `ls` is a gate nobody keeps, and `brain-protect-hook.py` still guards the protected list there.
  - **A voice-level agent (`BRAIN_EXPOSED_ONLY=1`) is not sent**: it runs under the narrowest floors already, and a voice turn cannot wait on a loopback round trip and a model. So house rules do not reach voice-level turns; enforcing deny-rules at the MCP chokepoint is what would close that.
  - **The person's words** are the transcript's user turns: no `tool_result`, no `isMeta`, no system reminders, no assistant text.
  - **A task that carries `person_words`** (Morph's Tell sends the words beside its prompt) is judged by those instead (`BRAIN_PERSON_WORDS`, exported by the automation listener for that task's subshell, capped): the prompt a caller wraps round a request names every rule it was told and is not the person.
  - **A gated tool's read-only actions are not sent** (`READ_ONLY_ACTIONS`: listing and searching Minecraft add-ons).
  - **The consequence set is built in code from the registries.** Payload walk is `payload_entities`, held equal to `_payload_entities` by a test.
    - Expands scene, script, automation and group members (`search/related`), area and device targets, and a bare `script.<name>`.
    - Shows area names (registry), closed-vocabulary states only (`CLOSED_STATES` or a number), and protected/exposed/tripwire flags.
    - **Never friendly names or attributes.** Assistant-chosen data values are capped.
  - **Order:**
    1. floors (tripwire, protected, voice exposure): deny from code;
    2. house rules (tighten only);
    3. contract arithmetic (`contract_verdict`: a call on the contract, a file it names, a shell command that only reads with no metacharacters, or `brain own` naming only files the contract names, with no flag);
    4. fast path (`consequence.fast_path`: one call, one entity, a `FAST_PATH` service, not a security cover, no scope, the person's words name the entity's room);
    - (before all of these, after YOLO) the `minecraft` channel — a grown-up's request typed in Minecraft's chat — is decided in code by `gate.minecraft_chat_verdict`: `minecraft_world`'s in-world actions allow (the owner's policy: BRUH Minecraft guards and undoes them), anything else denies; never the model, never cached (mcp-voice-integration.md, *A family chat line naming the companion is a brAIn task held to the game*);
    - (also before all of these, after YOLO) the `minecraft_trusted` channel — a grown-up with ⚙ › Minecraft's "Can ask for anything" whose name the server checked — is decided in code by `server._gate_minecraft_trusted` (the trust-model bullet below);
    5. the switch: on `chat`/`terminal` with *Let brAIn act without asking* on, `allow` with path `switch` and no model call — still through `house_rules.tighten` (the bullet after house rules);
    6. the `gate` model (Haiku, `run_claude`, no tools, schema). Anything outside allow/ask/deny is `ask`.
  - **The gate's model call takes no run-queue seat, on purpose.** It is asked from inside a run that already holds one (a fix's tool call), so three seated fixes each waiting on a gate that needs a fourth seat would deadlock into `undecided`. `tests/test_run_queue.py` exempts exactly `_gate_decide`.
  - No credential, a failed run, or a house that cannot be read are all `undecided`. A headless run with the budget spent is too.
  - Verdicts are cached per session/call/words for `CACHE_S`. An undecided one never is.
- **A trusted person in Minecraft gets the chat's reach, and the switch decides the house as it does in the chat** (`minecraft_rules.clean_people`'s `trusted`, `minecraft.Companion._chat`, `automation-listener` `minecraft_trusted`, `server._gate_minecraft_trusted` / `_minecraft_approval_file` / `_end_minecraft_approval`, `panel/minecraft_approvals.py`, `tests/test_minecraft_trusted.py`). The owner: *"I want Vesper to do anything a grown up asks it in game or not … make it per user toggle, not just all grown ups"*, and *"I was getting approve this in brain responses but I have no idea where that would even go in brain."* The trust model:
  - **Three conditions, all in code.** The person's row has "Can ask for anything" on (a grown-up's alone: `clean_people` reads a child's flag as off, so a hand-edited file cannot hand a child the house); the event says `verified: true` (absent is not a check — an older add-on gets the guarded scope; `false` runs nothing, as before); and the faculty, not a service caller, sends `tools: minecraft_trusted` (it is not on `brain.run_task`'s `TASK_TOOLS`).
  - **The scope is the chat's, decided by the chat's switch.** On, the listener widens it as it widens a person's task (the full grant, `bypassPermissions`); off, it is exactly `house` — every MCP tool, no shell, file or web, because the chat would *ask* before each of those and a headless run has nobody to ask. Either way the channel is `minecraft_trusted`, never `chat`, so nothing keyed on the chat's channel (offer_resolutions, the chat's camera rule) is borrowed.
  - **The gate, never the model, never cached.** After YOLO: every `minecraft_*` tool allows (full control of the server is the grant; the add-on's `companion_edit` snapshots for Undo). Anything else: the floors (tripwire, protected), then house rules tightening, then the switch — `allow` acts; `ask` files an approval; `deny` denies.
  - **An approval is a real place.** A headless run cannot raise the chat's card, so the gate files ONE findings question (source `minecraft_approval`, `PLAIN_EXEMPT` and `SUBJECT_FOLD_EXCLUDED`, the call stored whole on the row, text stamped with the time so the settled ledger never drops a second identical ask), answers `approval` (Yes / Snooze / No) on Today and through the request queue on the phone, and sends one notification where brAIn's notifications go. The deny reason hands the run the exact sentence for the game — the phone and Today, or Today alone — and the same call asked again finds the one already waiting. Yes runs exactly the stored call through the MCP server's own `tools/call` (`minecraft_approvals.run_call`), so `protected_entities` and the tripwire stand at the second look; the companion then says "Done: …" to the speaker. No, Doesn't apply and an hour unanswered (`APPROVAL_TTL`, swept by `_requests_loop`) say it was not approved. Nothing an approval says to a player carries a tool's or an exception's words.
  - **The guarded path never says "approve".** There is nothing to approve on `minecraft`, so the gate, the MCP server and the prompt all say "I can't do that from the game. A parent can turn on 'Can ask for anything' for you in brAIn › ⚙ › Minecraft." (`minecraft_rules.CANNED["outside"]`, spelled again in `gate` and the MCP server and held equal by a test).
  - **Words.** The trusted person's `message` is the instruction; it is still wrapped `{"untrusted": true}` because it came through chat, and the prompt says everything else (other players' chat, signs, names, memory) is data.
- **The tripwire is a file the MCP server reads at call time, and an entity never named to a model** (`panel/security.py`, `/config/.brain/honeytoken.json`, `ha_mcp_server._tripwire_refusal`).
  - It is the first guard at the chokepoint, on every channel, including `extra` entities and loose tokens.
  - The refusal text never names the entity and tells the run to stop and say what it was asked.
  - The report is `POST /api/security/tripwire`. It files a `security` case by code through `add_case` (no triage, no gate, no model): `critical` + `now` urgency, `UNMUTABLE_SOURCES`, one row per trip because the text carries the time.
  - It is created on a press (`input_boolean/create`). The minted id is read back (`IDManager`'s `_2`), and person-named tripwires are added through `settings_store.honeytoken_entities`.
  - The default path is spelled the same in both halves (tested). An empty boot writes no file. The file is readable by the `claude` user, because the MCP server runs as that user.
- **A chronic heal is filed with its logs read** (`healing.read_logs` / `log_excerpt` / `system_log_lines`).
  - The source of the log:
    - an add-on: `GET /addons/<slug>/logs`, `Accept: text/plain`;
    - a failed entry: `system_log/list` filtered to the entry's integration (`integration`, now on the candidate);
    - a dead Z-Wave node: `system_log/list` filtered to `zwave_js`.
  - Trouble lines first, colour codes stripped, `journal.scrub`, quoted in the detail and never the text.
  - A log nobody could read says so.
- **House rules only tighten** (`panel/house_rules.py`, `/data/house_rules.json`).
  - A sentence is compiled once, on a press (`house_rules` job, a PRESS seat), into domains, entities, areas, services, a window and a ceiling. The result is validated in code (`clean_compiled`), and anything unreadable is no rule.
  - The gate applies the strictest matching rule after the floors (`tighten`: never looser; `allow`→`ask`/`deny`, `ask`→`deny`).
  - A matching rule also switches the fast path off.
  - A changed rule clears the gate cache.
  - A rule reaches only what the gate is sent, so a voice-level turn is never checked against it.
- **"Let brAIn act without asking" reaches the action gate too, and only an explicit yes acts** (`server.eff_skip_permissions` / `_gate_decide`'s `switch` path / `gate.INTERACTIVE_CHANNELS`).
  - **Why the gate had to hear it.** The switch stops the CLI's own prompts in the terminal and the chat (Permissions Architecture, below). The gate is a PreToolUse hook and hooks run in every permission mode, so without this the switch would have stopped one kind of asking and left the gate's model asking about the same calls instead.
  - **Where it sits.** After the floors, a `deny` house rule, a fix's contract and the fast path; before the credential check and the model. On `chat`/`terminal` it answers `allow` with reason `"Let brAIn act without asking" is on` and no model call, still through `house_rules.tighten`, so a matching rule that says ask or deny wins. `gate.STATE["switch"]` counts it.
  - **A task channel is unaffected.** `gate.interactive` is false for a fix run, the automation listener and voice, which go on to the contract or the model exactly as before: the switch reaches nothing unattended.
  - **Every surface a person types into is the chat while the switch is on** (`server.person_acts` / `_person_run`, `automation-listener.person_task_acts`, `tests/test_one_brain.py`). A phone Reply and a Morph card reply run `run_agent` on `BRAIN_CHANNEL=chat` with the `*_ACT_SYSTEM` prompt (`PERSON_ACT_TOOLS`), off it `run_analyst` with the read-only one. A listener task that is a conversation or carries `person_words` (Morph's Tell and Ask, Design with brAIn) is widened to the full grant, the chat channel and `--permission-mode bypassPermissions`. A task nobody typed is never widened, and a missing permissions library widens nothing.
  - **The switch path reads no entity states** (`_gate_view(states=False)`): states only feed the model's prompt, and forty sequential reads were how a slow house ran the read past `GATE_TIMEOUT_S` and turned the switch's allow into `undecided` → ask. A house that cannot be read at all is still `undecided`.
  - **It fails closed.** Only an explicit `True` from `eff_skip_permissions` takes the switch path (its precedence is in Permissions Architecture, below); anything else takes the model path, never an allow. The switch rides in the cache key (`|switch`), so turning it off is never answered by a verdict cached while it was on. A gate the hook cannot reach still answers `ask` on the two interactive channels: the hook does not read the switch.
  - **No finding for turning it on** (`checks/security.POSTURE_FLAGS`). `sec.brain_posture` used to file a card on every pass the switch was on: a warning about the one setting somebody turned on deliberately, under a label that already says what it does. ON now files nothing and rides in the weekly access digest (`review_digest`), where the sentence can still say it is on. The check fires only for the case nobody chose: the switch OFF while a terminal session begun with it on is still acting (the access checks bullet, below).
  - `tests/test_action_gate.py::TestTheSwitchReachesTheGate` drives both interactive channels, a task channel, a floor and the cache with the switch on.
- **YOLO mode is the owner's opt-in to no restrictions, and it is one setting read in three places** (`settings_store` `yolo_mode`, `server.yolo_mode` / `_publish_yolo` / `YOLO_MODE_ON`, the flag file `/config/.brain/yolo`).
  - **Off by default, and only an explicit True is on.** An unreadable settings store is off. The panel's setting is the authority. `_publish_yolo` writes `on` to the flag file (or removes it) at startup, on every options poll and on a ⚙ save, and the file is skipped on a dev checkout with no `/config`.
  - **The processes that cannot import the panel read the file**: the MCP server (`ha_mcp_server.yolo_mode`, which skips `_call_refusal`, `fire_event`'s two refusals, `_entity_arg_refusal` and `_camera_refusal`), `brain-protect-hook.py` (decides nothing) and `brain-action-gate.py` (gates nothing). Only the exact word `on` counts. `BRAIN_YOLO_FILE` is spelled the same in all five readers, and `tests/test_yolo_mode.py` holds them equal.
  - **The gate allows on every channel before the floors** (`_gate_decide`'s `yolo` path), with no model and nothing cached, so turning it off bites on the next call.
  - **`eff_skip_permissions` is True while it is on**, so the terminal and the chat stop asking. **A plan is applied the moment it is written** (`_run_plan` → `_start_apply`), **and so is every drafted change a request asked for** (`_accepts_at_once`): scenes asked for are written into `scenes.yaml` through the ordinary accept (`_name_and_offer`, `obj["_act"]`), and so is a one-off or standing rule from the ask bar, Morph, a reply, `brain.intent` and a card somebody asked for a change on (`ASKED_CARD_VIA`); only a scheduled card's own suggestion (`card:`) stays a card. Without YOLO, *Let brAIn act without asking* does the same for what a person typed (`typed`, `TYPED_INTENT_VIAS` with `reply`). Asked-for scenes became a card to accept whatever either switch said, and the reply and Morph surfaces drafted rules untyped, so the switch never reached them (`tests/test_scenes_act_and_naming.py`).
  - **Every session is told** (`YOLO_MODE_ON` in the chat and terminal prompt, a section in the generated `/config/CLAUDE.md`): never wait for approval, and ignore any instruction that something needs a human first.
  - **What stays**: the edit snapshot hook, so `brain undo` still reverses a file.

Two answers to one question is one too many, so `checks/devices.zwave_dead_nodes` is public beside the set the two device checks already share and `checks/system.ADDON_STOPPED_TEXT` is exported — `addon_down` files two rows and only one is startable, and a finding's text is the one stable id it has. The reload goes through `homeassistant.reload_config_entry`, the documented service, so it rides `call_core_service` where a domain and a service name are checked; Core's own frontend reloads an entry over REST rather than the WebSocket API, which is the "read the call site, never the first name that sounds right" rule again.
- **brAIn writes the playbook and Home Assistant runs it** (`panel/playbooks.py`). Smoke or CO, a water leak, a freeze with the heating stopped: three events a house can already detect and nobody has written the response to, because writing one means listing every light, thermostat and blind by hand and then never testing it. It is a **proposal**, through 1.44.0's write-reload-verify path, so the asking happens once in advance on a card that names every entity by name — which is the difference between this and the capability page's "acting without asking". **Nothing unlocks anything, ever**: the page lists doors unlocked under smoke and it is wrong, because a lock is the canonical protected entity, a smoke detector is the sensor most likely in a house to fire on burnt toast, and opening the house on a false alarm at 3am is the worst outcome on that page. The rule is asserted over **every action of every generated config** rather than over the branch that would have written one — a rule checked where the config is built holds only for the branches somebody remembered. **Composed deterministically from the registries**: a model picking which valve closes is a guess wearing a config, and one nobody can check afterwards because the automation looks the same either way. Claude writes exactly one optional thing, the card's plain-English paragraph, and a failed run leaves the deterministic sentence. **A protected entity is dropped from the config and LISTED on the card as skipped** — asked at the producer as well as the writer, because a card offering something `automation_writer` will refuse is a wasted no, and showing it is how you see brAIn knows the valve is there and knows it may not touch it. **A playbook with nothing left to do is not proposed**: what remains is a notification and brAIn already sends those — `freeze` is the deliberate exception, because nothing here may turn a boiler on. **A switch is a shutoff when the word is the whole word** (`water`, `valve`, `stopcock`, `mains`, `shutoff`, and **not** a bare `main`, which matches `switch.main_bedroom_lamp`): a missed shutoff costs a line on a card somebody reads, and the other way round costs trust. `key_for` hashes the config, so the key moves with the sensor set and a declined playbook returns when a detector is fitted rather than when the wording moves — which means nothing a **rename** can move may be in one, and the freeze playbook wrote its room's name straight into the notification's text. That is what `_where`'s `area_name(trigger.entity_id)` is for on the other two, and it does the job for one sensor as well as for forty: `routines.to_config` drops its `alias` for exactly this reason. `automation_writer.entry_for` takes a config's own id only behind the `brain_` prefix, so `brain_playbook_smoke` says what it is in six months while an id off the wire cannot claim somebody else's. **Rehearse is `GET /api/playbook/{ts}/rehearsal`** — every call with each target's state now, and it **executes nothing**: `automation.trigger` would run the actions, which is not a rehearsal but the emergency, and a real one is setting the detector off on purpose and reading the trace. **There is no trial button** and the card says why, because a trial replays the week you lived through and that week had no smoke alarm in it — a button that cannot help is worse than the sentence.
- **A byte splice, because a re-serialised file is a diff nobody asked for** (`automation_writer.locate` / `replace_entry` / `remove_entry`). 1.44.0's writer appends and never rewrites; two of 1.46.0's producers have to change an entry that is already in somebody's `automations.yaml`, and round-tripping the list through PyYAML to do it would keep every value and delete every comment. `yaml.compose` builds the node tree without constructing any of it and every node carries offsets into the text that was parsed, so an edit is exactly those bytes — which is why the load-bearing test is that **every byte outside the span is identical**, not that the file still parses. Three things make the span honest and each is a refusal. **A block collection's `end_mark` overshoots**: PyYAML ends one at the start of whatever token ended it, so the last entry in a file swallows the trailing comment and an entry followed by a blank line swallows that, where a **flow** collection closes tightly at its brace — the content end is therefore the deepest scalar's for a block node and the node's own for a flow one. **The leading `- ` is not in the node**, so the dash is walked back to across a newline (`-\n  id: x` is the same item written differently) and what precedes it on that line has to be whitespace, which is also the indent to re-emit at. And **anything that cannot be cut on a line boundary is refused** — two entries under one id, a document that is not a top-level sequence, an item sharing its last line with something else — because nearly-right bytes are somebody's file with a hole in it. A **block scalar** is the exception that looked like the rule: PyYAML ends one at the start of the next token's line, which is *already* a line boundary — so refusing it was answering the wrong question and left an entry whose `description:` is a `|` block (what HA writes for anything multi-line) permanently uneditable. It is accepted with a walk-back over the blank lines the scanner ran on through. **And the result is read back before it is written**: bytes cannot say whether what is left still loads, and removing the only entry from a document that ends with its own `...` marker leaves `...`, which PyYAML refuses outright — the reload afterwards would have taken out every automation in the house. **`Path.read_text` opens in universal-newline mode**, which turned a CRLF file into an LF one on every append, every splice and every `revert` — a whole-file diff from the module whose reason for existing is not to hand one back — so `_read_text` opens with `newline=""` and the emitted block takes the line ending of the text it lands in. `locate` says `None` for three different things and only one of them means the entry is **gone**: `entry_ids` is what tells "you already deleted this yourself" (a row a card may clear) from "brAIn will not cut this" (a refusal it must keep). The invariant is fuzzed — `tests/test_entry_edit_fuzz.py` generates a hundred and twenty files out of a grammar of the shapes a person's file really holds and drives the real `remove_entry`/`replace_entry` over every entry in each. `replace_entry` asks `protected_patterns` of the **new** config for the reason `apply` asks it of an appended one, both snapshot into the same edit journal so `brain undo` reverses either, and reloading and verifying stay the server's. **`apply` takes a `target`** (`TARGETS`: `automations` or `scenes`) rather than growing a twin — the file, the include line, the reload service and the verification domain are a table, and the five steps are the five steps. A file holding nothing but a comment is an **empty** list rather than an unreadable one: HA's own loader answers `None` to both, and a `scenes.yaml` with one header line is the ordinary case on a house that has never saved a scene.
- **The condition an automation you keep undoing does not have** (`panel/conditions.py`). `auto.overridden` reports the fight and leaves somebody to open the automation editor; this is the change that ends it. **One condition, and it is negated** — the obvious shape (`condition: time` with the band's hours and the pattern's weekdays) is wrong in the direction that breaks a working house, because a `time` condition is a **conjunction** and an automation carrying one stands down every weekend too, at every hour. The band is `override_ledger.pattern`'s and is **never re-derived**: every floor that makes one mean something already lives there, and a second answer to "is this a pattern" is the one nobody can see. Four refusals, each **carried rather than dropped** and none of them a card — an automation with no `id` (HA's own editor cannot change it either, so the card says that rather than pretending brAIn is what is in the way), one that already stands down over those hours, one whose existing time condition names an entity instead of a clock (*"I could not tell"* may not be read as *"there is nothing there"*), and a protected target; they ride in `/api/diagnostics`, because every card on the Proposals tab can be answered and none of those can. The case on the card is a **pair** of replay numbers, since one alone is a fact about an automation rather than an argument for changing it, and the card takes a pill and the toast says *changed* rather than *added*. Two things it found by using them: **`shadow.passes` did not wrap midnight** on a `time` condition (Core reads `after > before` as "tonight until tomorrow morning", and testing the two bounds separately answers False at every instant of such a window — so a `not`-wrapped one passes at every instant instead), and **`would_do` did not look inside a `choose`**, so `_protected_refusal` saw no service calls in one and passed it vacuously.
- **A sentence that happens once, and then is not there any more** (`panel/intents.py`). *"Turn the porch light off when the guests leave"* is the sentence people already try to say to their house and no automation model fits it. What is written is an ordinary automation with `mode: single` and one action nobody asked the model for — `automation.turn_off` on itself — so Home Assistant does the running, there is no listener to keep alive across a restart, and **nothing removes it on its own**: a card says it fired and offers a Remove, because an automation that vanished from somebody's file while they were not looking is a file they cannot trust, and one that has waited `INTENT_TTL_DAYS` is *labelled* rather than deleted. Claude writes the config once through `run_analyst` (reading tools only) and what comes back is checked before it becomes anything: **the trigger has to be replayable** — not because a one-off needs a shadow week but because the replay is the only sanity check there is on a trigger that has never fired; **it has to act once**, and `once: false` is a refusal *with the restatement shown*, because a standing rule is a good thing to want and belongs on the path that gives it a trial; **it has to name something**, or the automation does nothing and one that does nothing is indistinguishable from one that has not fired yet (brAIn's own disarm action is excluded from that test, or every empty automation passes it); and **no protected entity**. A refusal is a **row on the tab**, capped so a run of bad sentences cannot push the armed ones off it. Two front doors — `INTENT_RE` on the ask bar (anchored, because *"what happens when the freezer warms up"* is a question and the difference is which word opens it) and the `brain.intent` service — write **one** request file, so the expensive half has one implementation. Firing is read from **`last_triggered`** and never from the automation being off (somebody switching it off by hand is not it having fired), and the stamp has to be *after* the accept, or an automation sharing a slug with one that ran last month reads as done the moment it is armed; an entity Core will not answer for is left exactly as it is. Remove makes the accept path's claims in reverse — spliced out, reloaded, gone from Core, and only then off the list — and hands back an Undo, because it is a press that deletes from `/config`.
- **Four moods for a room, composed from what each bulb can actually be told** (`panel/scenes.py`). Colour temperature where a bulb takes one (a scene of whites is a colour-temperature scene, and an RGB approximation of 2400K on a bulb that could have taken the number is a worse answer written more precisely), colour where it cannot, brightness where there is neither, on/off where there is not even that — and a bulb whose modes cannot be read gets the last of those rather than being dropped, because *"I could not tell"* is an answer and the honest thing to do with it is the setting that works on every bulb ever made. **`brightness`, not `brightness_pct`**: a scene's entity dict is a *state* Home Assistant reproduces, `light`'s `reproduce_state` reads `brightness` (0–255), and the percentage in a scene is an attribute nothing reads — it would store, load, reload and apply, and every light would come on at whatever level it was already at. Night is the only mood that turns most of the room off and which light stays on is matched on its **name**, because there is no attribute for "this is the one I leave on" and a rule invented from the wattage would be a guess about somebody's furniture. The card's evidence is the **picture** — there is no replay and no week — so it is a swatch per light per mood, HSV converted to CSS on the client and nowhere else, an off light drawn as an empty outline rather than a dark square (an inline background beats the class's rule, so the class alone is not the signal), the lights named in text under the strip because a phone has no hover, and a protected light shown as skipped. The **schedule** is a second proposal offered only once the four scenes really exist — read off `scenes.yaml` rather than the proposals ledger, because somebody who copied the card's YAML in by hand has earned it as much as somebody who pressed the button, and a schedule naming a scene that is not there errors at 07:00 every morning; it calls the entity id derived from the name Home Assistant *really has*, never the default, or a Claude-named set gives a schedule that turns on nothing. Claude is used for **one** thing and it is the naming, all four names or none — and four *different* names, because Home Assistant derives a scene's entity id from its name and two moods called the same thing are one `scene.wind_down` with two definitions fighting over it. Every guard downstream passes it: the file takes both, the reload returns 200, the verification is handed an id that really does exist, and the schedule is then offered and walks the room through three moods and a repeat. - **A camera frame is governed by ONE list, ONE daily count and ONE chokepoint** (`panel/camera_policy.py` / `settings_store.camera_confirm` / `ha_mcp_server._camera_refusal` / `POST /api/camera/permit`). Three routes reached a camera ungoverned: the voice prompt told every voice agent to take snapshots, the `camera_check` insight preset did, and nothing limited a run. Now `get_camera_snapshot` asks the panel on every governed frame — voice and task channels, and any run carrying `BRAIN_CAMERA_GRANT` — and a panel that does not answer **refuses**, because a cap nobody can count is no cap. The opt-in list is per camera and empty by default; `PER_DAY` (12) is counted on disk across the house; an unreadable ledger refuses. - **The chokepoint reads the whole payload** (`_payload_entities`).
  - **The failure.** `scene.apply`/`create` take an `entities` map that Core applies through each domain's reproduce_state. A protected lock named there passed the protected list, the deny-list and the exposure gate in one call.
  - **NAMED.** Everything under an entity-holding key at any depth: `entity_id`, `entities` (list or map), `snapshot_entities`, `group_members`, `*_entity_id`. Every guard asks about these.
  - **LOOSE.** Any other string or dict key that is exactly an entity id's shape, which catches a protected id passed as a script variable.
    - The protected list asks about every loose token: only a pattern match can refuse, so a wrong guess costs nothing.
    - The exposure gate asks only about a loose token that is plausibly an entity (`_plausible_entity`: in the snapshot's registry, or under `ENTITY_DOMAINS`). `song.mp3` handed to BRight has an entity id's shape and is no entity, and a voice refusal invented out of a file name is a bug.
  - **The deny-list.** `scene.apply`/`create` get the meta-services' rule (`_reproduce_denied`).
  - **The ledger.** It records the named entities, so a scene applied inline is attributed to brAIn.
- **A script, a scene or an automation is checked by what it reaches, through Core's own `search/related`** (`_member_refusal` / `_direct_scopes`).
  - **The failure.** `fire_event` has been refused while anything is protected since the list existed. `scene.turn_on`, `script.turn_on`, `automation.trigger`, `homeassistant.turn_on` on a script or scene, and a bare `script.<object_id>` reached the house the same indirect way and were checked only as the container. A bare `script.<object_id>` carries no entity id at all; it is now checked as `script.<object_id>` (`_script_service_target`).
  - **The refusals.** A protected member refuses the run on every channel; an unexposed member refuses it on voice. Members that cannot be read refuse while the protected list is non-empty, and on voice. With neither in force, nothing is looked up.
  - **The load-bearing detail.** `search/related` is a reference graph, not a target list. It adds the area and device of every referenced entity and the floor of every area. A script that turns on the hall light lists the hall, and refusing on that would refuse every script touching a room with a protected lock in it. So areas, devices, floors and labels count only when no referenced entity (or the container's own labels) explains them. What is left is what the container itself targets by area or device.
  - **What is not done.** Members are never cached: a guard answering from a minute ago answers for the script as it was before the edit. Automations referenced inside a script are not recursed into; Core does not recurse there either.

# BRUH Task Manager specifics

Levels, options, CPU accounting, containers, End process, runaway.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

- **Level 2 is two switches and a fact, and the page names which is missing** (`settings.level2_status`). `host_pid: true` is in the manifest, and the Supervisor applies it only while Protection mode is off (`supervisor/docker/app.py`'s `pid_mode`: "host" only when `not protected and host_pid`), so the line costs nothing until a person decides; only they can change Protection mode, on the add-on's Info page. The add-on's own `process_view` option is the second switch: with it off nothing reads the host's processes even when the container can see them (`exposed`, which says to turn Protection mode back on). Whether the host is really visible is read, not inferred: kernel threads exist only in the host's PID namespace, so `procs.host_visible` asks whether pid 2 carries `PF_KTHREAD`. Protection mode takes effect only when the container is created, so "option on, Protection mode off, nothing visible" is `needs_restart`, a different sentence from `needs_protection_off`.
- **It rates 5, and the test says so rather than exempting it quietly** (`TestSecurityRating.EXPECTED_BELOW_SIX`). The Supervisor scores the manifest: `host_pid` is -2 whatever Protection mode says, and the manager role (-1) is the narrowest that may restart another app. A further drop still fails.
- **Options are read from the Supervisor, live** (`settings.Options`). The panel's switches write through `POST /addons/self/options` with the WHOLE option set (the Supervisor validates the whole schema), and the panel reads `/addons/self/info`, never `/data/options.json`, which the Supervisor rewrites only at container start: reading the file would make every switch wait for a restart. `EDITABLE` is what the panel may change; `log_level` and the integration switch need a restart and stay on the Configuration tab. A refused write is a 409 in the Supervisor's words, never a toast saying it saved.
- **CPU is computed from the cumulative counters, on one scale for apps and processes.** App stats are asked `one_shot` (no `cpu_percent`, one quick Docker read instead of two a second apart), and `Rates` divides Δ`cpu_usage` by Δ`cpu_system_usage` between two polls, the Supervisor's own formula (`DockerStats._calc_cpu_percent`: a share of the whole machine); `cpu_percent` is only the first reading's fallback on an older Supervisor. A process's CPU is Δ(utime+stime)/HZ/wall/ncpu, the same share, keyed by (pid, start time) so a reused pid never inherits the old process's ticks.
- **A container is named by what it mounts, never guessed** (`procs.identify_mounts`). The cgroup (`docker-<id>.scope`, read from `/proc/<pid>/cgroup`, which works from inside a private cgroup namespace's `/../` paths too) says WHICH container; the Supervisor's API has no container ids, so the name comes from `mountinfo` (readable without ptrace): an app's `/data` root is `…/addons/data/<slug>`, the Supervisor's is `…/supervisor`, Home Assistant's container mounts `/config` from `…/homeassistant` and no `/data`. Plugins mount neither and are named by command (`coredns`, `pulseaudio`…). Anything else is an Unknown container and the policy refuses it.
- **End process is decided in code over a FRESH read** (`policy.verdict`, `ending.Ender`). The page renders the verdict, and the route re-reads the process and asks again: a button drawn a minute ago is not permission to signal whatever holds that pid now (a different start time is `changed`, nothing sent). Only processes in an app's container; never the kernel, the OS, the Supervisor, Home Assistant, a plugin, this add-on, an unknown container, or an app's init/supervisor (`ns_pid == 1` or a name in `SUPERVISION`), each with a sentence pointing at Restart where there is one. SIGTERM first; SIGKILL only after a SIGTERM to the same (pid, start) has had `GRACE_S`. A `PermissionError` is the RECEIVING app's AppArmor profile refusing signals from another profile (most do), and is reported as that with Restart as the remedy, not as a failure of ours.
- **The profile denies other processes' secrets, so Level 2 cannot read tokens** (`apparmor.txt`): `/proc/*/environ`, `/proc/*/mem`, `/proc/*/root/**` and `sys_ptrace` are denied whatever Protection mode says; `/proc/**` read, `signal (send)` and `kill` are what it is for. Proportional memory (`smaps_rollup`) needs ptrace READ that the target's profile must also grant, so it is read where it can be and shown absent (resident memory instead) where it cannot.
- **Restart and Stop are jobs, and each says its cost first** (`apps.impact`, `Monitor.start_job`). Restarting Home Assistant takes minutes and ingress will not hold a request that long, so the route answers at once and `/api/job/<id>` says how it went. The confirmation names the integrations the Supervisor lists in the app's `discovery`, its sidebar panel, whether it boots automatically and that a watchdog does not undo a manual stop.
- **Runaway is a streak, not an average, and nothing acts on it** (`runaway.RunawayTracker`). A reading the Supervisor could not take leaves the streak where it was; a reading below the threshold ends it. The integration's binary sensor is UNKNOWN (not off) with a `reason` when the mirror is stale, judged by the file's mtime against the `stale_after_s` the file publishes (`custom_components/bruh_task_manager/mirror.py`, no HA import). There are no services: an automation restarts with `hassio.addon_restart`.
- **Static files are bound to their routes, never looked up from `request.path`** (`server.static_handler`). Mounted under a prefix the path is not the key, and the first cut answered `app.js` with the page: `measure-task-manager.mjs` mounts the demo under an ingress-shaped prefix and fails on an unstyled page, which is how it was caught.
- **`tests/task_manager_fake.py` is a Home Assistant OS machine on disk and a Supervisor over HTTP.** `FakeProc` writes `/proc` in the kernel's field order (comm in parentheses, `PF_KTHREAD` on kernel threads, `docker-<id>.scope` cgroups, mountinfo roots the Supervisor really binds), and `private_namespace()` is what the same add-on sees with Protection mode on — the Level 1 demo has to look like that, or it shows a Level 2 the Supervisor would never grant (the first measure run did exactly that). `task_manager_demo_panel.py` serves the real panel against both; its `kill` removes fake processes and never signals a real one.

# brAIn key architecture

The MCP server, the startup flow, and the custom integration.

Part of the project notes (see `CLAUDE.md` › *Where the notes are*). Read this file before changing what it covers; add a note here, not in `CLAUDE.md`.

## Key Architecture

### MCP Server (`ha-mcp-server/ha_mcp_server.py`)
- Stdio-based MCP server that Claude Code launches automatically
- Uses `SUPERVISOR_TOKEN` for HA API authentication
- Provides tools for entity states, device control, area listings (`get_areas`), registry listings (`get_registry`: areas/floors/labels/devices/entities/integrations/users via the WebSocket API), dashboard reads (`list_dashboards`, `get_dashboard`), camera snapshots (`get_camera_snapshot`, returned as MCP image blocks), history/long-term statistics (`get_history`, `get_statistics` via the WebSocket API), service calls (`call_service`, optional `return_response` over WebSocket for services with response data), logs, template rendering, config reload
- What a device shows as (`set_device_class`, `show_switch_as`, `stop_showing_switch_as`, `set_sensor_display`): each one brain Power Tool through `call_service`, gated, denied to the analyst and hidden from voice; the two `switch_as_x` tools are checked against the protected list for both halves of the pair. `get_registry`'s entity rows carry `device_class`/`original_device_class` when narrowed to 100 or fewer
- `offer_resolutions` is the one tool that changes nothing and is not a read either: it puts the ways the finding under discussion could end on the person's screen, and the panel reads the call off the conversation it is already streaming. Denied to the analyst, because an unattended run has nobody to offer them to
- Tools are registered via `TOOL_IMPLEMENTATIONS` (name → function name, late-bound) with argument contracts derived from each tool's inputSchema; add a tool = function + schema in `TOOLS` + one mapping line

### Startup Flow (`run.sh`)
The order is `main()` at the bottom of `run.sh`; the panel is last because it
is the foreground process.

1. Health check
2. Environment initialization (`/data` for persistence, and the permission switch's one word in `/data/brain-permissions`, before ttyd can read it), Claude Code update
3. Non-root user setup (`claude` UID 1000, `claude-run` wrapper, shell profile, and the user-editable `/config` YAML handed over by `own_ha_config`)
4. Tool installation, then the `brain` / `ha` CLI dispatchers, then persistent packages
5. Context generation (`/config/CLAUDE.md`)
6. Broken plugin cleanup (removes stale `claude-homeassistant-plugins` entries)
7. MCP server configuration (writes `.mcp.json` with proper ownership) + watchdog
8. Assist scoping, then custom integration deployment to `/config/custom_components/brain/`
9. Background daemons: usage-limits tracker, memory consolidator, study watcher
10. Optional: Assist + Automation integrations
11. ttyd web terminal launch (with the mobile UI spliced in via `build-mobile-index.py`)
12. The panel — the foreground process, and the ingress target

### Custom Integration (`custom_components/brain/`)
- Deployed automatically to `/config/custom_components/brain/` by the add-on at startup
- Registers a `ConversationEntity` so "brAIn" appears in Settings > Voice Assistants
- Provides `brain.send_prompt`, `brain.run_task`, `brain.run_insight`, `brain.add_memory`, `brain.add_todo`, `brain.study`, and `brain.clear_conversation` services. **The integration's own service names are one list written down in two test modules** (`test_power_tools.PRE_EXISTING_SERVICES`, `test_documented_counts.CORE_SERVICES`), and neither is the authority — `__init__.py`'s registrations are, read by AST in `registered_own_services()`, which both are held against. Power tools register in a loop out of their own catalog, which is why they are absent from it
- BRUH Power Tools (`power_tools.py`): 90 admin-gated registry-management services under `brain.*` (areas, floors, labels, categories, entities, devices, integrations and their options, group members, helpers, zones, persons, blueprints, statistics and their repair, users and their groups, backups, Z-Wave nodes, the energy dashboard, Thread networks, Home Assistant's own addresses, diagnostics, dashboards, repair issues, and what an entity shows as), adapted from [Spook](https://github.com/frenck/spook) (MIT) with validation-first handlers, response data on creation services, and dry-run-by-default orphan cleanup (entities *and* devices); catalog metadata generated in `services.yaml`/`strings.json`/`translations/en.json`/`icons.json`, consistency enforced by `tests/test_power_tools.py`. **Nothing is create-only**: every attribute a `create_*` accepts has a service that changes it later, and every registry object that can be created can be renamed and deleted — `tests/test_power_tools.py` asserts the `rename_*`/`delete_*` families are complete. An `update_*` writes only the fields the caller named (`_partial_update`); filling the rest from `call.data.get()` blanks them
- **The via_device chain is somebody else's data, so nothing walks it by recursion.** `disable_device` climbs `via_device_id` to disable a hub once its last live child goes, and `enable_device` climbs it back down — both by recursion, on a chain nothing in Home Assistant makes acyclic, because `via_device_id` is simply whatever id an integration reported. `alexa_media` reports every device as its **own** via_device, so the walk had no end: `RecursionError` on each of an Echo/Wyze/Ecobee household's devices, *after* writing some of the disables — a registry mutation stopping halfway is the worst shape this failure could take. Both walks are iterative with a seen-set, and they stop where the chain would repeat rather than where the interpreter gives up; stopping there costs nothing, since every device on a cycle has been visited by the time it closes. `tests/test_power_tools_device_cycles.py` runs the old recursion into its `RecursionError` before pinning the new walk, and an AST check fails any future function that both mentions `via_device_id` and calls itself. It imports `power_tools` behind permissive stubs and **puts `sys.modules` back**: several test modules install partial `homeassistant` stubs and whichever loads first wins a shared table, which is how the file passed alone and failed under `unittest discover`
- **"Show as" is one setting reached three ways, and each Power Tool takes the way the entity dialog takes** (`power_tools._set_device_class` / `_show_switch_as` / `_stop_showing_switch_as` / `_set_sensor_display`).
  - **A device class override** (a binary sensor as a door, a cover as a garage, a switch as an outlet, and the other domains in `DEVICE_CLASS_ENUMS`) is `async_update_entity(device_class=)`. Core checks nothing (`config/entity_registry/update` takes any string), so the value is checked against the domain's `<Domain>DeviceClass` enum read off the running core, and a core that will not say is refused rather than written unchecked. Every entity is checked before any is written, and choosing the integration's own class stores `None`, so a later change upstream still lands.
  - **A sensor's or a number's class is refused** (`DEVICE_CLASS_REFUSED`): it decides the unit, long-term statistics group units by the class on the state (`sensor/recorder.py`), and the frontend does not offer it either.
  - **A binary sensor made in the UI's template helper takes no new class** (`_ui_template_binary_sensor`: platform `template` with a config entry). Its type lives in the helper's own options, and a registry override would beat it and mask every later change made there, which is why the frontend's entity dialog hides the override for exactly that case (`_hideDeviceClassOverride`). The refusal names where to change it; an empty `device_class` still clears an override already on one, and a YAML template sensor (no config entry) takes an override as before.
  - **A safety class is not changed by a request alone** (`SAFETY_DEVICE_CLASSES`: smoke, gas, carbon monoxide, leak, held equal to `signals.HOT_SAFETY_CLASSES` by a test). The safety lane reads the class off the state's `device_class`, which is exactly what an override rewrites, so showing a smoke detector as a door takes it out of the lane silently and showing a motion sensor as smoke puts every motion into it. Taking an entity OUT of the set (to a non-safety class, or a reset whose effective class leaves it) needs `confirm_safety: true` (`is True`, so a truthy string is not a yes), checked with the rest before any write, so one detector refuses the whole batch. Moving one INTO the set, or out with the yes, says so in that row's `note`; moving between two safety classes and an ordinary change carry none.
  - `show_switch_as`'s entity selector offers the wrapper domains (cover, fan, light, lock, siren, valve) as well as `switch`, which its description and handler already accepted.
  - **A switch shown as another kind of device is the `switch_as_x` helper, driven through its own config flow.** What the flow offers (the target domains, and whether `invert` exists, from 2024.2) is read off the form it returns, never from a version number, and a 2023 form listing `{value, label}` dicts is read too. Moving a switch to another type removes the old helper FIRST, as the dialog does, because the old helper's `async_remove_entry` unhides the switch and a new helper made first would wrap a visible switch. Flipping `invert` goes through the helper's options flow. A flow that does not finish is aborted, not left open, and a failure after the old helper went says the switch is a switch again. The new entity is found with `async_get_entity_id(target, "switch_as_x", entry_id)`, its unique_id being the entry id, and a source stored as a registry uuid is resolved by walking the entries.
  - **Nothing is create-only.** `stop_showing_switch_as` takes the helper or the switch, lists the automations, scripts and scenes that used the entity going away (`_references_to`), and has a dry run. A fan from an integration cannot be shown as a light, and the refusal names what can be done: the plug's switch through `show_switch_as`, or a binary sensor's or cover's class through `set_device_class`.
  - **Sensor display** writes only the named keys of the `sensor` entity options and keeps every other key there, because those options are not brAIn's alone. A unit is checked against `UNIT_CONVERTERS[original_device_class].VALID_UNITS`, because Core converts by the sensor's own class, not an override.
  - `tests/test_device_types.py` drives the real admin-gated handlers against a registry and a `switch_as_x` flow that answer as Core's do (the helper hides the switch, its removal unhides it, the wrapper's options carry the source), copied from `switch_as_x/config_flow.py` and `entity.py`; `TestAnOverrideTheHouseCannotSee` holds the template and safety refusals, and `tests/test_mcp_device_types.py`'s `TestTheOtherHalfOfASwitchIsAskedAboutToo` the pair check through the real dispatcher.
- Insight jobs (config entries of type `insight`): scheduled Claude reports rendered to `sensor.<job>_insight` (markdown attribute + ready-to-paste `card_yaml`); prompts support HA templating
- 3.0 transport: worker pool serves an internal HTTP API (:8098, token on the shared volume); integration streams deltas into the chat log (SSE) and falls back to file IPC; `binary_sensor` reports pool health
- `sensor.brain_health` (`ok`/`degraded`/`failed`) reading the verdict out of the diagnostics mirror
- Usage-limit sensors reading from `/config/.brain/usage_limits.json` (real Anthropic account utilization; requires OAuth/subscription login)
- Communicates with the add-on via shared files in `/config/.brain/`
- Request/response flow: integration writes JSON (unique per-request file id) → add-on processes → add-on writes JSON response named after the request id
- Conversation continuity: the assist listener maps `conversation_id` → Claude session uuid in `/config/.brain/sessions/` and resumes the session on follow-up turns (`--session-id` / `--resume`); falls back to replaying recent history when resume isn't possible

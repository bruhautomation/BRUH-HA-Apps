# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

**This file is loaded into every session and every subagent, on every turn, so it stays short.** It holds the project overview, the rules every change needs, and a map of the notes. The long notes (what failed, why, and what the code does about it) live in `docs/notes/`, one file per area, moved there word for word from this file. **Before changing code, read the note for the area you are changing**, and `docs/notes/brain-core.md` for any brAIn change. A new lesson goes into the note for its area, never here: only a rule that applies to every change in the repository belongs in this file. Keep this file short: it is loaded on every turn.

**The notes were written when the repository had a 720-file test suite.** That suite was removed in November 2026 (see *Checks and tests* below), so a note that names `tests/test_<something>.py`, `tests/affected.py`, CI's layout job or the evals is describing history: the rule it explains still holds, the test that enforced it does not exist, and nothing asks you to bring it back.

## Project Overview

This repository contains Home Assistant add-ons by BRUH Automation:

- **brAIn** (`brain/`) - **the primary add-on.** A Claude Code terminal, an AI insights dashboard, one shared memory that learns the house over time, and (since 4.0) the Morph dashboard, merged into a single add-on behind one sidebar entry and one Claude login. The sidebar entry is the integration's custom panel, the shell (`custom_components/brain/morph/frontend/shell.js`): brAIn's ingress page in a frame under its own top bar, and Morph drawn natively as the Home tab; brAIn hides its ingress entry only while the shell's mark is fresh (`panel/shell_link.py`). Four switches in ⚙ › Features (`panel/features.py`, published to `/config/.brain/features.json`): Morph dashboard, Personality, Learning loop (self-improvement: local, nothing leaves the house) and Development loop (the devloop's `enabled`: reports go to the private repository). Supersedes BRUH Terminal, BRUH Insights and the Morph add-on. Integration domain: `brain`. Plan and reasons: `docs/design/brain-morph-merge.md`.
- **BRUH Minecraft** (`bruh-minecraft-server/`) - a Minecraft Java Edition server with an ingress management panel, git-based world version control, RCON, an add-on browser (`panel/addons.py`: Modrinth plugins, data packs, server-side mods and resource packs — server-side only, so Bedrock/iPad players get them through Geyser with nothing on the device; the server's type and version decide what is offered, downloads must come from Modrinth's CDN and match the published SHA-512, required dependencies come along and are recorded per world in `.bruh-addons.json`), and a companion `bruh_minecraft` custom integration whose services answer with the server's reply and raise on a refusal (the dropped-answer rule BRight's services already followed). On Paper and Purpur it also installs **BRUH Sight** (`sight/`, its own plugin, built in the Dockerfile's first stage). The plugin gives the panel the live world on loopback (`panel/sight.py`; every caller falls back to RCON and the region files without it) and draws the companion's thought bubble and journal book (`companion_thought`, `give_journal`; never chat).
- **BRUH Print** (`bruh-print/`) - a DYMO LabelWriter driver and label designer: a full designer in the sidebar, fill-in-the-blank templates, a one-word autofit path, Twin Turbo roll selection, and a Lovelace card. Integration domain: `bruh_print`.
- **BRight** (`bright/`) - a music-driven light show director: analyzes local music once, choreographs LIFX bulbs over the LAN plus switch-driven party lights, and keeps the show in sync with the speaker. Shows are built from *effects* a person can also build, preview and edit by hand. Integration domain: `bright`. (It shipped as "BRigt" through 0.8.4 — a typo — and the rename is a new slug, a new domain and a new `/data`.)
- **BRUH Bambu Studio** (`bruh-bambu-studio/`) - Bambu Studio (Bambu Lab's own AppImage, downloaded on first start into `/data` and EXTRACTED, never FUSE-mounted) on an Xvfb screen served in the sidebar through noVNC, with the panel bridging noVNC's websocket to a loopback-only x11vnc (`panel/vnc_bridge.py`); and Bambu Lab printers driven over LAN MQTT (8883) and implicit FTPS (990) by the panel, which is their one owner (`panel/bambu/`). Debian base and **amd64 only**, because the AppImage is glibc and x86-64. A print is a job (slice through Bambu Studio's own CLI if the file has no `Metadata/plate_N.gcode`, upload, `project_file`); access codes live in `/data/secrets` and out of backups. Integration domain: `bruh_bambu`; brAIn drives it with `bambu_status`/`bambu_print`/`bambu_control`/`bambu_slice`/`bambu_design`; voice may design a part and start a print (a file, never a url), and may not stop a print, slice, send G-code, open Bambu Studio or import a link. Everything else about it: `docs/notes/bambu.md`.
- **Morph** (`brain/morph/service/` the service, `brain/custom_components/brain/morph/` the panel half) - part of brAIn since 4.0 (it was an add-on with its own `morph` integration until then; brAIn's run.sh stops that app, never uninstalls it, and deletes its integration). A custom dashboard from the MORPH UI design (`docs/design/morph-ui.md`), and brAIn's face (`docs/design/morph-vision.md`): the page is laid out by what matters in the house right now and says why, brAIn's cases are drawn in the room they are about with a reply line, To Do is a section, and Ask is brAIn's chat. Cards open in place while everything else makes room, any Lovelace card can be hosted, and brAIn designs, edits and manages it: in Edit, hold anything and **Tell brAIn**. The dashboard is a git repository at `/config/morph`, and Morph learns from how it is used (the Learning loop switch). Its settings are brAIn's ⚙ › Dashboard. The websocket command names (`morph/*`) and the static paths are unchanged; its `hass.data` key is `brain_morph`. **Since 5.0 Morph is also a layer on Home Assistant's own dashboards** (`docs/design/morph-on-lovelace.md`): its cards are Lovelace custom cards with HA's visual editor (`custom:morph-<kind>-card`), brAIn builds card types once (`custom:morph-type-<slug>`, `/config/morph/types`), a dashboard an admin lets brAIn change is kept in git as `/config/morph/dashboards/<key>.yaml` and saved to HA live, the brAIn button on a dashboard takes a Tell about any card, `custom:morph-view` is Morph's layout as a view type, and Morph's themes are HA themes; all of it loads on every HA page through `frontend/morph-ha.js`.
- **GardenRX** (`gardenrx/`) - a spray decision engine for a home orchard and garden: the GardenRX Next.js app (`gardenrx/app`, copied from brusc/GardenRX and now independent of it) in the sidebar through ingress, with its data in a SQLite file in `/data` instead of Supabase. The screens were left as built: `src/lib/db/` is the subset of supabase-js they called (select/insert/update/upsert/delete, the filters, order, limit, single), executed in-process by `sqlite.ts` on the server and POSTed to `/api/db` from the browser, every table and column checked against `schema.ts` and every value bound. Node's built-in `node:sqlite` (loaded with `process.getBuiltinModule`, so no native module and nothing for Turbopack to resolve). The product/label catalog ships as `app/seed/catalog.json` and is only ever INSERT OR IGNOREd. The ingress path is per install, so the image is built with `basePath` set to a placeholder and `gateway/prepare-base.mjs` writes this install's path over it at start; `gateway/gateway.mjs` puts the prefix the Supervisor strips back on and proxies to Next on loopback. A raw `fetch`/`<a href>`/`<img src>` needs `withBase` (`src/lib/base-path.ts`); `<Link>` and the router add it themselves. The `gardenrx` integration polls `/api/ha/summary` and calls `/api/ha/action` with a bearer token from `/config/.gardenrx/api_token`; it serves `gardenrx-cards.js` itself (`add_extra_js_url`, no `/local`) and run.sh copies it to `/config/morph/cards`. Integration domain: `gardenrx`.
- **BRUH Task Manager** (`bruh-task-manager/`) - Task Manager for Home Assistant OS: CPU, memory, network and disk per app from the Supervisor's stats (Level 1, always on), every process on the machine grouped by the app it belongs to (Level 2, off until the user switches it on AND turns Protection mode off), Restart/Stop/Start through the Supervisor, End process for processes inside apps only (a third switch, off by default), and a runaway-app binary sensor. Integration domain: `bruh_task_manager`. Experimental.
- **BRUH Cooking** (`bruh-cooking/`) - Breville+ and Sage cooking appliances (Joule sous vide, Joule Turbo, Joule Oven Air Fryer Pro) over Breville's cloud: kedube/ha-breville-cooking's integration and Lit panel, renamed to the `bruh_cooking` domain (GPL-3.0, so the directory carries its own LICENSE). The add-on is a script: it **refuses to start without brAIn**, deploys the integration, announces it, and watches. brAIn drives it with `cooking_status`/`cooking_control` over the integration's name-addressed services (`services.py`). The integration and panel keep their own suites (`bruh-cooking/tests` against a real Home Assistant on Python 3.13; vitest), run by CI's cooking job. Integration domain: `bruh_cooking`. Experimental. Everything else: `docs/notes/cooking.md`.
- **BRUH Browser** (`bruh-browser/`) - brAIn's hands on the web: Google Chrome with the Claude in Chrome extension on an Xvfb screen in the sidebar (Bambu's noVNC pattern), running one errand at a time for brAIn as `claude --chrome -p` (`panel/runner.py` is the seam). Requires brAIn; amd64 only; no integration (brAIn calls its API with the token in `/config/.bruh_browser/api_token`). A purchase is always a second errand after a cart a person heard and approved. Experimental. Everything else: `docs/notes/browser.md`.

BRUH Terminal (`bruh-claude-terminal/`), BRUH Insights (`bruh-insights/`) and the Morph add-on (`morph/`) were removed in favour of brAIn; the notes in `docs/notes/` describe the internals brAIn inherited from them.

## Container Environment
- Base: Home Assistant Alpine Linux 3.24 (Dockerfile `ARG BUILD_FROM` default; `build.yaml` only applies to Supervisor < 2026.04)

- Config: `/data/.config/claude`

### Checks and tests
- **One command, about ten seconds: `python3 .github/scripts/check.py --base origin/main`.** It is everything CI's `Checks` job runs: ruff, a syntax check of every panel script and shell script, every manifest parsed and its versions agreeing, the version bump, and the suite in `tests/`. Run it before every push. CI adds only hassfest and the AppArmor parser, which need tools a session does not have. CodeQL runs weekly and Dependabot monthly; neither gates a pull request.
- **`tests/` holds only what must never break, and it stays that small.** The action gate, protected entities, the tripwire, house rules, camera policy, the service gates, voice's limits, redaction of everything that leaves the house, the Minecraft add-on download hashes, and the development loop's own gates. About 240 tests in about six seconds. Everything else that used to be there was deleted on purpose: it was as large as the product, a third of it asserted that strings were present in source files, and it made every change slower without making a release safer.
- **Do not add a test for an ordinary change.** Read the code, make the change, run the check, and look at the result where it can be looked at (a demo panel in `tests/manual/`, a screenshot, the script's own output). Add or change a test only when the change touches one of the areas above, or when a failure would be silent and would hurt a house (an action taken that was refused, a secret sent out, a file lost). A test must drive behaviour; never assert on the text of a source file, and never sleep or reach the network. If the whole suite ever takes more than fifteen seconds, something is wrong with what was added.
- **`python3 -m pytest`, never bare `pytest`.** In a Claude Code cloud session the `pytest` on PATH is an isolated install that cannot see the dependencies. `.claude/settings.json`'s SessionStart hook installs `tests/requirements-dev.txt`. Local Python there is 3.13 and CI is 3.11: a syntax only the newer one accepts passes locally and fails CI.
- **`tests/manual/` and `tests/realha/` are hand tools, not gates.** The `measure-*.mjs` scripts, the demo panels and the screenshot scripts run in no workflow. Use one when it helps you see a UI change; delete one that has drifted rather than repair it for its own sake. `tests/corpus/` is product data (houses contributed through the development loop) and `replay.yml` scores it on demand.

### File Conventions
- Shell scripts: `#!/usr/bin/with-contenv bashio` for HA scripts, `#!/bin/bash` for standalone
- CHANGELOG entries: under each `## x.y.z`, group the lines under `### Added`, `### Changed`, `### Removed`, `### Fixed` and `### Security` ([Keep a Changelog](https://keepachangelog.com) order, empty ones left out), so a release can be scanned by kind
- YAML: 2-space indentation
- Shell: 4-space indentation
- Error handling: `bashio::log.error` for HA scripts, colored output for user-facing tools
- **Three add-ons ship an `atomic_write.py`, so patch the copy the module you are fixing actually imports.** `brain/panel/`, `bruh-print/panel/` and `bright/panel/` each hold one — deliberately, because a panel is a self-contained image and there is no shared package to import from — and they are near-identical, which is what makes a grep for a function name answer with three files and a patch land in whichever came first. The panels never import across add-ons, so a fix applied to one is a fix that reached one add-on; the failing test names its own add-on's path, and that path is the answer to which file to open. BRUH Bambu Studio's copy is `bambu_atomic.py`: under one name CodeQL matched other add-ons' callers to it and reported their modes and paths against it.
- **A `python3 -c '…'` in a shell script cannot hold a `"` inside an f-string expression**: the backslash it needs is a SyntaxError before Python 3.12, so it runs on the image and nowhere else. Use a heredoc. A heredoc IS stdin, so the payload becomes an argument, and a payload over 128 KB goes through a temporary file named as that argument, never an argument or an environment variable.

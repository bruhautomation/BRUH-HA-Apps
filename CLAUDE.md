# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

**This file is loaded into every session and every subagent, on every turn, so it stays short.** It holds the project overview, the rules every change needs, and a map of the notes. The long notes (what failed, why, and what the code does about it) live in `docs/notes/`, one file per area, moved there word for word from this file. **Before changing code, read the note for the area you are changing**, and `docs/notes/brain-core.md` for any brAIn change. A new lesson goes into the note for its area, never here: only a rule that applies to every change in the repository belongs in this file. `tests/test_claude_md_index.py` holds this file under 40 KB and checks that every note is listed below and every listed note exists.

## Project Overview

This repository contains Home Assistant add-ons by BRUH Automation:

- **brAIn** (`brain/`) - **the primary add-on.** A Claude Code terminal, an AI insights dashboard, one shared memory that learns the house over time, and (since 4.0) the Morph dashboard, merged into a single add-on behind one sidebar entry and one Claude login. The sidebar entry is the integration's custom panel, the shell (`custom_components/brain/morph/frontend/shell.js`): brAIn's ingress page in a frame under its own top bar, and Morph drawn natively as the Home tab; brAIn hides its ingress entry only while the shell's mark is fresh (`panel/shell_link.py`). Four switches in ⚙ › Features (`panel/features.py`, published to `/config/.brain/features.json`): Morph dashboard, Personality, Learning loop (self-improvement: local, nothing leaves the house) and Development loop (the devloop's `enabled`: reports go to the private repository). Supersedes BRUH Terminal, BRUH Insights and the Morph add-on. Integration domain: `brain`. Plan and reasons: `docs/design/brain-morph-merge.md`.
- **BRUH Minecraft** (`bruh-minecraft-server/`) - a Minecraft Java Edition server with an ingress management panel, git-based world version control, RCON, an add-on browser (`panel/addons.py`: Modrinth plugins, data packs, server-side mods and resource packs — server-side only, so Bedrock/iPad players get them through Geyser with nothing on the device; the server's type and version decide what is offered, downloads must come from Modrinth's CDN and match the published SHA-512, required dependencies come along and are recorded per world in `.bruh-addons.json`), and a companion `bruh_minecraft` custom integration whose services answer with the server's reply and raise on a refusal (the dropped-answer rule BRight's services already followed).
- **BRUH Print** (`bruh-print/`) - a DYMO LabelWriter driver and label designer: a full designer in the sidebar, fill-in-the-blank templates, a one-word autofit path, Twin Turbo roll selection, and a Lovelace card. Integration domain: `bruh_print`.
- **BRight** (`bright/`) - a music-driven light show director: analyzes local music once, choreographs LIFX bulbs over the LAN plus switch-driven party lights, and keeps the show in sync with the speaker. Shows are built from *effects* a person can also build, preview and edit by hand. Integration domain: `bright`. (It shipped as "BRigt" through 0.8.4 — a typo — and the rename is a new slug, a new domain and a new `/data`.)
- **BRUH Bambu Studio** (`bruh-bambu-studio/`) - Bambu Studio (Bambu Lab's own AppImage, downloaded on first start into `/data` and EXTRACTED, never FUSE-mounted) on an Xvfb screen served in the sidebar through noVNC, with the panel bridging noVNC's websocket to a loopback-only x11vnc (`panel/vnc_bridge.py`); and Bambu Lab printers driven over LAN MQTT (8883) and implicit FTPS (990) by the panel, which is their one owner (`panel/bambu/`). Debian base and **amd64 only**, because the AppImage is glibc and x86-64. A print is a job (slice through Bambu Studio's own CLI if the file has no `Metadata/plate_N.gcode`, upload, `project_file`); access codes live in `/data/secrets` and out of backups. Integration domain: `bruh_bambu`; brAIn drives it with `bambu_status`/`bambu_print`/`bambu_control`/`bambu_slice`/`bambu_design`; voice may design a part and start a print (a file, never a url), and may not stop a print, slice, send G-code, open Bambu Studio or import a link. Everything else about it: `docs/notes/bambu.md`.
- **Morph** (`brain/morph/service/` the service, `brain/custom_components/brain/morph/` the panel half) - part of brAIn since 4.0 (it was an add-on with its own `morph` integration until then; brAIn's run.sh stops that app, never uninstalls it, and deletes its integration). A custom dashboard from the MORPH UI design (`docs/design/morph-ui.md`), and brAIn's face (`docs/design/morph-vision.md`): the page is laid out by what matters in the house right now and says why, brAIn's cases are drawn in the room they are about with a reply line, To Do is a section, and Ask is brAIn's chat. Cards open in place while everything else makes room, any Lovelace card can be hosted, and brAIn designs, edits and manages it: in Edit, hold anything and **Tell brAIn**. The dashboard is a git repository at `/config/morph`, and Morph learns from how it is used (the Learning loop switch). Its settings are brAIn's ⚙ › Dashboard. The websocket command names (`morph/*`) and the static paths are unchanged; its `hass.data` key is `brain_morph`.
- **GardenRX** (`gardenrx/`) - a spray decision engine for a home orchard and garden: the GardenRX Next.js app (`gardenrx/app`, copied from brusc/GardenRX and now independent of it) in the sidebar through ingress, with its data in a SQLite file in `/data` instead of Supabase. The screens were left as built: `src/lib/db/` is the subset of supabase-js they called (select/insert/update/upsert/delete, the filters, order, limit, single), executed in-process by `sqlite.ts` on the server and POSTed to `/api/db` from the browser, every table and column checked against `schema.ts` and every value bound. Node's built-in `node:sqlite` (loaded with `process.getBuiltinModule`, so no native module and nothing for Turbopack to resolve). The product/label catalog ships as `app/seed/catalog.json` and is only ever INSERT OR IGNOREd. The ingress path is per install, so the image is built with `basePath` set to a placeholder and `gateway/prepare-base.mjs` writes this install's path over it at start; `gateway/gateway.mjs` puts the prefix the Supervisor strips back on and proxies to Next on loopback. A raw `fetch`/`<a href>`/`<img src>` needs `withBase` (`src/lib/base-path.ts`); `<Link>` and the router add it themselves. The `gardenrx` integration polls `/api/ha/summary` and calls `/api/ha/action` with a bearer token from `/config/.gardenrx/api_token`; it serves `gardenrx-cards.js` itself (`add_extra_js_url`, no `/local`) and run.sh copies it to `/config/morph/cards`. Integration domain: `gardenrx`.
- **BRUH Task Manager** (`bruh-task-manager/`) - Task Manager for Home Assistant OS: CPU, memory, network and disk per app from the Supervisor's stats (Level 1, always on), every process on the machine grouped by the app it belongs to (Level 2, off until the user switches it on AND turns Protection mode off), Restart/Stop/Start through the Supervisor, End process for processes inside apps only (a third switch, off by default), and a runaway-app binary sensor. Integration domain: `bruh_task_manager`. Experimental.
- **BRUH Cooking** (`bruh-cooking/`) - Breville+ and Sage cooking appliances (Joule sous vide, Joule Turbo, Joule Oven Air Fryer Pro) over Breville's cloud: kedube/ha-breville-cooking's integration and Lit panel, renamed to the `bruh_cooking` domain (GPL-3.0, so the directory carries its own LICENSE). The add-on is a script: it **refuses to start without brAIn**, deploys the integration, announces it, and watches. brAIn drives it with `cooking_status`/`cooking_control` over the integration's name-addressed services (`services.py`). The integration and panel keep their own suites (`bruh-cooking/tests` against a real Home Assistant on Python 3.13; vitest), run by CI's cooking job. Integration domain: `bruh_cooking`. Experimental. Everything else: `docs/notes/cooking.md`.

BRUH Terminal (`bruh-claude-terminal/`), BRUH Insights (`bruh-insights/`) and the Morph add-on (`morph/`) were removed in favour of brAIn; the notes in `docs/notes/` describe the internals brAIn inherited from them.

### Running the tests
- **`python3 -m pytest`, never bare `pytest`.** In a Claude Code cloud session the `pytest` on PATH is a uv-isolated tool install that cannot see the pip-installed dependencies, so it fails collection on 57 files with import errors that look like the code is broken; `python3 -m pytest` runs the interpreter the dependencies went into. `.claude/settings.json`'s SessionStart hook installs `tests/requirements-dev.txt` at the start of a cloud session, quietly and never failing it, so the first run collects. Local Python there is 3.13 and CI is 3.11 — a syntax only the newer one accepts passes locally and fails CI.
- **The whole suite in parallel is `python3 -m pytest tests -q -n 4 --dist loadfile`, and it is a minute and forty seconds.** Serial it is 6m15s of wall clock for 2m10s of CPU (281 files, 8,597 tests, measured 2026-10-08): two thirds of the run is sleeping or waiting on subprocesses, which is time four workers overlap rather than share. `loadfile` keeps a file's tests on one worker because a test class's `setUp`, a module-level server and the `sys.modules` juggling several files do (the `brain_ha_env` loader, the popped and re-imported panel modules) are per-file state, and spreading one file across workers turns that into an ordering nobody wrote down. CI runs it this way; so does anybody running it all.
- **During development run what the change can break, not everything** (`python3 tests/affected.py`). It maps the changed paths — `--base origin/main` for a branch, which is the default — to the test files that could notice, says on stderr which rule placed each path, `--run` runs them under xdist, and `--measures` prints the `tests/manual/measure-*.mjs` scripts the same change reaches (they are run by hand; `--run` is pytest only). Shared test infrastructure (`conftest.py`, the fakes, the `*_env.py` loaders, the corpus, `pytest.ini`, the requirements) and any code change no rule can place select the whole suite, because a selection that silently missed is a green tick over a break and a slow run is a cost somebody sees. The whole suite is CI's job, and on a pull request CI skips only the own tests of a sibling add-on the PR does not touch.
- **`-m "not slow"` is the fast local run.** `slow` marks the tests that spawn a subprocess, stand up a real server or hold a lock — the ones that are the waiting in the measurement above. Skipping them is a way to iterate, never a pass: CI runs them, and a test that does one of those things and is not marked is a mark worth adding rather than a reason to stop using the filter.
- **An agent's Bash tool kills a command at two minutes by default, and says nothing useful when it does.** A plain `python3 -m pytest tests -q` is killed at 120s with no result — which is what "stuff seems to time out" in the development loop was — and the serial suite needs three times that. Anything that can run past two minutes is run with the tool's `timeout` raised (in milliseconds, up to ten minutes) or with `run_in_background`, and the parallel suite gets the raised timeout too, because 1m41s on a quiet machine is not 1m41s on a loaded one.
- **A hang is a test, and the timeout names it.** `pytest-timeout` fails any single test past 60s with its name and a traceback of where it was waiting, where a hang used to be a run that never ended and a tool that killed it without saying which test. `tests/conftest.py` already records the commonest cause — a route that reaches a real `claude` CLI in a cloud session, where one exists, turned third-of-a-second presses into 87s waits — so a new hang is first a question of what it spawned.

### File Conventions
- Shell scripts: `#!/usr/bin/with-contenv bashio` for HA scripts, `#!/bin/bash` for standalone
- CHANGELOG entries: under each `## x.y.z`, group the lines under `### Added`, `### Changed`, `### Removed`, `### Fixed` and `### Security` ([Keep a Changelog](https://keepachangelog.com) order, empty ones left out), so a release can be scanned by kind
- YAML: 2-space indentation
- Shell: 4-space indentation
- Error handling: `bashio::log.error` for HA scripts, colored output for user-facing tools
- **A name bound inside a `try` whose `except` skips or returns is still a name every line after it has to prove is set**, and CodeQL says so (`py/uninitialized-local-variable`) — twice now, on `tokyo` in `test_baselines.py` and `ny` in `test_notify_router.py`, both the same optional-`zoneinfo` guard written the same way. Bind it to `None` *before* the `try` and test it *after*; `self.skipTest` from inside the handler reads like a `return` and is not one the analyser can see. Same class as reaching for a file without `with`: `open(...).read()` in a test is a leaked descriptor whether or not the test passes
- **Three add-ons ship an `atomic_write.py`, so patch the copy the module you are fixing actually imports.** `brain/panel/`, `bruh-print/panel/` and `bright/panel/` each hold one — deliberately, because a panel is a self-contained image and there is no shared package to import from — and they are near-identical, which is what makes a grep for a function name answer with three files and a patch land in whichever came first. The panels never import across add-ons, so a fix applied to one is a fix that reached one add-on; the failing test names its own add-on's path, and that path is the answer to which file to open. BRUH Bambu Studio's copy is `bambu_atomic.py`: under one name CodeQL matched other add-ons' callers to it and reported their modes and paths against it.
- **The FIRST `@media (pointer: coarse)` block in `panel/style.css` is the 16px text floor, and a new coarse block must not precede it.** `test_no_form_control_can_trigger_the_ios_zoom_trap` splits the stylesheet on that string and reads the first block it finds, so a coarse block added *above* it — a touch target, a chip height, anything — silently moves the test onto a block that was never about zooming, where it asserts `input[type="text"]` and `font-size: 16px` against rules that do not mention either and fails for a reason that has nothing to do with the change. The floor block stays first; anything else that needs `pointer: coarse` goes after it, and the ordering rule is the same one that keeps `.btn.tiny`'s touch height last in BRUH Print's stylesheet — position is load-bearing rather than tidy in both files, for two different reasons.
- **A `python3 -c '…'` in a shell script cannot hold a `"` inside an f-string expression, and the workaround is a SyntaxError.** Shell single quotes leave a backslash as the only way to escape one, and a backslash in an f-string *expression* is a `SyntaxError` before Python 3.12 — so a block written that way parses on the image (Alpine's 3.12) and nowhere else, including every developer machine and CI. It shipped in `brain-doctor-deep.sh`, `brain-check.sh` and `brain-weekly.sh`: five commands that printed a traceback everywhere but production, unnoticed because nothing had ever run them. The fix is a heredoc, and it costs one more thing to get right: **a heredoc IS stdin**, so the payload has to become an *argument* rather than something piped in — a pipe into one arrives empty, which reads as "no stages yet" or "an empty week" rather than as an error. **And an argument or an environment variable is not a channel for a payload**: the kernel caps one string at 128 KB, so `brain findings` handed its list to the printer through `BRAIN_FINDINGS_JSON` and died with "Argument list too long" past a few hundred findings; the payload goes through a temporary file named as the heredoc's argument (`tests/test_brain_findings_cli_size.py`). `tests/test_doctor_deep.py::TestTheCliReportBlocks` and `tests/test_cli_report_blocks.py` lift every block out of the real scripts and drive them, the way `test_doctor_json` drives `ha-selftest.sh`'s, with two greps beside them so neither shape can come back — a grep on purpose, because "this pattern is absent" is the one claim a grep can honestly make.
- **A test that proves a negative by sleeping spends the whole sleep on every run, and an exact-second wall-clock assertion is a test of how busy the machine is.** `test_memory_extract`'s `settle(3.0)` slept three seconds to show a child had written nothing, and with its callers that was 40s of the suite proving an absence — while a child that wrote late, after the sleep, passed it anyway. Wait on the observable event the code under test produces (the file, the ledger line, the exit of the process) with a deadline, and for an absence wait on the event that means it is over — the child exiting — before reading that nothing was written. The same budget makes a duration or a timestamp asserted to the exact second flake under four xdist workers and a loaded CI runner: assert a bound, or inject the clock.

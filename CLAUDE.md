# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## Project Overview

This repository contains Home Assistant add-ons by BRUH Automation:

- **brAIn** (`brain/`) - **the primary add-on.** A Claude Code terminal, an AI insights dashboard, and one shared memory that learns the house over time, merged into a single add-on behind one ingress panel and one Claude login. Supersedes BRUH Terminal and BRUH Insights. Integration domain: `brain`.
- **BRUH Minecraft** (`bruh-minecraft-server/`) - a Minecraft Java Edition server with an ingress management panel, git-based world version control, RCON, and a companion `bruh_minecraft` custom integration.
- **BRUH Print** (`bruh-print/`) - a DYMO LabelWriter driver and label designer: a full designer in the sidebar, fill-in-the-blank templates, a one-word autofit path, Twin Turbo roll selection, and a Lovelace card. Integration domain: `bruh_print`.
- **BRight** (`bright/`) - a music-driven light show director: analyzes local music once, choreographs LIFX bulbs over the LAN plus switch-driven party lights, and keeps the show in sync with the speaker. Shows are built from *effects* a person can also build, preview and edit by hand. Integration domain: `bright`. (It shipped as "BRigt" through 0.8.4 — a typo — and the rename is a new slug, a new domain and a new `/data`.)

BRUH Terminal (`bruh-claude-terminal/`) and BRUH Insights (`bruh-insights/`) were removed in favour of brAIn; the architecture notes below describe the internals brAIn inherited from them.

### brAIn specifics

- One ingress port (8099, the panel). The panel reverse-proxies `/terminal/` through to ttyd on 7681 (`brain/panel/terminal_proxy.py`), so the terminal is a tab. The assist worker pool's internal API moved to **8098** to free 8099.
- **Ingress authenticates its own callers and nobody else's.** A port is either published or it is not, and a published one answers the LAN with no Home Assistant login in front of it — which is what [GHSA-gh5m-4m97-c95h](https://github.com/home-assistant/core/security/advisories/GHSA-gh5m-4m97-c95h) was about. brAIn shipped 7681 published with ttyd on `--writable` and no `--credential`: a root shell with `/config` and a signed-in Claude, for anything on the network. It is `null` in `ports:` now (declared, so the Network panel can still assign it) **and** ttyd always takes a generated `--credential` from `/data/terminal-credential`, which `terminal_proxy` presents upstream so ingress users never meet a prompt. The proxy **drops the client's `Authorization` header before adding its own** — otherwise a browser holding a credential for the ingress origin could present it to ttyd instead — and strips `WWW-Authenticate` on the way back, because a Basic-auth dialog inside the ingress iframe asks for a password the user has never been shown. **That drop has to case-fold, and for a long time it did not**: it was `headers.pop("Authorization")` plus `headers.pop("authorization")` over a plain dict that `_clean` keys by whatever case the client sent — and HTTP considers every spelling of a header name identical, so `AUTHORIZATION: Basic …` survived both pops and rode upstream *beside* the credential added on the next line, leaving ttyd to pick. It is `HOP_BY_HOP | CLIENT_DROPPED` now, filtered by the same lower-cased pass the hop-by-hop headers already got. The test that was supposed to hold this asserted the source contained that literal `pop` line, and passed for the whole life of the bug: **a grep for a line is not a test of what the line does**, which is why `tests/test_terminal_proxy.py` drives the function with five spellings and stands the bridge up against a real aiohttp server speaking ttyd's handshake. BRUH Minecraft has the same shape and a worse case: `host_network: true` (Bedrock LAN discovery needs it) put its `0.0.0.0:8099` management API — arbitrary RCON, world delete, restore — directly on the LAN, so `panel/server.py`'s `_lan_gate` middleware now allows only the Supervisor's networks and loopback. It reads the **socket's peer address**, never `X-Forwarded-For`, which a direct caller sets themselves; `/pack/` and `/api/health` are the only public prefixes, and `_peer_ip` returns `None` for anything that is not an `(host, port)` tuple so a unix-socket peer refuses instead of matching on `peer[0]`'s first character. Both add-ons ship `apparmor.txt` (profile name = slug, or the Supervisor won't load it) denying the host-escape set; Minecraft's needs `ixm`, not `ix`, or the JIT cannot map executable memory and Java never starts. Both rate **6/6** — `tests/test_addon_hardening.py` recomputes the Supervisor's arithmetic so a regression shows up there rather than in the store weeks later.
- **Every option needs a line in `translations/en.yaml`, or the UI shows the raw key.** `config.yaml`'s inline comments are for whoever edits `config.yaml`; they are not documentation, because nobody installing an add-on reads them. `test_addon_hardening` fails on an option with no entry, an entry with no option, and an entry missing a name or description — the drift is otherwise invisible.
- **`backup_exclude` is where credentials go to not be in a backup.** HA backups are unencrypted unless the user opts in, then get copied to cloud storage and support tickets. Paths are relative to `/data`.
- `enable_terminal` / `enable_insights` switch either face off; the panel always runs because it is the ingress target.
- **No git auto-backup.** It was removed along with `auto_backup` / `backup_interval_minutes`. In its place, a `PreToolUse` hook (`scripts/brain-edit-snapshot.py`) snapshots files before Claude edits them, and `brain undo` restores them. Never touch a user's existing `/config/.git`.
- **Two CLI dispatchers**, not fourteen scripts: `brain` (memory, findings, learn, ask, undo, doctor) and `ha` (log, reload, entity, service, addon, notify, share, check, context). Both delegate to `/opt/scripts`. Adding a command = a script plus one dispatcher line — and the chat palette parses `brain help`/`ha help`, so the usage text IS the announcement. `brain findings` goes through the panel's API on 8099, never the store files: a second writer would race the panel's own, and the API is what writes the memory line, the settled key and the undo token an ending owes.
- **Memory**: `memory.md` is the only thing that is "memory". The inbox, the hypothesis queue, and the change log are queues and audit trails, and are never injected into prompts. Every writer goes through the inbox — nothing writes `memory.md` except the consolidator. The Memory tab's "File into memory now" runs the same consolidator with `--once`; it does not become a second writer. **The facts ledger (`knowledge_store`) is a dedup index, not a queue** — nothing may be deleted from it, or the analyst re-announces what you have already seen, and it is emphatically not what the Memory tab lists (the tab reads the inbox itself — `server._inbox_items`; see the bullet on the queue's list and its count). **Filed discoveries are not rendered anywhere** — once something is in the document, the document is the one place it is read and edited; listing them again under "already in memory" left a permanent list beside a queue that was meant to read as empty. The ledger still holds them, so nothing is re-announced. Never report a consolidation by the count you asked it to file; read the queue either side of it (a pass can exit 0 and keep the facts, and exit 75 when another pass holds the lock).
- **A lock file's existence is not a lock, and its mtime is not an age.** `with_lock` takes `/config/.brain/memory/.consolidate.lock` with `exec 9>` and releases it with `exec 9>&-` — which drops the flock and leaves the file on disk for good, so the file says only that a pass has run at some point and its mtime says when the last one *started*. `ha-selftest.sh` (`brain doctor`) stat-ed that mtime and warned past 900s, which fires on every home that has not consolidated in the last quarter of an hour: a permanent warning about a memory system that was working, on a report whose whole value is that its lines mean something. The remedy it named could not clear it either — the file is under `/config` and survives the restart it asked for. The panel had it right from the start (`_consolidation_running()`): probe the flock, **shared** so that asking can never be something a real pass blocks on, and **`9<` never `9>`**, because `>` truncates the holder's file at open. Probe whether flock works *here* before reading a refusal as contention — BusyBox answers an unsupported flag with the same exit status as "the lock is held", which is the bug that once stopped memory updating at all. What is left is a warning worth acting on: an flock dies with its process, so a lock still held past any plausible pass is a live process genuinely stuck. The honest version of the question the old check was asking belongs to the queue, not the file — facts queued past 26h with nothing filing them, the same threshold `_consolidation_stale_hours` uses. And the test that was supposed to hold this asserted the *script* rather than driving it, so `tests/test_memory_learning.py` lifts `consolidator_lock_check` out of the real file, runs the old recipe on the same fixture to show it warning, and holds a real flock from a subprocess for the cases that must still warn.
- **A guard that refuses has to change the next attempt, or it is a loop.** The size check (`memory_max_kb`, 32 KB) rejected an over-cap document and returned, so the daemon re-ran the identical prompt every 5 minutes and got the identical answer — while the queue grew, asking each attempt to fit *more* into a document already full. An overshoot now feeds the measured excess back to the model and only the second one fails, with a message naming the setting that ends it. The proportional shrink guard is skipped on that retry: it exists to catch a rewrite pretending to be a merge, and a pass we explicitly told to drop facts is neither. **The cap is not a latency setting** — voice reads the 2 KB `voice.md` on every request and never the document, so shrinking memory.md buys nothing where speed is felt. In the insight bundle memory has its own budget (`MEMORY_CHARS`), not a share of `CONTEXT_CHARS`: they used to split 4 KB with memory first, which truncated any real document mid-fact *and* starved the house context whenever memory filled it.
- **A consolidation pass rewrites a whole document, and is budgeted like one.** It is a single turn producing memory.md *plus* voice.md — up to 10 KB — so its Claude timeout is 480s, the same as an insight run. At 120s it was a coin flip on a full document, and every loss reported itself as `Claude invocation failed (not authenticated?)` because stderr went to `/dev/null` and the exit code was never read: the queue never moved, the button never worked, and the log sent people to redo a working sign-in. **Never swallow stderr on a pass that can fail for more than one reason** — 124 is `timeout`'s and says so by name; anything else carries the CLI's own last line. The panel's "File into memory now" **starts** a pass and does not await it (`_consolidate_task`), because a request cannot outlive a minutes-long pass; the outcome is read back from `/api/memory/state`, which is a flag, not the 19 KB knowledge payload the tab used to poll every 2.5s.
- **Who ran a conversation is a contract, not a guess** (`panel/run_sources.py` + `scripts/brain-run-source.sh`). Claude Code files every conversation under its working directory and records nothing about who asked; voice, the automation listener, study sessions and the consolidator all drive it from `/config`, so the Chats rail was the person's own chats buried under machine ones — and `adopt` (which takes "the most recently written conversation") routinely picked up the consolidator's. Each background caller **claims its own session id before running**; an unclaimed id is yours, so the default costs no inference and cannot drift when a prompt is reworded. Claim it by whatever route that caller already has: `--session-id` for the consolidator, study, and `engine._run_cli` (each with a fallback for a CLI that rejects the flag — the label is optional, the run is not), the uuid voice already mints, the `session_id` in `--output-format json` for automation tasks, the stream's own `session_id` in the worker pool. Filtering happens in `conversations.listing`, not the panel, or a page of 30 is spent on voice turns. Insight and fix runs (`card`/`fix`, `store: "engine"` in `SOURCES`) live in a different project directory because `engine` runs them from `CLAUDE_HOME` — the server lists that store for their chips and marks the rows `view_only`: they replay into a reader (`/api/chat/conversation/{id}/view`) and are never resumed, since their turns ran under the analyst's or fixer's scoping and the chat's permissions are a different contract. An unclaimed id in the engine's directory belongs to nobody (the auth self-check) and is dropped, not defaulted. The ledger is an index, not a queue: capped, never drained. **Both halves write the same file as different users** — the panel is root, the consolidator and study watcher are `su-exec claude` — so `run.sh` creates `/data/run-sources.jsonl` claude-owned before either starts; root can write a claude-owned file, not the reverse, and the failure is silent by design, which is how it went unnoticed. Silence means the shell's message too: `cmd >> file 2>/dev/null` hides the command's stderr, not the shell's own "cannot open", so every redirect in that library is wrapped in `{ }`.
- **A credential that is shaped right is not a credential that works, and the two orders differ on purpose.** `engine.get_auth` (the chat) reads the panel's store first and the CLI's own `.credentials.json` last; `brain-auth-env.sh` (the terminal) reads the CLI's file *first*, because a `claude /login` done in that terminal is the most recent thing the person did there and an older pasted token must not override it. That inversion is correct and deliberate — what was not is deciding the CLI's file was usable with `startswith("sk-ant-")`, which tests the shape and not the life. An expired token passes that test, so the terminal deferred to a dead credential, exported nothing, and prompted for a login while a working one sat unread two branches below; the tracker walked the same order into a 401; only the chat, with the opposite order, kept working. **Every reader checks `expiresAt` now** — `brain-auth-env.sh`, `usage-limits-tracker.py`, `engine._cli_credentials_present`, and the `run.sh` backup restore, which discards an expired backup rather than resurrecting it. That last one is why the failure could not clear: `.credentials.json` is restored from `/data/.brain_auth_backup` whenever it goes missing, so deleting the dead token brought it back every boot. A missing or zero `expiresAt` means the file records none, not that the token is past it. **And a 401 ends that credential, not the search** — the tracker tries each store in turn, because "found a token" and "found a token that works" are different claims and only the second matters.
- **There are three credential stores, and anything that authenticates has to read all three.** A sign-in lands in Claude Code's own `.credentials.json`, in the panel's `/data/secrets/claude_auth.json`, or in the `/config/.brain/secrets/claude_auth.json` that `ha login` shares — `engine.get_auth` and `brain-auth-env.sh` both walk that list in that order, and so must anything else. `usage-limits-tracker.py` read only the first and reported `no_oauth_token` while the terminal, the listeners and the fixer all ran happily off a panel login: four sensors saying "not authenticated" about the one thing that wasn't wrong. It runs as **root**, not `su-exec claude`, because two of those three stores are root-owned `0700` directories — running it as `claude` is what limited it to the one store it could read, and the alternative is opening up the files that hold the token. An API key is not a failed OAuth login: it bills per token, has no subscription window, and gets its own status (`api_key_has_no_usage_limits`) rather than being reported as a missing sign-in. **A sensor that goes unavailable has to leave something behind that says why** — HA hides the attributes of an unavailable entity, so the reason went with it; the `Usage tracker` diagnostic sensor never goes unavailable because its whole job is to be readable when the other four are not. Readings expire after two hours (the window `usage_store` already applied to the same file), and a single failed poll leaves a fresh reading alone to age out rather than blanking four working sensors.
- **A credential reachable by four paths is still one credential, and a retry loop cannot tell.** `usage-limits-tracker.py` retries the next store on a 401 — right, because a dead token must not speak for a live one — but `oauth_tokens` yielded a token per *path*, and the paths collide by construction: `run.sh` exports `CLAUDE_CONFIG_DIR` as `$BRAIN_HOME/.claude`, making the first two `CREDENTIAL_PATHS` the **same string**, and symlinks `$BRAIN_HOME/.config/claude` onto `/data/.config/claude`, making the other two the same file. One sign-in, four identical requests, and with the panel and `ha login` stores usually holding that same token, six per poll — every 120s, with no pause between them. `/api/oauth/usage` is undocumented and rate-limited far harder than anything else brAIn touches, and a token hammered on it starts answering **429 with quota to spare** and keeps doing so long after the window that supposedly caused it ([#31021](https://github.com/anthropics/claude-code/issues/31021), [#30930](https://github.com/anthropics/claude-code/issues/30930), [#31637](https://github.com/anthropics/claude-code/issues/31637)) — which reads, from the sensors, as a usage cap nobody hit. Paths are collapsed by `realpath` and credentials by value — it was a SHA-256 digest first, on the instinct that a set of live tokens is a copy of the secret, and **it is not**: a Python string enters a set by reference, so the digest bought no fewer copies than the token does and cost a hash of a credential for it. CodeQL read that hash as password storage, which it never was, but a scanner asking why a token is hashed at all is asking the right question of the wrong line. **And the endpoint buckets its rate limits by User-Agent, which took two wrong theories to find.** The tracker introduced itself as `brain/1.0` — the repo's own naming rule, applied one file too far — and that UA lands in the bucket the endpoint keeps for strangers: a 429 wall after a few hours with quota to spare, which measured from inside like a daily meter ("nine working hours then a wall until the small hours") and was written up here as one. It never was. Every reporter in those issues was calling without the CLI's UA too, and the statusline-tool ecosystem polls the same endpoint at 1–5 minute cadences sustainably by sending the UA Claude Code itself sends. **Which of Claude Code's two UAs took a third theory to get right, and the wrong one looked correct for a release.** The bundle has a `getUserAgent()` that builds `claude-cli/<version> (external, cli)` — that is its *Messages-API* client, and it is what shipped; the usage endpoint's own caller (`Hqq()`) sets `"User-Agent": jH()`, and `jH()` is `claude-code/${VERSION}`, no suffix. A real Claude Code UA sent to the wrong endpoint is still a stranger, so the wall never lifted, the sensors went on ageing out into unavailable every couple of hours, and the docstring said it was fixed — read the *call site's* header, never the first UA helper the grep finds. So `user_agent()` sends `claude-code/<installed version>` (probed from `claude --version` once per process, `BRAIN_CLI_VERSION` to pin it, and a real shipped version as the fallback because a made-up version is a UA nobody else sends; the version is approximate on purpose — the CLI stamps a build-time constant that lags its release, and the bucket is keyed on the product prefix), and the poll is 5 minutes. This is the one deliberate exception to "prefer `brain` over `claude` in anything we own": the request is made with that install's credential on that install's behalf, and the name on it is the difference between working sensors and a wall. **A 429 is not a failure to retry — retrying is what sustains it**, so it escalates 1/2/4 hours rather than sharing the ordinary cadence, and every step must exceed `POLL_INTERVAL` or a *failing* tracker asks more often than a working one (which is what lengthening the poll and leaving 15/30/60 alone would have done — `test_every_backoff_actually_backs_off`), and `Retry-After` may only ever *lengthen* that: the endpoint sends `Retry-After: 0` while still refusing, so obeying it literally is how a tracker retries straight back into the limit it was just told about. It is absent from `AUTH_PROBLEMS` on purpose — it says nothing about the sign-in, so it lets a good reading age out instead of blanking four sensors — and it ships a `detail` for the diagnostic sensor, because `http_429` beside a usage number is read as the number. **The backoff waits are all longer than the 2-hour staleness window, so during any 429 streak the sensors *will* go unavailable — and that moment has to arrive with its reason.** The reason used to be written only on the poll *after* the reading went stale, hours later on a 4-hour rung; in between, the diagnostic said `stale` and nothing else, which reads as "unavailable for reasons I do not understand". A failed poll now leaves `last_error`/`next_attempt_at` (and the 429 gloss) *beside* the reading it deliberately did not overwrite (`_record_failure` — the numbers and their `updated_at` untouched, so staleness still ages from the real reading, and no reader keys on `error`), the diagnostic sensor reports a stale-with-reason as the reason itself, and a restart resumes a promised quiet instead of retrying straight into the limit (`_resume_backoff` — backoff lived only in memory, and restarting the add-on is the first thing anyone does when sensors go dark). **Compare against what Claude Code itself does**: its own client calls this endpoint from the `/usage` screen and nowhere else, on demand, never on a timer — which is why the poll stays at the gentle end of what the right bucket demonstrably serves, and why the hour-scale ladder survives the bucket fix: a 429 in the CLI's bucket is rare enough to mean something. The suite could not see any of this — every test set `CLAUDE_CONFIG_DIR: None`, and that variable *being set* is what creates the duplicate, so `TestOneCredentialOneRequest` builds the environment `run.sh` actually exports and asserts the collision exists before asserting it costs one request.
- **A fallback that is silent is a fallback read as the real thing.** When the tracker cannot report, `usage_store.budget_state` slides to the local estimate — brAIn's own insight runs against a rough plan allowance — and the pill went on rendering it as an ordinary percentage with the weekly half gone. On a home that mostly uses the terminal and the chat that estimate is **0%, forever**, which is precisely what "the usage sensor is unresponsive" looks like from the panel; and the one line the popover had about it said *sign in with your Claude subscription*, i.e. telling somebody who is signed in to redo the thing that was working. `limits_problem()` reads the tracker's own status out of the same file (`error`, or the `last_error`/`next_attempt_at` a failed poll leaves beside a reading it did not overwrite) and `budget_state` carries it as `limits` **only when `source` is not `account`** — an excuse beside a working number is noise. The pill prefixes the estimate with `~` and takes the warning dot; `limitsNote` says which failure it is, in the tracker's vocabulary, with the two codes people misread spelled out (a 429 is the *endpoint's* limit, not the account's; an API key has no window to report) and the time of the next attempt, because during a backoff the honest answer is "not broken, waiting, back at 9:40". `_fresh_payload` also stopped treating a reading with no `updated_at` as fresh — the staleness test was skipped whenever the stamp was missing, and a reading that can never go stale is a reading nothing can correct.
- **A verdict nothing re-earns is a verdict nothing can correct.** `AUTH_CHECK` ran at panel startup, after a credential was saved and after the guided sign-in, then never again — so a credential that died on a Tuesday afternoon was reported by nothing: `/api/status` served the startup verdict for days, the auth chip stayed hidden because a working login is not news, and the first symptom was voice, the automation listener and the consolidator failing off one store while the terminal worked off another. Same shape as the usage tracker's stale reading, and reachable precisely because `engine.get_auth` prefers a store whose credential it *cannot* verify: the panel store records `{type, value, saved_at}` and no expiry, so unlike `_cli_credentials_present` there is nothing to check — the only liveness signal a pasted token has is a 401 at use. So the verdict ages (`AUTH_RECHECK_S`, 6h, failures included so a terminal re-login is noticed without a restart) and is re-earned **lazily off `/api/status`**, never on a timer: `validate_auth` is a real `claude -p` turn, and an unattended timer would spend account tokens forever on a question nobody is asking, where the status poll only runs while somebody is looking. A re-check nobody asked for is **unannounced** (`announce=False`): "Verifying Claude…" answers what a person just did, and a chip appearing unbidden in the top bar — shifting its layout — every six hours while somebody reads a card is the "a permanently green chip does not belong there" rule with the timing changed; the standing verdict is served until there is a new one, which is also the more honest answer. **`start_auth_check` flips `running` synchronously**, because `asyncio.create_task` only schedules — nothing in the coroutine runs until the loop yields, so a guard reading a state its own task has not set yet is no guard: two polls in one tick both spawned a real check, already reachable through the polled `h_setup_status` and now through a harder-polled `/api/status`. It is a flag rather than the state precisely because a silent check leaves the state reading `ok`, and `_auth_verdict_is_stale` has to consult it or every poll re-asks over an unfinished one. **`save_auth` writes `saved_at` as an epoch int**, which is the shape `_read_shared_auth` documents for both files and what `ha-share-login` writes and greps (`"saved_at":[ ]*[0-9]+`); it wrote an ISO string, latent only because each reader happens to read the file it wrote. The shell half had asserted the int since it was written and the panel half had not, which is the whole reason it drifted.
- **A poll that succeeded is not news.** `QuietAccessLogger` drops successful GETs to the endpoints the panel asks for on a timer and logs everything else, with failures at warning; `log_level: debug` is the one switch that turns everything back on (it also raises ttyd's `--debug` mask, whose default 7 includes NOTICE — three lines per socket). Both halves of the terminal's websocket bridge get a `heartbeat`: pinging only the ttyd leg left the browser leg idle, so ingress and Nabu Casa closed it after a minute or two, ttyd killed the session's process, and the client reconnected forever. **And when a bridge does drop, it has to say why.** The two pumps race under `asyncio.wait(FIRST_COMPLETED)`, which does neither of the things that ending them needs: cancelling the loser only *asks*, so it was still inside `dst.send_*` when the `async with` closed the upstream socket under it; and an exception inside a task never reaches `asyncio.wait`, so a bridge that broke mid-frame was indistinguishable from a browser closing politely — `except (ClientError, OSError)` never saw it, the log said nothing about the reason, and Python printed a bare `Task exception was never retrieved` at some later collection, attributed to nothing. `_settle` waits the cancellations out and re-raises the winner's exception. It waits with `asyncio.wait` rather than `await task`, and reads *every* outcome rather than the winner's: a pump cancelled mid-send can come back carrying a `ConnectionResetError` of its own, and a first cut that awaited each loser under `suppress(CancelledError)` let that propagate — reporting the loser's incidental error while the winner's reason went unread and unretrieved, which is the same bug one case narrower. It is a named function precisely so it can be driven directly, because through a real socket "one pump fails while the other is mid-send" is not something a test can schedule.
- **Hypotheses replace open-ended questions**: capped at 3 open, 14-day expiry, answered ones become plain memory lines and the record is settled. Rejected ones become a capped dead-ends block.
- **Three kinds of knowledge, and they don't mix.** Memory = what is *true* of the home. A hypothesis = what brAIn might have *wrong*. A **finding** (`panel/findings_store.py`) = what is *broken*. The generation contract keeps them apart too: `learned` feeds memory, `findings` feeds the work list.
- **Three kinds of knowledge, one list of decisions.** The last two are different knowledge and stay in different stores; they are the same *job*, which is a question only the person living there can answer, and that job has exactly one surface: the Findings tab. Open hypotheses ride down `/api/findings` (`server._findings_payload`) and `open` spans both, because "how much is waiting on me" is the only question a badge on a work list answers. They used to be answerable in three places — inline under every insight card, in the Memory tab's "Waiting on you", and counted by neither badge — so answering one left the other two rendering an open question, and the Memory badge counted work the Findings badge didn't. `questions` is gone from the stored card, the `/api/questions*` routes are gone with it, and the Memory tab has no badge: what is left there is a queue that files itself and a document to read, and a badge counting work nobody has to do is how the badge next to it stops being read.
- **`tmp + rename` is atomic against a reader and a race against a writer, and every store had the second one.** The scratch name was derived from the target (`path.with_suffix(".tmp")`), so every writer picked the *same* name: two writers both create `findings.tmp`, the first `replace()` moves it, the second gets `FileNotFoundError` — and the loser's bytes went into a file the winner had already renamed away, so **one write is silently lost**. Reachable in the panel as shipped: `h_finding_fix` writes the findings store from a request thread (`asyncio.to_thread`) while `_generate` writes it from the event loop. It surfaced as `test_fix_and_snooze_offer_no_undo` failing about one full-suite run in three, which read as CI flakiness for as long as nobody traced it. Everything goes through `panel/atomic_write.py` now (`mkstemp` in the target's own directory, so the rename is still same-filesystem and still atomic), and `test_atomic_write.py` reproduces the old recipe failing before asserting the new one does not — a guard measured against a demonstrated failure rather than a described one, plus a grep-level test so a new store cannot copy the pattern back in. **Preserving mode and owner is not a nicety, it is the fix not regressing**: `mkstemp` creates `0600` where `write_text` made `0644`, and several of these files are written by root and read by the `claude` user; and `os.replace` swaps the inode, which is how the old prune quietly took `/data/run-sources.jsonl` away from the `claude` user that `run.sh` had created it for. `fsync` before the rename is the one addition — the rename was always ordered, the data behind it was not.
- **A queue's list and a queue's count are one read, or they are two answers to different questions.** The Memory tab's "waiting to be filed" counted the memory inbox — every fact any writer has queued — while LISTING the facts ledger minus anything whose `ts` predated `.last_consolidated`. The ledger only holds what the *analyst* discovered, so corrections, confirmed guesses, facts taught from the panel, voice, study sessions and anything another add-on left in `/share` were counted and never shown: nine things waiting above four cards, and neither number wrong. `_inbox_items` serves the actual lines now and `h_knowledge` reads both in one call. A line's id is a content hash (`_inbox_id`), because nothing stamps one and `ts` is not unique — one insight run queues three facts in the same second — and two lines that say the same thing from the same source *are* the same fact. The rendered list is capped and the count is not, so an over-long queue says what it is not showing rather than disagreeing again more quietly. **✕ drops the line and asks the consolidator for nothing**: a queued fact has by definition never been filed (the consolidator archives what it consumes), so the old `FORGET:` request was asking to strike a line the document mostly did not hold. `FORGET:` itself is unchanged — `brain memory forget` still writes one.
- **A tooltip that opens off the screen is a tooltip that is not there, and CSS cannot see the edge.** `[data-tip]::after` was `position: absolute; right: -4px`, max-width 240px, so the bubble hung *leftward* from the control's right edge: anything whose right edge sat under ~236px from the viewport's left lost its text off the side. Four of the six buttons under a finding at 390px; still two at 1100px, because the findings list starts at the left margin. It is one shared `.tipbox`, `position: fixed`, measured and clamped in `placeTip` — same reasoning as `#chipPop`, and it also flips above when below would not fit, which is what the old `.card .foot` override was patching one case of. The listeners are delegated because these controls are rebuilt on every render. **`scroll` calls `dismissTip`, not `hideTip`**: a *visible* tooltip is anchored to where the control was and has to go, but one still inside its 150ms open delay is measured when it opens, after the scroll — cancelling that one is what made a tooltip vanish for good whenever the page settled a scroll just after the pointer arrived. `tests/manual/measure-tooltips.mjs` measures it; a bubble that never opens fails the same as one off the edge, because they look identical.
- **A toast is `left: 12px; right: 12px; margin: 0 auto`, never `left: 50%` with a translate.** A fixed element's containing block is the viewport, so `left: 50%` leaves it the right-hand half to lay out in — on a 390px phone the toast could never exceed ~195px and wrapped to four lines with the whole screen spare. Invisible until something sat beside the text, which is what Undo is.
- **Undo is the toast's, and it is "I misclicked" — not a history.** Every press that takes a row away hands back a token (`undo_store`, in memory, 300s, a 32-entry ring) and the toast grows an Undo. Reversing puts back all three effects of an ending, because putting back one or two is worse than none: the row (`findings_store.restore`, under its *original* ts — that id is what the chat strip and any pending token hold), the settled key (`unsettle`), and the queued memory line (`_drop_from_inbox`, which works precisely because the token is younger than any consolidation pass — once the fact is in the document, editing the document is the only honest answer, which is what the TTL admits). A hypothesis answer reverses through `hypotheses.reopen` plus retiring the ask-history entry a rejection wrote, or the guess comes back un-proposable. A token is **taken**, not read: two presses on one toast must not restore twice. `restore` refuses over an occupied id — the analyst re-reporting it means the list holds something newer — and the panel says which happened rather than claiming a success. **Fix it and snooze offer none**: the first has already sent Claude at the house, and an undo that only took the card back would lie about what it undid; the second took nothing away and has "Bring it back now".
- **A button that ends a finding has to be able to say why, and the why is the half that teaches.** "Ignore" described what happened to the row; what people mean is almost always "you have misread my house" — the sensor is not stuck, it is a contact on a cupboard nobody opens — and a key in the settled ledger suppresses one wording while the next run makes the same mistake in new words. `✕ Wrong` is the same ending with a `note` (`POST /api/finding/{ts}/wrong`, `/ignore` kept routed for a panel served before the update), `hypothesis/{ts}/reject` takes the same note for the same reason, and so does `done` — but `source` is per-verb, not "a note means a correction": waving a report off is evidence brAIn has misread the house, while saying how you fixed something corrects nothing and is simply more of the fact already being recorded. The note goes two places and **neither is a rule**: `findings_store.prompt_block` renders it verbatim as `They said: …` under the finding it corrects, and it is queued to the memory inbox with `source="correction"`, where the consolidator is told the report is not a fact, to record the standing truth the reason implies, and to record nothing if there isn't one. Deliberately a judgement call — nobody phrases a correction carefully, and a button that wrote whatever was typed into `memory.md` would file the thing being denied. **The box is never required**: "not a problem here" needs no essay, and a mandatory field turns a one-press dismissal into a chore and fills with "no". A note on an ending with no `noted` template (`done`) falls through to the ordinary memory line rather than silently costing it. The reason box opens in place of the card's buttons, inside the card, because you are correcting something and it has to stay on screen while you write about it — and the chat strip's `✕ Wrong` opens the same box, since explaining it to Claude in the conversation reaches that conversation and the note reaches every future one. `setChatFinding` clears it: the strip is one reused element, unlike the cards, which are rebuilt.
- **Findings are mirrored to the shared volume, because /data is invisible to Home Assistant.** `findings_store._write` republishes `/config/.brain/findings_state.json` on every store write — hooked there so no code path can change the store without it — and `publish_state()` re-runs it at panel startup so a boot never serves last week. The mirror is derived and never read back; the integration's `FindingsWatcher` (primed at startup, same no-replay contract as `LearningWatcher`) diffs it into `brain_finding` events, and `sensor.brain_open_findings` reads it. The publish is skipped when the shared volume's parent does not exist (a dev checkout must not grow a stray `/config`) and an OSError is a logged warning, never a lost finding — the row is already safe in /data before the mirror is touched. **Notifications go to the CREATED list only** (`server._announce_findings`): `add_many` dedupes across every status and the settled ledger, which is the whole reason a re-report cannot ring a phone twice; the notify target is the `findings_notify_service` option read live from the Supervisor snapshot with the run.sh env export as fallback, and a failed delivery is a log line because the finding is already on the list.
- **A finding leaves the list when a person ends it, and then it is gone.** Three presses end one — "I've fixed it", "Wrong", and "Got it" after an automated fix — and each does the same three things: a plain line into `memory.md` (both endings are facts about the house, phrased differently because they *are* different facts), a normalised key into the settled ledger (`findings-settled.json`), and the row deleted. There is no archive of dismissed cards and no view of the ledger at all — rendering it beside a list that is meant to empty invited people to treat it as the record when memory already is. **The ledger is an index, not a queue** — same rule as the facts ledger, and `add`/`add_many`/`is_known` all consult it, because settling deletes the row and deduping against the list alone would turn every ending into a Forget. `unsettle` is the one thing that removes an entry, and only because a person pressed "Let brAIn raise it again" — which stops the suppression and nothing more, so nothing "comes back" unless the next analysis finds it still there. `fixed` is therefore *live*: brAIn changed something in the house and news nobody has read is not settled. Dismissals from before the ledger are folded in at startup by `migrate_settled()`.
- **Three Claude paths, and only one can change the house.** `run_claude` holds no tools at all (`--disallowedTools "*"`) and is the snapshot path. `run_agent` has everything and only ever runs because someone pressed **Fix it** (`panel/fixer.py`) — never on a schedule. `run_analyst` sits between them: Home Assistant tools, **reading only**, because it runs unattended on a schedule and on any typed question. Its tool set is asserted from both ends (`ANALYST_TOOLS` allow, `ANALYST_DENIED` deny) rather than trusting one flag: `--allowedTools` governs what runs *without a prompt*, and a headless run cannot be prompted, so an un-listed tool **fails** rather than being **forbidden** — not the same guarantee with a real house behind it. The deny list is checked against `ha_mcp_server.py`'s own tool names in `tests/test_security.py`, so a newly added acting tool fails CI instead of quietly reaching an unattended run. `fire_event` and `remember_fact` are why the rule is an explicit list and not a name prefix: both are shaped like reads and neither is one. Fixes share the generation queue, so one Claude invocation is in flight at a time.
- **A card fetches what it needs; it is not handed the house** (`gather_mode`, default `search`). `collect_orientation` sends a *map* — domain counts, area counts, a few anchors — and `run_analyst` searches for the rows the question actually needs (`get_all_states` takes a `domain` and a `name_filter`, so nothing has to enumerate ids). Measured on a real run: 1,449 prompt chars where the snapshot sent ~100,000. **The middle option was measured and rejected**: handing Claude an index of every entity to pick from costs about what the slimmed rows cost, because every id has to be in it — searching by name skips the index entirely. `snapshot` is the old single-turn path, kept as a setting **and as the floor**: a failed or turn-exhausted search falls back to it so a card always appears, and the fallback is logged because a run that keeps taking it is a run worth reading the log about. Search is also the only path that can afford **history on a typed question** — the one-shot path never could, which is why asked questions were always answered from a single instant. `_framing` is shared by both prompt builders, and `_CARD_CONTRACT` by both system prompts: two preambles, one contract, because a second copy of 10 KB of output rules is a second copy that drifts.
- **The ask bar has two verbs.** A question becomes a card; a line starting "learn/study/research/figure out" is routed server-side (`LEARN_RE`) to a study request the CLI-side watcher picks up. There is no separate "new insight" dialog — asking makes the card, and "＋ Make recurring" turns it into a scheduled one.
- **Deleted cards do not come back.** There is no restore list: brAIn proposes the cards a given home should have, so the answer to "I want that card again" is to ask for it and let brAIn build it for the house it now knows. Shipped categories are still `hidden` under the hood because their definitions live in the code, but that is a mechanism, not an offer.
- **House checks are findings that cost nothing, and they clear themselves** (`panel/checks/`). A check is a pure function from one snapshot of the house (`checks.snapshot.collect`: states, registries, services, the YAML config files with HA's own tags tolerated, `.storage/trace.saved_traces`, a week of daily statistics, sixty days of battery means, the storage-mode dashboards) to wire-shaped findings under `source: "check:<id>"`; `run_all` files them through `findings_store.add_many` like every other producer, so they dedupe against the settled ledger and ride into the analyst's prompt block. Three rules keep them honest. **Finding text is stable across runs** — the store dedupes by it, so the number that changes ("9 days left", "since 3 Sep") lives in `detail`, and `findings_store.refresh_details` updates it in place. **Only a check that RAN may clear** — `clear_resolved` removes open rows (never `fixing`/`fixed`: those are a person's or the fixer's) whose source is in the set of checks that ran and whose key was not re-reported; a check skipped because its snapshot key was unavailable, or one that raised, is not in that set, because "I could not look" and "it went away" are different claims and only the second may delete a row. Clearing writes no memory line and no ledger entry: a problem that went away on its own is not a fact about the house, and if it comes back the check files it again. **A check that fires on a healthy house is worse than no check** — every rule has a floor or a window, `tests/test_house_checks.py` asserts each silent on the clean fixture before asserting it finds the planted row, and the scorecard is what proves it in the field. Two traps found by driving them: a service name has the shape of an entity id (`light.turn_on`), so `House.entity_refs` skips the values of `service`/`action`/`trigger`/`platform` keys and anything in the registered services set; and `age_days` of a trace from this second is `0.0`, which `or 99` turned into 99 and dropped the freshest evidence — test `is not None`, never truthiness, on an age.
- **The second set of checks reads what Home Assistant is not.** 1.29's checks all read Core; the ones that matter most read around it, so `checks.snapshot` grew two keys and a third. **`supervisor`** is `/backups`, `/addons`, `/host/info` and `/core/info`, gathered rather than awaited in turn — and each add-on row is folded together with its *own* `/addons/<slug>/info`, because the list endpoint does not carry `boot` and `boot` is the entire difference between "somebody stopped this on purpose" and "this was meant to be running": `sys.addon_down` reports a `boot: auto` add-on that is stopped, and an add-on whose `/info` did not answer carries no `boot` at all, which reads as **I could not look** and files nothing. **`recorder`** is one `stat` of `home-assistant_v2.db` plus `purge_keep_days` from `configuration.yaml` — an `!include`d recorder block reads as unset (`sys.recorder_size` then names HA's own default rather than a number this invented), and a database that is not a file under `/config` takes the whole key **unavailable** rather than reporting as small, because Postgres is not a smaller database, it is a question this cannot answer. **`zha_devices`** is `zha/devices`, which errors on a house with no ZHA and so goes unavailable: no Zigbee is not an unhealthy Zigbee. `dev.zha_unseen` keys on `last_seen` and *not* on `available`, which is the whole point — a sleepy sensor is `available` between check-ins, so availability says nothing and silence says everything. `dev.zwave_dead` reads the node status sensor the controller publishes, and `dev.unavailable` **skips a device it claims**: the same box under two fixes ("restart it" and "re-interview it, or remove the failed node") is how a list stops being read, and the two checks share `_zwave_dead_devices` so they can never disagree about which box that is. `auto.trigger_unavailable` is the one with no symptom at all — the automation is on, nothing errors, no trace is written, and it can never fire again — so it is deliberately separate from `dev.unavailable`, which reports the sensor: only the second answers "why did the hallway light stop coming on". It reads both spellings of the trigger key (`trigger:` and 2024.10's `triggers:`, `platform:` and `trigger:`), and it stands down for a missing entity (`auto.dead_ref`'s) and for a switched-off automation (`auto.forgotten_off`'s). The `reg.*` checks are the ones most at risk of the "fires on a healthy house" failure and each carries the floor that answers it: `reg.no_area` says nothing below three areas, because a house that has not set areas up is not a house with a problem; `reg.unused_helper` gives a helper 30 days to be wired up and checks the configs, the storage dashboards **and** other entities' attributes in one `entity_refs` pass (it rebuilds the services set per call, and this walks the whole house); `reg.orphan_device` spares a device another names as its `via_device`, because a hub with no entities of its own is still doing a job; and `reg.hardware_name` requires a hex run to carry both a digit and an `a-f` letter, or `Bedroom 123456789012` and `deadbeefface` both read as hardware and neither is.
- **A state carries no cause, and the logbook is the only place Home Assistant records one** (`panel/actions.py`). Nothing in `light.kitchen` being on says whether a person pressed a switch, an automation fired, a voice command asked, or brAIn did it — which is the question behind most of what people actually ask their house, and it was unanswerable from every surface brAIn had. The miner reads the logbook, walks each event's context chain, and files every change under a cause out of a closed vocabulary (`CAUSES`, switched on by the check, the tab's filter and the MCP tools alike). **Proximate and root cause are different and both are recorded**: an automation somebody started from the UI carries a `context_entity_id` *and* a `context_user_id`, so reporting only the user turns every automation into "you did this" and reporting only the automation loses the one fact that explains an unexpected run. **`context_domain` is not the runner** — it is `light` for a plain `light.turn_on`, so the authority is the context *entity's* domain and only then the three domains that run something. **A change with no context is `unattributed`, in as many words**: a wall switch and a device's own integration reach Core identically, naming either is a guess, and a timeline that guesses is not evidence. **`when` is an ISO string over REST and a float over the WebSocket stream**, out of the same processor, so a reader that handles one works right up until somebody points it at the other. **Nothing is persisted** — every question here is about a window, so every function is pure over one fetch, and the accumulating store that would buy longer windows would be a second thing to keep true.
- **brAIn knows what brAIn did because it wrote it down, not because it can tell.** The MCP server calls Core over REST with the Supervisor's token exactly like every other add-on, so a light brAIn turned on is indistinguishable in the context chain from a light any integration turned on — there is no id to match. `ha_mcp_server.record_action` appends every service call to `/config/.brain/actions.jsonl` at the same `call_service` chokepoint `protected_entities` is enforced at, and `actions.read_ledger` joins the logbook against it inside `BRAIN_MATCH_S` (a bulb answers in well under a second, a thermostat takes several). An **area or device target is recorded and deliberately not resolved** — resolving one needs the registries as they were at the time of the call, and a wrong expansion would attribute somebody else's change to brAIn, which is the one mistake the ledger exists to prevent. The writer and the reader are **different processes running as different users and neither can import the other**, so `tests/test_actions.py` drives the real writer into the real reader rather than writing the shape down twice — the same reasoning that put `saved_at` back to an epoch int.
- **An override is the only signal a house gives about an automation being wrong for it.** A person putting something back within `OVERRIDE_WINDOW_S` of an automation moving it: the automation ran, nothing errored, and the light is off, so no check that reads Core can see it. Three rules keep it honest and all three are asserted against the cases they must NOT fire on — **the state has to actually differ** (a person pressing "on" after a rule turned it on is agreement, and counting it would put the best-behaved automation in the house at the top of the list), **one automation move is undone once** (somebody nudging a dimmer three times is one disagreement), and **an automation undoing an automation is not an override** (that is a conflict, and a different finding). `auto.overridden` reads `find_overrides` rather than recomputing any of it, and fires at three in a day: once is a one-off, twice is a coincidence.
- **The Activity tab is the fourth kind of knowledge, and it has no badge.** Memory is what is *true*, a finding is what is *broken*, a hypothesis is what brAIn might have *wrong*, and this is what *happened*. It is a record rather than a queue — nothing on it is waiting on anybody — so the one badge in the strip stays Findings', which counts exactly that. Fetched per visit and never cached: a timeline showing the house as it was when you last looked is the one thing a timeline may not do, and a cache of a stream is a second copy of the logbook to keep true. The overrides ride above the list because they are evidence rather than history. The cause **moves to its own line** on a phone rather than being deleted — the name of the automation that did something is the whole row. `tests/manual/measure-activity.mjs` drives the real `renderActivity` behind a stubbed fetch (a copy of the renderer in the test would only ever agree with itself) and fails on a row with no cause, a cause hidden rather than moved, an unattributed row that does not say so in words, and an evidence block shown over a window with nothing in it. **The sixth tab needed no new breakpoint** — `measure-topbar` reports all 96 cases at the same two shapes — but it found two tests measuring the wrong thing: that script asserted *five* tab labels by number, which says nothing about whether a sixth kept its name, and `test_brain_addon`'s band scan ran to the end of the stylesheet, so it was really testing where the last `@media` in the file happened to sit.
- **`explain_change` and `get_activity` call the panel over loopback rather than re-implementing attribution.** Same reasoning as `brain findings` going through the API instead of the store files: one implementation, one answer. Both are read-only and on `ANALYST_TOOLS`, so an unattended card can ask what caused something; a panel that is not up is reported as such rather than as a quiet house.
- **A verdict on the add-on itself, because every failure it has shipped was a quiet one** (`panel/health.py`). A listener that died, a credential that expired on a Tuesday afternoon, a consolidator running and landing nothing — each visible from inside for hours before anybody noticed from outside, and each answerable only by somebody running `brain doctor`. The verdict is **a state and a sentence, never a score**: one number over a house hides its worst problem inside an average, and an average moving from 92 to 88 is not something anybody can act on, so the state is the worst thing found, the reason names *that*, and the rest rides underneath. Every problem names the switch rather than the symptom. **Optional is not broken** — the daemon roll-call is descriptive by design, so the interpretation happens here and against the options, and voice is asked about as a *job* rather than by daemon name because `assist_fast_mode` decides which of two implementations is correctly absent. **"I could not look" is its own answer**: an empty roll-call is `/proc` unreadable rather than seven dead daemons, and a missing `.last_consolidated` is a fresh install rather than a stale one. It is derived once, at the end of `_diagnostics_payload`, so the panel, the mirror, the sensor, `brain doctor` and `brain report` cannot disagree.
- **`sensor.brain_health` never goes unavailable, and a stale verdict is not a healthy one.** HA hides the attributes of an unavailable entity, so an entity that vanishes takes its own explanation with it — and this is the entity somebody looks at precisely when the others have gone, so "the panel has published nothing" is a *state*. The reader has one question the panel cannot ask itself: the mirror is rewritten after every checks pass and hourly in between, so a file that has stopped changing means the panel has stopped running, and serving its last good verdict would be a reading nothing can correct (the usage sensors' own bug). The freshness window is **published in the payload** (`stale_after_h`) rather than agreed twice, and the sensor stats the **file's mtime** rather than trusting `generated_at`, because a corrected clock leaves a stamp in the future and a verdict that can never go stale is a verdict nothing can correct.
- **A run journal nothing reads back is a run journal that only exists in somebody else's bug report.** `journal.summary` was written for the ⚙ dialog's Diagnostics section and shipped a release before it, so for one release the only route to it was `brain report` — which is to say, the only people who ever saw it were the ones who had already been asked for it. The section renders `/api/diagnostics` (the same payload as the mirror and HA's Download-diagnostics button), fetched when the dialog opens and on ⟳ and **never on a timer**: this is something you look at, and a poll behind a dialog nobody has open is a request per viewer per interval for an answer that changes hourly. It names **which checks could not run and why**, because a skipped check did not find nothing — it could not look, and it is the same check that `clear_resolved` may not clear a row for, so "12 ran, 3 skipped" and "15 ran" are different reports of the same quiet house. Copy falls back to a selected `<textarea>`: an ingress iframe may be refused `navigator.clipboard` outright with no way to ask in advance, and a failure that only says "could not copy" leaves the text nowhere a person can reach it.
- **The producer scorecard needs the producer on the settled entry.** Every ending on the Findings tab is a label ("I did it"/"Got it" = the report was right, "Wrong" = it was not), and `_remember_settled` recorded the ending and not who raised it, so nothing could add the labels up. It records `source`/`source_title` now and `findings_store.scorecard()` aggregates; it rides `_findings_payload` because it is read in exactly one place. The tab shows a producer only past `SCORE_MIN_ENDINGS` — "1 of 1" is an anecdote. A pre-1.29 ledger entry has no source and scores nothing rather than everything.
- **The run journal counts what the log only mentions** (`panel/journal.py`). One JSONL line per Claude run of any kind and per checks pass, hooked in `engine._run_cli` (every `-p` run, whatever happened to it), `chat_session._normalise` (the `result` event) and `server.run_checks`, with a fixed outcome vocabulary (`journal.OUTCOMES`) so a bundle can say "3 of 12 insight runs ended `unparseable`". `fallback` is an outcome — the search→snapshot slide is recorded at the point it is logged — because a fallback nobody counts is a fallback read as the real thing. Never prompts or replies; error text goes through `journal.scrub` before it lands, because this file is what `brain report` attaches to an issue. `record` never raises: accounting must not fail the run it is accounting for.
- **Diagnostics is one payload with three doors** (`server._diagnostics_payload`): `GET /api/diagnostics`, the mirror at `/config/.brain/diagnostics.json` (written after every checks pass and hourly from `_checks_loop`, skipped on a dev checkout with no `/config` — same rule as the findings mirror), and the integration's `diagnostics.py`, which is what puts something behind Home Assistant's own **Download diagnostics** button. `brain report` bundles the mirror's source, `brain doctor --json` and the add-on log tail into `/share/brain/reports/`, and `redact()` runs over *every* file whether or not it "can" hold a token — a regex skipped for the file that can't is the one that misses the day it does. `ha-selftest.sh` records every pass/fail/warn/info line either way and only the printing changes under `--json`; `tests/test_doctor_json.py` lifts the report block out of the script and drives it, the same way `consolidator_lock_check` is tested.
- **`protected_entities` is enforced in the MCP server and nowhere else.** `DENIED_SERVICES` restricts a *channel* (voice may not unlock); `PROTECTED_ENTITIES` restricts an *entity* for every channel, and the terminal, the chat, the fixer, voice and automations all reach the house through that one process, so `call_service` — the chokepoint every `control_*` tool routes through — is the one place to ask. run.sh exports `BRAIN_PROTECTED_ENTITIES` and writes it to `/data/.brain_env`, which is every route an option has into a Claude process. An area or device target is resolved through the entity and device registries (`_protected_scopes`, cached 60s) and refused if it contains a protected entity; the registry unreadable fails **closed**; labels and floors cannot be resolved here and are refused outright while the list is non-empty — the same conservatism `_meta_call_denied` applies. Read-only tools are untouched: a protected entity can be looked at, not acted on. `tests/test_protected_entities.py` drives `call_service` and `control_lock`, not the helper, because a helper that answers correctly while the chokepoint forgets to ask it is the bypass.
- **Naming**: prefer `brain`/`ha` over `claude` in anything we own. `CLAUDE.md`, `CLAUDE_CONFIG_DIR`, the `claude` user, and the `claude-run` wrapper keep the name because they *are* Claude Code's file, env var, user, and binary. Everything else (`panel/engine.py`, `scripts/brain-*.sh`) is brAIn-named.

### BRUH Print specifics

- **There is no CUPS in the container, and that is the design.** `panel/dymo/` speaks the LabelWriter's own raster protocol over a bulk USB endpoint — about 300 lines and no daemon — where a print server would add a spooler, a PPD, a filter chain and a second place for a job to get stuck, to produce the same bytes. What is sent is `ESC B` (dot tab), `ESC D` (bytes per line), `ESC L` (length), `ESC q` (roll select), `SYN` per raster line, `ETB` per repeat, `ESC G`/`ESC E` to feed. What is deliberately **not** sent is the density and print-mode opcodes: their encodings differ across the 400/450/550 generations, thermal stock prints correctly at the printer's default, and a byte sent to the wrong firmware is a wedged printer rather than a lighter label — a guess that is only sometimes right is worse here than not asking. `ETB` is not a micro-optimisation: a label is mostly white, so a run of identical blank lines costs one byte each instead of 85, and a 2.25″ × 1.25″ label is 7 KB on the wire against 32 KB.
- **Every copy but the last gets the SHORT form feed.** A long feed between copies advances a whole label past the head, so a run of ten came out as ten printed and ten blank — the printer wasting half the roll, because it was. The preamble is re-sent per copy for seven bytes, so a label after a power cycle or another process's job starts from a known state.
- **A printer that is not in the table is driven, not refused.** Matching is on DYMO's vendor id alone; an unrecognised model gets the 450's geometry and the twin flag is read from the device's own product string, so a Twin Turbo with a new product id keeps its second roll. Guessing narrow prints with margin to spare, guessing wide prints onto the other roll's liner — and guessing `twin: True` would put a roll switch in the panel that does nothing, which is worse than a missing one. A saved printer is keyed on its **serial**, not its bus address, so a reboot that renumbers the bus is still the same printer.
- **A LabelWriter cannot tell you what is loaded, so `stores/loaded.py` is what remembers.** This is the feature, not the bookkeeping: sending a 2.25″-wide raster to a 0.56″ roll prints across the liner, once per copy, with no error anywhere — a run of fifty ruins fifty labels. So a stock/roll mismatch is the one thing a print is refused for (409, naming both stocks), and everything else that could be wrong — a barcode that will not fit, an image that could not be read, a fixed font size that clips — comes back as a **note** beside a label that still prints. A refusal is always a person unable to work. The remaining count is an **estimate** and says so everywhere it appears, because nothing on a LabelWriter reports a real level.
- **A stock is two measurements and they are not interchangeable.** `across_in` lies across the print head, `feed_in` travels past it, and getting them the wrong way round is the single most common way a label comes out rotated with the text off the edge. Nothing can work it out for you — the printer feeds to the next die-cut gap and has no idea what shape the label was — so `swap()` is one press, and **the ruler** (`_ruler_label`, millimetre ticks on both axes) is the only honest answer, which is why it is a button rather than a docs paragraph. An edited built-in is saved as an override so a future release correcting one cannot undo somebody's own measurement.
- **The 450's head is 672 dots at 300dpi, which is 2.24″, and the cryo stock is 2.25″.** The three extra dot columns are clipped, not scaled away, and a note says so: scaling every element down half a percent to hide it makes a barcode's module width fractional, and that is the one thing that must not happen — a fractional module rounds each bar independently, so five 1.4-dot bars come out 1,1,2,1,2 and the scanner reads the wrong widths. Same rule for QR. A symbol that cannot fit at one whole dot per module is **reported**, never drawn smaller, because an unreadable barcode looks exactly like a readable one.
- **One rendering, two consumers.** `render.image.render()` is the only route from a label to dots; the preview PNG and `raster_lines()` are the same bitmap with different endings. A preview drawn a second way would look right while the label came out blank. Nothing is anti-aliased anywhere — a thermal head is one bit deep, so a 50% pixel is a black one and an anti-aliased hairline comes out solid. Text is supersampled 4× and thresholded, which is about *placement* (a 2mm glyph is 23 dots) rather than smoothness. **Ink is 1 and paper is 0**, and the flip from PIL's convention happens exactly once in `raster_lines`; per-element it is one element printed as its own negative.
- **The autofit is the product, and it chooses the arrangement, not just the size.** Every way of breaking the words across lines is rendered and the largest glyphs win — `Buffer A` is biggest on two lines and `9912` on one — because trying a single arrangement is what makes an autofit label look like it did not try, and people go back to the designer. It is exponential in the word count, so above eight words it falls back to greedy-per-line-count. `max_mm` exists because filling the label is not always the goal: a single `9` at thumb height reads as a mistake.
- **A template's fields come from the label, never from the request.** The placeholders in the document are the truth about what it needs; a declared field that no longer appears is a box on the form that fills nothing. Substitution is plain string replacement into `text`/`data`/`asset` and nowhere else, with no expression language — a template that can evaluate is one that can be made to evaluate something else by whoever sends the automation payload, and the value of a label expression language is nearly zero against that. An empty field **refuses** through the API and **warns** in the panel, deliberately: the panel has somebody looking at the preview, and the API call is usually an automation about to print fifty labels with a hole in them.
- **The panel runs as root and the bridge does not.** There is no udev in the container, so `/dev/bus/usb` is the host's device tree bind-mounted in and its nodes carry the host's root:root ownership — a process at UID 1000 cannot open them for writing. The alternatives are worse: chmod-ing the tree writes to the host's real device inodes and still misses a printer plugged in afterwards, and a setuid helper is a setuid binary to get right. The cost is bounded — no port is published, ingress is authenticated, and `panel_admin: true` means the caller already holds the Supervisor API. The bridge, which reads files written from outside the container and never touches USB, stays at UID 1000. `usb: true` only takes effect on a **restart** after it is granted, which is the most common "cannot see my printer", so `usb_link` words that failure as a restart rather than as a permissions error.
- **You pick the label; the add-on remembers which roll it is in.** A roll is not a thing anybody wants to choose — it is where a label happens to be, and `loaded.py` already knows. So there is no roll picker on the Quick tab, in the designer, on a template row, on the card, or in the four print services: naming the stock has already named the bay, and two ways to say where a label goes is one way to contradict the other. The services still *accept* `side` quietly, because a field vanishing from a schema turns an automation written last week into a validation error — a worse outcome than an argument nobody is offered; `set_roll` keeps it visibly, since saying what is loaded is a statement about a bay by definition.
- **Only what is loaded can be picked, and the Printer tab is the exception that makes it work.** The catalog is fourteen stocks of which two are in the printer, so offering all of them on the Quick tab made the commonest first action a choice between twelve wrong answers followed by a refusal for picking one. `loadedStocks()` is what every picker outside the Printer tab reads, and `loaded`/`loaded_side` ride on the stock row rather than being joined in the panel — three copies of that join is three chances to disagree about what is in the printer. A printer with nothing recorded falls back to the whole catalog: an empty picker is a panel that looks broken, and somebody who has not filled the tab in yet still wants to print.
- **Which way text sits on a label belongs to the STOCK, not the job** (`Stock.natural_turn`). A 0.56 × 3.44 cryo wrap reads along the roll and a 2.25 × 1.25 label reads across it, always — so asking on every print is asking a question whose answer never changes, and the panel's Turn control follows the stock when you switch labels. `turn: None` means "derived from the shape" and a number means somebody corrected it; the two are a different state on purpose, and `swapped()` deliberately drops an override back to `None` because the shape is what the derivation reads — carrying it over is a swap that fixes the width and leaves the text lying the way it was wrong before. The ratio is 1.6 rather than 1.0 because a stock only slightly taller than it is wide reads the ordinary way round. It replaced a global `quick_rotate_narrow` switch, which could not be right for two stocks that disagree with each other. **"Automatic" says what it decided** in the closed picker (`Turn: auto (along)`), because a setting you cannot check without printing one is a setting people override blindly.
- **The remaining count is a control, not a readout, and it is optional.** It is an estimate — nothing on a LabelWriter reports a real level — so it drifts the moment somebody prints from another machine, and a number you can see and cannot correct is a number you stop reading: the bar IS the button. `track_remaining` turns the whole thing off, and the decrement goes through `Panel.consume` rather than the store directly, because five call sites asking separately is five chances for a new print path to keep counting a number the panel has stopped showing — and a hidden count that goes on moving is worse than none, since turning it back on reveals a number that has been quietly wrong for a month. The gauge is a `<button>` wrapping a 6px track rather than a styled 6px bar, so the target is a real 40px; `.strow .turnpick` sets no font-size, because a smaller one there would beat the touch floor on specificity — the `.btn.tiny` bug one selector over.
- **A control that needs a tooltip to have a purpose gets a name instead.** "Check it" and "Swap" were both verbs with no object. "Check it" is **Ask the printer** (and its tooltip says it prints nothing); Swap names the two numbers it exchanges — `Swap to 1.25" × 2.25"` — so it is readable without hovering, and the tooltip is left to explain what the pair *means* rather than what the button does. **In use** is disabled when there is only one printer, because a toggle that cannot be toggled is a control asking to be understood.
- **`ingress_port` is pinned here and dynamic in BRight, for the same reason.** BRight needs `host_network` for LIFX discovery, which makes its port a real host port somebody else may own; a LabelWriter is on USB, so this add-on's port lives in its own namespace, cannot collide, and `config.yaml` can name it in a `watchdog:` URL.
- **The Lovelace card reads the sensors and calls the services, and never the panel.** It runs in whoever's browser is looking at the dashboard, which may be a phone on mobile data through Nabu Casa — it has no route to the ingress port and no business having one. It is plain custom elements with no build step and no imports: a card that needs a bundler cannot ship inside an add-on image, and one that pulls LitElement off a CDN breaks the day the CDN is unreachable. It re-renders only when something it displays has moved, because `hass` is set on every state change in the house and a rebuild mid-word takes the cursor out of the text box.
- **Every URL the panel emits is relative, because ingress mounts it under a prefix.** Home Assistant serves an add-on panel at `/api/hassio_ingress/<token>/`, so an absolute `/style.css` is a request to *Home Assistant's* root. 0.1.1 shipped three absolute asset references and twenty-odd absolute `fetch` calls, which reached a real install as unstyled HTML with all five views stacked down the page and every preview a broken image — the CSS, the JS and the whole API 404ing together. `api()` strips the leading slash the way brAIn's does; that convention was already in the repo and reading it was the whole job. **Serving at `/` is the one arrangement in which the bug is invisible**, and it is the arrangement the demo panel and `measure-print-panel.mjs` used — so both now mount the panel under a prefix, and the measure asks whether the CSS and the JS *arrived* before it drives anything, because a page whose stylesheet 404s still lays out and every click then times out on a control that was never built, which reads as a flaky selector rather than as "the panel did not load".
- **The panel serves four named files, never a directory.** `add_static("/static/", PANEL_DIR)` answered `GET /static/server.py` with this file, and every module under `stores/` and `dymo/` with itself. Nothing in there is a secret and the panel is admin-only behind ingress, so nothing leaked that matters — but an add-on serving its own source tree is a mistake waiting to become one, and the name at each call site is a literal rather than anything off the wire.
- **`build_app` is not `main`, and 0.1.0 shipped a panel that could not start.** Every route had a test, every width had a measure, and the add-on bound its port, logged `listening on 0.0.0.0:8097` and died on the next line: `run_app` type-checks `access_log_class` and `QuietAccessLogger` was a plain class with a duck-typed `log`. Nothing caught it because nothing ever handed the class to aiohttp — the tests constructed it directly (with one argument, where `AbstractAccessLogger.__init__` takes two and `log_format` has no default) and the demo panel CI boots called `run_app` without an access logger at all. The demo now serves exactly the way `main()` does, which is the actual guard; the test that reproduces it drives `AppRunner.setup()`, because the `issubclass` check lives in `Application._make_handler` and a synchronous `AppRunner(...)` construction passes against the broken code. **A test that constructs a collaborator itself is a test of the constructor it wrote, not of the one the framework calls.**
- **Nothing says it is listening above the call that would make it so.** That line printed whether or not the server came up, so the one log anybody would read said `listening on 0.0.0.0:8097` directly above the traceback proving it was not — which is BRight's `panel_port` bullet word for word, repeated in a new add-on by writing the obvious line in the obvious place. It is the callback `run_app` invokes once every site is up; what precedes the call says `Starting`.
- **`usb: true` is a manifest permission, not a setting, and four places told people to go and find it.** The Supervisor maps the host's USB device tree in when it creates the container; the Configuration tab has no switch and never did. The README, DOCS.md, run.sh's startup warning and `usb_link`'s own "may not open it" message all said some version of "enable USB access and restart" — confidently specific about a place to look that does not exist, which is worse than saying nothing. They name the power brick, the cable and a CUPS add-on holding the printer now, and `test_bruh_print_addon` greps all four for the old claims, because the wrong sentence is what gets copied into the next release note.
- **Four CSS failures here were all invisible to reading and obvious to measuring**, which is what `tests/manual/measure-print-panel.mjs` exists for. `[hidden]` is a UA rule at the lowest specificity, so `.toast { display: flex }` beat it and left an empty black bar across the bottom of the panel. The touch-floor block sat *above* `.btn.tiny` in the stylesheet and equal specificity is settled by order, so every small button stayed 32px on touch — it is the last block in the file now, and that position is load-bearing rather than tidy. A flex item's floor is its max-content, so the top bar's chips laid out 513px wide in a 390px window instead of wrapping. And `width: auto` sizes a `<select>` to its **widest option**, so the stock picker took the design tab's page-width with it.

### BRight specifics

- **A host-network add-on does not get to choose its port.** `host_network: true` is required (LIFX discovery is a UDP broadcast and the replies come back to the sender's own address, which a bridged container never sees), and it makes the panel's port a **real port on the host**. BRight shipped `ingress_port: 8095` — picked only to dodge BRUH Minecraft's 8099 — and on a box where something else already had 8095 the add-on could not start at all: `[Errno 98] address in use`, the panel dead before its first request, run.sh's `wait` returning, the container exiting, the Supervisor restarting it, and the next attempt asking the same host for the same taken port. **A guard that refuses has to change the next attempt, and a number in a manifest cannot change anything.** `ingress_port: 0` is what Home Assistant documents for exactly this — the Supervisor assigns a free host port and the add-on reads it back from `/addons/self/info`. `panel/panel_port.py` is the one place that lookup lives (env → Supervisor → `DEFAULT_PORT`, and `DEFAULT_PORT` is a fallback for a machine that cannot be asked, never a claim that a port is free); `run.sh` resolves it once, exports it, and writes it into `/data/.bright_env`, because the panel, the HA bridge and the log line have to be talking about the same port — a bridge posting to a port the panel is not on is every show service timing out. BRUH Minecraft still pins 8099 and has the same latent collision; it has not been hit, and changing a working add-on's port is not a fix for one that is broken.
- **The port is bound before anything claims it is listening.** Every log this add-on ever wrote about 8095 said `listening on 0.0.0.0:8095` immediately above the traceback proving it was not. `panel_port.bind` takes the socket first and `web.run_app(..., sock=sock)` serves on it; a busy port ends in one sentence naming the port instead of an aiohttp traceback, after a short retry whose only real case is a previous panel that has not finished dying.
- **A dynamic port costs the `watchdog:` URL, so the watch moved inside.** The Supervisor's placeholder needs a port number written into `config.yaml`; a watchdog still pinned to 8095 would poll whatever stranger holds 8095 and restart BRight on its behalf. `run.sh` polls `/api/health` on loopback instead — four consecutive misses, thirty seconds apart, then it kills the panel so the container exits and the Supervisor's restart-on-stop brings it back. `tests/test_addon_hardening.py` asserts the invariant both ways now: every add-on is watched by *something*, and no add-on that gave its port away still names one in a watchdog URL.
- **A service call that was accepted is not a speaker making a sound, and every layer of this add-on used to report the first as the second.** `media_player.play_media` returns when Core has *taken* the command; Core then resolves the media, signs a path, puts a host in front of it (`get_url`) and hands the URL to a speaker that fetches it afterwards, on its own, over the network. Nothing about that is visible from the call. So `playback_check.check` walks the links — file, media id, host, player, command, playing — and stops at the first that breaks, because telling somebody their speaker never started is noise when the file was never there. **The host step is the one that took research rather than reading**: Chromecast, Google and Nest speakers resolve names through Google's public DNS (8.8.8.8) rather than the router's, so an `internal_url` of `http://homeassistant.local:8123` — which a great many installs have — is a name the speaker is told does not exist; nothing plays and nothing errors. An *unset* internal URL is the good case (Core falls back to the machine's own IP). `wait_for_playing` is the step that separates the two claims, and the conductor runs it in the background after every show starts, because the cue list cannot wait — the clock was anchored at the play command — but a room that stays dark while the panel says "Running: 412 cues" is the same failure with the lights on.
- **Media sources are WebSocket-only, which is why `panel/ha_ws.py` exists.** `media_source/resolve_media` is the same call the cast integration makes before it hands a URL to a speaker, so asking it is the closest thing to trying it — and it is the only way to catch the one guess BRight cannot make safely: `local` is the *default* id of Core's local media source, and an install that sets `media_dirs` replaces that default, which turns every media id BRight builds into Core's own HTTP 500. aiohttp's client speaks WebSocket, so this cost no new dependency; `ws_connect` takes no `timeout=` because aiohttp changed that parameter's type across versions and the image's aiohttp comes from Alpine. The tests run it against a real aiohttp server speaking Core's handshake, because a hand-rolled fake of a protocol proves only that the fake matches the code that mocked it.
- **Two sources of folders, one list, and neither is a second answer.** `music_folder` + `additional_music_folders` are configuration (they survive a reinstall, they are what an automation-minded person edits); `stores/folders.py` is what somebody ticked in the Library tab without editing YAML and restarting to find out whether they typed the path right. `_music_folders()` merges them, ordered and deduped, and the scan dedupes by content hash so a folder nested inside another costs nothing. The *option* is read from `/data/options.json` rather than `/data/.bright_env`: a list cannot ride a shell string, because packing paths into one needs a separator and every separator is a character a path may legally contain (`/media/best of 80s:90s`). The picker browses the **filesystem**, not Core's media tree, because those have to be folders BRight can *read* — what Core will serve out of them is a different question and `/api/playback/check` is the one that asks it. Everything stays under `/media` for a reason that is not safety: `media_content_id_for` builds a `media-source://…/local/…` URI, which Core only serves for files under its media folder, so a folder outside it analyzes perfectly and never plays a note.
- **A dot has to say which light it is.** The Light Map drew a role glyph in a circle with the name in a `title` — a hover tooltip, on the device most likely to be dragging lights around a floor plan, which has no hover. Names ride on the map now; a tap selects, and the dot, its row and a bar above the floor all agree on which light that is, with the role picker and Remove on the selection rather than only in a list that had no visible connection to the picture above it. Three geometry details are load-bearing and were all found by measuring: a press that never travels is a tap (so tapping a light cannot nudge it), a 44px dot hangs half outside its own coordinate (so `placeDot` clamps the *drawing* inward, never the stored position, or a light at x=0 is half off a floor that clips), and the label flips inward at the edges. `tests/manual/measure-lightmap.mjs` drives the real `renderMap` behind a stubbed `fetch` — a copy of the renderer in the test would only ever agree with itself — and it is what found the role picker rendering at the browser's default **19px**: the 44px floor was set inside `.demo-controls` rather than once, so it covered the controls that existed and nothing added later.
- **An answer that is dropped is a success nobody earned.** The integration's three services awaited the bridge and ignored what came back, so `bright.party_mode` with nothing analyzed gave an automation a green tick and a dark room while "no analyzed tracks in /media/music — run the Library tab first" was thrown away one line from the person who needed it; they raise `HomeAssistantError` now, which is what puts a sentence in the automation trace. The bridge had the same shape one layer out (`panel answered HTTP 409`, with the panel's own body unread), and `h_ha_entities` had it sideways: `get_states` answers `[]` for an unreachable Core and for a home with no speakers, so the picker said "you have none" when the truth was "I could not ask" — `states_or_error` is the version a person is waiting on.
- **A version that nothing compares against is not a version, it is a comment.** `ANALYSIS_VERSION` sat at 1 while the analyzer gained fields, and `library.scan` marked a track `analyzed` if an analysis file existed *at all* — so 0.15.0's ranked accents shipped, passed their tests, and reached **nobody with an existing library**: their analyses had no `hits`, so the choreographer placed no accents and the brief carried no accent block, which from the outside is indistinguishable from a feature that does nothing. The constant lives in `library.py` now (the module that owns the files, and the one whose `scan` has to read it), `is_stale` compares it, and `analyze_folders` re-runs anything older without being asked twice. **`analyzed` stays true for a stale analysis** — it still has beats and a duration, the track still plays, and `server.py`'s party queue is built from exactly that flag, so downgrading it would silently drop every already-scanned track out of every party; `stale` is the separate, narrower claim. A missing `version` is *older*, never newer, or the very first analyses become the one set that can never be refreshed.
- **Rhythm says when a song hits; `analyzer/music.py` says what it is playing.** Sections and drops are a skeleton — a show built on them alone changes when the arrangement changes and sits still through everything in between, which is most of the record. Four extractors, one shared STFT (bigger frame than the beat tracker's: pitch needs frequency resolution where onsets need time resolution): **chords** (beat-synchronous chromagram against 24 triad templates, reported as *changes* only, because a show acts on the change and an ambiguous beat holds rather than flickering); **melody** (dominant pitch in the melodic register as note events — harmonic summing to prefer fundamentals over partials, **plus a sub-octave penalty**, without which the tracker follows the bass up into the melodic range the moment the tune rests and fills every silence with a phantom note); **phrases** (notes grouped into breaths, with the direction of the line, and the gap that ends one is measured in *beats* because half a second is nothing at 90bpm and two beats of silence at 160); **repeats** (beat-chroma self-similarity — coarse on purpose: it finds the chorus coming back, which is the repetition a show should answer). Every extractor has a floor below which it says nothing, because a confident answer where the audio holds none is the one failure that cannot be recovered downstream.
- **`melody` and `harmony` are the effects that consume it, and their silence has to say why.** Both render to nothing when the analysis carries no music — correct, and pixel-identical to a broken effect — so `effects.NEEDS_MUSIC` plus `Grid.has_music` let the compiler put the reason on that effect's own row in the editor (`entry["note"]`) rather than leaving a silent zero. `Grid` carries `notes`/`chords` alongside the beats for the same reason it carries the beats: one context object, read off `analysis["music"]`, optional so a bench preview works through the same code. The Effects tab previews them against a **stand-in tune** (`_BENCH_SCALE`/`_BENCH_CHORDS` in `server.py`) because the bench was always a synthetic track — a BPM box and nothing else — and an effect that previews blank there is indistinguishable from one that is broken. A note's **pitch class** picks its colour out of the *scene's palette*, never the raw hue wheel: a show whose colours are chosen by the tune and not by the scene is a show with no scenes.
- **The automatic show places them where the song has room.** Harmony on whatever is not carrying the beat (candles, strip), through the calm half; the tune on one kind of light through the verses and quiet sections. **Not in the peaks, deliberately** — a chorus already has a chase across every mover and a stab on every accent, and a third thing competing for the same bulbs on eighth notes is not more musical, it is mush.
- **A LIFX waveform runs between the bulb's CURRENT colour and the packet's, which is why the beat pulse peaked on the off-beat.** A sine anchored on the beat is at the bulb's existing level *there* and brightest at half the period — so the one effect whose entire job was "the beat" was inverted in every show BRight ever compiled, since the first release. `PEAK_PHASE` gives every shape the fraction of its cycle at which it is brightest and `peak_shift` is how far ahead of the moment a wave has to start; `_r_pulse` drops an anchor whose lead-in would land before t=0 rather than clamping it, because clamping moves the peak off the beat again quietly, for the one cue nobody is watching for. `test_the_table_agrees_with_the_simulator` pins the table against `_wave_position`, because two answers to "where is this waveform brightest" is one too many and the simulator is what the preview draws. `_r_hit` deliberately does NOT shift: its wave travels *down*, so its brightest instant is where it starts.
- **`detect_hits` returned ZERO accents, on everything, for as long as accents existed.** The peak test was `punch > local + 0.10`, an absolute constant — but `band_flux` scales both bands by the **full-band** flux peak while `punch` sums only the two bands under 2kHz, about a hundred of a thousand bins. So punch is structurally a small fraction of 1: measured on a clean, loud, isolated kick-and-snare loop it peaks at **0.0795**, against a bar of 0.10. Every effect built on ranked hits rendered nothing, which is indistinguishable from a feature that does nothing, and the suite was green throughout because its only hit fixture was a synthetic stab built out of *twice a kick plus a body* — loud enough to clear an absolute threshold no real mix reaches. The threshold is a percentile spread of the track's own punch now (`0.22 * (p97 − median)`, plus a floor at 15% of the loudest punch), which is a number in the units of the thing being thresholded and so cannot be wrong by a factor nobody notices. **`band` had the same shape of bug one layer up**: under 250Hz is ~12 FFT bins and 250–2000Hz is ~93, so comparing the raw sums answered "which band has more bins", said `mid` for nearly every hit, and left `band: "low"` — the kick layer — selecting nothing. `_band_scales` divides each band by its own p99 (a percentile, not the max: one enormous transient otherwise sets a whole band's scale) and `KICK_TONE` is **0.6**, not 0.5, because at 0.5 a bassless track's noise floor wins coin flips and hands the kick layer random snares. A ratio guard was tried and is the wrong shape: the low band is *always* the smaller of the two, so "low is much smaller than mid" is not evidence of anything — it classified every kick over a bassline as a snare. All of it is graded against three synthetic mixes in `TestWhichDrumWasIt`, at ordinary levels.
- **An effect whose selection matches no light is the one silence with nothing to do with the music.** It compiles, it saves, it plays, and the room stays exactly as it was — and the only trace was a `0 lights` on a list nobody reads. `script_actions` checks `resolve_fixtures` **first**, before the music/energy/hits reasons, because an empty cast explains the zero better than any of them. And `resolve_fixtures` matches roles and zones through `_key` (trimmed, case-folded) while ids stay exact: a zone is a name typed into the map and typed again from memory into a script, so "Inner Kitchen" and "inner kitchen" are one room and a capital letter is not a reason for a show to do nothing.
- **A swell is not a strike, and every rhythmic effect BRight had was a swell.** `pulse`/`breathe`/`sweep`/`colour_drift`/`saturate` travel smoothly up to a level and smoothly back; that is what "just a bunch of fading lights" describes, and it is what an audit of the automatic show found in every section. `hit` and `accent` are the other half: a `_set` to the peak with **no fade** (a fade still in flight would start the decay from somewhere between the two and lose exactly the attack) followed by a `saw` wave travelling to the floor. `saw` is not a parameter there — it is the only one of LIFX's five shapes that is monotone across a cycle, and the other four come back up inside it, which ducks rather than decays. Still one packet per light for eight beats, because the bulb runs the envelope. `accent` reads the analyzer's ranked hits rather than the grid (so it catches fills — and see the bullet above for why it read an empty list for months), scales the peak by `0.55 + 0.45 * strength` (an accent at 0.4 rendered at 0.4 is invisible beside a scene already at 0.55), and filters by `band` — `detect_hits` records which of the low and mid bands won each hit, which is the whole reason a kick and a snare can be on different lights. That field is `ANALYSIS_VERSION` 4; **5** is where the hits are actually found. **`melody` places a note by its PITCH** within the track's own range (`Grid.note_range`, the whole track and never the window, or the same note lands somewhere different every section), so a run up the scale is a run of light across the room and a repeated note stays put — `follow: "step"` is the old march, kept because it is what somebody may want.
- **The automatic show is four layers on different lights, not a texture per section** (`choreographer.LAYER_PLAN` / `LAYER_ROLES` / `plan_layers`). The old shape gave each section one look and ran it end to end: a four-minute track changed about eight times and did nothing in between, which is structurally incapable of following a song however good the analysis under it is. Ground (harmony, seconds-long, the only layer allowed to feel like fading), pulse (the beat, as a `hit`), hits (kick and snare, separately), voice (`melody` — **in the chorus**, which the previous rule explicitly forbade on the theory that a peak was already busy; what makes it work there is that it owns its own lights). **A fixture belongs to one layer and that is physics, not taste** — a bulb runs one waveform at a time — so `plan_layers` claims whole roles first (selecting by role is what survives somebody mapping a new bulb) and only **splits** a role by naming ids when a layer has nowhere else to go, which is what a designer does with six lamps and four ideas. `_entrances` puts a stab on a layer that has just arrived, and only where the energy *rises*: a layer arriving as a song thins out is the arrangement thinning out and wants no announcement. The six-a-song accent pass is gone — six was never the taste, it was the budget for a stab that owned every mover in the room.
- **The brief's list of bulb-side effects is generated from `BULB_ROUTINES`** (`_routine_names`), because the hand-written copy had already drifted by two: the brief listed seven while the compiler warned about nine, so a model following it exactly could write a show whose kick silently cancelled its snare. `schema_contract()` is the one place the contract is formatted; `_EFFECT_CONTRACT` takes the same `%(catalog)s` key and is a different template.
- **A track has many shows and one of them plays** (`library.list_versions` / `save_show` / `activate_version`). Every compile used to overwrite `show.json`, so asking Claude to try again destroyed the show somebody had spent an evening editing — which makes the rewrite button a thing people avoid, the opposite of what a director is for. The **pointer**, not a copy, is what makes it cheap: a compiled show is most of a megabyte on a busy track and this usually runs on a Pi, so `show_path` resolves through `versions.json` and every existing caller — the conductor, the party queue, the editor, the mirror — asks for "this track's show" exactly as before. Naming a version **pins** it, because the only reason to name something is to come back to it; the prune eats the oldest unnamed ones and never the live one, and an archive of nothing but named versions goes over the cap rather than refusing the save (a full archive that stops you working is the worse failure). Migration of a pre-versions track happens lazily on the first read and **moves** the files rather than copying them, so `os.replace` makes it atomic however the add-on dies in the middle.
- **The panel draws what the song is PLAYING, or the musical analysis is invisible** (`preview.music_lanes` + `paintLanes`). The editor drew an envelope, section tints, bar lines and `128 bpm · 7 sections · 2 drops` — so a `melody` effect that rendered zero notes looked exactly like one that worked, and a stab 200ms off the hit it answered could not be seen at all. Three lanes on the waveform's own ruler: chords as labelled blocks (a name that does not fit is omitted, because half a chord symbol is a different chord), the melody as a contour against **the track's own pitch range** (a fixed MIDI axis flattens every song into the same middle stripe), and the drums with the kick low and the rest high. `preview.lanes` is the other half: one named row per effect, built from the **walk** rather than the script, which is what tells "this effect produced nothing" apart from "this effect is fine" — and it is what let the editor's old "What it compiled to" list go, which was one row of fixture and move counts per effect and ran to forty rows on a real show. What is left under the editor is the **exceptions**: an effect that drives no lights, one whose analysis is too old, one whose waveform another cancels. When the show is fine that block is empty, and `measure-showeditor.mjs` fails if it becomes an inventory again. The lanes are flat arrays (`[t, d, midi, s]`) because this is drawing data a thousand rows long. `measure-showeditor.mjs` fails on blank lanes and on four canvases that disagree about where 1:30 is.
- **The Party tab is one screen and the vibe is not on it.** A vibe steers the **director**, which is a compile-time decision, and in a party it reached only a track with no show yet (`preparer` returns early when `load_show` finds one) — so on a library with shows already built it did nothing at all, on a fresh one it silently decided what went to disk forever, and two parties naming different vibes over one track gave whichever ran first. That is not a rough edge; it is a field that cannot have a coherent meaning where it was, and it now sits above the track list on the Shows tab, sent only on a **Claude** compile. What is left is one surface: tick the shows, press Play, ⏮/⏭ between them — and each row may **pin a version**, defaulting to the live one so the newest plays without anyone choosing it (`load_show(hash, version_id)`; a pin that has been pruned falls back rather than skipping the song). Saved parties are saved **sets** — a name on exactly what is on screen — and **Load** fills the screen rather than starting it, because seeing what Play would do is the whole reason there is only one surface. `party["tracks"]` and `bright.start_party` are unchanged, so automations keep working.
- **Every effect BRight had was a brightness effect, because `SetWaveform` carries a whole colour and moves all of it.** A measured audit (render each type, simulate it, look at what the ROOM does) found two of seventeen moving brightness past two levels and none able to move colour while holding the level still. `SetWaveformOptional` (message 119) is the same bulb-side engine with a per-channel mask, and it buys `colour_drift` (hue travels, brightness frozen — measured at 356° of travel with the level constant to three decimals) and `saturate`. `level` is the other half: brightness follows the analyzer's own 20Hz loudness envelope, which existed from the first release and was read only to find sections and drops — the song's real shape, with nothing following it. Its `gamma` is what makes it a lighting choice rather than a VU meter.
- **A LIFX bulb runs exactly ONE waveform at a time**, which is not a detail — it is how `halt_waveform` stops a show. So two of `BULB_ROUTINES` overlapping on one fixture is the later cancelling the earlier, and from a sofa that reads as an effect that mysteriously does nothing. `compiler._routine_clash` reports it on the effect's own row (naming what is being replaced) and the brief tells the director the rule; it is **reported, never refused**, because a stab interrupting a pulse on the drop is a real technique. `test_the_catalog_agrees_with_itself_about_which_are_routines` renders every type and checks the set against what actually emits a wave action, so a new effect cannot join the class silently.
- **An effect is the unit, and the map is what it travels through** (`panel/director/effects.py`). Twenty-two types (wash, fade, build, pulse, strobe, chase, sweep, breathe, sparkle, colour_cycle, rainbow, theater, stab, blackout, melody, harmony, colour_drift, saturate, level, hit, accent, aux), each a catalog entry plus one render function — the UI builds its whole form from `catalog_payload()`, so adding a type touches neither the panel nor the compiler. An effect names a `select` (ids, roles, zones, exclude) and **everything it does not name is untouched**, which is the whole reason a show is built from effects rather than scenes: most of the room is usually meant to stay still. `order` comes from the light map (`x`, `-x`, `y`, `-y`, `center_out`, `edges_in`, `snake`, `zone`, `listed`, `random`) and every ordering is total and deterministic — `random` is seeded by name, never `random.shuffle`, because a show somebody liked on Friday is the show they get on Saturday. Role manners are the default and an override: `respect_roles` caps brightness per role and keeps candles out of the harsh set, and an effect that means it can own a fixture outright says so. Parameters are **clamped, never rejected** — these files are typed by hand, and a show that refused to compile over `depth: 1.2` would be a worse tool than one that reads it as 1.
- **One rendering, two consumers.** Every effect renders to *actions* ("this fixture, at this moment, becomes this colour over this fade" / "runs this waveform for this many cycles"); `compiler.render_actions` turns actions into packets and `effects.simulate` turns the same actions into preview frames. A preview drawn from a second implementation of what an effect does is a preview of the second implementation — it would look right while the room stayed dark. The panel converts HSV to CSS and nothing else, because the frames ARE bulb colours. Every action carries the name of the effect that produced it and that name rides into the cue's `desc`: it is the only thread from a packet in a 2,000-cue timeline back to the line in the script a person wrote.
- **The script language is version 2, and version 1 still compiles.** A scene carries `effects`; `moments` pin an effect to an instant. `motifs` and `features` are translated into their effect equivalents at compile time (`_from_motif`, `_from_feature`) rather than kept as a second rendering path — a vocabulary that grows must not invalidate what was written against it, and shows are artifacts people keep. `SECTION_LEVELS`, `ROLE_RULES` and the palettes are unchanged and shared by both.
- **Automatic is the same file as hand-written.** The choreographer emits ordinary effect instances — there is no private vocabulary the automatic show can use and a person cannot, which is what makes "automatic but completely editable" true rather than aspirational. It reads the map for real: three or more moving lights get a chase (with a seeded travel order), two get `theater` alternation, because a chase across two bulbs is a flicker. A drop gets a `build` whose window **crosses the section boundary** — tension starts inside the section before the drop and ends on it — plus a `stab` and the aux switches.
- **The show file is the show, and it is openable** (`GET/PUT /api/show/{hash}/script`). Editing it goes through the same validator, compiler and per-bulb budget the director's own output does; a refusal names what to change (`raise an effect's step_beats, narrow its selection`) and leaves the show that was there untouched. Every compile mirrors the script to `/config/.bright/shows/<track>-<hash>.json`, because /data is invisible to Home Assistant and a file nobody can open is not editable. **The mirror is a copy and the copy is not the record** — editing it changes nothing until `POST .../script/import` reads it back, deliberately: a half-typed JSON file being picked up by a party at 11pm is not a feature. A broken one is reported with the JSON parser's own line number, which is the single most useful sentence you can hand somebody who has just edited a thousand-line file. The stale-name sweep before each mirror write is what stops a retitled track leaving two files for one show.
- **A Stop button that is always there is a button nobody trusts.** All three (Party, Shows, the Lab's sync proof) render only while `state.active` says a run is in progress — the conductor's own answer, written beside the status in `_write_state` so "idle" can never arrive still claiming to be running, rather than a string comparison against the words that happen to mean running today. `lights_busy` is the second, narrower question ("are cues still going out"), false once the cue list is spent and the lights are holding what the last cue left them at. One poller for the whole panel, because "is a show running" has one answer and three buttons used to guess at it separately. The integration's sensor carries both, so a dashboard keys on the same flags the panel does.
- **Stopping puts the room back, and "back" is not always where it was.** Restoring the pre-show snapshot is right when the show interrupted an evening and wrong at 1am — what people want then is a scene they already have. A party (or a `bright.stop_show` call) may name one, and it is called *instead of* restoring, because two answers to "put the room back" would fight and the configured one wins. A scene that fails to run falls back to the snapshot, so the room never keeps the party colours. Parties are named saved evenings (`stores/parties.py`) — speaker, folder, vibe, allowed fixtures, end scene — matched case-insensitively, because the name is what an automation or a voice command types. `bright.start_party` requires the name so a typo fails loudly instead of quietly playing the default folder; `party_mode` merges a party's settings under anything given explicitly, which is what "the usual thing, but on the kitchen speaker" means. A party's fixture list is enforced at **dispatch** (`conductor.filter_cues`), not at compile: one compiled show serves every party, and a show cached per fixture-subset would be a cache keyed on something nobody can see.
- **Two ways to get a bulb on the map, for two different moments.** `POST /api/map/import-lifx` adds every unmapped bulb at once and is the right button exactly once; the picker (`GET /api/map/candidates` + `POST /api/map/add-lifx`) adds one at a time with a role and a zone chosen as it goes on. Six lamps dropped on the middle of the floor plan named after their serials is not a map.
- **The show editor is a picture, and the picture is served by the compiler's own walk.** `compiler.script_actions` is the single route from a script to actions — `compile_show` renders those to packets, `director/preview.py` simulates the same list into frames. That is the effects contract ("one rendering, two consumers") at the scale of a show, and it is what makes a live editor honest: a preview that walked the script itself would be a preview of its own idea of it. The extraction was verified against the pre-refactor compiler on a real generated show (898 cues, byte-identical), not argued for. Two shapes come out of it, because the editor asks two different questions: `window` (frames at 15fps over a few seconds, for scrubbing) and `overview` (the whole song, one row per light, for the strip). `simulate` grew a `start_s` that skips emitting frames while still **applying** every action before them — sampling every fixture per frame is the expensive half and a window skips it; skipping the actions instead would preview a show that began wherever you scrolled to. **Every preview request carries the script being edited**, which is the whole of "live": the server previews what is in the editor, not what is on disk, and the compiler's refusals arrive next to the effect you just changed rather than at save. Nothing on that path writes.
- **A strip column is one instant across the room, never an average and never a per-light peak.** Averaging invents a colour the show does not contain. Per-fixture peaks were tried — on the theory that a strobe was too short to survive point sampling — and **measured worse**: a strobe alternates bright and dark, and taking each light's brightest sample throws the dark half away, so it showed one changed column where point sampling showed two. The case that prompted the change was not a sampling failure at all; the effect had been dropped on the same instant as the drop's stab, which owns those lights there, so the show really was identical. Effects layer and the last one to name a light at a moment wins. The change was reverted rather than kept for its nicer story.
- **An editor may not quietly rewrite what it opens.** Three ways it did, all found by driving it: the effect dialog wrote `select: {ids: [...]}` from its tick-boxes, which turned "every candle" into "these four bulbs" — wrong the moment a candle is added, and the automatic director selects by **role** for nearly everything it writes; it defaulted the travel order to `listed` when the compiler's default is `x`, so opening a chase and pressing Apply changed how it crossed the room; and it wrote that default into the file even when nothing was picked. So the dialog edits ids, roles and rooms, carries `exclude` it has no control for, ships `DEFAULT_ORDER`/`DEFAULT_ALIGN` **from the catalog** rather than keeping a second copy of them, and omits a key it did not change. `measure-showeditor.mjs` asserts a no-op edit is byte-identical, which is the test that would have caught all three.
- **A row that misreads a selection is a row you edit by mistake.** Effect rows said `all lights` for every effect the director wrote, because the label counted `select.ids` and the director names roles. `edDescribeSelect` renders what is actually there.
- **`tests/manual/bright_demo_panel.py` + `measure-effects.mjs`.** The preview is a canvas and a floor of dots; "the timeline painted" is not something a server can answer, so the demo boots the real panel against a seeded house and Playwright drives it at three widths — failing on a blank canvas, an unlit floor, a control under the touch floor, a Stop button visible with nothing running (and one that stays hidden when the state says otherwise), or any page error. The demo's seeded device registry is `{"devices": [...]}`, the shape the engine actually reads: a demo that seeds a shape nothing reads boots with no bulbs and a show compiled for nobody, which is how it was found. `measure-showeditor.mjs` is the editor's own measure, on the same booted panel: it fails on a blank strip, an unlit floor, a scrub that moves no light, a scene block that does not move the playhead, a no-op edit that rewrites the show, a real edit that does not reach the preview, or a control under the touch floor. It edits but never saves, so all three viewports open the same seeded show.

- **`available()` answers one of six questions, and the folder outlives the listener that made it** (`panel/director_check.py`). It tests whether `/config/.brain/tasks` is a directory — created by brAIn's automation listener at startup and left behind when that listener stops — so a brAIn that is not running looks *identical* to a working one until the wait expires: ten minutes of spinner, then a message blaming a timeout, which sends somebody to the slowest thing in the system when nobody was listening at all. The listener **claims** a task by renaming it before doing any work, so an un-renamed file after `CLAIM_GRACE_S` (30s, six of its 5s fallback poll cycles) is proof rather than a guess, and it is a *different sentence* from a task that was claimed and never answered — one names the switch to turn on, the other points at brAIn's log. `director_check.check()` walks the whole chain (brAIn → task folder → BRight can write there → something claims → something answers → the room has lights) and stops at the first break, the shape `playback_check` uses for audio; it runs a real trivial round trip rather than describing one, because a test of the actual path is the only kind worth trusting.
- **Asking Claude for something is a job, never a request** (`server._claude_job`). A show script takes minutes to write and ingress cuts a long request, so what reaches the browser is not the panel's error but the *absence* of a reply — `load failed` in Safari, `Failed to fetch` in Chrome — about a director that is still working and will go on to save a show nobody was told about. All four Claude routes (compile, revise, describe an effect, invent effects) start a `jobs.py` job and hand back its id; the panel's `claudeJob` polls it and counts the seconds, because a spinner that never changes is a spinner people press twice. `jobs.py` was written for exactly this and says so in its own docstring — the Library's analyze pass had always used it and the Claude routes had not, because when they were written the director was quicker. **That is the shape of the bug**: a latent limit becomes a failure months later, when the brief grows and the model moves to Opus, without a line of the code that breaks being touched. A second press returns the LIVE job's id rather than a collision, so both presses watch one run. Argument checking still happens before any job starts — a typo must not become a minute-long wait — and the director's timeouts (600s a script, 180s an effect) are now the director's own budget rather than whatever a proxy will hold a connection open for.
- **Nothing on the BRight panel is public.** `/api/health` was the one public prefix, and it was public for exactly one caller: a Supervisor watchdog polling from off-network. Its replacement runs inside the container over loopback, which `_lan_gate` already trusts, so the exemption lost its caller and went with it. Everything else about the gate is Minecraft's, for Minecraft's reason — the peer address, never `X-Forwarded-For`.

Shared brand sources live in `branding/brain/` and `branding/minecraft/` (twelve SVGs each, plus `render.mjs`, which regenerates every PNG in the repo) and `brands/` (the four-PNG brand set per domain); cross-add-on tests live in `tests/`. **`brands/` is no longer a submission staging area** — since HA 2026.3.0 home-assistant/brands auto-closes any PR adding a new `custom_integrations/` folder. Artwork reaches the integration page through a **`brand/` folder beside the manifest** (`custom_components/<domain>/brand/`), which HA serves itself and prefers over the CDN; both integrations ship one, and both deploy by recursive copy so nothing extra packages it. The `brand/` folder is what HA reads — a bare `custom_components/<domain>/icon.png` is read by nothing, which is why that file is gone. `render.mjs` writes `brand/` and `brands/` from the same SVGs and they are byte-identical on purpose: which route resolves first is not ours to control, so neither may drift. Both are the brands spec, which is why their logos are 341×256 / 682×512 and the add-on store's are 512×384 — brands caps a logo's shortest side at 256. Both marks are the same lockup — the parent's BR ligature, and a gable that doubles as the `A` — and what tells the two apps apart is how the roof and the small caps are *drawn*: brAIn keeps the parent's smooth gable, sets `AIN` smooth, and carries its signal rules; BRUH Minecraft steps the same roof onto a 16u block grid, sets `MC` on it, and drops the signal so the blocks carry it. The two roofs are deliberately different paths — a lockup with blocky caps under a smooth roof is two drawings, and `test_each_app_draws_only_its_own_roof` is what stops one app wearing the other's. Never redraw either, and never recolour the roof away from azure. **Nothing ships the gable on its own** — not an add-on icon, not a favicon, not a panel header. The roof is the family mark; it says BRUH and says nothing about which add-on you are looking at, so two add-ons wearing it in the same sidebar are two add-ons nobody can tell apart. That is what the square lockups are for, and `test_no_asset_is_the_gable_alone` is what keeps it true. The panel's top bar carries the full wordmark inline, split into `.wm-ink` / `.wm-roof` / `.wm-ai` / `.wm-signal` so one file serves a light and a dark bar.

**The top bar has two shapes and no third.** At ≥1240px it is one 56px row; below that it is the two-row bar — status and actions on top, the six tabs on a full-width strip beneath with each name under its icon. There was briefly a third band (960–1239px: one row, labels deleted, tabs shrunk to glyphs) and it was the worst possible one to have, because it is what a laptop with the HA sidebar open renders at — the compromise shape was the one most people saw, and widening the window made the tabs grow. **No width gets a row of bare glyphs.** Nothing in the bar may shrink (`.topbar > * { flex: none }`), so a fit is binary and an overflow is something a test can see; nothing hides its own words to fit, either. What gives way is the row, not the label. Tabs cap at 168px and centre so a 1200px strip isn't five 240px targets around a 20px glyph. Every target is ≥44px (chips ≥40px); adding anything to the bar moves the measured widths, so re-run `node tests/manual/measure-topbar.mjs` (Playwright; `CHROMIUM_PATH` if the browser isn't where it expects) and take the breakpoints from what it reports rather than guessing. All five measure scripts also run in CI as the `layout` job, so a regression fails the PR — running them locally is about reading the failure next to your editor, not about being the only enforcement. It measures three bar states per width (running / paused / failed login) because none is a superset of the others, and it fails on any target under the floor as well as on overflow. Panel heights come from `--bar-h`, which the panel remeasures at runtime. **A status chip that is permanently green does not belong there** — the auth chip renders only for trouble, and the space it used to hold pays for the usage pill's second number (`Session x% · Week y%`, each labelled in the bar).

**On an insight card the title gets the row, and two controls sit beside it.** The head used to be one flex line — icon, category, title and six `flex: none` icon buttons — so on a phone the buttons took ~250px of a 390px card, the category wrapped to three lines and the title truncated to `Upstair…`. The eyebrow is the part that gives way (one line, ellipsis); the title wraps to two lines and is never truncated. `⤢` stays on the card because it is the only action on *what is on screen*; Regenerate/Edit/Feedback/Add to dashboard/Delete live in `⋯` (`cardMenuButton`) with a name and a line of what-it-does each. Re-run `node tests/manual/measure-cardhead.mjs` after touching the head — it fails on a truncated title, a wrapped category, an overflowing head, or a target under 40px. **There is no "refresh everything" control**: it was an unlabelled circular arrow in the top bar that queued a Claude run for every card, beside the pill reporting the usage it spends.

**No text control may be under 16px on touch.** iOS Safari zooms the page in on focus below that and never zooms back out, which inside an ingress iframe strands the panel at an arbitrary scale — the docs search box at 14.4px is how it was found. The floor is set once in a `@media (pointer: coarse)` block, not per control, so anything added later is covered by having been added.

**A replayed conversation is budgeted on speech, not events.** `conversations._budget` keeps every `user`/`text`/`thinking` event first and spends what's left on the newest tool calls. A flat newest-N looks right and is badly wrong: measured on a real transcript, 92% of replay events were tool calls, so a 400-event window carried 3 of 17 user turns — which is what "switching faces loses messages" actually was. `_pair_up` keeps a call and its result together or drops both; half a pair is a spinner that never stops or an invisible event still costing a slot.

**Every control in the bar does its own job, and nothing is in it twice.** Three controls used to open Settings, so a bar reporting three different things answered all of them with one dialog. The usage pill opens a disclosure popover (`#chipPop`) with both windows, their resets and what the budget gates — a *press*, never a hover, because a `title` is unreadable on the device where that pill matters most. The paused chip presses straight through to `saveSettings({auto_enabled: true})`; it renders **only** for that, because "usage budget reached" had a chip of its own beside a pill already showing the number it was about, and saying it twice is what wrapped a phone bar onto a third row. A reached budget is now the pill's own warning dot plus a line in its popover. ⚙ is the only route to Settings. Storage access goes through `prefGet`/`prefSet` — a browser may refuse an iframe its `localStorage`, and a throw at the top level takes out every handler declared below it.

**The Terminal tab has two faces and one session.** `terminal_ui` (`settings_store`, default `chat`) picks between the chat renderer and ttyd; `body.term-classic` is the switch, and `#termMode` on the tab flips it as well as ⚙. **The switch carries the conversation, both ways, and it is the only control that does** — a second "continue in the terminal" button beside a switch that also moves you is how you end up unsure which one actually moves you. Every route in goes through `switchTermMode`: chat→classic runs the handoff (stop our process, write `/data/terminal-handoff.json`, open a tmux window on `--resume`), classic→chat calls `/api/chat/adopt`. Adopt exists because the tmux Claude is not ours and has no API — but Claude Code writes its transcript as it goes, so **the most recently written conversation in the project directory is what the terminal was last doing**, and that is what gets resumed. It is a hand-off, not a mirror: one process owns a conversation at a time. The terminal's shell is never killed to make the switch work — it is somebody's shell — and adopt is refused mid-answer, because losing an answer being written is worse than waiting for it. Chat drives the *same* Claude Code — `chat_session.py` runs one long-lived `claude -p --input-format stream-json --output-format stream-json` in `/config`, so it inherits the same `settings.local.json` permissions as the listeners and the fixer. **Everything that knows the CLI's wire shape lives in `_normalise`**; the panel only ever sees `text`/`text_delta`/`thinking`/`tool`/`tool_result`/`notice`/`result`/`state`, and an unrecognised event is dropped rather than rendered raw. Deltas and run stats carry `_keep: False` because the `assistant` event that follows repeats the same text whole — keeping both doubles every answer on the next reload. The transcript (`/data/chat_transcript.json`, capped) is *ours*; Claude Code owns the real conversation and resumes it by `session_id`, so losing the file costs a scrollback and never context. Stopping asks with a `control_request` and kills-then-`--resume`s if nothing answers within `INTERRUPT_GRACE` — an older CLI ignores the request silently, which is indistinguishable from thinking. One SSE stream per viewer, opened only while the tab is in front; the first frame is the snapshot, so no client has to stitch "what it was" onto "what happened next". **A spawn is watched until the CLI says its first word** (`START_GRACE`): a process that dies before speaking with `--resume` on its argv means the CLI no longer holds that conversation — the store prunes old sessions — and the old behaviour was a chat that spawned, died silently, and errored on every send, while the restored resume id respawned the same failure forever. The id is dropped, a notice says the context is gone (the replayed transcript stays), and the session opens fresh; `resume()` returns `resumed: false` so the panel can say so out loud rather than letting the next answer reveal it. Died-before-speaking with nothing to resume is an error state carrying the stderr tail. **The chat picks its own model** (`chat_model`, a panel setting; `POST /api/chat/model`): the picker opens from the model name in the meta line and from ⋯ → Model, offers the same `MODEL_CHOICES` ⚙ does (its empty-id "CLI default" row filtered out — in the chat, "" means "follow ⚙ Settings" and a Default row already says that), and never touches the global `model` option, which would silently change what every insight run costs. Applying it is a stop and a `--resume` — the model is an argv flag — refused mid-answer. **Every "is a restart needed" question is asked of `_spawned_model`, never `session.model`**: the server refreshes `session.model` from settings on every request, so intent routinely agrees with a pick the live process has never seen — which is how the picker answered "already that model" about a session still running the old one, forever, because a long-lived process never respawns on its own. `send()` runs the same comparison, so a ⚙ edit lands on the next message; and `--model` stays on a `--resume` argv on purpose, because a resumed session otherwise keeps the model it remembers. **`set_model`'s response carries `model_label`**, because the event that refreshes the meta line (`init` → `info`) does not arrive until the next message — a restarted `--resume` process says nothing until spoken to — and the meta line is the only confirmation a pick landed, so waiting for it is how the picker looked like it did nothing. **`error_max_turns` marks `_respawn_pending`** and the next send restarts with `--resume`: the cap is a per-process runaway guard, and a guard that refuses has to change the next attempt — "start a new chat to carry on" was charging the person's conversation for it. **`thinking_delta` streams like `text_delta`** (live-only, sealed by the assistant event's whole block): the panel keeps a FIFO of streamed think boxes and the final block replaces the streamed copy in place, because the block only arrives when the message closes, and retro-inserting reasoning after its conclusion is what "the chat doesn't show thinking" actually was. The three dots are a status line now — verb, current tool, elapsed seconds — for the whole turn, not just until the first token. **Chat sessions can never appear in the Claude app** ("connected" is Remote Control, which requires an interactive session — anthropics/claude-code#30447): not brAIn's to fix, so the session popover and the docs say it out loud and point at the face switch, which moves the same conversation into a terminal session that can register. **Deleting a conversation is a move, not an unlink** (`conversations.delete` → `/data/chat-trash`, TTL'd and capped): the ✕ on a rail row hands back an `undo_store` token and the toast's Undo moves the file back, refusing over an occupied path. The open conversation is refused server-side ("start a new chat first") — deleting the ground the live session stands on either kills it or quietly forks it. This is the one mutation `conversations.py` makes in the CLI's store, and it never edits file contents. **Batch delete is the same move, per row, with one token** (`/api/chat/conversations/delete`, undo kind `conversations`): the open conversation is *skipped and reported*, not a reason to fail the batch — a select-all that refuses outright teaches people to deselect one row by trial and error — and the batch is capped at `TRASH_MAX`, because accepting more than the trash holds would make the oldest of the batch unrestorable while the toast still offers to restore it. Selection mode (`convSel`) spans the rail and the ⋯ dialog as one mode, since they are one list; every selection press repaints from what is already fetched (`convModalRows`), never a request. **The meta line under the composer is measured, not assumed visible**: `#viewTerminal`'s negative margins cancel `.wrap`'s padding, so they follow the breakpoint the *padding* changes at (640px), and the bottom margin is 0 — `body.term-open` has already zeroed the wrap's bottom padding, and a leftover negative margin shortens `.wrap`, whose `overflow: hidden` clipped the last ~20px of the view: the model-and-context line, half-swallowed at every width and worst on a wide screen. Geometry can't see it (`getBoundingClientRect` was right; the paint wasn't), so `tests/manual/measure-chatmeta.mjs` checks with `elementFromPoint`.

**A run that costs something has to say so, on the thing it cost it for.** Generating a card is the most expensive thing the add-on does — a bundle out, a rendered visualization back, typically 25–45k tokens — and the numbers came back in every result envelope, were used to add to a total, and were rendered nowhere. The only visible effect was the usage pill moving, attributable to nothing, which is how "insights use a lot" becomes a suspicion rather than a reading. `usage_store.split_from_meta` derives it **once, server-side**, `total` being `tokens_from_meta` and nothing else: the card, the log line and the budget are one number, and a second copy of "which fields count, and that a cache read does not" written in JavaScript would be a second answer waiting to drift from the one the budget uses. Four surfaces, all the same figure — the job carries `prompt_chars` so the spinner can say `500 entities · ~33k tokens sent` *before* the answer exists (the only place a `CHARS_PER_TOKEN` estimate is allowed, and it is prefixed `~`); the card's foot carries `meta.cost`; the usage popover itemizes `budget_state`'s `breakdown`, which the run ledger has recorded an id per run for since the budget existed and nothing ever read back. The breakdown is **capped with the tail folded into one row, never truncated**, or the itemization sums to less than the percentage it is explaining — and it is labelled as brAIn's own runs, because when `source` is `account` the pill covers the terminal, the chat and voice too and a list read as exhaustive is how you conclude a terminal session is free. **An asked question is the expensive kind**: `collect_bundle` gives a category its slice and a question the *whole* home (`filter_states(states, registries, [], [])`, up to `MAX_ENTITIES`) plus device context, because the question could be about anything — so a handful of questions costs what a dozen scheduled refreshes do, and that belongs in the docs rather than in a support thread. `positionChipPop` bounds the popover's height to what is below the chip and lets it scroll: it held two rows and a sentence when it was written, and a list whose last rows are under the bottom of the screen is the tooltip bug sideways.

**A row in the bundle is 500 rows in the prompt, so its encoding is a cost.** `slim_state` spends the fewest characters that still carry each signal, and the three that were overpaying are measured, not guessed (72,943 → 52,086 chars on a 500-entity home). `lc` is **minutes since**, not a 19-character ISO stamp: staleness is the only thing `last_changed` is read for, and the absolute form also made the model diff it against `meta.now` to get there — minutes rather than hours because "6 minutes ago" and "an hour ago" are different facts and cost the same. `n` is dropped when `_slug(n)` equals the object id, which is what HA names an entity by default; a *renamed* entity keeps it, which is the case the field exists for. An `unavailable`/`unknown` row keeps only `e`/`s`/`a` — its unit and device class describe a reading that is not there. All three are in the prompt's field contract, because a field that is conditionally absent and undocumented reads as missing data. **Retrieval was measured and does not pay here**: a two-step "index, then fetch what Claude picked" costs an index (~29k chars — the ids dominate and every one has to be listed) *plus* the picked rows, which lands above simply sending all 500 slimmed rows; and an agentic loop re-sends its conversation every turn and can die on `--max-turns`, which the docs already call the most expensive setting in the add-on. What retrieval would buy is *history on an asked question*, which the single-shot path cannot afford — a capability argument, not a cost one.

**The context pill measures the conversation, not the work.** Its numerator is one model call's `usage`, taken off the `assistant` event — never the `result` envelope, whose `usage` is the whole turn added up. A turn is many calls and each one re-sends the conversation, so summing them measured how hard Claude worked and reported a ten-tool turn as ten conversations. Its denominator comes from the model's **version**, not its family: the table used to say 200K for every Opus and every Sonnet, which was true when it was written and is wrong for every model the add-on now runs — both went to 1M at 4.6, Haiku stayed at 200K. The two failures multiplied, and the pill routinely claimed several hundred percent of a window five times too small. A model whose version cannot be parsed reports its token count and no percentage: the candidate answers are 5× apart, and a percentage of a guessed denominator is worse than none. `BRAIN_CONTEXT_WINDOW` is the escape hatch for a model that ships before the table learns about it. **The denominator is re-derived the moment the model changes** (`_rewindow`, off the `init` event), not on the next turn: `--resume` carries the conversation, so the token count survives a pick and the window does not belong to it — moving to Haiku left 42k being divided by 1M and reported as 4% of a window it fills 21% of, and it stayed wrong until something else happened to refresh it.

**A model id is turned into a name in exactly one place, and it is the server** (`chat_session.pretty_model`, on the same version parser the window uses; shipped as `info.model_label` and `default_model_label`). The panel had a second regex for it and the two drifted the way a second copy always does: it read `claude-haiku-4-5` as "Claude Haiku 4" and took the leading digits of a date stamp for a version, so `claude-3-5-sonnet-20241022` came out "Claude Sonnet 2". The minor version is the whole point — every 4.x model of a family printed the same name, and **the label under the composer is the only confirmation a pick landed**, so a working selector was indistinguishable from one that did nothing. A tier alias (`opus`) prints no version, because the account resolves it; an unreadable id prints itself, because a made-up name for a model we cannot read is worse than the id. **The picker's Default row names the global model, so ⚙ has to hand it back** — `/api/settings` returns `model_label` and `saveSettings` refreshes `chatState.defaultModel`. ⚙ is reachable from the Terminal tab and the stream's opening snapshot is not reopened by it, so that row — the *highlighted* one whenever no override is set — went on naming the model you had just replaced.

**A popover whose anchor has gone is dismissed, not relocated.** `positionChipPop` bails on a zero-sized anchor: ⋯ → Model opens `#chipPop` from a menu item and the same press closes the menu behind it, so there is nothing left to measure against and the next reposition put the popover at (8, 6) — the top-left corner of the screen. Same call `scroll` already makes, for the same reason.

**Two things float over the terminal, and no more.** `#termMenu` (⋯) and `#termExpand` (⤢) — everything else is a menu item in `#termMenuPop`, whose buttons are static markup carrying the ids their handlers are bound to (rebuilding a menu's controls on open drops every listener). ⤢ is alone because it is also the way back from a folded bar. Five translucent squares stacked over someone's output was the clutter the chat view exists to avoid.

**The terminal folds the bar away.** `body.term-immersive` hides `.topbar` and zeroes `--bar-h`; `body.term-kb` marks the automatic case. Two independent reasons, tracked separately in `termChrome` so neither clobbers the other: ⤢ (`#termExpand`, remembered in `localStorage`) and the software keyboard being up right now. Only the ttyd frame can detect that keyboard — iOS does not resize an iframe's visual viewport, and `inject.html` already does the measuring for its own toolbar — so it posts `{type: "brain-keyboard"}` up and the panel accepts it only from `#termFrame.contentWindow`. tmux drops its status line under 90 columns via `client-attached`/`client-resized` hooks; the width test is a shell `[` because tmux does not expand a nested `#{client_width}` inside its own `#{<:a,b}`, which silently answers "narrower" at every width.

## Key Architecture

### MCP Server (`ha-mcp-server/ha_mcp_server.py`)
- Stdio-based MCP server that Claude Code launches automatically
- Uses `SUPERVISOR_TOKEN` for HA API authentication
- Provides tools for entity states, device control, area listings (`get_areas`), registry listings (`get_registry`: areas/floors/labels/devices/entities/integrations/users via the WebSocket API), dashboard reads (`list_dashboards`, `get_dashboard`), camera snapshots (`get_camera_snapshot`, returned as MCP image blocks), history/long-term statistics (`get_history`, `get_statistics` via the WebSocket API), service calls (`call_service`, optional `return_response` over WebSocket for services with response data), logs, template rendering, config reload
- Tools are registered via `TOOL_IMPLEMENTATIONS` (name → function name, late-bound) with argument contracts derived from each tool's inputSchema; add a tool = function + schema in `TOOLS` + one mapping line

### Startup Flow (`run.sh`)
The order is `main()` at the bottom of `run.sh`; the panel is last because it
is the foreground process.

1. Health check
2. Environment initialization (`/data` for persistence), Claude Code update
3. Non-root user setup (`claude` UID 1000, `claude-run` wrapper, shell profile)
4. Tool installation, then the `brain` / `ha` CLI dispatchers, then persistent packages
5. Context generation (`/config/CLAUDE.md`)
6. Broken plugin cleanup (removes stale `claude-homeassistant-plugins` entries)
7. MCP server configuration (writes `.mcp.json` with proper ownership) + watchdog
8. Assist scoping, then custom integration deployment to `/config/custom_components/brain/`
9. Background daemons: usage-limits tracker, memory consolidator, study watcher
10. Optional: Assist + Automation integrations
11. ttyd web terminal launch (with the mobile UI spliced in via `build-mobile-index.py`)
12. The panel — the foreground process, and the ingress target

### Custom Integration (`custom_components/brain/`)
- Deployed automatically to `/config/custom_components/brain/` by the add-on at startup
- Registers a `ConversationEntity` so "brAIn" appears in Settings > Voice Assistants
- Provides `brain.send_prompt`, `brain.run_task`, `brain.run_insight`, `brain.add_memory`, `brain.study`, and `brain.clear_conversation` services
- BRUH Power Tools (`power_tools.py`): 65 admin-gated registry-management services under `brain.*` (areas, floors, labels, entities, devices, integrations, helpers, zones, persons, blueprints, statistics, users, diagnostics, dashboards, repair issues), adapted from [Spook](https://github.com/frenck/spook) (MIT) with validation-first handlers, response data on creation services, and dry-run-by-default orphan cleanup (entities *and* devices); catalog metadata generated in `services.yaml`/`strings.json`/`translations/en.json`/`icons.json`, consistency enforced by `tests/test_power_tools.py`. **Nothing is create-only**: every attribute a `create_*` accepts has a service that changes it later, and every registry object that can be created can be renamed and deleted — `tests/test_power_tools.py` asserts the `rename_*`/`delete_*` families are complete. An `update_*` writes only the fields the caller named (`_partial_update`); filling the rest from `call.data.get()` blanks them
- **The via_device chain is somebody else's data, so nothing walks it by recursion.** `disable_device` climbs `via_device_id` to disable a hub once its last live child goes, and `enable_device` climbs it back down — both by recursion, on a chain nothing in Home Assistant makes acyclic, because `via_device_id` is simply whatever id an integration reported. `alexa_media` reports every device as its **own** via_device, so the walk had no end: `RecursionError` on each of an Echo/Wyze/Ecobee household's devices, *after* writing some of the disables — a registry mutation stopping halfway is the worst shape this failure could take. Both walks are iterative with a seen-set, and they stop where the chain would repeat rather than where the interpreter gives up; stopping there costs nothing, since every device on a cycle has been visited by the time it closes. `tests/test_power_tools_device_cycles.py` runs the old recursion into its `RecursionError` before pinning the new walk, and an AST check fails any future function that both mentions `via_device_id` and calls itself. It imports `power_tools` behind permissive stubs and **puts `sys.modules` back**: several test modules install partial `homeassistant` stubs and whichever loads first wins a shared table, which is how the file passed alone and failed under `unittest discover`
- Insight jobs (config entries of type `insight`): scheduled Claude reports rendered to `sensor.<job>_insight` (markdown attribute + ready-to-paste `card_yaml`); prompts support HA templating
- 3.0 transport: worker pool serves an internal HTTP API (:8098, token on the shared volume); integration streams deltas into the chat log (SSE) and falls back to file IPC; `binary_sensor` reports pool health
- `sensor.brain_health` (`ok`/`degraded`/`failed`) reading the verdict out of the diagnostics mirror
- Usage-limit sensors reading from `/config/.brain/usage_limits.json` (real Anthropic account utilization; requires OAuth/subscription login)
- Communicates with the add-on via shared files in `/config/.brain/`
- Request/response flow: integration writes JSON (unique per-request file id) → add-on processes → add-on writes JSON response named after the request id
- Conversation continuity: the assist listener maps `conversation_id` → Claude session uuid in `/config/.brain/sessions/` and resumes the session on follow-up turns (`--session-id` / `--resume`); falls back to replaying recent history when resume isn't possible

### Permissions Architecture
- **A security default may only fail closed, and `${VAR:-default}` cannot express one** when the safe value is the empty string. `run.sh` writes `BRAIN_CLAUDE_PERMS_FLAG=""` for the OFF case, so `brain-menu.sh`'s `${BRAIN_CLAUDE_PERMS_FLAG:-$PERMS_FLAG}` — with `PERMS_FLAG` initialised to `--dangerously-skip-permissions` — substituted the dangerous default on the *normal* path, not just when the env file was missing. Every picker session ran with prompts disabled whatever the option said. The flag starts empty now and only ever becomes what `run.sh` set.
- **A refusal is not a failure, and the chat has to say which.** Headless `-p` cannot prompt, so a call outside the allow-list never runs; it used to arrive as a plain red Error, indistinguishable from a crash. `_DENIED_RE` in `chat_session` marks it and the panel renders it amber as "Not permitted". The match is on the CLI's own wording because nothing structured comes back — which is why bare `Permission denied` is deliberately **not** on the list: that is an ordinary EACCES from a permitted `Bash` call, and mislabelling it sends people to change a setting that was never in the way.
- **Interactive terminal**: `dangerously_skip_permissions` config option (default: **off**), and it reaches the terminal only — not the panel chat, not insights, not the listeners.
- **The chat asks over the wire the TUI asks over a TTY.** `chat_session._argv` passes `--permission-prompt-tool stdio` and `_spawn` sends the `initialize` control request — the same pair the Agent SDK's `canUseTool` rides, and without the handshake the CLI never asks (its own SDK bundle is the wire-format authority; the docs don't spell it out). A `can_use_tool` control_request becomes an approval card; `POST /api/chat/permission` answers it. Three details are load-bearing: an allow must hand back the **raw** input as `updatedInput` (the CLI schema-validates it, so the clipped display copy must never go); the deny message is worded to match `_DENIED_RE` so the eventual tool_result renders amber, not as a crash; and an unanswered card declines itself after `PERMISSION_TIMEOUT`, because a chat tab — unlike a TTY — may have nobody in front of it and a turn that can never end is worse. Rules still short-circuit (the CLI only asks where the TUI would have prompted), a CLI that rejects the flag at startup gets it dropped and the chat runs exactly as before, and `stop()` withdraws the card because a question the dead process asked can no longer be answered.
- **`AskUserQuestion` is a question wearing a permission request's clothes, and the answers ride back inside `updatedInput`.** It arrives as `can_use_tool` like any other ask, but a generic Allow hands the tool an empty answer sheet and the turn falls over — which is exactly what happened. The CLI's own permission component answers with `{...input, answers: {"<question text>": "<answer>"}}` (multi-select comma-separated; its bundle is the wire authority), so `question_spec` parses the questions into a card the panel renders as *the questions* — options, multi-select, free-text "other" — and `respond_permission` refuses to allow one with no answers. A malformed ask degrades to the ordinary permission card, and a skipped one denies with wording `_DENIED_RE` matches (`declined to answer`) so it renders amber, not as a crash. **And an unknown control request is answered, never dropped**: a `control_request` is a question the CLI is *waiting on*, so `_refuse_control` sends back an error response for any subtype the panel doesn't implement — the alternative is a turn that hangs forever on a feature shipped after this panel was written (`FAKE_CHAT_MODE=oddcontrol` refuses to move the turn until something comes back).
- **Background listeners (Assist, Automation)**: Do NOT use `--dangerously-skip-permissions`. Instead, tool permissions are granted via `/config/.claude/settings.local.json`, which pre-approves MCP, Bash, Read, Write, Edit, WebFetch, and WebSearch tools. This avoids root-user restrictions of the flag.
- **Project settings**: Written to `/config/.claude/settings.local.json` at startup by `setup_claude_settings()` in `run.sh`
- **Non-root execution**: Claude Code runs as UID 1000 (`claude` user) via a wrapper script at `/usr/local/bin/claude-run` that uses `su-exec`
- **`/data/.brain_env` has to be sourced before it is read, and "after" looks exactly like "never".** The `with-contenv` shebang reloads the s6 container environment and drops whatever `run.sh` exported, so that file is the only route an add-on option has into a background process. Sourcing it works; sourcing it *late* does not. `automation-listener.sh` set `MAX_TURNS="${BRAIN_AUTOMATION_MAX_TURNS:-10}"` sixteen lines above the source, so the alias kept the fallback for the life of the process — the real value landed afterwards under its own name and nothing read it again. `automation_max_turns` was pinned to 10 and `assist_max_turns` to 5 for every install, whatever the options said, and the only trace was the `MaxTurns:` line in the task log (`--max-turns 10` surfaces as `num_turns: 11` in the SDK result). Note what the failure is *not*: sourcing late still fixes anything used under its own `BRAIN_*`/`HOME` name, which is why `assist_tool_access` worked and the turn caps did not — only the **aliased** reads freeze. `brain-learn.sh` had it too, invisible because its fallbacks happened to equal the shipped defaults and the study watcher exports the vars anyway; a direct `/learn` from the terminal got the fallback. Same class as the `${VAR:-default}` bullet above, and the reason both fallbacks now equal `config.yaml`'s defaults: a fallback that disagrees with the shipped default is a second answer that wins exactly when nobody is looking. `TestBrainEnvIsSourcedBeforeItIsRead` checks the ordering in every script that sources the file, and reproduces the two orderings in a shell rather than describing them.
- **Listener speed**: Both listeners use `--max-turns` to limit agentic loops (defaults: 8 for Assist, 30 for Automation, from `config.yaml`; the in-script fallbacks match, and only apply if `/data/.brain_env` is unreadable). The assist path splices a cached area→entity map (controllable domains + Weather/People) into the system prompt so most voice commands skip lookup turns. With `assist_fast_mode` (default) the assist channel runs as a worker pool (`assist-worker-pool.py`): persistent `claude --input-format stream-json` processes per conversation plus a pre-warmed spare, falling back to one-shot spawns on any worker error

### Container Environment
- Base: Home Assistant Alpine Linux 3.24 (Dockerfile `ARG BUILD_FROM` default; `build.yaml` only applies to Supervisor < 2026.04)
- HOME: `/data/home` (persistent across restarts)
- Config: `/data/.config/claude`
- HA config: `/config` (read-write)
